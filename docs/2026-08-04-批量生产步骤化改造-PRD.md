## 1. 背景

「智能混剪」下有两个模式:单条精准混剪(手工做一条)和批量生产(自动做几十条)。

单条模式是 4 步向导,交互完整、配音链路通畅,已可正常产出成片。

批量模式的后端地基造得比单条更严谨 —— 输入锁定、内容指纹校验、租约调度、审计、不覆盖发布,全部到位。但存在两类问题:

- **功能上**:流水线缺「生成口播」这一环,导致所有成片都是无声的,而出厂闸门要求必须有配音,于是**一条都导不出来**。
- **体验上**:所有功能堆在一页长滚动里,界面上印着研发内部代号,和单条模式像两个不同的软件。

## 2. 问题定义(用户视角)

| # | 问题 | 用户实际遭遇 |
|---|---|---|
| P1 | 批量产不出成品 | 跑完整个流程,点「正式导出」,弹出一串英文报错,按成片条数重复 N 遍。零产出。 |
| P1b | 成片没有背景音乐 | 即便配音接通,成片仍是「只有人声、没有音乐」的半成品。分配器会给每条挑曲子,但渲染器根本不混音轨。 |
| P2 | 两个模式交互模型不一致 | 单条是 4 步向导,批量是一页平铺。学会一边不能迁移到另一边。 |
| P3 | 界面印着研发代号 | `Phase A/B/D/E`、「联合分配」「冻结」「代理」「静音视觉候选」等,用户看不懂在说什么。 |
| P4 | 页面里套页面的滚动 | 素材区是固定高度的内滚窗口,外面页面还能滚,鼠标滚轮容易滚错区域。 |
| P5 | 重要操作长得像脚注 | 归档/清理/重试/暂停/取消/重新分配全是一行带下划线的小字,看不清也点不准。 |
| P6 | 两个素材区名字太像 | 「项目素材池」和「批次素材池」并存,且出现位置随分支变化。 |
| P7 | 排版细节不一致 | 中文里混用英文半角逗号分号,同句可见(单条模式无此问题)。 |

## 3. 目标与非目标

### 3.1 目标

| # | 目标 | 对应问题 |
|---|---|---|
| G1 | 批量生产能真正导出**合格成片**:有配音、有字幕、有 BGM、有封面 | P1 P1b |
| G2 | 批量改成与单条同构的 4 步向导 | P2 P4 P6 |
| G3 | 界面文案全部人话化 | P3 P7 |
| G4 | 操作可发现性对齐单条模式 | P5 |

### 3.2 非目标(本次不做)

- 不改批量生产的后端数据模型和调度机制(快照冻结、租约、指纹、审计一律沿用)
- 不改单条精准混剪的任何**行为**(仅在骨架抽取时做无行为变更的重构)
- 不新增画幅、不改分配算法、不做配音以外的新能力
- 不做 A/B 两种布局并存或灰度开关

### 3.3 明确保留

- **工作台破格到 1440px 及 dvh 撑高** —— 为小屏监看有意设计,原样保留
- 现有的输入锁定语义(锁定后改项目内容不影响已锁定批次)
- 现有的不覆盖发布语义(正式产物永不被覆盖)

## 4. 目标用户与场景

**用户**:内容运营 / 短视频投手,懂剪辑和调色,不懂开发。

**典型场景**:手上有 8 份口播文案、40 条产品素材,需要在一个下午产出 40 条成片投放测试。要求每条配音一致、画面各异、画幅统一 9:16。

**关键诉求**:
1. 跑之前能确认「这次会出多少条、用哪些素材、什么配音」
2. 跑的过程中能看到进度,不用猜
3. 跑完能快速筛出不满意的,单独重做,不影响其他条
4. 导出失败要说清是哪条、为什么、怎么办

### 5.1 信息架构

```
┌─ 顶栏 ────────────────────────────────────────────┐
│  批次:[8月产品口播 ▾] [+新建]    画幅:[3:4|9:16|16:9]  状态徽标  │
├────────┬──────────────┬───────────────────────────┤
```

与单条模式共用同一套骨架(顶栏 / 步骤条 / 侧栏 / 主区),仅主区内容不同。

| 步骤 | 批量生产 | 对应单条 |

| 1 | 准备素材 | 导入素材 |
| 2 | 脚本与口播 | AI 智能创作 |
| 3 | 检查成片 | 预览调整 |
| 4 | 导出成片 | 导出渲染 |

### 6.3 第 2 步 · 脚本与口播 ★ 核心

**核心心智:一份脚本 = 一个独立创作单元。** 每份脚本有自己的份数、音色、语速和 BGM;同一份脚本的 N 条成片共用这些设置,**只有画面不同**。

单列卡片流:**每份脚本一张创作卡** → 全局输出设置卡 → 开始按钮 → 进度卡。

创作卡内部布局:

```
┌─ 脚本《春季新品·痛点开场》 ────── [✓ 已选]  15 秒  份数 [ 8 ] ┐
│  文案预览(前两行,可展开)                                      │
│  ─────────────────────────────────────────────────────── │
│  配音   服务商 [Qwen3 TTS ▾]   语速 ●━━━━━ 1.0x            │
│         音色 [女声·亲和] [男声·沉稳] [女声·活泼] … [搜索更多]   │
│                                              [试听]         │
│  ─────────────────────────────────────────────────────── │
│  背景音乐  自动分配(曲库 12 首)         [手动指定曲目 ▾]      │
└──────────────────────────────────────────────────────────┘
```

- **时长只读**:15 秒来自脚本自身设定,在第 3 步写脚本时已按档位约束过字数,这里不再提供修改
- **BGM 默认折叠为一行**:不展开就是自动分配,展开才手动挑
- **音量、淡入淡出整批统一**,放在下方的输出设置卡,不占创作卡版面

#### 6.3.3 背景音乐(每份脚本单独设置) ★ 新增

> **现状**:批量渲染器完全不处理 BGM。分配器已有「按 `成片序号 % 曲目数` 轮询挑曲」的逻辑,但曲目列表从未被传入,永远为空。单条模式的 BGM 能力是完整的(曲库扫描、响度归一化、增益、淡入淡出、与口播混音),本需求以复用该能力为前提。

**交互原则:默认零操作,想控制时才展开。**

用户往曲库文件夹里放满曲子,什么都不用选,系统自动给每条成片分配。需要控制曲风时,才手动指定曲目范围。

| # | 需求 | 优先级 |
|---|---|---|
| FR-S2-40 | 曲库为 `storage/bgm/` 文件夹,**与单条模式共用**,用户放文件即可,不需要在应用内逐首导入 | P0 |
| FR-S2-41 | **默认自动模式**:不做任何选择时,系统从整个曲库为每条成片自动分配 | P0 |
| FR-S2-42 | **可选手动模式**:每份脚本可手动指定 1–N 首,指定后只在该范围内分配 | P0 |
| FR-S2-43 | 分配须**均匀且可重现**:同一锁定版本重跑必须得到相同结果;曲目使用次数尽量平均,不出现某首用多次而某首没用过 | P0 |

### 6.5 第 4 步 · 导出成片

#### 6.5.1 交付物定义

**一条合格成片 = 视频 + 封面图,两个文件同名成对。**

| 文件 | 内容 |
|---|---|
| `<成片名>.mp4` | 画面 + 配音 + 烧录字幕 + BGM |
| `<成片名>.jpg` | 封面图 |

**合格判定**:

| 要素 | 是否必需 | 说明 |
|---|---|---|
| 配音 | **必需** | 缺配音一律不可导出,不提供任何旁路 |
| 字幕 | **必需** | 已烧录进画面;有配音时按配音时间轴对齐 |
| 封面 | **必需** | 随成片自动生成 |
| BGM | **必需** | 每份脚本至少 1 首;缺 BGM 在第 2 步即被拦下,不会进入生产 |

**存放结构**(现有实现已满足,本次只需补上入口与说明):

```
storage/projects/<项目>/批量成片/<批次>/
├── <产品编码>-<日期>-<脚本标识>-plan01-v1-export1.mp4
├── <产品编码>-<日期>-<脚本标识>-plan01-v1-export1.jpg
├── <产品编码>-<日期>-<脚本标识>-plan02-v1-export1.mp4
├── <产品编码>-<日期>-<脚本标识>-plan02-v1-export1.jpg
└── …
```

一个批次一个文件夹,视频与封面同名成对,可直接整个文件夹交付投放。

## 12. 数据库迁移影响

v1.2 的两项决策需要**新增批量迁移 v17**:

| 表 | 新增字段 | 用途 | 对应需求 |
|---|---|---|---|
| `batch_scripts` | `targetDurationSec` | 项目脚本目录承接脚本自带的时长 | FR-S2-20a |
| `batch_script_snapshots` | `targetDurationSec` | 锁定时冻结各脚本的目标时长 | FR-S2-20c |
| `batch_productions` | `archivedAt` | 批次归档(空值表示未归档) | FR-G-01c |

> **有现成先例可照抄**:迁移 v9 就是同时给 `batch_scripts` 和 `batch_script_snapshots` 各加三列(`coverTitleJson` / `shotSetId` / `contentRevision`),本次照同样模式追加 `targetDurationSec` 即可,默认值 15。
>
> **上游还要补一处**:脚本草稿本身带 `targetDurationSec`,但 `syncProjectScripts` 同步进批量脚本目录时**没有把它带过来**(目前只带封面标题、分镜组、内容修订)。加列之外还需在同步逻辑里补上这个字段,否则新列永远是默认值。

**约束**:

1. 批量迁移必须走既有的**共享写锁 + 验证备份 + 审计**网关,不得放进旧核心表的 catch-and-continue 流程。
2. 已发布的 v1–v16 迁移**不得修改**,只能追加 v17。
3. `archivedAt` 必须是**独立于 `status` 的新维度**,不能塞进现有的批次状态枚举(`draft` / `running` / `partially_completed` / `completed` / `failed`),否则会破坏现有状态机。
4. 历史批次快照没有 `targetDurationSec`,读入时回落 15 秒,不得因此报错。

> 另需同步改造分配器:目前目标时长是**整批一个值**,需改为每条成片从自己的脚本快照读取。详见技术方案 §4.6。
