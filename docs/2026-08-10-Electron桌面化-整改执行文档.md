## R1 · 退出时间预算对齐（高）

### 现状

两侧预算互相冲突，繁忙退出时壳会在服务自己承诺的收尾窗口结束前就动手 TERM：

- **壳侧**（`desktop/service.ts:10-12`）：`SHUTDOWN_REQUEST_TIMEOUT_MS = 2_000`、
  `GRACEFUL_EXIT_TIMEOUT_MS = 8_000`、`FORCE_EXIT_TIMEOUT_MS = 2_000` → 约 10 秒后 KILL。
- **服务侧**（`app/api/shutdown/route.ts:4`）：`SHUTDOWN_TIMEOUT_MS = 15_000`。

问题出在 `lib/shutdown.ts` 的 `performGracefulShutdown`：

```ts
const stepTimeoutMs = Math.max(1, Math.floor(timeoutMs));
```

`timeoutMs` 被当成**每步**上限，而不是总预算。后面 scheduler.stop / waitForBatchTasks /
waitForFinalEdit / waitForFfmpeg / stopSidecar 五个步骤各自可以烧满 15 秒 → 最坏 75 秒。

空任务实机退出测得过，只是因为每步都秒回，掩盖了这个问题。

### 改法

1. `lib/shutdown.ts`：把 `timeoutMs` 改成**总预算**。开头算一次
   `const deadline = Date.now() + timeoutMs`，每步传入 `Math.max(0, deadline - Date.now())`。
   步骤顺序、`pendingTasks` 计数语义、`waitForStep` 的实现都不变——只换预算来源。
   注意 `stopControlledSidecar` 是最后一步，预算耗尽时它仍应被**调用**（spawn 后 unref，
   不需要等待），只是不再等它。
2. `app/api/shutdown/route.ts`：`SHUTDOWN_TIMEOUT_MS` 15_000 → **12_000**。
3. `desktop/service.ts`：`GRACEFUL_EXIT_TIMEOUT_MS` 8_000 → **20_000**，
   `SHUTDOWN_REQUEST_TIMEOUT_MS` 2_000 → **15_000**（请求本身要能等到编排返回，
   否则壳拿不到 `pendingTasks` 就盲等）。`FORCE_EXIT_TIMEOUT_MS` 维持 2_000。

改完的不变量：**壳的等待窗口永远严格大于服务端的总预算。** 把这句话写成
`desktop/service.ts` 里常量上方的注释，防止将来有人单独调其中一个数。

### 验收判据

- `scripts/graceful-shutdown.test.ts` 加一个用例：让 batch / finalEdit / ffmpeg 三个 wait
  各自永久挂起，断言 `gracefulShutdown({ timeoutMs: 300 })` 的**总耗时 < 600ms**
  （现在会是 ~900ms+），且返回 `stopped: false`。
- 本机可验。

## R2 · 导航封锁不再打断存量功能（高）

### 现状

`desktop/main.ts:333-339` 的注释白纸黑字：

```ts
// Electron's programmatic loadURL() does not emit will-navigate. Therefore
// the initial load needs no exception here; every renderer-initiated
// top-level navigation is denied, including same-origin navigations.
window.webContents.on('will-navigate', (event) => {
  event.preventDefault();
});
window.webContents.setWindowOpenHandler(() => ({ action: 'deny' }));
```

安全上正确，但打断了三个存量功能：

| 功能 | 位置 | 机制 |
|---|---|---|
| 导出 ZIP 包 | `app/projects/[id]/page.tsx:329` | `window.location.href` → 被 `will-navigate` 拒 |
| 导出 CSV 报表 | `app/projects/[id]/page.tsx:332` | `window.open` → 被 `setWindowOpenHandler` 拒 |
| 参考图看大图 | `components/ResultGallery.tsx:155` | `target="_blank"` → 同上 |

前两个的响应头都是 `Content-Disposition: attachment`
（`download/route.ts:72`、`export/route.ts:62`）。

这直接违反原规格第 278 行 Phase 1 验收里的「窗口里是现有工作台，**功能与浏览器版一致**」。

### 改法（不放宽安全面）

1. **`will-navigate` 改成同源放行、跨源仍拒。**
   复用 `desktop/ipc.ts:33` 已有的 `sameOrigin()` 逐项比对 protocol/hostname/port。
   **禁止 `startsWith('http://127.0.0.1')` 之类字符串判断**（原规格第 260 行）。

   > ⚠️ **必须用「从 `ipc.ts` 导出 `sameOrigin`、在 `main.ts` import」的做法，
   > 不要把它挪进新的共享模块。** 因为 `scripts/electron-shell-security.test.mjs:200-207`
   > 是靠 `braceBlock(ipc, 'function sameOrigin')` 在 `ipc.ts` 里定位这个函数并
   > 逐项校验它的实现的。挪走会让那 4 条断言直接失效——那才是真正的削弱。

   > 为什么这不是安全放宽：renderer 本来就能 `fetch` 同源任意路径，同源导航没有给它
   > 任何新能力。而 attachment 响应在 Chromium 里会被转成下载，页面根本不跳走——
   > ZIP 导出由此自动恢复，且 SPA 状态不丢。

2. **`setWindowOpenHandler` 同源改成 deny + 主动下载。**

   ```ts
   window.webContents.setWindowOpenHandler((details) => {
     if (sameOrigin(details.url, origin)) window.webContents.downloadURL(details.url);
     return { action: 'deny' };
   });
   ```

   仍然**不创建第二个 BrowserWindow**（生产代码里 `new BrowserWindow` 必须保持只有一处，
   这是 `scripts/electron-shell-security.test.mjs` 已锁定的不变量）。CSV 导出由此恢复。

3. **参考图 `_blank` 的行为差异要如实记录。** 经上面这条改动，桌面里点参考图会变成
   「下载该图片」而不是「新标签查看」。这是**已知行为差异，本次接受**——写进
   `MACOS.md` 的已知差异小节。若不接受，另开票做应用内灯箱，不塞进本次。

4. 不需要加 `session.on('will-download')`：Electron 默认就会弹系统保存对话框，
   这正是桌面应用该有的行为。**不要**去 `setSavePath()` 静默落盘。

### ⚠️ 这条会撞掉三条现有安全断言——照下表精确处理

`scripts/electron-shell-security.test.mjs` 的 E 段（`:210-213`）是按「无条件全拒」写死的。
R2 必须动它。**这是本次唯一一处「改测试」，所以要格外说清楚**——上游验收最反感的就是
用改测试掩盖缺陷，而这里是相反的情况：**旧断言锁住的是一个打断存量功能的实现，
新断言必须同样严格，只是换了不变量。** 三条逐一处理：

| 现有断言 | 为什么会挂 | 换成什么 |
|---|---|---|
| `:212` `assert.doesNotMatch(navigation.source, /\bif\s*\(/)`<br>（禁止 `will-navigate` 里出现任何 `if`） | R2 要加 `if (!sameOrigin(...))` | 改成断言该块**必须**调用 `sameOrigin(...)`、**必须**含 `event.preventDefault()`、且**不含** `.startsWith(` |
| `:213` `assert.match(main, /setWindowOpenHandler\(\s*\(\)\s*=>\s*\(\{ action: 'deny' \}\)\)/)`<br>（要求零参箭头直接返回字面量） | R2 要用 `(details) => {...}` | 改成用 `braceBlock` 取出 handler 体，断言**每条 return 都是 `action: 'deny'`**（即 `assert.doesNotMatch(block, /action\s*:\s*['"]allow['"]/)` 且至少一处 `'deny'`） |
| `:207` `assert.doesNotMatch(ipc, /\.startsWith\s*\(/)` | 不会挂（`ipc.ts` 结构不变） | 保持，**另外**对 `main.ts` 的 navigation 块加同款 `doesNotMatch` |

`:200-206` 那 4 条 `sameOrigin` 实现校验**一条都不许动**——只要照上面「从 `ipc.ts` 导出」
的做法，它们会原样通过。

### 验收判据

- 上表三条改完后 `node scripts/electron-shell-security.test.mjs` 全绿，且
  `new BrowserWindow` 仍只有一处、六项 `webPreferences` 断言未被触碰。
- 实机 CDP 复跑 `outputs/2026-08-10-electron-acceptance-electron-cdp.raw.log` 那套：
  **跨源导航仍 `blocked: true`**（这条必须保持），新增验证 ZIP 与 CSV 真的落盘。
- 本机可验。

**改完必须实机验证壳仍能连上 `http://127.0.0.1:<随机端口>`**——这是本条唯一的风险点。

## R7 · 撤掉「秒进」这个不实说法（中）

### 现状

`app/api/desktop/import-linked/route.ts:76` 串行逐条调 `registerLinkedSource`，
后者对每个文件做 ffprobe + **完整 SHA-256 顺序读**——`media-catalog.ts:122` 的注释
自己就写着「完整内容核验:顺序读取整个文件计算 SHA-256(V1 的正确性基准)」。

20 条 ≥2 GB 就是至少 40 GB 顺序读，装在一个阻塞 POST 里，全程无进度。**这不是「秒进」。**

**好消息是 UI 文案本来就是诚实的**：`BatchStepMaterials.tsx:299` 写的是
「从本机选择原片（不复制）」，`:140` 的反馈是「已登记 N 条原片（不复制原文件）」，
都没有承诺速度。**「秒进」只出现在原规格的说人话版**（第 42 行、第 135 行）。

### 改法

改全指纹算法属于领域改动（素材身份的正确性基准），**明确不在本次范围**。本次只做两件：

1. **改原规格第 42 行和第 135 行的措辞**，把「秒进」换成如实表述：
   「不复制、不占额外磁盘；首次登记需要完整读一遍做内容校验，大素材要等」。
   这份文档是对外的价值主张来源，不能留一个跑不出来的数字。
2. **`BatchStepMaterials.tsx` 补进度表达**：`linkedImportBusy` 现在只显示「登记中…」，
   改成「正在校验 N/M」。实现方式：**main 侧分批 POST（每批 1 条）**，累加计数后
   通过 IPC 返回渐进结果，**不改 `/api/desktop/import-linked` 的端点契约**。
   若分批带来的复杂度超出预期，退路是只改文案为「正在校验，大素材需要几分钟」，
   并在文档里记为待办——**不要**为了进度条去改端点或指纹算法。

本轮实现采用首选路径：main 侧每条原片单独调用既有端点，progress channel 只传递
`requestId/completed/total`，preload 校验后转发为 renderer 事件，UI 显示「正在校验 N/M」；
HTTP 输入/输出契约与 SHA-256 指纹算法均未改动。

### 验收判据

- 原规格第 42/135 行不再出现「秒进」。
- 导入 3 条中等素材时能看到计数推进。
- 真实的 20 条 ≥2 GB 实测属于「发版前置条件」，见下。

## R8 · Windows 停止脚本（改得了、验不了）

### 现状

`installer/windows/stop-installed.ps1:22` 对匹配路径的进程直接：

```powershell
& taskkill.exe /PID ([string]$process.ProcessId) /T /F | Out-Null
```

开始菜单的「停止」和卸载流程都调它（`installer/windows/CreativeStudio.iss`）。
**不先调 `/api/shutdown`**——在写数据库或落任务状态时会被直接砍断，
**正好抵消掉 Phase 0 的全部价值**。

更糟的是 `scripts/windows-installer.test.mjs:68-69` 把这个行为**锁成了通过条件**：

```js
assert.match(stop, /taskkill\.exe/);
assert.match(stop, /\/T \/F/);
```

这是典型的「测试适配掩盖真实缺陷」——上游验收挑得对。

### 改法

1. `stop-installed.ps1`：先尝试优雅停机——从 Electron 记录的服务地址
   （或 `storage/run/stack.json`）取端口，`Invoke-WebRequest -Method POST` 打
   `/api/shutdown`，有限等待进程自行退出；**超时后才**降级到现有的 `taskkill /T /F` 兜底。
   **脚本必须保持 UTF-8 with BOM**（PS 5.1 会误读 BOM-less 中文而解析失败）。
2. `scripts/windows-installer.test.mjs`：断言改成「**先**出现 `/api/shutdown` 调用、
   `taskkill /T /F` **只作为兜底分支**存在」，而不是断言强杀本身。

本轮实现由 Electron 在 `CREATIVE_STUDIO_DATA_ROOT/storage/run/electron-service.json`
受控记录 `version/origin/instanceId`，正常退出按 instance 清理；停止脚本先校验 loopback
origin 与 `/api/desktop/health` 返回的 instanceId 一致，再 POST shutdown 并有限轮询，
最后才对匹配安装路径的壳进程执行进程树兜底。未使用端口扫描或 `Get-NetTCPConnection`。

### 验收判据

- 静态测试（`node scripts/windows-installer.test.mjs`）本机可跑。
- **真机验证挂起**：需要 Windows x64 主机跑安装 → 起任务 → 开始菜单停止 →
  确认无 ffmpeg 孤儿、任务可恢复。在拿到主机前，这条在矩阵里标注为「未验证」，
  **不得宣称通过**。
