# 批量混剪「检查成片」预览：流式 + 可缓存 + 拖动手感（执行文档）

> 本文是 2026-08-25 会话的已批准执行计划留底，先写文档后执行；执行中如有实现偏差，回头同步本文。
> 需求来源：用户反馈——Windows 上在「检查成片」里**替换过视频之后再预览会很卡顿**，**拖进度条也卡**，
> 并且**拖动进度条时画面不跟着动**。
> 已确认的取舍：**代理（proxy）方案本轮不做，排后**。本轮只做「服务端流式 + 可缓存」与「客户端拖动手感」。

---

## 一、背景：诊断结论与实测证据

### 1. 素材本身对「拖动」是最坏情况（本轮不修，但决定了为什么其他两层必须修）

直接解 `storage/videos/*.mp4` 的 MP4 盒结构，实测（93 个文件）：

| 项 | 实测值 |
| --- | --- |
| 分辨率 / 帧率 / 时长 | 1248×1664、24fps、5.04s、121 帧 |
| **关键帧数** | **整段只有 1 个**（`stss` sync sample = 1） |
| 码率 / 体积 | 5–47 Mbps；单文件 3.2–28.6MB；**平均 13.9MB** |
| moov 位置 | `ftyp > free > mdat > moov`，**在文件尾**，非 faststart |
| 编码声明 | 大文件 `profile_idc=66`(Baseline) / `level_idc=40`(L4.0) |

两个后果：

- **整段一个 GOP**：拖到第 3 秒，解码器必须从第 1 帧连续解 72 帧 2MP 画面才能出图。每拖一格重来一次。
- **码率越级**：H.264 L4.0 的码率上限是 20/25 Mbps，实际到 47 Mbps。Windows 的 DXVA/D3D11 硬解对
  level 越界很敏感，容易拒收退回软解；macOS 的 VideoToolbox 宽容且快得多。这是「开发机没事、Win 用户卡死」
  的分水岭。**此推断来自编码参数，未在 Windows 机器上实测**，执行时不要把它当已验证结论写进代码注释。

### 2. 预览走原片，代理从未生效（本轮不修，排后）

- `lib/batch-production/preview.ts:70` —— 只有已 ready 的代理才用代理，`lutId` 为 null 时直接返回
  `kind: 'original'`。
- 实测本机库：`batch_proxy_cache_items` **空表**；501 条 `batch_asset_pool_items` 全是 `lutId: null`。
  → 预览一直在播原片。
- 代理规格（`lib/batch-production/proxy-executor.ts:19-31`）本身恰好是为拖动设计的（720p / faststart /
  固定 GOP 50 / CRF 26），但只有在准备页手动点「请求代理」才生成
  （`components/batch-production/BatchPreparationPanel.tsx:1091`），「检查成片」不会自动请求。

**本轮明确不动这一层。** 但本轮的缓存设计必须给它留好位置，见 §三-步骤 5 的「遗留约束」。

### 3. 服务端：热路径是全仓库唯一一个「同步全量读进内存」的媒体服务

`app/api/batch-production/preview/[assetId]/route.ts`：

- `serveFile`（23-88 行）用 `Buffer.alloc`（58 行）+ `fs.readSync`（61 行）把请求区间**一次性读进内存**。
  Chrome 的首个媒体请求是 `Range: bytes=0-`，等于把整个 28MB **同步**读进内存再返回，
  期间 Node 事件循环被阻塞。
- `Cache-Control: no-store`（72 行 / 84 行）→ 浏览器一个字节都不能复用。
- 对照：同仓库另外两个媒体端点早就是流式的——
  `lib/batch-production/project-asset-media-response.ts:25-99`（`createReadStream`，被
  `app/api/batch-production/assets/[assetId]/preview/route.ts` 使用）和
  `app/api/batch-production/batches/[id]/outputs/[planId]/media/route.ts`。
  **唯独热路径这条没用。**

### 4. 客户端：「拖动时画面不动」是代码明写的行为

`components/batch-production/BatchTimelinePreview.tsx`：

- `components/final-edit/preview-playback.ts:90`：
  `if (video.readyState < 2 || video.seeking || !video.videoWidth || !video.videoHeight) return false;`
  —— seek 中不画，故意保留上一帧。
- `BatchTimelinePreview.tsx:224`：`if (playing) loop(); else paint();` —— 暂停态只有
  `seeked` / `loadeddata` 才补一帧。
- 同步 effect（170-204 行）的依赖数组里放了 `slotClips`，而 `slotClips` 是 **144 行每次 render 新建的数组**
  → 该 effect **每次 render 都跑一遍** → 拖动时每 1/24 秒重写一次 `video.currentTime`，
  上一次 seek 还没完成就被顶掉，`seeked` 迟迟不触发。

三者叠加 = canvas 一直停在旧帧，松手才画一帧。素材越难 seek（§1），冻结窗口越长。

### 5. 「换过素材之后才明显变卡」的机制

- 双 slot 按片段**序号奇偶**分配（`components/final-edit/preview-playback.ts:15-22`）。
  替换 / 插入 / 删除会让后面所有片段的序号奇偶翻转 → 两个 slot 的 `src` 全变 → 之前下好的字节全作废。
- 叠加 `no-store` → 每次换 `src` 都要重新拉完整文件（14–30MB）。
- 叠加 moov 在尾 → 每次重载还要多一轮「先拉头、再拉尾」才拿到索引。

## 二、范围与红线

### 本轮做（两件事）

1. **服务端**：`preview/[assetId]` 路由改流式，并让浏览器能复用已下载字节（ETag + 条件请求）。
2. **客户端**：`BatchTimelinePreview` 的 seek 合流 + 上屏时机改造，让拖动时画面真的跟着动。

### 本轮明确不做

- 代理自动请求 / 预览走代理（排后，单独一轮）。
- 生成侧码率、GOP、faststart 治理（排后）。
- `outputs/[planId]/media/route.ts` 的第三套媒体服务合并（可选收尾，见 §五）。
- 单条混剪 `FinalEditPreview.tsx` 的同款改造（默认做，见步骤 9；如时间紧可拆出但必须在文档里记一笔）。

### 红线（沿用 `AGENTS.md`）

- `lib/batch-production/` **只从 `media-core/` 导入，绝不从 `final-edit/` 导入**。
  本轮服务端改动不引入任何 `final-edit` 依赖；客户端组件层引用
  `@/components/final-edit/preview-playback` 是既有约定，可以保持。
- 本机服务不得暴露公网 → 缓存头一律 `private`，**不许出现 `public`**。
- 日志不打印请求头、密钥、完整鉴权串。
- 迁移只能追加；本轮不碰任何 schema。

## 三、服务端：流式 + 可缓存

改动集中在 `app/api/batch-production/preview/[assetId]/route.ts` 与
`lib/batch-production/project-asset-media-response.ts`。

### 缓存策略的选型（先读这段，别自己改主意）

两条路都能消掉重复下载：

- **A. URL 版本化 + `immutable`**（缩略图现在的做法，`project-asset-media-response.ts:17-19`）。
- **B. 强 ETag + 条件请求**（本轮选这条）。

**选 B，理由**：预览响应的内容不只取决于 `contentFingerprint`，还取决于**代理是否已 ready**
（`resolvePreviewSource` 会在代理就绪后把同一个 URL 的内容从原片换成代理）。A 方案要求 URL 构造方
（`lib/batch-production/output-arrangement.ts:376`）把代理状态并进 token，而那里根本不知道代理状态——
这会给排在后面的代理工作埋一颗雷。B 方案由服务端在每次响应时自证内容身份，代理落地时天然正确。

代价是每次复用要走一次 304 往返。**这是可以接受的**：省掉的是 14–30MB 的 body，换来的是一个空响应。
若后续实测 304 往返仍是瓶颈，再把 `max-age=0` 调成 `max-age=600`（ETag 仍然兜底正确性），
不需要改结构。

### 步骤

**1. `lib/batch-production/project-asset-media-response.ts`：扩展成唯一的流式媒体服务**

在 `projectAssetMediaResponse` 上追加可选能力，**不改变现有调用方的默认行为**
（`assets/[assetId]/preview` 与缩略图路由现在的表现必须逐字节不变）：

- 新增可选入参（建议改成单个 options 对象，或在末尾追加可选参数，二选一，保持既有两个调用点可编译）：
  - `cacheControl?: string` —— 覆盖 `PROJECT_ASSET_MEDIA_HEADERS` 里的 `Cache-Control`。缺省保持
    `no-store, private`。
  - `etag?: string` —— **强 ETag**（带双引号的完整值，如 `"a1b2…"`）。传了才启用条件请求。
    注意：Range 请求不接受弱验证器，**不许发 `W/` 前缀**。
  - `onClose?: () => void` —— 在返回的读流 `close` 与 `error` 上各挂一次（用一次性哨兵保证只调一次）。
    给调用方释放资源用，见步骤 4。
- 条件请求处理（仅在传了 `etag` 时生效）：
  - `If-None-Match` 命中 → 返回 **304**，body 为空，头带 `ETag`、`Accept-Ranges: bytes`、
    `Cache-Control`；**不要**带 `Content-Length` / `Content-Range`。命中判断按 RFC 9110：
    `*` 或逗号分隔列表里有相等项即命中。
  - `If-Range` 存在且与 `etag` 不等 → **忽略 Range，退回 200 全量流**（不是 416）。
  - `If-Range` 与 `etag` 相等，或没有 `If-Range` → 按现有逻辑走 206。
  - 早退到 304 的分支必须 `fs.closeSync(fd)`，不能泄 fd。
- 现有的 416 分支、`O_NOFOLLOW`、`matchesProjectAssetFileIdentity` 校验一律保留。

**2. 新增 ETag 计算工具**

放在 `lib/batch-production/project-asset-media-response.ts` 或同目录新文件（导出纯函数，便于测试）：

```
buildMediaEtag(parts: string[]): string   // sha1(parts.join(' ')) → `"<hex>"`
```

要求：纯函数、无 IO、结果带双引号、同输入同输出。

**3. `preview/[assetId]/route.ts`：删掉自制 `serveFile`，改调共享实现**

- 整个删除 23-88 行的 `serveFile` 与 `mimeTypeFor`。mime 改用现成的
  `projectAssetMimeType`（`lib/batch-production/project-asset-media.ts:367-378`），它已覆盖
  `.mov` / `.webm` / `.avi` 并默认 `video/mp4`，是被删掉那份的超集，不要在路由里再写一份。
- 三个媒体分支（`original` 210 行、`original_pending_lut` 219 行、`proxy` 234 行）统一改为调
  `projectAssetMediaResponse`，传：
  - `cacheControl: 'private, max-age=0, must-revalidate'`
  - `etag: buildMediaEtag([...])`，输入项按分支拼：
    - 公共：`source.kind`、`poolItem.contentFingerprint`、`COLOR_PIPELINE_VERSION`、
      `PROXY_PROFILE_VERSION`、`poolItem.colorJson`（原始串即可，不必解析）
    - `original` / `original_pending_lut`：再加 `stat.size`、`stat.mtimeMs`
    - `proxy`：再加 `source.cacheItemId`、`stat.size`、`stat.mtimeMs`
  - 原有的 `X-Preview-Kind` / `X-Preview-Warning` / `X-Preview-Original-Online` 头**原样保留**
    （前端来源徽标依赖它们）。
- **`previewInfo=1` 的 JSON 分支（172-195 行）与所有错误 JSON 分支保持 `no-store`，一个字都不改。**
  它报告的是代理/在线状态，缓存了会骗人。

**4. 代理读取租约必须活到流结束（这条是正确性红线，别漏）**

现状 225-240 行：

```
const release = acquireProxyReadLease(source.cacheItemId, db);
try { … return serveFile(…); } finally { release(); }
```

同步全量读时这样是安全的（返回时字节已在内存）。**改成流式后就不安全了**：
`releaseProxyLease`（`lib/batch-production/proxy-cache.ts:438-448`）在引用归零时会调
`completePendingProxyDeletion(db, cacheItemId)` 直接删文件，而流还没读完。
Windows 上删除被打开的文件本就会失败/被拒，属于双重踩坑。

改法：把 `release` 交给步骤 1 的 `onClose`，并且**只在真正返回流响应时**这样做；
早退分支（文件不存在 → 404、304、416）仍要在返回前同步 `release()`。
建议在路由里包一个 `let released = false; const releaseOnce = () => { if (!released) { released = true; release(); } };`
每条出口都能安全调用。

**5. 遗留约束（写给排在后面的代理工作）**

代理落地后，同一个 `previewUrl` 的内容会从原片切成代理。步骤 3 的 ETag 输入里已经包含
`source.kind` 与 `source.cacheItemId`，**代理 ready 的那一刻 ETag 必然变化，浏览器会自动重新拉取**。
做代理时请勿把 ETag 简化成只依赖 `contentFingerprint`。

## 四、客户端：拖动手感

改动集中在 `components/batch-production/BatchTimelinePreview.tsx`，共享逻辑落在
`components/final-edit/preview-playback.ts`。

**6. 让同步 effect 不再每次 render 都跑**

`BatchTimelinePreview.tsx:144` 的 `slotClips` 每次 render 都是新数组，导致 170-204 行的 effect 每次
render 都执行。改成 memo：

```ts
const slotIndexA = slotPlan.clipIndexes[0];
const slotIndexB = slotPlan.clipIndexes[1];
const slotClips = useMemo(
  () => [
    slotIndexA == null ? null : sortedClips[slotIndexA],
    slotIndexB == null ? null : sortedClips[slotIndexB],
  ] as [BatchTimelinePreviewClip | null, BatchTimelinePreviewClip | null],
  [slotIndexA, slotIndexB, sortedClips],
);
```

`sortedClips` 已经是 `useMemo(…, [clips])`（108 行），所以播放头在同一片段内移动时 `slotClips` 引用稳定，
effect 只在 `bodyFrame` 变化时跑。依赖数组保持 `[activeClip, activeSlot, bodyFrame, frozenVideoTail,
playing, slotClips]` 不变即可，`react-hooks/exhaustive-deps` 不会报警。

**7. seek 合流：一次只允许一个在途 seek，最新目标获胜**

在 `components/final-edit/preview-playback.ts` 新增一个可测试的纯逻辑 + 一个薄封装：

```ts
/** 返回本次是否应当真的写 currentTime。seek 在途时一律不写，等 seeked 再补最新目标。 */
export function shouldIssueSeek(
  video: { seeking: boolean; currentTime: number },
  targetSec: number,
  toleranceSec: number,
): boolean;
```

在 `BatchTimelinePreview` 里用一个 `useRef<[number | null, number | null]>([null, null])` 记两个 slot 的
最新目标；同步 effect 里把 `video.currentTime = expected` 换成：

- 先写 `seekTargetRef.current[slot] = expected`；
- `shouldIssueSeek(video, expected, 1 / FPS)` 为真才真的赋值；
- 给两个 `<video>` 各挂一个**常驻**的 `seeked` 监听（挂在独立 effect 里，依赖为空，只在挂载时装一次），
  回调里读 `seekTargetRef.current[slot]`，若与 `video.currentTime` 差超过 `1 / FPS` 就补一次赋值。

效果：拖动 = 「最新目标获胜」，同一时刻只有一个在途 seek，`seeked` 能稳定触发。

**8. 上屏改用 `requestVideoFrameCallback`**

TypeScript 5.9.3 的 `lib.dom.d.ts:17719` 已带 `HTMLVideoElement.requestVideoFrameCallback` 类型，
不需要额外补丁。

改 207-230 行的上屏 effect：

- 若 `typeof video.requestVideoFrameCallback === 'function'`：
  - 用 rVFC 代替 `requestAnimationFrame` 循环。播放中在回调里 `paint()` 后再排下一次；
    暂停中排**一次**，seek 完成后新帧上屏会自然触发，画完即止。
  - rVFC 在**暂停状态下 seek 完成时也会触发**（新帧被提交合成），这正是拖动跟画面的关键。
- 否则回退到现有的 `requestAnimationFrame` + `seeked` / `loadeddata` 方案。
- **`seeked` / `loadeddata` 的 `paint` 监听两条路径都保留**——多画一次无害，少画一次就是黑屏。
- 清理函数里用 `video.cancelVideoFrameCallback(handle)`。

顺带收益：源是 24fps、屏幕通常 60Hz，rVFC 把 1080×1920 的 `drawImage` 从每秒 60 次降到 24 次。

**9. 拖动期间少做无用功**

- `seek()`（354-359 行）每次 `onChange` 都调 `stopPlayback()` → `pauseAllMedia()`。加个早退：
  已经处于「非播放且无在途 rAF / 无待触发音频定时器」时直接跳过 `pauseAllMedia()`。
- `synchronizePausedAudio`（309-317 行）每格拖动都 seek 口播 + BGM 两个 `<audio>`。
  暂停态音频根本不发声，改成 **debounce ~120ms**（用 ref 存 timer，组件卸载与 `togglePlayback` 起播前
  必须清掉，避免起播瞬间被一个迟到的 seek 打乱基线）。
- `<video preload="auto">`（373-374 行）**保持不动**：预载下一段是播放流畅的前提，
  真正的问题是重复下载，那由 §三 的缓存解决。

**10. 同款问题在单条混剪也存在，一并修**

`components/final-edit/FinalEditPreview.tsx` 有完全相同的两个缺陷：
依赖数组里的 `slotClips`（249 行）、以及 251-275 行的 rAF/`seeked` 上屏模型。
步骤 7 的 `shouldIssueSeek` 放在共享的 `preview-playback.ts` 里就是为了这里能直接复用。
按步骤 6/7/8 同型改造，注意它比批量版多了 `activeAsset` / `showSelectedMaterial` / `framing` 三个条件分支，
别把这些判断改丢。

### 人工验收（开发机可验的部分）

1. 打开「检查成片」→ DevTools Network 过滤 `preview/`：
   - 首次加载某素材 → 200/206，响应头含 `ETag` 与 `private, max-age=0, must-revalidate`；

4. 替换 / 插入 / 删除片段各一次，再拖动：不出现「越用越卡」。

- 重点确认：替换后再拖动的主观卡顿是否明显下降。
- **如果 Windows 上仍然明显卡**：说明瓶颈已经落到 §一-1 的素材本身（单关键帧 + 越级码率 + 软解），
  本轮改动已到边界，**下一轮必须做代理**。请把这个结论记回本文档，不要在本轮继续加补丁。

## 六、验收口径

- 服务端：`preview/[assetId]` 不再有任何 `Buffer.alloc` / `readSync` 全量读；
  代理分支的读取租约覆盖整个流生命周期；`previewInfo=1` 与错误响应仍是 `no-store`。
- 客户端：拖动进度条时 canvas 持续更新；同步 effect 不再每次 render 执行；
  同一时刻至多一个在途 `currentTime` 赋值。
- 缓存：同一素材的第二次加载走 304，不重新传输 body。
- 回归：播放、声画对位、字幕、封面、来源徽标（`X-Preview-*` 头）全部不变。
