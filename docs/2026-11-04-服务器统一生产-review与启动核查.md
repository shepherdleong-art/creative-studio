## 2. 已验证问题（按严重程度）

### P0-1 生产没有资源池配置入口，首次部署无法完成任何付费生成

**证据**

- [admission.ts](file:///i:/m7-studio/lib/media-core/execution/admission.ts#L47-L51) 在准入时要求 `execution_pools` 中存在对应池；缺失时返回 `pool_missing`。
- [legacy-media-execution.ts](file:///i:/m7-studio/lib/legacy-media-execution.ts#L42-L74) 定义了 `configureLegacyMediaProviderPool` 和 `ensureProviderPool`，但全仓库调用 `configureLegacyMediaProviderPool` 的只有 [legacy-media-execution.test.ts](file:///i:/m7-studio/scripts/legacy-media-execution.test.ts#L168) 等测试文件。
- [pools.ts](file:///i:/m7-studio/lib/media-core/execution/pools.ts#L107-L142) 的 `upsertExecutionPool` 也只被 `scripts/execution-*.test.ts` 调用；`app/api/` 下没有任何写入 `execution_pools` 的路由。
- [verify-provider-budgets.mjs](file:///i:/m7-studio/scripts/team-server/verify-provider-budgets.mjs#L63-L76) 只做结构化校验并写报告，不写数据库。
- 全新数据根没有任何 `execution_pools` 记录。

**触发条件**：管理员完成首次登录和供应商配置后，提交图片、视频、普通脚本、详情页脚本、TTS 或画布任务。

**影响**：所有需要资源池的执行操作会以 `pool_missing` 被拒绝，或进入 `deferred` 等待（员工端显示“资源池未配置”），无法产生任何正式结果。也就是说，服务器可以登录、可以看页面，但**不能生产**。这不是“某个供应商没配好”，而是统一执行设施没有生产侧接线。

**最小修复**：

1. 增加一个仅管理员可用的受控 CLI 或 API，用于 `upsertExecutionPool`，要求显式传入 `poolKey`、容量、启用状态和 mapping snapshot。
2. 为常用链路建立默认池：`llm:remote`、`tts:remote`、`media:remote`，以及旧图片/视频按 `baseUrl + apiKey` 指纹生成的 `media-upstream:*`。
3. 在供应商保存/启用时同步校验池映射；没有可信容量或定价时 fail closed，但必须有管理员可见的配置入口。
4. 增加“全新数据根 → 初始化管理员 → 配置供应商 → 配置池 → 用假供应商完成一次提交”的端到端测试。现有测试在测试代码里自行 `upsertExecutionPool`，不能证明首次部署可生产。

### P0-2 一次性初始/重置凭据可以重复登录

**证据**

- [service.ts](file:///i:/m7-studio/lib/team-service/auth/service.ts#L188-L220) 的 `login` 只校验密码哈希、账号状态和凭据过期时间；成功登录后只创建 session，**没有消费凭据**。
- `mustChangePassword` 会话可以反复创建；`changeOwnPassword` 只要求当前密码匹配，并不会阻止同一凭据再次登录。
- 本轮用 release 自带 Node 和临时数据根做了运行验证：初始化管理员后，用同一初始凭据连续登录两次，第二次仍然成功，且两次都返回 `mustChangePassword=true`。

```json
{"firstMustChange":true,"secondLoginSucceeded":true,"secondMustChange":true}
```

**触发条件**：管理员初始化或重置账号后，初始凭据在用户改密前被他人获取；或者用户在多个浏览器/设备上重复使用同一初始凭据。

**影响**：违反需求共识与验收矩阵 A03 的“一次性凭据不可重放”。攻击者可以在用户改密前建立多个长期会话，或反复登录。登录页文案“一次性凭据只能使用一次”与实际行为不一致。

**最小修复**：在 `login` 成功创建 `mustChangePassword` 会话的同一事务中消费凭据，例如把 `credentialExpiresAt` 置为当前时间，或新增 `credentialConsumedAt` 并在登录条件中检查。`changeOwnPassword` 仍然用当前密码哈希校验，不受影响。补一个回归测试：第一次登录成功，第二次登录返回 `invalid_credentials`，原会话仍可完成改密。

### P0-3 服务端软删除只覆盖 6 条 DELETE 路由，其余路由仍硬删除并 unlink

**证据**

- [route-wrapper.ts](file:///i:/m7-studio/lib/team-service/route-wrapper.ts#L171-L178) 的 `SERVER_SOFT_DELETE_ROUTES` 只有：
  - `/api/projects/[id] DELETE`
  - `/api/images/[id] DELETE`
  - `/api/canvas/[id] DELETE`
  - `/api/batch-production/batches/[id] DELETE`
  - `/api/batch-production/scripts/[scriptId] DELETE`
  - `/api/projects/[id]/script-studio/scripts/[scriptId] DELETE`
- 其他资源 DELETE 仍然进入原 handler：
  - [scene-references/[id]/route.ts](file:///i:/m7-studio/app/api/scene-references/%5Bid%5D/route.ts#L34-L42) 直接 `DELETE FROM scene_references`。
  - [shot-sets/[id]/route.ts](file:///i:/m7-studio/app/api/shot-sets/%5Bid%5D/route.ts#L168-L181) 调用 `deleteShotSet`。
  - [video-reference-assets/[id]/route.ts](file:///i:/m7-studio/app/api/video-reference-assets/%5Bid%5D/route.ts#L70-L105) 直接 `DELETE FROM video_reference_assets` 并 `fs.unlinkSync`。
- 这些路由都被 `withTeamRoute` 包装，但在 server 模式下没有被软删除拦截，handler 会真实执行。

**触发条件**：员工在 server 模式删除场景参考图、分镜组、视频参考素材，或其它未列入白名单的资源。

**影响**：违反需求共识 §4“server 模式 DELETE 改为软删除”和验收矩阵 F05。可能删除仍被任务、成片或导出引用的文件；回收站里看不到，也无法恢复；与“删除不等于取消已提交任务、任务依赖文件保留”直接冲突。

**最小修复**：不要只维护 6 条白名单。把所有资源 DELETE 路由纳入统一软删除策略，或在 `withTeamRoute` 中对 `method === 'DELETE' && policy.category === 'resource'` 默认软删除，只有管理员永久清理才允许物理删除。物理清理必须先做跨模块引用、在途任务、备份 pin 检查。每条 DELETE 路由补一个 server 模式测试。

### P0-4 服务端启动没有恢复批量生产与详情页脚本；生成的 server 环境也没有启用画布/详情页脚本

**证据**

- [runtime/index.ts](file:///i:/m7-studio/lib/team-service/runtime/index.ts#L51-L61) 的 server 模块列表只有：成片剪辑、普通第三步脚本、创作画布、旧图片/视频。**没有批量生产，也没有详情页脚本（script-studio）**。
- [instrumentation.ts](file:///i:/m7-studio/instrumentation.ts#L29-L37) 在 server 模式直接 `return`，不会调用 `startBatchSchedulerAfterReadiness()` 或 `startScriptStudioSchedulerAfterReadiness()`。
- 批量调度器只会在打开批量工作区等 API 时懒启动，例如 [workspace/route.ts](file:///i:/m7-studio/app/api/batch-production/batches/%5Bid%5D/workspace/route.ts#L27-L29)；重启后如果没有人打开批量页面，排队/运行中的批量任务不会恢复。
- 详情页脚本同样依赖 API 懒启动，[tasks/route.ts](file:///i:/m7-studio/app/api/projects/%5Bid%5D/script-studio/tasks/route.ts#L171-L176)，而 [script-studio/bootstrap.ts](file:///i:/m7-studio/lib/script-studio/bootstrap.ts#L79-L85) 明确要求 `CREATIVE_STUDIO_SCRIPT_STUDIO_ENABLE_SCHEDULER=1`，否则抛错。
- [generate-config.mjs](file:///i:/m7-studio/scripts/team-server/generate-config.mjs#L227-L237) 生成的 `app.env` 没有 `CREATIVE_STUDIO_SCRIPT_STUDIO_ENABLE_SCHEDULER`，也没有 `CREATIVE_STUDIO_CANVAS_ENABLE`。本轮实际生成临时 `app.env` 确认只有 9 个键，均不含这些开关。
- [creative-canvas/bootstrap.ts](file:///i:/m7-studio/lib/creative-canvas/bootstrap.ts#L100-L108) 在功能开关关闭时直接返回 `null`，因此部署后画布入口不会启用。
- [team-instrumentation.test.ts](file:///i:/m7-studio/scripts/team-instrumentation.test.ts#L57-L67) 明确断言 server 模式 `batchSchedulerStarted: false`。这说明本地测试通过是因为测试接受了这个行为，而不是覆盖了生产恢复。

**触发条件**：服务器重启、维护更新、或首次部署后员工提交批量/详情页脚本任务。

**影响**：违反技术方案 §2“模块恢复注册包含批量、详情页脚本，不能等员工打开页面才恢复”和验收矩阵 R01/Q08。批量任务在重启后可能长期停留；详情页脚本在默认部署中完全不会执行；画布默认不可用。需求共识要求首版覆盖四类模块（常规五步、批量、详情页脚本、创作画布），当前 server 组合根并没有做到。

**最小修复**：

1. 为批量生产和 script-studio 各做一个 `ExecutionModuleLifecycle`，把 `registerRecovery / recover / start / drain` 接入 `startTeamServiceRuntime`，放在 owner、schema、恢复之后启动。
2. 在生成的 `app.env` 中显式写入 server 需要的开关：`CREATIVE_STUDIO_SCRIPT_STUDIO_ENABLE_SCHEDULER=1`、`CREATIVE_STUDIO_CANVAS_ENABLE=1`（如果首版要交付画布），并把这些开关纳入部署配置的显式字段，而不是让安装脚本硬编码。
3. 补“服务重启后无人打开页面，批量/详情页脚本仍恢复”的 L1/L2 测试；不要再用 `batchSchedulerStarted=false` 当作 server 预期。

3. 先在两台员工设备上验证：安装/解压、登录、上传、下载、退出、断网、升级、回滚。当前只有测试 fixture，不是正式包。

## 3. 首次启动说明（从现有 release 开始）

> 这一节只解决“怎样把现有 release 启动到可登录”。它**不代表生产可上线**：登录后仍会撞上 P0-1（没有资源池配置入口）、P0-4（模块未启用/未恢复）等问题。
> 下面所有 `<...>` 都是必须替换的现场值；不知道的值请先向网络/运维负责人确认，不要猜证书、账号、端口或 CIDR。

### 3.1 先准备什么

1. **一台 Windows Server**，已安装 Windows Server，管理员可通过远程桌面登录。`10.20.16.165` 只是远程桌面里看到的地址候选，**不代表已经配置 HTTPS 入口**。先在服务器上执行：

   ```powershell
   Get-NetIPAddress -AddressFamily IPv4 | Format-Table IPAddress,PrefixLength,InterfaceAlias
   # 先记下你准备使用的 HTTPS 入口端口、app 回环端口和 LiteLLM 回环端口，再替换下面的变量
   $entryPort = '<待填写>'
   $appPort = '<待填写>'
   $liteLLMPort = '<待填写>'
   Get-NetTCPConnection -State Listen | Where-Object { $_.LocalPort -in $entryPort,$appPort,$liteLLMPort } | Format-Table LocalAddress,LocalPort,OwningProcess
   ```

   确认员工网段能访问哪个地址、443/自定义入口端口是否被 IIS 或其他程序占用。

2. **证书和私钥**：必须是员工电脑信任的证书，证书 SAN 必须覆盖你准备使用的域名或 IP。
   - 如果使用 `https://10.20.16.165`，证书必须包含 IP SAN `10.20.16.165`。
   - 如果公司证书只签了 DNS 名，请使用该 DNS 名作为 origin，不要用 IP 强行打开，也不要在浏览器里跳过证书警告。
   - `install.ps1` 不会生成自签证书，也不会修改员工电脑的证书信任。

3. **服务账号**：只接受无口令 gMSA（`DOMAIN\name$`）或 `NT AUTHORITY\NetworkService` / `NT AUTHORITY\LocalService`。不要用普通域账号+密码。
   如果使用 `NT AUTHORITY\NetworkService`，要确保它能读取证书/私钥和 release 目录；install 只给 deploymentRoot/dataRoot/backupRoot 授权，证书若在管理员私有目录需要额外授权。

4. **三个互不重叠的目录**：部署根、数据根、备份根。数据根必须是空目录或不存在；备份根不能放在数据根或部署根里面；三者都不能放在旧工作台数据目录里。

5. **一个可用的 HTTPS origin**：形如 `https://<域名或IP>` 或 `https://<域名或IP>:<端口>`，不能带路径、查询参数或账号密码。

6. **releaseId**：打开服务器上的 `release-manifest.json`，读取 `releaseId`。本机同版本包的值是 `team-server-0.7.1-3b84378`，服务器副本要以实际文件为准。

### 3.2 校验 release 包

在服务器上以管理员身份打开 PowerShell：

```powershell
$releaseRoot = 'E:\CreativeStudio\deploy\releases\<releaseId>'
& "$releaseRoot\runtimes\node\node.exe" "$releaseRoot\service\probe-team-server.mjs" --release "$releaseRoot"
```

这条命令只读：校验 manifest、SQLite/sharp 原生模块、FFmpeg/FFprobe、Caddy、Python/LiteLLM 和管理 CLI。退出码不是 0 就不要继续安装。

如果包还保持在 `E:\CreativeStudio\team-server-release-3b84378`，先按 3.3 移动到 `releases\<releaseId>`，因为 `generate-config` 只认 `<deploymentRoot>\releases\<releaseId>`。

### 3.3 目录与部署配置

下面的目录名只是示例，必须按现场确认后替换：

```powershell
$deploymentRoot = 'E:\CreativeStudio\deploy'   # 待确认
$dataRoot       = 'E:\CreativeStudio\data'     # 待确认，必须空
$backupRoot     = 'E:\CreativeStudio\backups'  # 待确认
$configPath     = 'E:\CreativeStudio\deployment.json'
$preflightDir   = 'E:\CreativeStudio\preflight'

New-Item -ItemType Directory -Force $deploymentRoot, $dataRoot, $backupRoot | Out-Null

# 数据根必须为空；如果有内容，停止并换一个空目录
Get-ChildItem -Force $dataRoot

# 把现有包移动到 deploymentRoot\releases\<releaseId>
$releaseId = (Get-Content 'E:\CreativeStudio\team-server-release-3b84378\release-manifest.json' -Raw | ConvertFrom-Json).releaseId
New-Item -ItemType Directory -Force "$deploymentRoot\releases" | Out-Null
Move-Item 'E:\CreativeStudio\team-server-release-3b84378' "$deploymentRoot\releases\$releaseId"
$releaseRoot = "$deploymentRoot\releases\$releaseId"
$releaseId
```

创建 `deployment.json`。下面是一份字段完整的模板；**所有尖括号占位符都要替换**：

```json
{
  "schemaVersion": 1,
  "deploymentId": "<部署ID，例如 studio-prod>",
  "releaseId": "<release-manifest.json 里的 releaseId>",
  "deploymentRoot": "E:\\CreativeStudio\\deploy",
  "dataRoot": "E:\\CreativeStudio\\data",
  "backupRoot": "E:\\CreativeStudio\\backups",
  "oldRoots": [],
  "appPort": "<待填写：未被占用的回环端口，填数字>",
  "liteLLMPort": "<待填写：另一个未被占用的回环端口，填数字>",
  "servicePrefix": "CreativeStudio",
  "enableLiteLLM": false,
  "origin": "https://<证书匹配的域名或IP>",
  "serviceAccount": "NT AUTHORITY\\NetworkService",
  "certificate": {
    "certPath": "<证书绝对路径>",
    "keyPath": "<私钥绝对路径>"
  },
  "allowedNetworks": ["<员工网段CIDR，例如 10.20.16.0/24>"],
  "stopTimeoutSeconds": 240
}
```

说明：

- `appPort` / `liteLLMPort` 必须是 127.0.0.1 上未被占用的两个不同整数端口；把尖括号占位符替换成数字，不要保留字符串。它们不是 443，也不对员工开放。
- `enableLiteLLM=false` 表示不安装公司网关服务；外部供应商仍可在 `/settings` 配置。若设为 `true`，还必须准备 `<deploymentRoot>\config\litellm\config.yaml`，install 不会替你创建这个文件。
- `oldRoots` 没有旧数据根就填 `[]`；如果有旧工作台路径，填进去，预检会检查新旧目录不重叠。
- `allowedNetworks` 必须是明确的 CIDR，不能用 `0.0.0.0/0`；只填员工实际网段。
- `origin` 必须与证书、员工实际打开的地址完全一致。**不要**用 `http://`，也不要用 `https://127.0.0.1` 给员工访问。

### 3.4 预检

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File "$releaseRoot\service\preflight.ps1" `
  -ConfigPath $configPath `
  -OutputDirectory $preflightDir
```

预检只读，会生成 `preflight-report.json`。它会检查：

- 新根目录是否存在（所以 3.3 要先创建空目录）；
- 新旧目录是否重叠；
- app/litellm 端口是否被占用；
- 磁盘、内存、GPU、网络、当前账号对目录的 ACL。

预检通过不等于安装会成功：它不校验证书路径、release manifest、HTTPS 入口端口和真实服务账号 ACL。若报告里有 `DIRECTORY_MISSING`、`PORT_OCCUPIED`、`DIRECTORY_PERMISSION_INSUFFICIENT`，先修，不要继续。

### 3.5 安装（dry-run 然后 -Apply）

先 dry-run，核对解析出的根目录、服务名、端口：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File "$releaseRoot\service\install.ps1" `
  -ConfigPath $configPath `
  -DeploymentId '<部署ID>'
```

确认输出中的 `deploymentRoot/dataRoot/backupRoot/ports/services` 都对，再以管理员身份执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File "$releaseRoot\service\install.ps1" `
  -ConfigPath $configPath `
  -DeploymentId '<部署ID>' -Apply
```

`-Apply` 会：

- 生成 `deploymentRoot\service` 下的 Caddyfile、`app.env`、WinSW XML、`resolved-services.json`、网络计划；
- 创建/校验控制凭据；
- 设置 ACL；
- 创建只放行入口端口的防火墙规则；
- 安装并启动按 `servicePrefix` 生成的 App、Caddy 和可选 LiteLLM 三个 SCM 服务；
- 在安装前运行 release 原生探针。

它**不会**：

- 运行 `init-admin`；
- 修改员工电脑的证书信任；
- 创建 WinSW 日志目录（见 P1-3）；
- 创建每日备份计划任务。

### 3.6 检查服务状态

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File "$releaseRoot\service\status.ps1" `
  -ConfigPath $configPath `
  -DeploymentId '<部署ID>' -Apply
```

期望看到 app 的 `ready: true`。如果 `ready: false`，先看：

- `<dataRoot>\storage\logs\services\*.err.log`（如果目录存在）；
- Windows 事件查看器中的 WinSW/SCM 事件；
- `<dataRoot>\storage\logs` 下的应用日志。

如果 install 在启动服务阶段因为日志目录不存在而失败，可由管理员手动创建目录、授权，然后启动服务：

```powershell
New-Item -ItemType Directory -Force "$dataRoot\storage\logs\services" | Out-Null
icacls "$dataRoot\storage\logs\services" /grant "NT AUTHORITY\NETWORK SERVICE:(OI)(CI)M"
Start-Service -Name '<servicePrefix>App'
Start-Service -Name '<servicePrefix>Caddy'
```

此时不要直接重跑 `install.ps1 -Apply`：数据根可能已经非空，install 会以“非空且没有部署标识”拒绝。这只应作为 P1-3 修复前的现场绕过；正确修复应由 install 在启动前完成。

### 3.7 初始化首个管理员

`install.ps1` 不会建账号。用 release 自带的 Node 和安装生成的 `app.env` 执行：

```powershell
& "$releaseRoot\runtimes\node\node.exe" `
  --env-file="$deploymentRoot\service\app.env" `
  "$releaseRoot\app\scripts\team-server\init-admin.mjs" `
  --employee-id '<工号>' --name '<姓名>'
```

注意：

- `--env-file` 必须指向 install 生成的 `app.env`，里面包含 server 模式、数据根、部署 ID、固定端口和受信 origin。
- 命令会输出一次性的初始凭据；只显示一次，不要写入日志或聊天记录。丢失后用 `recover-admin.mjs` 走受控恢复。
- 如果提示“团队身份结构未就绪”，说明 app 还没完成首次迁移；等 `status.ps1` 显示 ready 后重试。

### 3.8 打开登录地址

在信任证书的员工电脑上打开：

```text
https://<origin 中的域名或 IP>[:端口]/team/login
```

必须与 `deployment.json` 的 `origin` 完全一致。比如配置是 `https://studio.example.com`，就不要用 `https://10.20.16.165` 或 `https://localhost` 打开；登录 POST 会因为 Origin 不匹配被拒绝。

首次登录：

1. 工号 + 初始凭据登录；
2. 页面进入“设置新密码”，至少 12 位；
3. 保存后进入 `/` 工作台。

### 3.9 登录后必须做的事

1. 管理员进入 `/settings` 配置供应商；公司网关用户还要准备 LiteLLM `config.yaml` 并确认 `enableLiteLLM`。
2. 管理员进入 `/team/admin/users` 创建员工账号；**每个新账号默认月度额度 0、个人并发 0**，必须点开“费用与并发”设置额度/并发，否则员工无法发起付费生成。
3. 检查 `/team/tasks` 与 `/team/errors` 是否能看到任务和错误。
4. 在修复 P0-1 之前，不要指望图片/视频/脚本/画布能真正执行：当前 release 没有资源池配置入口。

### 3.10 安全停止

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File "$releaseRoot\service\stop.ps1" `
  -ConfigPath $configPath `
  -DeploymentId '<部署ID>' -Apply
```

它会先调用应用的受控停机入口，再按依赖顺序停止 LiteLLM/Caddy。不要在开发流程里误触 `/api/shutdown`；server 模式下该端点已被 Caddy 阻断并返回 404。

正式员工端不是原型，也不是 `outputs/prototype-team-ui`。它是服务器 Web 应用本身；`Header` 在 server 模式显示“任务/错误”，并按角色显示“账号/供应商”。

### 4.2 管理端

管理端与员工端共用同一个 Web 应用和同一个登录页，没有独立的“管理端程序”或独立端口。

| 管理页面 | 实际入口 | 说明 |
| --- | --- | --- |
| 工号/角色/账号启停/成员额度与并发 | `/team/admin/users` | `TeamUsersPanel`，仅 admin 可进 |
| 供应商配置 | `/settings` | `settings/layout.tsx` 要求 admin |
| 全部任务 | `/team/tasks` | 管理员 API 可看全部；员工只看自己 |
| 全部错误/诊断 | `/team/errors` | 管理员可查看诊断 |
| 用量/CSV | `/usage` + `/team/admin/users` 的“导出本月 CSV” | `/usage` 只显示当前登录人；CSV 在用户页 |
| 公共资源发布 | 只有 `POST /api/team/public-resources` | 无管理页面 |
| 备份/发布/恢复/停止 | `backup.ps1` / `release.ps1` / `restore.ps1` / `stop.ps1` | 服务器上的管理员 PowerShell，不是 Web 页面 |
| 回收站/永久清理/维护屏障 | 只有 API | 无管理页面 |

管理员入口不是 `https://<origin>/team`（仓库没有 `app/team/page.tsx`）；登录后从 Header 的“账号”“供应商”“任务”“错误”进入。

### 4.3 之前的双端原型

- 启动方式：在**源码机**执行 `npm run prototype:team`，打开：
  - 员工原型：`http://127.0.0.1:3317/prototype/team?role=client&variant=A`
  - 管理原型：`http://127.0.0.1:3317/prototype/team?role=server&variant=A`
- 边界：原型使用 `outputs/prototype-team-ui/` 独立沙箱，不加载正式 layout、instrumentation、API、数据库或 worker；所有数据在内存里，刷新即重置。
- [page.tsx](file:///i:/m7-studio/app/prototype/team/page.tsx#L7-L9) 在 production 或未设置 `CREATIVE_STUDIO_TEAM_UI_PROTOTYPE=1` 时直接 `notFound()`，因此正式 server 包打不开这个路由。
- 结论：**原型没有接正式 API**。它是布局评审工具，不是员工端/管理端实现，也不能从服务器 release 启动。
