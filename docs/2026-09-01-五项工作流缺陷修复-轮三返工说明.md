## 1. R1（P3）补齐 `rowid` 决胜，并把假守护改成真守护

### 1.1 现象与证据

`lib/video-queue.ts:629` 仍是：

```sql
ORDER BY createdAt, id LIMIT 1
```

`scripts/video-queue-resume.test.ts:227-232` 插入的是 `resume-job-a` → `resume-job-b`，
**id 的字典序恰好等于插入顺序**，因此 `ORDER BY createdAt, id` 与 `ORDER BY createdAt, rowid`
结果完全相同——断言无法区分两者。

复核者把该测试复制成临时探针，只把插入顺序倒过来（先 `resume-job-b` 后 `resume-job-a`，
使 id 字典序与插入顺序相反），立刻露出真相：

```
AssertionError: PROBE: 先插入的应先领取
  actual:   'resume-job-a'    ← 实际按 id 领取
  expected: 'resume-job-b'    ← 按 rowid 应有的结果
```

同样的无鉴别力问题也存在于 pending 路径的断言（`scripts/video-queue-resume.test.ts:201-206`
用的是 `job-batch-1/2/3`，也是升序 id）。那处**代码是对的**，但测试同样退化不回来——
将来谁把它改回 `id`，测试不会变红。

### 1.2 要做的两件事

**（a）改代码，一行。**

`lib/video-queue.ts:629`（`claimNeedsCheckVideoJob` 内）：

```sql
-- 改前
ORDER BY createdAt, id LIMIT 1
-- 改后
ORDER BY createdAt, rowid LIMIT 1
```

`claimNextVideoJob`（`:587`）与 `lib/batch-production/prepare.ts:135` 已经是 `rowid`，**不要重复改**。
顺带把 `claimNeedsCheckVideoJob` 的函数注释补一句批内决胜口径，与 `claimNextVideoJob` 的注释对齐。

**（b）把两处断言改成有鉴别力的。**

`scripts/video-queue-resume.test.ts` 的两段（`:201-207` 与 `:227-232`），
把 job id 换成**字典序与插入顺序相反**的一组，例如：

- pending 路径：按 `job-batch-c` → `job-batch-b` → `job-batch-a` 的顺序插入，断言领取顺序为 c → b → a。
- needs_check 路径：按 `resume-job-b` → `resume-job-a` 的顺序插入，断言领取顺序为 b → a。

记得同步改 `providerTaskId` 的 `UPDATE` 语句和末尾清理状态的 `UPDATE ... WHERE id IN (...)` 里的 id。

在两段断言上方各留一行注释，写明**为什么 id 必须逆序**（"顺序 id 会让 `ORDER BY id` 与
`ORDER BY rowid` 结果相同，断言就退化成恒真"），避免下一个人"顺手"把 id 改回顺序命名。
