## 二、按时间顺序的报错与处理

### 1. git clone SSL 握手失败

- **报错**：`schannel: failed to receive handshake, SSL/TLS connection failed`
- **原因**：git 全局走 schannel，经本地代理（127.0.0.1:7897）时握手失败；curl 正常。
- **处理**：本仓库 `git config http.sslBackend openssl`，克隆与后续操作正常。

### 2. `npm ci` 第一次失败

- **报错**：`ffmpeg-static` 的 `install.js` 直连 GitHub `ETIMEDOUT 20.205.243.166:443`
- **原因**：postinstall 下载不读 npm 代理配置。
- **处理**：`HTTP_PROXY/HTTPS_PROXY=http://127.0.0.1:7897` 下重跑成功。

### 3. Electron 二进制缺失

- **报错**：`@electron/get` 的 undici fetch 不认代理环境变量，`fetch failed`
- **处理**：`ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ node node_modules/electron/install.js` 补齐。

### 4. LiteLLM 用 Python 3.14 装不上

- **报错**：`No matching distribution found for litellm==1.89.2`，1.83–1.89 各版本均 `Requires-Python >=3.10,<3.14`
- **处理**：winget 安装 Python 3.12.10 → 建 `.venv-litellm` → 装 `requirements-litellm.txt`（litellm[proxy]==1.89.2 + socksio），`litellm --version` 验证通过。

### 5. LiteLLM「打开失败」

- **原因**：当时仓库根缺 `config.yaml`（网关配置），任何启动路径都会跳过或失败。
- **处理**：用户放入 `config.yaml` 后在 4001 端口实测：健康检查通过、`/v1/models` 返回完整模型清单（seedance / seedream / image2 / nano-banana / kling 等）。

### 6. `start-windows.cmd` 打开的是浏览器而非桌面壳

- **原因**：该脚本原本是网页版启动器（dev server + 浏览器）；桌面壳源码启动脚本此前只有 macOS 版。
- **处理**：
  - 新增 `scripts/start-desktop-windows.ps1`（对齐 macOS `start-desktop.command`：依赖检查 → Electron 运行时检查 → 3000 端口提醒 → LiteLLM sidecar → standalone 构建检查 → 编译桌面壳 → 启动 Electron；支持 `-Rebuild`）。
  - `start-windows.cmd` 改调桌面版脚本；网页版入口保留为 `scripts/start-windows.ps1`。
  - 同步更新 `README.md`「Windows 快速启动」与 `AGENTS.md`。

### 7. 双击 `start-windows.cmd` 中文乱码

- **原因**：cmd.exe 按系统 ANSI（GBK）解析批处理，而文件是 UTF-8 且为 LF 换行（多行 `if/else` 块在 LF 下还会解析错乱）。
- **处理**：文件转为 CRLF，开头加 `chcp 65001 >nul`；用同结构测试批处理验证中文渲染与块解析正常。
- **注意**：`scripts/*.ps1` 必须 UTF-8 **带 BOM**（PS 5.1 按 ANSI 读无 BOM 中文会解析失败）。编辑工具会抹掉 BOM，两次都靠 `printf '\xef\xbb\xbf'` 前缀补回。

### 8. 「端口 4000 已被占用」导致设置页显示未启动

- **现象**：设置页「公司供应商运行环境：未启动 / LiteLLM 代理：不可用」。
- **原因**：4000 被旧环境 `H:\Creative Studio\` 的 litellm 占用；本项目按设计不接管陌生进程，不写 `stack.json`，状态页因此判未启动（判定逻辑：`lib/company-provider-runtime.ts`，需 stack.json + PID 存活 + 健康检查 200）。
- **处理**：用旧环境自己的 `scripts/stop-company-sidecar.ps1` 优雅停止（PID 48228），再用本项目 `start-stack.ps1 -SkipApp` 拉起受控代理（PID 68980），状态页转 ready。

### 9. `start-stack.ps1` 不支持复用健康实例

- **现象**：sidecar 已在运行时再次启动会报「端口 4000 已被占用……启动失败」（实为无害）。
- **处理**：给 `scripts/start-stack.ps1` 补复用逻辑（stack.json PID 存活 + 健康 200 → 提示复用并退出 0），与 `start-litellm.sh` 语义一致。company-provider-startup（8 项）、company-provider-runtime（10 项）测试全绿。
- **附带**：`litellm-config.example.yaml` 曾被误删，已从 git 恢复（测试与文档引用它）。

### 10. 生图 401 `Invalid token`（**当前唯一未决**）

- **报错**：`API error 401: {"error":{"code":"","message":"Invalid token ...","type":"new_api_error"}}`
- **定位**：绕过工作台与本地代理，直接拿 `config.yaml` 里的 key 请求网关 `https://llm-gateway-idc.linshimuye.com/v1/models`，返回**一模一样**的 `Invalid token`。
- **结论**：`config.yaml` 中的上游网关 Key 已失效（吊销/过期）。与 LiteLLM 环境、COS 均无关。
- **待办**：去公司网关（new-api）控制台重新生成令牌 → 替换 `config.yaml` 里 19 处 `api_key` → `scripts\stop-stack.ps1` 后重启 → 实测一次生图。

### 11. COS 已配置但运行中应用显示 `cosConfigured: false`

- **排查链**：
  1. `.env.local` 已有真实值；`COS_LIVE_TEST=1 node scripts/cos-media.test.ts` 真机上传+下载比对**通过** → 密钥本身没问题。
  2. 优雅重启应用后依旧 `false`。
  3. 查明：standalone `server.js` 不加载任何 `.env` 文件；桌面壳 `desktop/service.ts`  spawn 私有 Node 服务时只透传 `process.env`——**桌面/standalone 链路从来没有读 `.env.local` 的环节**（网页版 `next dev` 才有）。这是桌面链路的真实缺陷。
- **修复**：`desktop/service.ts` 新增 `loadEnvFile()`，启动服务时把 `<dataRoot>/.env.local` 注入子进程环境（显式环境变量优先，与 Next dev 语义一致；macOS 桌面壳同享此修复）。
- **验证**：重新编译桌面壳（`npm run build:desktop`），electron-shell-security / standalone-desktop-boundary / electron-phase234-contract 测试通过；重启后健康接口返回 `{"status":"ready","proxyAvailable":true,"cosConfigured":true}`。

### 12. 结果媒体下载偶发 `fetch failed`（ECONNRESET）

- **报错**：`Remote image/video ready but local download failed. Network error downloading http://store.vod-qcloud.com/... : fetch failed`
- **定位**：任务已成功（网关 Key 已恢复），失败在把结果图/视频从腾讯云 VOD 存储下载回本机。对照实验：curl 直连与走代理均 200；Node（undici）fetch 当时连续 `ECONNRESET`，稍后 5/5 成功，两个边缘 IP 也均正常——判定为 CDN 边缘节点间歇性重置，大体积视频传输更易命中。
- **佐证链路**：经 LiteLLM 代理（4000）发真实生图请求，返回 `litellm.AuthenticationError ... Invalid token`，证明 工作台 → 代理 → 网关 链路本身通畅，401 只出在上游认证。
- **修复**：`lib/gateway-media-url.ts` 的 `downloadGatewayMedia` 增加有限重试——仅对无 HTTP 状态码的网络层失败（连接/读取中断）重试，最多 3 次、退避 1s/2s；HTTP 状态错误、重定向上限、JSON 错误体不重试。`scripts/gateway-media-url.test.ts` 新增 3 个用例（瞬时失败后成功 / 持续失败有界放弃 / 确定性 HTTP 错误不重试），gateway-media-url、media-download-policy、media-transport 测试全绿。
- **注意**：桌面版跑的是 standalone 构建，lib 改动需 `npm run build` 重建后重启才生效。

### 13. 提交限流退避（429/5xx）

- **背景**：视频并发按项目隔离（默认 10），多项目并行时可能打满公司网关；原逻辑下提交被限流的任务打回 pending 会被立刻重新领走、快速耗尽 2 次重试。
- **修复**（`lib/video-queue.ts`）：
  - `isRateLimitedSubmitError` 识别提交阶段的 429 与 5xx；
  - 限流失败**不消耗 maxAttempts**，按 providerId 记冷却（30s/60s/120s 逐级退避），冷却期内 `claimNextVideoJob` 视同被闸门挡住（gated），worker 等待而不是反复撞墙；
  - 同一任务限流重排上限 5 次（`RATE_LIMIT_MAX_REQUEUES`），超过才标失败并注明"网关持续限流"；提交成功即解除该供应商的退避计数。
  - 冷却状态在内存中：进程重启只是提前结束冷却，任务不丢（pending 持久化在库）。
- **测试**：`scripts/video-queue-resume.test.ts` 新增限流用例（识别 429/5xx 排除 400、重排有界、最终失败信息、不消耗 maxAttempts），全绿。
