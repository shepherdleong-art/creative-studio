## 0. 已确认的决策

以下内容已经确定，实施时不再保留多选分支：

1. 脚本生成改为“服务端任务 + 状态查询”，HTTP 连接只是观察者，断开连接不能取消服务端任务。
2. 同一项目同一时间只允许一个脚本生成任务。相同 `generationId` 的重试返回原任务；不同 `generationId` 的重复提交返回当前活动任务，不重复调用模型。
3. 支持步骤切换和页面刷新恢复；本期不支持 Node/桌面应用进程重启后续跑。应用退出时必须取消并等待脚本任务结束，再关闭数据库。
4. Windows 免安装包保留现有 `node-runtime/`，新增 `python-runtime/`，其中预装 Python、LiteLLM 和全部传递依赖。
5. 免安装包不再携带 `.venv-litellm/`。终端用户侧不执行 `winget`、Python 安装器、`python -m venv` 或 `pip install`。
6. 本期不做自动下载 runtime，不做 macOS Python runtime，不改变 Inno Setup/DMG 安装包“不带公司 sidecar”的策略。
7. 源码开发环境继续支持现有 `.venv-litellm`。发布包中的专用 `start-windows.cmd` 必须显式传入 `-Portable`，`portable-manifest.json` 负责完整性校验；不能只凭某个 runtime 目录是否存在猜测模式。
8. 内网免安装包继续携带 `config.yaml` 和 `.env.local`。它们不得提交 Git，日志和自检不得输出密钥或完整鉴权串。
9. `python-build-standalone` 是 Astral 维护的第三方可再分发 Python 构建，不表述为 PSF 官方便携版。Windows 使用 `x86_64-pc-windows-msvc install_only_stripped` 基线构建。

## 工作流 A：脚本生成任务化与进度恢复

### A1. 当前问题

现有链路由客户端流式请求拥有任务生命周期：

1. `components/ScriptPanel.tsx:210` 在组件卸载时主动 abort。
2. `app/api/projects/[id]/script/route.ts:217-219` 把请求断连转换为服务端 abort。
3. 同一路由在流写入失败和 `ReadableStream.cancel()` 时也会 abort。
4. `lib/script-generation-control.ts` 只保存 `projectId + AbortController`，没有进度、结果和终态。
5. 新挂载的 `ScriptPanel` 只请求一次已完成的 `script_drafts`，无法发现进行中的任务。

因此，仅删除组件卸载清理仍不够：旧组件持有异步流，新组件无法接收旧组件后续的状态更新。

### A2. 本期保证边界

| 生命周期事件 | 行为 |
|---|---|
| 外层步骤切换导致组件卸载 | 任务继续；新组件挂载后查询状态 |
| 浏览器刷新或流断开 | 任务继续；重新查询状态 |
| 显式取消按钮 | 取消任务 |
| 同项目第二次提交 | 返回当前活动任务，不调用第二次模型 |
| 不同项目同时生成 | 允许并行，互不泄漏状态或取消权限 |
| Node 热重载/崩溃/桌面应用重启 | 本期不续跑；进程退出前尽量取消，重启后只显示已落库草稿 |
| 项目在生成中被删除 | 持久化前重验项目；不存在则进入 `failed`，稳定错误码 `project_deleted`，不得写入草稿或其他项目 |

### A3. 服务端状态模型

新建 `lib/script-generation-manager.ts`，由它拥有 AbortController、任务 Promise 和项目级互斥。状态使用以下固定字段：

```ts
export type ScriptGenerationState =
  | 'running'
  | 'succeeded'
  | 'failed'
  | 'cancelled';

export interface ScriptGenerationSnapshot {
  generationId: string;
  projectId: string;
  state: ScriptGenerationState;
  progress: ScriptGenerationProgress;
  draftId: string | null;
  error: { code: string; message: string } | null;
  cancellationReason: 'user' | 'shutdown' | null;
  startedAt: string;
  finishedAt: string | null;
}
```

管理器必须提供：

```ts
startScriptGeneration(input): {
  created: boolean;
  snapshot: ScriptGenerationSnapshot;
}
getProjectScriptGeneration(projectId): ScriptGenerationSnapshot | null
cancelScriptGeneration(projectId, generationId): boolean
beginScriptGenerationShutdown(): number
waitForScriptGenerationsIdle(timeoutMs: number): Promise<number>
```

固定规则：

- 注册项目占用必须发生在任何异步模型调用之前，利用单 Node 进程事件循环完成原子检查。
- 管理器必须是进程级单例（可用 `globalThis + Symbol.for(...)`），避免 Next 路由模块重载或不同服务端入口各自创建一套注册表；测试必须证明重复导入共享同一状态。
- 相同 `projectId + generationId` 重试返回原快照。
- 同项目已有其他 `running` 任务时返回该任务，并标记 `created: false`。
- 成功后保存 `draftId`；失败只保存脱敏的错误码和中文说明。
- 终态保留 10 分钟，供页面刷新后读取；活动项目索引在进入终态时立即释放，允许再次生成。
- 管理器另存项目的“最近任务”指针；项目无活动任务时，GET 在 10 分钟内仍能返回最近终态，过期后返回 null。
- 进度必须来自现有 `generateAndPersistScriptV3(..., { onProgress })`，不得用定时器伪造。
- 仅显式取消和进程停机使用管理器自己的 AbortController；不再向生成服务传递 `request.signal`。
- 后台 Promise 必须在管理器内部完整捕获成功、失败和取消并落入终态，不能产生未处理的 Promise rejection。
- `beginScriptGenerationShutdown()` 先把管理器切成“不再接受新任务”，再以 `cancellationReason: 'shutdown'` abort 全部运行任务；此后 POST 返回 503，直到进程退出。
- 用户 DELETE 使用 `cancellationReason: 'user'`。取消后的进度回调和迟到结果全部丢弃，不得把 `cancelled` 改回成功或失败。
- 现有服务在写草稿前必须保留 `signal.aborted` 门禁；管理器测试和服务测试都要覆盖“上游忽略 abort、稍后才返回”时不写草稿。
- 持久化前再次查询项目；若项目已删除，返回稳定领域错误 `project_deleted`，manager 记为 `failed` 且 `cancellationReason: null`。

### A4. HTTP 接口

新建 `app/api/projects/[id]/script-generation/route.ts`，不要继续把任务生命周期塞进现有草稿/模型路由。

该 route 固定声明 `export const runtime = 'nodejs'` 和 `export const dynamic = 'force-dynamic'`；本方案只面向本地常驻 Node/standalone 进程，不支持部署到请求结束后可冻结进程的 serverless 平台。

#### POST：启动或取得当前任务

- 请求体沿用当前生成参数，并要求非空 `generationId`。
- 新任务返回 HTTP 202：

```json
{
  "created": true,
  "generation": {
    "generationId": "客户端生成的 UUID",
    "state": "running"
  }
}
```

- 同一个 `generationId` 重试或同项目已有活动任务时仍返回 HTTP 202，但 `created` 为 `false`，并返回权威任务 ID。
- JSON 形状错误、项目不存在等可在启动前判定的错误使用 4xx，不注册任务；shot set、素材和供应商等由现有生成服务判定的领域错误进入任务的 `failed` 终态并由 GET 返回。
- 停机已经开始时返回 HTTP 503 和稳定错误码 `script_generation_shutting_down`，不得注册后台任务。

#### GET：查询项目当前/最近任务

- 返回 `{ "generation": null }`，或完整 `ScriptGenerationSnapshot`。
- 只能按路由中的 `projectId` 查询，不接受任意项目 ID 参数。
- 响应头设置 `Cache-Control: no-store`。

#### DELETE：显式取消

- 查询参数要求 `generationId`。
- 仅当该任务属于路由中的项目时才取消。
- 已终态任务幂等返回当前状态；不存在或跨项目返回 404。

现有 `app/api/projects/[id]/script/route.ts` 的 POST 只保留 `action: 'analyze'`；旧的非流式/流式 `generate` 和 `cancel` 全部分支、默认 `action='generate'` 及其 helper 一并删除。旧客户端误调生成或取消时返回 HTTP 410 与稳定错误码 `script_generation_endpoint_moved`，不得转发或暗中产生第二种任务生命周期。仓库中现有调用者迁移完成后，确定删除 `lib/script-generation-stream.ts`、`lib/script-generation-control.ts` 及对应两个旧测试。

为避免只靠正则检查 route，新建可注入依赖的 `lib/script-generation-route-handler.ts`：它实现 POST/GET/DELETE 的输入校验和响应映射，Next route 只负责注入真实 manager/数据库并转发。动态测试直接调用 handler，并使用受控异步执行器验证真实状态流转。

### A5. 前端行为

`components/ScriptPanel.tsx` 改为轮询任务状态：

1. 挂载时，在现有项目/草稿/模型/shot set 请求之外，并行 GET `script-generation`。
2. 发现 `running` 后设置 `generating=true`，每 1 秒查询一次。
3. 轮询使用组件自己的查询 AbortController；卸载只取消查询，不取消服务端任务。
4. POST 启动返回后，以服务端返回的 `generationId` 为准开始轮询。
5. `succeeded` 后停止轮询，重新加载草稿，按 `draftId` 选中结果。
6. `failed` 后显示服务端中文错误并允许重试。
7. `cancelled` 后恢复按钮状态，不显示失败弹窗。
8. “取消生成”调用 DELETE；不能通过 abort 查询请求代替服务端取消。

新增 `scripts/python-runtime-win-x64.lock.json`，必须提交以下真实值：

- schema version；
- Python 版本、python-build-standalone release、目标 triple；
- 官方 GitHub release 直链；
- 归档 SHA-256；
- LiteLLM 版本；
- 完整依赖锁文件 SHA-256；
- 构建脚本版本。

锁文件不得使用 `latest`、版本范围或空哈希。首次实施时从不可变 GitHub release 及其 `.sha256` 伴随文件取得摘要，写入锁文件后由第二人或独立 Agent 对照复核。

新增 `requirements-litellm-win-x64.lock.txt`：

1. 从当前已验证的专用 `.venv-litellm` 导出全部发行包的精确版本。
2. 用导出的锁文件在全新 staging runtime 中重新安装。
3. 重新执行 `pip freeze --all`，排序后必须与锁文件一致。
4. 安装阶段要求二进制 wheel；任何包尝试源码编译都使构建失败。

### B3. Runtime 构建脚本

新建 `scripts/build-python-runtime-windows.ps1`，仅供维护者构建分发包，终端用户不运行。脚本必须：

1. 硬校验当前平台为 Windows x64。
2. 读取 `python-runtime-win-x64.lock.json`。
3. 下载归档到 `.cache/python-runtime/`，下载后计算 SHA-256；不匹配立即删除本次缓存并失败。
4. 在仓库内独立 staging 目录解压，不覆盖现有 `python-runtime/`；`install_only` 归档顶层是 `python/`，须把该目录内容规范化为最终 `python-runtime/` 根结构，并硬断言 staging 解释器自带可运行的 `python.exe -m pip`。若精确归档不满足该断言，则判定锁定基线无效并停止发布，不得现场下载 pip 或换用系统 Python 补洞。
5. 先用完整锁文件执行 `pip download --only-binary=:all:` 下载全部 Windows x64 wheel 到临时 wheelhouse；为每个 wheel 记录文件名和 SHA-256。任何源码包或缺 wheel 都使构建失败。
6. 再使用 `pip install --no-index --find-links <wheelhouse>` 从该 wheelhouse 安装完整锁文件，证明安装阶段不依赖网络和浮动解析；安装完成后删除成品目录中的 wheelhouse。
7. 不调用 pip 生成的 `litellm.exe`；运行时入口只使用包内解释器加载 Python 模块。
8. 验证：

```powershell
python-runtime\python.exe --version
python-runtime\python.exe -c "from importlib.metadata import version; assert version('litellm') == '1.89.2'"
python-runtime\python.exe -c "from litellm import run_server; print('LiteLLM entrypoint OK')"
```

9. 用临时、无真实密钥的最小配置，通过包内 Python 执行 `scripts/start-litellm-proxy.py --config ... --host 127.0.0.1 --port <空闲端口>`，等待 `/health/liveliness` 成功后按 PID 停止；这一步同时验证 `run_server()` 确实消费 CLI 参数。
10. 暂时清除构建进程的代理和包索引环境，并通过防火墙或 Windows Sandbox 的断网环境重复 import 和健康检查，确认成品运行不下载依赖。
11. 写入 `runtime-manifest.json`，记录版本、平台、依赖锁哈希、wheel 哈希清单、构建时间和构建脚本版本，不记录机器用户名、绝对路径或密钥。
12. 生成第三方许可证清单。python-build-standalone 自带的许可证文件必须保留，Python 包许可证从安装元数据汇总。
13. 全部验证通过后，把旧目录重命名为同盘备份，再把 staging 重命名为 `python-runtime/`；任一步失败立即回滚，成功后才删除旧备份。不得先删除唯一可用 runtime。

Windows 构建存在 VC++ Runtime 依赖。发布前必须在未安装 Python、Node 和开发工具的干净 Windows 10/11 VM 或 Windows Sandbox 中运行 `python-runtime\python.exe`。若缺少 VC DLL，按 Microsoft 允许的 app-local 方式把所需 Redistributable DLL 与许可证放入 `python-runtime/`；不得把“请用户安装 VC++”留给同事。

### B4. LiteLLM 启动入口

新建 `scripts/start-litellm-proxy.py`：

```python
from litellm import run_server

if __name__ == "__main__":
    run_server()
```

这样避免 `litellm.exe` 内嵌构建机绝对路径，也避免 PowerShell `-c` 参数转义差异。

新增发布模板 `installer/windows/start-windows-portable.cmd`。装配时把它复制为成品根目录的 `start-windows.cmd`，它固定调用 `scripts/start-desktop-windows.ps1 -Portable`。源码仓库原有 `start-windows.cmd` 继续走开发模式。

模板的关键调用固定为：

```bat
cd /d "%~dp0"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "%~dp0scripts\start-desktop-windows.ps1" -Portable %*
exit /b %ERRORLEVEL%
```

`start-desktop-windows.ps1` 和 `start-stack.ps1` 新增 `-Portable` 参数并逐层显式传递。只要收到该参数，无论 manifest 是否存在，都不得降级为源码模式；随后必须校验根目录 `portable-manifest.json` 的 schema、模式 `windows-portable-v1` 和关键文件清单。manifest 缺失或无效即报告包损坏。

`scripts/start-stack.ps1` 的固定选择顺序：

1. 免安装模式下，必须校验 `python-runtime/python.exe`、`runtime-manifest.json`、Python 3.12.10、LiteLLM 1.89.2 和 manifest 中的关键文件哈希，然后执行：

```text
python-runtime\python.exe scripts\start-litellm-proxy.py
  --config config.yaml
  --host 127.0.0.1
  --port 4000
```

2. 免安装模式下，runtime 缺失、损坏或哈希不符时，不删除、不联网修复、不回退 `.venv-litellm` 或系统 Python；明确提示“免安装包不完整，请重新复制”，sidecar 失败但工作台其他功能继续启动。
3. 非免安装模式下，存在且验证通过的 `python-runtime/python.exe` 时可供维护者验证；否则使用源码开发环境的 `.venv-litellm/Scripts/litellm.exe`。
4. `start-stack.ps1` 永不自行创建 venv 或回退系统 Python；源码态需要创建/修复 venv 时，仍由 `start-desktop-windows.ps1` 的既有开发分支显式完成。

`scripts/start-desktop-windows.ps1`：

- 收到 `-Portable` 时进入免安装模式，禁止执行现有 venv 重建分支；manifest 缺失或损坏时同样禁止误走源码分支。
- 免安装模式下缺少 `node_modules`、Electron 或 standalone 产物时，不执行 npm 下载/构建，直接提示重新完整复制免安装包。
- 免安装模式收到 `-Rebuild` 时直接拒绝并提示由发布者重新生成免安装包；终端用户机器不得执行 Next 或 Electron 构建。
- 未传 `-Portable` 的源码态保留既有 venv 修复逻辑；源码目录是否碰巧存在 `python-runtime/` 不改变该规则。
- `scripts/start-windows.ps1` 的公司组件检测同时识别内置 runtime 和 venv，保持开发入口兼容。

`storage/run/stack.json` 继续记录受控 `litellmPid`，并新增运行时种类与实际解释器路径。不得记录命令行中的密钥。`scripts/stop-stack.ps1` 优先按状态文件 PID 停止，并校验可执行路径属于当前项目的 `python-runtime/` 或 `.venv-litellm/`；不得再仅凭 4000 端口杀死未知进程。

### B9. 共享盘发布流程

共享盘只作为分发源，不直接在其中运行工作台或做构建。

1. 在维护者本地仓库构建并验证 `python-runtime/`、standalone 和桌面壳产物。
2. 执行 `scripts/build-windows-portable.ps1 -OutputPath <本地新目录>`，由脚本按白名单装配成品；不得人工复制整个仓库，也不得在旧目录上边运行边覆盖。
3. 装配脚本必须先跑 runtime 和 payload 验证，并生成不含密钥值的 `portable-manifest.json`（文件相对路径、大小、SHA-256、版本）；任何关键文件缺失都不发布目录。
4. 发布脚本显式加入更新后的启动脚本、自检、使用说明、`config.yaml` 和 `.env.local`，但不复制 `.venv-litellm/`、`data/`、`storage/` 或其他开发/本机状态。
5. 将本地验收通过的新目录复制到共享盘的新版本目录，复制后用 manifest 复核文件完整性，再切换团队入口。
6. 从共享盘成品再完整复制到一个新的本地中文路径进行验收，避免只验证构建目录。
7. 断网后验证 Node、Python、LiteLLM 和应用启动；联网后验证实际公司供应商请求。
8. 验收通过后再将新目录切换为团队使用版本；旧版本保留一个发布周期用于回滚。

体积按实际成品测量记录。当前 `.venv-litellm` 约 495 MiB，最终是用 `python-runtime/` 替换它，不允许两套环境并存，因此总包体积预计与当前接近，而不是简单增加 400–500 MiB。

## 2. 推荐执行顺序

两个工作流可以独立合并和发布。按当前业务痛点，推荐：

1. 先完成工作流 B，发布真正开箱即用的 Windows 免安装包。

## 3. 完成定义

只有同时满足对应工作流的全部条件，才允许写“完成”：

### 工作流 A

- 自动化测试全部通过。
- 真实供应商验证步骤切换、刷新、取消、完成和重复提交。
- 无跨项目状态泄漏。
- 应用停机先处理脚本任务再关闭数据库。
