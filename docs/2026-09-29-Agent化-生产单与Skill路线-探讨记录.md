## 0. 结论速览

1. **设想**：只给「型号 + 共享盘路径 + 成片数量」，agent 自己找图、出图、出视频、写脚本，最后交付对应数量的成片。
2. **现状**：后半段（脚本、批量生产、统一审片）基本具备；卡在前半段。卡点不在 agent 本身，而在四件事：共享盘目录约定、图片 prompt 模板化、合格线、从 N 倒推备料（§3）。
3. **路线**：第一步做一个 **skill**，把判断交给 Claude / Codex，先供负责人自己探路；稳定下来的判断再逐步固化进工作台，做成生产单 / 流水线（§4、§5）。
4. **skill 跑得起来的前提**：一个窄命令行工具管动作、能写成规则的不交给判断、用阻塞式等待代替轮询、每个判定连同理由落账（§5.2）。
5. **v0 范围**：型号 + 路径 → 建项目 → 认图 → 出场景图和分镜图 → 判图 → 出视频，到此为止（§6）。
6. **下一步卡在一个问题**：共享盘里一个型号的目录长什么样（§8）。

## 1. 起点

用户原话大意：未来希望交给 agent 处理——只给产品型号、共享盘路径和成片数量，agent 自己去路径找对应的图片，自己生成图片、视频和脚本，最后得到对应数量的成片。用户自评「感觉想的很美好」。

与 08-15 的关系：08-15 的起点是「投喂一张需求表 → 全自动产出并导出」，这次把需求表具体化成了三个输入字段。08-15 的三条结论仍然有效：

- 目标是「自动跑完 + 集中审片」，不是全程无人干预；
- 图片 prompt 模板化是前提，不是优化项；
- 选片要闸门，不要排序器。

## 3. 四个真正的难点

这四件事和 agent 聪明与否关系不大，换成人来跑同样会遇到。

### 3.1 找图靠共享盘的目录约定

- 如果每个型号下面有固定子目录（白底 / 实拍 / 详情页切图），找图就是几十行确定性代码，用不着 AI。
- 如果命名因人而异，就得让模型识图分类；分错会一路传下去，而且很难被发现。
- **运行位置的坑（判断）**：按 [09-20 服务器方案](2026-09-20-轻客户端与服务器统一生产方案梳理.md)，生产集中在服务器。服务器上的工作台如果以后台服务方式常驻，看不到登录用户映射的盘符（如 Z:），须改用 UNC 路径，并给运行账号开共享盘读权限。
- 09-20 方案目前的前提是员工在客户端拖入文件上传，并没有让服务器直接读共享盘。agent 直读共享盘，是对那份方案的新增要求。

### 3.2 图片 prompt 模板化：仍是零进度（已核实）

本机库图片任务共有 22 个不同的 prompt，归成三种句式：

| 句式 | 开头 | 变体数 | 任务数 |
|---|---|---|---|
| A 分镜重绘 | 「图1 是待编辑分镜图…」 | 11 | 123 |
| B 场景生成 | 「基于图1生成新的…场景图」 | 2 | 31 |
| C 旧式场景改写 | 「保持图中…一致性不变」 | 6 | 22 |
| 其他 | — | 3 | 5 |

- 变体之间的差别，基本只在品类词（沙发 / 实木床 / 产品 / 床）和少量措辞。
- 新建项目的默认 prompt 写死成了床：`app/api/projects/route.ts:162`（场景）、`:163`（分镜）。库里那条「保持图中沙发的一致性不变…让客厅温馨舒适」，一看就是从床的默认句手改来的。
- 后果：agent 接一个柜子项目，要么照抄床的 prompt，要么自己编，两条路都会崩。
- 本次新增的落地选项：模板先写进 skill 跑起来，跑稳后再比照 `video_prompt_templates` 建表搬进工作台，供界面使用（§5.2）。

### 3.3 合格线，以及审片点放在哪

**对 08-15 的修正（已核实）**

08-15 §4.2 说「系统从未记录过任何一次否决」，当时只查了 `shots.reviewMark`（现在仍然全空，0/115）。实际情况是：

- 点「重新生成」会自动给原任务打 `jobs.reviewMark = 'rework'`：`app/api/jobs/[id]/regenerate/route.ts:23` 的 `markOriginal` 默认为 true，`components/ShotSetPanel.tsx:490` 和 `app/projects/[id]/page.tsx:322` 两处调用都显式传 true。
- 本机库里出图成功后被标 rework 的任务有 17 条：16 条是分镜图（按候选表核对），1 条是场景图。
- 视频任务早就有 `rejectedAt` / `rejectReason`（`app/api/video-jobs/[id]/route.ts:48-50`），但本机库只毙过 1 条，写了理由的 0 条。
- 图片任务的 `jobs.reviewMark` 只有标记，没有理由列。

结论：「哪张被毙了」有记录，「为什么被毙」没有。就算有理由字段，人也不会去填。

**审片点放在哪（判断，待用户确认）**

08-15 定的是「自动跑完 + 最后一次集中审片」。这次补算一笔账：

- 图便宜，视频贵。一张柜子嵌进床垫的分镜图如果拖到成片阶段才发现，视频的钱已经花掉了。
- N 条成片之间允许复用素材（见 §3.4），一个坏镜头可能同时进入好几条成片。
- 建议把人工那一眼前移到**分镜图出齐时**：扫一遍网格，大约一分钟，拦下的是最贵的浪费；成片阶段的统一审片保留，作为兜底。目标从「一次集中审片」变成「两次，各几分钟」。

### 3.4 成片数量要倒推整条链

- **同一条成片内**：每张原始分镜图只选一个视频版本；凑不够就报「素材不足」，不会拿同源版本凑数（`batch-allocation-v4`，见[批量生产模块参考](reference/批量生产模块.md)「同源互斥」）。
- **N 条成片之间**：素材可以复用，差异主要来自脚本和排片。
- 所以原图数量决定了单条成片能不能排出来；N 一大，瓶颈就从算力变成素材多样性——料不够，产出的是 N 条大同小异的片子，有平台查重风险。
- 因此要先倒推：要 N 条 → 需要几个分镜 × 几个版次 + 几份脚本 → 预计花多少钱；超预算就停下来问人。
- 这就是 08-15 的缺口 C（run manifest + 预算闸门）。这次确认，它是「成片数量」这个输入的必然配套，不是可选项。

## 4. 第一轮看法：生产单 + 流水线（判断）

- 这个设想更像「一张生产单 + 一条流水线」，而不是一个自己琢磨的 agent。大部分步骤是确定性的：套模板、按约定找图、按份数排批次。需要 AI 判断的节点（识图、写脚本、素材匹配）已经嵌在各自模块里。
- 让大模型编排整条链，等于在最需要稳定的地方加进随机性。agent 更适合处理异常：失败后是重试还是换模型、拿不准的时候问人。
- 08-15 §12 悬着的「agent 跑在哪」，对员工这一侧已经有答案：按 09-20 的服务器方向，员工看到的「agent」是服务器上的一张生产单（型号 + 路径 + 数量），而不是每人去跟 Claude 对话。

§5 调整了先后顺序：生产单不作废，但不是第一步。

## 5. 第二轮：Skill 路线（判断，倾向作为第一步）

用户追问：能不能写成一个 skill，把判断交给 Claude、Codex 这样的 agent？

结论：对**负责人自己用**来说，skill 比生产单更适合当第一步。

### 5.1 为什么先走 skill

1. **流程还没定型。** 哪张图该用、怎么判、出错了怎么办，现在都还在用户脑子里。写成 SKILL.md 就是一份能执行的 SOP，改一句话行为就跟着变，当天就能迭代。现在就写死成流水线代码，等于把还没想清楚的东西冻住。
2. **判断马上有人接。** Claude 和 Codex 都能看图。08-15 说的「候选图对照原图」不用另建闸门，agent 自己就能做。
3. **缺的数据顺手补上。** 让 agent 每毙一张都写理由，人最后审片时只管同意或推翻，「为什么被毙」的数据就攒起来了，还能顺带算出 agent 判得准不准。这和 08-15 被否掉的「两周人工标注」不是一回事：标注由 agent 来做，人只负责纠错。
4. **两边通用。** SKILL.md 这种格式 Claude Code 和 Codex 都认；本机 `~/.codex/skills` 已装有 guizang-ppt-skill，Claude 侧也装了同名 skill。
5. **正好是 08-15 §9.1「拿外部 agent 做逼真检验」的轻量版**：agent 卡住的地方，就是工作台 API 语义不够自解释的地方。

### 5.2 必备的四个配套

光有一份 skill 文档跑不起来，成败看这四件：

1. **skill 管判断，工具管动作。**
   - 工作台现在有 161 个 API 路由（08-15 时约 120 个），没有任何鉴权层：仓库根目录没有 `middleware.ts` / `proxy.ts`，`app/api` 下也没有鉴权检查。
   - 让 agent 自己用 curl 拼「上传 → 绑定 → 出图 → 轮询」，调错顺序、传错参数会是常态，还可能误调删除接口或 `/api/shutdown`。
   - 所以要配一个范围很窄的命令行工具：十来个子命令，每个对应一个决策点（参考 08-15 §9.2 列的十二个），共享盘只读，不开放删除和停机。
2. **能写成规则的，别交给 agent 判断。**
   - 目录约定、prompt 模板、景别白名单、份数换算都写死；不然同一个型号跑两次，结果都不一样。
   - prompt 模板可以先写进 skill 里跑，跑稳了再搬进工作台。这样「模板化」这个前提的启动成本就低多了。
3. **别让 agent 盯进度。**
   - 视频生成和批量渲染动辄几个小时。agent 每隔几分钟查一次状态，轮询记录会把上下文吃光，跑到一半就可能被压缩甚至断掉。
   - 工具里要有一个「一直等到这一步做完」的命令，只返回一段简短汇总。
   - 重试和断点恢复本来就是工作台调度器在管，不用 agent 操心。
4. **判断要落账。**
   - 每个判定连同理由都写回工作台：视频任务直接用现成的 `rejectReason`；图片任务要给 `jobs` 追加一个理由列（走 `CORE_DB_MIGRATIONS` 追加，不改已有条目）。
   - 这样能事后审计、能攒数据，agent 中途挂了也能照着记录接着跑。

**实用做法：联系表。** 把 20 张候选图和对应原图拼成一张带编号的大图给 agent 看，别让它一张张读 40 张。这样更省钱、更快，并排对比也判得更稳。仓库里的 sharp 和 ffmpeg 就能拼；视频同理，抽帧后拼成一张。

### 5.3 哪些判断能交给 agent

| 类别 | 内容 |
|---|---|
| 能交 | 从乱目录里认出白底图、实拍图、详情页切图；发现特写变成全景；产品明显走样、变色、logo 糊；直接采纳规划器推荐的脚本模板 |
| 交不出去 | 柜子嵌进床垫这类空间穿模，仍由人看（08-15 §5.1 已认定为输出端检测的弱项，不再另提方案）；视频运动到一半的变形——agent 在命令行里看不了视频，只能看抽帧拼图，这类问题大多会漏 |
| 审美取舍 | 四张场景图挑哪张：agent 能挑出不出错的，挑不出最好看的。偏好可以写进 skill，但替代不了人的眼光 |

### 5.4 边界：给负责人用，不是给 20 个同事用

- skill 跑在某个人自己的 Claude Code 或 Codex 会话里。按 09-20 的方向，员工用的是轻客户端，不会去开这些工具。
- 要给员工用，就得让 agent 在服务器上后台运行（`claude -p`、Agent SDK 或 `codex exec`），随之而来的问题是：公司网络能不能访问这些模型、key 放在哪、费用谁来管。这些是后话，现在不用解决。

### 5.5 和流水线的关系：先后，不是二选一

- 先用 skill 探路，再把稳定的部分固化进工作台。
- 判断标准：某一类判断，agent 连续十次都跟人判得一样，就下沉成规则或代码；一直需要人纠正的，就留在集中审片。
- 为 skill 做的命令行工具，将来做生产单或 MCP 也用得上，不会白做。
- **skill 放在哪（判断）**：这个 skill 跟着工作台 API 变，应该放进仓库、和代码一起管版本，不要像 Matt Pocock 那套一样装成全局插件；否则 API 一改，它就会悄悄失效。

## 6. 建议的推进顺序（判断）

1. 用户提供共享盘目录树 → 定目录约定。
2. 出 skill 设计文档：SKILL.md 草稿、命令行子命令清单、判图提示词、v0 验收标准。交给 Codex 或另开会话实现。
3. **v0**：型号 + 路径 → 建项目 → 认图 → 出场景图和分镜图 → 判图 → 出视频，到此为止。没把握的环节都在这一段。
4. v0 跑通后接后半段：脚本（采纳推荐模板）→ 按 N 倒推份数、建批次 → 统一审片 → 导出。后半段本来就基本自动化，接上去主要是体力活。
5. 判定记录攒起来后，把稳定的判断下沉进工作台：图片 prompt 模板表、生产单、预算闸门。
6. 需要给员工用时，再评估在服务器上后台运行 agent。

```sql
-- 分镜级否决标记（仍全空）
SELECT COUNT(*) FROM shots WHERE COALESCE(reviewMark, '') <> '';

-- 任务级标记分布（rework 由「重新生成」自动打）
SELECT COALESCE(NULLIF(reviewMark, ''), '(空)') AS mark, status, COUNT(*)
FROM jobs GROUP BY 1, 2 ORDER BY 3 DESC;

-- 出图成功后被 rework 的任务里有多少是分镜图（走候选表，勿用 inputImageId 关联）
SELECT CASE WHEN id IN (SELECT jobId FROM shot_result_candidates) THEN '分镜图' ELSE '其他' END AS kind,
       COUNT(*)
FROM jobs WHERE reviewMark = 'rework' AND status = 'succeeded' GROUP BY kind;

-- 视频被毙与理由
SELECT COUNT(*) AS rejected,
       SUM(CASE WHEN COALESCE(rejectReason, '') <> '' THEN 1 ELSE 0 END) AS with_reason
FROM video_jobs WHERE rejectedAt IS NOT NULL;

-- 图片 prompt 句式归类
SELECT CASE WHEN prompt LIKE '图1%待编辑分镜图%' THEN 'A 分镜重绘'
            WHEN prompt LIKE '基于图1生成新的%'   THEN 'B 场景生成'
            WHEN prompt LIKE '保%一致性不变%'     THEN 'C 旧式场景改写'
            ELSE 'D 其他' END AS fam,
       COUNT(DISTINCT prompt) AS 变体数, COUNT(*) AS 任务数
FROM jobs WHERE COALESCE(prompt, '') <> '' GROUP BY fam;
```
