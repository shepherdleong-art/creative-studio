# 定时备份快照超时与屏障恢复

2026-11-18，团队服务器的 02:30 定时备份在 SQLite 快照阶段运行到 6 小时上限。任务计划在 08:30 终止进程，保留了半成品数据库、目标回滚日志和活跃的备份屏障。本次调查通过既有域运维通道读取状态并短时采样。修复保留在本地源代码，`r2` 发布包保持待上传。

## 根因与复测

旧版使用 `better-sqlite3` 默认的分批拷贝。每批之间结束读取事务，其他连接提交后，SQLite 的下一批可能从头重来。生产写入持续发生时，备份能不断读页，却一直到不了末尾。进程被任务计划强停后，JavaScript 的 `finally` 无法释放已经落库的屏障。旧每日锁文件也会遗留，后续启动只能依赖时间判断。参考 [SQLite Online Backup API](https://www.sqlite.org/c3ref/backup_finish.html) 和 [WAL 快照隔离](https://www.sqlite.org/isolation.html)。

线上采样使用已安装版本的 SQLite 3.53.1、同一个活动业务库和备份盘的独立临时目录。库处于 WAL 模式，196,507 页，约 805 MB。采样全程只读业务库，完成后清理测试副本。

| 读取方式 | 采样结果 |
| --- | --- |
| 默认分批拷贝 | 5.545 秒内回退 15 次，最高进度 53,000 页，采样主动停止 |
| WAL 固定读取事务 | 并发提交期间无回退，8.829 秒完成，SQLite `quick_check` 返回 `ok` |

见 [线上采样](../outputs/05-日志与排查/2026-11-18-daily-backup-snapshot/live-snapshot-probe.jsonl)、[隔离复现](../outputs/05-日志与排查/2026-11-18-daily-backup-snapshot/synthetic-snapshot-probe.json) 和 [任务终止证据](../outputs/05-日志与排查/2026-11-18-team-server-candidate-r2/live-interrupted-backup-evidence.jsonl)。

## 修复

- 备份用独立只读连接固定 SQLite 读取事务，业务连接可继续提交。每批拷贝之间检查两分钟期限，超时写入 `backup_snapshot_timeout`，清理临时副本并释放屏障。媒体仍按既有备份 pin 保全，发布仍以完整校验和成功标记为准。
- 备份在数据根持有 SQLite 进程锁。启动新备份及现有维护进程空闲轮询时，只有取得同一把锁，且数据库里的屏障和暂存目录的备份 ID、部署、类型、数据根及随机标识一致，才回收这条屏障并记录 `backup_interrupted`。保留半成品用于核查，受管每日状态标记失败。旧版或人工建立的屏障依照既有现场核验流程处理。
- 每日锁采用同样会在进程退出后释放的 SQLite 锁，保留过渡期对旧锁文件的识别。全局维护锁持有到完整备份操作结束。pin 建立和屏障解除共用一个事务。恢复备份时，在已验证的还原副本中释放生成该备份时留下的屏障。

## 验收

- 并发写入回归通过。另一连接在每批拷贝时真实提交，备份通过完整性校验，读到拷贝开始时的版本。期限耗尽后没有成功副本，屏障清零。
- 使用真实的每日备份 CLI 进入 SQLite 拷贝后强停子进程。存活时回收被拒绝，终止后维护进程回收屏障、记录失败。原 ID 随即重试成功，人工屏障继续生效，已验证备份的还原副本也能正常继续。
- 回归包含还原、轮换、后台维护入口、计划任务、文件鉴权和项目主流程。Windows 的短暂目录占用复用现有的有限重试，校验和发布边界继续生效。
- 共 17 个回归文件通过。在叠加修复的 `r2` 源码上 TypeScript 校验通过，现有 `r2` ZIP 的 SHA-256 复核一致。见 [备份修复补丁](../outputs/05-日志与排查/2026-11-18-daily-backup-snapshot/team-backup-fix.patch)。
