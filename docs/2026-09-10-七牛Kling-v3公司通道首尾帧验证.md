# 七牛 Kling v3 公司通道首尾帧验证

2026-09-10，用户授权真实任务验证。第一轮提交三条 3 秒任务；第二轮补充两条 6 秒任务及三次创建前拒绝的字段探测。全部经过本机 LiteLLM → 公司 API，模型为 `qiniuyun/kling-3.0`，未直连 Modelink。第一轮仅验证；第二轮已接入工作台和本机模型路由。

## 结论

普通 v3 的首尾帧已通过成片验证。公司 OpenAI 风格接口需要将首帧放入 `images[0]`，尾帧通过 `end_image_url` 传入。不能直接照搬 Modelink Omni 的 `image_list`，也不能仅传 fal 的 `start_image_url`。

本次有效请求（URL 已脱敏）：

```json
{
  "model": "qiniuyun/kling-3.0",
  "prompt": "镜头平稳运动，从首帧画面自然过渡至尾帧画面，保持家具细节。",
  "images": ["<首帧 COS 预签名 URL>"],
  "end_image_url": "<尾帧 COS 预签名 URL>",
  "seconds": "3",
  "generate_audio": false
}
```

首帧、尾帧均来自仓库已有验证素材，经 `lib/cos-media.ts` 上传。首帧原图超过 4.8MB，经既有视频压缩参数生成 COS 副本；原文件未修改。使用临时回环代理 `127.0.0.1:4001`，复用现有公司连接，仅配置本次模型。正式工作台及 4000 代理保持运行。

## 三条对照任务

| 方案 | 参数 | 真实结果 |
| --- | --- | --- |
| Omni OpenAI 写法 | `image_list` 两图，`first_frame` / `end_frame`；`mode=pro`；`sound=off` | 提交 200、任务成功，但画面为无关客厅，首尾帧均未生效。720×1280、3.042 秒、24fps，存在音轨。不能以成功状态认定字段生效。 |
| fal 原生字段 | `start_image_url`、`end_image_url`；`seconds=3`、`duration=3`；`mode=pro`；`generate_audio=false` | 提交 200、任务成功，但画面为无关木椅，首尾帧均未生效。720×1280、3.042 秒、24fps，无音轨。 |
| 公司首帧 + 七牛尾帧 | `images=[首帧]`、`end_image_url=尾帧`；`seconds=3`；`generate_audio=false` | 首尾帧均与输入高度一致。828×1108、3.042 秒、24fps，无音轨。 |

第三条的画面内容与构图均正确：首帧是成人卧室及人物，末帧是儿童床与玩偶。将输入图与抽取帧缩放到 192×256 做 RGB 平均绝对差，仅作辅助指标：首帧对输入首帧为 1.955/255，末帧对输入尾帧为 3.457/255，末帧对输入首帧为 62.019/255。未声称逐像素无损。

## 轮询与下载

- 提交使用 `POST /v1/videos`，轮询使用 `GET /v1/videos/{提交时的完整id}`。
- 本轮观察到 `queued`、`in_progress`、`completed`。完成响应无产物 URL，使用提交时完整 id 的 `/content` 成功下载。
- 轮询返回 id 中的 model_id 丢失，继续保持现有规则：使用原始提交 id，不用轮询 id 替换。
- 任务响应的 `seconds`、`size` 为 null，实际时长和尺寸必须以 ffprobe 为准。
- 本机 LiteLLM 参数转换函数检查显示以上自定义字段均保留；未抓取公司内部转发请求，不能据此断言上游内部实现。

## 第二轮：1080P 与单提示词智能分镜

- `pro-smart`：在有效首尾帧请求中加 `mode=pro`、`multi_shot=true`、`shot_type=intelligence`，6 秒。产出仍为 828×1108，说明仅 mode 不足以升级清晰度。半秒间隔抽帧可见卧室全景、床品特写、儿童房全景。
- `size-auto`：增加 `size=1024x1366`（公司 §6.2 的 1K 名义格），`shot_type=intelligent`，其余沿用单提示词、首尾帧、`multi_shot=true`。产出 **1244×1660、6.042 秒、24fps**，无音轨（本次显式关闭），首尾帧 RGB 平均差分别 2.597/255 与 1.852/255。可见全景→细节→尾帧全景的景别变化。此为本次 3:4 素材的 1080P 档输出，不是将 828×1108 后处理放大。
- 没有做同提示词、只切换 multi_shot 的成对消融实验；不能仅凭镜头变化断言每次开关都强制产生切镜或证明参数的独立因果作用。生产实现保留用户要求的原生单提示词开关，不改写用户提示词。
- `multi_prompt` 的额外探测不作为生产方案：与非空 prompt 共存被上游 400 拒绝；省略 prompt 被 LiteLLM 500 拒绝（必填参数）；空 prompt 被公司入口 400 拒绝。这三次均未返回任务 id。用户明确选择单提示词 + multi_shot，正式请求不包含 multi_prompt。

正式新增供应商 `company-qiniuyun-kling-3-0` / 公司七牛可灵 3.0，使用 `openai-video`、本机 4000 LiteLLM、精确模型 `qiniuyun/kling-3.0`。默认 `mode=pro`、按首帧比例选择公司 1K 名义 size、`generate_audio=true`。智能分镜默认开启：`multi_shot=true` + `shot_type=intelligent`；关闭发送 `multi_shot=false` 并省略 shot_type。腾讯模型保持 `shot_type=intelligence` 和原有尾帧协议。

新增模型单首帧及双帧都要求本机 LiteLLM + COS，不允许图片 URL 回退；3–15 整数秒与读取首帧尺寸在提交前校验。原有 multiShot 的 API、SQLite 存储与 UI 开关直接复用，无新增迁移。补充轮询中间状态，继续用原始提交 id 下载。

## 验证边界

单首帧独立真实请求、4K、除 3/6 秒之外的时长、主体 elements 未单独验证。1080P 本轮仅实测 3:4，其他比例按公司尺寸表映射；未宣称逐格验证。第一轮 `sound=off` 实际仍含音轨，生产使用七牛字段 generate_audio。不要将腾讯的 `LastFrameUrl` / `OutputConfig` 协议直接复用给该模型。

适配器、精确能力匹配、开关存储/API/UI/队列合同、供应商补种和尺寸映射均有本机测试；新旧渠道回归与 TypeScript 检查通过。
