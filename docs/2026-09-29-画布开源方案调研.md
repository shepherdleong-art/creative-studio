# 2026-09-29 画布开源方案调研：LibTV / TapNow 那种画布能不能直接接

> 提问：不想再自己造画布，社区有没有现成的开源画布可以直接接进来用？
> 调研方式：全部结论走一手材料（GitHub 仓库实际文件、LICENSE 原文、npm registry、官方文档），不看二手转述。
> 配套文件：`outputs/research/node-canvas-ui-libraries.md`（画布**引擎库**横向对比，含 8 条未核实项）。

---

## 0. 结论速览

**有，但它不是「插件」，是同类成品应用；其中有一个和本仓库技术栈几乎同构。**

原本的假设「这个品类只有闭源商业产品」是**错的**。中文社区已经有两个万星级、MIT 许可、可商用的开源实现，而且其中一个的节点模型、`@` 引用、节点级专业工具、Agent 驱动画布，跟 LibTV / TapNow 是逐项对得上的。

三个分层，别混为一谈：

| 层 | 是什么 | 代表 | 能不能「接进来」 |
| --- | --- | --- | --- |
| **A. 同类成品应用** | 完整 AI 创作画布产品（前端 + 后端 + 模型接入） | `basketikun/infinite-canvas`、`HBAI-Ltd/Toonflow-app` | 不能 `npm i`；可自托管、可 fork、**可移植其 MIT 源码** |
| **B. 画布引擎库** | 只解决「节点 + 连线 + 视口」 | `@xyflow/react`（**本仓库已用**）、`@workflowbuilder/sdk` | 能，但你已经在用最好的那个 |
| **C. 完整执行引擎** | 画布 + 执行 + 模型管理，自带协议 | ComfyUI、Langflow、Flowise、Dify、n8n | 采用 = 换掉自己的后端架构，且域不匹配 |

**三个核心判断：**

1. **画布引擎层不存在「更好的替代品」**——本仓库用的 `@xyflow/react` 就是这一层的天花板（MIT、38.5k★、1367 万周下载、节点即你自己的 React 组件）。换掉它是净损失。
2. **执行与状态层没有任何开源成品可以接**——planner / 持久化 runner / 名额 / 恢复 / 账本这一层，所有候选要么没有，要么是进程内同步求值，要么绑死自家协议。这恰好是本仓库已经建好的部分。
3. **真正值得拿的是「特性面」**——TapNow / LibTV 的竞争力在节点级专业工具（抠图 / 局部重绘 / 放大 / 切图 / 多角度 / 打光）、`@` 引用上游素材、以及**节点插件化**。这三块有 MIT 源码可以直接移植。

> 一句话：**你「重新造画布」的直觉方向反了**。你造的不是画布，是执行引擎——那部分全社区都在等别人开源。而画布上的功能细节，别人已经写好了 MIT 版本，可以拿来主义。

## 1. 目标形态拆解：TapNow / LibTV 的画布到底是什么

从官方文档与实测报道归纳（[TapNow 官方文档](https://docs.tapnow.ai/zh/docs/canvas/understand-nodes-and-connections)、[量子位 LibTV 实测](https://www.qbitai.com/2026/03/390320.html)）：

| 能力 | TapNow | LibTV |
| --- | --- | --- |
| 无限画布 | ✅ | ✅ |
| 基础节点类型 | 文本 / 图片 / 视频 / 音频 | 文本 / 图片 / 视频 / 音频 / **脚本** |
| 建节点方式 | 左栏 `+`、双击空白、拖文件 | 双击画布 |
| 节点内预览产物 | ✅ | ✅ |
| 连线语义 | 上游=参考内容，下游引用 | 上游输出→下游输入 |
| Prompt 内 `@` 引用上游 | ✅（连线后 `@` 选上游图片） | ✅ |
| 从节点侧边 `+` 派生下游 | ✅（两侧 `+`） | ✅ |
| 多选后一次连到新节点（fan-in） | ✅ | ✅ |
| 快捷键 | ⌘C/V、Delete、⌘Z、Shift 多选、框选 | 同左 + `/` 调出隐藏功能面板 |
| 节点级专业工具 | 多角度、打光 | 一键高清、智能扩图、局部重绘、擦除、抠图、多角度、打光、标记融合、九宫格 / 四宫格 / 25 宫格、切图、视频裁剪、摄像机控制 |
| 脚本节点 → 批量分镜 → 转视频 | — | ✅（三种脚本生成模式） |
| 工作流复用（打组→工具箱） | — | ✅ |
| 模型自由选择 | ✅ | ✅（图像/视频/音频各选模型） |
| Agent 作为一等用户 | — | ✅（Skill + OpenClaw 自动拍片） |
| 计费 | Tapies | — |

**要点：这套形态没有任何"秘密武器"级的技术难点，是工程量与细节打磨。** 而"Agent 也能操作画布"这一条，恰好和 `infinite-canvas` 的 canvas-agent 是同一个设计。

## 2. 候选 A（首选）：`basketikun/infinite-canvas`

- 仓库：<https://github.com/basketikun/infinite-canvas>　7,164★（Trendshift 上榜）
- LICENSE：**MIT**，README 原文明确「任何人都可以免费使用、复制、修改、分发、再授权和商业使用本项目，也可以用于闭源产品」
- 技术栈：**React 19.2.5** + Vite 7 + **Tailwind CSS 4** + zustand 5 + antd 6 + shadcn/radix + react-router 7 + localforage
- 规模：`web/src` 174 文件 / 33,598 行；其中**画布相关 61 文件、约 1 万行**

### 2.1 架构事实（读源码得出，非推测）

- **画布是手绘的，不用 React Flow**。`components/canvas/infinite-canvas.tsx` 自己实现 pan/zoom/视口变换，`canvas-connections.tsx` 自己算连线路径，另有自研 mini-map、zoom-controls。依赖表里没有任何 xyflow。
- **内置节点只有 6 种**：`image` / `text` / `video` / `audio` / `config` / `group`。其余（Markdown、SVG、HTML、3D 全景、便利贴）**全部是插件**。
- **有真正的画布插件 SDK**：`plugins/canvas/sdk`（`definePlugin`、automatic JSX 运行时转发宿主 React 保证单实例、`buildPlugin` 一行 esbuild 封装、类型自包含）。插件产物是 ESM（React external），**托管到任意静态地址后由用户在「节点插件」管理器里填 URL 安装**；官方插件走 jsDelivr 从孤儿分支 `plugins-dist` 拉取。SDK **未发布到 npm**。
- **画布数据模型**（`docs/.../canvas-data-structure.mdx`）：`CanvasProject { id, title, nodes, connections, chatSessions, viewport }`、`CanvasNodeData { id, type, title, position, width, height, metadata }`、`CanvasConnection { id, fromNodeId, toNodeId }`。存储在 **localForage / IndexedDB**（项目在 `app_state`，图片 blob 在 `image_files`，其它媒体在 `media_files`）；项目 JSON 存 `storageKey` 而非 base64。
- **生成能力走客户端直连**用户自配的 **OpenAI 兼容端点**（图片/视频/音频），并提供 `model-script-editor` 让用户自写调用脚本适配非标准接口。
- **`canvas-proxy`**：可选的本地转发代理（`npx @basketikun/canvas-proxy`，127.0.0.1:23210），纯粹为了绕开浏览器直连第三方 API 的 CORS，只转发不改写、不落盘。**不是云依赖。**
- **`canvas-agent`**：本地 Node/Bun Agent，自带 MCP server（`src/server/mcp.ts`）、canvas operations/schemas/session/tools、skills store，支持 Claude / Codex 客户端。另有 Codex / ZCode 插件包（`plugins/infinite-canvas`，含 `marketplace.json` 与 canvas / open-canvas 两个 skill）。
- 其它：WebDAV 同步、ZIP 导出、提示词库、素材库。

### 2.2 与 TapNow / LibTV 逐项对照

| TapNow / LibTV 的能力 | infinite-canvas 对应实现 |
| --- | --- |
| 无限画布、双击/`+` 建节点 | ✅ 自研画布 + `canvas-create-menus` |
| 节点内预览图/视频 | ✅ `canvas-node.tsx`（992 行） |
| `@` 引用上游素材、自动编号 | ✅ `canvas-resource-mention-textarea`（352 行） + `canvas-prompt-chip-input`（426 行，`@` 时内联真实缩略图） |
| 一键高清 / 局部重绘 / 抠图 / 擦除 / 切图 / 多角度 | ✅ 对应 `canvas-node-upscale-dialog`、`canvas-node-mask-edit-dialog`（438 行）、`canvas-node-crop-dialog`、`canvas-node-split-dialog`（299 行）、`canvas-node-angle-dialog` |
| 节点悬浮工具栏 | ✅ `canvas-node-hover-toolbar`（311 行） |
| 模型自由选择 | ✅ OpenAI 兼容端点 + 自定义脚本 |
| 工作流复用 | ⚠️ 有 group 节点，但未见「存为工作流模板」 |
| Agent 也可操作画布 | ✅ canvas-agent + MCP + Codex/ZCode 插件（比 LibTV 更开放） |
| 插件化扩展节点 | ✅ **LibTV/TapNow 都没开放，这个有** |
| 服务端执行 / 持久化调度 / 配额账本 | ❌ 全在浏览器，无执行引擎 |

### 2.3 风险与代价（必须知道）

1. **它不是库，是应用**（`private: true`，Vite SPA）。没有 `npm i` 这条路。
2. **整体换过去是增加代码**：它的画布层约 1 万行（因为视口/选区/连线全手绘），而本仓库 `components/creative-canvas/` 只有约 2,500 行（重活交给 React Flow）。**整体替换 = 用 1 万行换 2,600 行**，只有在"要它的功能面"时才划算。
3. **存储模型冲突**：它把画布与素材放浏览器 IndexedDB，生成请求由浏览器直发供应商。本仓库是服务端 SQLite + planner/runner + 素材管线 + 配额账本。移植时必须换掉它的存储与生成编排层。
4. **插件信任模型有安全含义**：插件是**从任意 URL 拉取的 ESM，在宿主 React 实例里执行**，同源可访问用户存在浏览器里的 API Key。对本地优先工作台是个需要设防的点（白名单 / 签名 / 只允许官方 registry）。
5. **遥测**：`analytics.ts` 会加载 GA4，但仅在配置了 `VITE_*` 埋点 ID 时生效，`trackPageview` 默认 no-op；无其它云依赖。移植时直接不接即可。
6. **项目属性**：个人项目，README 顶部有大量 API 中转商赞助位，商业化可持续性弱于公司背书的项目。

## 3. 候选 B（架构参考）：`HBAI-Ltd/Toonflow-app`

- 仓库：<https://github.com/HBAI-Ltd/Toonflow-app>　**16,216★**，LICENSE **MIT**，当日仍有推送
- 定位：AI 短剧 / 漫剧创作平台（小说→剧本→分镜→图片/视频→成片）
- 技术栈：**Bun** workspace + **Vue 3.5** + **@vue-flow/core 1.48.2** + Element Plus + TDesign + Pinia；桌面端用 electrobun
- 结构：`apps/{web,server,desktop,updateServer}` + `packages/{providers,mcp,ffmpeg,nodeScaffold,toolScaffold,teamScaffold,assets,modelIcons}` + `packages/nodes/*` + `packages/tools/*` + `packages/teams/*`

### 3.1 为什么值得看：它把「节点插件化」做成了第一等公民

- `packages/nodeScaffold` / `toolScaffold` / `teamScaffold` 三套**脚手架**，配套 `packages/nodes/{textNode,imageNode,imageGenerationNode,videoGenerationNode,audioNode,director3dNode}`——**每个节点是独立的 Vite 库包**，默认导出自己的 Vue 组件，带 `readme.md` 与 `vite.config.ts`。
- `packages/providers` 是独立的能力/供应商抽象层，被 web 与 server 共用。
- `packages/mcp` 原生 MCP。
- 文档截图里有 `pluginMarket.png`，即**插件市场**。

### 3.2 服务端与数据

- `apps/server`：Bun + TypeScript + Express，`createApp({ webRoot, dataDirectory })`，桌面端通过 `@toonflow/server/app` 复用同一应用。
- 画布存成**工作区里的 JSON 文件**（如 `画布1.json`，用 `toonflowCanvas` 标记字段），通过 `/api/workspaces/files/*` 读写；前端有统一的 `useWorkspaceFiles` 封装。

### 3.3 对本仓库的价值

**代码不能直接复用（Vue），但架构可以直接抄**：节点/工具/团队三层脚手架 + 独立打包的节点包 + provider 抽象层，正是把"画布"从"一个页面"升级成"一个平台"的解法。

## 7. 接入路径对比

| 路径 | 工作量 | 得到 | 失去 | 判断 |
| --- | --- | --- | --- | --- |
| **P1 整体自托管 + iframe/新窗口** | 最低（Docker/静态站点 + 一个入口） | 立刻拥有完整画布体验 | 两套数据存储、两套素材、无法共用你的 planner/runner/账本/公司网关；Agent 与配额割裂 | 只适合「先让用户体验起来」的过渡 |
| **P2 移植其画布交互层**（约 1 万行 MIT React） | 中高 | 节点级专业工具、`@` 引用、插件体系 | 要**放弃/重做**其手绘视口层（你自己用 React Flow 更薄）；要重接存储与生成编排 | 只在"整块功能面都要"时做，且应**只搬功能组件、不搬视口引擎** |
| **P3 抄特性清单，在现有画布上补**（推荐） | 分阶段、可增量 | 用最小代码补齐与 TapNow/LibTV 的差距 | 需要逐个读 MIT 源码再重写 | **推荐**：你已有的 planner/runner/账本不动 |
| **P4 Fork 整个应用当产品** | 高（等于换产品） | 起点好看 | 丢掉全部服务端能力与既有测试；插件从 URL 执行 ESM 的信任模型在本地优先场景要重新设防 | 不建议 |
| **P5 换 ComfyUI 后端** | 高（换栈） | 本地扩散模型生态 | 与本项目"调用外部供应商 API + 不依赖外部后台"的架构直接冲突（ComfyUI 的 API Nodes 若走 comfy.org 闭源模型则仍需外部账号） | 不建议 |

## 8. 建议

**不要换画布引擎，也不要整体切过去；把两个 MIT 项目当"参考实现 + 可抄代码库"。**

理由：本仓库缺的不是画布，是画布上的功能细节与节点扩展性；而执行/状态层（`planner.ts` / `runner.ts` / `tasks.ts` / `recovery.ts` / `usage.ts` / `scheduler.ts`）恰好是开源界没有的东西——这层是你真正的资产，不该为了「省画布」而丢掉。

具体三条动作：

1. **画布引擎保持 `@xyflow/react`**，不动。它 MIT、社区最大、节点即自有 React 组件，本仓库 2,600 行的前端比你手改 1 万行更划算。
2. **从 `basketikun/infinite-canvas` 移植"功能组件"而非"画布引擎"**（MIT，保留版权声明即可）。优先级：
   - `canvas-resource-mention-textarea.tsx` + `canvas-prompt-chip-input.tsx` —— `@` 引用上游素材 + 内联缩略图（TapNow/LibTV 的核心交互，本仓库目前没有）
   - `canvas-node-mask-edit-dialog.tsx` / `canvas-node-upscale-dialog.tsx` / `canvas-node-crop-dialog.tsx` / `canvas-node-split-dialog.tsx` / `canvas-node-angle-dialog.tsx` + `canvas-node-hover-toolbar.tsx` —— 节点级专业工具
   - `types/canvas-plugin.ts` + `lib/canvas/plugin-{loader,registry,runtime}.ts` + `plugins/canvas/sdk` —— 你自研节点插件契约的**设计参考**（注意其"任意 URL 拉 ESM"的信任模型不要照抄）
   - `canvas-agent/src/canvas/{operations,schemas,tools}.ts` —— 让 Agent 操作画布的操作集设计
3. **节点插件化架构参考 `HBAI-Ltd/Toonflow-app`** 的 `packages/nodeScaffold` / `toolScaffold` + `packages/nodes/*` 独立打包模式（Vue 代码不可复用，只抄结构）。

## 9. 未核实项（如实记录）

1. `@xyflow/react` 在 **React 19 下的运行时行为**未经真机验证；其仓库根 devDeps 仍是 React `^18.2.0`，无官方"核心库已针对 19 测试"的一手声明（peer 为 `>=17`，不会报冲突）。搜索摘要中出现的 xyflow Issue #5229「React 19 not supported」**存在性与结论均未核实**。
2. tldraw **水印付费移除**的具体条款与价格未找到（`/legal/license`、`/legal/watermark` 均 404）；但 LICENSE.md 的 License Key / Production Environment 强制条款有原文佐证。
3. `@workflowbuilder/sdk` 的"开源核心 vs 商业版"长期边界未核实。
4. ComfyUI **API Nodes**（调用闭源模型）的准确目录、许可证与是否需要 comfy.org 账号/付费，本轮未拿到一手文档，结论（"若走该路径仍需外部账号"）属**未验证推断**。
5. `basketikun/infinite-canvas` 的 star 数与推送日期来自 GitHub 搜索 API 快照（2026-09-29 当日）；该仓库后续 API 调用遇到限流，未再复核 star 趋势与 release 节奏。
6. `HBAI-Ltd/Toonflow-app` 的许可证文件、技术栈、目录结构均为一手核实，但**其画布层与本仓库的移植成本未做逐文件评估**（因栈不同，判定为不可直接复用）。
7. 本调研未在任何候选上执行构建或运行验证；所有"可移植性"判断基于源码阅读与依赖分析，不是实测结论。
