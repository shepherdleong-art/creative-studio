# Beta 首次改密与 EXE 安装修复

## 首次改密 CSRF 失败

页面的 `TeamFetchBridge` 缓存 CSRF 令牌，Electron 传输和诊断使用相同 Session Cookie jar。后台再次 GET CSRF 时，旧实现总是签发新 Cookie，使页面缓存的令牌与 Cookie 不同，首次改密被拒绝为 403。桌面写入另有先读取 Cookie、再初始化 CSRF 的顺序问题，首次请求可能携带旧 Cookie。

修复后，CSRF 接口复用格式有效的 32 字节 base64url Cookie，缺失或畸形才重新签发。Origin、双提交比较及 HttpOnly/Secure/SameSite 限制保持；桌面写请求先等待令牌，再读取 Cookie。没有调整账号、密码或一次性凭据的消费规则。

`team-auth-route.test.ts` 加入共享 Cookie 后台请求后的真实改密回归，修复前稳定复现 403，修复后通过；原有错误 Origin、缺失/错误 CSRF、一次性凭据和会话撤销回归继续通过。桌面传输与诊断首个请求的 Cookie 回归也分别从失败变为通过。

`brand-login-page.playwright.test.mjs` 在首次改密前用共享浏览器上下文发起绕过页面桥的后台 CSRF 请求。Chromium/WebKit 上首次登录、改密和新密码登录通过。该测试支持用 `CREATIVE_STUDIO_AUTH_TEST_STANDALONE` 指向独立生产负载，避免开发服务器追踪本地大量运行目录。

## 真正的 Windows 安装程序

新增 `scripts/build-team-client-installer.mjs`、`installer/windows/team-client.iss` 和 C# GUI 启动器，消费既有签名轻客户端负载，生成中文 EXE 安装向导。默认安装到当前 Windows 账号目录，提供开始菜单/桌面快捷方式；首次公开根证书信任由用户明确选择。卸载保留设备状态和下载，不撤销证书信任。

第一份安装验收发现主程序缺失，未分发给同事。最小复现证明当前 Windows Node 22 的 `fs.cpSync` 原生递归路径对中文目录会静默遗漏目录或原生崩溃。两种团队装配器改为使用带 filter 的 JS 遍历，保留逐文件拒绝覆盖。客户端和安装器在发布前明确检查启动文件；包边界测试改用中文与空格临时目录，并在修复前失败、修复后通过。

失败的 r2 EXE 及负载已归档到 `outputs/04-测试与验收/beta-csrf-20261109/失败安装包-勿分发/`。最终候选为 `studio-beta-csrf-20261109-r3`，分发目录为 `outputs/02-客户端/分发压缩包/`。

真实 r3 EXE 已完成中文/空格路径首次安装、211 个程序文件逐项 SHA-256 比对、GUI 启动和 HTTPS 登录控件检查，客户端健康检查通过。再次安装保留设备/状态，卸载移除程序并保留下载与设备标记；测试未安装证书、未登录真实用户账号。安装器尚未配置 Authenticode 签名，更新包继续使用现有 Ed25519 签名。
