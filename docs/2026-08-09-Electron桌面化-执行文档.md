# Creative Studio 桌面化：Electron 薄壳执行文档

---

## 说人话版（给不懂技术的人看，三分钟）

### 现在是什么情况

把这个软件想成**一家自己啥都有的餐厅**：厨房、冷库、厨师全是自己的（视频处理、数据库、AI 调用都在你电脑本地跑）。

但这家餐厅**没有自己的大门**。客人想吃饭，得先走到隔壁商场里，找到一个对外窗口来点餐——这个"商场窗口"就是浏览器。

所以现在双击图标，实际发生的是：偷偷把厨房打开 → 然后帮你打开浏览器 → 你在浏览器里操作。

### 这样有什么问题

商场那个窗口有**尺寸限制，而且是改不了的**：

- **一次最多递进来 256 MB 的东西。** 一条 4K 原片动辄好几个 G，**根本递不进去**。
- **递进来的东西必须原样复制一份存在店里。** 100 G 素材进来，硬盘就少 200 G。
- 客人想让服务员帮忙"打开文件夹看看"，商场不让——所以现在这个按钮只在安装版能用，浏览器里只能退而求其次让你"下载"。

### 最扎心的一点

厨房里**其实早就修好了一条流程**：客人自带食材，厨师直接用，用完原样还给客人，**一点不复制、一点不占地方**。

这条流程代码写完了，测试也跑过了，注释里白纸黑字写着"用户原文件永远只被引用，任何项目操作都不删除它"。

**但它从来没被用过一次。** 因为它需要知道"食材现在在客人家的哪个位置"，而商场窗口出于安全规定，**永远不会告诉你这个地址**。

所以这不是"要不要花钱装修"的问题，是**你已经付过钱造好的东西，因为缺一扇门而一直闲置着**。

### 那要做什么

给餐厅**装一扇自己的大门**（这就是 Electron）。

关键在于：**厨房一根手指都不动。** 不是重建餐厅，是在现有餐厅外面加个门面。

装完之后：

- 双击就直接是软件窗口，没有浏览器、没有地址栏，像个正经软件。
- **批量生产**那一步点"导入素材"，弹出你熟悉的系统选文件窗口，**几十条几个 G 的 4K 原片，秒进，不复制，硬盘一点不多占**。
- 关窗口不等于关软件——任务继续在后台跑完，不会因为你手贱关了个标签页就前功尽弃。

> 一句实话：软件里有两条素材通道（"批量生产"和"智能混剪"），它们在内部是**两套独立的东西**。上面说的那条已修好的流程只属于**批量生产**那条。混剪那条这次先不动，还是老样子——把它一起改的工作量，相当于把整件事再做一遍，不划算。

### 有多大风险

这是最该问的问题，答案是**可以量化的**：

过去 9 天，这个项目的核心业务代码长了 **3 万多行**，而"门面"这部分的代码只动了 **98 行**。

也就是说：**业务疯狂长的时候，门面这块几乎纹丝不动。** 这说明这两块本来就是分得开的，不是我拍脑袋说"应该能分开"。

而且方案是**分四步走，每步都能单独停下来**。走到第二步就已经能自己用了。哪怕第一步就发现走不通，删掉一个新文件夹就行，**原有的东西一行都没被改过**。

### 关于 Windows 用 MSIX（新格式）

一句话：**现在不行，以后也未必划算，但方案会留好口子，不会把路堵死。**

三个原因，任何一个单独都足以否掉：

1. **它默认不许软件跟"自己家的厨房"说话。** 这个软件的门面和厨房是靠内部对讲机联系的，MSIX 默认把这条对讲机掐了。虽然能申请解除，但**微软的开发工具会在开发者自己的电脑上自动帮你解除**——结果就是你测的时候一切正常，装到客户电脑上直接连不上厨房。这种"上线才炸"的坑，最费钱。
2. **必须有官方认证的签名才能装，没有就是装不上**（旧格式没签名只是弹个警告，还能装）。微软有个每月十美元的便宜签名服务，但**只对美国/加拿大、且成立满 3 年的公司开放**，个人开发者的通道目前是关着的。剩下的选择要么是买贵得多的传统证书（还得配个硬件加密狗），要么上架微软商店过审核。
3. **换了它也不白送自动更新。** 现成的打包工具明确不支持给这种格式做自动更新，得自己再搭一套更新服务器。

所以：**现在用成熟的旧格式（Inno Setup）**，同时在方案里把"打包"和"装配"拆成两步——将来真要换 MSIX，只换后面那一步，前面不用重做。

## Context

### 为什么做

现在的形态是**本地 Next 服务 + 系统浏览器当显示器**。安装版已经有 `CREATIVE_STUDIO_DESKTOP=1` 桌面模式开关，"打开文件夹"只在安装版可用，浏览器里降级成"下载视频"——说明已经在被浏览器边界卡住，只是用降级文案糊住了。

### ⚠️ 两个素材子系统必须先分清（执行前务必读懂这一节）

**混剪侧和批量侧是两套独立的素材系统，互不相通。** `grep -rn "final_edit_external_assets" lib/batch-production/` 结果为 **0**。搞混会直接建错东西。

| | 混剪 / final-edit 侧 | 批量生产 / batch-production 侧 |
|---|---|---|
| 表 | `final_edit_external_assets` | `batch_assets` + `batch_asset_sources` |
| 导入 UI | `components/mixcut/MaterialStep.tsx:129`（拖拽 + `<input type="file">`） | **今天没有任何视频导入入口**（唯一的 `type="file"` 在 `BatchStepMaterials.tsx:388`，`accept=".cube"`，是 LUT） |
| 素材从哪来 | 用户浏览器上传 | **只能来自模块 4 生成的视频**（`prepare.ts:133` 只调 `registerModule4Video`） |
| 是否支持"链接不复制" | ❌ 无此概念 | ✅ 后端整套已建成 |
| 痛点 | 256 MB / 512 MB 上传上限 + 复制进 storage | 用户自己拍的原片**根本进不来** |

### 为什么做

真正的缺口有两个，**分属两侧**：

**① 批量侧：用户原片完全进不来。** 批量生产今天只能用模块 4 生成的视频（`BatchStepMaterials.tsx:354` 的空态原文就是"暂无可用视频素材，请先在第 4 步完成视频生成"）。用户自己拍的素材没有任何入口。

而这一侧**"链接不复制"的后端已经整套建成并测试过了**：

- `lib/batch-production/media-catalog.ts:393` `registerLinkedSource` —— 注释原话："登记用户原文件位置为链接来源。素材身份是内容指纹；用户原文件永远只被引用，任何项目操作都不删除它。"
- 同文件另有 `registerManagedCopy`（托管副本）、`relocateLinkedSource:523`（原片挪走后重新定位）、`verifyAssetSources:488`（来源健康核验）。
- `lib/batch-production/assets.ts:9` `BatchAssetSourceKind = 'module4' | 'managed' | 'linked'`；`schema.ts:36` 的 DB CHECK 明写 `linked|managed`。
- 素材身份是 SHA-256 内容指纹，不依赖路径；`status: online|offline` 已覆盖原片掉线。

**关键利好**：`prepare.ts:138` 用 `listProjectAssets(db, projectId)` 拉**全部** `batch_assets`，**不按 sourceKind 筛选**；`prepare.ts:180` 的展示层已经写好了 linked 的标签 `'用户文件'`。所以 **linked 素材一旦登记，会自动出现在批量素材区**，缩略图、预览、健康核验、内容分析全部沿用现有链路——Phase 2 在批量侧只需要"登记"，不需要碰列表、分析或分配。

**但 `registerLinkedSource` 和 `registerManagedCopy` 今天只有 `scripts/batch-media-catalog.test.ts` / `batch-asset-preparation.test.ts` 在调，零个 HTTP 入口、零个生产调用方。** 整个 `linked|managed` 来源体系在生产里从未被使用过一次，只有 `module4` 被接上了。

它等的是一个**真实绝对路径**，浏览器给不了。这是 Electron 唯一不可替代的作用。

**② 混剪侧：上传有硬上限。** `lib/final-edit/material-import-http.ts:12-13` 写死单文件 256 MB、单次 512 MB，注释自承 `Request.formData()` 在 Next 里不是流式的；导入还必须复制一份进 storage。**本次 V1 不解决这一侧**（见「明确不做」），因为混剪侧没有 linked 数据模型，补它是另一个量级的工程。

所以本项目桌面化的核心价值不是"外观像个软件"，而是**解锁批量侧一套已建成、已测试、从未通电的能力**。

### 为什么"项目已经很大"不是阻力

2026-07-31 的桌面边界票（`docs/superpowers/plans/2026-07-31-batch-mixcut-desktop-wayfinder/03-确定桌面应用与本地服务的边界.md`，状态 `closed`）已定"薄 Electron 壳"。2026-08-09 复核，用 `feb74da` → HEAD 实测（589 文件，+107,638 / **-1,431**）：

| 区域 | 增量 |
|---|---|
| `lib/`（本地服务内部） | +31,860 / -383 |
| `scripts/` | +28,766（其中 27,561 是测试） |
| `docs/` | +8,797 |
| `app/`（API 路由） | +3,661 / -578 |
| **`installer/`（壳的边界）** | **+98** |
| **`package.json`** | **+6 / -1** |

删除仅 1,431 行 —— 增量堆叠，不是重写。**业务长 3 万行的同时壳边界几乎没动**，这是边界稳定性的实证。

长大对壳的三个实际影响，两个是**变简单**：

1. 🟡 `lib/ffmpeg.ts:62` 的 `signal?: AbortSignal` 统一取消信号**是这 9 天新加的**（7-31 审计点名的缺口）。但**这只是能力就位，接线没做**：全仓 grep，今天**零个 ffmpeg 调用方传 `signal`**（`lib/` 下所有 `signal:` 命中都是 fetch/HTTP，属于脚本供应商和 COS，与 ffmpeg 无关）。所以 Phase 0 的实际工作是把 signal **串through 约 10 个调用点**，不是"调个现成接口"。
2. ✅ `lib/batch-production/scheduler.ts` 改为租约制（5 分钟租约 + 心跳 + `expectedState`/`controlState`）。异常退出后任务靠租约过期自动回收——壳最怕的"强杀后状态烂掉"已在设计上免疫。
3. ⚠️ **唯一变难**：在飞子进程种类变多（proxy / render / narration / 分析），而服务侧**至今无任何优雅停机入口**（全仓无 `SIGTERM`/`SIGINT` 处理；`app/api/shutdown/route.ts` 是 500ms 后硬 `process.exit(0)`）。这是 Phase 0 必须先补的前置。

### 交付后的样子

双击应用 → 原生窗口直接打开工作台（无浏览器、无地址栏）→ 点"导入素材"弹出系统文件选择器 → 选几十条 4K 原片，**秒进素材池、不复制、不占额外磁盘** → 关窗只隐藏、任务继续跑 → 明确退出时暂停任务并干净回收进程树。

## 不可动摇的边界（沿用 07-31 结论）

五层职责，**任何阶段都不得越界**：

| 层 | 负责 | 严禁 |
|---|---|---|
| Electron main | 单实例、窗口、原生文件/文件夹选择、启动看管本地服务、应用退出 | 领域模型、SQLite 查询、素材分配、FFmpeg 参数 |
| preload | 逐项命名的强类型方法 | 暴露 `ipcRenderer` / `fs` / `path` / `child_process` / 任意 channel |
| Next renderer | 现有 React UI | 直接读任意路径、启动命令、Node API |
| 本地 Next 服务 | SQLite、任务调度、AI/FFmpeg 执行、恢复与产物登记 | 创建窗口、处理系统生命周期 |
| 媒体子进程 | FFmpeg / ffprobe | 由 renderer 直接启动 |

**最关键的一条**：Electron main/preload **绝不加载** `better-sqlite3`、`sharp`、`ffmpeg-static`。这些继续留在私有 Node 22 子进程里，保持现有 ABI 和构建校验。壳只加载纯 JS + Electron 官方 API。**这一刀是"存量不动"的全部保障**——违反它，这份文档的风险评估立即作废。

安全基线（显式写死并用测试锁定，不依赖默认值）：

```ts
webPreferences: {
  preload,
  nodeIntegration: false,
  contextIsolation: true,
  sandbox: true,
  webSecurity: true,
  webviewTag: false,
}
```

## Phase 0：服务侧优雅停机（前置，非 Electron 工作）

> 这是"项目变大"唯一带来的新债。**不做这一步，壳的退出逻辑无处可接。**
> 独立价值：做完之后，现在的浏览器版关闭按钮也不再砍断在飞的渲染。

**改动文件**

- 新增 `lib/shutdown.ts` —— 唯一的优雅停机编排入口。
- `instrumentation.ts` —— 现在只 `startBatchSchedulerAfterReadiness()`，补上对称的停止注册。
- `app/api/shutdown/route.ts` —— 把 `setTimeout(500) + process.exit(0)` 换成 await 编排结果。

**`lib/shutdown.ts` 契约**

```ts
export async function gracefulShutdown(opts: { timeoutMs: number }): Promise<{
  stopped: boolean;
  pendingTasks: number;   // 未能在超时内收尾的任务数
}>;
```

顺序（每步都要能单独超时，任何一步失败不得阻塞后续）：

1. 停止调度器领取**新**任务（`lib/batch-production/scheduler.ts` 的 claim 入口设一个 draining 标志）。
2. 向在飞的 FFmpeg 广播 abort —— **复用 `lib/ffmpeg.ts:62` 已有的 `signal?: AbortSignal`，不要新造取消机制**。

   ⚠️ **这是 Phase 0 里最大的一块，不要低估**：`lib/ffmpeg.ts` 接受 `signal`，但**今天没有任何调用方传它**。需要把 signal 从调度器串到每个 ffmpeg 调用点。已确认的调用点（`grep -rln "runFfmpeg" lib`）：

   ```
   lib/batch-production/batch-renderer.ts       ← 正式渲染，最长命，优先
   lib/batch-production/proxy-executor.ts       ← 代理转码，最长命，优先
   lib/batch-production/project-asset-media.ts
   lib/batch-production/lut-catalog.ts
   lib/media-core/adapters/video-analysis.ts
   lib/media-core/adapters/tts-common.ts
   lib/media-core/scene-detect.ts
   lib/final-edit/prepare-preview.ts
   lib/final-edit/video-frame.ts
   lib/final-edit/beat-detect.ts
   ```

   **允许分级收工**：优先接 `batch-renderer.ts` 和 `proxy-executor.ts`（长任务，强杀损失最大）；缩略图/探针类短任务（`video-frame.ts`、`scene-detect.ts` 等）可以先靠超时自然结束，在文档里记为已知缺口即可，不阻塞 Phase 1。

   执行器层维护 in-flight `AbortController` 注册表：`lib/batch-production/executors.ts`、`proxy-executor.ts`、`batch-render-executor.ts`、`lib/final-edit/worker.ts`。
3. 等待在飞尝试落库为可恢复状态（租约制已保证：即使这步超时，租约过期后也会自动回收）。
4. 关闭 SQLite 连接（`lib/db.ts`）。
5. 停 LiteLLM sidecar —— **复用现有 `stack.json` 受控脚本逻辑**，原样搬运，不要重写路径校验。

**注册进程信号**：`process.on('SIGTERM')` / `SIGINT` → `gracefulShutdown` → `process.exit(0)`。这是 Electron main 回收子进程的抓手。

**验收**

- 新增 `scripts/graceful-shutdown.test.ts`：起一个假渲染任务 → 触发 shutdown → 断言子进程收到 abort、任务落库为可恢复、函数在超时内返回。
- 手工：跑一个批量渲染，中途点 UI 关闭按钮，确认无 ffmpeg 僵尸进程（`pgrep ffmpeg`）。

## Phase 1：壳骨架（窗口 + 服务看管）

**新增目录 `desktop/`**（与 `app/`、`lib/` 平级，**纯 TS/JS，零业务依赖**）

```
desktop/
  main.ts           # 单实例、生命周期、启动服务、创建窗口
  preload.ts        # contextBridge 白名单桥
  service.ts        # 启动/健康检查/回收私有 Node 服务子进程
  ipc.ts            # ipcMain.handle + sender 校验
  bridge-types.ts   # DesktopBridge 类型（renderer 也 import 这个）
  tsconfig.json     # 独立编译，不并入主 tsconfig
```

**依赖**：`electron` 进 `devDependencies`（它是打包工具，不是运行时依赖）。

**随机端口 + 健康身份**

现在 `installer/macos/launcher.sh:12` 和 `installer/windows/launcher.cs` 都写死 3000，且"已在运行"判断只证明该端口有网页在应答，不能证明是本实例。改法：

1. main 以 `PORT=0` 启动服务子进程，让 OS 分配。
2. 服务在监听成功后，把 `{ port, instanceId }` 写到 stdout 一行约定前缀（如 `__CREATIVE_STUDIO_READY__ {json}`），main 解析。
3. 新增 `app/api/desktop/health/route.ts`，返回本次启动的 `instanceId`。main 校验 `instanceId` 一致才认这个服务，**不用"3000 端口有响应"当判据**。
4. main 拿到确定 origin 后才 `loadURL` 并建立 IPC sender allowlist。

> **端口方案的取舍（已定，不要自己改主意）**：不要用"main 侧 `net.createServer().listen(0)` 预占端口 → 释放 → 传给服务"这种写法 —— 释放和服务真正绑定之间有竞态窗口，别的进程可能抢占，表现为偶发启动失败，极难复现。
>
> **定案**：由**服务进程自己**用 `PORT=0` 绑定，绑定成功后把真实端口写到 stdout 的约定行，main 解析后使用。Next standalone 的 `server.js` 尊重 `PORT` env，但不会打印结构化端口——所以在 payload 里加一层薄启动包装 `runtime/server-entry.js`：它 require standalone 的 `server.js`，从 server 实例读回 `address().port`，打印 `__CREATIVE_STUDIO_READY__ {"port":N,"instanceId":"..."}`。**这层包装放在 `desktop/` 之外，构建时复制到 `.next/standalone/runtime/`，以保持 `desktop/` 目录的传递依赖图不触达 Next 业务/native 依赖。**
>
> 若 standalone `server.js` 的结构不允许拿到 server 实例（需实测），退路是让服务启动后主动 POST 一个回调到 main 监听的临时 loopback 端口。**实测后在文档里记下实际走的是哪条。**

**单实例**：`app.requestSingleInstanceLock()` 必须在创建窗口和启动服务**之前**。第二次启动只唤醒聚焦已有窗口。
**这条是硬性要求，不是体验优化**——`lib/schema-upgrade/` 有跨进程 SQLite 写锁，两套服务同时跑会撞上迁移 gate。

**导航封锁**：`will-navigate` 一律 `preventDefault()`（除首次加载本次 origin）；`setWindowOpenHandler` 默认 `{ action: 'deny' }`。

**IPC sender 校验**：每个 `ipcMain.handle` 先确认 `event.senderFrame` 是主窗口 main frame，且用 `new URL()` 逐项比对 protocol/hostname/port —— **禁止 `startsWith('http://127.0.0.1')` 之类字符串判断**。

**构建接线（文档不写清楚这里会卡住，务必照做）**

现在 `package.json` **没有 `main` 字段**，也没有任何 Electron 相关脚本。需要补：

## Phase 2：原生导入（本次桌面化的核心价值）

> 目标：让 `registerLinkedSource` 拿到真实绝对路径。**不改任何已有业务函数。**

**preload 契约**（`desktop/bridge-types.ts`）

```ts
interface DesktopBridge {
  platform(): Promise<'macos' | 'windows'>;
  chooseMediaFiles(): Promise<{ requestId: string; count: number }>;  // 只回身份，不回路径
  chooseFolder(): Promise<{ requestId: string; count: number } | null>;
  getAppVersion(): Promise<string>;
}
```

**关键设计：路径永不进 renderer。** 流程：

1. renderer 调 `chooseMediaFiles()`。
2. main 开原生多选对话框（`dialog.showOpenDialog`，`openFile` + `multiSelections`）。
   > 平台注意：Windows/Linux 上同一对话框不能既选文件又选目录，所以 `chooseMediaFiles` 和 `chooseFolder` 必须是两个入口。
3. main 拿到用户**本次明确选中**的绝对路径，直接 POST 给本地服务的新端点（带每次启动的认证 secret，见下）。
4. 服务端点调用**已有的** `registerLinkedSource(db, projectId, { filePath })`，一行业务代码都不写。
5. renderer 只收到 `requestId` 和素材数量，随后走**现有**素材列表接口刷新。

**新增端点** `app/api/desktop/import-linked/route.ts`

```
POST { projectId, filePaths: string[] }
→ 逐条 registerLinkedSource，返回 { assetIds, errors }
```

守卫（缺一不可）：

- `process.env.CREATIVE_STUDIO_DESKTOP === '1'` —— **复用现有开关**（`lib/final-edit/desktop-reveal.ts:6` 的既有模式），不要新造 flag。
- 每次启动的 secret（main 生成，经 env 传给服务子进程，main 调用时放请求头）。**secret 不得进 URL query、日志、崩溃报告，或任何 renderer 可读存储。**
- 只接受 main 提交。renderer 直接 `fetch` 这个端点必须失败 —— 这是"页面不能伪造绝对路径让后端读文件"的最后一道闸。

**为什么安全**：路径的唯一来源是用户在系统对话框里的明确点击，renderer 全程碰不到路径字符串。

**UI 改动（小）—— 落在批量侧，不是混剪侧**

> **不要碰 `components/mixcut/MaterialStep.tsx`** —— 那是 final-edit 子系统，写的是 `final_edit_external_assets` 表，**没有 linked 数据模型**，接上去会写错表或被迫新建一套 linked 支持（另一个量级的工程，见「明确不做」）。

- 桌面能力探测沿用 `BatchStepExport.tsx:125` 已有的 `revealAvailable ? 按钮 : 降级文案` 模式，**不要发明新的探测机制**。

**验收（本阶段的成败判据）**

## Phase 3：生命周期与进程树回收

**已确认的交互规则（07-31 用户确认，不重新讨论）**

- 关窗只隐藏，macOS 与 Windows 都继续后台运行，任务不停。
- 首次关窗给一次系统提示，说明任务仍在后台，并给重新打开入口。
- 再次点图标恢复原窗口原页面，不创建第二套服务。
- 只有明确"退出 Creative Studio"才真退出；有任务时先提示"暂停任务并退出"。

**退出编排**：main 先停接新桌面操作 → 调服务 `POST /api/shutdown`（Phase 0 已改成 await 编排）→ 有限等待 → 超时则 SIGTERM 子进程 → 再超时 SIGKILL → **验证无遗留监听端口和 ffmpeg 孤儿进程**。

**必须实测、不能假设**：Node `child_process` 在 macOS/Windows 上**不保证**自动清理整棵孙进程树（服务 → ffmpeg）。macOS 用 `detached: true` + `process.kill(-pid)` 杀进程组；Windows 需要 job object 或 `taskkill /T /F`。两平台都要真机验证。

**Windows 系统关机/注销不触发 `before-quit`** —— 所以正确性只能靠持久化 + 租约恢复，绝不能寄托在退出回调上。这一点现有租约制调度器已经满足。

## Windows 未来改 MSIX：可行性核实（2026-08-09 查证）

**结论：V1 不做。三个卡点任何一个单独都足以否掉，但架构上按下方"留门"处理，不堵死后路。**

### 卡点 1：loopback 限制 —— 对本架构是致命级，且有"上线才炸"陷阱

MSIX 包默认**禁止访问 localhost / 127.0.0.1**，即使声明了 `runFullTrust` 也一样。而本项目的整个形态就是 renderer 通过 `http://127.0.0.1:<port>` 访问本地 Next 服务 —— 这条限制直接打断主动脉。

full-trust 应用可以调 API 为自己解除该限制，所以**技术上有解**。但真正的风险在这句：

> Visual Studio automatically removes the localhost loopback restriction locally during development, which makes a great surprise at a later time when you realize that it doesn't work once installed on other machines.

**开发机上自动豁免，用户机上没有。** 本机测试全绿、装到客户电脑上连不上服务——这是最贵的一类 bug。若将来真上 MSIX，**必须在一台从未装过开发工具的干净 Windows 上验收**，不接受开发机测试结果。

### 卡点 2：签名是硬门槛，且当前地区拿不到便宜方案

- Windows **不安装未签名的 MSIX**，连 MDM 推送都不行（旧格式 exe 未签名只是弹 SmartScreen 警告，仍可安装）。
- 自签证书可用，但**每台目标机器都要先手动信任该证书**，对外分发不可行。
- Azure Trusted Signing（约 $10/月，**无需硬件令牌**）本是最优解，但截至 2025-04-02 仅对**美国/加拿大**、且有**3 年以上可验证历史**的法人开放；个人开发者入驻在公开预览期内暂停，同样限美加。**当前地区拿不到。**
- 剩余路径：传统 OV/EV 代码签名证书（更贵，且 2023-06 起 CA/B Forum 要求私钥必须存硬件令牌/HSM），或走 Microsoft Store 由微软代签（需开发者账号 + 通过认证审核）。

### 卡点 3：换了 MSIX 也不白送自动更新

`electron-builder` 有 `appx` target，但 **`electron-updater` 明确不支持 AppX/MSIX** —— AppX 自动更新由 Microsoft Store 负责。想脱离 Store 自动更新，要自行配置 `.appinstaller` 文件加托管更新源，是另一套独立工程。

### 留门设计（本次就做，成本几乎为零）

1. **服务地址解析集中在 `desktop/service.ts` 一处**，不散落到 main/preload/renderer。将来加 loopback 豁免只改这一个文件。
2. **打包脚本拆成两步**：`产物装配`（Electron 包 + Node 服务 payload + FFmpeg）与`安装器封装`（Inno Setup）。换 MSIX 时只替换第二步。
3. **数据根继续只用 `CREATIVE_STUDIO_DATA_ROOT` 指向用户目录，不写注册表、不写安装目录。** MSIX 的文件系统/注册表虚拟化会重定向这类写入 —— 本项目**现状已经天然满足**这一条，只需在 Phase 4 加一条断言防止将来退化。

## 明确不做（防止范围膨胀）

- **自动更新**：Electron 内置 `autoUpdater` 只认 Squirrel.Windows / MSIX，你现在是 Inno Setup，**不兼容**。V1 继续手动下载安装包。界面和发布说明**不得出现"自动更新"字样**。
- **Windows 改 MSIX**：见上节三个卡点，V1 不做，只留门。
- **混剪侧（final-edit）的原生导入 / 链接不复制**：V1 只做批量侧。混剪侧的 `final_edit_external_assets` **没有 linked 数据模型**，要补就得新增来源表、健康核验、掉线状态、重定位一整套——等同于把 batch-production 的 `media-catalog.ts` 在另一个子系统重做一遍。混剪侧 V1 维持现有的 256 MB 浏览器上传。**另开票。**
- **全 API 认证**：113 条路由现在就对本机任意进程开放，这是浏览器版的既有状态，不是 Electron 引入的回归。本次只给 `desktop/*` 新端点加认证。全 API 加固另开票，避免一次改动扫过所有路由。
- **迁移业务逻辑进 Electron main**：一行都不迁。
- **改 `data/`、`storage/` 位置**：继续通过 `CREATIVE_STUDIO_DATA_ROOT` 传现有路径（macOS 装机版是 `~/Library/Application Support/CreativeStudio`），擅自换目录会让老用户数据消失。

## 执行顺序与止损点

```
Phase 0（服务优雅停机）—— 独立价值，即使不做 Electron 也该做
   ↓ 止损点：做完可停，浏览器版已受益
Phase 1（壳骨架）
   ↓ 止损点：能起窗口就证明边界成立；不成立则此时放弃，存量零损伤
Phase 2（原生导入）←—— 全部价值在这里兑现
   ↓ 止损点：到这里已可自用
Phase 3（生命周期）
Phase 4（打包分发）←—— 只有要对外发版才需要（含签名公证成本）
```

每个 Phase 独立可交付、可回退。Phase 1 之前不动任何现有文件（Phase 0 只碰 3 个文件且有独立价值）。**"迁不动"的风险被压在 Phase 1 结束时可判定**——那时若发现边界不成立，损失只是一个可整目录删除的 `desktop/`。
