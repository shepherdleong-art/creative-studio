# 批量生产与视频生成问题修复方案（交接执行文档）

来源：`docs/0804-2251-修改需求`（用户反馈 8 条）。本文档面向执行代理：每条问题给出**现象 → 根因（带 file:line 证据）→ 修改方案 → 验证方式**。所有证据已在 `batch-m7-ui-defects` 分支（`e766a6d`）的代码上逐条核实并复核过一轮。

**复核补入的关键修正**（原稿有误、照原样实现会出事的地方，已就地改进方案）：问题 1 只改建表默认值对存量库无效；问题 6 换封面必须走原片而非成片。其余以「**注意**」形式标在各方案条目下。另：**问题 4 经用户拍板**——正常使用必配视觉供应商，不做"无供应商时降级 technical"的通路，采用单按钮方案（无供应商时置灰 + 指引文案）。

## 执行须知（仓库约定，先读）

- 技术栈：Next.js 16（App Router）+ React 19 + TypeScript strict + Tailwind CSS 4 + better-sqlite3。
- 没有 `npm test`。测试是 `scripts/*.test.ts` 和 `scripts/*.test.mjs`，用 `node scripts/<name>` 直接运行（Node 22+）。改动某模块后跑相关测试——**按文末速查表点名跑，别猜文件名**（比如改 `lib/video-queue.ts` 要跑的是 `scripts/video-polling-policy.test.ts`，仓库没有 `video-queue` 开头的测试）。改完跑 `npm run lint`。
- 数据库迁移纪律：批量生产走 `lib/batch-production/schema.ts` 逐版本迁移，**只能追加新版本号，不得修改已发布条目**；核心表走 `CORE_DB_MIGRATIONS` 追加式。批量迁移前必须经过 `lib/schema-upgrade/` 的备份+锁+审计。
- 本地文件路径一律走 `dataRoot()`，不硬编码 `data/`、`storage/`。
- UI 文案中文。日志不打印密钥（`lib/logger.ts` 会脱敏）。
- 最小改动原则：每条问题按方案改到位即可，不顺手重构无关代码。

## 执行顺序建议

- **批次 A（后端性能，收益最大、风险低）**：问题 2 → 问题 1
- **批次 B（流程死锁，中等改动）**：问题 7 → 问题 5
- **批次 C（UI 重构，改动最大）**：问题 3 → 问题 4 → 问题 6/8

## 问题 1：视频生成越到后面越慢，退化成"单个单个生成"

### 根因（按可能性排序）

1. **300 秒轮询窗口悬崖 → `needs_check` → 只能手动逐条补抓（最直接原因）**
   `lib/video-queue.ts:24` `DEFAULT_VIDEO_TIMEOUT_MS = 300_000`；轮询超 5 分钟即转 `needs_check` 并释放 worker（`lib/video-queue.ts:318-325`）。而补抓接口 `app/api/video-jobs/[id]/resume-poll/route.ts:71` 每次点击只轮询**一次**，还在跑就保持 `needs_check`；UI 的 3 秒自动刷新不包含 `needs_check` 状态（`components/VideoGenerationPanel.tsx:230-233`）。
   推理：供应商随任务积压越来越慢（见根因 2），后面的任务纷纷超过 5 分钟掉出自动化管线，用户只能对着卡片一张张点「补抓结果」——这就是字面意义上的"单个单个生成"。

2. **供应商侧排队/限流，本地无每供应商限速**
   `lib/provider-concurrency.ts:8-14` 是纯透传且只被图片队列引用；视频侧唯一节流是**每项目** 3 并发（`lib/video-queue.ts:21-23`，`VIDEO_CONCURRENCY` 环境变量；`runningQueues` 按 projectId 建队列，每队列开 concurrency 个 worker，所以多项目同时跑时总并发是 3×N）。前 3 条立即在远端开跑所以"前面快"，之后的任务在供应商侧排队，实际速度退化为供应商的真实并发度。

3. **适配器内部超时被误判为"用户取消" + 视频任务零自动重试**
   三个视频适配器的 submit 有独立 120s 超时、poll 有 30s 超时（如 `lib/video-providers/kling.ts:95-96,141-142`）；这些内部 AbortError 在 `lib/video-queue.ts:327-334` 被归到「Canceled by user」分支写成 `canceled`。同时 `video_jobs.maxAttempts` 默认 1（`lib/db.ts:285` 附近），首次失败即终态，只能单条手动重试。对照：图片队列有自动重试（`lib/queue.ts:762-776`）。

4. 次要：3 个 worker 全程独占（提交+轮询+下载一体，`lib/video-queue.ts:100-124, 271-295`），下载大文件期间占槽；领取顺序 `ORDER BY id`（uuid 随机序，`lib/video-queue.ts:354-357`）与 UI 的 `createdAt DESC` 不一致，造成"后面的先跑"的混乱观感。

### 修改方案

- **P0-a 轮询窗口加大并可配**：引入 `VIDEO_TIMEOUT_MS` 环境变量，默认从 300s 提到 15 分钟。
  **不要另起炉灶：按供应商给默认值的 seam 已经存在**——`lib/video-polling-policy.ts` 的 `resolveVideoPollingTimeoutMs` 取 `max(请求值, 适配器最小值)`，适配器通过可选的 `VideoProviderAdapter.minimumPollingTimeoutMs(request)` 声明下限，jimeng seedance-2 15 分钟就是它的第一个使用者（`lib/video-providers/jimeng.ts:53-61`）；`lib/video-queue.ts:239-243` 已经在调这条链路。所以本条只要做两件事：(1) 把 `DEFAULT_VIDEO_TIMEOUT_MS`（`lib/video-queue.ts:24`）改成读 `VIDEO_TIMEOUT_MS` 且默认 15 分钟（写法参照同文件 :21-23 的 `VIDEO_CONCURRENCY` 钳制）；(2) 需要给某个供应商更长下限时，在该适配器实现 `minimumPollingTimeoutMs`，别改队列。对应测试是 `scripts/video-polling-policy.test.ts`。
- **P0-b `needs_check` 自动续跑**：队列仍活跃时，对 `needs_check` 任务自动续跑一个轮询窗口（而不是掉出管线）；或把 `resume-poll` 改为服务端循环轮询直到出结果/超时。UI 的自动刷新集合把 `needs_check` 纳入（`VideoGenerationPanel.tsx:230-233`）。
- **P0-c 修取消误判**：`runVideoJob` 的 catch（`lib/video-queue.ts:327`）只用队列级 `abort.aborted` 判定用户取消；适配器内部超时（reqAbort 触发）映射为普通可重试错误。
- **P0-d 自动重试**：把 `video_jobs` 的有效重试上限提到 2–3。
  **只改 `lib/db.ts:285` 的建表默认值是无效的**：那是 `CREATE TABLE ... maxAttempts INTEGER NOT NULL DEFAULT 1`，只影响新建库；存量库的列默认值和存量行都还是 1，而两处 INSERT（`app/api/shot-sets/[id]/video-jobs/route.ts:58`、`app/api/shot-sets/[id]/video-jobs/batch/route.ts:83`）都不显式写 `maxAttempts`，一律吃默认值。二选一：
  - **推荐（运行时兜底，零迁移）**：照图片队列的成熟写法，在 `runVideoJob` 的失败分支把 `job.maxAttempts` 换成 `job.maxAttempts || DEFAULT_VIDEO_MAX_ATTEMPTS`（对照 `lib/queue.ts:762` 的 `job.maxAttempts || maxAttempts || 2`），同时把 `lib/db.ts:285` 的默认值一并改成 2（让新库直观一致）。注意 `video-queue.ts:338` 的判定和 :149 的日志文案都读 `job.maxAttempts`，要一起走同一个兜底值。
  - **或（显式落库）**：往 `CORE_DB_MIGRATIONS` 追加一条 `UPDATE video_jobs SET maxAttempts = 2 WHERE maxAttempts <= 1`，并让两处 INSERT 显式写入。追加式纪律照旧：只加新条目，不改已发布条目。
  注意防重复扣费纪律：**拿到供应商 task_id 之后的失败不允许重新 submit**，走 `needs_check` 补抓；只有 submit 前/未拿到 task_id 的失败才自动重试。
- **P1**：每供应商并发闸门（按 providerId 统计 running 数，在 `claimNextVideoJob` 处拦截；默认值可内置，如 kling=2）。两个坑：
  - 队列是**按项目**建的，所以 running 数必须**跨项目**统计（`SELECT COUNT(*) FROM video_jobs WHERE providerId = ? AND status = 'running'`，不带 projectId 条件），否则闸门在多项目并行时形同虚设。
  - worker 在 `claimNextVideoJob` 返 null **且**本项目 running 数为 0 时会直接 `break` 退出（`lib/video-queue.ts:109-116`）。加了闸门后必须能区分"被闸门挡住"和"真没活了"（例如让 claim 返回 `'gated'` 而不是 null，或退出前再查一次本项目 pending 数），否则会出现 pending 任务留在库里没人跑的静默停摆。
- **P2**：领取顺序改 `ORDER BY createdAt, id`；下载阶段与 worker 解耦（可选）。

### 验证

- `node scripts/video-polling-policy.test.ts`（超时解析）、`node scripts/video-auth.test.ts`、`node scripts/media-download-policy.test.ts` 全绿。
- 构造一个 poll 永远 processing 的假适配器单测：超过旧 300s 窗口后任务仍被续跑而不是转 `needs_check`（或按新超时配置生效）。
- 构造适配器内部 AbortError，断言状态不是 `canceled`。
- 断言存量库（`maxAttempts = 1` 的旧行）在新逻辑下也能重试一次。

## 问题 2：进入「智能混剪 → 批量生产」很慢，像在一直刷新

### 根因（按影响排序）

1. **`prepare` 每次调用全量重复哈希 + ffprobe（主因）**
   `GET /api/batch-production/prepare` → `lib/batch-production/prepare.ts:109` 每次串行做：
   - `registerModule4Video`（prepare.ts:130-136）对**每一个**已成功的 `video_job` 逐个 await，**不检查是否已登记**：每次 = 1 次 ffprobe 子进程 + 1 次完整文件 SHA-256（`lib/batch-production/media-catalog.ts:280-282`，哈希在 `resolveAssetId` 查重之前就执行）。
   - `verifyAssetSources`（prepare.ts:140-142）对**每个素材的每个来源**再算一遍完整 SHA-256（media-catalog.ts:396 附近）。
   - 即每次进入 ≈ 把全部素材完整读盘 3–4 遍，全部串行 await。

2. **缩略图端点每次请求重复哈希**
   素材网格每张图走 `GET /assets/[assetId]/thumbnail`（`components/batch-production/BatchStepMaterials.tsx:253` 等），服务端 `lib/batch-production/project-asset-media.ts` 每次请求做 **2 遍全量 SHA-256 + 1 次 ffprobe**（:146、:174、:160；第二遍是 TOCTOU 设计），且响应头 `Cache-Control: no-store`（`lib/batch-production/project-asset-media-response.ts:9`），浏览器每次重挂载都重新请求一轮。

3. **分析任务每完成一个就整页重载，放大 1+2**
   `BatchPreparationPanel.tsx:519-530`：任何素材分析任务 succeeded → `void load()` → 整个 prepare 全量重跑。分析 N 个素材 = N+1 次全量哈希。

4. **前端重复/永不停止的轮询**
   `loadProxyTasks`（:306）和 `loadBatchTasks`（:447）拉的是**同一个** `GET /batches/[id]/tasks`；workspace 轮询条件 `counts.processing > 0`（:428）把 waiting/paused 卡片也算进 processing（`lib/batch-production/batch-workspace.ts:387`），导致只要还有没开始的卡片就永远每 3 秒轮询——这是"一直在刷新"的观感来源。

### 修改方案

- **P0-a 登记快速路径**：`registerModule4Video` 开头先按 `videoJobId` 查 `batch_asset_sources` 是否已有 module4 来源；已登记且文件 stat（size + mtime）与记录一致 → 直接返回已有 assetId，跳过 ffprobe 和哈希。stat 变了才重验。
- **P0-b 来源核验快速路径**：`verifyAssetSources` 同样加"文件 stat 未变则信任上次哈希"的快速路径；或把健康核验降为低频/后台异步，prepare 直接返回上次已知状态。
- **P0-c 缩略图缓存**：缩略图 URL 按内容指纹版本化（URL 本身不可变），响应头改 `immutable` 长缓存；服务端命中已发布缩略图时跳过重复核验。
  **注意：后端磁盘缓存已经存在，别重复造。** `lib/batch-production/project-asset-media.ts:50-54` 的 `thumbnailRelativePath` 已经按 `projectId+assetId+完整指纹` 落盘到 `storage/batch-media/thumbnails/<hash>/<hash>/<fingerprint>.jpg`，`materializeProjectAssetThumbnail`（:265-286）还有 in-process 的 `thumbnailJobs` 并发去重和原子发布。真正缺的只有两处：
  1. `materializeProjectAssetThumbnail` **无条件**先跑 `resolveVerifiedProjectAssetMedia`（双全量 SHA-256 + ffprobe），磁盘缓存已命中也不跳——这里加早退路径；
  2. URL 里不带指纹、且 `PROJECT_ASSET_MEDIA_HEADERS` 是 `no-store`（`project-asset-media-response.ts:8-11`）——把指纹写进 query/path 并对缩略图单独用 `immutable` 头（原片预览端点保持 `no-store`）。
  **安全边界（这条动的是 CLAUDE.md 明写的不变量，必须按此改）**：第一遍全量 SHA-256 **不能省**——省了就会在原片被替换后继续吐旧缩略图。可以省的是"命中已发布缓存后的第二遍复核"，用 `projectAssetFileIdentity` / `matchesProjectAssetFileIdentity`（:62-75，dev+ino+size+mtimeMs）做身份比对即可，这套身份比对本来就已经用在缩略图发布前的复核上（:240-249）。改动要连 `scripts/batch-asset-preparation.test.ts` 的相关断言一起更新，并在 PR 说明里写清哪一遍被替换成 stat 身份比对、为什么安全。
- **P1-a**：分析任务完成回调（:519-530）只局部更新该素材的分析状态，不整页 `load()`。
- **P1-b 轮询收敛**：合并 :306 与 :447 为一次 `/tasks` 拉取派生两种视图；workspace 轮询条件排除纯 waiting（无活跃任务即停）；串行 await 改有限并发。

### 验证

- `node scripts/batch-media-catalog.test.ts`、`node scripts/batch-asset-preparation.test.ts`、`node scripts/batch-prepare.test.ts`、`node scripts/batch-production-prepare-route.test.mjs` 全绿；为"已登记素材不重复哈希"补一个单测（mock computeFileSha256 计数或直接断言行数/耗时）。
- 手工：准备一个含 10+ 素材的项目，两次进入批量生产，第二次应明显快（无全量读盘）。

## 问题 3：准备素材区域 3 个滚动条；画质/LUT/代理占地太大

### 根因

三层纵向滚动条从外到内：

2. **shell 主区滚动**：`.mainCol { overflow-y: auto }`（mixcut-shell.module.css:193），shell 固定高 `calc(100dvh - 230px)` 且 `overflow: hidden`（:39-43）。
3. **素材列表内滚**：`BatchStepMaterials.tsx:234` 和 `:297` 的 `h-[clamp(400px,56vh,760px)] overflow-y-scroll` 固定高内滚区。（同文件 :102-105 的注释自称"没有固定高度内滚区"，注释已过期，改完顺手修正。）

「画质与调色（进阶）」折叠区（`BatchStepMaterials.tsx:337-509`）默认收起，但展开状态持久化到 localStorage `batch-media-prep-open`（:107-113, 142-146）——**展开过一次就永远展开**，里面是 LUT 导入/列表、低清预览片生成+任务列表、缓存清理三个全宽 tile。

### 修改方案

- **P0-a 消灭第 3 层滚动**：去掉 :234/:297 的固定高 `overflow-y-scroll`，让素材网格在主区 `.mainCol` 单一滚动层内自然排布（回到该文件注释描述的原始设计）。
- **P0-b 进阶设置弹窗化**：素材区工具行放一个「画质与调色」小按钮，点击弹出 modal（复用现成的预览弹窗模式，`BatchPreparationPanel.tsx:1562-1595` 的 `role="dialog"` 结构），把 LUT、低清预览片、缓存清理三个 tile 原样搬入；删除 localStorage 展开态和常驻 section。
- **保留**：已勾选素材卡底部的 LUT 下拉 +「为当前素材生成代理」按钮（`BatchInputSelectionCards.tsx:335-360`）——它是快照输入的一部分、操作频率最高。
- P2：检查低视口下 shell `min-height:560px` 与页头叠加导致的窗口滚动，必要时让 shell 高度减去实际页头高度。

## 问题 4：「基础分析」和「内容分析」并存，用户困惑

### 根因

- 数据模型：`batch_assets.currentAnalysisId` → `batch_asset_analysis`，能力级别写在 `analysisJson.analysisLevel`（technical = 本地 FFprobe 媒体参数；content = FFprobe + 视觉模型语义分析）。**勾选门槛是"有过任意一次分析"**——`BatchInputSelectionCards.tsx:191` 是 `asset.status === 'online' && Boolean(asset.currentAnalysisId)`，不校验级别；content 只影响"按画面语义分配"的质量。
- **背景约束（已核实）**：两个按钮的可用条件不同。「基础分析」`disabled={analysisCandidates.length === 0 || analysisBusy !== null}`（`BatchStepMaterials.tsx:214`），**不依赖视觉供应商**；「内容分析」`disabled={!visionProviderId || visionProviderMissing || ...}`（:220），没配视觉供应商就是灰的，后端 `executors.ts:164-170` 也要求 `contentRequest.providerId` 指向一个启用了 `supportsVision` 的脚本供应商。即：删掉「基础分析」后，无视觉供应商的环境将无法让素材变成可勾选——**用户已拍板接受这个代价**（正常使用必配视觉供应商），界面只需给出明确指引。
- UI 把内部分级直接暴露成两个并排按钮：「基础分析（N）」（`BatchStepMaterials.tsx:211-216`）和「内容分析待补齐（N）」（:217-222），再加三套卡片徽标文案（「待分析 / 基础分析可用 / 内容分析可用」）。
- 注意：**「一键全选」已经存在**（`BatchStepMaterials.tsx:223-229` → `BatchPreparationPanel.tsx:1222-1241`），用户写需求时该功能尚未发布，无需重复实现。

### 修改方案（纯前端，后端不用动）

- **P0-a 单入口**：素材区头部只留一个主按钮「内容分析（N）」，**删除「基础分析（N）」按钮**（:211-216）。候选集 = `contentAnalysisCandidates`（`BatchStepMaterials.tsx:149`，所有 `analysisLevel !== 'content'` 的在线素材——从未分析的素材 `analysisLevel` 为 undefined，天然包含在内），调 `analyzeAssets(ids, 'content')`。**链路已核实可一步走通**：后端 content 任务内含 FFprobe 先行探测（`lib/batch-production/executors.ts:154` 的 `resolveVerifiedProjectAssetMedia`），analyze 路由对 assetIds 也没有"须先跑过基础分析"的限制（`app/api/batch-production/batches/[id]/assets/analyze/route.ts:79-93`），所以从未分析的素材可以直接跑内容分析，不需要 technical 前置。

- 视觉模型下拉保留在按钮旁（现状 :199-210）。
- 小坑：`analyzeAssets` 的 busyKey 用候选集大小判断"全部"（`BatchPreparationPanel.tsx:627`），两个候选集合一后这段逻辑自然简化，注意同步。它内部还会按 mode 重算一遍 candidates（:614-622）并在为空时给出 `mode === 'content' ? '在线素材都已有内容分析。' : '没有需要基础分析的在线素材。'` 的提示——单入口后 technical 分支没有调用方了，连带清理掉。

## 问题 6 + 问题 8：检查成片无确认机制、不能换封面、预览太小（合并重做）

用户期望：封面墙（只看封面，看得清）→ 点击弹窗预览视频 + 修改（含封面）→ 封面下方可单条标记"可以"→ 一键全选 → 旁边「通过 / 返工 / 取消」推进流程。

### 根因

- 卡片上唯一操作是「重新渲染」（仅 task failed 时显示，`BatchStepReview.tsx:222-224`）、「换一批画面」（reallocate，:225-229），以及一个**界面上没有可见文案的勾选框**（:142-150，实际是给导出步骤用的选择——只有 `aria-label="选择成片 N"` 和禁用时的 title 提示，肉眼看不出用途）。领域里没有"用户审核通过"概念（全 `lib/batch-production/` 无 approve/review 字段）；「等待中」是"等待调度"（`batch-workspace.ts:198`），不是"等你确认"。
- 封面是渲染时**从原片第一镜头**抽帧（`batch-renderer.ts:779-793`，`-i first.sourcePath`），**批量域没有任何封面自定义入口**。
- 布局：网格 `lg:grid-cols-2`（:117），卡内媒体区 `sm:grid-cols-[minmax(0,1fr)_10rem]`（:181），封面被挤在 160px 宽窄条里（:188-192）。

### 修改方案（分两期，先做 A 再做 B）

**A. P0 封面墙 + 弹窗预览（纯前端，不改领域模型）**

1. `BatchStepReview` 网格改为封面墙：3–4 列、每卡以 `aspect-[3/4]` 封面大图为主视觉 + 脚本名 + 状态徽标；去掉卡内小视频。封面 URL 逻辑（`BatchStepReview.tsx:71-76` → `GET .../outputs/[planId]/media?kind=cover&source=candidate|artifact`）原样复用。
2. 点击封面开弹窗：复用现成 modal 模式（`BatchPreparationPanel.tsx:1562-1595`），内放全宽 `<video>` 预览 + 卡片详情（状态、失败原因、blockers）。
3. 把那个无可见文案的勾选框改成明示文案「选中」（A 期它仍然只驱动导出选择，但**文案不要写死成"选中导出"**，理由见下方第二条注意）；底部操作栏放「一键全选 / 全不选」。
   **注意（跨期依赖）**：该勾选框当前 `disabled={!card.publishable}`（`BatchStepReview.tsx:146`），而在问题 7 的死锁场景下全部卡片 `publishable=false`。**只做 A 不做问题 7，「一键全选」会一条都选不中**——这不是全选做坏了。所以执行顺序必须是批次 B（问题 7）在批次 C（问题 6/8）之前，A 期自测也要在有可导出成片的批次上做。
   **注意（与用户原话的语义冲突，B 期定案前必须想清楚）**：需求原文是"点击封面下方的名字或者小窗口来告诉系统，说 ok 这个视频我觉得可以"——用户心里那个框就是**审核通过**，不是导出选择。若 A 期把它固定成"导出选择"、B 期再另加一套 通过/返工，同一张卡上会出现两套选择机制，正是用户抱怨的"混乱"。**推荐口径**：勾选框只保留"选中"这一个语义（既是审核对象也是导出对象），旁边的「通过 / 返工 / 取消」是对**当前选中集**的批量动作。A 期文案就按「选中」写，别写「选中导出」，给 B 期留出空间。

**B. P1 审核机制 + 换封面（需要新领域概念和新 API）**

4. 审核状态：扩展点选 `batch_output_versions.arrangementJson` 加 `review: {decision:'approved'|'rework'|null, decidedAt}` 字段——就地 JSON 升级有先例（`narration-executor.ts:257-265` 的 `json_set(arrangementJson, '$.narration', ...)`），**零迁移**；`arrangementJson` 全仓只有两处写入（`plans.ts:190` 的 INSERT 和上述 json_set），也没有整体指纹，所以加字段是安全的。若倾向列存储，则按纪律在 `lib/batch-production/schema.ts` 追加新版本迁移。
   **注意**：`reallocate` 会走 `plans.ts:190` INSERT 一个全新 output version、写全新 arrangementJson，**审核态自然丢失**。语义上"换了画面要重新审"是正确的，但要在 UI 上明确表达（返工/换画面后卡片回到未审核态），否则会被当成 bug 修回来。
5. 新 API：`POST /api/batch-production/batches/[id]/outputs/review`，**body 接受 `planIds: string[]` + `decision`**（而不是 per-planId 端点）。「通过」写 approved；「返工」写 rework 并可联动现有 `POST .../outputs/[planId]/reallocate`（换画面）或 `POST /tasks/[taskId]/retry`（重渲染）。
   **为什么是批量端点**：交互是「一键全选 → 点通过」，per-planId 端点会退化成 N 次串行请求，中途失败还没有一致的回滚语义。
6. 门禁接线：`publishSelectedBatchOutputs` 的闸门（`phase-e.ts:419`，函数体从 :340 起）增加"已 approved"条件——这是**权威的服务端单点判断，必须加**。
   **注意：不要把 approved 直接并进 `publishable`（`batch-workspace.ts:372`）**。`publishable` 同时驱动三处：勾选框的 disabled（`BatchStepReview.tsx:146`）、`counts.publishable`（`batch-workspace.ts:387`）、以及导出页那句报错文案（`BatchStepExport.tsx:69-73`）。若 approved 并入 `publishable`：(a) 未审核 → 勾选框禁用 → 没法勾选去审核，形成回路；(b) `counts.publishable === 0` 会让导出页显示"成片需要配音、字幕、封面与背景音乐齐全"，对"只是还没审"的情况是错误归因。
   **正确做法**：`publishable` 保持"技术上可发布"的语义不变，另加一个 `approved` 字段和 `counts.approved` 计数；导出页按 `publishable && approved` 筛选，并把"N 条待审核"作为**独立**的一条提示（与问题 7 P0-c 的 blockers 列表并列，不要混在同一句里）。
7. 换封面（简化版先行）：新 API `POST .../outputs/[planId]/cover` 接受抽帧时间点，**改写 `arrangement.cover` 的时间点后重跑封面抽帧，仍然从原片抽**。
   **注意：不能"从成片抽帧"。** 渲染器的封面来自原片第一镜头（`batch-renderer.ts:781-791`：`-ss <t> -i first.sourcePath`），时间点已有现成数据 seam `arrangement.cover.timeUs ?? frameTimeUs ?? sourceTimeUs`（:783-784），并且硬性约束 `first.sourceStartUs ≤ t < first.sourceEndUs`（:785，越界直接 throw「封面冻结时间点不在第一镜头原片区间内」）。正式导出还会核验 `arrangement.cover.assetId` 指向的原片（`phase-e.ts:423-431` → `checkFormalExportPreflight`）。改成从成片抽帧会同时打破 original-media-only 不变量和导出预检，卡在发布环节。
   因此 UI 上的时间轴范围要限制在**第一镜头的原片区间**内（把 `sourceStartUs/sourceEndUs` 一起下发给前端），而不是成片全长。`batch-export.ts` 发布按 coverRelativePath 成对复制并校验指纹（:117、:169、:231-264），走原片抽帧这条路时封面产物仍由 renderer 产生、指纹链不变，无需改发布路径。完整封面编辑器（主副标题/字体，参考 `components/mixcut/CoverEditorDrawer.tsx`）工程量大，建议另立迭代。
8. 状态轮询注意：引入"等待审核"后，检查 `counts.processing` 的构成（`batch-workspace.ts:387` 把 `waiting`/`paused` 也算进 processing），别让待审核卡片导致轮询永不停、也别让审核中状态被漏算。这一条与问题 2 的 P1-b 是同一处代码，两条一起改。

### 验证

- 封面墙清晰可见；弹窗能播放视频；通过/返工状态落库并在刷新后保持；未通过项不出现在可导出集合；换封面后导出包里是新封面。
- 未审核项在导出页显示的是"待审核"而不是"缺配音字幕封面BGM"。
- reallocate 之后该卡回到未审核态，且 UI 有明确提示。
- 封面时间点选在第一镜头原片区间之外时被前端拦下（或后端返回可读错误），不产生半成品。
- UI 契约测试：`node scripts/batch-phase-e-ui-contract.test.mjs`、`node scripts/batch-preparation-workspace.test.mjs`。

## 问题 7：导出报"当前没有可导出的成片"，用户卡死

### 根因（死锁链）

1. 口播任务失败或未配置 TTS 时，渲染任务**不等待口播**，直接产出 `silent_placeholder` 静音样片（`batch-renderer.ts:682-687`）。
2. 口播后来成功时只是**就地升级 arrangement.narration**（`narration-executor.ts:256-265`），**不会触发已成功的静音候选重渲染**；`scheduleAllocationRenderTasks`（`phase-e.ts:71-94`）只取消 queued/running/failed 的旧渲染，不动 succeeded 的。
3. 于是卡片有预览但 `publishable=false`（`publishable` 强制要求 `audioMode==='narration'`，`batch-workspace.ts:372, 142-163`）；检查页对它没有任何重渲染入口（按钮只在 failed 时出现）；导出页只显示一句「当前没有可导出的成片——成片需要配音、字幕、封面与背景音乐齐全。请在检查页确认渲染完成后重试。」（`BatchStepExport.tsx:69-73`）——文案让用户去检查页，但检查页没有能改变局面的操作。**死锁。**

### 修改方案

- **P0-a 打通重渲染链路**：口播任务成功提交后（narration-executor 落账处），对同脚本快照下 `audioMode='silent_placeholder'` 的已成功渲染候选**自动排队一次重渲染**（新建 render task 指向当前 output version；renderer 会通过 `resolveNarrationFromArrangement` 读到已核验口播，`batch-render-executor.ts:93-111`）。这是让 `publishable` 从 0 变非 0 的关键缺口。
- **P0-b 检查页补入口**：对 `silent_placeholder` 候选显示「重新渲染（带配音）」按钮（放宽 `BatchStepReview.tsx:222` 的 `card.task?.status === 'failed'` 显示条件），复用 `POST /tasks/[taskId]/retry`。
- **P0-c 文案可操作化**：导出页的提示改为列出每条不可导出的具体原因（数据已有：`card.blockers`、`candidate.audioMode`），如「N 条缺少配音：前往检查页重试配音/重新渲染」。同步更新 `humanizeSkipReason`（`BatchPreparationPanel.tsx:104-117`）的映射，新增跳过原因都要有人话文案。

### 验证

- 复现死锁路径：不配 TTS 开跑 → 得静音候选 → 配好 TTS 重跑口播 → 静音候选自动（或一键）重渲染为带口播版 → 可导出。`scripts/batch-*.test.ts` 中 phase-e/narration 相关测试全绿，并为"口播成功触发静音候选重渲染"补单测。
