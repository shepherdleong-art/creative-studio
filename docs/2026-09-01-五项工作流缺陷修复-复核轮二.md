## 3. F3 / F4 修复的实现核验

`components/batch-production/BatchTimelinePreview.tsx`：

- **首帧标记与源标记拆开**（`:451-452`、`:465-466`）。`lastBgmFileUrlRef` 只记"上一次的源"，
  `bgmSyncInitializedRef` 单独记"这个 effect 是否跑过第一次"，`null` 不再兼任两种语义。
- **`if (!element) return`（`:462`）不会误吞初始化标记**。我确认组件只有 `:640` 一个 `return (`，
  `<audio ref={bgmRef}>` 在 `:705` 无条件渲染，因此 effect 首跑时 `bgmRef.current` 必非 null，
  不存在"守卫先返回、标记没置上、后续换源被当首帧跳过"的二次踩坑。
- **异步分支读 ref 而非闭包**（`:477` `const currentSec = lastDrivenSecRef.current`），
  音量包络输入另立 `bgmLevelsInputRef` 并在每次渲染后的 effect 中同步（避开渲染期写 ref 的
  React 编译器红线）。effect 依赖收敛成 `[bgmFileUrl]`，语义正确：只有换源才该重跑。
- **监听器有 cleanup**（`:501`），与同文件 `:257` 的既有惯例一致，快速连换两首不会留下过期 seek/play。

## 4. 新 findings

### G1（P3）`rowid` 决胜漏了三处读取端

`fada88e` 给列表 API、项目/分镜组 ZIP、creative-package、Mixcut context 都补了 `rowid` 决胜，
但下面三处仍是 `ORDER BY createdAt, id`。整批共用一个 `createdAt` 之后，决胜落到 UUID v4：

- `lib/video-queue.ts:585`（`claimNextVideoJob`）——**这处最刺眼**：它上面的函数注释明写
  「领取顺序与 UI 的 createdAt 一致，避免"后面的任务先跑"的混乱观感」。整批同 createdAt 后，
  批内领取顺序变成 UUID 随机，这句注释在批内已不成立。
- `lib/video-queue.ts:627`（`claimNeedsCheckVideoJob`）——续跑领取，同因。
- `lib/batch-production/prepare.ts:135`——成功视频登记为批量素材（`registerModule4Video`）的顺序，
  批内同样落到 UUID。

**不比基线差**：基线 `abaadcd` 的批量插入根本不写 `createdAt`，走 `DEFAULT (datetime('now'))`
秒级并列，批内本来就由 UUID 决胜。所以这是"没修全"，不是"改坏了"。
但它与 `fada88e` 自己 commit message 的说法（"add rowid as the stable tiebreaker … so identical
timestamps keep insertion order"）对不上，也和交付摘要 §10 F5 行的口径对不上。

**修复方向**：三处 `ORDER BY createdAt, id` → `ORDER BY createdAt, rowid`（`video-queue` 两处保留 `LIMIT 1`）。

### G2（P3）F5 的对齐在最主要的展示位被既有 status 排序抵消

`components/VideoGenerationResults.tsx:67-69` 在拿到列表 API 结果之后，又按状态重排：

```ts
const order: Record<string, number> = { succeeded: 0, running: 1, pending: 2, needs_check: 3, failed: 4, canceled: 5 };
```

`Array.prototype.sort` 稳定，所以同状态内保留 API 顺序——但**跨状态会重排**。
于是 API / ZIP / Mixcut 三层现在确实是 V01→V02→V03 了，用户在视频结果卡上看到的批内顺序
**仍然会随任务陆续完成而跳位**。

这是既有行为、本轮没引入（轮一 F5 已备注），但它决定了 F5 这次对齐在用户侧只兑现了一半。
C4 给图片定的红线是"状态不参与位置计算"，视频这条链路至今没有同等约束。
**要不要把这个 status 排序也去掉是产品决定，不是 bug**——但如果不去掉，
交付摘要里"批内 V01→V02→V03 与 C4 图片规则对齐"这句在视频结果卡上并不成立。

### G3（P3）交付摘要的构建证据口径比实际强

交付摘要 §3 写 `npm run build` "反馈修复轮重跑一次（含 standalone 资产同步）"，§10 也把
`npm run build` 列进反馈轮定向验证。但复核开始时的实际状态是：

```
.next/BUILD_ID          Sep  1 21:30
find .next -newermt "2026-09-01 21:35" | wc -l   →  0
```

而 `71786b3` 提交于 21:35、`fada88e` 提交于 21:53。**`.next` 里没有任何文件新于 21:35，
说明最后一次构建早于这两个 commit**——`fada88e` 改的五个路由文件从未进过 `npm run build` 验证。
（`71786b3` 的情况有歧义：代码可能在 21:30 前就已改好并构建，21:35 才提交。）

我已自行补跑 `npm run build`（exit 0）与 `npx tsc --noEmit`（exit 0），**结论不受影响**，
但摘要的证据陈述应当与实际执行顺序一致，否则下一轮 review 无法据此判断"哪些改动进过构建"。
