# 固定渲染命令与验收契约

本文记录 `lib/film-render/` 的输入、输出、运行时、classic/1 冻结边界、技术检查与金样对照。修改这些文件、`packaging/templates/classic/1`、`packaging/film-builders` 或实拍成片渲染验收前先读本文。四套 overlay 包装和共享贴纸业务另见 `docs/reference/视频包装.md`，打包资源见 `docs/reference/打包与桌面运行.md`。

## 1. 命令入口现状：不要虚构 CLI

当前工作树中**没有 `scripts/film-render.ts`**，`package.json` 也没有 `film-render` 命令；同时没有 `scripts/film-render*.test.*` 这样的专用测试文件。因此本文不把推测的 `doctor/render/compare` 参数写成可执行命令，也不虚构 CLI 的 stdout 或进程退出行为。

当前真实存在的是一组 TypeScript 库入口：

| 入口 | 输入 | 输出/副作用 |
| --- | --- | --- |
| `renderSpecFromProject(projectRoot, variant, options)` | 源码工程根、片号，以及可选 `baseName`、`musicInSec`、`coverFrame`、`onAdjustment` | 只读工程文件，返回已经 `parseRenderSpec` 校验的 `RenderSpec` |
| `parseRenderSpec(input)` | 渲染单对象或 JSON 字符串 | 返回通过校验的 `ClassicRenderSpec` 或 `OverlayRenderSpec`；非法输入抛 `FilmRenderError` |
| `doctor()` | 当前包装运行时、Node、ffmpeg/ffprobe | 返回运行组件、路径、版本和警告；缺件或版本漂移抛错 |
| `renderFilm({ spec, runDir, signal?, onStage? })` | 已组装的 spec 和全新 run 目录 | 渲染视频/封面，写 spec、检查、manifest 等证据，返回 manifest 对象 |
| `verifyFilm({ spec, video, cover, workDir, signal? })` | 已有视频、封面和全新检查目录 | 写 `checks.json`，返回 `{ ok, checks, checksPath }` |
| `compareFilms({ spec, video, reference, workDir, ... })` | 新视频、调用方提供的参考/金样视频和全新对照目录 | 写对照图与 `comparison.json`，返回 SSIM、媒体、音频和 composition 对照结果 |
| `gateOpening(projectRoot, variant)` | 工程根与片号 | 只核验开场选择、视觉审核和文件哈希，返回开场证据，不启动渲染 |

`FilmRenderError` 带有 `code` 和 `exitCode` 元数据：2 表示输入/用法类，3 表示运行环境/模板资源类，4 表示媒体处理或技术验收类。因为没有专用 CLI，这些数值当前首先是库错误分类，不能未经核对就写成某个命令的进程退出码表。

### 不要混淆的另一条命令

`scripts/reassembled-workbench.mjs` 是正在运行的桌面服务客户端，不是在本地直接执行固定渲染的 CLI：

```bash
node scripts/reassembled-workbench.mjs doctor <DATA_ROOT>
node scripts/reassembled-workbench.mjs import <DATA_ROOT> <导入清单.json>
node scripts/reassembled-workbench.mjs review <DATA_ROOT> <成片登记ID>
```

它读取 `electron-service.json`、核验桌面实例与数据目录身份，再调用 HTTP API 并打印 JSON。固定渲染核心本身不读工作台 SQLite；上述客户端的存在也不改变这一点。

## 2. 运行资源与离线约束

### 2.1 必需组件

`doctor()` / `runtimeInfo()` 要求：

- 当前调用进程和包装 Node 都是 Node 22+。
- HyperFrames 精确为 `0.8.134`，并且 `packaging/package.json` 声明、root lock 依赖、`package-lock.json` 中安装版本、`node_modules/hyperframes/package.json` 四处一致。
- `film-runtime.json` 为 `schemaVersion: 1`，HyperFrames 版本同上，Chrome 精确为 `152.0.7977.30`。
- HyperFrames dist 中声明的 Chrome 版本唯一且与契约一致，实际 `chrome-headless-shell --version` 也匹配。
- `node_modules/hyperframes/bin/hyperframes.mjs`、`runtime/chrome-headless-shell/`、`win-hide-spawn.cjs`、classic 冻结资源均真实存在。
- ffmpeg、ffprobe 能实际执行 `-version`，不只是路径字符串存在。

开发仓库可用以下命令装配或修复包装运行时：

```bash
node scripts/setup-packaging-runtime.mjs [--from <参考packaging目录>] [--force]
# 等价 npm 入口
npm run setup:packaging -- [--from <参考packaging目录>] [--force]
```

装配脚本会复制运行时、按契约补齐 `film-runtime.json`，版本不符时重装固定 HyperFrames，并验证 Chrome。classic 字体或 GSAP 缺失时，只允许接受 SHA-256 与冻结值完全相同的下载内容；不能拿“最新版本”替换。与固定运行组件或 classic 资产有关的缺口未消除前，不得视为固定渲染已验收；普通 overlay 包装是否可用应按其自身资源判断。

### 2.2 HyperFrames 调用

classic 画面由 `renderHyperframes` 执行：

- 设置 `HYPERFRAMES_SKIP_SKILLS=1`、`HYPERFRAMES_NO_AUTO_INSTALL=1`、`HYPERFRAMES_NO_TELEMETRY=1`。
- 显式传入 Chrome、ffmpeg、ffprobe 路径和本次 hf 私有工作目录。
- 先执行 `lint --json`，要求 `ok: true` 且 `errorCount: 0`。
- 再执行高质量 render，固定 `--fps 24 --workers 2`。
- 只对匹配 ffprobe deadline 的失败保留一次重试；中止信号不重试，其他错误不盲目重试。
- 最终真实探测 `picture.mp4`，解码帧数必须等于 `canvas.frames`。

日志写入本次 run 的 `hf/renders/`，不能写回模板或共享参考运行时。固定渲染不启动 Python；`python-format.ts` 仅用于保留历史 Python JSON/浮点文本兼容性。

## 3. 渲染单输入

### 3.1 共同结构

`RenderSpec` 的 `schemaVersion` 和 `template.version` 都只能为 `1`。共同字段包括：

```text
project:  { root, variant, baseName }
canvas:   { width: 1080, height: 1440, fps: 24, introFrames: 20, frames }
shots:    [{ id, file, startFrame, endFrame, inSec, rate, approvedSourceRangeSec? }]
subtitles:[{ text, startFrame, endFrame }]
audio:    { voices, music, loudness }
output:   { coverFrame }
template: { id, version: "1" }
```

核心约束：

- `project.root` 必须是已存在的绝对目录；`variant` 是受限标识符；`baseName` 必须是跨平台安全文件名。
- 画布只接受 **1080×1440、24fps、20 帧片头**；`canvas.frames >= 360`，即总片长至少 15 秒。
- 正文第一个 shot 从第 20 帧开始，shots 必须连续，最后一个 shot 的 `endFrame` 必须等于 `canvas.frames`。
- shot ID 不可重复，同一素材文件不能在单条成片中重复登记。`approvedSourceRangeSec` 存在时，源片入点和含转场余量的出点都不得越出人工审核区间。
- 字幕帧区间位于 `[20, frames]` 内且非空；`output.coverFrame` 只能取 `0–19`。
- 所有工程输入通过 `projectFile` 解析：禁止越出 root、跨平台伪绝对路径、目录代替文件和经符号链接逃逸。

音频约束：

- 每条 voice 是 **48kHz、单声道、PCM16 WAV**，裁切区间有效。
- `atFrame` 不递减，配音不能重叠，也不能越过片尾；每帧对应 2000 个采样。
- 配乐必须存在且有时长，入点小于源时长；gain、淡入淡出、ducking 和 loudness 数值都在渲染单限定范围内。
- 混音会循环/截断配乐到准确片长，做旁白侧链压缩、两遍 loudnorm 和时长复核。

### 3.2 classic 输入

classic 渲染单额外包含：

```text
template: { id: "classic", version: "1" }
classic: {
  projectCss, designDoc, theme, durationText?,
  cover: { image, title, tag, note, brand, model, productName },
  labels, callouts,
  outro: { title }
}
```

`projectCss`、`designDoc`、cover image 都是 root 内文件。封面和片尾标题必须恰好两行。`durationText` 若存在，数值必须与 `frames / 24` 一致；它保留历史 Python 对整数/浮点根属性的文本差异，避免 HTML 字节级漂移。

classic 的 shot 之间预留 **4 帧**转场余量，最后一个 shot 不预留。`Callout` 必须绑定现有 shot、至少持续 24 帧，点、卡片和跟踪关键帧必须位于安全区，跟踪线不得穿过自己的卡片。classic 自有 callout/label/outro 不等于 `packaging/stickers` 共享贴纸系统。

### 3.3 overlay 输入与贴纸排除

固定渲染的 overlay spec 使用：

```text
template: { id: <受支持包装模板>, version: "1" }
cover: { image }
packaging: { enabled, template, varsOverrides, pointCues, pointCuesMode, layouts }
```

`packaging.enabled` 必须为 `true`，且与 `template.id` 一致。主副标题非空，文案、pointCue 和 layouts 必须已经过共享规则清洗，不能指望校验器静默丢掉非法内容。pointCues 使用显式 `timed` 时序；无卖点时为 `none`。overlay 不使用 classic 的 4 帧转场余量。

贴纸边界必须逐字理解：

- **classic/1 不进入共享贴纸系统**：`ClassicConfig` 没有 `stickers`、`stickerDefaults` 或 `stickerAssets`，classic 分支也不会调用共享贴纸正式导出。
- **固定 overlay spec 同样不接受贴纸字段**：`lib/film-render/overlay-spec.ts` 对 `packaging` 的键白名单只有 `enabled`、`template`、`varsOverrides`、`pointCuesMode`、`pointCues`、`layouts`。因此 `packaging.stickers` 会以 `INVALID_PACKAGING` 拒绝；`cover` 也只允许 `image`。
- 共享 `renderVideoPackaging` 的完整业务配置在别处可以包含贴纸，但 `OverlayRenderSpec.packaging` 是对该配置的收窄 Pick。不能把其他包装入口的能力反向写入固定 spec。
- overlay spec 还不允许存在 `classic` 字段。不要通过混入 classic 配置、额外顶层数据或共享贴纸变量来绕开冻结边界。

## 4. 从源码工程生成 spec

`renderSpecFromProject` 是对已审核源码工程的只读适配器，不读工作台数据库，也不从文件名或时间戳猜归属。

它读取：

- `variants/<variant>/timeline.json`：画布、总帧数、shots、字幕、voices、music、封面和 classic 文案/标注。
- `packaging.json`：品牌、型号、产品名、片号对应包装或 classic 配置。
- `review/delivery.json`（若存在）：显式片号到交付视频名的映射。

输入中的媒体路径先按 variant 目录解析，再转换成工程 root 相对路径。timeline 没有 voices/music 时会失败，不会猜测配音或配乐。`baseName` 可由调用方显式传入；未传且没有 delivery 文件时默认使用 variant，存在 delivery 文件时则只接受明确的 variant 映射，没有映射会报 `DELIVERY_MAPPING_UNKNOWN`。

选项的实际默认值：

- `musicInSec`: `0`。
- `coverFrame`: `16`，仍必须位于片头 20 帧内。
- classic 音频参数由适配器固定写入：配乐 gain `-14 dB`、淡入 `0.25s`、淡出 `1s`，目标响度 `-16 LUFS`、真峰值 `-1.6 dBTP`、LRA `11`。
- overlay 的显式帧区间会转换成秒，并复用共享 pointCue 后处理；`onAdjustment` 可接收每项清洗/删除原因，调用方应保留这些调整证据。

`gateOpening` 是独立审核证据函数：核验四种允许的开场效果、首镜头和视觉审核状态；审核记录带 SHA-256 时必须与当前文件一致，旧记录无哈希则通过 `legacyReviewWithoutHash` 明确标出。它不是 `renderSpecFromProject` 或 `renderFilm` 内部隐式调用的一步；如果某条验收流程要求开场 gate，调用方必须显式执行，不能声称单纯调用渲染就已经完成视觉批准。

## 5. 输出位置与渲染阶段

### 5.1 `renders/<runId>` 红线

`renderFilm` 要求 `runDir` 解析后恰好是以下目录的**直接子目录**：

```text
<project.root>/variants/<project.variant>/renders/<runId>
```

目录必须尚不存在，root 和已有祖先不能被符号链接带出工程。创建采用先创建父目录、再以非 recursive 方式独占创建 runDir，已存在或并发抢占都会失败。核心渲染不会覆盖旧 run、旧视频、旧封面或旧 JSON。

这意味着输出证据按 run 隔离；不要用固定 `latest/` 目录反复重写，也不要把渲染临时文件写到 `packaging/templates/classic/1`。

### 5.2 主要阶段

`onStage` 会收到 `start`、`done`、`failed` 事件和耗时。阶段失败会尽量写 `failure.json`，并给错误附加 stage。

1. **prepare**：逐 shot 规范化到 1080×1440 / 24fps，classic 保留转场尾帧，overlay 使用无损中间质量；检查真实帧数和源片长度。
2. **composition**：classic 在 runDir/hf 生成冻结 HTML、GSAP 时间线、媒体和资源；overlay 在 runDir/base 生成静帧片头、硬切底片、字幕和 `composition.json`。
3. **hyperframes（classic）**：lint、浏览器渲染 picture、帧数核验。
4. **edge**：抽样检查右侧是否出现源片之外的渲染黑条。
5. **audio**：生成 narration/premix/final WAV，记录两遍响度和时长。
6. **mux**：合成画面和音频；若确认是人造右边条，裁去 8 像素后恢复 1080×1440，并在 manifest 记录修正。
7. **packaging（overlay）**：基于冻结 spec 调用共享包装，先生成未包装底片，再发布为交付名。
8. **cover**：按 `coverFrame` 导出 review PNG 和交付 JPG。
9. **verify**：执行技术检查并写 `checks.json`，任一检查失败则渲染失败。
10. **manifest**：重新计算输入和模板哈希，确认渲染期间未变化，写 `render-manifest.json`。

交付文件名为：

```text
<runDir>/<baseName>.mp4
<runDir>/<baseName>-封面.jpg
```

runDir 还包含 `spec.json`、`checks.json`、`render-manifest.json`、`prepared-media/`、`audio/`、`review/`、`edge-check/`，classic 另有 `hf/`，overlay 另有 `base/`。manifest 记录工具和版本、输入哈希、模板/构建器哈希、composition 哈希、音频测量、各阶段、边缘修正，以及视频/封面的路径、SHA-256、帧数和时长。

工作台任务恢复层可以读取并复核已有 run 的 manifest 后决定复用；那是 `lib/final-edit/reassembled/jobs.ts` 的上层恢复策略，不表示 `renderFilm` 自身会覆盖或续写旧目录。

## 6. classic/1 冻结与哈希

### 6.1 冻结资产

`packaging/templates/classic/1/template.json` 必须声明 `id: classic`、`version: 1`，其 `assets` 映射必须与代码中的冻结清单一致。当前已核对实际文件的 SHA-256：

| 文件 | SHA-256 |
| --- | --- |
| `assets/fonts/SourceHanSansCN-VF.ttf` | `25a01e41b5cc99893eb35a6cd2cc7611841dc19eb03cbaf7f0c1de8210f2ba0b` |
| `assets/scripts/gsap.min.js` | `c174bfce53a729418d57a8ad8625e7247c793a22fef8e2851e3cfa3de9cd8280` |

缺 manifest、身份不符、资源缺失或哈希漂移分别会触发模板/资源错误。不要把字体子集化、GSAP 升级、重新压缩或换 CDN 文件当成无损操作。overlay 字幕也复用 classic 的 Source Han 字体，因此不能以为只改 classic 就不会影响其他分支。

### 6.2 冻结构建器来源

classic 构建器清单固定为：

- `templates/classic-v1.ts`
- `templates/classic-callouts-v1.ts`
- `python-format.ts`

当 `packaging/film-builders/` 存在时，运行时不执行其中源码，而是以它作为**发布来源归档**：逐个计算归档文件 SHA-256，并要求与 `film-builders/manifest.json` 一致。只有归档不存在且原始源码存在时，开发环境才回退到当前源文件哈希。归档存在但文件缺失或哈希错误必须报 `BUILDER_RESOURCE_INVALID`，不能悄悄回退到另一份源码。

当前归档与源文件已核对一致的 classic 哈希为：

| 构建器 | SHA-256 |
| --- | --- |
| `classic-v1.ts` | `e155de849c54512d3294a16a4d3d0add2e91c639a5e8ad56b5cfe9201833bc71` |
| `classic-callouts-v1.ts` | `ef97d6e9d2de914cd45126211a1e150924883b04782abc7584989a8bf4844913` |
| `python-format.ts` | `301fe8dfa2cc7e14ed22d10bd447e68302ee085559d57dc51d5846f7b4d78a27` |

classic HTML 的 CSS 空白、数字格式、data 属性、动画时间和资源内容都可能影响 composition 字节与金样对照。任何改动都不能只凭“画面看起来差不多”视为兼容。

## 7. 技术验收与金样/hash 对照

### 7.1 `verifyFilm`：单片技术检查

技术检查会真实探测和解码媒体，不是只检查扩展名：

| 检查 | 核心判定 |
| --- | --- |
| 视频格式 | 1080×1440，`r_frame_rate` 与 `avg_frame_rate` 都是 24 |
| 帧数与片长 | 实际解码帧数等于 spec；总片长至少 15 秒，与 spec 差不超过 1 帧 |
| 音轨覆盖 | 音轨存在，起点约在首帧，覆盖全片，容器/音轨时长差不超过 2 帧 |
| 完整解码 | 视频全解码、可选音频流解码无错误 |
| 响度 | 整体响度在 −17 至 −15 LUFS 之间，真峰值不高于 −1.4 dBTP |
| 黑帧 | 无连续 0.1 秒以上黑帧 |
| 20 帧片头 | 第 0–19 帧与首帧平均绝对差均小于 0.8，首帧不是几乎全黑 |
| 封面 | 指定静帧与交付 JPG 的 SSIM 至少 0.98 |
| 右边缘 | 不出现源片自身没有的人造右边黑条 |
| overlay 包装可见性 | 第 10 帧与无包装封面明显不同，SSIM 必须小于 0.98 |

所有检查汇总为 `checks.json` 和布尔 `ok`。技术通过不等于人工视觉审核通过；它不会判断文案是否正确、构图是否美观或开场是否已获批准。

### 7.2 `compareFilms`：与调用方金样对照

`compareFilms` 的 `reference` 是调用方提供的已有视频。固定渲染核心没有内置“自动寻找并更新金样”的命令，也不会把 reference 覆盖成新结果。调用方应把金样当作只读验收输入，并为每次对照提供全新的 `workDir`。

默认 `threshold = 0.98`，可在 `(0, 1]` 内显式调整。对照包括：

1. 新旧的宽、高、两种帧率、解码帧数是否一致，片长差是否小于 `1e-5` 秒。
2. 新旧整体响度差是否不超过 0.5 LU，音轨时长差是否不超过 1/24 秒。
3. classic 的 `hf/index.html` 或 overlay 的 `base/composition.json` 是否字节一致；必要时调用方可显式给 `referenceHtml`。
4. 对第 0、10、19、末帧、镜头开始附近/中点，以及 classic label/callout 或 overlay pointCue 的代表帧逐一计算 SSIM，每项都必须达到阈值。

输出包括逐帧 `samples`、`minSsim`、媒体 probe、响度、composition 对照、新旧视频 SHA-256、`comparison.jpg` 和 `comparison.json`。最终 `ok` 要求媒体、音频、composition 和所有抽样 SSIM 同时通过。**视频整文件 SHA-256 会被记录，但金样判定不是简单要求新旧 MP4 容器字节完全相同。**

哈希还有另一条证据链：渲染开始和结束分别计算输入与模板哈希，防止渲染期间源文件或模板变化；已有成片导入工作台时还会复核 spec、render manifest、输入、模板和输出文件哈希，并重新执行技术检查。不要用一张 SSIM 对照图替代这些来源校验。

## 8. 24fps 与 20 帧片头的跨分支契约

- classic HTML 根属性固定 `data-fps="24"`，片头 scene 为 `20 / 24` 秒；正文 shots 从帧 20 开始。
- overlay 明确生成 20 帧无损静帧 cover video，再与正文拼接，并启用 `staticCover`。
- HyperFrames 固定 24fps，FFmpeg 中间片与交付 probe 也按 24fps 验证。
- `coverFrame` 只允许 0–19，保证封面来自片头；默认从工程适配器产生时为 16。
- 技术验收不仅数帧，还逐像素比较前 20 帧，防止“帧数够但片头在动”。

共享贴纸业务另有“贴纸只进入正文、片头 20 帧不出现贴纸”的规则，但该规则不构成给 classic/1 或固定 overlay spec 增加贴纸字段的理由。

## 10. 修改红线速查

- 不修改 classic/1 冻结资产、构建器、数字格式或 CSS 空白后仍声称版本不变；来源归档和 manifest 必须一致。
