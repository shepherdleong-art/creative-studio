## 卖点＋详解交付（2026-09-18）

- 当前运行时执行器 v24 使用 C 方案：`adapters/direct-vision.ts` 直接识图并输出核心卖点＋完整详解，默认 Luna，仍尊重用户选定的视觉模型。不接 OCR、不自动逐条二次核验。通常约 6–12 条，按实际信息决定，不硬截断数量。
- 上传详情页和“裁切图文件夹”共用后续来源集→卖点库→模板→脚本流程。文件夹只读直接子文件、按数字文件名自然排序，最多 200 张/512 MB、单张 32 MB；只支持静态 JPEG/PNG/WebP，复制原字节到 `dataRoot()`，整批验证后事务入库，失败清理本批副本。路径只用于导入，分析不依赖外部文件持续存在。
- `direct-vision-contract.ts` 固定 v7 图片坐标参数：适合的小图（≤1200×4096、≤6 MiB）不重编码；长图按每页 3000 万像素预算、宽度≤1200、切片高4096、重叠256、JPEG q70 处理。COS 对本流程保留已处理图片原字节。≤50 张合为一次识图；更多图片均衡分批、最多2路并发，每批最多2次尝试；仅多批结果额外调用全局组织器。
- 来源核对按用户决定改为手动：仍执行结构/引用范围/促销检查，结果 `evidenceGate=skipped`，不宣称二次核验通过。卖点的“查看支撑事实与来源”中可按需读取最多6个来源区域，依卖点修订版本恢复坐标；编辑详解/排除通过原有不可变修订保存。
- 组织器只生成标题、详解、事实编号映射；事实正文、引文、定位及核验状态由本地从成员恢复。每条合格事实恰好属于一组，遗漏/重复/未知编号或新增高风险词项拒绝保存；最多两次请求，第二次带上原结果与具体校验反馈。失败不静默回退成碎片库。确定性词项检查不等于完整语义核真。
- 新库仍使用不可变卖点修订及原表，不新增 schema。C 方案保存 `promptContractVersion=7`；历史 v6 为逐条提取、自动核验后全局组织。手动整理保留较高版本，防止核对时误用旧切片坐标。`library/organize` 为显式整理入口，使用用户选定供应商；模型完成后以 `baseRevisionId` 比较并保存新版本，期间发生编辑则返回冲突，旧脚本引用不改。
- 界面在模板选择前与结果页复用完整卖点列表，详解不截断，原事实和来源可展开；普通脚本与模板改写都使用相同卖点及通过检查的详解。新增回归：`node scripts/script-studio-selling-point-organizer.test.ts`。本条更新此前迁移方案 A04 的“不增加独立归纳请求”范围，以本次用户明确要求为准。

## 模块边界

- 模板改写执行器 v26 / prompt v3：JSON 首稿的 `label` 统一为不带括号的纯段名，润色文本解析兼容重复包裹的 `【【段名】】`，避免外层 `】` 残留进口播。只处理段名边界，保留正文内的括号；历史脚本版本不批量改写。回归覆盖首稿、去 AI 味、朗读检查到落库正文与字幕。

- 爆文模板改写执行器 v25 / prompt v2：文本子步骤及该模式的标题修复保留 8192 输出 token（推理模型的上限包含推理消耗），共享原有每方案请求次数预算。风格分析失败仍带参考开头/结尾锚点；原文风格优先于本地预设。多份变体轮换筛选白名单中的主卖点，最终稿按正文顺序比较，相似时最多改写一次，仍重复则该方案失败。朗读检查同时复核副标题是否承接主标题，仅接收副标题字段并继续走标题/证据校验。结果页可重新挑模板，每次明确提交创建新的幂等 action，断连重试冻结同一 body。实测及边界见 `docs/2026-09-19-爆文模板降级与再生成排查.md`。

- 卖点分析耗时与 H 盘工作台的流程对比、v23 长图重复缩放优化及同图实测见 `docs/2026-09-18-卖点分析耗时对比.md`。普通长图只物化一次整页缩放结果，超限图仍使用条带管线。

- 核心代码位于 `lib/script-studio/`，使用独立的 `{version, sql}` 迁移流（`schema.ts`），不走会吞错误的旧 core runner。
- 模块只依赖 `lib/media-core/` 与通用 `lib/`；**不允许 import `lib/final-edit/`**。需要共享的脚本可读性逻辑已上移到 `lib/media-core/script-visibility.ts` 和 `project-script-reader.ts`。
- `script_drafts` 保留只读兼容，新流程写 `project_scripts` / `project_script_revisions`；历史数据不做批量改写。
- 调度器默认关闭，只有 `CREATIVE_STUDIO_SCRIPT_STUDIO_ENABLE_SCHEDULER=1` 才会启动真实供应商执行。阶段 0-5 测试直接注入假供应商，不走该调度器。

## 关键约定

1. 空 `shotSetId` 表示项目级脚本，同一项目内可见；非空历史脚本保持原有窄隔离。
2. 实际使用时才把脚本快照绑定到目标 `shotSetId`。
3. 卖点库修订和项目脚本版本都不可变；人工编辑/再生成追加版本，切换历史只改当前指针。
4. C 方案采用手动来源复核，单次识图不得标记 `passed`；历史二次核验结果才可写“已通过二次证据检查”，不得写“逐字核真”。详解的确定性事实检查仍保留。
5. 通用资源限制值来自 `lib/script-studio/limits.ts`；C 方案坐标参数来自 `direct-vision-contract.ts`，导入文件预算来自 `import-directory.ts`。
6. 源像素/解码缓冲超过保护值**不阻断导入**：超限只写 `logLimitHit` 日志并在来源集报告里提示「自动压缩/分条处理」；超大图在 `tiling.ts` 走逐条带「源坐标裁剪 → 缩放」的流式管线，峰值内存只与单条带相关。
7. 切片编号契约：提取 prompt 约定切片按从上到下顺序 `tile_1` 起编号，`tileRefs` 必须用此编号；服务端共享的 `parseTileRefIndex`（`tiling.ts`）只接受完整匹配的 `tile_N` 或正整数（1-based），`garbage2`、`tile_2_evil`、`tile_0` 等全部返回无效。结构门禁对无效非空定位 fail closed；取图辅助函数只接收已过门禁的定位。改编号规则要 prompt、解析与门禁一起改。
8. 历史自动核验适配器仍保留：最多4条 claim、6张去重切片、4路并发，逐条在服务端匹配；C 方案不调用它。
9. 历史 `vision-extract.ts` 保留页内6张、4路并发契约；当前运行时使用 `direct-vision.ts` 的跨页50张、2路并发契约。两者均记录每批尝试次数与耗时，便于排查上游长尾；不得将旧批大小套到 C 方案。
10. 任务取消语义：`POST .../tasks/[taskId]/cancel` 打取消标记并中断运行中信号；Next instrumentation 与 API route 可能被打入不同模块实例，因此运行中控制器通过全局 `Symbol.for(...)` 注册，API 不能依赖自己的模块级 `Map`。runner 落库 `cancelled`（不再领取），区别于停机中断的 `queued`（租约恢复）。
11. 脚本方案默认 2 路并发；按完成顺序串行执行兄弟方案差异校验、标题修复和逐条保存，合格方案无需等待整组完成。正文相似仍走正文重试；标题冲突只修不合格标题。每次保存立即更新任务成功数，前端轮询加载已完成结果且继续追踪余下任务。
12. 第三步会列出已配置、已启用且支持视觉的脚本供应商，用户为每个任务显式选择一个模型；视觉提取、证据复核和脚本生成全程共用该选择，并把 `providerId + model` 固定进任务快照。**执行端以快照为准**：`runtime.ts` 用快照 `providerModel` 覆盖执行模型并经 `completeJson` 的 `model` 参数固定实际调用，排队期间供应商配置从 A 改为 B 不会让任务显示 A 却调用 B。服务端自动生成的任务 `requestKey` 必须包含解析后的 `providerId + providerModel`，否则同一输入切换模型会错误命中旧任务；调用方显式提供的幂等键仍原样优先。新项目默认选择公司 Luna，并明确标注"需要公司内网"；离开内网时可手动切换到已配置的外部 Gemini 等模型。所选模型不可用时提交前失败关闭，不得静默回退；历史任务没有选择快照时继续沿用公司视觉供应商默认值。
13. 公司 Luna 的响应存在显著随机长尾：同一 6 图批次曾第一次 120 秒超时、第二次 23.8 秒成功；2026-08-31 17:14 冷启动后的零并发 6 图探针又连续两次卡满 120 秒。客户端优化可以减少请求数和关键路径，但不能消除公司上游排队；完整证据见 `docs/2026-08-31-详情页智能脚本真机实测.md`。
14. Script Studio 调度器保存在 `globalThis` 以跨 Next bundle 转发取消，但开发热更新不会替换旧 executor 闭包；凡是改变任务实际供应商或执行语义，都必须递增 `bootstrap.ts` 的 `SCRIPT_STUDIO_SCHEDULER_EXECUTOR_VERSION`。所有创建任务的 API 必须先 `await ensureScriptStudioSchedulerStarted()` 再入队，版本不一致时先停旧调度器再启动新实例，避免任务快照显示外部模型而旧闭包仍请求 Luna。
15. 卖点层级数据契约（schema v2/v3，只追加不改已发布版本）：`script_studio_selling_points` 增加 `themeKey`/`themeTitle`/`hierarchyRole`/`importance`（v2）与 `evidenceRefsJson`（v3）。`themeKey` 一律由本地按 `pageIndex + 规范化 themeTitle` 生成（NFKC + 空白折叠 + 小写；模型 themeKey 只作辅助信息，绝不直接作为修订级稳定键；同页同标题跨批次归并，跨页不碰撞）；v3 迁移用 SQL 近似（TRIM）重写老数据。大标题只是策划主题：分组、排序与 prompt 语境可用，写进脚本的事实仍必须来自通过证据门禁的原子卖点。手动编辑创建新修订时这些字段原样保留；去重合并时主题取首个非空、角色取最强、重要度取最高。视觉提取 `promptContractVersion` 为 3，老模型/老响应缺字段时本地默认值兜底，不强制重读详情页。字段规范化统一在 `selling-point-normalize.ts`（`normalizeImportance`：null/undefined/NaN/空串回退 50，`Number(null)=0` 不会被钳成 1）。
16. 证据定位契约（v3）：权威结构是 `evidenceRefsJson`——每条引用自带 `pageIndex + tileRef` 配对，跨页去重合并后仍能把每条 evidenceQuote 定位回正确页面与切片；旧 `sourcePageIndex`/`tileRefsJson` 两列由配对结构派生，仅供兼容。解析（vision-extract）、去重（dedupe）、持久化（libraries）、结构门禁（evidence-gate）、二次核验取图（runner `evidenceTilesForPoint`）与卖点库 UI 展示全部使用配对结构；v3 迁移从旧两列回填。结构门禁同时校验定位合法性：非空 tileRef 必须能按 `tile_N`/数字完整解析，提供页数/切片数范围时页码与切片索引均不得越界（`pageIndex=999`、`tileRef=not_a_tile` 直接证据失败）。首次提取用本轮切片结果校验页数与每页切片数；历史库复用不重读图片，但 runner 必须从该修订的来源集恢复页数并在 plan 前重验非法格式/页码越界，来源范围确实不可用时只执行无需范围的结构校验。单条卖点核验取图硬封顶 `reprobeMaxImagesPerBatch`（默认 6）：精确切片优先、相邻片按序补位，6 条引用带相邻片膨胀成 18 图的溢出不允许发生；`runEvidenceGate` 的公共入口也必须再次截断去重图片，不能依赖调用方守预算。
17. 跨页商品身份保护只把有证据的明确冲突拦截：不同具体型号、不同产品大类或两个明确不同品牌优先判为冲突；缺失身份、品牌/品类泛称，以及同一产品不同页的名称改写判为信息不足，不因名称不相似直接失败。runner 只把已验证的同项目来源集 `filename` 作为辅助分段线索——同一主干、不同末尾编号只能在一边是品牌/品类泛称或身份缺失时帮助判为 `unknown`；两边都识别出不兼容的具体商品名时仍判冲突，文件名不能覆盖型号/品类/品牌冲突，也不能用文件名前缀推断项目归属。提取阶段失败时保存候选数、逐页身份、来源文件名和比较诊断，避免界面把"身份保护拦截"误报成零候选；该身份保护修复自执行器版本 **11** 引入，当前 Script Studio 执行器版本为 **16**。
 18. 方向卖点包（`direction-briefs.ts`）：`plan` 阶段一次为本轮全部方向做纯本地、确定性编排。证据边界 fail closed——`evidenceGate=failed`、`usable=0`、用户禁用或本地结构重验失败的卖点一律不进入卖点包（usable 被重新打开也不例外）；全部方向候选为空时任务以 `evidence_insufficient`（可用证据不足）失败，不得产出零引用脚本。每方向按组成规则编排（如 scene_seeding 必须含场景/外观主张 + 功能/结构证据支撑，组成不足时降级补位并在理由中记录），排序优先级为「方向类型匹配 > 本轮重复惩罚 > 主主题连贯 > 主题角色 > 提取重要度 > 证据状态」；可选槽位先补给本轮尚未使用的方向内类型（类型分数是硬优先，只罚排序无法让未使用的次级类型上位），保证多方向卖点包在供给充足时实质分化。容量每方向 6–10 候选 / 3–5 必选（15 秒为 8/3）；`feature_showcase` 的必选优先跨 3 个不同主题。每个方向的主题、必选/可选 ID、候选数量、降级标记与理由写入 `plan` 阶段快照，首稿与相似度重试复用同一份包。
 19. 生成与校验边界（fail closed，不可绕过）：`generator.ts` 的 `brief` 为必填，缺少 brief 直接抛错且不发起模型调用，没有回退完整卖点库的旧兼容入口；提示词只包含包内候选（required 标 `priority`），归一化丢弃模型返回的包外 ID，时长补齐与确定性回退也只从包内取事实。`validation.ts` 的引用白名单同样排除 evidenceGate=failed 卖点，且整条脚本至少引用一条卖点——零引用脚本（`selling_point_refs_required`）不得通过校验。提取/核验适配器的资源默认值（批大小、并发、超时、重试）一律取自 `limits.ts`，业务模块不再各自硬编码。
## 生成数量契约与再生成幂等（2026-09-02）

- 单批脚本生成数量上限 6（原 5），集中在 `lib/script-studio/generation-contract.ts` 这个不读 `process.env`、前后端共用的纯契约：`SCRIPT_GENERATION_MAX_COUNT=6`、UI 选项 `[1,2,3,5,6]`、时长白名单 `[15,20,30,45,60]`，以及 `parseScriptStudioRequestedCount`（**不先 `Math.floor`**，`1.5`/0/7/NaN 一律拒绝并抛统一错误）与 `parseScriptStudioTargetDuration`。route、runner、planner、`createTask` 全部导入该契约，不再各自复制范围判断或静默 `Math.min/Math.floor` 钳制；客户端组件也只导入这个纯模块，不碰读 `process.env` 的 `limits.ts`。
- 生成数量是「每条方案一次独立 LLM 调用」的有界并行（并发见 `limits.ts` 的 `generationConcurrency`），上限只约束单批方案条数；planner 的模板/角度池容量锁在 `script-studio-generation-contract.test.ts` 里（requestedCount=6 必须产出 6 个不同 template/angle），列表缩短会直接红掉测试而不是静默少产。
- 「再生成一组」是独立的 regeneration action：每次用户明确点击都生成新 `requestKey`（`regenerate-group:<uuid>`）并冻结**完整 POST body**（`RegenerationAction = { requestKey, body }`），即使参数与上次完全相同也必须产出新任务/新脚本组。同一次 action 因双击/重试重送时复用同一 key/body，服务端只创建一个任务；服务端结果不确定（5xx/断连）时前端保留原 action 并呈现「重试本次提交」，不得从最新表单重建 body。
- `createTask` 是数据库层原子 get-or-create：`INSERT ... ON CONFLICT(projectId, requestKey) DO NOTHING` 后回读。canonical identity（`buildTaskIdentity`/`taskStoredIdentity`）覆盖 `projectId`、mode、sourceSetId、libraryRevisionId、requestedCount、parentTaskId 与规范化后的**完整** `inputSnapshot`（不漏未来字段）；route 快速预查与原子冲突回读共用同一 comparator——一致返回 `202 + created:false`，同 key 不同 body 一律 `ScriptStudioError('conflict')` 返回 409，不静默复用旧任务。
- 对显式 action key 的既有任务重放：先按任务 `inputSnapshot` 里冻结的 providerId/providerModel 比较身份，**不要**按重试时的当前供应商配置重算 model；只有全新 key 才解析当前供应商、冻结实际 providerId/providerModel 并原子创建。丢包期间供应商配置变化不会把安全重试误判为新请求或冲突。
- 「再生成一版」（单条修订、固定 1 条、时长取脚本自身）行为与 requestKey 语义不变。

### 标题生成与修复契约（2026-09-09）

- 商品型号用于匹配身份，展示名称从冻结目录名称/卖点库名称清理型号及话题符后派生；原始查找键、目录修订、来源行保持原样。新知识快照额外保存 `productIdentity`，旧快照用已有 `normalizedModelKey` 兼容，不在执行时读取当前商品配置。
- 标题根据当前方向与已核验卖点生成。脚本标题 4–16 字、封面主标题 4–12 字、副标题 4–10 字（含标点，不计空白）；内部脚本标题不能只套商品名或写入型号、话题符，封面主标题可以使用冻结的展示商品名，封面副标题要表达本方案的卖点、场景或购买理由。搜索词独立留在 `content.knowledgeContext.searchTerms`；`searchTermsUsed` 只记录自然命中，不再强制标题包含完整统一名称或 1–2 个搜索词。
- 内部脚本标题独立检查同批及同项目最近 **30 天、最多 100 个项目脚本版本**；封面按主标题与副标题的完整组合检查同一范围，包含归档脚本和旧修订，不扫描旧 `script_drafts`。单条再生成排除自身所有版本。比较忽略大小写、空白、标点及末尾编号，并拦截编辑距离很小的近似标题；封面商品展示名主标题可以复用，同主标题配不同实质副标题、实质不同主标题配同副标题都不等同于完整组合重复；主标题只加一个语气字等极小变化仍按近似组合拦截；副标题的完整字符多重集相同也会拦截明确的词序调换（如“横厅高颜值隔断”和“横厅隔断高颜值”），不会仅因共享商品名或品类字判重。
- 只修复服务端指出的标题字段，最多 **2 次**；请求带当前方向、已用标题、具体冲突原因、只读正文和本方案引用的可用事实。封面完整组合重复时优先只修复副标题，保留合格的商品展示名主标题。服务端忽略模型返回的正文、字幕、卖点引用、时长和其他合格标题字段。每次修复后重验；最终标题检查与新增版本在同一写事务内执行，失败不保存本方案，其他合格方案仍可用。
- 标题中的数字及常见材质、认证、功效、绝对化用语通过确定性词项检查，对照本方案引用的可用卖点事实；搜索词/目录名称不能充当证据。此检查不等于任意语义事实均已被验证。执行器版本为 **12**；无需 schema 迁移，不批量改写历史脚本或下游快照。

## 生成链路延迟优化（2026-09-15，执行器 v15）

- 结尾本地检查与语义审核保留；每次首稿的结尾问题最多定向修复一次，修复后仍需本地校验与语义审核。失败记录具体原因，不再通过整篇重写重复同一修复/复审循环。正文结构/事实引用/同组相似度的有界重试、每方案总请求预算 8 次、标题最多修复 2 次均保留。失败项可显式补跑，可能比旧策略更早返回部分完成。
- `validationJson.generationPlanIndex` 与项目脚本版本在同一写事务保存，用 `projectId + generationTaskId + libraryRevisionId + generationPlanIndex` 恢复已保存方向。首次提取任务恢复时读取本任务 `save_library` 阶段中的不可变修订，跳过已完成的识图与复核；不会用当前卖点库替换本任务来源。无此标记的历史版本不猜测方向，不做批量回填。
- 运行中成功数逐条更新；首次结果出现时进入结果页，保留生成进度/停止按钮并继续轮询。停止保留已保存版本；生成中不允许从结果页再发起整组或单条生成。失败展示实际生成/校验错误，不把 JSON/网络错误统一称为“差异未通过”。
- 浏览器回归：`npm run build && node scripts/script-studio-progress.playwright.test.mjs`，生产前端 + API 夹具 + 临时数据根，覆盖提前显示、持续轮询、停止保留、实际错误说明，不调用真实模型。
- 本次样本、覆盖范围与限制见 `docs/2026-09-15-脚本生成链路延迟优化.md`。真实模型首次提取与证据复核仍有固有等待，不能用本地测试宣称具体真实提速比例。

## 默认卖点选择流程（2026-09-15，执行器 v16）

用户明确要求取消第二份“提炼卖点确认”。默认生产流程现为：AI 提取中性事实 → 证据校验 → 自动保存并使用可用卖点 → 脚本生成。`runtime.ts` 不再注入 distiller，runner 不创建额外提炼阶段、不读取提炼表达。历史提炼记录/API/显式注入测试仍保留，不修改旧脚本冻结引用。

- 结果页只保留产品卖点库，默认使用通过核验且未被排除的卖点。用户可点“选择 / 排除卖点”，取消勾选后保存，之后也能重新保留。选择写入不可变新修订，不修改正在执行的任务或旧脚本；下一次生成采用新修订。
- 选择同时保存 `usable` 与 `disabledByUser`，重新勾选清除人工排除状态。未通过证据校验的卖点不能通过勾选绕过门禁。前端提交 `baseRevisionId`，服务端拒绝旧列表覆盖新修订。
- 多页提取共享原有并发上限（默认 4），结果保持原页序与引用配对；已发出的请求排空后才返回失败。证据复核优先复用图片重合最多且容量足够的批次，仍限制每批最多 4 条主张/6 张图、4 路并发，每条主张只用自己的 `imageIndexes` 与 ID 匹配。
