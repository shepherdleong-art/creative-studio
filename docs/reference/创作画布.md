# 创作画布

本文记录 `lib/creative-canvas/`、`app/canvas/`、`app/api/canvas/` 与 `components/creative-canvas/` 的常驻架构。修改图定义、持久化调度、供应商适配器、素材、恢复、用量或 ZIP 导出前，应先读本文和对应实现。

## 1. 独立模块边界与两层开关

### 1.1 领域边界

- 画布独立管理图草稿、节点运行投影、运行/任务、不可变素材、导出和日志，**不写入旧 `jobs`、`video_jobs`、`projects`、`shot_sets`**。
- 需要共享媒体存储能力时只从 `media-core/` 方向取用；当前 `assets.ts` 使用 `media-core/storage-path.ts` 的受控路径与 symlink 守卫。**不得从 `final-edit/` 导入。**
- 现有底层共享还包括 DB、`dataRoot()`、FFmpeg、图片/视频供应商适配器、COS/本地 URL 交付、通用用量账本和共享 schema gate。用量代码可以读取供应商配置与计价依据，但不能据此写旧任务表。
- 图定义 `graphJson`、服务端运行投影 `creative_canvas_node_states`、任务/输入快照和不可变资产是四类不同事实，不能混写进 React 节点 data。
- 画布没有 `projectId + shotSetId` 上下文，归属键就是 `canvasId`。素材、运行、任务、导出和日志都必须按画布归属读取，不得从文件名或时间戳推断归属。

### 1.2 功能开关与执行器开关不是一回事

功能总开关：

```bash
CREATIVE_STUDIO_CANVAS_ENABLE=1
```

执行器模式：

```bash
CREATIVE_STUDIO_CANVAS_EXECUTOR=disabled   # 默认
CREATIVE_STUDIO_CANVAS_EXECUTOR=fixture
CREATIVE_STUDIO_CANVAS_EXECUTOR=company
```

精确定义：

- `CREATIVE_STUDIO_CANVAS_ENABLE` 未设为 `1` 时，`startCanvasAfterReadiness()` 立即返回：**不执行 readiness、不创建画布表、不启动 worker**。`assertCanvasApiReady()` 也在触碰画布表前返回 `canvas_disabled`（503）。顶部导航入口由 `app/layout.tsx` 按同一开关隐藏。
- 功能开启但 executor 为 `disabled` 时，可以执行迁移、编辑和保存画布，但不启动生成 worker；启动运行会得到 `runtime_unavailable`。非法 executor 值按 `disabled`。
- `company` 选择真实适配器工厂，按能力表分流公司渠道和已配置的外部渠道；没有可用真实适配器时不能静默换成 fixture。
- `fixture` 只用于受控测试，必须同时设置 `CREATIVE_STUDIO_CANVAS_TEST_ROOT=1` 和 `CREATIVE_STUDIO_DATA_ROOT`。缺任一项都会被拒绝并退回 `disabled`。
- `instrumentation.ts` 负责启动接入；API readiness 恢复后也会补启动。bootstrap 和 scheduler 通过 `globalThis` Symbol 单例跨 Next bundle 共享，修改执行语义必须递增 executor version，先停旧闭包再启动新实例。
- `lib/shutdown.ts` 会停止画布领取、abort 本地 I/O 并在关库前 drain 在飞任务。

## 2. Schema、共享升级 gate 与无副作用要求

### 2.1 独立迁移流

`lib/creative-canvas/schema.ts` 的 `CREATIVE_CANVAS_MIGRATIONS` 当前目标为 v4，版本记录表为 `creative_canvas_schema_migrations`。

**迁移只能追加，已发布条目不得修改，也不能塞回会吞错误的旧 core runner。** 每条迁移在 `IMMEDIATE` 事务中执行并做 `foreign_key_check`，通过后才记录版本。

| 职责 | 表 |
| --- | --- |
| 图草稿 | `creative_canvases` |
| 不可变素材 | `creative_canvas_assets` |
| 节点运行投影 | `creative_canvas_node_states` |
| 运行与任务 | `creative_canvas_runs`、`creative_canvas_tasks`、`creative_canvas_task_inputs` |
| ZIP 导出 | `creative_canvas_exports` |
| 粘贴幂等 | `creative_canvas_copy_operations` |
| 模型/提交节奏 | `creative_canvas_rate_limits` |
| 视频附加元数据 | `creative_canvas_video_metadata` |
| 独立日志 | `creative_canvas_logs` |

v2 已放开“同一节点最多一个未结束任务”的旧唯一索引，以支持单点多变体。发布安全不再靠该索引，而靠 `nodeEpoch`、任务归属和成功输出校验；不要恢复成会误伤多变体的单任务假设。

`canvasTablesPresent()` 是关闭开关无副作用检查和结构检查使用的核心表探针。已有版本记录但核心表缺失、历史缺版本/未知版本、数据库来自更新版本时均进入兼容模式，不对残缺库强行执行 DDL。

### 2.2 共享 gate

- `readiness.ts` 使用 `runSchemaUpgradeGate({ scope: 'creative-canvas', ... })`，共享跨进程锁、JSONL 审计、备份验证和中断恢复。
- gate 持锁后处理遗留审计和临时备份；`ensureCreativeCanvasSchemaReady()` 对待执行迁移先创建经过校验的 SQLite 备份，再逐版本迁移，gate 最后记录结果并释放锁。
- 失败结果是 `available=false / compatibility_only`，只禁用画布，不能影响不读画布表的旧功能。错误包括锁/审计不可用、备份失败或校验失败、磁盘不足、迁移失败、历史异常和 schema 过新。
- 运行路径由 `dataRoot()` 派生：备份 `data/backups/schema-upgrades/`，锁 `data/schema-upgrade.lock.db`，审计 `storage/logs/schema-upgrades.jsonl`。
- `runtime-readiness.ts` 只缓存成功结果，失败允许后续重查。`http.ts` 的顺序固定为“功能开关 → readiness → 注册能力 → 补启动 scheduler”。

## 3. 图定义、运行投影与任务数据模型

### 3.1 图草稿与服务端投影

`types.ts` 当前 `CANVAS_GRAPH_SCHEMA_VERSION=1`，节点类型为：

- `material`：图片、视频或音频素材；
- `prompt`：固定文本；
- `image-generation`：图片生成；
- `video-generation`：视频生成。

节点类型元信息的单一事实源是 `node-kinds.ts`。图片生成接受图片/文本，视频生成接受图片/视频/音频/文本。`graph.ts` 在服务端严格解析未知字段、重复 ID、悬空/重复连线、自环、循环和端口不兼容；客户端出现 `currentAssetId`、`activeTaskId`、`nodeEpoch`、`phase` 等运行字段一律拒绝，不能静默剥离后假报保存成功。

生成节点的参考槽位含稳定 `refId`、只增不减的 `label`、用途、备注和来源。断线后槽位对账移除，编号不回收，避免提示词中的 `@参考N` 悄悄指向另一份素材。生成节点到素材节点的连线是结果溯源边，不参与输入计划和端口匹配。

持久化分三层：

1. `creative_canvases.graphJson/viewportJson`：客户端可写编辑定义，`graphRevision` 做乐观并发；保存必须带 `expectedGraphRevision`，冲突返回 409。
2. `creative_canvas_node_states`：服务端维护 `nodeEpoch`、删除 tombstone、活跃任务、当前结果和结果任务。删除节点只打 tombstone 并递增 epoch，不删除任务身份；旧任务迟到后不能重新发布。
3. `creative_canvas_runs/tasks/task_inputs/assets`：不可变执行快照和产物。编辑后来草稿不会改变旧任务。

`publishCanvasNodeResult()` 要求节点存在且未删除、epoch 匹配、任务确实属于该节点并成功产出该资产。多变体并存时采用“最后完成者成为 currentAssetId 主结果”；每节点最近 12 个成功输出另作候选投影。

### 3.2 计划与输入快照

`planner.ts` 只读，不写库。`CanvasPlan` 冻结图修订、执行范围、任务、供应商身份、精确模型、参数、完整提示词和全部输入身份，并生成稳定 fingerprint。

- `single`：运行一个生成节点，支持 1/2/4 个变体；同节点已有活跃任务加本次变体不得超过 `MAX_NODE_VARIANTS=8`。
- `branch`：从起点沿依赖运行分支，默认复用已有起点结果；范围内输入绑定本次上游任务，范围外输入固定当前资产，不自动扩大计划。
- 已有素材固定 `assetId`；等待已有上游固定 `upstreamTaskId`；固定文本保存 `textContent`。计划内上游节点在创建运行时映射成这次运行的任务 ID。
- 任务输入表用 CHECK 保证每行恰好是“已有素材 / 等待上游 / 固定文本”之一；`resolvedAssetId` 只能出现在等待上游的输入上。
- 图生视频的图片角色按计划内图片顺序确定首帧和后续尾帧；模型可接受的模式、输入组合和参数仍由能力表最终校验。

`runs.ts` 先查 requestKey 幂等记录，再按当前图重算并比较 fingerprint，最后在同一事务创建 run/tasks/inputs 和节点活跃关联。同 key 不同请求或过期 fingerprint 返回冲突。

`creative_canvas_runs.status` 类型虽定义 planned/running/partial/succeeded/failed/cancelled，但当前创建路径写入 `running`，模块内没有运行结束后的聚合更新 writer。**界面完成度与恢复应以 task phase 为准，不要把 run.status 当成已实现的聚合状态机。**

## 4. 任务阶段、名额与调度器

### 4.1 全部任务阶段

```text
waiting_input
queued
preparing
submitting
polling
downloading
download_failed
succeeded
failed
blocked
cancelled
uncertain
resume_pending
```

终态为 `succeeded / failed / blocked / cancelled`。`download_failed`、`uncertain` 和 `resume_pending` 是需要人工或恢复入口继续处理的非终态，不能简单按“失败即释放并重发”处理。

提交状态另行持久化：

```text
not_sent | maybe_sent | accepted | terminal
```

`phase` 是本地执行阶段，`submissionState` 是远端提交事实，两者不能合并。

### 4.2 全局 10 名额与租约

- `tasks.ts` 定义 `CANVAS_DEFAULT_GLOBAL_TASK_LIMIT=10`，所有画布的图片与视频任务共享，默认不是每画布 10 个。
- 占名额阶段为 `preparing / submitting / polling / downloading / uncertain`。
- `waiting_input / queued / download_failed / resume_pending` 和终态不占名额。等待上游时不会卡住其他可运行任务。
- `slotHeld` 在 SQLite 写事务中计数并领取，多个 scheduler 实例也不能突破全局上限。每模型 `quotaKey` 可另有上限；`seedance20-4k` 还有内建单并发与提交间隔保护。
- lease 是本地工作权，不是远端生成名额。默认 lease 60 秒，scheduler 按 lease/3 心跳续期；`fence + leaseOwner` 防止失去所有权的 worker 继续写状态。
- 有远端身份的过期 polling/downloading 可以接管原任务和原名额，不会回到 preparing 重新 POST。某任务缺输入或模型名额不足时跳过它继续扫描。
- scheduler 默认 tick 2 秒（生产 bootstrap），循环异常不能终止调度；前端 1.5 秒轮询只更新展示，不驱动任务。

## 5. 执行、产物发布与恢复

### 5.1 单次任务执行红线

`runner.ts` 和 `adapters/types.ts` 把执行拆成 `prepare / submit / poll / download / cancel`：

1. scheduler 领取任务、名额和 lease/fence，runner 从任务快照构造输入，等待上游只认绑定的产物，不读后来更新的节点当前结果。
2. `prepare` 只做媒体预检和交付，不产生生成调用。失败表示尚未提交，按普通失败结束。
3. 任何生成 POST 前，必须以当前 fence、leaseOwner 持久化 `submitting + maybe_sent`；条件更新失败则不发送。
4. `submit` 只执行一次生成 POST。拿到 `providerTaskId` 立即落库，再进入轮询；响应不明或普通网络 `TypeError` 进入 `uncertain`，不得自动重发。
5. 有远端身份后只查询原任务。轮询错误保留身份并在后续继续；本地 abort 不清除远端身份或名额。
6. 下载写任务专属文件并做媒体探测，再登记不可变资产。资产插入、任务成功、使用租约检查和节点发布在同一数据库事务中完成；失去租约的 worker 只能清理自己的临时文件。
7. 如果输出已经登记、只是发布事务曾中断，恢复会接管同一 `outputAssetId`，不会重新下载或生成。

每个任务最多一个正式输出；生成结果不做内容去重。上传导入素材则在同一画布内按内容哈希复用。

### 5.2 启动恢复与人工操作

`recoverCanvasTasks()` 在 readiness 通过后、创建新 scheduler 时运行：

| 中断情形 | 恢复结果 |
| --- | --- |
| 有 `providerTaskId` | 清 lease，交 scheduler 续查或补下载，不重新提交 |
| `preparing` 且无远端 ID | 确定未提交，转 `resume_pending`、释放名额，等用户继续 |
| `submitting` 且无远端 ID | 可能已送达，转 `uncertain + maybe_sent`、保留名额，禁止自动重发 |
| 已有 `outputAssetId` | 接管同一输出并完成收尾，不重新生成 |

人工恢复 API 的语义：

- `resume`：只允许 `resume_pending`，用原输入和参数回 `queued`；不读取后来编辑的草稿。
- `reconcile outcome=not_created`：用户确认远端未创建，按失败收尾并释放名额。
- `reconcile outcome=remote_id`：填入实际远端 ID，接管原任务续查。
- `download-retry`：只允许 `download_failed` 且有远端 ID，回 `polling` 补下载，不新增生成调用。
- `cancel`：未提交任务直接取消；已提交任务只记录取消意图，远端未确认取消时转 `uncertain` 并保留身份与名额。

## 6. 能力表与真实适配器

- `capabilities.ts` 按“供应商类型 + 路由身份 + 精确模型别名 + 合同版本”登记能力，校验模式、输入类型/角色/数量、媒体组合和参数。
- 证据等级为 `verified / mapped / candidate`。只有真实链路样例才能提升为 verified；fixture 通过不能把 mapped 变成 verified，文档出现的新字段也不能直接当成已验证。
- 注册表放在 `globalThis`，避免 instrumentation 与 route 各自打包导致能力表分裂。`capabilities-bootstrap.ts` 按 executor 注册 fixture、公司以及当前设置中真实可用的外部能力；历史注册项可供在途任务恢复，但新选择列表只含当前可用项。
- `company-providers.ts` 在执行前从 `providers` / `video_providers` 读取实际 baseUrl 和 API Key。任务快照只存脱敏的供应商身份与精确模型别名；找不到、已禁用、模型或协议漂移都在 POST 前失败。
- `media-delivery.ts` 把素材交付与生成 POST 分开。七牛渠道和公司尾帧必须走 COS 预签名 URL，缺配置或上传失败在 POST 前 fail closed；视频/音频参考也没有本机 URL 回退。外部图片在特定路径可回退 data URL，不能把这个例外放宽到视频/音频。
- 画布按节点显式角色和提示词提交，不自动叠加旧工作流“图 1 是底图、图 2-N 是参考图”的前缀。

## 7. 素材、用量、ZIP 与日志安全

### 7.1 素材与文件边界

- 上传只接受 multipart 文件，**不接受客户端提交的任意本机路径**。文件复制到 `dataRoot()/storage` 下受控画布目录，之后使用不可变资产 ID。
- 导入上限：图片 32 MiB、视频 512 MiB、音频 64 MiB；这是本地导入边界。交付层另有更严的默认边界（图片 30 MiB、视频 200 MiB、音频 15 MiB，视频/音频默认最长 15 秒），能力表可按模型进一步收紧。
- 图片用 sharp 探测，必要时回退共享 FFmpeg；视频/音频尽力探测时长。结果视频还记录宽高、时长、编码和像素格式。
- 读取必须校验资产归属、受控路径和 symlink，支持单段 Range。浏览器预览可生成兼容副本；正式下载与 ZIP 始终使用原始文件。

### 7.2 用量记账

`usage.ts` 是通用账本的画布包装：

- `refType='canvas-task'`、`refId=taskId`，稳定 `eventKey='canvas-task:<taskId>:submitted'`。
- 远端接受提交后记账，产物完成后可再次补充视频时长；同一 eventKey 去重，所以查询、补下载、重试、复制、切换画布和导出都不会增加生成调用数。
- 视频按实际/任务参数时长计量，图片数量为 1。没有价格依据、非公司计价身份或样片阶段未具备计价依据时明确返回未计价，不伪造 0 元记录。
- 账本写入是尽力而为的旁路，失败只漏记并由通用 reconcile 补记，绝不能改变任务状态或触发重新生成。
- ZIP 导出不占生成名额、不调用模型，也不新增用量。

### 7.3 ZIP 导出

`export.ts` 的流程是“固定 manifest → 预检文件 → 写完整 ZIP → 标记 ready → 下载”：

1. 在服务端固定选中生成节点当时的 `currentAssetId`、图修订、文件大小和 SHA-256；打包期间节点后来出新结果不影响这份导出。
2. 无结果、已删除或非生成节点进入 `skipped`；一个可导出项都没有则拒绝。已选资产或文件缺失会报错，不能静默少文件却宣称成功。
3. 文件名清洗并处理重名，ZIP 内含选中原始媒体与 `manifest.json`。ZIP 内 manifest 记录文件名、节点、媒体类型、大小和哈希，不包含未选输入、历史产物、API Key 或签名 URL。
4. 导出记录状态为 `pending / ready / failed`，只有 ready 才能下载，Content-Disposition 文件名同样经过清洗。

### 7.4 日志与敏感信息

- `logs.ts` 使用独立 `creative_canvas_logs`，并写 `storage/logs/canvas-YYYY-MM-DD.log`，不借用旧项目日志表。
- 所有消息经过 `sanitizeMessage()`，会清理 URL query、API Key、Bearer/Authorization 等模式。网关错误还使用 `sanitizeGatewayMediaDiagnostic` 并截断；新增日志点不得输出请求头、密钥、完整签名 URL 或媒体 Base64。
- 阶段变化、远端身份、错误和取消意图才记任务日志；轮询计数和 lease 心跳不刷屏。历史任务没有完整日志时明确展示“历史快照”，不得编造过去过程。
- 日志 DB/文件写入失败都不能改变任务结果。启动运行失败会额外写一条画布错误日志。
- `/api/canvas/models` 只返回脱敏能力，不返回密钥、私密配置或完整鉴权 URL。`providerTaskId` 为恢复核查和样本回执而返回，不应把它当作密钥，但也不能因此放宽其他字段。

## 8. API 与 UI 入口

### 8.1 API 总表

所有 `/api/canvas` 路由统一过功能开关和 readiness。

| 路由 | 方法与职责 |
| --- | --- |
| `/api/canvas` | GET 画布列表；POST 新建空图 |
| `/api/canvas/[id]` | GET 图、节点投影、近期任务与候选；PATCH 分别保存图、名称或视口 |
| `/api/canvas/[id]/assets` | GET 画布素材；POST 上传不可变素材 |
| `/api/canvas/assets/[assetId]` | GET 预览/下载原文件，支持 Range |
| `/api/canvas/assets/[assetId]/draft` | GET 样片来源及视频元数据 |
| `/api/canvas/[id]/copies` | POST 同画布节点复制/粘贴，snapshotKey 幂等 |
| `/api/canvas/[id]/plan` | POST 单点/分支计划预检，只读 |
| `/api/canvas/[id]/runs` | POST 幂等创建运行和任务 |
| `/api/canvas/tasks` | GET 跨画布近期任务，可按 canvasId/phase 筛选 |
| `/api/canvas/tasks/[taskId]/cancel` | POST 请求停止 |
| `/api/canvas/tasks/[taskId]/resume` | POST 继续确定未提交任务 |
| `/api/canvas/tasks/[taskId]/reconcile` | POST 提交待核查结论 |
| `/api/canvas/tasks/[taskId]/download-retry` | POST 补下载原产物 |
| `/api/canvas/models` | GET 当前脱敏模型能力与 executor |
| `/api/canvas/[id]/logs` | GET 画布/任务日志 |
| `/api/canvas/[id]/exports` | POST 固定选中当前结果并生成 ZIP |
| `/api/canvas/exports/[exportId]` | GET 导出状态；`?download=1` 下载完整 ZIP |

复制目前只支持同一画布，跨画布返回 forbidden。复制会重新分配节点身份、映射内部连线、保留固定结果资产，不复制任务、lease 或 activeTaskId；同 snapshotKey 重试返回同一结果。

### 8.2 页面与前端职责

- `app/canvas/page.tsx` 是列表和新建页；`app/canvas/[id]/page.tsx` 挂载 `CanvasEditor`。
- `CanvasEditor.tsx` 使用 `@xyflow/react` 提供节点、连线、视口、撤销/重做、复制粘贴、单点/分支运行、任务抽屉、日志和选中结果导出。
- `editor/save-pipeline.ts` 以 600ms 防抖保存图，携带 expectedGraphRevision；保存期间的新编辑串行补保存，409 保留本地草稿并显示冲突，不用服务端旧图覆盖正在编辑的内容。
- `editor-store.ts` 严格区分编辑定义与运行投影。每 1.5 秒获取画布投影，但不重建图；`runtime-store.ts` 按 nodeId 精确订阅，避免任务轮询打断输入。
- 新成功产物会自动物化成带固定 assetId 的素材节点和溯源边；旧任务重跑不会替换已物化节点的资产。
- `nodes.tsx` 提供停止、继续、待核查、补下载等恢复操作；`CanvasTaskDrawer.tsx` 每 2 秒读取跨画布近期任务。两者都只是控制/展示入口，真正执行在后端 scheduler。
- React Flow 样式位于 `app/globals.css` 的 Tailwind 导入之后。新增画布 UI 继续使用设计令牌和暗色覆盖约定。

## 10. 测试与验证入口

### 10.1 当前测试文件事实

当前工作树**没有收录** `scripts/*creative-canvas*.test.*`、`scripts/canvas-*.test.*`，也没有其他测试文件导入 `lib/creative-canvas/`。因此不能编造 `node scripts/canvas-*.test.ts` 之类的专用命令。

`scripts/final-edit-canvas.playwright.test.mjs` 读取的是 `components/final-edit/text-canvas-renderer.ts` 和 `lib/final-edit/cover-framing.ts`，用于成片文字 Canvas 渲染，**不是创作画布测试**，不能作为本模块验收依据。

修改本模块时应补充真实的同名领域测试，至少覆盖：关闭开关零表/零 worker、迁移历史与 gate、跨 scheduler 名额、lease/fence、单次 POST 与 uncertain、输出发布中断恢复、项目/画布归属、用量去重和 ZIP 内容边界。

### 10.2 可运行的共享设施回归

以下命令只验证共享升级机制，不等于创作画布全量验收：

```bash
node scripts/schema-upgrade-lock.test.ts
node scripts/schema-upgrade-recovery.test.ts
```

通用停机与静态检查：

```bash
node scripts/graceful-shutdown.test.ts
npm run lint
```

真机 fixture 验收必须同时提供显式功能开关、临时数据根标记和独立数据根；不要在默认开发数据根上用 fixture 代替真实供应商，也不要把 fixture 结果当成公司能力的 verified 证据。
