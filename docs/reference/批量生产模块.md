# 批量生产模块

本文是 `lib/batch-production/`、批量 API、统一审片与批量导出的常驻架构参考。修改这些代码前先读本文；共享包装与贴纸运行时另见 `docs/reference/视频包装.md`。

**当前事实基线**：`lib/batch-production/schema.ts` 的 `BATCH_SCHEMA_MIGRATIONS` 最新版本是 **v27**。统一审片代码中的“v14 工作台”是界面行为基线，和数据库迁移 v14 不是一回事，不要混淆。

## 1. 模块边界与主链路

### 1.1 责任边界

批量模块负责：

- 项目素材目录、素材来源健康与分析版本；
- 批次、整体输入版本、脚本快照、成片计划与输出版本谱系；
- 口播、语义矩阵、联合分配、代理与封面/整片渲染任务；
- 统一审片、当前成片 arrangement 编辑、审核、正式发布；
- 批量自己的 schema 迁移及共享安全升级门禁。

共享能力从 `lib/media-core/` 取用：存储路径、媒体分析/TTS/对齐、字幕与封面领域、音轨编辑、包装与贴纸、渲染合同等。**不得从 `lib/final-edit/` 导入实现**；旧路径中的兼容再导出不是新的依赖方向。静音视觉候选只用于检查，不能通过正式发布。

前端入口是 `components/mixcut/MixcutWorkspace.tsx` 的批量模式，主面板为 `components/batch-production/BatchPreparationPanel.tsx`。统一审片位于 `components/batch-production/review/`。

### 1.2 当前生产顺序

```text
准备脚本与素材
→ 基础/内容分析并锁定 analysisId
→ 确认整体输入（draft 快照 + N 条稳定计划）
→ 开跑前语义矩阵门禁
→ start 冻结批次版本、BGM 池与导出身份
→ 每份脚本快照一条口播任务
→ 口播全部到终态后做全批联合分配
→ 每条计划建立/复用候选 output version，并排独立封面任务
→ 统一审片编辑与审核
→ 导出阶段按当前完整渲染合同排整片任务
→ 成功候选重新预检并发布 MP4 + JPG 正式产物对
```

编辑器优先模型下，生产阶段**不预渲染整片 MP4**。分配后排的是 `output_version_cover`；完整视频仅在正式导出时按需生成。

## 2. Schema、备份、跨进程锁与审计

### 2.1 迁移规则与当前版本

权威清单位于 `lib/batch-production/schema.ts`，历史记录表为 `batch_schema_migrations(version, appliedAt)`。

- 新迁移只能在 `BATCH_SCHEMA_MIGRATIONS` 末尾追加；不得修改已发布 SQL，不得复用旧 core migration runner 吞错。
- 每个版本在一个 `IMMEDIATE` 事务中执行 SQL、`foreign_key_check`、版本记录和截至该版的结构校验；失败时本版整体回滚，后续版本不执行。
- 迁移历史存在缺版、未知版本或高于当前代码版本时进入 `compatibility_only`。没有待迁移项时也会复核实际结构与 `integrity_check`。
- SQLite 不能直接修改 CHECK 的表按“新表 → 拷贝 → 改外键引用 → 先删叶子表 → 再删父表 → 改名”处理。v14/v21/v23/v25 的任务表重建必须保留 attempts；v25 还必须保留 `batch_asset_analysis_requests`，避免 `foreign_keys=ON` 时 DROP 父表触发隐式级联删除。
- 当前结构校验还覆盖正式产物删除保护、代理请求谱系、分配谱系、素材级代理的部分唯一索引及脚本目录删除状态。

### 2.2 升级门禁

`readiness.ts` 调共享 `lib/schema-upgrade/gate.ts`；`runtime-readiness.ts` 用 `dataRoot()` 解析运行路径并缓存成功结果，失败结果下次重查：

```text
data/backups/schema-upgrades/
data/schema-upgrade.lock.db
storage/logs/schema-upgrades.jsonl
```

一次门禁的顺序：

1. 在独立锁库上以 `BEGIN IMMEDIATE` 获取跨进程写锁；默认等待 15 秒，超时为 `upgrade_in_progress`，其他锁错误为 `lock_unavailable`。
2. 修复可修复的 JSONL 审计：重写有效记录、登记坏行恢复；为只有 `started` 没有完成记录的旧尝试补 `interrupted_recovered`；清理中断遗留的 staging 备份目录。
3. 写 `started`。审计不可写则 fail closed，不执行迁移。
4. 有待迁移版本时，先做 SQLite Online Backup。空间要求为数据库大小加 `max(16MiB, 10%)`；备份库重新打开做完整性/外键检查，记录字节数和 SHA-256，写 `manifest.json` 后将 staging 目录原子改名发布。
5. 逐版本迁移与结构/完整性校验。备份失败、空间不足、历史异常、迁移失败都进入兼容模式，不执行后续升级。
6. 写入 `backup_completed` / `migration_completed` / `validation_completed` 或 `compatibility_entered`，最后写 `finished`；结果审计写失败同样判不可用。

所有批量 API 在读写 `batch_*` 前必须 `assertBatchApiReady()`。兼容模式返回 `BatchApiUnavailableError`，由 HTTP 层统一映射为 **503**；不依赖批量新结构的旧功能不被要求中断。不得用“先读一下看看”绕过门禁。

`GET /api/batch-production/recovery` 只列出经 manifest 大小、SHA-256、完整性和外键复核的恢复候选。`requiresApplicationShutdown=true`、`automaticRestoreAvailable=false`：必须完全退出工作台后再次验证并人工恢复，运行中不覆盖数据库。

### 2.3 调度启动

`bootstrap.ts` 在 readiness 通过后启动进程内单例调度器；应用启动和批量写 API 都可幂等触发。启动前会：

- 重试上次因占用而持久化延后的代理删除；
- 将旧实例遗留 running attempts 标为 interrupted 并按控制态恢复任务；
- 注册 `asset_prepare`、`proxy_generate`、`narration`、`semantic_score`、`render` 执行器；
- 以 2 秒间隔轮询，不随每个 API 请求新建调度器。

## 3. 批次、版本、脚本快照与输出谱系

### 3.1 两层“版本”不要混淆

**批次输入版本** `batch_production_versions`：

- 固定 `copyCount` 与 `defaultsJson`；`batch_productions.currentVersionId` 指向当前输入版本。
- 确认整体输入时先处于 `draft`；真正冻结发生在 start，`inputState='frozen'` 且写 `frozenAt`。
- 整体输入相同可幂等复用；输入变化创建新输入版本，并冻结先前 draft。旧版本、历史候选和正式产物保留。
- `archivedAt` 是独立于生产状态的批次归档维度；`deletedAt` 是逻辑删除，均不物理抹掉历史谱系。

**单片输出版本** `batch_output_versions`：

- 属于一条稳定 `batch_output_plans`，含 `versionNumber + arrangementJson + allocationRunId`。
- `batch_output_plans.currentVersionId` 是当前候选；重新分配可新建输出版本并切换指针。
- 审片中的普通编辑是**就地改当前候选 arrangement**，不是每次编辑都新建 output version。
- `currentArtifactId` 独立指向已发布视频 artifact，不随候选切换或重新分配自动变化。旧正式成片因此仍可播放，直到新候选明确发布。

### 3.2 脚本与快照

`batch_scripts` 同时容纳：

- 第三步同步的项目脚本、手动导入脚本（`manual:` 命名空间）；
- 仅属于某个未冻结批次版本的外部文案（`ownerBatchVersionId`），后者不进入项目脚本目录。

`snapshotScriptIntoBatch` 将当时内容冻结为 `batch_script_snapshots`，包括：标题、正文、来源版本、`scriptCode`、封面标题、`shotSetId`、`contentRevision`、每脚本目标时长、口播配置和本脚本生成份数。每份快照的 `copyCount` 决定计划数，同一脚本 N 条成片共用同一口播。

`createBatchSnapshot` 在一个事务中建立/复用 draft 输入版本、全部脚本快照、素材池和计划：

- 至少一份脚本和一份带 ready 分析版本的在线素材；
- 校验项目归属、来源可用性、素材/分析归属、重复选择与正整数份数；
- 计划序号在输入版本内全局递增，每份快照恰好 `copyCount` 条，失败重试不能多出计划；
- 相同输入幂等返回稳定计划；比较也包含当前上游正文/元数据、素材 analysisId、完整色彩身份和 defaults；
- `batchMusicPool` 与 `batchExportIdentity` 是 start 时服务端补入的运行期快照，不参与“客户端整体输入是否变化”的比较。

start 会在同一事务里再次同步第三步权威草稿并把最新脚本字段刷新进快照，然后冻结，避免“确认后、开跑前”的上游修改被静默锁成旧内容。冻结时还把 `batchExportIdentity` 写入版本 defaults：后续口播、渲染与发布不随项目当前身份切换。

### 3.3 分配运行与产物谱系

```text
project
└─ batch_productions
   └─ batch_production_versions
      ├─ batch_script_snapshots ─ batch_script_narrations
      ├─ batch_asset_pool_items ─ batch_asset_exclusions
      ├─ batch_allocation_runs
      └─ batch_output_plans
         ├─ batch_output_versions ─ batch_task_attempts.resultJson（渲染候选）
         └─ batch_artifacts（正式 video/cover）
```

- 分配运行以 `(batchVersionId, ruleVersion, seed, inputFingerprint)` 唯一，当前规则版本为 `batch-allocation-v4`，arrangement schema 为 `batch-arrangement-v1`。
- `currentAllocationRunId` 是显式指针，不用创建时间猜“当前运行”。排除再恢复素材时可重新激活一个旧的确定性运行。
- 输出版本记录 `allocationRunId`，可追溯到具体运行；正式 artifact 另存完整项目/批次/输入版本/计划/输出版本谱系与 checksum。
- 审核态也位于当前 output version 的 `arrangement.review`，不另建审核表；重新分配产生没有 review 的新版本，自然要求重审。

## 4. 素材身份、来源、分析与代理

### 4.1 内容身份与多来源

`batch_assets` 的身份是 **`projectId + contentFingerprint`**，不是文件名或路径。同项目同指纹复用素材；同名不同内容必须是新素材。规范指纹为 `sha256:<hex>`。

权威多来源在 `batch_asset_sources`：

| 来源 | 定位与约束 |
| --- | --- |
| `module4` | 从成功且未剔除的 `video_jobs` 登记，保存 videoJobId、shotSetId、shotId 与 storage 相对路径；只引用原产物，不复制/移动 |
| `managed` | 浏览器上传后复制到 `dataRoot()/storage/batch-media/<projectId>/<fingerprint>.<ext>`，数据库保存 dataRoot 相对路径 |
| `linked` | 用户原文件绝对路径，只引用；项目不得删除、移动或改写用户原文件 |

`batch_assets.sourceKind/locationJson` 只是首个来源的兼容字段，CHECK 仅允许 `linked|managed`；首个来源为 module4 时记录为 managed。新增来源不得覆盖首个兼容字段。

来源健康为 `healthy/offline/changed`：至少一个 healthy 时主素材 online；全部不可用则 offline；用户 archived 不被健康聚合覆盖。重新定位链接必须重新计算完整 SHA-256，内容相同才能沿用旧素材身份。剔除 module4 视频后，对应来源不得进入新批次；若同内容另有合法 managed/linked 来源，仍可使用该素材。

准备区和缩略图读取可使用 `lastVerifiedIdentityJson` 的 `dev/ino/size/mtimeMs` 快速路径；身份不一致或缺失时仍须完整哈希，不能用文件大小/名称代替内容身份。

### 4.2 分析版本

`batch_asset_analysis` 属于项目素材，可被多个批次复用；素材池锁定具体 `analysisId`，不是到分配时才读“最新分析”。

- **technical**：本地 ffprobe 的时长、宽高和媒体信息。
- **content / vision**：抽帧视觉分析，含场景、标签、可用区间、质量与封面时间点；`batch_asset_analysis_requests` 冻结任务创建时的素材指纹、provider、model 和 external/company executionScope，重试不得静默换模型或路由。
- **content / filename**：外部导入素材的本地文件名描述。它仍核验原片并记录整段场景，但明确不是画面观察，不推断动作时间或真实画质；已有 vision 内容分析不会被文件名描述覆盖。

只有分析适配器显式写 `analysisLevel='content'` 才按内容分析使用，不能凭 JSON 中出现 scenes 就把旧技术数据升级为内容分析。`currentAnalysisId` 的切换与分析版本创建在同一事务发布；历史批次仍引用旧 analysisId。

### 4.3 代理与预览不是正式原片

代理身份只由 `assetId + 原片完整指纹 + profileVersion` 组成。当前 profile 为 `proxy-v1`：高度不超过 720、H.264/yuv420p、AAC、faststart、固定 GOP 50。**LUT、文件名、显示名和路径不参与 proxyKey；换 LUT 不重转码。**

三层职责：

- `batch_proxy_cache_items`：按 proxyKey 全局唯一的可复用派生文件；
- `batch_proxy_requests`：稳定请求身份，可绑定批次版本，也可以是 v25 起的素材级请求（batchId/batchVersionId 同时 NULL）；`currentCacheItemId` 在缓存删除时 SET NULL，请求历史不悬空；
- `batch_tasks`：目标始终是 request，不是可删除的 cache 行。素材级任务的 batchId 也可为 NULL，只有这一类任务允许无批次。

预览统一走 `resolvePreviewSource`：匹配 ready 代理优先，其次 healthy 原片，否则不可用。原片离线仍可观看到已生成代理，但必须标注“正式导出不可用”。预览媒体持读取租约；生成持写入租约；清理遇占用写 `pendingDeleteAt`，最后租约释放后删除，进程重启也会恢复删除。清理不会自动重建代理，只有用户再次显式请求才生成。

代理生成前重新完整核验原片，临时文件验证后才原子发布；正式渲染绝不回退到代理。浏览器原片不能解码时可使用独立 H.264 预览衍生物，这同样不改变正式导出的原片要求。

## 5. 准备、冻结、分配与任务控制

### 5.1 准备和开跑门禁

`prepareBatchProductionInputs` 只做准备展示，不建快照、不开跑：

1. 同步第三步有效脚本；
2. 自动登记第四步成功且未剔除的视频，单个登记失败只形成 warning；
3. 核验所有素材来源并聚合健康；
4. 返回安全的脚本/素材视图，不向浏览器暴露本地路径。

`PUT /batches/[id]/start` 的顺序：

1. 显式开跑先把 paused/stopped 控制态重新激活；这与普通 resume 不同，是用户明确的新动作。
2. draft 输入先准备语义矩阵；仍有打分任务时返回 `semantic_scoring`，尚未冻结。打分失败、无供应商或无内容场景不阻塞后续关键词/质量兜底。
3. `startOrResumePhaseE` 冻结输入；BGM ready 曲库为空会拒绝开跑，非空池快照进 `batchMusicPool`。
4. 每份脚本快照建一条幂等口播任务；未完成时返回 `narration_pending`，前端在任务终态后续跑同一入口。
5. 口播全部到终态后执行联合分配并排封面任务。口播失败仍允许生成静音候选供检查，但正式发布会 fail closed。

### 5.2 口播与语义分配

口播执行以 `batch_script_narrations` 为权威快照，每份脚本快照一条：

- 快照正文 + provider/type/model/baseUrl + voice + speed + adapter version 形成复用键，同脚本 N 条成片共享音频；
- `local_ready` 必须包含安全 storage 相对路径、完整音频指纹、正时长和合法对齐句段，`productionReady=true`；
- 渲染先读当前 arrangement 的口播 seam，新分配没有 seam 时可回落权威表；
- 渲染前重新核对音频指纹和实际时长（容差 0.1 秒），缺路径/指纹/就绪位的静音候选不能正式发布。

分配器是纯函数，SQLite/网络/文件装配都在 `allocation-store.ts`：

- 使用冻结脚本、锁定分析、口播真实句段时间、排除集合、锁定片段、色彩身份和冻结 BGM 池；
- 语义矩阵按脚本句段内容键 + 素材池场景内容键复用，不按输入版本硬绑；0.6 均匀 fallback 不落库，分配改走关键词重合与质量；
- opening/body 角色参与取用，同源原始分镜图有分组/避让；长句可按词级时间戳细分，单素材装不下时可拼接多镜头；
- 当前版本里 `locked=true` 的片段作为锁定输入保留；
- 有已核验口播时，目标时长和句段时间使用真实对齐，arrangement 直接写入口播路径/指纹/句段；无口播时保留明确的非生产就绪占位与预计字幕；
- 输出只更新当前候选和当前分配运行，不碰旧正式 artifact。

排除素材会重算全批；离线或非 ready 分析自动形成排除原因，手工排除存 `batch_asset_exclusions`。单条“换一批画面”以当前运行 seed、planId、原因和当前 outputVersionId 派生新 seed，避让该计划历史所有版本用过的素材与封面；没有可用新安排或与当前完全相同时不新增 output version。候选切换后，旧版本/被阻塞计划的封面和整片任务失去提交资格。

### 5.3 任务、租约与恢复

当前工作类型：`asset_prepare`、`proxy_generate`、`narration`、`semantic_score`、`render`。任务状态为 `queued/running/succeeded/failed/cancelled`，期望状态为 `running/paused/stopped`；attempt 另有 `interrupted`。

- `requestKey` 是稳定业务幂等键，重复提交返回同目标任务；已取消任务会释放 key，代理 cache 失效也会释放死任务的 key。不得把时间戳或随机数放进幂等身份。
- 每次领取递增 attemptCount，写 claimedBy、heartbeat 和默认 5 分钟租约。默认 worker 并发 2，代理真正 FFmpeg 编码另有进程内单并发互斥。
- 心跳独立续租并检查任务 expectedState、批次 controlState、渲染目标是否仍是当前版本。进度写库默认节流 1 秒，不可测进度用 null，不伪造百分比。
- 成功提交在 IMMEDIATE 事务里复核租约、控制态、当前目标和渲染合同；commit 的数据库发布与 succeeded 同一事务。迟到候选用执行器 `discard` 清理。
- 崩溃/过期恢复将 running attempt 标 interrupted，任务回 queued，同时尊重 paused/stopped 期望；应用 shutdown 不是用户取消，任务保持可恢复。
- 整片 render 还有口播领取闸门：同脚本口播 queued/running/failed 时不可领取；独立封面任务不走这个整片闸门。

控制语义：

| 操作 | 行为 |
| --- | --- |
| 批次 pause | 立即停领新任务，queued 标 paused；运行任务心跳中止后回 queued/paused |
| 批次 resume | 恢复 running，只有 queued+paused 的任务回到 running 期望；stopped 不能普通恢复 |
| 批次 stop | queued/failed 直接 cancelled，运行任务中止并取消；成功结果、历史和正式产物保留 |
| 单任务 pause/resume/cancel | 只改目标任务 expectedState，不改批次或其他任务；cancel 是终态，重提交业务动作才形成新任务 |
| retry | 失败任务原地回 queued，只增加 attempt；成功 render 也允许显式重试，不新增成片计划 |
| 显式 PUT start | 可重新激活 paused/stopped 批次，再走幂等生产续跑，不是调度器擅自恢复 |

口播重试成功排队后，还会清除同脚本快照下当前成片的人工字幕覆盖（保留字幕样式），递增 editRevision 并清审核，防止旧字幕/旧审核误导出。

## 6. 工作区聚合与统一审片（v14 行为）

### 6.1 服务端工作区事实

`batch-workspace.ts` 不从“最后一条任务”拼卡片状态，而是组合当前 arrangement、口播、独立封面任务、整片任务、正式 artifact 对和渲染合同：

- `reviewable`：有当前候选且批次未 stopped；
- `approvable`：当前候选 + 口播 productionReady + 当前封面合同任务成功 + 未 stopped；
- `approved`：当前 `arrangement.review.decision === 'approved'`；
- `exportEligible`：approvable + approved + 口播任务未 failed；
- `formalOutdated`：当前正式视频/封面不能证明对应当前完整渲染合同；缺配对封面、指纹找不到成功渲染来源也保守判过期；
- `exportStatus`：由服务端统一给 `not_exported/rendering/failed/exported`，前端不得自行从 fullRenderTask 另拼一套。

封面 A→B→A 时必须按当前 `coverContractHash` 选任务，不能拿较新的 B 任务冒充 A。老批次没有独立封面任务时才回落最近成功整片候选。

### 6.2 四区同屏与三种独立选择状态

`BatchUnifiedReviewWorkspace` 当前为四区：

1. 左上素材池：opening/body 分类、预览、项目内导入、使用次数和高亮定位；封面使用与视频片段使用分开统计，分割后的两段各计一次。
2. 中央实时预览：当前成片、原素材预览、源监视器、封面和包装叠加。
3. 右侧检查器：字幕、画面、封面、音频、包装；贴纸页签在包装内。
4. 底部统一时间轴：共享秒尺/播放头，每片独立的字幕、卖点、贴纸、视频、口播和 BGM 轨道。

三套状态不能混用：

| 状态 | 用途与持久性 |
| --- | --- |
| `selectedPlanId` | 当前检查器/编辑目标，单片；不等于多选，也不是眼睛状态 |
| `selectedPlanIds` | 复选框集合，供批量审核/导出及贴纸复制初始目标；由外层控制，可 approvable 的行才可勾选 |
| `eyeMap` | 每行眼睛可见性，默认 true，仅工作台本地 UI 状态，不写数据库、不影响审核与导出 |

预览规则：通常取卡片顺序中**第一条眼睛可见**的成片，所有行共用播放头。包装检查器页签下优先预览 `selectedPlanId`，以便编辑当前包装；没有可见行时显示全部隐藏提示。

单条“确认这条”保存成功后才隐藏当前行眼睛、选择下一条仍可见的成片并复位播放头；保存失败不推进。它不改多选集合，也不改其他行眼睛。撤销已确认只撤销审核，不做自动前进。

### 6.3 v14 时间轴与素材检查

- 行筛选“全部/待检查/已确认”只隐藏不匹配行，不改数据和眼睛。
- “区间重复”保留全部行，只调暗没有重复/同源提示的片段；重复统计包含同片多段与 split，不只跨片。
- “显示全部轨道”只恢复所有眼睛，不清除行筛选。
- 同一素材用同编号/同色分组，源区间真实重叠另用斜纹；同源图生成的不同视频也有分组提醒。提醒用于审片，不自动阻塞审核或导出。
- 支持选择/分割、播放头分割、删除留空、撤销/重做、磁吸、缩放、素材替换/间隙插入/末尾追加。拖动使用本地草稿，松开一次持久化，Esc 不落数据。
- 素材池定位只高亮，不改变预览选择；开场与正文库都允许显式导入，新增素材只影响后续分配或显式编辑，不自动重排既有成片。

审核 API `POST /outputs/review` 只接受当前输入版本的 planIds，写 `approved/rework/cancelled`。cancelled 归一为 `decision=null` 并保留 decidedAt；它返回目标是否仍有 queued/running 整片任务。实质编辑清审核的逻辑在下一节，不在审核 API 中推断。

## 7. Arrangement 编辑、editRevision 与审核失效

权威实现为 `lib/batch-production/output-arrangement.ts`，当前可编辑事实在 `batch_output_versions.arrangementJson`。

### 7.1 写入门禁与版本策略

写编辑必须同时满足：批次输入已 frozen、批次未 stopped、计划属于批次当前输入版本、已有当前候选且 clips 数据有效。单条读取视图中的 `editable` 是 UI 提示，后端仍重新校验完整谱系。

- 普通编辑整读—修改—整写当前 output version，单事务落库；**不创建新 output version**。
- `set_packaging`、`set_cover`、`trim`、撤销恢复等需要乐观锁的命令同时校验 `expectedOutputVersionId` 和/或 `expectedEditRevision`，防止覆盖较新的正式修订。
- 实质内容变化（画面、音频、字幕、封面、BGM、包装）统一 `editRevision += 1` 并删除 `arrangement.review`。结果中的 `reviewCleared` 表示编辑前确有审核态。
- 视频 split 和音频 split 是纯结构操作：不改时长、不递增 revision、不清审核、不触发重渲染。字幕 split 会改变字幕结构，按实质编辑处理。
- `restore_arrangement` 逐字段校验撤销/重做快照。若视觉内容流及其余字段都等价，可按纯结构恢复；存在较新 revision 时拒绝覆盖，前端清空冲突历史。
- unchanged 命令不递增 revision、不清审核。

支持的编辑面包括：等长/变长 trim、源出入点、移动、替换、删除留空、插入、split、0.25–4 倍速、构图；口播/BGM 音轨分割、修剪、移动、删除；封面素材/时间/构图/标题与包装合并保存；BGM 曲目/增益/淡入淡出、口播增益；字幕文字/时间/分割/删除/恢复自动及样式；完整包装配置与撤销恢复。

最短视频/音频片段为 0.5 秒，时间边界按 24fps 处理。替换/插入/封面优先使用冻结池，也允许项目内当前在线的可用素材；被排除素材不能新引入。素材时长以冻结分析为主、媒体信息兜底，不能信任浏览器提交的任意路径。

### 7.2 编辑后的任务与审核

编辑只保存，不自动排整片。路由比较编辑前后的 `coverContractHash`，合同可解析且未变化时不排任务；封面素材、抽帧时间、构图、标题或会影响封面的首片段发生实质变化时才排/复用独立封面任务，BGM、字幕、口播音量等变化不触发封面任务。旧数据合同无法解析时保留 `visualChanged` 即尝试排封面的兼容回退。

`editRevision` 与包装、音频、字幕、封面、BGM 等一起进入完整渲染合同，因此贴纸或其他 arrangement 变化都会使旧整片任务/旧正式 artifact 过期。渲染执行完成时还会再次检查当前指针与合同，旧结果不得 succeeded。

## 8. 正式渲染、发布与 ZIP/快照边界

### 8.1 渲染合同与候选

`cover-contract.ts` 定义两类合同：

- `coverContractHash`：`cov_...`，含封面渲染版本、素材身份/指纹、抽帧时间、画幅、色彩快照、构图和标题；
- `fullRenderContractHash`：`rnd_...`，当前整片 adapter 为 `batch-render-v3`，含 outputVersionId、editRevision、包装（含贴纸）、音频编辑、preserveGaps、画幅、封面合同、clips、口播、字幕和音乐。

任务键分别为 `cover:<outputVersionId>:<cov>` 与 `render:<outputVersionId>:<rnd>`。渲染 executor 读任务冻结 arrangement 计算合同，完成时旧合同结果不能提交；正式 artifact 新鲜度用同一合同判断，老任务才回落 editRevision + coverTimeUs 兼容比较。

整片候选写到 `storage/batch-renders/<outputVersionId>-<uuid>/video.mp4` 与 `cover.jpg`，独立封面候选使用带 `cover-` 的唯一目录。失败/中止清理本次临时候选，迟到被丢弃的候选也不能成为正式产物。

### 8.2 导出编排与发布

`orchestrateBatchExport` 是正式导出唯一编排入口，对每条计划依次：

1. 校验当前输入版本、候选、审核通过与口播 productionReady；包装启用时默认拒绝主/副标题占位文字。
2. 对实际使用的原片重新做正式预检，再计算当前完整渲染合同。
3. 当前正式 artifact 对仍新鲜则 `already_published`，不重复复制；旧合同活动任务取消。
4. 无成功候选则创建/复用整片任务，返回 `render_queued/rendering`；失败返回 `render_failed`。渲染完成后再次调用导出即可进入发布，刷新页面后也需按当前状态续跑。
5. 成功候选在发布前重新核对完整谱系、`audioMode=narration`、`productionReady=true`、审核、合同、没有待渲染任务和原片预检。除整组共享前置校验或批次级门禁失败外，单条失败可 skipped，不回滚其他合法兄弟项。

正式预检 `checkFormalExportPreflight` 对每个使用素材重新完整哈希，至少一个原片来源匹配才可继续；使用 LUT 时还要求 FFmpeg 支持 `lut3d`、冻结 LUT 记录/路径存在，实际文件同时匹配冻结快照和目录记录。**不得用代理、同名新 LUT 或空指纹替代。**

发布位于项目成品目录：

```text
dataRoot()/storage/projects/<冻结 exportDirName>/成片/
```

文件名由冻结生产身份基础名（旧数据走回退命名）和脚本/开场/包装生产码决定；无生产码时追加两位 plan 序号，重名导出递增 `-02/-03`。发布过程使用独占 `.publish.lock` 预留、复制后双向 SHA-256 校验、临时文件 + hard-link no-replace，不覆盖既有文件。复制完成后、注册 artifact 前的最终事务里再次做修订号、封面时间、审核和完整合同 CAS；复制期间撤销审核也会被拦住。

每次成功发布登记一对 cover/video artifact，视频成为 currentArtifactId，封面按同版本与成对文件名匹配。旧 artifact 不删除；候选已修改未发布时旧正式成片继续可播可下载。

### 8.3 ZIP 与“快照”必须准确区分

当前批量代码**没有独立批量 ZIP 导出端点，也不会在正式导出时生成 ZIP 或 ZIP manifest**。批量正式交付物是逐片 MP4 + JPG 及数据库 artifact 谱系；批次/脚本/arrangement 快照保存在 SQLite，可通过批次详情与 arrangement API 检查。

不要把这些不同能力混写：

- `POST /api/batch-production/batches/[id]/exports`：上述逐片渲染与发布，不是 ZIP；
- `POST /api/batch-production/batches/[id]/snapshot`：建立 draft 数据库快照，不是下载快照包；
- `GET /api/projects/[id]/download`：项目旧 jobs/video_jobs 图片与视频 ZIP；
- `GET /api/projects/[id]/creative-package`：项目分镜、视频、脚本与 `project_artifacts` 的创作包。

后两个项目级路由并不以 `batch_artifacts` 或 `batch_output_versions` 为来源，不能默认它们已包含批量正式产物或批量 arrangement 快照。若未来增加批量 ZIP，必须显式设计所选正式 artifact 对、manifest 与快照字段，并沿用路径安全/指纹/谱系校验，不能把数据库备份当成产品 ZIP。

## 9. BGM、字幕、封面、LUT 与包装渲染

### 9.1 BGM 与口播音频

- start 时冻结 ready 曲库为 `batchMusicPool`，条目含 trackId、storage 相对路径、内容指纹和时长；自动分配使用冻结池，`batchMusicSelection` 可限定手动曲目集合。
- 当前单片可覆盖 `arrangement.music.trackId/gainDb/fadeInSec/fadeOutSec`。整批默认参数来自 `batchBgmParams`，缺省 `-18dB / 1.0s / 1.5s`，增益范围 -60–0dB、淡入淡出 0–30 秒。
- 渲染优先核验冻结曲目，也允许检查阶段新选的当前 ready 曲目；路径、文件和内容指纹不一致即失败。音频编辑空数组表示明确移除 BGM，不是回退到自动曲目。
- 口播增益在 `arrangement.narration.gainDb`，缺省走共享默认值。片头 20 帧期间静音，正文音轨整体后移。

### 9.2 字幕

有真实口播时，自动字幕由**本次冻结口播对齐句段**重新派生：先清洗标点，再按不超过 16 字切 cue，段内按去空白字数比例分配时间；不使用旧 estimated 槽位冒充新对齐。无口播的静音候选才使用分配阶段预计字幕。

人工 `arrangement.subtitle.source/mode=manual` 时以人工 cues 为准。恢复自动字幕删除人工 cues，但保留单片字幕样式覆盖；口播重试前清人工覆盖同样保留样式。

整批样式存 defaults 的 `subtitleStyles` 与 `subtitleStylesByScript`（按 sourceScriptId）；单片 `arrangement.subtitle.style` 只覆盖当前计划。渲染将字幕 PNG 在正文时间窗叠加，并随片头整体后移。

### 9.3 封面与片头

封面是独立冻结素材抽帧决定，不随时间线窗口变化而被重置。显式 cover 可指向冻结池内不在 clips 中的素材，抽帧范围为该素材整段原片；未指定时沿首片段默认起点。

封面标题配置由脚本快照 `coverTitleJson`、批次 defaults 的 `coverTitleMode/preset/styles/stylesByScript/framing` 共同决定；单片覆盖在 `arrangement.cover.title/framing`。sharp 负责裁切构图、SVG 主副标题与 JPEG quality 92。

整片片头是**同一封面静帧的 20 帧（24fps）**，正文画面、字幕和音频随后。启用 HyperFrames 包装时，底层封面标题让位给包装层，避免重复；贴纸只出现在正文，不出现在片头。

### 9.4 LUT 与输出验证

LUT 是受管内容身份：同项目同完整指纹复用，同名不同内容建立新身份。导入仅接受 .cube，复制到 `storage/luts/<projectId>/<fingerprint>.cube`，经真实 FFmpeg lut3d 小样验证后登记。归档只影响新选择，历史冻结引用保留；只有无引用时才允许物理清理。

素材池保存完整 `ColorSnapshotV1`：lutId、lutFingerprint（引用 LUT 时必须非空）、colorPipelineVersion、interpolation、outputContract。引用时必须与项目受管内容一致，`unresolved:` 或空指纹不能进入新输入。预览按冻结 LUT 实时叠加；代理不烘焙 LUT；正式渲染按冻结文件重新核验并用 lut3d 烘焙。

输出画幅预设为 3:4（1080×1440）、9:16（1080×1920）、16:9（1920×1080，也接受 x 写法）。整片最终验证包括 H.264/yuv420p、24fps、MP4、AAC 48kHz、实际尺寸与时长；不是写完文件就算成功。

包装配置由 `arrangement.packaging` 冻结，保存时补齐文案 overrides、字体和卖点时序并严格校验贴纸。预览与草稿预览只读配置，不随机改数据；正式导出经共享 HyperFrames 包装合成，包装关闭时保留但不渲染已有贴纸。

## 11. 贴纸：批量持久化、编辑与跨片复制

贴纸是独立领域，不与 `pointCues` 混合，也不新增表。

### 11.1 存储位置与当前片编辑

批量贴纸只存于**当前 output version**：

```text
batch_output_versions.arrangementJson
└─ packaging
   ├─ stickers?: PackagingStickerInstance[]
   └─ stickerDefaults?: { animation }
```

`packaging` 还包含目标自己的 enabled/template/varsOverrides/pointCues/layouts/fonts 等。跨片复制不得覆盖这些其他字段。

当前片添加、移动、修剪、换轨、缩放、旋转、改风格/动效、删除、自动布置、修改默认动效都通过 `set_packaging` 保存完整配置，并携带当前 `expectedOutputVersionId + expectedEditRevision`。后端 `prepareBatchPackagingConfig` 保留显式贴纸配置，按 `max(visualDurationUs, narration.durationUs)` 算正文帧并严格校验；成功后按普通实质编辑递增 revision、清审核，完整渲染合同随之变化。

主要 UI/运行时文件：

- `components/batch-production/BatchStickerPanel.tsx`：素材、默认/实例动效、一键布置、跨片入口；
- `BatchPackagingEditor.tsx`：包装设置/贴纸页签；
- `BatchPackagingOverlay.tsx`：预览内选中、几何编辑、删除与播放；
- `review/BatchReviewTimelineDock.tsx` 与 `BatchPackagingTrack.tsx`：贴纸轨道和卖点轨道；
- `review/BatchStickerCopyDialog.tsx`：目标筛选、已有贴纸替换与重审提示；
- `lib/media-core/packaging-sticker*.ts`：共享纯领域、规划、资源、变体与预览/渲染合同。

### 11.2 时间与实例规则

统一 24fps 整帧，片头 20 帧禁止贴纸；`endFrame` 为开区间。

- 默认手动时长 48 帧，最短 19 帧，正文剩余不足 19 帧不能添加；
- 自动一键布置要求正文至少 144 帧（6 秒），生成开头 2、中段 explain + gesture、结尾 2，共 6 张；
- 每片最多 128 张；自动换一组只替换自动实例并保留手动实例，已有编辑过的自动实例会先提示确认；
- 实例保存素材 ID、固定/跟随模板风格、起止帧、有效图案中心、视觉宽度、旋转、轨道、动效和 manual/auto 来源；自动来源含 autoGroupId/autoEdited；
- `stickerDefaults.animation` 是新贴纸默认值，不批量改写既有实例。“应用到全部贴纸”才是显式覆盖当前片所有实例动效；
- 四套模板分别映射 comic/journal/editorial/show。预览和正式导出都读已保存实例与原始 PNG，不能在 React 状态里临时生成“正式结果”。

### 11.3 跨片复制只换两个包装字段

入口为 `lib/batch-production/sticker-copy.ts` 与 `POST .../outputs/sticker-copy`，`type='copy'` 时必须给 sourcePlanId 与 targets，每个 target 带：

```ts
{ planId, expectedOutputVersionId, expectedEditRevision }
```

复制前统一校验：

- 来源与全部目标都在同一批次、同一当前输入版本，已 frozen、未 stopped、已有当前候选；
- 来源与目标包装均 enabled；来源至少一张贴纸；目标不得为空、重复或包含来源自身；
- 所有目标 outputVersionId/editRevision 与提交时一致；
- 目标正文能容纳映射后的贴纸，未编辑自动贴纸另受 144 帧下限。

实际写入只替换目标的 `packaging.stickers` 与 `packaging.stickerDefaults`，并保留目标模板、字体、文案、卖点、版式、clips、音轨和其他 arrangement 字段。目标已有这两个字段被整体替换；来源没有 stickerDefaults 时，目标该键也会被移除，不是合并残留。来源本身及来源审核态完全不改。

变体规则：

- 手动和已编辑自动贴纸保留素材、风格、位置、尺寸、旋转、轨道与动效，起止帧按目标正文等比映射；映射后仍逐张严格校验；
- 未编辑自动贴纸只复制来源仍存在的实例，按目标三阶段重新规划，从目标模板同类别素材和安全槽位抽取，并避开高使用素材；每张独立抽取 soft/bounce/rise/slide/zoom 可见动效；
- 每个目标生成新的实例 ID 与自动组 ID；随机只在 copy 命令规划时发生一次。

**生成结果立即写入目标 arrangement。预览、刷新、撤销后重做、再次正式渲染只重放已保存实例，绝不重新随机。**

### 11.4 多目标事务、恢复与审核清除

copy 在单个 SQLite 事务中先读取并预检全部目标，再统一规划、逐目标写入；任何目标冲突、时长不足、目录不可用、校验或写失败都使**所有目标零写入**。目录 catalog 在事务外读取，事务内只做同步规划与数据库操作。

每个目标写后：

- 当前 output version 不变，editRevision 加 1；
- 删除目标 arrangement.review，已审核目标必须重审；
- 返回 before/after 两个仅含 stickers/stickerDefaults 的快照、前后 revision 和 reviewCleared，供统一工作区记录一条跨片历史。

`type='restore'` 用同一事务与 CAS 恢复整组 before（撤销）或 after（重做）：只接受 stickers/stickerDefaults 两字段，目标仍须同输入版本且包装 enabled；任一片已有更新修订则整组拒绝。恢复本身也是新的实质编辑，会再次递增 revision 并清当前审核；重做直接使用上次持久化的 after，不调用随机源。

### 11.5 渲染与测试合同

`parsePackagingConfig` 负责旧配置兼容清洗，但保存/复制边界必须严格 validate，不能靠静默丢弃非法实例完成导出。完整渲染合同包含 packaging，因此贴纸变化必然使旧整片渲染与正式 artifact 过期；共享包装渲染读取任务冻结的贴纸快照，片头没有贴纸。

重点测试：

- `scripts/batch-sticker-copy.test.ts`：双目标、只换两字段、手动时长映射、来源不变、审核清除、任一冲突/无效目标全回滚、整体撤销/重做不重新随机；
- `scripts/packaging-sticker-variants.test.ts`：三阶段、手动/已编辑映射、随机变体、ID/自动组、素材去重与短时长门禁；
- `scripts/batch-packaging-stickers.test.ts`：四模板批量预览、默认值、原图、编辑桥与旧配置兼容；
- `scripts/batch-sticker-render.test.ts`：真实 FFmpeg/HyperFrames 四模板、手动与自动贴纸、片头安全区域、重渲染不重新随机；
- `scripts/batch-stickers-editor.playwright.test.mjs`：真实 Next + 临时数据根 + 内置 Chrome 的批量编辑、跨片复制、整体历史与数据库断言。

## 13. 修改时必须保持的红线

1. 批量迁移只追加；每次迁移必须经过共享备份、跨进程锁、可修复审计和结构/完整性 gate，所有批量 API 不得绕过 readiness。
2. 谱系只能按显式 ID：project → batch → batchVersion → plan → outputVersion → artifact；不得从文件名、路径或时间戳推断混剪/贴纸/任务归属。
3. 冻结输入与当前候选是不同层：整体输入变化新建 batchVersion；普通审片编辑只改当前 outputVersion arrangement；正式 artifact 指针独立。
4. 任何实质 arrangement 编辑都必须递增 editRevision 并清 review；纯视频/音频 split 才保留 revision/review。渲染与发布都要做合同和控制态 CAS。
5. 代理只服务预览，正式导出必须重新核验原片和冻结 LUT；静音候选不得正式发布。
6. 不复制一套批量专用媒体/TTS/包装实现；共享能力只从 `media-core/` 取，不从 `final-edit/` 反向导入。
7. 不新增贴纸表，不把贴纸混入 pointCues。跨片只改 `packaging.stickers/stickerDefaults`，多目标必须整体成功或整体回滚，随机结果持久化后不得重新随机。
8. 批量正式导出与项目 ZIP、schema 备份是不同事物；不得声称当前存在批量 ZIP 或快照包下载能力。
