# 打包与桌面运行

本文记录 Creative Studio 的 standalone 产物、Electron 桌面壳、Windows/macOS 安装包、Windows 免安装包，以及启停和运行资源的常驻契约。修改 `next.config.ts`、`scripts/sync-standalone-assets.mjs`、`desktop/`、`installer/`、相关构建或快启脚本前先读本文；公司网关的业务配置另见 `docs/reference/公司网关与COS中转.md`，classic 固定渲染另见 `docs/reference/固定渲染命令.md`。

## 1. 运行与分发形态

| 形态 | 服务与入口 | 主要产物/运行时 | 数据根与公司网关 |
| --- | --- | --- | --- |
| 源码网页版 | `npm run dev`；macOS `start.command`，Windows 源码网页脚本 `scripts/start-windows.ps1` | Next dev server，绑定 `127.0.0.1`，默认 3000 | 默认仓库根；有 `.venv-litellm` 与 `config.yaml` 时可起 LiteLLM |
| 源码桌面版 | macOS `start-desktop.command`；Windows `start-windows.cmd` → `scripts/start-desktop-windows.ps1`；开发命令 `npm run dev:desktop` | Electron + 已有 production standalone + 私有 Node，监听 `127.0.0.1` 随机端口 | 默认仓库根，与源码网页版共用 `data/`、`storage/`；不要同时运行 |
| standalone 服务 | `npm run build` 后由桌面壳启动 `.next/standalone/runtime/server-entry.js` | Next production server、被追踪依赖和强制同步的运行资源 | 由启动者注入 `CREATIVE_STUDIO_DATA_ROOT`；standalone 自身不负责注入 `.env.local` |
| Windows 安装包 | `npm run build:win-installer` → Inno Setup → `dist/windows/CreativeStudioSetup.exe` | `CreativeStudio.exe`、`resources/app/` 下的 standalone、`dist-desktop/`、私有 Node | 默认 `%APPDATA%/CreativeStudio`；不带 LiteLLM、便携 Python、`config.yaml` 或 `.env*` |
| macOS 安装包 | `npm run build:mac-installer` → 签名 `.app` 与 DMG | Apple Silicon Electron、`Contents/Resources/app/`、私有 arm64 Node | 默认 `~/Library/Application Support/CreativeStudio`；不带公司网关运行组件 |
| Windows 免安装包 | 包根 `start-windows.cmd` 显式传 `-Portable` | 完整目录：`node-runtime/`、`python-runtime/`、`node_modules/`、standalone、`dist-desktop/`、`scripts/` | 默认包根；明确携带 `config.yaml` 与 `.env.local`，公司网关只使用包内便携 Python |

`npm run build` 只负责 Next production build 和 standalone 资源同步；`npm run build:desktop` 只把 `desktop/*.ts` 编译到 `dist-desktop/`。`npm run dev:desktop` 不会替缺失的 standalone 产物先执行 `npm run build`，因此 standalone 必须先备好。

源码桌面入口支持 `--rebuild`（macOS）或 `-Rebuild`（Windows）强制重建。两个入口还会在 `scripts/runtime/build-stamp.mjs` 存在时检查构建戳；该辅助文件不存在时，不能把“必然按源码 mtime 自动重建”当作保证。免安装模式拒绝 `-Rebuild`，也不执行 npm 安装、Electron 下载、Next 构建、桌面壳编译、venv 重建或 pip 修复。

## 2. standalone 构建边界

### 2.1 Next 配置

`next.config.ts` 使用 `output: 'standalone'`，并处理三类边界：

1. `outputFileTracingExcludes` 从 `scripts/packaging/forbidden-paths.json` 生成排除规则，防止本机数据、密钥和开发目录进入 standalone。
2. Next 16 Turbopack 不会把 route tracing excludes 完整应用到 instrumentation，因此 `runAfterProductionCompile` 会在 standalone 复制之前，直接过滤 `instrumentation.js.nft.json`。构建后再删文件不能替代这一步：被追踪的本地文件若已消失，构建阶段就可能失败。
3. `outputFileTracingIncludes['/**']` 强制补入 Next server production runtime、React 运行文件，以及 `packaging/stickers/**/*`。最后一项是贴纸正式负载，不是仅供开发预览的资源。

`ffmpeg-static`、`ffprobe-static`、`@ffprobe-installer/ffprobe` 位于 `serverExternalPackages`，不要把它们 bundling 成失去二进制路径语义的 server chunk。

### 2.2 `sync-standalone-assets.mjs` 的强制同步

`npm run build` 在 `next build` 后执行同步脚本。它必须完成以下工作：

- 把 `.next/static` 复制到 `.next/standalone/.next/static`，把 `public` 复制到 standalone。
- 删除旧 `standalone/runtime` 后，只从根目录 `runtime/server-entry.js` 重新复制服务包装入口。该文件故意不放在 `desktop/`，避免桌面壳的依赖边界传递包含业务和原生依赖图。
- 整目录复制 `node_modules/ffmpeg-static`、`node_modules/ffprobe-static` 和 `node_modules/@img`。其中 `@img` 不能只复制 `.node`：Windows sharp 还依赖同目录 libvips DLL，漏拷会导致 `ERR_DLOPEN_FAILED`。
- 再次按 forbidden JSON 的 `core` 清理 standalone，并清除 standalone 根下 `.env` 与 `.env.*`；最后做存在性硬断言。

递归复制是脚本自己的逐文件实现，不要不加验证地换成 `fs.cpSync`：代码记录了 Windows 中文、空格、长路径下的原生崩溃约束。

`better-sqlite3` 没有在这个脚本里另写整目录复制规则，不能据此推断它不重要；其原生加载仍必须在最终私有 Node 下实测。贴纸由 Next tracing include 进入 standalone，同步脚本没有再实现一份贴纸复制器。安装包和免安装包后续复制整个 standalone，因此保留这份正式贴纸负载。

### 2.3 Electron 壳与服务包装入口

`desktop/` 是纯壳边界：主进程、窗口、preload、IPC 和服务管理只应依赖 Electron、Node 内置模块及 `desktop/` 内模块，不直接导入 `better-sqlite3`、sharp、ffmpeg 或业务数据库。

`runtime/server-entry.js` 包装 Next standalone 启动：

- 强制 hostname 为 `127.0.0.1`、port 为 `0`，由操作系统分配空闲端口。
- 从 stdout 只报告一次 `__CREATIVE_STUDIO_READY__ {"port":...,"instanceId":...}`。
- `desktop/service-ready.ts` 校验端口、instanceId 和 `/api/desktop/health`，拒绝 origin 跳转与身份不符的响应。

因此桌面版不是“Electron 内嵌 Next dev”，也不是把 3000 端口换一个窗口展示。

## 3. Node ABI 与原生资源

### 3.1 构建机与私有 Node

Windows/macOS 安装包构建都固定下载 Node `22.22.3`：Windows 为 `win-x64`，macOS 为 `darwin-arm64`。构建机也必须是 Node 22.x；Windows 还要求 `win32/x64`，macOS 还要求 `darwin/arm64`。不要用 Rosetta 或不同主版本构建后直接发布。

原因是 `better-sqlite3` 等预编译原生模块按 Node ABI 和平台架构生成。`sharp` 还同时受平台二进制和 libvips 资源影响。构建通过不等于目标机器能加载，发布验收必须在包内私有 Node 下真实执行：

```js
const Database = require('better-sqlite3');
const db = new Database(':memory:');
db.close();
```

并对 sharp 做一次真实图片处理。Windows 免安装启动也会先尝试用选定的 Node 加载 `better-sqlite3`，失败时明确阻止继续，而不是等服务启动后才暴露 ABI 错误。

普通源码 Web 开发入口接受 Node 20+；固定渲染运行时另有 Node 22+ 要求，两者不要混为一个版本承诺。

### 3.2 各资源的发布契约

| 资源 | 必须保留的事实 |
| --- | --- |
| `better-sqlite3` | 平台、架构、Node ABI 必须与私有 Node 一致；安装版 payload 测试要实际打开内存数据库 |
| sharp / `@img` | 整个 `@img` 进入 standalone，尤其是 `.node` 同目录的 libvips DLL；不能只靠 Next 对 `.node` 的追踪 |
| ffmpeg | `ffmpeg-static` 整包同步；Windows 安装器断言 `ffmpeg.exe`，macOS 安装器检查 arm64 和实际 `-version` |
| ffprobe | `ffprobe-static` 整包同步；运行解析还受 `CREATIVE_STUDIO_FFPROBE`、可执行性探测与平台适配影响 |
| Electron | npm 依赖元数据存在不等于二进制已安装；缺失时源码/构建脚本运行 `electron/install.js`，随后硬断言真实二进制 |
| 桌面编译产物 | 分发的是 `dist-desktop/*.js`，清理 `.map`、`.ts`、`.tsx`；不携带 `desktop/` 源码 |

`lib/ffmpeg.ts` 的工具解析顺序是显式 `CREATIVE_STUDIO_FFMPEG` / `CREATIVE_STUDIO_FFPROBE`、包内二进制、PATH，并有可执行性检查。Windows ffprobe 还优先尝试 `@ffprobe-installer/ffprobe`，避免旧静态二进制卡住。`probeDurationSec` 在 ffprobe 失败时有 ffmpeg 解析回退；不要把这个单一 API 的回退扩大解释为所有直接 ffprobe 调用都自动回退。

macOS 构建对 `ffprobe-static` 的 arm64 文件做实际架构和运行检查；发现名为 arm64、实为 x86_64 或不可执行的负载时会移除它。macOS 安装器仍强制验收 arm64 ffmpeg，不允许用错误架构二进制凑齐目录。

## 4. 包装运行时与贴纸正式负载

### 4.1 包装目录解析

`lib/media-core/packaging-runtime.ts` 中的目录和 Node 解析优先接受显式环境变量：

- `CREATIVE_STUDIO_PACKAGING_DIR`：包含 `package-video.mjs`、templates、runtime 和包装依赖的目录。
- `CREATIVE_STUDIO_PACKAGING_NODE`：执行包装管线的 Node。

未显式指定时，包装目录依次探测 `dataRoot()/packaging`、当前工作目录下 `packaging`，以及 standalone cwd 的上两级回退；包装 Node 依次探测数据根/仓库的 `node-runtime`，最后回退 `process.execPath`。Windows 免安装版使用包根 `node-runtime/node.exe`，安装版服务最终可使用自身的私有 Node。解析结果必须包含真实 `package-video.mjs`，不能只创建一个空 `packaging/` 就视为可用。

`npm run setup:packaging` 执行 `scripts/setup-packaging-runtime.mjs`，用于开发仓库装配包装运行时。`--from <目录>` 可指定参考运行时，`--force` 允许覆盖已有文件；脚本排除 renders、mockups、扫描缓存和 demo 输出，校验 HyperFrames、Chrome、`film-runtime.json` 与 classic 冻结资产。它不是 `npm run build` 的隐式步骤，发布前应单独确认运行时完整。

### 4.2 贴纸目录不是开发附属品

正式贴纸位于 `packaging/stickers/`：原始 RGBA PNG、`catalog.json`、WebP 缩略图及共享 `runtime.js`。`scripts/build-sticker-assets.mjs --source <目录>` 负责从源素材装配并记录尺寸、alpha 包围框、字节数和 SHA-256；当前目录契约是 115 张原图，四风格分别为 show 29、comic 28、journal 29、editorial 29。

发布链必须同时保住两件事：

1. 浏览器经 `/api/packaging/stickers/...` 和模板资源路由读取清单、缩略图、原图与共享运行时。
2. 正式导出按任务快照实际使用的贴纸解析相对路径和 SHA-256，缺原图、路径越界或哈希异常必须失败，不能静默少贴一张。

`next.config.ts` 的 `./packaging/stickers/**/*` tracing include 是 standalone/安装负载的强制入口。修改贴纸目录结构、构建 exclude 或复制逻辑后，应直接检查最终 `.next/standalone/packaging/stickers`，而不是只验证开发服务器能显示缩略图。

贴纸业务规则见 `docs/reference/视频包装.md`。尤其不要把“贴纸是正式负载”误解为“classic/1 接受贴纸”：classic 是另一条冻结渲染域。

## 5. LiteLLM、便携 Python 与敏感文件

| 运行形态 | Python/LiteLLM 来源 | `config.yaml` / `.env.local` | 失败策略 |
| --- | --- | --- | --- |
| macOS / Windows 源码运行 | 项目 `.venv-litellm`；Windows 源码入口可探测失效 venv 并用本机 Python 3.12 重建 | 开发根目录文件，绝不进入 standalone/安装包 | sidecar 缺失或启动失败只禁用公司供应商，不阻塞工作台 |
| Windows 免安装包 | 只用包内 `python-runtime/python.exe`，经 `scripts/start-litellm-proxy.py` 导入 `run_server` | 作为内网分发的显式敏感例外随包复制 | manifest/runtime 损坏则不启动 sidecar；不联网修复、不回退 venv 或系统 Python，其余工作台功能可继续 |
| Windows/macOS 安装包 | 不携带 `.venv-litellm` 或 `python-runtime` | 构建时清除并断言不存在 | 安装版没有公司 sidecar，不应伪造“公司网关已就绪” |

LiteLLM 默认端口 4000，健康检查为 `/health/liveliness`。所有启动参数必须显式 `--host 127.0.0.1`；不得改成 `0.0.0.0`，也不得以隧道或公网端口替代本机代理。启动时设置本地 model cost map，避免无谓远程价格表请求；代理环境变量只在需要的子进程范围内处理。

Windows 便携运行时的权威输入是：

- `scripts/python-runtime-win-x64.lock.json`：Python `3.12.10`、python-build-standalone release `20250529`、目标 `x86_64-pc-windows-msvc`、LiteLLM `1.89.2`、归档 SHA-256、依赖锁及其 SHA-256。
- `requirements-litellm-win-x64.lock.txt`：每个依赖都是 `name==精确版本`，其文件哈希必须与 lock JSON 一致。

`build-python-runtime-windows.ps1` 先校验锁文件，再校验下载归档，使用纯 wheel 下载和离线安装，实测 loopback LiteLLM 启动，检查 VC++ 私副本与许可证，最后通过同目录改名备份/staging 发布并支持失败回滚。`verify-python-runtime-windows.ps1` 是只读验收，不联网、不执行 pip 变更，也不读取 `config.yaml`、`.env.local` 或密钥字段。

便携 Python 不使用 pip 生成的 `litellm.exe` 入口，因为该入口可能嵌入构建机绝对路径；统一由包内解释器运行固定的 `start-litellm-proxy.py`。

## 6. 数据根与 `.env.local` 注入

`lib/data-root.ts` 在进程启动时解析一次数据根：`CREATIVE_STUDIO_DATA_ROOT` 优先，否则 `process.cwd()`。所有数据库、上传素材、日志、运行状态和包装工作目录都必须从 `dataRoot()` 派生，不要在业务代码里另写死 `data/`、`storage/`。

Electron 主进程的选择规则：

- 安装版：环境变量优先，否则 `app.getPath('appData')/CreativeStudio`。
- 非 packaged 的源码桌面和 Windows 免安装目录：环境变量优先，否则应用项目/包根。
- standalone 子进程 cwd 是 server root，但必须另传 `CREATIVE_STUDIO_DATA_ROOT`，不能拿 `.next/standalone` 当用户数据目录。

standalone server 不自行加载 `.env` 文件。`desktop/service-spawn.ts` 会读取 `<dataRoot>/.env.local` 并注入子进程；只接受常规 `KEY=value` 行，可去掉成对单双引号。合并顺序是“文件值 → 当前进程环境 → 调用方显式 environment”，所以显式进程环境优先于文件。密钥不会写入 `electron-service.json`、`stack.json` 或 portable manifest。

安装包会删除 `.env*`，但运行时需要时可由受控的数据根提供 `.env.local`。Windows 免安装包是有意的例外：包根同时是数据根，包内 `.env.local` 可直接被外壳读取。日志、manifest 和构建输出只能记录路径、大小、哈希等元数据，不能打印文件内容或完整鉴权串。

## 7. 启动、状态文件与优雅关闭

### 7.1 桌面服务状态

`storage/run/electron-service.json` 由桌面服务在 ready 与 health 核身后原子写入，当前持久化字段为：

```json
{ "version": 1, "origin": "http://127.0.0.1:<port>", "instanceId": "<本次启动ID>" }
```

临时文件与正式文件位于同目录，写入模式为 `0600`；Windows rename 不能覆盖旧文件时，只对这个确定的状态路径先删旧目标再改名。正常停止只清除 instanceId 相同的记录，避免误删新实例状态。共享停止工具兼容读取可选 `pid`，但当前 `desktop/service-state.ts` 写入的必需字段不包含 pid，不能把 pid 当成必有值。

`storage/run/stack.json` 是 LiteLLM sidecar 状态，不是任意命令执行配置。Windows 当前记录 `litellmPid`、`appPort`、`proxyPort`、`litellmRuntime`、`litellmInterpreter`、`stopScript`、`startedAt`；共享工具还容忍 `appPid`、`appCmdPid`、`litellmPort` 等可选旧字段。它不存 API Key/master key，必须是无 BOM UTF-8 JSON。停止时优先按状态 PID 与归属校验处理，不能仅凭 4000 端口杀未知进程。

`storage/run/reassembled-navigation.json` 是桌面导航的一次性收件箱，只接受匹配的 instanceId、30 秒内的记录和受控 ID，不接受任意 URL 或路径。

### 7.2 关闭链

应用唯一进程级编排是 `lib/shutdown.ts` 的 `gracefulShutdown`：重复调用共享同一个 Promise，按总时间预算执行，而不是每一步重新获得完整超时。

顺序要点：

1. 停止各调度器领取新任务，拒绝新的脚本生成。
2. 向批量、成片、脚本工作室等任务和直接 FFmpeg 子进程广播中止，并等待收尾。
3. 等待仍需写数据库的任务后关闭 SQLite。
4. 只执行数据根或项目 `scripts/` 下已知的 sidecar 停止脚本。

`POST /api/shutdown` 使用 12 秒总预算，先 await 编排结果，再延迟 100 ms `process.exit(0)`。客户端遇到连接中断不一定代表请求未接受，不能立刻把它当成强杀依据。

Electron 外壳停止私有服务时，先请求同一 `/api/shutdown`，给 20 秒优雅退出窗口；仍需升级时，Windows 用 `taskkill /T /F`，POSIX 对 detached 服务进程组依次尝试 SIGTERM、SIGKILL。窗口 X 和应用菜单退出进入同一个页面内退出确认，不应绕开服务清理直接销毁窗口；SIGINT/SIGTERM/SIGHUP 属于异常/终端信号路径，跳过确认但仍走同一 `shutdown()`。

`stop-desktop.command` 和 `scripts/runtime/desktop-service.mjs` 先严格验证 loopback origin，再用 health 的 instanceId 核身，之后才能请求关闭。instance 不匹配、origin 非法、状态损坏或归属不明都必须 fail closed。Windows 安装版的 `stop-installed.ps1` 还按当前安装目录的 `CreativeStudio.exe` 精确匹配外壳，优雅链失败后才使用进程树强杀。

`stop.command` / `stop-windows.cmd` 还负责网页或源码入口；端口上的非本项目进程只报告，不得误杀。`start.sh`、`stop.sh` 只是对应 `.command` 的终端转发，不维护第二套实现。

### 7.3 免安装 manifest 与 Windows 更新占用

`portable-manifest.json` 的条目只含相对路径、`size`、`sha256`，不包含密钥值。装配脚本当前写入 `schemaVersion: 1`、`mode: windows-portable-v1` 和 `files`，在全新同盘 staging 中组装后改名发布，目标已存在则拒绝覆盖。

启动预检是另一层消费者：除 schema/mode/files 外，它还要求 `appVersion`、`builtAt`、`sourceCommit`，并要求 manifest 的 appVersion 与包内 `package.json` 一致，再逐项核验关键文件。修改装配或预检时必须同时核对两侧字段集合；“生成了 manifest”不等于“启动预检会通过”。关键文件哈希也不是整包每个文件的哈希，不能替代完整的发布验收。

Windows 正在运行的 Electron、Node、Python 可能锁占二进制和原生 DLL。更新免安装目录前必须完全退出旧实例，不得用共享盘新包覆盖本机 `data/`、`storage/`；文件占用失败不能被误报为成功的增量同步。这里的进程文件锁与前述 Python 依赖 lock JSON 是两件事。

## 8. 安装包构建细节

### 8.1 Windows / Inno Setup

`build-win-installer.ps1` 要求 Windows x64 + Node 22，默认执行 `npm ci`，可按维护者判断传 `-SkipNpmCi`。它分别构建 standalone 与桌面壳，复制 Electron runtime，把 `electron.exe` 改名为 `CreativeStudio.exe`，并组装 `resources/app/`。

构建会检查私有 Node 主版本、ffmpeg/ffprobe 实际路径、桌面源码泄漏和禁入目录，再把 `stop-installed.ps1`、`clear-user-data.ps1` 复制到应用级 `scripts/`。`CreativeStudio.iss` 使用当前用户目录安装，无需管理员权限，卸载前先运行停止脚本。

`installer/windows/launcher.cs`、`start-installed.ps1` 是保留的历史/辅助资源；当前 Electron 安装链不编译或依赖 `launcher.cs`，也不靠旧浏览器 launcher 启动。`installer/macos/launcher.c`、`launcher.sh` 同样不进入正式 `.app` 负载，正式入口是 Electron 主进程。

### 8.2 macOS / DMG

`build-mac-installer.sh` 必须在 Apple Silicon macOS 上运行，并要求 Xcode Command Line Tools。它检查 Electron、私有 Node、ffmpeg 的 arm64 架构，组装 `Info.plist`、图标、`.app` 和 DMG。

正式发布需要 `CREATIVE_STUDIO_MAC_SIGNING_IDENTITY` 与 `CREATIVE_STUDIO_MAC_NOTARY_PROFILE`，完成 Developer ID 签名、notarytool 和 staple。`--allow-adhoc` 只允许本地测试，不能当成已公证发布。`macos-installer-payload.test.mjs` 是需要真实构建产物和本机工具链的验收，不是 Windows 开发机上的普通静态测试。

## 9. 编码与禁入清单

### 9.1 文件编码

- `scripts/*.ps1` 和随包 PowerShell 停止/维护脚本必须保持 UTF-8 with BOM，现有守护测试同时要求关键脚本为 CRLF。PowerShell 5.1 会按 ANSI 解读无 BOM 中文脚本。
- `scripts/runtime/stack-state.mjs` 写 `stack.json` 使用无 BOM UTF-8；读取方可以剥离 BOM，但写入方不要依赖这种容忍。
- `scripts/packaging/forbidden-paths.json` 必须保持 ASCII-only。Windows PowerShell 5.1 对无 BOM 非 ASCII JSON 的读取可能破坏 `ConvertFrom-Json`。
- Windows `.cmd` 快启/便携模板保持 CRLF；不要用编辑器随意重存改编码和行尾。

### 9.2 禁入边界

`forbidden-paths.json` 的 `core` 包括 `.git`、`.venv-litellm`、`config.yaml`、`data`、`desktop`、`dist*`、`docs`、`installer`、`outputs`、`python-runtime`、`scripts`、`storage` 等；`fileEntries` 标记 `config.yaml`、`litellm-config.yaml`、`.env`、`.env.*` 是文件/模式而不是目录前缀。`nextStandaloneExcludes.extra` 补充环境文件排除。

当前代码有两层需要一起核对：

1. `next.config.ts` 与 `sync-standalone-assets.mjs` 直接读取共享 JSON。
2. Windows/macOS 安装脚本和 Windows 免安装脚本还有各自的硬编码 prune、allowlist 与硬断言；它们不是通过运行时 import 共享 JSON 来生成全部规则。

因此修改禁入边界时，不能只验证 Next tracing；还要检查安装脚本、免安装白名单和守护测试。两层的目的相同：任何本机数据库、产物、密钥、开发源码、缓存和 sidecar 构建环境都不得意外进入正式负载。唯一明确的敏感分发例外是 Windows 免安装包的 `config.yaml` 与 `.env.local`，且只能复制、不能读取打印或纳入 Git。

## 10. 关键测试与验收入口

按改动范围选择，不存在统一的 `npm test`：

```bash
node scripts/standalone-desktop-boundary.test.mjs

```

macOS 另运行静态 `node scripts/macos-installer.test.mjs`；真实 `.app`/DMG 验收在 Apple Silicon 构建机运行：

```bash
node scripts/macos-installer-payload.test.mjs [app路径] [dmg路径]
```

这些文件中既有静态源码契约，也有临时目录行为测试和真实原生负载验收，覆盖重点不同。修改当前实现后应确认所跑测试仍对应当前文件布局；不能把“测试文件存在”写成“本机已全部通过”，也不能用静态字符串断言替代私有 Node 下 better-sqlite3/sharp、ffmpeg/ffprobe 和实际启停验收。

## 11. 修改红线速查

- 不让桌面壳导入业务/原生依赖，不把 `runtime/server-entry.js` 移回 `desktop/`。
- 不把本机服务绑定到公网；桌面服务只用 loopback 随机端口，LiteLLM 只用 loopback 4000。
- 不在 standalone 或安装包中保留 `data/`、`storage/`、`outputs/`、`.env*`、`config.yaml`、`.venv-litellm`、`python-runtime/` 或开发源码；Windows 免安装敏感例外不得外溢。
- 不只拷 sharp 的 `.node`，不跨 Node ABI/CPU 架构复用原生负载。
- 不用端口或进程名直接强杀未知进程；必须先做实例身份与项目归属校验。
- 不让 `stack.json` 成为任意脚本执行入口，不在状态文件或 manifest 中记录密钥。
- 不让免安装模式静默降级为源码修复；缺文件应报告重新完整复制。
- 不让贴纸资源只停留在开发目录，也不用“支持贴纸”为由修改 classic 冻结域。
