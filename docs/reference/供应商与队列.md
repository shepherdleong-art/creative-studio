# 供应商与队列

本文记录项目主工作台中图片、脚本、视频供应商的适配器边界，以及 `jobs` / `video_jobs` 两条内存队列的常驻契约。修改 `lib/providers/`、`lib/script-providers/`、`lib/video-providers/`、`lib/queue.ts` 或 `lib/video-queue.ts` 前必读。公司模型经本机 LiteLLM、COS 和尺寸映射的细节另见 `docs/reference/公司网关与COS中转.md`；创作画布、批量生产各有自己的调度器，不把本文的队列状态机套过去。

## 1. 架构边界与注册方式

三类供应商共用“持久化配置 → 运行时解析 → 适配器调用 → 任务状态与产物落库”的方向，但注册方式不完全相同：

- **图片**：`lib/queue.ts` 按 `providers.type` 显式分派。`geekai-json`、`gateway-task-image`、`packy-images`、`packy-gemini-image`、`ark-images` 各有分支；其余类型落入 `openai-compatible` 同步分支。新增类型不能只新增文件，必须同时在队列分派中注册，并补齐产物、错误和恢复语义。
- **脚本**：`lib/script-providers/index.ts` 是统一注册入口。持久化的 `apiStyle` 决定传输协议，`type` 保留供应商/计价身份，不能用 `apiStyle` 反推全部身份。配置解析和列表读取分别在 `config.ts`、`store.ts`。
- **视频**：`lib/video-providers/index.ts` 的 `adapters` 表注册 `kling`、`jimeng`、`openai-video`。`getVideoAdapter()` 查表；`registerTestVideoAdapter()` 只供脚本测试覆盖，不是生产扩展入口。适配器合同在 `types.ts`，基本方法是 `submit` / `poll`，可选能力包括 `submitText`、`submitReference`、`submitFinal`、`minimumPollingTimeoutMs` 和 `tailFrameCapability`。

主队列只负责主工作台的 `jobs` 与 `video_jobs`。供应商标识、模型、提示词和输入资产在任务创建时固化到任务行；运行中读取任务行和供应商连接配置，不能靠当前 UI 选择推断旧任务身份。

## 2. 持久化配置、种子与密钥显示

### 2.1 配置真源

| 类别 | 数据表 | 运行时配置要点 |
| --- | --- | --- |
| 图片 | `providers` | `baseUrl`、`apiKey`、`model`、`type`、`enabled`、`defaultCostPerImage` |
| 脚本 | `script_providers` | 另含 `apiStyle`、`maxTokens`、`supportsVision`、`visionCostPerRequest`、`executionScope`、`isBuiltin` |
| 视频 | `video_providers` | 另含 `defaultModel`、`defaultDurationSec`，可灵直连使用 `accessKey` / `secretKey` |

当前运行时以 SQLite 中的连接与密钥为准。表里的 `apiKeyEnv`、`baseUrlEnv`、`modelEnv` 等字段仍用于元数据/兼容，但 `resolveScriptProviderRuntimeConfig()` 和 `resolveVideoProviderRuntimeConfig()` **不会用环境变量补齐空的数据库密钥或地址**。不要根据旧字段名恢复“env 优先”或“env 回退”。COS 密钥和 LiteLLM 进程配置是另一套环境/文件边界，见公司网关参考。

图片任务供应商选择还由 `lib/image-provider-selection.ts` 复核：供应商必须存在、启用且有非占位的数据库 API Key；仅配置环境变量不算可用。可灵直连优先使用分列的 Access Key/Secret Key，也兼容数据库旧 `apiKey` 中的 `access:secret` 组合；只填一半会判定未配置。

### 2.2 种子行为

`lib/seed.ts` 负责内置与公司供应商补种：

- 空图片供应商表首次播种 GeekAI、Packy、GPT.ge 等预设；后续 `ensure*Providers` 只做缺省补种和必要的旧类型修正。
- 方舟直连补种 `ark-seedream-5-0-pro`，模型固定为 `doubao-seedream-5-0-pro-260628`，默认禁用且不虚构价格。
- 公司图片、视频按 canonical ID 补缺，统一指向本机 LiteLLM；已有 canonical 行的用户连接、模型和启用状态不被重播覆盖。公司图片的固定价格会按计价表同步。
- 新库内置 `gpt` 脚本供应商指向 `GPT-5-6-Luna-Standard`、`company` scope 和本机 LiteLLM，并开启视觉；Gemini、Qwen、Kimi 保持 `external`。已有脚本行的 `apiStyle`、模型、连接、密钥、scope、视觉能力和 `maxTokens` 不被补种覆盖；空的标准 `gpt.type` 只补为 `openai-compatible`。
- 公司种子中的非空本地 Bearer 是 LiteLLM 调用占位，不是公司上游真实密钥；上游密钥属于 `config.yaml`，不能复制到日志或前端。

### 2.3 API 不回显秘密

- `GET/POST /api/providers`、`GET/PUT /api/providers/[id]` 返回 `configured`、`missing`、`hasApiKey`，把 `apiKey` 置为 `undefined`；更新时只有请求显式带 `apiKey` 才修改或清空。
- `GET/POST /api/providers/script` 与 `PUT /api/providers/script/[id]` 通过 `listScriptProviderMeta()` 输出安全元数据，不输出数据库密钥。内置脚本供应商只能禁用，不能删除。
- `GET/POST /api/providers/video` 与 `PUT /api/providers/video/[id]` 手工挑选安全字段，不返回 `apiKey`、`accessKey`、`secretKey` 或 `*Env` 字段；可灵以密钥对是否齐全设置 `hasApiKey`。
- 图片供应商被项目引用、视频供应商被视频任务引用时禁止删除。新增或改为 `openai-video` 还要经过 `video_provider_schema` readiness gate，不能用普通启动路径重建旧表。

前端只能显示“是否已配置”，不能增加密钥明文回显、调试导出或含密钥的日志接口。

## 3. 图片适配器协议与模型约束

| `providers.type` | 提交与结果协议 | 关键差异 |
| --- | --- | --- |
| `openai-compatible` | 同步 `POST /v1/images/edits`，multipart；读取 `data[0].b64_json` 或下载 `url` | 通常重复字段 `image[]` 并请求 `b64_json`；`api.gpt.ge`、`api.v3.cm` 改用单数 `image`，且不强制 `response_format` |
| `ark-images` | 同步 JSON `POST <base>/api/v3/images/generations`；URL 或 Base64 结果 | 仅支持方舟直连 `doubao-seedream-5-0-pro-260628`；`image` 为按顺序排列的 data URL 数组，PNG 输出、无水印 |
| `geekai-json` | JSON `POST /v1/images/edits`，`async: true`；轮询 `GET /v1/images/<taskId>` | 兼容同步 URL/Base64 和异步 `task_id`；图片以 data URL 放在 `images` |
| `gateway-task-image` | 通常以 `POST /v1/videos` 提交图片任务，`GET /v1/videos/<id>` 轮询，再下载结果 | 虽为图片也使用视频任务端点；完成态无 URL 时回退 `/content`。公司 Seedream Pro 是单独的同步 `/v1/images/generations` 分支 |
| `packy-images` | 同步 multipart `POST /v1/images/edits` | 重复单数字段 `image`，`output_format=png`；只有模型能力表允许时才发送 `quality` |
| `packy-gemini-image` | 非流式 `POST /v1/chat/completions` | 文本与 data URL 图片组成 multimodal `messages`；从文本/内容部件中提取 data URL 或图片 URL，再解码或下载 |

### 3.1 方舟 Seedream 5.0 Pro 直连

`lib/providers/ark-images.ts` 在发送 POST 前构造并校验完整请求：

- 模型必须是精确的 `doubao-seedream-5-0-pro-260628`。
- `images` 包含底图与参考图，总数最多 10；单张不超过 30 MB，只接受 PNG/JPEG/WebP。
- 图片宽高均须大于 14 像素，总像素不超过 36,000,000，宽高比须在 1:16 到 16:1。
- 尺寸由 `lib/seedream-image.ts` 校验：可传 `auto`、`1K`、`1.5K`、`2K` 或合法像素；自定义像素总量须在 921,600–4,624,220，比例同样在 1:16–16:1。`auto` 映射 `2K`，特定 21:9 1K 预设映射到官方同档尺寸。
- 请求超时为 10 分钟并联接调用方 AbortSignal；结果 URL 下载不附方舟 API Key。

### 3.2 质量、同步超时与不可重试错误

`lib/image-model-capabilities.ts` 是图片模型 `quality` 与推荐超时的能力表。GPT-Image-2 支持 `quality`；列出的 Nano Banana/Gemini 图片模型与公司 Nano Banana、Seedream Pro 不发送该字段。自定义模型保留历史默认 `supportsQuality=true`，不要据此推断所有上游都支持。

Packy 两类图片适配器都是长连接同步请求。队列对 Packy 的超时/网络类错误不自动重试，因为远端可能已经生成并扣费；Packy 4xx 和明确的模型/端点不匹配也不自动重试。其他类型按通用 `maxAttempts` 处理。`lib/packy-errors.ts` 是这条策略的单一判断入口。

## 4. 多图顺序是不可破坏的跨层合同

所有图片编辑适配器统一：

```text
图1 = 待编辑底图；图2…N = 用户参考图，保持 referenceImageIds 的原始顺序
```

`lib/queue.ts` 不用 SQL `IN (...)` 的返回顺序直接发图，而是按持久化 ID 数组重新排序，再选择 `processedPath || path`。OpenAI/Packy 使用 multipart 时按此顺序 append；GeekAI、Packy Gemini、方舟和公司网关也按相同顺序组 JSON/content。

有参考图时，OpenAI-compatible、Packy、GeekAI 和公司网关会添加结构化提示，明确底图是修改主体、后图只作参考。`referenceGuidanceMode='none'` 只关闭 GeekAI/公司网关的主体保持前缀，不改变图片顺序；Packy 队列分支固定不重复添加该模式前缀，而使用适配器自身的图序说明。

新增适配器必须同时保证“实际数组顺序”和“提示词中的图号”一致，不能只改其中一处。

## 5. 脚本供应商协议

`completeJson()` 先检查配置与执行 gate，再按 `apiStyle` 分发。视觉输入在直连供应商中使用 Base64 data URL；`company` scope 必须先通过本机 LiteLLM gate，并把每张图片上传 COS 换为预签名 URL，未配置或上传失败时不发模型请求。

| `apiStyle` | 端点与请求 | 响应/视觉差异 |
| --- | --- | --- |
| `openai-compatible` | `/v1/chat/completions`；`messages`、`max_tokens`，JSON 模式发送 `response_format` | 可普通 JSON 或 SSE；有图时文本在前、图片在后。默认 temperature 0.7，特殊模型见下节 |
| `openai-responses` | `/v1/responses`；始终 `stream: true`，`max_output_tokens`，`reasoning.summary='auto'` | 只从 SSE 的 output text/reasoning delta 汇总；图片用 `input_image`，不把 Chat Completions 的 `response_format` 或 temperature 字段照搬过来 |
| `anthropic-messages` | `/v1/messages`；独立 `system`、`max_tokens`，同时发送 Bearer、`x-api-key` 和 `anthropic-version: 2023-06-01` | 普通响应连接 text block；流式可启用 thinking（预算 2048）。有图时图片在文本前，URL source 或 base64 source |
| `native-gemini` | `/v1beta/models/<model>:generateContent?key=...` | system 与 user 合并为 prompt；只接受 `inlineData` Base64 图片，不能接受公司视觉的 URL-only 形式 |

四种协议共享 JSON 围栏清理与 `JSON.parse`，但不能假设它们接受同一组参数。请求控制统一支持外部取消和默认 120 秒超时；SSE 读取由 `sse.ts` 处理跨 chunk 断行、注释、`[DONE]` 和中止清理。

### 5.1 公司 `GPT-5-6-Luna-*` 的 temperature=1 三层保障

该约束只在 `openai-compatible` 适配器中实现：

1. 模型名匹配 `^GPT-5-6-Luna/i` 时，首次请求就直接固定 `temperature=1`。
2. 其他模型若返回 HTTP 400，且错误文本同时表明 `temperature` 不受支持，则用 `temperature=1` 重试一次。
3. 命中上述 400 后，以 `${baseUrl}|${model}` 为键写入**进程内**名单，后续请求直接固定为 1，避免再次先失败。

名单不持久化，进程重启后，非已知前缀的模型可能再经历一次特征 400；已知 Luna 前缀不受影响。把公司 Luna 改到 Responses/Anthropic 等另一种 `apiStyle` 不会自动继承这套重试逻辑。

连带身份约束也不能拆散：内置固定行只有在 `id='gpt'`、`type='openai-compatible'`、`apiStyle='openai-compatible'`、`executionScope='company'` 和精确模型 `GPT-5-6-Luna-Standard` 同时成立时，才由供应商 PUT 锁定 `visionCostPerRequest`，不允许改为另一套价格。核心用量计价除 canonical `gpt` 外，也接受其余字段相同且 baseUrl 为回环地址的手工公司行。`supportsVision` 用于向前端声明视觉能力；实际 `completeJson` 公司视觉请求另强制经过 media gate 和 COS 上传。

## 6. 视频适配器与模型特殊约束

### 6.1 可灵直连 `kling`

- 认证由 Access Key/Secret Key 生成 HS256 JWT：`iss=accessKey`、有效期 1800 秒、`nbf` 提前 5 秒。
- 提交 `POST /v1/videos/image2video`，轮询同路径加 `/<taskId>`；首帧是无 data URL 前缀的原始 Base64。
- 请求使用 `model_name`、字符串 `duration`、`mode='pro'`、`sound='on'`。匹配 v3/3.0 的直连模型发送字符串 `multi_shot='true'` 与 `shot_type='intelligence'`，不要与公司网关的 JSON boolean 混用。
- 直连适配器没有声明尾帧能力，因此不能仅凭“模型可能支持”放行尾帧。

### 6.2 方舟/即梦 `jimeng`

- 默认提交与轮询 `/contents/generations/tasks[/<id>]`；`createJimengAdapter()` 允许公司通道复用同一请求合同但替换传输路径，不能再复制一套模型映射。
- 图生视频 content 为文本项后接图片项；可用交付层 URL，否则读本地文件成 data URL。文生视频不伪造首帧，多模态参考按调用方顺序编码 image/video/audio role。
- `seedance-contract.ts` 的精确模型合同如下：

| 模型 | 时长上限 | 参考数量合同 | 分辨率/样片 |
| --- | --- | --- | --- |
| `doubao-seedance-2-5-260628` | 30 秒 | 30 图、10 个视频/音频类媒体 | 480p/720p/1080p；支持 draft，draft 只能 480p；支持 MOV |
| `doubao-seedance-2-0-260128` | 15 秒 | 9 图、3 个视频/音频类媒体 | 480p/720p/1080p/4k；不支持 draft |
| `doubao-seedance-2-0-fast-260128`、`...-mini-260128` | 15 秒 | 9 图、3 个视频/音频类媒体 | 480p/720p；不支持 draft |

普通生成默认无水印、开启音频；Fast/Mini 默认 720p，其余通常默认 1080p。Final-from-Draft 只接受 Seedance 2.5 的有效 draft task，并固定正式输出 1080p。方舟序列化请求体上限 64 MB，超过时要求改用 COS 交付，不能靠截断素材通过。

Seedance 2.x 且目标时长至少 15 秒时，适配器声明最低 15 分钟轮询窗口；用户配置更长时保留更长值。

### 6.3 网关 `openai-video`

通用协议为 `POST /v1/videos`、`GET /v1/videos/<id>`，请求使用 `model`、`prompt`、字符串 `seconds` 和 `images`。结果 URL 兼容 `metadata.url`、`output.url`、`video.url`、`result.*` 等结构；完成态无 URL 时使用原始 task ID 的 `/content`。尺寸、首帧/尾帧和公司模型字段见公司网关参考。

公司 `kling-3.0` 与 `qiniuyun/kling-3.0` 的智能分镜只由精确模型判定，持久化默认开启、显式 `false` 可关闭；网关字段是 JSON boolean，开启时另带 `shot_type='intelligence'`。`kling-3.0-Omni` 不命中该能力。

### 6.4 视频尾帧精确 allowlist

尾帧能力必须由适配器的 `tailFrameCapability(model)` 按**精确模型名**声明；`lib/video-tail-frame.ts` 再统一校验资产。禁止把 allowlist 放宽为前缀、正则或“同系列应该支持”。

| 供应商类型 | 精确模型 | 协议 |
| --- | --- | --- |
| `jimeng` | `doubao-seedance-2-0-260128` | `ark-content-roles` |
| `jimeng` | `doubao-seedance-2-5-260628` | `ark-content-roles` |
| `jimeng` | `doubao-seedance-2-0-fast-260128` | `ark-content-roles` |
| `openai-video` | `kling-2.5` | `company-gateway-kling` |
| `openai-video` | `kling-3.0` | `company-gateway-kling` |
| `openai-video` | `qiniuyun/kling-3.0` | `company-gateway-qiniuyun-kling` |
| `openai-video` | `doubao-seedance-2-0-260128` | `company-gateway-seedance` |
| `openai-video` | `doubao-seedance-2-0-fast-260128` | `company-gateway-seedance` |
| `openai-video` | `doubao-seedance-2-5-260628` | `company-gateway-seedance` |

其他 `openai-video` 模型返回 `contract_unverified`；其他未声明类型/模型返回 `unsupported_model`。方舟首尾帧分别使用 content role `first_frame` / `last_frame`，图生视频比例固定 `adaptive`。

上传和创建任务还有独立校验：尾帧一次一张，必须是当前项目 `role='input'`、`usage='video_tail_frame'` 的资产；带尾帧的运镜必须填写提示词。队列再次复核项目归属和用途，且只有尚未取得远端 task ID 时才需要读取/校验本地尾帧并提交。

## 7. 图片队列 `lib/queue.ts`

### 7.1 并发与领取

- 队列按 `projectId` 存放在进程内 Map，状态为 `idle/running/paused`；重复启动会拒绝。暂停只停止继续领取，不中止已经发出的请求；恢复沿用原队列。取消会 Abort 并把项目下 pending/retrying/running 任务标为 canceled。
- `POST /api/projects/[id]/run` 的默认请求并发为项目值或 10，默认 `maxAttempts=2`、`timeoutMs=600000`。`getEffectiveImageConcurrency()` 当前只做有限值、向下取整和最小 1 的规整，**没有供应商专属并发上限**。
- worker pool 中每个 worker 原子领取 `pending/retrying`，按任务 `id` 排序；领取时递增 `attempt`、写 `startedAt` 并转 running。进程重启后的遗留 running 在下次启动时转 retrying。
- 所有 worker 结束后按任务实际状态计算项目终态；请求完成和最终成功更新都复核任务仍是 running，避免取消后落盘旧结果。

### 7.2 同步、异步与恢复

同步 OpenAI/方舟/Packy 请求受项目超时和 AbortController 控制。GeekAI 与通用 gateway-task 图片任务使用提交 → 轮询 → 下载：

- 适配器轮询间隔在前 2 分钟为 5 秒，之后 10 秒；单次轮询请求 30 秒，适配器自身最长轮询窗口 15 分钟。队列还受项目 `timeoutMs` 限制，未显式传入时该分支回退 5 分钟。
- 异步任务保存 `providerTaskId`、`providerStatus`、截断的原始响应、`submittedAt`、`lastPolledAt` 和 `pollCount`。完成但无图片 URL 的 gateway 任务走 `/content`。
- 轮询超时而仍有 task ID 时进入 `needs_check`，不直接当作可重新提交的失败；`POST /api/jobs/[id]/resume-poll` 只补抓原任务，不再次提交，补抓窗口为 5 分钟。
- `gateway-task-image` 在提交前强检查是否已有 task ID；已有或无法确认远端身份时失败关闭到 `needs_check`，避免重复计费。手工 retry 对任何已有 task ID 的图片任务也改为 `needs_check`，而不是清零重交。
- 远端已成功但本地下载失败时，主队列标 `failed` / `providerStatus='download_failed'` 并保留远端 URL，不自动重试花第二次钱。图片补抓遇到 gateway 下载失败则保持 `needs_check`，便于稍后继续。

产物落盘前由 `lib/image-output-normalize.ts` 规整；公司原生交付与普通 cover/resize 的差异见公司网关参考。正常完成还同步 `image_assets`、分镜历史候选和最新结果。

## 8. 视频队列 `lib/video-queue.ts`

### 8.1 并发、超时与领取

- 默认并发由 `VIDEO_CONCURRENCY` 提供，缺省 10 并钳制在 1–10；项目 `videoConcurrency` 可覆盖，API 同样钳制 1–10。
- 默认轮询窗口 15 分钟，可由 `VIDEO_TIMEOUT_MS` 覆盖并钳制在 1 分钟到 24 小时。适配器可声明更长下限，当前用于长时间 Seedance 任务。
- `maxAttempts <= 1` 的旧行在运行时按 2 处理，更大的显式值保留。提交前的普通失败会回 pending 自动重试，达到上限才 failed。
- 遗留 running 在启动时恢复 pending；领取按 `createdAt, rowid`，与 UI 顺序一致。每个项目独立 worker pool。
- `VIDEO_PROVIDER_CONCURRENCY_LIMITS` 当前为空，所有类型默认无额外供应商限速。若以后配置，该闸门按 `providerId` 跨项目统计 running，与项目并发是两层不同限制。
- 暂停/恢复/取消控制与图片队列相似；视频取消写 pending/running 为 canceled，适配器内部 AbortError 不能被误判为用户取消。

### 8.2 防重复提交与限流退避

- 只有没有 `providerTaskId` 的任务才执行 `adapter.submit()`。已有 task ID 的 pending 或 `needs_check` 任务直接续跑轮询；队列在没有新 pending 时会自动领取 `needs_check`，无需用户重新提交。
- 拿到 task ID 后的轮询异常或超时进入 `needs_check`，不重新 submit。供应商明确返回 failed 是终态，不自动重试；人工 retry 只有在“供应商明确失败、尚无远端/本地产物”时才清除旧 task ID 并允许新任务，其他情况保留身份。
- 提交错误文本命中 `submit error 429/5xx` 时走独立限流逻辑：按供应商冷却 30/60/120 秒，同一任务最多重排 5 次，超过才 failed。该重排不消耗 `maxAttempts`，冷却状态在内存中，任务本身仍持久化。
- 每 5 秒轮询一次并持久化供应商状态与计数。下载成功后写 `storage/videos/`，再生成浏览器预览衍生物；预览失败有内部回退，不应把已下载任务变成失败。

### 8.3 首帧资产选择

视频首帧和尾帧优先使用 `originalPath`，其次 `processedPath`，最后 `path`，避免把为图片 API 压缩过的副本作为视频生成起点。MIME 按实际选中文件扩展名推导，再以资产 MIME 回退。首帧/尾帧如何交付给上游由适配器决定，公司链路的 fail-closed 规则不能用本地路径绕过。

## 9. 成本与用量不是同一笔账

- `lib/cost.ts` 的旧图片估算为 `defaultCostPerImage × attempt`；未配置价格按 0。`jobs.estimatedCost` 是估算，不是供应商账单。
- 已接入核心用量计价的公司模型会在首次真实提交前冻结 `usageSnapshotJson`。图片正常完成时优先按快照价格与尝试次数计算 `estimatedCost`，快照不可用时才回退旧单价；视频按快照和 `durationSec` 记录成功用量。
- 快照写入失败不阻塞核心生成，但不能在已有远端 task ID 后补造一份“首次提交价格”。成功事件的实时用量写入失败只告警，交由 reconciler 补记，不回滚已经成功的任务。
- 图片旧 CSV 工具保留 `estimated_cost_cny`、尝试次数、延迟、供应商 task ID 等字段；它不能替代 `usage-pricing.ts` 的精确身份匹配和整数 micros 计价。

## 12. 修改红线

- 新增供应商必须实现对应适配器并注册，不把供应商协议分支散落到 UI 或项目 API。
- 不恢复数据库密钥的 env 回退，不在任何 GET/PUT 响应中回显秘密。
- 不改变“底图在前、参考图在后”的顺序，不让 SQL 查询顺序代替持久化 ID 顺序。
- 不把视频尾帧能力改成前缀匹配；上传、创建、队列提交三层校验都要保留。
- 视频与 `gateway-task-image` 已有远端 task ID 后，超时、崩溃或下载失败不能自动变成第二次付费提交；其他图片类型也不得绕过各自恢复语义。视频人工重交只能走明确的确认失败分支。
- 不用 `defaultCostPerImage` 覆盖核心用量快照，不把估算成本称为真实账单。
