## 结论

方案方向和主要风险判断成立，尤其是独立公式计划器、真实 audioPlan、冻结与审核分离、原声时长优先以及保留正式发布事务。需要补齐的是既有实现的接入限制，不能把“复用调度器/音频编辑/导出界面”理解为整条业务链已经现成。

建议实施前优先定稿 R1、R2、R3、R6、R7；R4、R5、R8–R10 纳入对应阶段的显式工作与验收。本次新增核查记录，不直接改写方案、计划或应用代码。`300efeb..327f531` 的批量领域、批量组件/API、共享媒体及 package.json 没有差异，下面的问题主要是原计划对复用边界描述不够细，而非这次提交漂移造成。

## 生成流程、数据与声音

### R1 · P1：把“点击生成后自动完成”落实为持久化、逐条推进的服务端编排

**计划对应**：§3.4 写“重任务使用既有持久调度器”，P4/P6 要一键完成、单项失败隔离；功能方案 §3 明确已完成项可先进入第三步。

**源码事实**：`startOrResumePhaseE` 为所有脚本创建口播任务，等待全批 queued/running 口播归零才调用分配（[phase-e.ts](../lib/batch-production/phase-e.ts:262)）。下一阶段依赖浏览器 `autoStartAfterGatesRef` 和 effect 再次调用 start（[BatchPreparationPanel.tsx](../components/batch-production/BatchPreparationPanel.tsx:218)、[BatchPreparationPanel.tsx](../components/batch-production/BatchPreparationPanel.tsx:623)）；持久化任务执行器的注册中没有负责后续阶段推进的公式编排（[bootstrap.ts](../lib/batch-production/bootstrap.ts:20)）。start 路由还会先无条件走普通语义打分准备（[start/route.ts](../app/api/batch-production/batches/[id]/start/route.ts:41)）。

**影响**：直接复用现有 start 流程，刷新/关闭页面会丢失“完成后继续”的前端意图；一个长时间配音任务会挡住其他脚本进入分配和审片。公式模式也不应先为整篇文案生成 TTS，再决定哪些文字已被原声覆盖。

**建议调整**：P0/P1 增加生成请求、阶段依赖、状态和幂等身份设计，使用同一个调度器在服务端推进“选片/原声核验 → 文案映射 → 必要 TTS/对齐 → 最终时长/执行快照 → 封面/包装预览”。按成片或具有相同冻结输入的工作单元推进，批次状态只做聚合；公式 start、重选片、恢复都显式分路，不进入语义重排。补验收：配音中关页后继续、进程重启续接、某条任务一直未完成但其他条可审、阶段提交后崩溃不重复创建下一阶段、同一生成请求重复提交。

### R2 · P1：声音产物与任务身份不能继续“一份脚本只有一条整篇配音”

**计划对应**：§3.1/§3.3 已设计逐条冻结计划和 audioPlan，P2 候选轮换、P4 混合声音、P5 单条修改；尚未明确如何替换现有声音任务及权威存储的粒度。

**源码事实**：口播任务目标固定为 `script_snapshot`，requestKey 只含版本和脚本快照（[phase-e.ts](../lib/batch-production/phase-e.ts:145)）。执行器对整份 `bodyText` 生成段落，复用键包含脚本与配音参数，没有实际候选/文案用途映射（[narration-executor.ts](../lib/batch-production/narration-executor.ts:104)、[narration-executor.ts](../lib/batch-production/narration-executor.ts:223)）。落库按 `scriptSnapshotId` upsert 一份配音，兼容更新还会写到该脚本对应的所有输出版本（[narration-executor.ts](../lib/batch-production/narration-executor.ts:365)、[narration-executor.ts](../lib/batch-production/narration-executor.ts:387)）。

**影响**：同脚本两份成片选择不同原声候选、或只修改其中一份的台词/声音用途时，剩余 TTS、真实时长、对齐都可能不同。沿用现有脚本级一对一身份会共用错误声音，或把一条重试结果写进其他成片/历史版本。

**建议调整**：在 P0 定义“实际声音计划修订”和“可复用音频块”的独立身份。音频块可以按确切文本、供应商、音色、参数及算法版本复用；其引用、位置与原声覆盖关系必须属于相应输出计划修订。提交时校验目标版本和期望声音修订，只更新本次目标；禁止按脚本广播覆盖。补“同脚本两份不同原声”“单条改词不改兄弟输出”“旧配音任务迟到不覆盖新版本”用例。

**阶段依赖调整**：P2 可以冻结候选与生成输入，P3 可以先实现纯时长算法；包含真实音频和最终区间的可执行快照只能在 P4 得到实际 TTS/对齐后完成。需要写清输入冻结与最终执行冻结两次边界、失败后的重入规则，不把 P2 的候选冻结当成完整声音/时长计划已就绪。

### R3 · P1：补“无 BGM”显式配置与启动通路

**计划对应**：功能方案 §8.3 明确 BGM 可不选；开发计划 P4 目前主要写 ducking、增益和限幅，没有列出现有必选门禁需要调整。

**源码事实**：曲库为空时 start 直接报错（[phase-e.ts](../lib/batch-production/phase-e.ts:256)）。BGM 选择只有 `auto | manual`，手选为空会回退整个池（[bgm.ts](../lib/batch-production/bgm.ts:97)、[bgm.ts](../lib/batch-production/bgm.ts:125)）；UI 也明确“取消全部勾选恢复自动分配”（[BatchStepScripts.tsx](../components/batch-production/BatchStepScripts.tsx:366)）。

**影响**：曲库为空的用户无法开始；取消勾选所有音乐也不能得到方案所说的“无 BGM”。

**建议调整**：为公式模式加入持久化的 `none` 选择，贯穿冻结、选择、预览、渲染及发布，缺省旧数据仍保持旧语义。纯原声且不需要 TTS 的输出也不得依赖 TTS 供应商才能运行。补“空曲库 + none 可以生成导出”“有曲库 + none 不自动回填”“选择音乐但文件丢失仍明确报错”，不要用音量设零冒充无 BGM 配置。

### R4 · P2：素材命名表需要独立于视频存在的编号定义

**计划对应**：§3.1 当前列出集合、`logicalCode → assetId` 绑定、素材区间和脚本修订；P1 要双表导入，P2 要判断缺号替换是否同动作/同卖点。

**源码事实**：现有 `batch_assets` 身份依赖实际内容指纹，同项目同指纹复用同一素材（[assets.ts](../lib/batch-production/assets.ts:48)、[assets.ts](../lib/batch-production/assets.ts:94)）。计划中的 binding 也以 `assetId + 指纹` 为中心，没有明确无文件编号的定义如何持久化。

**影响**：S76 虽缺视频，但命名表仍有“3cm 金属脚/扫地机同框”的定义；P100 则连定义都没有。若只保存有视频的 binding，这两类会同样变成“查不到素材”，自动替换失去原始卖点依据。工作簿级指纹本身不能替代逐编号的原表内容和来源。

**建议调整**：增加逻辑素材定义（可用表或版本化 JSON），保存 `collectionId + logicalCode`、命名表原字段/单元格、台词、动作/卖点/花字、修订与文件名冲突处理；实际候选绑定是其 0..N 个关联。也可允许 binding 的媒体引用为空，但需明确“有定义无文件”和“无定义”状态，不创建虚假 batch_asset。补这两类缺号、定义更新不改冻结替换、同内容多编号各自保留语义资料的用例。

### R5 · P2：P4 单列实时音频预览改造，现有源时间模型尚未贯穿播放器

**计划对应**：§2 认为源/时间线区间可复用；P4/P5 和 A12/A13 要音画同步、预览与导出一致。目标正确，但缺少播放器本身的具体工作项。

**源码事实**：现有预览仅接一条 `narrationUrl`，视频双 slot 默认静音（[BatchTimelinePreview.tsx](../components/batch-production/BatchTimelinePreview.tsx:96)、[BatchTimelinePreview.tsx](../components/batch-production/BatchTimelinePreview.tsx:851)）；音频裁切用于判断当前是否可听，seek 仍直接使用正文时间 `bodyOffset`（[BatchTimelinePreview.tsx](../components/batch-production/BatchTimelinePreview.tsx:496)、[BatchTimelinePreview.tsx](../components/batch-production/BatchTimelinePreview.tsx:575)、[BatchTimelinePreview.tsx](../components/batch-production/BatchTimelinePreview.tsx:699)）。而渲染已在移动音频时按 `sourceStartUs/sourceEndUs` 裁切，再延时到 `timelineStartUs`（[batch-renderer.ts](../lib/batch-production/batch-renderer.ts:764)）。`audioAudibleAt` 本身只判断时间轴范围，不计算取源时间（[audio-edit.ts](../lib/media-core/audio-edit.ts:69)）。

**影响**：源 5–7 秒移到正文 0–2 秒这类编辑，现有浏览器路径仍会 seek 源 0 秒；增加“原声”轨道或让 FFmpeg 正确混音并不能使审片试听自动正确。多原声来源、TTS 和代理切换会进一步扩大这个差距。这是静态调用链核对结果，尚未做浏览器听审复现。

**建议调整**：把 `BatchTimelinePreview`、`BatchReviewPreviewDock`、受控声音媒体接口与工作区声音就绪聚合纳入 P4。预览和渲染共享纯时间映射、声音窗与 ducking 语义，明确缓存/代理下取哪个音频源；不要同时播放代理内音轨与另取的原声音轨。新增有可辨识声标的播放测试，覆盖源区间移动、seek、暂停恢复、换成片、切代理、片头偏移、串音和声音资源代际取消，并与真实导出对照。

## 发布、包装与兼容边界

### R6 · P1：明确公式迁移失败时普通批量模式的可用性

**计划对应**：§1 要求迁移失败不阻塞不依赖新结构的功能；P1 新增所需迁移；A17 验证迁移与旧快照；§7 保留旧语义路径。

**源码事实**：当前 readiness 是整个批量模块的门禁。`batchReadinessUnavailable` 在 `available=false` 时直接拒绝（[readiness.ts](../lib/batch-production/readiness.ts:67)）；所有批量 API 读写前都调用 `assertBatchApiReady`，兼容状态统一抛出不可用错误（[runtime-readiness.ts](../lib/batch-production/runtime-readiness.ts:30)）。`ensureBatchSchemaReady` 以迁移清单最后版本为目标，新迁移失败返回 `compatibility_only`（[schema.ts](../lib/batch-production/schema.ts:2621)、[schema.ts](../lib/batch-production/schema.ts:2700)）；启动恢复也会因此不启动批量调度器（[bootstrap.ts](../lib/batch-production/bootstrap.ts:34)）。这里的“旧功能仍可用”目前指批量模块以外的既有功能，不等于普通批量可以继续。

**影响**：如果公式表直接追加到同一强制升级流，却不调整能力门禁，公式迁移/备份失败会一起阻断已有普通批量。不能仅复用当前 gate 就宣称满足计划中的兼容要求。

**建议调整**：P0 明确“普通批量也必须在公式升级失败后继续工作”是否属于此次兼容目标。若是，设计可验证的基础批量 readiness 与公式 capability readiness，仍共用备份、锁和审计设施；不能跳过完整性检查或忽略失败。补上“已有 v27 普通批次 + 公式升级失败 + 普通批量读写/领取仍按预期可用”的验收。若只保留模块外功能，计划应准确说明受影响边界。

### R7 · P1：审核提交本身要做版本/修订校验

**计划对应**：§3.4 已提出写操作携带期望修订；P5 要确认当前版本、修改后重新待审；A16 主要覆盖导出中编辑/撤审。

**源码事实**：现有审核输入只有 `planIds + decision`（[review.ts](../lib/batch-production/review.ts:47)）；保存的审核信息只有 `decision + decidedAt`（[review.ts](../lib/batch-production/review.ts:81)），按服务器读到的 `currentVersionId` 更新，未收到浏览器看过的输出版本/编辑修订（[review.ts](../lib/batch-production/review.ts:94)）。正式发布最终事务已经复核审核态与渲染契约，但无法知道用户实际审过哪个页面快照（[phase-e.ts](../lib/batch-production/phase-e.ts:741)）。

**影响**：两个标签页并行时，旧页展示版本 A/修订 1，另一页改为 B/修订 2，旧页点击“通过”可能批准服务器当前内容。公式模式将一次审核同时确认替换、自动区间和声音差异，这个竞争条件会直接影响“确认当前可见替换”的承诺。

**建议调整**：把审核路由和 `review.ts` 列为 P5 显式改造项。每条提交携带 `expectedOutputVersionId + expectedEditRevision`，在写入审核的同一事务校验并记录被确认的修订/问题快照；多条冲突语义明确为整批拒绝或逐条结果。A16 补“旧页确认不能批准新内容”“同版本编辑修订变化”“审核后再修改问题清单”用例。

### R8 · P2：把 ZIP 与剪辑清单拆为独立交付和验收

**计划对应**：P5 只有一项“完整剪辑清单及 ZIP”；当前 A01–A24 没有针对 ZIP 内容、清单版本一致性和下载失败的专项验收。

**源码事实**：当前批量 `POST exports` 负责排渲染和正式发布，返回 JSON 状态（[exports/route.ts](../app/api/batch-production/batches/[id]/exports/route.ts:20)）；第四步只有逐条视频、封面下载（[BatchStepExport.tsx](../components/batch-production/BatchStepExport.tsx:220)）。项目“全部产物”ZIP 查询的是图片 `jobs` 与 `video_jobs`，不包含 `batch_artifacts`（[download/route.ts](../app/api/projects/[id]/download/route.ts:20)、[download/route.ts](../app/api/projects/[id]/download/route.ts:35)）。可复用的是底层 ZIP 流工具（[zip-download.ts](../lib/zip-download.ts:107)），不是现成的批量正式产物 ZIP 业务接口。

**影响**：仅接现有项目下载接口会漏掉公式成片；若临时读取当前 arrangement 来写清单，又可能把旧正式视频与新编辑计划混在同一包中。

**建议调整**：P5 明确新增所选正式产物打包/下载契约，冻结 `planId、outputVersionId、editRevision、renderContractHash、video/cover artifactId 与 checksum` 及与该次渲染一致的剪辑清单。清单由渲染/发布快照生成，不能读取后来改变的草稿。补验收：部分条目未发布、打包中返工、封面缺失/损坏、重名处理、中文名、连接中断/重试、JSON/CSV 不含绝对路径和密钥，且清单中的相对文件名确实存在于 ZIP。

### R9 · P2：P5 轨道顺序漏掉已有“卖点”轨道

**计划对应**：P5 写的是“字幕 → 视频 → 原声 → 配音 → BGM”，同时要求保留既有统一审片能力和花字调整。

**源码事实**：当前工作台在字幕与视频之间已经渲染 `BatchPackagingTrack`（[BatchReviewTimelineDock.tsx](../components/batch-production/review/BatchReviewTimelineDock.tsx:1421)），底部明确显示“字幕 → 卖点 → 视频 → 口播 TTS → BGM”（[BatchReviewTimelineDock.tsx](../components/batch-production/review/BatchReviewTimelineDock.tsx:1634)）。

**建议调整**：改为“字幕 → 卖点（启用包装时）→ 视频 → 原声（存在时）→ 配音 → BGM”。补原声轨道插入后卖点添加、修剪、删除、画内编辑与快捷键选择的回归，避免新轨道布局挤掉已有包装编辑入口。

### R10 · P2：冻结原脚本号与份次，不能借用现有重名后缀

**计划对应**：§3.1 保存原脚本序号，P5 要文件名含“脚本序号/份数/包装”；但尚未规定如何接入共享导出身份。

**源码事实**：`batch_output_plans.seq` 是批次内全局序号，并非 Excel 原序号或脚本内份次（[plans.ts](../lib/batch-production/plans.ts:80)）；创建多份时只递增全局 `seq`（[plans.ts](../lib/batch-production/plans.ts:131)）。`BatchExportIdentity` 没有原序号/份次字段（[batch-export.ts](../lib/batch-production/batch-export.ts:11)），只要 `productionCodes` 中有包装等编号就直接用编号命名，不使用 `planSeq` 后缀（[batch-export.ts](../lib/batch-production/batch-export.ts:140)）。文件尾 `-02/-03` 是目录防覆盖时生成的冲突序号（[batch-export.ts](../lib/batch-production/batch-export.ts:171)），会受发布顺序影响，不能解释为第 2/3 份。

**建议调整**：P0 确定公式导出身份的版本化扩展，冻结原表脚本标识与 `copyIndex`，随 render result 交给发布，保持旧 J/K/f 命名兼容；防覆盖序号仍独立。补相同脚本多份、只选脚本 12/141、并发乱序完成、包装关闭、重新生成与重试不改变份次的文件名/清单测试。不要给素材 G/VO 编号虚构 K 含义。

## 已有要求的具体落点提醒

以下不作为新增产品需求或单独缺陷；计划已经提出目标，但实施时应把相关文件列入改造清单。

1. **封面随机必须按成片落快照。** 现有封面覆盖是 `stylesByScript[sourceScriptId]`（[cover-title.ts](../lib/batch-production/cover-title.ts:154)）。同脚本多份不能靠这张映射实现逐成片随机；应沿用/扩展输出 arrangement 的覆盖，并同时冻结构图。计划 §3.2 的逐条完整配置要求是正确方向。
2. **包装对时必须切换到实际声音映射。** 当前包装词级时间从 `batch_script_narrations` 按脚本快照读取（[packaging.ts](../lib/batch-production/packaging.ts:18)），不是多源 audioPlan；初始化包装也会重新生成 cue ID（[packaging.ts](../lib/batch-production/packaging.ts:71)）。公式模式的初次冻结、重试与人工重提取需分开，按最终原声/TTS 时间线消费词级/字幕时序，避免旧整篇配音时序漏入。
3. **三种声音模式的门禁不只在 renderer。** `phase-e` 的结果解析/发布、`batch-export` 仍限定 narration，需与 plan 中的 audioPlan 契约一起修改（[phase-e.ts](../lib/batch-production/phase-e.ts:493)、[phase-e.ts](../lib/batch-production/phase-e.ts:666)、[batch-export.ts](../lib/batch-production/batch-export.ts:249)）。计划已明确不能绕过静音占位门禁，这条应保留。
4. **新任务类型涉及真实表重建。** `batch_tasks.workType` 是 SQL CHECK（[schema.ts](../lib/batch-production/schema.ts:1155)），不是只改 TS union。若新增公式阶段 workType，重建必须保留 attempts 和 `batch_asset_analysis_requests` 等引用子表；v25 已有漏子表会触发级联删除的说明（[schema.ts](../lib/batch-production/schema.ts:1103)）。这是 P1 迁移实施清单的必要细化。
5. **补手动编辑后的公式身份规则。** 现有编辑器允许插入、删除、移动、替换与分割；替换默认取新素材 0 秒起的等长区间，删除保留空位，分割生成新 clipId（[output-arrangement.ts](../lib/batch-production/output-arrangement.ts:1144)、[output-arrangement.ts](../lib/batch-production/output-arrangement.ts:1164)、[output-arrangement.ts](../lib/batch-production/output-arrangement.ts:1203)）。需写清 slotId 与分割后的多个 clipId 关系，以及人工插入/删除/换序如何记录为显式偏离；不能静默改变公式后继续宣称符合原公式。人工换片还须重选合法范围/保护区间。普通“重新分配”接口目前直达语义分配（[phase-e.ts](../lib/batch-production/phase-e.ts:294)），也必须模式分路。是否保留会造成黑场的手动操作与正式门禁应在 P0 定稿，而非只在生成器禁止黑场。
6. **导入依赖和既有限制可直接写实。** 仓库已依赖 ExcelJS（[package.json](../package.json:28)），可复用库，但现有其他模块 `cellText` 接受计算结果缓存（[normalize.ts](../lib/script-studio/catalog-import/normalize.ts:7)），不宜直接复用来满足公式模式“必填计算单元格要求转值”的规则。旧手动导入单次最多 50 条（[manual-script-import.ts](../lib/batch-production/manual-script-import.ts:8)），视频上传单次最多 100 文件、单文件 256MiB、整请求 512MiB（[import/route.ts](../app/api/batch-production/assets/import/route.ts:21)）。P1 需要公式导入会话及分批上传，而非让 300 条脚本或 257 个视频直接穿过旧单次接口；是否提高单文件上限应根据真实样本测量决定。

## 建议对开发计划的修订顺序

1. **先补 P0 契约**：持久化逐条编排；声音块/声音计划身份；逻辑编号定义；输入与执行快照两次冻结；公式与普通模式 readiness；审核版本校验；导出原序号/份次。
2. **P1 同时做基础接入**：公式导入会话、分批上传和无文件编号资料；任务/请求 schema 及迁移兼容验证；`none` BGM 设置。先避免导入和启动入口上的硬阻塞。
3. **P2/P3/P4 明确依赖**：候选与输入先冻结，纯时长算法可独立验证，但完整排片必须等真实声音；提前串通一个原声+TTS 的小样本，而非到 P5 才首次接浏览器声音。
4. **P5 补具体交付**：审核 CAS、卖点轨道兼容、单条声音修改、受控音频预览、正式清单/ZIP 及稳定文件名。追加 R1–R10 对应的用例，不只沿用“总体一致”一句验收。
5. **P0 完成后重估排期**：原 17–26 工程日明确是估算，可以保留为旧基线；持久化编排、播放器源映射、审核 CAS 和 ZIP 会影响实际工作量，目前没有依据给出新的确定天数。
