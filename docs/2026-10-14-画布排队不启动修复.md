# 画布排队不启动修复

## 现场证据

用户反馈图片节点持续显示「排队中」，另建独立节点也无法开始。只读检查当前本地数据库，截图对应的三个任务均为 `queued / not_sent`，`slotHeld=0`、`pollCount=0`、无远端任务 ID；全局没有被占用的画布名额。

`storage/logs/schema-upgrades.jsonl` 中，2026-10-14 14:10 启动时批量模块持有共享升级锁，画布启动检查以 `upgrade_in_progress / lock_timeout` 退出。15:02 打开画布时，API 的 readiness 已重新通过，但原实现只有启动钩子会启动调度器，API 恢复后没有补启动。这导致接口可以保存和提交任务，队列却无人领取。

画布本身已有后端远端轮询和全局默认 10 个并发名额，前端每 1.5 秒刷新状态。正常轮询与租约心跳按日志合同不逐次记录。此次问题发生在领取任务之前。

## 修复

- 画布 API 通过 readiness 后，幂等确保调度器已启动。
- 启动钩子与多个 API 请求共用进程级启动 Promise，避免重复创建调度器。
- 恢复扫描随新实例创建执行一次；重复请求不清除活跃任务租约，不重新提交已有远端身份的任务。
- 保留功能关闭、执行器关闭以及共享数据库升级 gate 的约束。

## 验证

新增 `node scripts/creative-canvas-bootstrap.test.ts`，真实持有升级锁复现首次启动失败，再经实际路由恢复。修复前失败于「API 必须补启动调度器」，修复后通过；同时验证六个并发 API 请求只创建一个实例、恢复旧准备任务、持续轮询、第一个节点生成时新建的第二个独立节点完成，以及重复提交的幂等性。测试仅用隔离临时根和 fixture，不调用真实供应商。

以下检查通过：

- `creative-canvas-bootstrap.test.ts`
- `creative-canvas-scheduler.test.ts`
- `creative-canvas-recovery.test.ts`

调度测试有一次在临时数据库备份/迁移准备阶段返回 `compatibility_only`，未进入调度断言；单独重跑通过，未调整迁移门禁。

本次未关闭正在运行的桌面工作台，未替换其 standalone 产物，未改写用户任务。源码修复在退出工作台并通过正常源码启动入口重新打开、自动重建后生效；已有排队任务保留，无需重新点击生成。
