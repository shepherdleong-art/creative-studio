## 任务 C：口播优先重构（P1，核心）

### C0 为什么要做 —— 实测证据

用户项目 G564（脚本 3 句、目标 15 秒）的真实数据：

| | 口播真实时间 | 画面时间 | 偏差 |
|---|---|---|---|
| 第 1 句 | 0 – 4.06s | 0 – 5.00s | — |
| 第 2 句 | 4.06 – 8.31s | 5.00 – 10.00s | 慢 0.94s |
| 第 3 句 | 8.31 – 13.37s | 10.00 – 15.00s | **慢 1.69s** |

三处成因：

1. `allocator.ts:495-502`：句段无显式时长时按 `目标时长 ÷ 句数` 平均切 → 3 × 5.00s 写死等长；
2. `allocator.ts:924-953`：每句只挑**一个能整段装下的连续区间** → 1 句 = 1 镜头，永远 3 刀；
3. `batch-renderer.ts:718-721`：渲染以口播时长 13.37s 为准，把 15s 画面直接裁掉尾巴，第 3 镜头只播 3.37s。

而**字幕走口播真实时间**（`batch-renderer.ts:690`），画面走估算时间 —— 字幕对得上、画面对不上，这就是「生拼硬凑」的实感来源。
语义打分本身没问题（该批 `semanticScore` = 0.92 / 0.88 / 0.84，reason 全 `semantic_primary`），**别误伤**。

单条为什么不这样：顺序是 TTS 先行；有 `buildTtsAwareMatchSentences` 按"最长可用场景时长 + 可用场景数"把长句再切成最多 8 个视觉单元；还有节拍吸附与复用上限。

### C1 前置：统一断句（必须先做，否则后面全是错位）

两套断句**并存且不等价**：

- `lib/batch-production/narration.ts:56 splitScript`：`(?<=[。！？!?；;])|\n+` —— 零宽 lookbehind，**保留标点**
- `lib/batch-production/allocator.ts:463 splitAllocationScriptBody`：`(?:[。！？!?；;]\s*|\n+|\r+)` —— **吃掉标点**

正常文本两者句数一致，但连续标点（`A。。B`）等边界会一个给 3 句、一个给 2 句。P1 要把 narration 句段按序号映射到分配句段，句数必须是单一事实。

**做法**：新建 `lib/batch-production/script-sentences.ts`，导出
`splitBatchScriptSentences(bodyText): Array<{ text: string; textWithPunctuation: string }>`，
narration / allocator / semantic-match 三处全部改调它。

**红线**：`stableSegmentId(scriptSnapshotId, index, text)` 用的是**带标点**的 text，既有 `batch_script_narrations` 的句段 id 依赖它 —— 所以 `textWithPunctuation` 供 narration 算 id，`text`（去标点）供 allocator 与语义矩阵。**不得改变任何既有句段 id**。

**回归脚本**：写一次性脚本对 `batch_script_snapshots` 全表跑两种切分，断言数量逐条一致；有不一致的先报出来再决定。

### C2 口播产物补上词级时间戳（已有数据，只是被丢了）

TTS 适配器**已经返回** `wordTimings`（`lib/final-edit/adapters/tts-registry.ts:27`，vapi/doubao 两个适配器都填了），但批量侧丢弃了：`narration-executor.ts:207` 只取 `segmentTimings`，`narration.ts:127 createLocalNarrationSnapshot` 也不接收。

1. `BatchLocalNarrationArtifact`（`narration.ts:41` 附近）加可选 `wordTimings: Array<{ text; startUs; endUs }>`，写进 narration 快照 JSON。
   `batch_script_narrations.narrationJson` 是整块 JSON，**追加字段不需要迁移**；但 `BATCH_NARRATION_SCHEMA_VERSION` 要 bump，且 `wordTimings` 必须是可选的（老快照没有 → 退回不再切分）。
2. **顺带修一个既有缺陷**：`narration-executor.ts:172-178` 命中音频缓存时走 `proportionalTimings`（`narration.ts:112-124`）把时间**又平均切回去**了 —— 同一脚本重跑一次，句时间反而退化。改成先读 `batch_script_narrations.narrationJson` 复用真实对齐；读不到才回落平均切，并在结果里标 `timingSource: 'estimated'`。

### C3 反转 phase-e 顺序

现状 `lib/batch-production/phase-e.ts`：freeze → `persistBatchAllocation`（`:161`）→ 建 narration 任务（`:104-110`）+ 建 render 任务（`:114-120`）。

目标：**freeze → narration → allocate → render**。

- 可行性已确认：narration 的权威产物是 `batch_script_narrations`（按 scriptSnapshotId），**不依赖 output version**；executor 里那句 `UPDATE batch_output_versions SET arrangementJson = json_set(...)`（`narration-executor.ts:258`）只是把占位就地升级，反转后不再需要 —— 分配时直接把真实 narration 烤进 arrangement。
- **续跑机制照抄语义打分那套**，不要在 runner 里埋跨模块回调：`startOrResumePhaseE` 发现该版本 narration 未齐 → 返回 `narration_pending`，前端沿用现有自动续跑（`BatchPreparationPanel.tsx:468-479` 的同款 effect，把 workType 判断扩成 `narration | semantic_score`）。
- 静音占位路径保留（口播失败仍能出静音预览候选），正式发布闸门由现有 `assertNarrationPublishable` 守住，不放松。

### C4 分配吃真实口播

- `allocation-store.ts buildFrozenInput`：读 `batch_script_narrations`，把每个 plan 的 `{ durationUs, segments, audioFingerprint, wordTimings }` 挂到 `FrozenBatchInput.plans[].narration`。
- `allocator.ts normalizePlan`（`:525-554`）：有 narration 时，句段时间**取真实对齐时间**，不再走 `targetDuration ÷ 句数`；`plan.targetDurationUs = narration.durationUs`。无 narration 时保留现有估算路径（老版本兼容）。
- **指纹自动生效**：`buildResult` 的 `inputFingerprint` 已经包含 `normalized.plans`（`allocator.ts:1089`），narration 进了 `NormalizedPlan` 就自动纳入身份 → 换音色 = 新分配运行，`readExistingRun` 幂等逻辑一行不用改。

### C5 TTS 感知再切分（真正解决「只有 3 刀」）

- **复用** `lib/final-edit/match-sentence-refinement.ts` 的 `buildTtsAwareMatchSentences`，**不要复制一份**。
- 入参：`segments` = narration 句段；`wordTimings` = C2 落库的词级时间；`maxSceneDurationUs` = 素材池最长场景时长；`availableSceneCount` = 场景总数。默认上限 8 个单元、单元最短 1.2s。
- 单元 id：`${planId}:segment:<i>:unit:<k>`；`sourceSegmentId` **保留原句 id** —— `createArrangement`（`allocator.ts:685-719`）已按 `sourceSegmentId` 归并做字幕，字幕仍按整句切一次，不会碎。
- **语义分继承母句**：矩阵仍按原句缓存（`batchSemanticScriptKey` 不变），子单元用母句的 `semanticScores`。
  这是与单条的**有意偏差**（单条按 TTS 单元打分）——理由：打分时机保持在快照确认后，才能满足任务 B 的「用户无感」；若改成按单元打分，打分必须等口播完成，链路会再长一截。同一句的多个单元分数相同时，分配器的 `reuseCount * 3` 与 overlap 惩罚（`allocator.ts:944`）会自动把它们推到不同素材，画面依然有变化。
- 预期效果：3 句 15s → 最多 8 个视觉单元，每刀落在真实词边界上，且句起点与口播严格对齐。

### C6 渲染侧收尾

- 对齐后 `visualDurationUs == narration.durationUs`，`batch-renderer.ts:720-721` 的 `tpad`/`trim` 变成 no-op。**分支保留**作兜底，但加一条：偏差 > 0.15s 时记 warning（不阻塞渲染），这是回归探针。
- 字幕已经走 narration 真实时间（`:690`），不用动。

### D2 目标与命名规则

**必须落库固定下来**：`CORE_DB_MIGRATIONS` 追加 `ALTER TABLE projects ADD COLUMN exportDirName TEXT NOT NULL DEFAULT ''`。首次导出时按规则生成并写入，之后**即使用户改了产品编码也不再变**（否则老文件全成孤儿）。

生成规则：
1. `sanitizeExportFilenamePart(productCode)`（`lib/final-edit/export-identity.ts:1-6` 已有）+ `-` + `YYYYMMDD`；
2. 结果为空 → 回落项目名 → 再回落 projectId；
3. 目录已存在且 `exportDirName` 属于别的项目 → 追加 `-2`、`-3`；
4. 校验：只允许 `[A-Za-z0-9._\-一-龥]`，不得为 `.`/`..`，不得含分隔符（沿用 `assertSafeProjectId` 同款守卫，`export-naming.ts:24-28`）。
