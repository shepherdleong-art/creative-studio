# 团队单条混剪预览等待：排查与修复

日期：2026-11-13。用户确认入口为连接公司服务器的团队客户端，单条项目的智能混剪预览。

## 已确认的原因

`lib/video-browser-preview.ts` 原来把视频格式探测也放进生产媒体资源闸门。即便原件是可直接播放的 H.264/yuv420p，只要其他渲染任务占满媒体名额，预览请求就会得到 `202 preview_pending`。浏览器收不到视频帧，等待其他任务释放名额后才能恢复。

这个问题可仅通过占用软件资源名额复现，无需人为降低磁盘或网络速度。它证明代码本身存在阻塞，但不能据此断言现场全部卡顿来自同一原因。

原实现也没有复用可直接播放原件的格式探测结果：每次后续 Range 请求可能再次启动 FFprobe。双播放器预加载、切片和拖动会增加请求数。

## 修复

- 将格式探测与重型转码资源分离。冷探测独立限制为最多 2 个；真正需要转码时仍进入既有生产媒体闸门。
- 按绝对路径及文件身份缓存成功探测结果，最多 256 项。文件身份包含设备、文件号、大小、修改时间和状态变更时间；失败不缓存，文件变化重新探测。
- 每个调用者在命中缓存或复用进行中的任务之前独立完成文件授权。

## 复现与结果

运行 `node scripts/mixcut-preview-initial-frame.playwright.test.mjs`。新增用例使用真实 `FinalEditPreview`、H.264 解码、`ensureBrowserPreview` 和 Range 流，独立占用生产媒体名额；按画布实际像素判定出帧，隔离用户数据库及素材。

| 条件 | 结果 |
| --- | --- |
| 修改前，媒体名额被其他任务占用 | 连续 7 个 202，等待 2.5 秒仍没有解码画面，用例失败 |
| 修改后，同一场景 | 约 150 毫秒出画面，用例通过 |

这里的 150 毫秒包含隔离页面打开与点击，来自本机 320×240 合成视频测试；不是生产服务器或真实大视频的性能承诺。

验证通过：

- `node scripts/mixcut-preview-initial-frame.playwright.test.mjs`：首帧、重载恢复、超时重试、全屏降级、服务器繁忙时实际出帧。

## 现场判断边界

用户确认机械盘指服务器的素材盘。团队模式应分别测服务器素材盘读取、网络传输与客户端解码/绘制。本次预览修复只在隔离环境验证，尚未测量生产素材盘性能，也没有部署修改；另一次 LLM 故障的线上只读查询不属于预览性能测量。

另有代码上可见、尚未量化的耗时路径：两个单条预览路由在返回衍生视频时会重复调用 `registerManagedFile`，`registerReadyTeamFile` 在已有登记判断前会同步完整计算文件 SHA-256。大文件、多次 Range 请求可能放大服务器磁盘读取；应以真实衍生物的首字节耗时及读取量衡量其影响。

HEVC 首次转码、原始高分辨率/高码率素材的网络与解码开销，也不由本次修改消除。现场复核应选出一条发生问题的素材，分别比较服务器空闲/渲染中、首次打开/再次打开、连续播放/拖动跳转的请求状态、首字节和首帧耗时，再确定后续优化重点。
