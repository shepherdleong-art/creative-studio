# 版本页面阻塞与服务恢复

## 现场

用户在服务器桌面的工作台浏览版本内容后，其余页面无法刷新。与 11 月 9 日仅观察到客户端无窗口不同，本次从另一台电脑访问登录页、成员页、客户端能力和 readiness 均在 8 秒超时；服务器回环 `127.0.0.1:3300` 同样超时。SCM 显示主服务 Running，但 Node PID 5004 持续消耗 CPU。

当时运行版本为 `team-server-model-pricing-20261110-r1`，发布清单共 37,802 个文件、约 2.18 GiB。`GET /api/team/release-candidates` → `readCurrentTeamReleaseVersion` → `verifyReleaseManifest` 会在网页主线程同步读取、计算整个发布负载的哈希并扫描文本；打开页面即触发这条路径。这个阻塞缺陷已由针对实际调用点的测试确认。现场尝试抓取调用栈因服务进程访问权限失败，没有取得实时调用栈，不能声称已采样证明 PID 5004 当时的确切栈帧。

## 已批准的生产恢复

用户明确批准临时隔离列表和重启，正常停止超过 240 秒后另行明确批准强制结束精确 PID 5004。再次核验该 PID、父服务 PID 7204、当前发布路径，以及唯一子进程为既有 conhost，随后仅结束主应用 PID，再启动原服务。未切换 release 或改动业务数据库。

- Caddy 临时仅拦截 GET `/api/team/release-candidates` 和 GET `/api/team/maintenance/backups`，返回 HTTP 503 JSON 维护提示，防止用户停留页面时立即重复触发重型读取。其他方法及接口不变。
- 原 Caddyfile 保存在服务器 `E:\CreativeStudio\deployment\preflight\preview-hang-20261110\Caddyfile.before`，已验证的临时配置为同目录 `Caddyfile.recovery`，恢复阶段通过 `deployment\service\Caddyfile` 生效；正式修复发布后已撤销临时拦截。
- Windows 服务依赖关系在停止 App 时连带停止 Caddy，恢复时两者均已重新启动。Maintenance、LiteLLM 均 Running。
- 恢复后 HTTPS readiness、登录页、成员页、客户端能力均 HTTP 200，耗时约 0.1–0.2 秒；ready=true、maintenance=false。未登录请求对成员页的检查会重定向到登录页，不能等同于管理员页面内容验收。
- 恢复前后业务状态计数一致：图片任务成功 22 / 取消 1；视频任务成功 16；中央执行成功 113 / 失败 1；成片任务成功 3；批量任务成功 14。SQLite `quick_check=ok`。恢复前无运行或排队的业务任务。临时 inspector 未成功启动，恢复后 9229 无监听。

## 修复方案

当前版本展示改为异步读取发布清单的同一份字节，核对由部署指针保存的 SHA-256 和 releaseId，并校验正式清单及版本格式，然后读取数据库实际 schema 版本；不再遍历程序负载。安装与升级执行的完整校验保持原实现。这个函数只返回版本身份，不能代替安装完整性验证。

新增 `scripts/team-release-current-version.test.ts`，修复前在真实版本查询调用点因为读取发布负载失败，修复后通过；另覆盖清单篡改、指针身份不符、fixture 清单和非法版本。候选、安装、上传边界测试通过。

版本候选与备份列表的完整复核移到 `scripts/team-server/preview.mjs` 独立只读子进程；网页进程通过 IPC 等待结果，不执行完整负载哈希或 SQLite integrity_check。单个网页进程最多同时运行一个校验子进程，最多排队四种请求，相同请求共享进行中的读取。候选列表结果缓存 30 秒，上传成功后清除已完成缓存；备份只合并进行中的读取，不缓存完成结果，确保手动刷新能看到新备份或介质损坏。子进程超时 10 分钟后结束，失败不阻塞后续队列；应用优雅停机主动结束校验子进程。

版本页面前端同一轮刷新未结束时不重叠发起轮询。独立进程入口由服务器打包白名单明确装配，不作为 Next 模块解析。安装、升级与还原执行仍独立完整复核，不使用展示缓存作为执行凭据。

新增 `scripts/team-maintenance-preview.test.ts` 验证忙碌子进程下主线程心跳、12 次并发读取合并、串行队列、异常退出/超时后的恢复和停机；原备份与候选测试增加真实子进程下的有效及篡改负载案例。生产构建、TypeScript、针对修改文件的 ESLint、服务器打包边界测试与 `check:main-path` 通过。

## 服务器隔离验收

候选发布 `team-server-preview-responsive-20261110-r1` 包含 37,805 个文件，完整 manifest SHA-256 为 `9b0d64ba42dff9c6f91cb814a9054e6e53c10c8e2c24b992ad7d32dcae5912eb`。本机与服务器均完成完整负载核验及 Node/SQLite/sharp/FFmpeg/Python/Caddy 原生探针。

在服务器通过 SQLite Online Backup 制作业务数据库副本，在副本创建临时管理员，使用新包实际 HTTP 路由并绑定回环随机端口。测试子进程阻断外网，未调用付费供应商；只读读取生产备份目录。测试结束后停止专用进程树并移除临时副本。

- 同时发起 6 次备份列表与 6 次版本候选列表请求，全部 HTTP 200；31 份实际备份全部 `verified`。当前实际候选目录为空，有效及篡改候选的负载校验由真实子进程回归测试覆盖。
- 备份完整校验约 50.4 秒；版本候选请求在同一串行队列等待备份完成，约 50.5 秒。该约束限制重型校验并发，也意味着同时刷新两个列表时，版本列表会等待备份校验。
- 此期间持续请求健康接口、已登录成员 API、成员管理页面及登录页，共 1,120 次，全部成功；p95=11ms、最大=138ms。四类接口最大耗时分别为 18ms、12ms、109ms、138ms。
- 副本启动后 schema 保持 16，完整性检查通过；既有用量账本、历史错误及项目/任务计数保持不变。线上原服务同时测得 readiness=200/54ms。

完整证据位于 `outputs/05-日志与排查/2026-11-10-preview-responsive-r1/`，包括 `compat-result.json`、`compatibility.json`、`native-probe.json`、构建和阶段日志。
