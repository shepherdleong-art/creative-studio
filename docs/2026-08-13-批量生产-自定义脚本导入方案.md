## 1. 背景与问题

批量生产（Batch Production）的脚本输入目前只有一条路：第 3 步「脚本生成」用 LLM 生成的脚本草稿（`script_drafts`），经 `syncProjectScripts` 同步进 `batch_scripts` 目录，供批次勾选。

用户反馈：**在别处写好的脚本，没有窗口和选项能接入批量生产。** 批量生产第 2 步「脚本」卡片区只渲染项目脚本，空态文案为「暂无可用项目脚本，请先在第 3 步生成并保存脚本」，没有任何导入/粘贴入口。

## 2. 现状梳理

### 2.1 后端能力已就绪，但入口断线

数据模型（schema v9）早已区分两类脚本来源：

| 类型 | `script_draft` | `external` |
|---|---|---|
| 含义 | 第 3 步 AI 生成并保存的项目脚本 | 在别处写好、手工接入的文案 |
| 归属 | 项目级，跨批次复用 | 绑定到某个批次版本，不进项目目录 |

针对 `external` 的域函数已全部实现并有测试（`lib/batch-production/scripts.ts`、`scripts/batch-domain-scripts.test.ts`）：
`createBatchExternalScript` / `updateBatchExternalScript` / `getBatchExternalScript` / `saveExternalScriptAsProjectScript`。

但经全仓检索确认，这些函数**没有任何生产代码调用**（只出现在自身定义处和 `scripts/batch-domain-scripts.test.ts`），三层入口全部缺失：

1. **API 层**：`app/api/batch-production/scripts/` 下只有 `[scriptId]/narration-config`（配音配置），没有「创建/列出/更新外部文案」的路由。
2. **prepare 层**：`prepare.ts:146` 的 `prep.scripts` 只调 `listProjectScripts`（仅 `script_draft`），不返回当前批次版本内的 `external` 文案。
3. **UI 层**：`BatchStepScripts.tsx` 只渲染 `prep.scripts`，无导入/粘贴入口。

结论：`external` 是一条「能力做完、没通电」的半成品。

### 2.2 为什么不走 PRD 原本设计的 `external`

PRD（`docs/superpowers/specs/2026-07-31-batch-mixcut-desktop-prd.md` US 37/38）设计的是批次级 `external` + 「保存为项目文案」显式回写。**这条路目前是坏的，不能直接用。**

`batch-flow.ts:300` 的注释写明「当前版本仍是未确认 draft(无脚本快照)时复用,否则新建」——也就是说确认快照之后，只要再改任何输入（换素材、改份数、改封面设置）就会新建批次版本。而 `external` 通过 `ownerBatchVersionId` 绑死创建它的那个版本，`batch-flow.ts:83` 与 `scripts.ts:392` 都会直接抛「外部文案不属于当前批次版本」。

要走通 `external`，得额外补一套版本间重新挂载逻辑——没人写过，且不在本次范围内。

反过来，项目级这条路有现成先例：`saveExternalScriptAsProjectScript`（`lib/batch-production/scripts.ts:331`）产出的正是本方案要写的同一形状的行（`sourceKind='script_draft'` + `catalogManaged=0` + 任意 `sourceId`），且 `scripts/batch-script-catalog.test.ts:203-217` 已经用测试锁死「独立保存到项目的脚本不得被同步器隐藏」。

因此选方案 B：把自定义脚本写为 `script_draft` 类型的项目脚本。

### 2.3 对 PRD US 38 的正式 supersede

PRD US 38 原文：「作为用户，我希望批次中修改过的外部文案只有在我明确选择『保存为项目文案』后才写回项目。」

本方案的自定义脚本**直接成为项目级脚本**，不经过「显式保存」这一步——这是**有意的产品决策变更**，理由见 §2.2（`external` 的版本绑定使那条路在当前代码下不可用）。

执行时需一并处理，否则后续验收会出现两套相反标准：在 `docs/superpowers/specs/2026-07-31-batch-mixcut-desktop-prd.md` 的 US 38 处补一条 supersede 批注，指向本文档与日期，说明 V1 交付改为项目级导入，`external` + 显式回写留待后续版本。**不要删改 US 38 原文**，只追加批注。

## 3. 决策记录

| 项 | 决定 |
|---|---|
| 导入形态 | 弹窗双 Tab：**单条**（标题 + 正文 + 时长）与**批量粘贴**（一个大文本框按空行切多条，首行作标题，时长统一填） |
| 作用域 | **项目级**，导入一次后该项目所有批次都能勾选 |
| 入口位置 | 批量生产第 2 步「脚本」卡片区标题行 |
| 字段 | 标题/时长手填（时长默认 15s），封面主/副标题从标题自动拆 |
| 后续管理 | 手动脚本卡片带「手动」徽标，支持编辑与删除 |

批量粘贴形态对应 PRD 的 US 37 与 US 43（「作为批量粘贴文案的用户，我希望系统自动从每份文案提取封面标题」）。

## 4. 数据落点设计

复用 `createProjectScript`（`lib/batch-production/scripts.ts:61`），约定如下：

| 字段 | 取值 | 原因 |
|---|---|---|
| `sourceKind` | `'script_draft'` | 复用项目脚本身份，进 `listProjectScripts` |
| `sourceId` | `manual:${uuid}` | 独立命名空间，满足 `UNIQUE(projectId, sourceId)`。**这是承重设计，见 §6.1** |
| `catalogManaged` | `0`（默认，不传） | 手动脚本不被 `syncProjectScripts` 的软删扫描命中 |
| `sourceVersion` | `'1'`，每次编辑 +1 | UI 的 `V{n}` 徽标（`BatchStepScripts.tsx:967`）需要它；且它参与输入身份比对，递增是语义正确的 |
| `coverTitleJson` | `splitCoverTitle(title)` | 不设则封面标题不会被烤进片头，见 §6.2 |
| `shotSetId` | `''` | 手动脚本没有分镜组归属 |
| `contentRevision` | `''` | 仓库里非空 `contentRevision` 的含义是「有上游草稿修订身份」（v12 迁移 `schema.ts:349-353` 拿它当判据）。手动脚本没有上游，留空更诚实 |

**不写 `script_drafts` 表**：那是第 3 步 AI 生成专用（生产代码里唯一写入点是 `lib/script-generation-v3-service.ts:246`），`isUsableMixcutScriptDraft` 强校验 `shotSetId` 非空 + `segments` 非空，手写文案没有这些，硬塞会破坏第 3 步展示/编辑逻辑。手动脚本只写 `batch_scripts`，因此第 3 步 ScriptPanel 看不到它——这是预期行为。

## 5. 已验证的下游安全性

对整条链路（prepare → 快照 → 冻结开跑 → 语义打分 → 口播 → 分配 → 渲染）逐层核实，手动脚本（空 `shotSetId`、空 `contentRevision`、无 `script_drafts` 行、无结构化 segments）能完整走通。

- **`shotSetId` 在整个批量链路里从未被解引用**。全部用法只有三类：字符串相等比较（`batch-flow.ts:203`）、拷贝进快照（`scripts.ts:408`）、展示（`BatchInputSelectionCards.tsx:166`）。没有任何分镜组查找、场景池或素材池以它为键——素材池只按 `batch_asset_pool_items.assetId/analysisId` 组织。
- **语义打分不依赖结构化 segments**。`semantic-match.ts:54-60` 的 `buildBatchSentences` 从扁平 `bodyText` 经 `splitAllocationScriptBody` 断句；矩阵按内容指纹 `(projectId, scriptKey, poolKey)` 落库，与版本无关。
- **分配器同理**。`allocator.ts:492-507` 的候选链最后回落到 `splitBody(bodyText)`，结构化 segments 是遗留分支。
- **口播只要 `bodyText`**。`narration-executor.ts:186-191` 只读 `bodyText` + `narrationConfigJson`；未配音色时按第一个可用供应商回落（`narration-executor.ts:70-94`）并记日志，不阻塞。
- **`contentRevision` 参与比对但恒等**。`batch-flow.ts:204` 确实比对它（v1 方案说「不依赖」不准确），但手动脚本快照与源头两边恒为 `''`，是稳定身份；改动检测由 `title`/`bodyText`/`targetDurationSec`/`coverTitleJson` 的逐字节与 canonical JSON 比对承担（`batch-flow.ts:196-205`）。

## 6. 复核发现的修正

以下 7 点是前两版方案缺失或写错的地方（6.1–6.6 来自第一轮复核，6.5 的补充与 6.7 来自第二轮），实现时必须按本节执行。

### 6.1 `manual:` 前缀是承重设计，不是命名习惯

`syncProjectScripts`（`lib/batch-production/script-catalog.ts:59-70`，注意在 `script-catalog.ts` 而非 v1 方案说的 `scripts.ts`）先后跑两条语句：

```sql
-- 认领：不看 catalogManaged，按 sourceId 是否是真草稿无条件提权
UPDATE batch_scripts SET catalogManaged = 1
WHERE projectId = ? AND sourceKind = 'script_draft' AND ownerBatchVersionId IS NULL
  AND sourceId IN (SELECT id FROM script_drafts WHERE projectId = ?);

-- 软删：只扫 catalogManaged = 1
UPDATE batch_scripts SET sourceAvailable = 0, updatedAt = ?
WHERE projectId = ? AND sourceKind = 'script_draft'
  AND ownerBatchVersionId IS NULL AND catalogManaged = 1;
```

之后只有 `script_drafts` 里的行会被重新置回 `sourceAvailable = 1`。

所以：**一旦手动脚本的 `catalogManaged` 被置 1，下一次 prepare 或开跑就会把它永久杀掉**——它从 `listProjectScripts` 消失，且 `batch-flow.ts:471` 会对已经确认过的批次抛「项目脚本的上游来源已不可用」。`manual:` 前缀保证 `sourceId` 永不落入 `SELECT id FROM script_drafts` 集合，这是唯一的保护。

`syncProjectScripts` 的生产调用点有两处：`prepare.ts:122`（每次加载准备区）与 `batch-flow.ts:434`（开跑冻结事务内）。

### 6.2 编辑不能复用 `updateProjectScript`，也不能用 `createProjectScript` UPSERT

- `updateProjectScript`（`scripts.ts:208-233`）**只能写 `title`/`bodyText`/`sourceVersion`**，碰不到 `coverTitleJson` 和 `targetDurationSec`。而这两个字段都参与 `matchesCurrentInput`（`batch-flow.ts:200,202`），且 `coverTitleJson` 决定 `batch-renderer.ts` 烤进 20 帧片头的封面标题——用它改标题会留下**旧的封面标题拆分**，直接烤进成片。
  （附带：`coverTitleJson` 为 `'{}'` 时 `loadFrozenCoverTitleConfig` 返回 `null`（`cover-title.ts:139-140`），封面标题静默不合成、无任何告警。这也是 §4 必须写 `coverTitleJson` 的原因。）
- 改用 `createProjectScript` 的 UPSERT 路径绕开上述问题也不行：它会把 `narrationConfigJson` 覆写成 `'{}'`（`scripts.ts:81`），**抹掉用户在配音配置里设的音色**。

两条现成路都不能用，必须新写一个更新函数，见 §7.1。

### 6.3 prepare 层不是「零改动」

`PrepareScriptView`（`prepare.ts:20-33`）不携带 `sourceKind`/`sourceId`/`catalogManaged` 中的任何一个，UI 无从区分手动脚本与 AI 同步脚本，「手动」徽标和编辑/删除入口做不出来。必须加字段，见 §7.4。

（`listProjectScripts` 本身确实零改动——它不过滤 `catalogManaged`，手动脚本自动出现。v1 方案这半句是对的。）

### 6.4 PUT / DELETE 必须限定 `manual:` 脚本

不限定的话用户能编辑 AI 同步脚本，而 `prepare.ts:122` 每次加载都跑 `syncProjectScripts` 把该行按草稿内容重新 UPSERT——**用户的改动会被静默回滚**，且没有任何提示。

### 6.5 缺输入校验，其中一条会拖到渲染期才炸

`createProjectScript` 不 trim、不限长、不校验非空；`targetDurationSec` 只有 `Math.max(1, Math.round(...))`，`NaN` 能穿过去。更关键的一条：

```ts
// lib/batch-production/narration.ts:220
if (texts.length === 0) throw new Error('口播正文不能为空');
```

正文切不出句子时，这个错误在**渲染期**才抛，口播任务永久失败，并被 `phase-e.ts:526-528` 的正式发布门禁挡住。必须在导入时就拦下来。

**但只用断句器判断是不够的**（v2 在此写错）。`splitBatchScriptSentences`（`script-sentences.ts:18`）的句界只有 `。！？!?；;` 和换行：

| 输入 | 断句结果 | 说明 |
|---|---|---|
| `'   '` | 0 条 | `:14-15` trim 后为空，挡得住 |
| `'。。。'` | 0 条 | 整体被当作边界，前后都是空串，挡得住 |
| `'，，，'` / `'……'` / `'——'` | **1 条** | 这些字符不在句界集合里，整串成为 tail（`:31-34`），**漏过** |

必须叠加实义字符校验：`countScriptContentCharacters(bodyText) > 0`（`lib/script-duration-policy.ts:19`，按 `/[\p{L}\p{N}]/u` 计数）。两条都过才算合法正文。

### 6.6 冻结卡片会渲染空标签

`BatchFrozenScriptCard`（`BatchInputSelectionCards.tsx:165-168`）无条件渲染 `分镜组 {snapshot.shotSetId}` 与 `修订 {snapshot.contentRevision.slice(0, 8)}`。手动脚本这两项为空串，会渲染成孤零零的「分镜组 」「修订 」。改成非空才渲染。

### 6.7 CRUD 之后不能直接调 `load()`（v3 新增）

`BatchPreparationPanel.tsx:197` 的 `load()` 里有 `setBatches(batchResult.batches)`（`:218`）。而 `loadBatchDetail` 的依赖数组含 `batches`（`:292`），`:499-503` 的 effect 又依赖 `loadBatchDetail`——于是每次 `load()` 都会连锁触发一次批次详情重载：

- 有已确认版本 → `:276-279` 用**上一次快照**覆盖 `selectedScripts` / `selectedAssets`
- 没有版本 → `:259-267` 直接清空 `selectedScripts` / `selectedAssets` / `outputPlans`

两种情况都会把用户当前**尚未确认**的份数、素材、LUT 选择冲掉。所以 v2 §7.5 里的 `onResync={() => void load()}` 不能照搬。

另外 `markInputChanged()`（`:677-681`）只清 `outputPlans` / `inputConfirmed` / `feedback`，**不碰 `selectedScripts`**。删掉一个已勾选的手动脚本后，卡片从列表消失但 ID 还留在 `selectedScripts` 里，确认时仍会随 `scriptSelections` 提交（`:881`）。

编辑已确认脚本的风险更隐蔽：`start/route.ts:37` 先按**旧快照**排队语义打分，`batch-flow.ts:476` 才在冻结时把项目脚本新正文覆盖进快照——会形成「旧正文打分、新正文生产」。强制重新确认（`markInputChanged()`）即可堵住：`inputConfirmed = false` 后必须重新确认，重新确认会因输入变化新建版本，打分随新快照重排。

正确做法见 §7.5。

## 7. 实现清单

### 7.1 领域层 `lib/batch-production/scripts.ts`

新增三个函数，WHERE 条件一律带 `sourceId LIKE 'manual:%' AND sourceKind = 'script_draft' AND ownerBatchVersionId IS NULL`：

```
createManualProjectScript(db, projectId, { title, bodyText, targetDurationSec, now? }): string
updateManualProjectScript(db, projectId, scriptId, { title, bodyText, targetDurationSec, now? }): void
deleteManualProjectScript(db, projectId, scriptId): { mode: 'hard' | 'soft' }
```

- **create**：`sourceId = 'manual:' + randomUUID()`；`coverTitleJson = splitCoverTitle(title)`（`lib/media-core/cover-domain.ts`，与 `script-catalog.ts:31` 同款）；`sourceVersion = '1'`；`shotSetId = ''`；`contentRevision = ''`；`catalogManaged` 不传。委托现有 `createProjectScript`。
- **update**：单条 UPDATE，写 `title` / `bodyText` / `coverTitleJson` / `targetDurationSec` / `sourceVersion + 1` / `updatedAt`，**不碰 `narrationConfigJson`**。WHERE 额外带 `sourceAvailable = 1`（现有 `updateProjectScript` 漏了这条，软删的行仍可被编辑）。
- **delete**：**整体包在 `db.transaction(() => {...}).immediate()` 内**（身份校验 + 引用查询 + 删除/软删）。先查 `SELECT 1 FROM batch_script_snapshots WHERE sourceScriptId = ?`：无引用 → 物理 `DELETE`；有引用 → `sourceAvailable = 0` 软删。`schema.ts:135` 的 `ON DELETE RESTRICT` 决定了没有第三条路。
  不加事务会有 TOCTOU：查询与删除之间若有别的连接建立了快照，外键虽能防止数据损坏，但 `DELETE` 会直接抛错，而不是按设计降级为软删。`createBatchExternalScript`（`scripts.ts:138`）等既有函数都是这个写法。

三个函数的错误一律抛 `BatchDomainError`（见 §7.3），不要抛裸 `Error`。

### 7.2 校验与切分 `lib/batch-production/manual-script-import.ts`（新文件）

纯函数、无 db 依赖，可被 node 测试直接跑，前后端共用：

- `normalizeManualScriptInput({ title, bodyText, targetDurationSec })`
  - `title` trim 后非空，长度 ≤ `MANUAL_SCRIPT_TITLE_MAX = 200`
  - `bodyText` trim 后非空，长度 ≤ `MANUAL_SCRIPT_BODY_MAX = 5000`
  - **两条正文实义校验都要过**（见 §6.5）：
    - `countScriptContentCharacters(bodyText) > 0`（`lib/script-duration-policy.ts:19`）
    - `splitBatchScriptSentences(bodyText).length >= 1`（`lib/batch-production/script-sentences.ts`，与口播/分配同一套断句）
  - `targetDurationSec` 必须是 1–600 的有限整数（先 `Number.isInteger` + `Number.isFinite`，不要依赖 `createProjectScript:80` 的 `Math.max(1, Math.round(NaN))`，`NaN` 能穿过去）
- `splitPastedScripts(text): Array<{ title, bodyText }>`
  - 按空行（`/\n\s*\n/`）切块；每块首行作标题、其余作正文；只有一行的块，该行同时作标题与正文；忽略切完为空的块
- 容量上限（批量粘贴一次可能创建大量库记录，并各自触发语义打分与**付费 TTS** 任务，必须有边界）：
  - `MANUAL_SCRIPT_BATCH_MAX = 50` —— 单次导入最多脚本条数
  - `MANUAL_SCRIPT_PASTE_CHARS_MAX = 100_000` —— 单次粘贴总字符数
  - 前端切分后先本地提示，**服务端必须再校验一次**，不能只信前端

校验放领域层而不是只放路由，测试才能覆盖；路由只做 `typeof` 形状检查。

### 7.3 API 层

照 `app/api/batch-production/batches/route.ts` 与 `scripts/[scriptId]/narration-config/route.ts` 的现成模板：`runtime = 'nodejs'` + `dynamic = 'force-dynamic'`；手写 `typeof` 校验（这棵树里没有 zod）；`await assertBatchApiReady()` 作为 try 内第一句（在廉价 400 之后、任何 `getDb()` 之前）；全部响应带 `BATCH_NO_STORE_HEADERS`；单个 catch 交给 `batchRouteErrorResponse`。

**错误类型必须是 `BatchDomainError`。** `batchRouteErrorResponse` 只认它——`invalid_input` → 400、`not_found` → 404、`conflict` → 409（`lib/batch-production/http-errors.ts:29-41`）；裸 `Error` 会落进 `:48-56` 的兜底，变成**被脱敏的 500**，前端只能看到无用的通用文案。领域层三个函数与 `normalizeManualScriptInput` 的抛错口径：

| 场景 | 错误 |
|---|---|
| 标题/正文/时长不合法，条数或总字符超上限 | `BatchDomainError('invalid_input', '<具体原因>')` |
| 脚本不存在、不属于该项目、或不是 `manual:` 脚本 | `BatchDomainError('not_found', '手动脚本不存在')` |
| 更新目标已被软删（`sourceAvailable = 0`） | `BatchDomainError('conflict', '该脚本已被删除')` |

（注意：既有的 `updateProjectScriptNarrationConfig` 抛的是裸 `Error`，靠路由自己先做 400 校验兜底——不要沿用这个旧写法。）

- **`POST app/api/batch-production/scripts/route.ts`**
  body `{ projectId, scripts: [{ title, bodyText, targetDurationSec }] }`。单条即长度 1 的数组，批量粘贴由前端切好再提交。整批放一个事务，全成功或全失败；显式 404 `project_not_found`；返回 201 + `{ created: [{ id, title }] }`。
- **`PUT / DELETE app/api/batch-production/scripts/[scriptId]/route.ts`**
  `projectId` 走 query string（与同目录的 `narration-config` 一致）。

## 8. 关键约束

### 8.1 删除策略

`batch_script_snapshots.sourceScriptId` 外键 `ON DELETE RESTRICT` 到 `batch_scripts.id`（`schema.ts:135`），已被批次快照引用的手动脚本**不能物理删除**：

- 未被引用 → 物理删
- 已被引用 → 软删（`sourceAvailable = 0`，从列表消失，历史快照保留）

与 `listProjectScripts` 的 `sourceAvailable = 1` 过滤一致。

### 8.2 下游零改动

快照 → 冻结 → 开跑 → 分配 → 渲染 → 导出链路对任意 `script_draft` 一视同仁，全部零改动。本方案不新增数据库迁移——`batch_scripts` 的所有必需列（`coverTitleJson` / `shotSetId` / `contentRevision` v11、`sourceAvailable` / `catalogManaged` v12、`targetDurationSec` v19、`narrationConfigJson` v20）都已发布。

### 8.3 不要动 `sourceKind` 的 CHECK 约束

`batch_scripts.sourceKind CHECK(sourceKind IN ('script_draft', 'external'))`（`schema.ts:113`）。新增第三种 kind 需要整表重建，必须过 `lib/schema-upgrade/` 的备份/锁/审计 gate，成本远高于收益。手动脚本用 `manual:` sourceId 前缀作标记即可。
