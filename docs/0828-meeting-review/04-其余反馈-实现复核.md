## P1 · 剔除会让已有混剪成片失效，且三处报错文案都误导

**优先级最高。** 这是唯一会让用户卡死且看不懂的问题。

### 现象

用户在模块 4 剔除一条视频后，如果这条视频**已经在某个混剪成片的时间轴里**：

| 操作 | 实际报错 | 用户看到的意思 |
|---|---|---|
| 再做任何时间轴编辑 | `source_out_of_range` 「片段超出源视频真实时长」 | 以为是裁剪越界 |
| 点导出 | `video_file_missing` 「视频素材 xxx 缺失」 | 以为文件丢了（其实还在磁盘上） |
| 换封面到该视频的关键帧 | `cover_not_found` 「视频关键帧封面不属于当前分镜组」 | 完全对不上 |

三处都不提「剔除」两个字。

### 定位

`b79a1df` 在这三处 SQL 都加了 `AND ${videoJobNotRejectedSql(db, ...)}`：

| 位置 | 作用 | 失败后抛的错 |
|---|---|---|
| `lib/final-edit/workspace.ts:589-596` `editableVideoSource()` | 编辑命令校验片段来源 | `workspace.ts:1824` `source_out_of_range` |
| `lib/final-edit/workspace.ts:2072` `enqueueRender()` | 导出前解析片段来源 | 同行 `video_file_missing` |
| `lib/final-edit/workspace.ts:1784-1790` | 封面关键帧归属校验 | `workspace.ts:1790` `cover_not_found` |

### 为什么是问题

1. **超出 `03` 的设计意图。** 原文写的是「被剔除的素材**默认不进池**，但可手动恢复」——针对的是素材枚举，不是已经落进时间轴的片段。
2. **UI 完全没有预警。** `issueList()`（`workspace.ts:599`）里没有任何剔除相关的 code，`variant.issues` 也是**持久化**在 `issuesJson` 里的（`workspace.ts:1833`、`868`），只在应用命令时重算。所以剔除之后成片在界面上一直显示「可导出」，点下去才炸。
3. **报错文案与真实原因无关**，用户没有任何线索能想到去模块 4 点「恢复使用」。

对照一下批量侧就做对了：`lib/batch-production/batch-flow.ts:460-463` 抛的是「批次素材池包含已剔除视频，不能启动」，明明白白。

### 两个改法，二选一

**方案 A（推荐，改动小、语义回到 `03` 原意）**
把剔除过滤限制在**素材枚举侧**，不动这三处「解析已提交片段」的查询：

- 保留：`mixcut-context.ts:234/293`、`workspace.ts:468/930`、`prepare.ts:133`、`isBatchAssetEligible` 全家 —— 这些都是「列素材池」，正是该过滤的地方
- 回退：`workspace.ts:589-596`、`:1784-1790`、`:2072` 三处的 `videoJobNotRejectedSql`

代价：已经用上的素材，剔除后当前成片照常导出。这其实符合用户心智（「我剔的是以后别再用它」）。

**方案 B（保留硬约束，但补预警）**
三处过滤保留，另外：

1. 在 `refreshOverlap()`（`workspace.ts:998-1013`）里按同样的模式补一条 issue —— 那个函数已经是「load 时重算跨 variant issue 并写回 `issuesJson`」的现成钩子：
   ```ts
   const issues = variant.issues.filter((issue) =>
     issue.code !== 'high_overlap' && issue.code !== 'duplicate_cover' && issue.code !== 'source_rejected');
   // 对 variant.timeline.clips 里非 external- 前缀的 videoJobId 查 isVideoJobRejected
   // 命中就 push { code: 'source_rejected', severity: 'blocking', message: '片段素材已在模块 4 被剔除，请恢复或替换', targetId: clip.id }
   ```
   `FinalEditIssue.code` 是 `string`（`lib/final-edit/types.ts:49-54`），加新 code 不用改类型。
2. 三处报错文案改成点名剔除，例如 `video_file_missing` → 新 code `source_rejected` +「视频素材 xxx 已被剔除，请在模块 4 恢复或替换该片段」。

**倾向 A。** B 要动 issue 生命周期（持久化 + 重算时机），风险面比这条反馈本身大。除非产品明确要「剔除即全局失效」。

### 验收

1. 剔除一条已在时间轴里的视频后，用户要么能正常导出（A），要么在界面上立刻看到一条说清是「已剔除」的 blocking 提示（B）
2. 无论走哪条，都不再出现「片段超出源视频真实时长」「视频素材 xxx 缺失」这类与真实原因无关的文案
3. 素材池（混剪 STEP 01 / 批量 prepare）仍然默认不显示已剔除素材
4. `final-edit-mixcut-flow.test.ts` 补一个用例：剔除已用素材 → 断言期望行为

## P2 · 二次确认阈值按分镜数算，多行时会漏

### 定位

`components/VideoGenerationPanel.tsx:964`：

```ts
const requiresBulkConfirmation = safeShots.length >= BULK_CONFIRM_THRESHOLD;  // 5
```

但每个分镜最多 10 行（`components/video-bulk-prompt.ts:1` `MAX_ROWS_PER_SHOT = 10`）。

**4 个分镜 × 10 行 = 40 条付费视频，零确认直接提交。**

### 为什么是问题

`03` 字面写的确实是 `safeShots.length >= 阈值`，实现没违背文档。但同一段文档里写着「批量生成是**要花钱的外部调用**，误触成本实打实。不建议（完全去掉）」——按字面实现反而把要保的东西漏了。

### 改法

`plan.totalClips` 就在上面几行现成的（`:940` 的 `planBulkVideoGeneration` 返回值）：

```ts
const requiresBulkConfirmation =
  safeShots.length >= BULK_CONFIRM_THRESHOLD || plan.totalClips >= BULK_CONFIRM_THRESHOLD;
```

顺带可以考虑：`safeShots.length` 里已有任务的分镜其实不会提交，用 `plan.ready.length` 判断比 `safeShots.length` 更贴合「这次真要提交多少」。不过这属于口径优化，不是缺陷。

### 验收

1. 3 个分镜各填 1 行 → 点「全部生成」直接提交，无二次确认
2. 3 个分镜各填 5 行（共 15 条）→ 出现内联二次确认，文案说明将提交 15 条
3. `video-bulk-prompt-ui-contract.test.mjs` 补断言覆盖「分镜少但条数多」

## P3 · `lastOpenedAt` 写在 2 秒轮询路径上

### 定位

- 写入点：`app/api/projects/[id]/route.ts:20` —— `GET` 里无条件 `UPDATE projects SET lastOpenedAt = datetime('now')`
- 调用方：`app/projects/[id]/page.tsx:181` —— 队列运行时 `setInterval(loadProject, 2000)`；另有 `components/ScriptPanel.tsx:450`、`components/VideoGenerationPanel.tsx:254` 也 GET 同一个端点

### 为什么是问题

语义没错（还是「最近打开」），排序结果也对。但生成任务跑着的时候，**每 2 秒一次写事务**打在 SQLite 上，纯属白写；WAL 也会跟着涨。`03` 推荐这个方案时的假设是「取项目详情 = 打开项目」，没料到详情端点同时是轮询端点。

### 改法（任选）

- **节流（改动最小）**：只在 `lastOpenedAt` 为空或早于 N 秒（比如 60s）时才写
  ```sql
  UPDATE projects SET lastOpenedAt = datetime('now')
  WHERE id = ? AND (lastOpenedAt IS NULL OR lastOpenedAt < datetime('now', '-60 seconds'))
  ```
- **换端点**：走 `03` 里的备选方案，新增 `POST /api/projects/[id]/touch`，前端只在 `projects/[id]` 页面挂载时打一次

### 验收

1. 打开项目并让队列跑 5 分钟，`lastOpenedAt` 的更新次数远小于轮询次数
2. 打开老项目再退出，首页仍然排到第一
3. 从未打开过的项目仍按创建时间排

### 补充（不用改，留档）

`createdAt` 与 `lastOpenedAt` 都用 SQLite 的 `datetime('now')`（`lib/db.ts:59`），格式一致，所以 `ORDER BY COALESCE(...)` 的字符串比较是对的，前端 `localeCompare` 也是对的。

但两者都是 **UTC 且不带 `Z`**，`formatCompactTime()`（`app/page.tsx:103`）里 `new Date('2026-08-30 12:46:32')` 会被当本地时间解析 —— 东八区显示会差 8 小时。**这是存量问题**（`createdAt` 一直如此），不是这次引入的，要不要一起修由产品定。

## 两条小的

### S1 · `rejectReason` 前端永远传不进去

`app/api/video-jobs/[id]/route.ts` 的 PATCH 接受 `reason` / `rejectReason` 并落库，但 `components/VideoGenerationPanel.tsx:1137` 的 `handleRejectVideoJob` 只发 `{ action: 'reject' }`。于是 `components/VideoGenerationResults.tsx:207-210` 那段「剔除原因」渲染是**不可达代码**。

二选一：剔除时弹个输入框收原因；或者删掉展示、`rejectReason` 列留作后用。`03` 说的是「可选 rejectReason」，两条都合规，别让它半吊子挂着。

### S2 · GIF 透明通道会变黑

`lib/final-edit/material-import.ts:352` 用 `-pix_fmt yuv420p` 且没垫底色。`03` 的「需要验证的」一节点名提过：「透明通道 GIF：`yuv420p` 会把透明变黑。要不要垫白底？建议垫白底并在 UI 提示」——没做。

改法是在 `-vf` 前加一层白底合成，例如：

```
-f lavfi -i color=white:s=<w>x<h> ... [0:v]fps=24[v];[1][v]overlay=shortest=1,scale=...
```

或者更省事：先探测 GIF 是否含 alpha，只对含 alpha 的走垫底路径，其余保持现状。

**另外记一笔**：`app/api/videos/[...path]/route.ts:26` 的扩展名白名单是 `['.mp4','.mov','.webm']`，不含 `.avi`。所以 `.avi` 外部素材走不通这个预览端点。混剪外部素材走的是 `external-assets/.../media` 路径，模块 4 产物都是 mp4，**当前不影响**，但以后要统一预览端点时会撞上。
