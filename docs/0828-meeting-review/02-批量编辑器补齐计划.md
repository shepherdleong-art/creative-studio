# 02 · 批量「调整片段」对齐单条「预览调整」

> 覆盖反馈：#1（封面算进片段使用、封面没得手动更换、整体体验）  
> 产品诉求原话：「直接用单条精准混剪的预览调整不就好了吗？」「操作起来更顺手，而且可以减少使用学习的摩擦」  
> 决策：**照做。** 口播变速本轮不做（见 G 项）

---

## 1. 先澄清一个前提

**批量的编辑器本来就是照着单条抄的。** 见 `docs/2026-08-24-batch-output-timeline-edit-plan.md` §2「可复用的既有设施」：

- `components/batch-production/BatchTimeline.tsx:9` 与 `BatchClipTrimEditor.tsx:6` 直接 `import styles from '../mixcut/mixcut-content.module.css'`
- 共用 `components/final-edit/timeline-edit.ts`（拖拽换算）与 `preview-playback.ts`（视频 slot 调度、seek 合流、逐帧绘制）
- `BatchTimeline.tsx:38`：`// 伪波形组件：原样复制自 components/mixcut/MixcutTimeline.tsx（那边没有 export）。`
- 方案原文：「`MixcutTimeline.tsx` 的交互范式——**照抄模式，不改它的文件**」

所以本文档不是「要不要照搬」，而是**把抄了一半的部分抄完**：外壳与画面轨已对齐，缺的是右侧检查器与字幕轨。

## 2. 唯一的架构约束（不阻止照搬）

来自 `AGENTS.md` 与 `docs/reference/批量生产模块.md`：

> `lib/batch-production/` **只从 `media-core/` 导入，绝不从 `final-edit/` 导入**。  
> UI 层共享是允许的：`BatchTimelinePreview.tsx` 复用 `components/final-edit/preview-playback.ts` 纯函数即为先例。

**要复用什么，就把它提到 `lib/media-core/`。** 该目录已沉淀 `cover-framing` / `cover-domain` / `cover-title-svg` / `cover-title-presets` / `cover-types` / `render-contract` / `tts-speed` / `scene-detect` / `export-identity` / `storage-path`。

组件层不受此约束，但注意方向：`FinalEditPreview` 的签名焊死在 `FinalEditGroupView / FinalEditVariantView / FinalEditAssetView` 上，批量没有这些类型；而 `BatchTimelinePreview` 收的是纯原始形状（`clips[] / assetsById / coverUrl / subtitleCues / narrationUrl / bgm`）。**后者是更好的抽象**，统一时应让单条向批量靠，不是反过来。

## 3. 一个必须记住的产品风险

> **长得越像，行为差异越伤人。**

批量的字幕轨目前只读。如果外观照搬到 100% 而行为不齐，用户看到字幕块会去双击改字（因为单条能改），改不动时不会理解成「批量模式的限制」，只会认为**功能坏了**。

因此本计划的红线是：**每一项要么把行为补齐，要么把禁用态显式画出来并写明原因**，不允许出现「长得一样但点不动、也没解释」的控件。


## G · 口播变速 —— 本轮不做

### 为什么不做（留档，避免以后重问）

**两边是不同机制，不是缺个入口。**

| | 单条混剪 | 批量 |
|---|---|---|
| 参数 | `playbackRate`（0.8x / 1.0x / 1.2x / 1.5x） | `speed` |
| 作用点 | **渲染期 atempo**，整体缩放时间轴 | **给 TTS 供应商的语速参数** |
| 存储位置 | group scope，可随时改 | 脚本快照 `narrationConfigJson`，批次版本冻结 |
| 代码锚点 | `set_narration_playback_rate`（`lib/final-edit/workspace.ts:274`） | `lib/batch-production/narration-executor.ts:209` |

批量里改变速会改变口播时长，而画面 clips 是**按原时长铺好的**（allocator 按句段估算时长分配区间）。改速度就得重新分配这一条的画面——那不是「调一个滑杆」，是重跑分配。

### UI 上怎么处理

按第 3 节的红线，**不能留一个点不动的控件**。在编辑器右侧对应位置放禁用态卡片：

> **口播语速**  
> 批量模式下语速属于脚本设置，在「脚本与口播」步骤统一调整。  
> 〔跳转到脚本步骤〕

### 如果以后要做

前置条件是：单条重分配（`reallocate`）能接受一个「目标口播时长」入参并重铺画面。届时口播变速 = 改 speed → 重跑该条 TTS → 重分配 → 重渲染，是一条完整链路而不是一个滑杆。

## 6. 第二阶段：统一重构（不要提前做）

做完 A–F 之后，两边的差异清单就**收敛为口播变速一条**。那时候把编辑器抽成一个共享组件是机械劳动，风险接近零。

目标形状：

```
<TimelineEditor>
  props: clips[] / subtitleCues[] / assets[] / music / cover / narration
         + capabilities: { editSubtitles, editMusicParams, narrationRate, ... }
         + commands: { onTrim, onSplit, onReplace, onSetCover, onSetSubtitleText, ... }
```

- mixcut 写一层 `FinalEditGroupView → props` 的适配
- batch 写一层 `arrangement → props` 的适配
- `capabilities` 里为 false 的能力渲染成**带原因的禁用态**，不是消失

**顺序不能反。** 现在就重构的话还不知道批量需要哪些 capability flag，一定会抽错抽象。

**方向是让单条学批量**：`BatchTimelinePreview` 收的已经是纯原始形状，`FinalEditPreview` 焊死在领域模型上，需要改的是后者。
