## #1 ·「需要再点一下渲染」— 表达问题

### 同事原话

> 当使用调整片段后，需要再点一下渲染，才能将修改落实。这太笨了！

### 结论：功能其实已经有了

`components/batch-production/BatchOutputEditor.tsx:108-122` 已经在卸载时自动提交重渲染：

```tsx
useEffect(() => {
  // 退出这一轮调整(关闭弹窗/换成片/切步骤)时才把欠着的重渲染一次性提交。
  const url = `.../clips?projectId=...`;
  return () => {
    if (!pendingRenderRef.current) return;
    pendingRenderRef.current = false;
    void fetch(url, { method: 'POST', body: JSON.stringify({ type: 'commit_render' }), keepalive: true })
      .then(() => onChangedRef.current?.()).catch(() => undefined);
  };
}, [projectId, batchId, planId]);
```

这是 `12b16a3`（2026-08-25「片段调整期不排重渲染，退出这一轮时一次性提交」）引入的。

**让用户误解的是常驻的警告文案**（`:287-296`）：

```tsx
{pendingRender && (
  <span className="... text-warn">
    修改尚未渲染成成片
    <button ...>立即重新渲染</button>
```

黄色警告 + 一个按钮 = 用户读作「你必须点这个」。

### 改动清单

1. 文案改为陈述自动行为：`修改已保存，退出本轮调整后会自动重新渲染`
2. 颜色从 `text-warn` 降为 `text-ink-secondary`（这不是警告，是状态）
3. 按钮保留但改文案为 `立即渲染`，样式降为次要

### 注意

**「导出的还是原来的素材」那半句是另一回事**，是真的正确性缺陷 —— 见 [01 文档 BUG-1](01-导出与封面-正确性缺陷.md#bug-1--片段编辑后可能导出编辑前的成片)。只改文案不能解决那个。

### 验收

编辑片段后退出，不点任何按钮，渲染仍然自动排队并完成。

## #2 · 视频分析只抽一帧

### 同事原话

> 批量混剪那里的模型分析，我没记错的话应该是 Luna 抽取一帧来分析视频内容……这样对视频素材的理解是否到位？能不能直接将整个视频丢进去让 ai 理解？

### 结论：属实，而且比描述更极端

`lib/media-core/adapters/video-analysis.ts:29-38`

```ts
const detectedScenes = await detectVideoScenes({ filePath, durationUs, signal });
for (let index = 0; index < detectedScenes.length; index += 1) {
  const scene = detectedScenes[index];
  const timeSec = ... (scene.startUs + (scene.endUs - scene.startUs) * 0.3) / 1_000_000;
  await runFfmpeg(['-ss', ..., '-frames:v', '1', ...]);   // 每个场景抽 1 帧
}
```

流程是：ffmpeg 场景切分（`lib/media-core/scene-detect.ts`，阈值 0.20、最短 0.3s）→ **每个场景在 30% 位置抽 1 帧** → 一次性发给视觉模型。

**关键**：`detectVideoScenes` 在没检测到硬切时返回单个区间：

```ts
resolve(ranges.length ? ranges : [{ startUs: 0, endUs: input.durationUs }]);
```

AI 生成的 5 秒素材通常没有硬切 → **整条视频真的只有 1 帧**。同事记得没错。

### 改造要点

**卡点在 `completeJson` 只收图片**：`lib/script-providers/index.ts:118`

```ts
images?: Array<{ mimeType: string; imageBase64: string }>;
```

要支持整段视频需要：

1. `ChatImagePart` 扩成媒体 part，支持 `video/mp4` 等
2. `lib/script-providers/gemini.ts` 处理视频输入（Gemini 原生支持 `inline_data` + File API）
3. `lib/cos-media.ts` 的中转路径要能传视频（`tryUploadBufferToCosAndSign` 目前用于抽帧图片，`:340` 的注释写的是「内存图片」）
4. `lib/media-core/adapters/video-analysis-prompt.ts` 的 prompt 要重写（现在的措辞明确说「这些图片按顺序分别来自同一视频的场景区间…每个场景在 30% 位置抽一帧」）

### 建议：先做一次技术验证，再决定

**验证项（不改生产代码）**：

- 目标供应商是哪个？公司 Luna 那条线是否支持视频输入？（`docs/reference/供应商与队列.md` + 实测）
- 5 秒 720p mp4 的 token 消耗 vs 现在 1 帧的消耗，差多少倍
- 分析质量是否真的提升（同一批素材，两种方式各跑一遍，人工比对 `summary` / `sellingPoints` / `usableRanges`）
- 耗时变化（影响批量准备阶段的整体时长）

**折中方案（如果整段视频不可行或太贵）**：把「每场景 1 帧」改成「每场景 N 帧」或「按固定间隔均匀抽帧」。改动只在 `video-analysis.ts:31-38` 的循环里，`completeJson` 不用动，成本可控。这条几乎零风险，可以先上。

### 验收

先出验证结论，再定方案。不建议直接开工改 `completeJson`。

## #3 · 项目列表没有约束框

### 同事原话

> 进来工作台这里，可以看到很多项目以及封面，但没有一个约束的框，会导致下拉条随着项目增多而无限增长。

### 结论：属实

`app/page.tsx`：

- 表格视图 `:364-447`：`<div className="card overflow-hidden"><div className="overflow-x-auto">` —— 只有横向滚动，无高度约束
- 卡片视图 `:453`：`<div className="grid grid-cols-2 gap-x-4 gap-y-6 sm:grid-cols-3 lg:grid-cols-4">` —— 无约束

页面随项目数无限增长。

### 三个选项

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 容器内滚动**（推荐） | 改动最小，一个 `max-h` + `overflow-y-auto` | 长列表滚动性能一般 |
| B. 分页 | 性能好 | 要加分页控件与状态，找项目要翻页 |
| C. 虚拟列表 | 性能最好 | 引入依赖或手写，与现有卡片布局不好配 |

**建议 A**：首页已经有搜索和表格视图（memory 记录 08-16 已做完），配合搜索，内滚足够。

### 改动清单

1. 列表容器加 `max-h-[calc(100vh-<头部高度>)] overflow-y-auto`，具体数值按现有布局量
2. 滚动容器加 `overscroll-contain`，避免滚到底带动页面
3. 卡片/表格两个分支都要加
4. 暗色模式无需额外处理（走既有设计令牌）

### 验收

50+ 项目时页面本身不产生纵向滚动条，列表在自己的容器里滚。

## #7 · 视频生成阶段的删除 / 打标

### 同事原话

> 视频生成模块，有时候我们会生成一些不满意的素材。我希望可以增加一个删除或者打标的方式，提前做剔除，这样就方便我在混剪版块时对素材的了解，并且可以第一时间就剔除不需要的内容。

### 结论：属实，需要新增能力

- `video_jobs` 表（`lib/db.ts:276-306`）**没有任何剔除/打标字段**
- `app/api/video-jobs/[id]/route.ts:25-55` 的 PATCH **只支持 `action: 'cancel'`**，且只作用于 `pending / running / needs_check` —— 是取消在途任务，不是标记已完成的成品

下游确实有排除概念（`batch_asset_exclusions`，见 `lib/batch-production/output-arrangement.ts:356`），但那是**素材入池之后**才生效，位置太晚，且只作用于单个批次版本。

### 设计要点

**打标 vs 删除**：建议**打标为主，删除为辅**。

- 视频文件是花钱生成的，直接删不可逆
- 打标可撤销，且能表达「这条不好但先留着」
- 参照 `components/VideoGenerationPanel.tsx:384-386` 已有的处理哲学：删自由素材工位时明确说明「视频文件保留在本地磁盘上，不会被删除」

**建议的状态**：一个 `rejected` 布尔 + 可选 `rejectReason` 文本，而不是一堆标签。先做最小可用。

### 改动清单

1. **迁移**（`CORE_DB_MIGRATIONS` 末尾追加）：
   ```ts
   `ALTER TABLE video_jobs ADD COLUMN rejectedAt TEXT`,
   `ALTER TABLE video_jobs ADD COLUMN rejectReason TEXT`,
   ```
   用 `rejectedAt` 而不是布尔，顺便得到「什么时候剔的」。
2. **API**：`app/api/video-jobs/[id]/route.ts` 的 PATCH 增加 `action: 'reject' | 'unreject'`
   - 只允许作用于 `status = 'succeeded'` 的任务
   - `reject` 写 `rejectedAt = datetime('now')` + 可选 reason
   - `unreject` 置空
3. **下游枚举要认这个字段**（这一步最容易漏）：
   - `lib/final-edit/workspace.ts:466` 附近的素材查询 —— 混剪素材池
   - `lib/batch-production/media-catalog.ts` —— 批量素材目录（它「只信 `video_jobs` 权威记录」，见 `docs/reference/批量生产模块.md`）
   - `app/api/projects/[id]/creative-package/route.ts` —— ZIP 导出，**决定是否排除被剔除的视频**（建议：仍然导出，但在 manifest 里标记）
   
   **策略建议**：被剔除的素材**默认不进池，但可手动恢复**，而不是彻底隐藏。UI 上给个「显示已剔除（N）」的开关。
4. **UI**：`components/VideoGenerationPanel.tsx` 的视频结果卡加剔除按钮 + 已剔除的视觉标识

### 与 #8 的关系

**建议 #7 和 #8 一起做。** 同事的诉求本质是同一件事：**素材可控性** —— 「我要能看清它，然后决定要不要它」。#8 解决「看清」，#7 解决「决定」。分开做会让 UI 改两次。

### 验收

1. 已生成的视频可标记剔除，可撤销
2. 被剔除的素材默认不出现在混剪/批量素材池
3. 可通过开关查看并恢复已剔除素材
4. 视频文件不被物理删除
5. 剔除状态在项目内一致（混剪与批量看到同一个结果）

## #9 · GIF 进混剪素材池

### 同事原话

> 混剪素材有一个自定义上传的选项，我在想，加入 gif，让 gif 也进入混剪素材池里面。

### 结论：需要新增，但**不要直接放行扩展名**

**卡点**：`lib/video-file-format.ts:4-9`

```ts
export const SUPPORTED_VIDEO_MIME_BY_EXTENSION: Readonly<Record<string, string>> = {
  '.mp4': 'video/mp4',
  '.mov': 'video/quicktime',
  '.avi': 'video/x-msvideo',
  '.webm': 'video/webm',
};
```

这是唯一的校验入口，被三处引用：`lib/final-edit/material-import.ts:153,222`、`lib/batch-production/media-catalog.ts:136`、`lib/batch-production/project-asset-media.ts:88`。

### 为什么不建议直接加 `.gif`

GIF 与整条流水线的假设冲突：

| 假设 | GIF 的情况 |
|---|---|
| 24fps 固定帧率（`media-core/render-contract.ts`） | 可变帧延迟，每帧独立 delay |
| 有音轨（口播/BGM 混音链路） | 无音轨 |
| ffprobe 容器校验（`isDetectedVideoContainerCompatible`） | format 是 `gif`，需要新分支 |
| 代理缓存 / LUT 色彩链（批量侧） | 调色板色彩模型，与 SDR filter 链假设不同 |
| 场景检测 + 抽帧分析 | 短循环动画，场景切分基本无意义 |

放行扩展名会让这些问题一路捅到渲染层，且分散在多个模块里。

### 推荐方案：导入时转码

**在 `material-import.ts` 的导入路径上加一步 GIF → mp4 转码，落库的仍然是 mp4。下游零改动。**

1. 前端 `accept` 加 `.gif`（`components/mixcut/MaterialStep.tsx:129` 与 `:25` 的 `SUPPORTED_VIDEO_EXTENSIONS`）
2. `lib/final-edit/material-import.ts` 检测到 `.gif` 时先转码：
   ```
   ffmpeg -i in.gif -movflags +faststart -pix_fmt yuv420p
          -vf "fps=24,scale=trunc(iw/2)*2:trunc(ih/2)*2"
          -c:v libx264 -crf 20 -an out.mp4
   ```
   - `fps=24` 对齐 `FINAL_EDIT_FPS`
   - `scale=trunc(iw/2)*2:...` 保证偶数尺寸（yuv420p 要求）
   - `-an` 明确无音轨
3. 转码用 `lib/ffmpeg.ts` 的 `runFfmpeg`，**必须传 `signal`**（遵守停机信号契约，见 `AGENTS.md`）与合理 `timeoutMs`
4. 转码产物按既有规则落 storage，指纹按**转码后**文件算（保持「素材身份是内容指纹」不变）
5. **循环时长决策**：GIF 通常 1~3 秒。要不要自动循环到最短可用时长？建议 **MVP 不循环**，原样转码；不够长时靠既有的 `videoFreezeTail`（末帧延长）机制兜。如果实测体验差再加。

### 需要验证的

- 极大 GIF（几十 MB、上千帧）的转码耗时与内存
- 透明通道 GIF：`yuv420p` 会把透明变黑。要不要垫白底？建议垫白底并在 UI 提示

### 验收

1. GIF 可拖入混剪素材池，转码后作为普通 mp4 参与混剪
2. 转码失败给出可行动错误，不产生半成品文件
3. `SUPPORTED_VIDEO_MIME_BY_EXTENSION` 保持不变（不放行 `.gif` 进入下游校验）
4. 转码过程可被应用停机中断，不留孤儿进程
