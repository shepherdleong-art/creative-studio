## BUG-1 · 片段编辑后可能导出「编辑前」的成片

### 严重度

**高。** 同事描述的是「要多点一次渲染，太笨了」，实际后果比这严重：**正式导出可以发出一条内容与用户所见不一致的成片，且所有既有校验都会放行。**

### 复现路径

1. 在「检查成片」里点「调整片段」，做任意**视觉变化**编辑（变长修剪 / 替换 / 删除 / 插入）
2. 退出这一轮调整（关弹窗 / 换成片 / 切步骤）→ 前端自动提交重渲染，任务进队列
3. 渲染实测需 4~7 秒。**在它完成之前**，回到检查页给这条成片点「通过」
4. 立刻进入「导出成片」，勾选并正式导出
5. **导出的是第 1 步之前那次渲染的产物**

### 机制（三处代码共同造成）

**① 片段编辑是就地改，不建新版本**

`lib/batch-production/output-arrangement.ts:623-645`

```ts
if (visualChanged) {
  rippleClips(clips);
  arrangement.clips = clips;
  const nextEditRevision = editRevision + 1;
  arrangement.editRevision = nextEditRevision;
  delete arrangement.review;              // 画面变了 → 清审核态
  db.prepare(`UPDATE batch_output_versions SET arrangementJson = ? WHERE id = ?`)
    .run(JSON.stringify(arrangement), outputVersionId);   // ← 同一个 outputVersionId
}
```

同一个 `outputVersionId` 下，编辑前后各存在一次渲染任务，靠 `editRevision` 区分（`phase-e.ts:42-49` 的 requestKey 含 `edit:${editRevision}`）。

**② 审核接口对「有渲染在排队」零门禁**

`lib/batch-production/review.ts:78-88` —— `setBatchPlanReviews` 直接 `json_set` 写入 `$.review`，不检查该版本是否有 pending/running 的 render 任务。

**③ 导出选候选时不看 `editRevision`**

`lib/batch-production/phase-e.ts:522-556`

```sql
JOIN batch_tasks t ON ... AND t.targetId = p.currentVersionId AND t.status = 'succeeded'
...
ORDER BY t.createdAt DESC, t.id DESC
LIMIT 1
```

取该版本**最新一条已成功**的渲染。谱系校验查了 `projectId / batchId / batchVersionId / planId / outputVersionId / planSeq / outputVersionNumber` —— **唯独没有 `editRevision`**。新渲染还没成功时，编辑前那条旧渲染满足全部条件，被当作合法候选发布。

> `editRevision` 已经进了渲染任务的 requestKey，却没有进渲染**结果**的谱系身份。这是这个 bug 的根。

### 为什么现有防线挡不住

| 现有防线 | 为什么失效 |
|---|---|
| 编辑清 `$.review`，必须重新审核 | 用户可以在渲染完成前就点「通过」，审核接口不拦 |
| `hasNewerCandidate`（`batch-workspace.ts:474`） | 比的是 `outputVersionId`，同版本不同 editRevision 一律相等 |
| 发布前指纹比对（`phase-e.ts:604`） | 比的是「发布产物 vs 渲染候选」，两边都是旧的，一致通过 |
| `checkFormalExportPreflight` | 校验原片可用性与谱系，不校验渲染新鲜度 |

### 修复方案

**推荐：把 `editRevision` 纳入渲染结果谱系（治本）**

1. 渲染执行器在写 `resultJson` 时带上当次的 `editRevision`
   - 位置：`lib/batch-production/batch-renderer.ts` 的 `BatchRenderResult` + `lib/batch-production/executors.ts` 的 render executor
   - `editRevision` 从渲染时读取的 `arrangementJson` 里取（与 requestKey 同源，保证一致）
2. `phase-e.ts` 的 `parseRenderResult` 增加 `editRevision` 字段解析
3. `publishBatchOutputPlan` 的谱系校验增加一条：
   ```ts
   if (render.editRevision !== currentEditRevision) {
     throw new BatchDomainError('conflict', '成片已被调整过，请等待重新渲染完成后再导出');
   }
   ```
   其中 `currentEditRevision` 从 `row.arrangementJson` 的 `$.editRevision` 读（缺省视为 0）
4. **旧数据兼容**：历史 `resultJson` 没有 `editRevision`。规则定为「结果缺字段 且 当前 arrangement 的 editRevision 为 0」→ 视为一致放行；「结果缺字段 但 当前 editRevision > 0」→ 拒绝并要求重渲染。这样不会卡住从未编辑过的历史批次。

**配套（治标，同时做）：审核与导出侧提示**

5. `setBatchPlanReviews` 在目标版本存在未完成 render 任务时，仍允许写入审核态，但在返回值里带 `pendingRender: true`；`BatchStepReview` 据此把「通过」按钮旁标注「渲染中，完成后才可导出」
6. `BatchStepExport` 的可勾选条件增加「渲染新鲜」：`workspace.cards` 里补一个 `renderStale: boolean`（由 `batch-workspace.ts` 比对当前 editRevision 与最新成功渲染的 editRevision 得出），stale 的成片不可勾选并显示原因

**顺带清理 #1 的「表达问题」**

同事说「需要再点一下渲染，太笨了」——**自动提交其实已经做了**（`components/batch-production/BatchOutputEditor.tsx:108-122`，卸载时 `commit_render`，`12b16a3` 引入）。让用户误解的是常驻的黄字提示：

`components/batch-production/BatchOutputEditor.tsx:287-296`
```tsx
{pendingRender && (
  <span className="... text-warn">
    修改尚未渲染成成片
    <button ...>立即重新渲染</button>
```

建议改成陈述自动行为，把手动按钮降级为次要入口：
- 文案：`修改已保存，退出本轮调整后会自动重新渲染`
- 按钮：`立即渲染`（保留，但不再是唯一出路的暗示）

### 验收标准

1. 编辑片段 → 立刻审核通过 → 立刻导出：**被明确拒绝**，错误信息指向「等待重新渲染」
2. 编辑片段 → 等渲染完成 → 审核通过 → 导出：成功，且产物内容与编辑后一致
3. 从未编辑过的历史批次（`editRevision` 缺失）导出：不受影响，正常通过
4. 导出页对渲染未完成的成片不可勾选，并显示原因
5. 编辑器不再暗示「必须手动点渲染」

### 测试锚点

新增 `scripts/batch-output-export-freshness.test.ts`（`:memory:` SQLite）：

- 造一条 plan，写入 editRevision=0 的成功渲染 + approved
- 断言：可导出
- 就地把 arrangement 改成 editRevision=1（模拟片段编辑）
- 断言：导出抛 `conflict`，且错误信息含「重新渲染」
- 写入 editRevision=1 的成功渲染
- 断言：恢复可导出
- 单独一例：`resultJson` 无 `editRevision` 且 arrangement editRevision=0 → 放行（旧数据兼容）

相关既有测试：`scripts/batch-*.test.ts`，改动 `phase-e.ts` 后一并跑。

## BUG-2 · 封面抽帧时间滑杆时有时无

### 严重度

**中。** 不产出错误内容，但让「换封面帧」这个功能随机消失，用户无法预期。**它不是偶发，是前端与渲染器契约相反。**

### 现象

进入某条成片的预览，有时能看到「封面抽帧时间」滑杆，有时整块不见。

### 机制

**前端：封面素材不在时间线内 → 藏起来**

`lib/batch-production/batch-workspace.ts:148-173`

```ts
function arrangementCoverRange(value: unknown): BatchCoverRangeView | null {
  ...
  } else if (cover && typeof cover.assetId === 'string') {
    selected = clips.find((clip) => clip.assetId === cover.assetId) ?? null;
    if (!selected) return null;   // ← 封面素材不在时间线内:无法从 arrangement 推导原片时长
  }
```

`components/batch-production/BatchStepReview.tsx:483` —— `{modalCard.coverRange && (...)}`，`null` 就整块不渲染。

**渲染器：封面素材本来就可以不在时间线内**

`lib/batch-production/batch-renderer.ts:456-458`

```ts
const coverAssetId = coverInput?.assetId ?? selectedCoverClip?.assetId ?? firstClip.assetId;
// An explicit cover asset/time is an independent frozen source-frame
// decision. It may legally point outside every timeline clip while still
// belonging to the frozen pool, so do not inherit the first clip's range.
```

后面 `:474-486` 会直接从 `batch_assets` + `batch_asset_pool_items` 解析原片、套冻结 LUT、抽帧——**完全不需要该素材出现在时间线里**。

**分配器还主动制造这个情况**

`lib/batch-production/allocator.ts:1226-1231`

```ts
.sort((a, b) => {
  const aUsed = usedOpeningAssets.has(a.assetId) ? 1 : 0;
  const bUsed = usedOpeningAssets.has(b.assetId) ? 1 : 0;
  return aUsed - bUsed || a.assetId.localeCompare(b.assetId);
});
```

升序排列 → **优先选没被用作开场的素材**当封面。也就是说分配器倾向于让封面落在时间线之外，而前端恰好在这种情况下把控件藏掉。两边逻辑互相拆台。

### 修复方案

**`arrangementCoverRange` 不再依赖 clips 推导范围，改为按封面素材自身时长返回。**

1. `BatchCoverRangeView` 增加 `assetId: string`（当前只有 start/end/current）
2. `arrangementCoverRange` 改为需要素材时长信息。两个选项：
   - **推荐**：在 `batch-workspace.ts` 里对 `arrangement.cover.assetId` 查一次 `batch_asset_pool_items`/`batch_assets` 的 `mediaJson.durationUs`，用 `[0, durationUs)` 作为范围。同一批次内可先建 assetId→durationUs 的 Map 复用，避免 N 次查询
   - 备选：把 `durationUs` 写进 arrangement 的 cover 字段（需要动 allocator 与迁移，不推荐）
3. 封面素材落在时间线内时，**仍然给全片时长范围**，不再限制在该 clip 的 source 区间内——这与渲染器的契约一致（注释明说封面是独立决定）
4. 素材不在冻结池 / 查不到时长时才返回 `null`，UI 显示「封面素材不可用」而不是静默消失

### 与 02 的关系

本条修完后，「封面抽帧时间」滑杆恒定可见。**「更换封面素材」是 02 文档的 A 项**，两者共用 `arrangement.cover` 结构，建议同一个改动周期内完成，避免 `BatchCoverRangeView` 改两次。

### 验收标准

1. 任意一条成片，无论封面素材是否出现在时间线里，滑杆都可见
2. 滑杆范围 = 封面素材完整时长，不再是「第一镜头原片区间」
3. 拖动并应用后，重渲染产出的封面与所选时间点一致，且标题仍在（`batch-renderer.ts:1007` 的重放逻辑不受影响）
4. 封面素材被移出冻结池的异常情况，显示明确文案而非空白

### 测试锚点

扩展既有 `scripts/` 下批量工作区相关测试：

- 造 arrangement：`cover.assetId` = 一条**不在 clips 里**的池内素材
- 断言：`getBatchWorkspace` 返回的 `coverRange !== null`，且 `endUs` 等于该素材时长
- 造 arrangement：`cover.assetId` = 池外素材
- 断言：`coverRange === null`
