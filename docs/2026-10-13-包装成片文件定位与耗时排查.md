# 包装成片文件定位与耗时排查

## 文件定位

同一请求地址 `http://127.0.0.1:2464`，携带该地址的 Origin 时返回
`403 cross_origin_reveal_denied`，改为 `http://localhost:2464` 后通过来源检查。
Next 构造的 `request.url` 使用了内部 hostname，不能用它的 host 代替浏览器实际请求的 Host。

另外，联动导出的 render 任务只先发布封面，视频由其关联的 packaging 任务发布。
ExportStep 原先始终读取 render 任务的发布路径和任务 ID：无路径时退回 HTTP，
即使来源检查通过，也会得到“渲染任务尚未写回已发布成片”。

修正：

- 单条与批量文件定位共用 `isSameOriginRequest`，按实际 Host、协议和端口核对 Origin；不信任转发头，不把不同本机域名/端口一概放行，非法来源返回拒绝。
- ExportStep 在关联 ID 匹配且包装成功时使用 packaging 任务的发布路径和 ID，覆盖 Electron IPC 与 HTTP 两条路径；普通导出继续使用 render 任务。
- 保留工作台 action 标记、发布状态与受控存储路径检查。

验证：`node scripts/final-edit-export-reveal.test.ts` 在修正前依次复现来源误拒和选错任务，修正后通过。
该测试执行实际路由及点击回调，替换数据库与系统文件管理器边界；覆盖不同协议/端口/来源、非法 Origin、缺标记、普通导出及旧包装任务残留。
`tsc --noEmit --incremental false` 通过；改动文件 ESLint 无错误，ExportStep 保留已有 img 提示。
当前运行的 standalone 未重启，真实桌面窗口需下次启动重建后使用修复。

## 包装耗时

只读查询最近成功任务：视频长 24.792 秒，1080×1440、24fps、综艺撕纸模板。
render 任务耗时 5.429 秒；packaging 任务耗时 66.408 秒，领取前几乎没有排队。

使用相同原片、模板和冻结配置，在独立 outputs 目录复测包装管线：

| 阶段 | 实测耗时 |
| --- | ---: |
| 探针、素材准备、取色 | 约 1.2 秒 |
| HyperFrames 透明动画层 | 32.8 秒 |
| FFmpeg 叠加、产物复制 | 约 3.5 秒 |
| 管线总计 | 约 37.5 秒 |

复测不包含应用侧最终封面合成、校验和发布，因此不能把 37.5 秒与原任务的 66.4 秒直接视为提速结果。
原任务没有分阶段记录或同期资源监控，无法认定差值由 Kimicode、冷启动或资源竞争中的某一个因素造成。
这次未改变包装渲染实现；瓶颈证据指向透明动画层。仅远程 API 请求通常不会承担本机动画渲染，但同时下载/处理素材会竞争 CPU、内存或磁盘。

诊断脚本与测量输出保留在忽略目录 `outputs/packaging-timing-20261013/`，不改写原项目成片。

## 后续性能补测

同日继续使用上述冻结输入，保存 HyperFrames 内部日志后观察到：

- 自动并行选择 6 个 worker，实际已经启用静止帧复用，不能把“增加并行”和“跳过静止帧”描述为尚未实现的功能。
- 一轮正常透明层耗时约 29 秒，其中画面采集约 13 秒、VP9 编码约 10 秒，其他为启动和准备。
- 复现最终成片时长探针 `ffprobe deadline`：已经完成透明层编码，校验等待约 30 秒失败；外层随后重新启动整个 HyperFrames 渲染。该次管线总计 105.6 秒。日志仅保留第二次渲染全文，首次错误已在诊断工具输出中确认。
- 显式 4 个 worker 的透明层耗时 28.4 秒；这轮输入探针又出现一次 15 秒超时，因此整体为 48.1 秒。该结果不能证明稳定提速。
- 独立重复 48 次已完成 WebM 的嵌套同步/异步探针没有复现超时，说明仍需定位发生条件；不能声称探针问题已修好。

结论：仍有优化空间，特别是避免校验超时触发整段重渲染；但仅修改并行数不足以证明稳定收益。
本轮只新增忽略目录中的测量脚本和输出，没有应用包装提速生产改动，也没有降低画质。
