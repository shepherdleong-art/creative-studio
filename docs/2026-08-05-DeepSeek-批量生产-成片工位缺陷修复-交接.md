## 问题 1：内容分析没有进度条，页面还会自己刷新

> 「准备素材的内容分析界面，我点内容分析，没有进度条，我不知道分析得怎么样，页面还会自己刷洗一下，很奇怪。」

拆成两半：**A = 页面自己刷新**（严重，影响全页），**B = 没有进度条**（体验）。

### 1-A 根因：两个轮询 effect 是自触发死循环

`components/batch-production/BatchPreparationPanel.tsx:414-426`：

```ts
useEffect(() => {
  if (!selectedBatchId) return;
  const initial = window.setTimeout(() => void loadTasks(selectedBatchId), 0);   // ← 无条件立即拉一次
  const hasActiveTask = batchTasks.some(...);
  if (!hasActiveTask) return () => window.clearTimeout(initial);
  const interval = window.setInterval(() => void loadTasks(selectedBatchId), 3_000);
  return () => { window.clearTimeout(initial); window.clearInterval(interval); };
}, [selectedBatchId, loadTasks, batchTasks]);   // ← batchTasks 既是依赖又是产物
```

`loadTasks`（:301-328）里 `setBatchTasks(view.tasks)` 写入的是 `JSON.parse` 出来的**新数组**，引用必然变化 → effect 依赖变化 → cleanup + 重跑 → `setTimeout(0)` 又拉一次 → 无限循环。

**关键点：`hasActiveTask` 的早退挡不住它**——`initial` 那次拉取在早退分支之前就已经排好了。所以**即使一个任务都没有**（`view.tasks = []`，每次也是新的空数组），循环照样跑。

`:428-441` 的 workspace effect 同样的写法，而且依赖数组里 `workspace` 和 `batchTasks` 都有，`setWorkspace(view)` 也是新对象 → 第二条死循环。两条循环互相踩：任一条刷新都会触发另一条。

后果链：
- 页面每轮全量重渲染 → 用户看到的"页面自己刷洗一下"；
- `/tasks` 和 `/workspace` 被以网络速度连续打 → 整个批量生产页发卡；
- `progressView`（:449）每轮重算 `Date.now()` → 问题 4 的"做完了还在计时"。

### 1-A 修改方案

把"进入时拉一次"和"周期轮询"彻底拆开，**周期 effect 的依赖里只允许出现布尔量，不允许出现数组/对象状态**。

在 `:414` 之前先派生一个稳定布尔：

```ts
const hasActiveBatchTask = useMemo(
  () => batchTasks.some((task) => (
    (task.status === 'queued' || task.status === 'running') && task.expectedState === 'running'
  )),
  [batchTasks],
);
```

然后把 `:414-441` 的两个 effect 改成四个（每个数据源一对）：

```ts
// 进入 / 切批次时各拉一次
useEffect(() => {
  if (!selectedBatchId) return;
  const timer = window.setTimeout(() => void loadTasks(selectedBatchId), 0);
  return () => window.clearTimeout(timer);
}, [selectedBatchId, loadTasks]);

// 只有还有活跃任务时才周期轮询
useEffect(() => {
  if (!selectedBatchId || !hasActiveBatchTask) return;
  const interval = window.setInterval(() => void loadTasks(selectedBatchId), 3_000);
  return () => window.clearInterval(interval);
}, [selectedBatchId, loadTasks, hasActiveBatchTask]);
```

workspace 同构（`loadWorkspace`，依赖 `[selectedBatchId, loadWorkspace]` 和 `[selectedBatchId, loadWorkspace, hasActiveBatchTask]`）。

**【坑】`loadTasks` / `loadWorkspace` 本身是 `useCallback(..., [projectId])`，引用稳定，放依赖里安全。真正有毒的只有 `batchTasks` / `workspace` 这两个数组/对象状态——改完请再通读一遍这两个 effect 的依赖数组，确认它们不在里面。**

**【坑】不要用 `JSON.stringify` 比较来"稳住引用"当作修法。**那只是把无限循环换成无限序列化，任务多时更慢。依赖数组改对就够了。

`hasActiveBatchTask` 从 `false → true` 的那一刻，周期 effect 才挂上，第一次触发在 3 秒后；因为启动/排队动作（`startBatch`、`analyzeAssets`、`requestProxies`）都已经在自己的 handler 里显式 `await loadTasks(...)`，不会有空窗。

### 1-B 根因：排队即完事，没有全局进度

- `analyzeAssets`（:608-653）只是 POST 排队，`finally` 里立刻 `setAnalysisBusy(null)`（:651）→ 按钮瞬间从「分析中…」跳回「内容分析（N）」，用户以为没反应。
- 每张卡片里其实有阶段文字（`BatchInputSelectionCards.tsx:236-246`，`content_analyzing` → 「画面内容分析」），但素材区是 2-3 列网格 + 内部滚动，用户看不到整体进展。
- 数据其实全都有：`assetPrepareTasks` 已经带 `status` 和 `progressJson`（`BatchPreparationPanel.tsx:314-323`），并已作为 prop 传进 `BatchStepMaterials`（`:1443`）。**只是没渲染。**

### 1-B 修改方案

在 `components/batch-production/BatchStepMaterials.tsx` 素材区标题块（`:182-231`）内补一条分析进度行。派生（放在 `:160` `onlineAssetCount` 附近）：

```ts
const analysisTotal = assetPrepareTasks.length;
const analysisDone = assetPrepareTasks.filter(({ status }) => status === 'succeeded').length;
const analysisFailed = assetPrepareTasks.filter(({ status }) => status === 'failed').length;
const analysisActive = assetPrepareTasks.filter(({ status }) => status === 'queued' || status === 'running').length;
```

渲染规则：
- `analysisActive > 0` 时，在 `:187` 那段说明文字下面显示一行：
  `分析中 {analysisActive} 条 · 已完成 {analysisDone}/{analysisTotal}{analysisFailed > 0 ? ` · 失败 ${analysisFailed} 条` : ''}`，
  配 `<progress max={analysisTotal} value={analysisDone} className="mt-1 h-1.5 w-full" />`。
- `analysisActive === 0 && analysisFailed > 0` 时只显示失败条数 + 「失败的素材卡片上可单独重试」提示。
- 「内容分析（N）」按钮（`:211-216`）：`disabled` 条件追加 `|| analysisActive > 0`，文案在 `analysisActive > 0` 时改成 `分析中 {analysisDone}/{analysisTotal}`。

**【坑】`assetPrepareTasks` 是本批次**全部历史**的 asset_prepare 任务，不是"本次点击"的。所以进度条只在 `analysisActive > 0` 时出现，文案说「已完成 x/y」而不是「本次分析 x/y」——不要试图去区分"本次点击的那一批"，那需要额外记账，收益不抵复杂度。

## 问题 3：不要无配音、无封面的预览片（本轮核心）

> 「我不要无配音、无封面的预览片，直接做好它吧。重新生成也是重新生成有配音有字幕有封面的成片给我。而且现在预览的片子也打不开，并且没有修改封面的界面。」

四个子问题：**A 静音样片从哪来**、**B 重新生成**、**C 预览打不开**、**D 换封面 UI（本轮暂缓，见 3-D）**。

**本轮只做 A / B / C。** D 用户已明确暂缓，`BatchStepReview.tsx:402-431` 的换封面区**保持原样，一行都不要改**。

### 3-A 根因：渲染没等口播

`lib/batch-production/phase-e.ts:96-121` 在**同一个事务**里先排 narration 任务、再排 render 任务：

```ts
for (const snapshotId of narrationSnapshotIds) {
  taskIds[`narration:${snapshotId}`] = createBatchTask(db, projectId, { workType: 'narration', ... });
}
for (const [planId, outputVersionId] of Object.entries(allocation.outputVersionIds)) {
  taskIds[planId] = createBatchTask(db, projectId, { workType: 'render', ... });
}
```

注释写着「排在渲染之前领取」，但**领取端没有任何闸门**。`lib/batch-production/scheduler.ts:50-59`：

```sql
WHERE t.status = 'queued' AND t.expectedState = 'running'
  AND p.controlState = 'running' AND p.deletedAt IS NULL
ORDER BY t.createdAt, t.id
LIMIT 1
```

`createdAt` 同一毫秒时 tie-break 是随机 UUID，顺序本来就不保证；更要命的是 `lib/batch-production/runner.ts:63` 默认 **concurrency = 2**——即使 narration 排第一被槽 A 领走，槽 B 立刻就把 render 领走并跑完了。TTS 是网络往返，FFmpeg 渲染短片很快，render 赢的概率非常高。

于是 `lib/batch-production/batch-renderer.ts:687`：

```ts
const audioMode: BatchRenderAudioMode = narrationInput ? 'narration' : 'silent_placeholder';
```

`narrationInput` 来自 `snapshot.arrangement.narration`，而那个 seam 是 narration executor 成功后才 `json_set` 写进去的 → 落成静音样片。

上一轮的补丁（`lib/batch-production/narration-executor.ts:268-311`，口播落账后自动补排一次「带配音重渲染」）是**事后补救**：用户仍然会先看到一批静音片，仍然要等第二轮 FFmpeg，第一轮完全白跑。用户这次的要求是"别给我看半成品"，所以要改成**事前闸门**。

### 3-A 修改方案：给 render 加口播依赖闸门

在 `lib/batch-production/scheduler.ts` 的 `claimNextTask`（:50-59）候选查询里追加 `NOT EXISTS` 条件：

```sql
  AND NOT EXISTS (
    SELECT 1
    FROM batch_output_versions ov
    JOIN batch_output_plans op ON op.id = ov.planId
    JOIN batch_tasks nt
      ON nt.batchId = t.batchId
     AND nt.workType = 'narration'
     AND nt.targetKind = 'script_snapshot'
     AND nt.targetId = op.scriptSnapshotId
    WHERE t.workType = 'render'
      AND t.targetKind = 'output_version'
      AND ov.id = t.targetId
      AND nt.status IN ('queued', 'running', 'failed')
  )
```

语义：一条 render 任务，只要它所属 plan 的 `scriptSnapshotId` 还有**未成功**的 narration 任务，就不可领取。

**【坑 1】闸门必须写在 SQL 的 WHERE 里，不能写成"先 `LIMIT 1` 取出来、在 JS 里判断、不合格就 `return null`"。** 后者会让两个并发槽在队首是 render 时直接空转退出（`runner.ts:73-75` 领不到就 `return`），整批停摆。写进 WHERE，SQLite 会自动跳过被挡住的 render 去选下一条可领取任务。

**【坑 2】`nt.status` 的取值必须精确：**
- `succeeded` → 不在集合里 → 放行。正常路径。
- `queued` / `running` → 挡住。这是闸门本身。
- `failed` → **挡住**（不是放行）。用户明确说不要无配音的片子，所以配音失败时宁可让这条成片停在"待处理"，也不要产出静音样片。**但这意味着必须给用户一个重试口播的入口，否则死锁——见【坑 3】。**
- `cancelled` → **不挡**（不写进集合）。旧版本被新版本取代时 narration 任务会被取消，那些行不该继续挡住新版本的 render。

**【坑 3】必须同时补"重试配音"入口，否则 narration 失败 = 永久死锁。** 现在 `BatchStepReview.tsx` 的卡片只暴露 render 任务（`card.task`），没有 narration 任务的任何信息。需要在 `lib/batch-production/batch-workspace.ts` 的卡片视图里补一个 `narrationTask` 字段——在 `:378` 的 taskRow 查询旁边加：

```ts
const narrationTaskRow = plan.scriptSnapshotId ? db.prepare(`
  SELECT t.id, t.status, t.expectedState, a.errorMessage
  FROM batch_tasks t
  LEFT JOIN batch_task_attempts a ON a.taskId = t.id AND a.attemptNumber = t.attemptCount
  WHERE t.projectId = ? AND t.batchId = ? AND t.workType = 'narration'
    AND t.targetKind = 'script_snapshot' AND t.targetId = ?
  ORDER BY t.createdAt DESC, t.id DESC LIMIT 1
`).get(projectId, batchId, plan.scriptSnapshotId) as { id: string; status: BatchTaskStatus; expectedState: BatchTaskExpectedState; errorMessage: string | null } | undefined : undefined;
```

接进卡片视图（`:427-449` 的返回对象）为 `narrationTask`，并接到派生状态上：
- narration `queued`/`running` 且还没有候选 → `deriveCardStatus`（`:246-261`）的 `nextAction` 给「等待配音完成」，status 保持 `waiting`；
- narration `failed` → 往 `blockers` 里加一条「配音失败：{errorMessage}，请点『重试配音』」，status 走 `needs_attention`。

对应地在 `components/batch-production/BatchStepReview.tsx` 卡片操作区（`:330-344`）加一个「重试配音」按钮，`card.narrationTask?.status === 'failed'` 时显示，复用现有 `onRetryRender` 那条路径的兄弟 handler（打到 `/api/batch-production/tasks/{narrationTask.id}/retry`）。narration 重试成功后闸门自动放行，render 无需人工干预。

**【坑 4】删掉上一轮的补渲染补丁。** `lib/batch-production/narration-executor.ts:268-311`（口播落账后扫描 `silent_placeholder` 候选并 `createBatchTask` 补排 `...:narration-upgrade:<fp>` render）在闸门生效后是死代码，而且有害：它会让同一个 `outputVersionId` 下存在**两条** render 任务，使 `lib/batch-production/output-media.ts:114-124` 和 `batch-workspace.ts:378-387` 的 `ORDER BY t.createdAt DESC, t.id DESC LIMIT 1` 选到哪条变得不确定。连同它引入的 `import { BATCH_RENDER_ADAPTER_VERSION } from './phase-e.ts'` / `import { createBatchTask } from './tasks.ts'` 一起删掉——那个 import 还制造了 `phase-e ↔ narration-executor` 的循环依赖。

**保留** `scheduler.ts:417` 那条放宽（`succeeded` 且 `targetKind === 'output_version'` 的任务允许 retry）——问题 3-B 的"重新生成"要用它。

### 3-B 修改方案：「重新生成」常驻，且必然带配音

`components/batch-production/BatchStepReview.tsx:333-337` 现在的条件：

```tsx
{card.task && (card.task?.status === 'failed' || card.candidate?.audioMode === 'silent_placeholder') && (
  <button ...>{card.task?.status === 'failed' ? '重新渲染' : '重新渲染（带配音）'}</button>

```

闸门生效后不会再有 `silent_placeholder`，这个按钮在正常成片上会**消失**——用户就没有"重新生成"入口了。改成：

```tsx
{card.task && (
  <button
    type="button"
    className="btn-secondary h-8 px-3 text-xs"
    disabled={phaseEBusy !== null || card.task.status === 'running' || card.task.status === 'queued'}
    onClick={() => onRetryRender(card.task!.id)}
  >{card.task.status === 'failed' ? '重试渲染' : '重新生成'}</button>

```

因为闸门保证 narration 已 `succeeded`、seam 已写进 arrangement，重渲染读到的必然是有配音的输入 → 产物必然带配音 + 字幕（`batch-renderer.ts:698-700` 用 narration segments 作字幕）+ 封面（`:703-705` 每次渲染都出 `cover.jpg`）。**不需要为"重新生成"单独写逻辑**，这正是把闸门做在领取端的收益。

同步删掉 `:307-309` 的「无配音样片」警告块和 `:191` 的「没有真实口播时会先生成无配音样片供检查」说明——闸门生效后这两句话不再成立，留着是误导。

### 3-C 根因：重渲染会让老成片"打不开"

`lib/batch-production/output-media.ts:114-124` 取候选的查询：

```sql
JOIN batch_task_attempts a ON a.taskId = t.id
  AND a.attemptNumber = t.attemptCount AND a.status = 'succeeded'
WHERE ... AND t.status = 'succeeded'
```

两个条件都太紧：
- `t.status = 'succeeded'`：用户一点「重新生成」，`retryTask`（`scheduler.ts:414-422`）把任务打回 `queued` → **重渲染期间整条成片查不到候选**，卡片变「暂无封面预览」、弹窗打不开；
- `a.attemptNumber = t.attemptCount`：`retryTask` 里 attemptCount 会 +1，于是**上一版成功的 attempt 因为编号对不上也匹配不到了**。重渲染一旦失败（`t.status = 'failed'`），那条本来能播的成片就**永久变成打不开**。

`lib/batch-production/batch-workspace.ts:406-408` 的 `candidate` 用了同一口径（`taskRow?.status === 'succeeded'`），所以卡片和媒体端点会一起失效。这两处就是"现在预览的片子也打不开"的机制。

### 3-C 修改方案：候选一律取"最近一次成功的 attempt"

`output-media.ts` 候选分支（`:112-133`）改成：

```sql
SELECT a.resultJson
FROM batch_tasks t
JOIN batch_task_attempts a ON a.id = (
  SELECT id FROM batch_task_attempts
  WHERE taskId = t.id AND status = 'succeeded'
  ORDER BY attemptNumber DESC LIMIT 1
)
WHERE t.projectId = ? AND t.batchId = ? AND t.workType = 'render'
  AND t.targetKind = 'output_version' AND t.targetId = ?
ORDER BY t.createdAt DESC, t.id DESC LIMIT 1
```

即：去掉 `t.status = 'succeeded'`，attempt 改成"该任务最近一次成功的尝试"。

`batch-workspace.ts:406-408` 同步改口径：`candidate` 不再看 `taskRow.status`，改为读同一条"最近一次成功 attempt"的 `resultJson`（把 `:378-387` 的 taskRow 查询里 `LEFT JOIN ... AND a.attemptNumber = t.attemptCount` 拆成两次取：**当前 attempt 用于 `task.errorMessage`/进度，最近成功 attempt 用于 `candidate`**）。

**安全边界不变**：`parseCandidate`（`output-media.ts:39-72`）本来就逐字段校验 `projectId / batchId / batchVersionId / planId / outputVersionId` 谱系和 `productionReady === (audioMode === 'narration')`，放宽任务状态不会让跨批次或半成品产物泄漏出去。

**【坑】不要顺手清理旧的 jobDir。** `batch-renderer.ts:640` 每次渲染新建 `${outputVersionId}-${uuid}` 目录，旧候选文件不删——这**正是**"重渲染期间/失败后老版本仍可播放"能成立的原因。旧目录确实是磁盘泄漏，但清理需要引用计数，**本轮明确不做**，只在本文档记一笔留给后续。

### 3-D 根因：换封面 UI 会整块消失

`components/batch-production/BatchStepReview.tsx:402-431` 的换封面区整块被 `previewCard.coverRange &&` 守卫。而 `coverRange` 来自 `batch-workspace.ts:136-170` 的 `arrangementCoverRange`，它在**任何一个**下列情况返回 `null`：

- clips 为空（`:157`）；
- `sourceStartUs/sourceEndUs` 非有限数或 `end <= start`（`:161`）。

→ 用户看到的就是"没有修改封面的界面"。而且即使有，现在也只是一根**没有画面反馈的裸滑杆**——拖到哪一帧完全靠猜，跟用户点名要的单条模式抽屉（`components/mixcut/CoverEditorDrawer.tsx`：取材选择 + 抽帧时间 + 构图 + 主副标题文字 + 预设，canvas 实时预览）差得远。

## 问题 4：生产进度做完了还在计时，做的时候又看不见

> 「这个生产进度，明明已经做完了，但依旧在计时，做的时候又不见它喔。」

### 根因（三条，独立）

1. **计时永不停**：`BatchPreparationPanel.tsx:467` 的 `elapsedSec` 在 `useMemo` 里现算 `Date.now()`，而问题 1-A 的死循环让 `batchTasks` 引用永远在变 → `useMemo` 每轮重算 → 批次早就 `completed` 了，秒数还在涨。**问题 1-A 修完这条会缓解，但不会根治**——终态时应该显式停表，而不是靠"没人再触发重算"。
2. **起点算错**：`:460-462`
   ```ts
   const startedAtMs = batchTasks.length > 0
     ? Math.min(...batchTasks.map((task) => new Date(task.createdAt).getTime()))
     : null;
   ```
   `batchTasks` 是**全部** workType，包括第 1 步的 `asset_prepare` 和 `proxy_generate`。于是"已用时"是从"很久以前做内容分析那一刻"起算的 —— 数字本身就是错的，跟本次生产无关。
3. **做的时候看不见**：进度卡只渲染在**第 2 步**（`BatchStepScripts.tsx:615-656`）。`startBatch`（`:865` 的注释「不自动跳到检查成片」）确实把用户留在第 2 步，但用户开跑后自然会切到第 3 步「检查成片」盯卡片看——那里**没有整体进度**。等他回到第 2 步时早跑完了，看到的正是一块还在跑表的进度卡。

### 修改方案

**4-1 抽成共享组件。** 新建 `components/batch-production/BatchProductionProgressCard.tsx`，把 `BatchStepScripts.tsx:615-656` 的 JSX 原样搬过去，并把 `BatchProgressView` 类型定义（现在在 `BatchStepScripts.tsx:35`）一并移过去。`BatchStepScripts.tsx` 和 `BatchPreparationPanel.tsx:23` 的 import 改指向新文件。组件加一个 `variant?: 'full' | 'compact'` prop：`full` 是现在的完整卡（阶段列表），`compact` 只有一行标题 + 总进度条 + 用时。

**4-2 在 `commonMain` 里统一渲染。** `BatchPreparationPanel.tsx:1421-1431` 的 `commonMain` 是所有步骤的公共包裹层，在 `{feedback && ...}` 之后、`{content}` 之前插入：

```tsx
{progressView && activeStep !== 0 && (
  <BatchProductionProgressCard progress={progressView} variant={activeStep === 1 ? 'full' : 'compact'} />
)}
```

同时删掉 `BatchStepScripts.tsx:615-656` 的原地渲染和 `:73` / `:133` 的 `progress` prop、`BatchPreparationPanel.tsx:1551` 的 `progress={progressView}` 传参——避免第 2 步出现两块进度卡。

**4-3 起点只算生产任务。** `:460-462` 改成只取 `workType === 'narration' || workType === 'render'` 的任务：

```ts
const productionTasks = batchTasks.filter((task) => task.workType === 'narration' || task.workType === 'render');
const startedAtMs = productionTasks.length > 0
  ? Math.min(...productionTasks.map((task) => new Date(task.createdAt).getTime()))
  : null;
```

**4-4 终态停表。** 派生一个终态判定，终态时用"最后一条生产任务的完成时刻"而不是 `Date.now()`：

```ts
const finished = !hasActiveBatchTask && productionTasks.length > 0;
const finishedAtMs = finished
  ? Math.max(...productionTasks.flatMap((task) =>
      task.attempts.map((attempt) => (attempt.finishedAt ? new Date(attempt.finishedAt).getTime() : 0))))
  : 0;
const endMs = finished && finishedAtMs > 0 ? finishedAtMs : nowMs;
elapsedSec: startedAtMs ? Math.max(0, Math.floor((endMs - startedAtMs) / 1000)) : 0,
```

`BatchTaskAttemptView` 已经带 `finishedAt`（`lib/batch-production/tasks.ts:386`），**不需要改 schema 或 API**。

`BatchProgressView` 加一个 `finished: boolean`，组件里据此把「已用时 X 分 Y 秒 · 刷新页面不丢失进度」换成「**已完成** · 总用时 X 分 Y 秒」，并把整体进度条固定成 100%（失败时用 `failed` 配色 + 「部分失败」）。

**4-5 计时用显式 tick，不再蹭副作用。** 加一个只在运行时跳动的 state：

```ts
const [nowMs, setNowMs] = useState(() => Date.now());
useEffect(() => {
  if (!hasActiveBatchTask) return;
  const timer = window.setInterval(() => setNowMs(Date.now()), 1_000);
  return () => window.clearInterval(timer);
}, [hasActiveBatchTask]);
```

`progressView` 的 `useMemo` 依赖数组加上 `nowMs`。**【坑】依赖数组里千万别再放 `Date.now()` 或任何每次渲染都变的表达式**——那等于把刚修掉的死循环换个地方重来一遍。
