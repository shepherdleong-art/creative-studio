# 实拍重组 Skill 与 Creative Studio 五步工作台接入：需求共识

日期：2026-10-12  
状态：需求讨论归档，作为后续设计与开发依据；尚未进入实现或验收。同日第二轮对照仓库代码与 skill 原文复核后修订，修订内容已经用户确认：再次导出由覆盖原文件改为生成新版本、限定本地桌面版、MCP 暂缓、包装按模板组织。2026-10-14 用户再定：HyperFrames 统一为 `packaging/` 的一份锁定版本，工作台与固定命令共用；模板资源放进仓库；现行包装（classic）仍是第一个模板，技能以后也能选用工作台的四套模板。第 3、8、10、12 节已同步。  
对象：`reassembled-product-film` skill、Creative Studio 现有五步项目工作台。

## 1. 核心决定

以后新建的实拍重组工程，从开工起就接入本机的 Creative Studio 桌面版。Skill 指导 Agent 自主制作，工作台提供执行与工程管理能力，并承接用户的精确修改。

Agent 与用户操作同一份项目数据。场景图、分镜、脚本、视频和混剪产物分别进入现有五个步骤，不新增一个专门容纳 Agent 产物的独立工作区。

最终交付仍包含成片、封面、工程文件和 HTML 审片页。审片页中每条成片提供“在 Creative Studio 中编辑”入口，直接定位对应项目、成片及版本。用户手动保存和确认的修改，必须成为后续 Agent 工作的依据。

用户在工作台精确修改后再次导出，或在对话中让 Agent 返工，新成片都写回原先指定的交付目录，按 skill 现有命名生成 `-v2`、`-v3` 等新版本；上一版连同封面移入同一交付目录下的 `旧版/`，交付目录中每条只保留当前版本。工作台内部工程、缓存或渲染目录不能取代用户的交付目录。从工作台导出的成片与 skill 直接交付的成片使用同一套渲染与包装，结果一致。

适用范围：本机 Agent 与本地桌面版工作台。服务器统一生产（2026-09-20 方案）暂不联动，之后另议。

**本次只整理文档。历史工程暂不迁移，业务代码、skill 和生成执行流程均未因本文发生变更。**

## 2. 背景与要解决的问题

目前实拍重组流程已经能由 Agent 完成选材、生图、脚本、视频、剪辑和包装，但成片仍可能出现产品结构、材质、构图或局部画面的错误。

用户这两天的实际使用感受是：包装问题相对少，产品本身的错误更突出；不同 Agent 和模型的判断效果也有差异。这是需求来源，不是经过统一基准验证的模型能力排名。

如果每次都通过对话重新描述问题，让 Agent 回找素材、判断、生成和审片，返工耗时较长，也可能再次判断错误。用户需要在看到问题时，直接定位到镜头并进行人工精修。

目标是保留 Agent 自主制作的效率，同时提供连续、可追溯、不会覆盖人工决定的接管流程。

## 4. 用户流程

### 4.1 安装 skill 后，开工前检查工作台

Agent 首先检查 Creative Studio 桌面版是否可用、服务是否运行，以及接口版本和所需能力是否匹配。

能从本机环境确认的信息直接检查；找不到安装位置或存在多个候选时，再询问用户。缺少工作台时，说明依赖并引导安装。服务未启动与未安装应区分；启动须走现有启动脚本，公司网关才会随之启动。

已核实的约束：

- 桌面版每次启动使用随机端口，当前地址记录在数据根的 `storage/run/electron-service.json`，不能假定固定地址。
- skill 与桌面版必须使用同一个数据根。skill 从其所在仓库的数据库读取供应商配置；从仓库启动的桌面版以仓库目录为数据根，与网页版共用数据库，安装版则使用系统 AppData 目录。检查时应核对二者一致，不一致时拒绝登记并说明，不能把项目登记进用户不会打开的库。

自动发现的具体实现、启动授权与交互、版本兼容策略留待技术设计，不在本文假定已经实现。

### 4.2 创建项目并建立制作归属

通过工作台提供的接口创建项目，登记产品素材和本次制作需求，建立场景、分镜组、脚本及成片之间的明确关联。

后续产物使用这些稳定标识归档，不靠文件名、目录时间或 Agent 的临时记忆推断所属项目和片号。

### 4.3 Agent 自主完成制作

Agent 继续负责选材、提示词、视觉判断、脚本、镜头选择、剪辑和包装。工作台承接生成任务及结果管理；已有能力通过正式接口复用，能力缺口在后续设计中补齐。

用户中途打开项目时，应能看到已登记的进度、素材与结果。接入不能只在最终完成后上传一个 MP4。

每次付费生成只能有一个明确的执行方负责提交与恢复，避免 skill 和工作台分别提交同一任务：

- Agent 提交的任务由 skill 队列负责。工作台只登记已到终态的结果及出处（本地任务 ID、实际存在的远端 ID、提示词、输入指纹），不把进行中的任务写进工作台任务表，避免被工作台队列领取或恢复后重复扣费。
- 进度展示只读 skill 台账，或为任务增加执行方标记，工作台领取和恢复时一律跳过。
- 用户在工作台发起的返工是工作台自己的新任务，由工作台队列负责。
- 已有远端任务继续查询，不因界面同步或重新连接而重复生成。

### 4.4 HTML 审片与工作台接管

Agent 完成后提供成片、封面、工程文件和 HTML 审片页。每条片子独立展示，并带“在 Creative Studio 中编辑”按钮。

用户点击第 17 条时，直接打开桌面版中对应项目的第五步、该条成片及当前可编辑版本；不要求用户再次手动寻找项目、分镜组或时间线。

桌面版端口随机，审片页不能写死服务地址。编辑入口建议使用桌面版注册的专用链接（例如 `creative-studio://`）：桌面版运行时直接跳到该条；未运行时先经现有启动脚本拉起，再跳转。具体机制待技术设计。

审片页需要保留其展示的成片版本身份。如果工作台中存在尚未导出的修改或更新的版本，应明确提示差异，不能把交付目录中的成片与新时间线当作同一版本。具体打开旧版查看还是进入当前版编辑的交互待设计。

目标不存在或版本不兼容时，应给出明确恢复入口，不能静默打开首页后让用户自行寻找。

### 4.5 精确修改与再次导出

- 某几帧产品变形：调整源片入出点，避开问题区间。
- 整个镜头结构有误：替换为已有候选或用户提供的新素材。
- 节奏或顺序不合适：调整裁剪、速度或镜头顺序。
- Agent 没识别出问题的分镜图：在第二步人工修改后重新生成，第四步用新图生成视频片段，再在第五步替换回时间轴。
- 包装不符合用户想法：通过后续提供的包装编辑能力调整；已有人工设置须保留。

源图或源视频中的产品错误，不一定能靠剪辑修复。应能从第五步准确定位第四步的视频或第二步的分镜，局部生成新候选后再替换回成片。为此，Agent 登记的分镜和视频必须带上实际提交的输入、提示词与模型（见第 5 节），否则工作台重新生成时只能套用默认提示词。

新片段放回时间轴时默认保持原片段时长，包装的时间点不随之移动；时长确需改变时，按第 8 节检查受影响的包装。

修改后保存新版本，重新合成并导出。修改一条片子不应改动同批其他已确认成片。

### 4.6 沿用原交付目录

Agent 首次制作时登记用户指定的交付目录，并将其与项目、对应成片关联。用户从 HTML 审片页进入工作台后，这一交付目标必须随工程保留；修改后的成片继续导出到该目录，不要求用户重新寻找或搬运文件。

例如，Agent 首次把某条成片交付到用户指定的文件夹，用户在工作台替换其中一个镜头后，再次导出的成片仍进入同一个文件夹。

- 由 skill 导入的成片，导出目标是 Agent 的交付目录，而不是工作台内部目录。工作台可以在内部保存工程、源素材、缓存和中间渲染结果，但导出成功必须包含向交付目录完成交付，不能仅以内置存储中的文件已生成作为成功依据。
- 导出结果与 skill 直接交付的成片一致：使用同一套渲染、包装与混音（见第 8 节），并通过同样的技术检查（完整解码、音画时长、响度、封面静帧）。
- 交付目录作为独立配置保存，不能从当前安装目录或内部数据根推导；工作台升级或搬动程序位置不应自动改变交付目标。
- 如果各条成片有单独指定的交付目录，保留各自的对应关系，不将整批强制改到同一个内部目录。
- 目标目录不存在、外置磁盘未挂载或没有写入权限时，明确提示并允许恢复访问或重新选择，不静默回退到工作台默认目录。
- 版本命名沿用 skill 现有规则：首次交付不带版本号，之后依次为 `-v2`、`-v3`，封面与成片同名并追加 `-封面.jpg`。
- 新版本完整渲染并通过检查后才写入交付目录，再把上一版成片与封面移入同一交付目录下的 `旧版/`，文件名不变；交付目录中每条只保留当前版本。生成或交付失败时不产生新版本文件，也不移动旧版。
- 旧版移动失败（例如 Windows 上审片页仍在播放该文件）时，新版本照常交付，旧版暂留原处，并提示用户关闭占用后重试。
- 操作仅针对本条成片，不移动或改动其他成片。
- 对话中让 Agent 返工时，按同一规则生成新版本并移走旧版。
- HTML 审片页同步更新该条的交付版本信息，重新打开或刷新后播放新版本。

封面、随附文件和审片页的更新范围也需在设计中明确，保证交付记录准确指向实际导出的版本。

## 5. 五步工作台的内容落位

| 现有步骤 | Agent 需要登记的内容 | 关键关联 |
| --- | --- | --- |
| 场景图 | 原始产品素材、场景候选、选定场景、生成与审核来源 | 项目、输入素材、场景 |
| 分镜 | 每条片子的分镜图、历史候选、选用结果；实际提交的原实拍裁图（图1）、本条场景（图2）、最终提示词与模型 | 项目、场景、分镜组、具体分镜 |
| 脚本 | 已完成的口播、镜头说明、脚本版本 | 对应片号、分镜组及成片使用的脚本版本 |
| 视频 | 各分镜的视频任务、输出、历史候选、真实生成记录；最终运镜提示词、模型与时长 | 项目、分镜组、分镜、来源图片 |
| 混剪 | 时间线、配音、字幕、BGM、封面、包装模板与本条包装内容、导出成片 | 成片标识、编辑版本、具体素材与包装版本 |

这些是目标归属，不意味着现有接口已经完整支持所有字段。尤其脚本与分镜组的精确关联、包装工程管理、外部编排结果登记及完成时间线接收，需要在设计阶段核实。

Agent 已写好的脚本或已制作好的包装，应按来源保存；不能为了“走完五步”再调用一次模型生成，也不能编造供应商、远端任务 ID 或审核记录。

重新导出所需的片段、配音、BGM、封面和包装源文件，工作台必须能可靠找到并核验：可以保存托管副本，也可以按链接素材记录路径和内容指纹。Agent 工程目录被移动或改动时应能发现并重新定位，不能静默使用错误的文件。

## 6. 一批与一条的组织方式

产品方向是“管理时看一批，修改时看一条”。批次关系用于组织和总览，编辑页面只展开当前选中的成片，不同时铺开 28 条时间线。

针对本 skill 当前每条独立场景、独立分镜和独立视频的要求，建议默认映射如下：

```text
现有项目：某产品的本次制作
├─ 公共产品素材与事实依据
├─ 成片 01：场景 → 分镜组 → 脚本 → 视频 → 混剪版本
├─ 成片 02：场景 → 分镜组 → 脚本 → 视频 → 混剪版本
└─ ……成片 28
```

同一产品的 28 条独立片子，可以落在一个项目内的 28 套分镜组及对应成片；不同型号可按产品拆项目，并保留本批制作关联。这是后续设计的建议起点，不把“28 条必定对应 28 个分镜组”冻结成通用数据库规则。

以分镜组作为每条成片的边界，还有一个结构上的好处：分镜组是单条精准混剪的素材隔离边界，编辑第 17 条时选不到其他条的生成素材，等于由系统守住 skill 的跨条独立性要求（skill 现有导出不会自动拦截跨条引用，靠 Agent 逐条检查）。批量生产的共享素材池、联合分配和开跑即冻结，不适合 Agent 已写好的时间线与边做边交，因此不作为首期容器；其正式产物发布与新鲜度判断机制可以借用（见第 10 节）。

不要求用户在审片入口先选择“单条剪辑”或“批量剪辑”。对用户统一表达为“编辑这条成片”，内部如何复用现有组件和数据结构由实现设计决定。

避免把制作批次、项目、成片、编辑版本和一次生成任务统称为“任务”。最终术语与现有领域模型对齐：编辑版本可对应“成片版本”，导出文件可对应“正式产物”，审片页上展示的那条可对应“当前成片”；“交付目录”是新词，定稿后补入 `CONTEXT.md`。

## 7. Agent 接入方式与工作台接口

用户最初设想工作台像 MCP 服务一样，为安装了 skill 的不同 Agent 提供统一入口。复核后决定首期不做 MCP：

- 目前调用方只有本 skill，它本来就在仓库中运行命令行工具（队列、审核均如此），Claude Code 与 Codex 都能执行命令。首期为 skill 增加少量命令行子命令（例如建项目、登记分镜和视频、登记成片、获取编辑链接），由它们通过 `storage/run/electron-service.json` 找到桌面版并调用工作台接口。
- 真正需要建设的是工作台接口本身。以后若要给同事使用，或服务器版需要远程 Agent 接入，再在同一套接口外增加 MCP 外壳。

需要评估的能力包括：发现工作台及查询能力、创建项目与素材归属、登记生成结果与选用结果、登记脚本、保存剪辑及包装工程、读取最新版本、获取可定位的编辑链接。本文没有冻结命令名、端点或参数。

接入须遵循以下约束：

- 本机服务保持本机访问，不为审片跳转或 Agent 接入暴露公网端口。
- Agent 通过受控接口操作项目，不直接改 SQLite 绕过校验和版本保护。
- 创建、提交、结果登记和重连具备去重与恢复依据，不能重复扣费或反复生成同一对象。
- 区分任务执行状态、Agent 审核结果与用户确认状态，生成成功不自动等于用户认可。
- 用户和 Agent 并行工作时，需要版本检查和明确的冲突处理。
- 工作台接口目前没有鉴权，收窄 Agent 可用的命令并不能阻止绕过；版本检查与人工修改保护必须落在界面和 Agent 共用的写入逻辑上（见第 9 节）。

## 8. HyperFrames 包装、模板与封面

Agent 继续默认制作包装。用户明确要求保留手动客制化入口，不能把“不做首期完整包装编辑器”理解为“以后也不允许用户改包装”。

包装按模板组织：

- 现行 skill 使用的这套包装（20 帧静帧封面、贴纸、卖点标注等）整理为模板之一，其中贴纸就是逐镜标签 `labels`；具体元素清单在抽取模板时盘点。
- 用户的新包装设计已于 2026-10-13 迁入工作台：A 花字种草、B 手账拼贴、C 极简高级、D 综艺撕纸四套叠层模板（见 `docs/reference/视频包装.md`）。2026-10-14 定：技能以后也能选用这四套，排在现行包装之后接入。
- 各模板共用同一份输入约定：时间线、本条包装内容（文字、坐标、关键帧、出现时间）以及按产品调整的字体、配色等参数。模板决定样式与动效，本条包装内容决定“说什么、指哪里、何时出现”；用户精修主要改后者，换模板是显式操作。
- 每条成片记录所用模板及其版本，重新导出默认沿用；换模板或升级模板由用户明确选择，不静默改变已交付成片的再导出结果。

从新工程开始至少需要保留包装源工程、配置、依赖资源、时间关系及镜头对应关系。干净的源视频和独立音轨等可编辑资产不能只剩下压制后的 MP4。

**固定渲染命令是再次导出的前提。** 目前 skill 的包装脚本只生成 HTML，HyperFrames 渲染、混音和封面导出依赖 Agent 在各工程中现场适配的脚本；第五步现有导出使用另一套渲染（ffmpeg 与自带字幕、标题叠层），不产出 HyperFrames 包装，混音规则也不同。因此需要把“包装、HyperFrames 渲染、混音、封面与技术检查”做成不依赖 Agent 的固定命令：输入时间线、模板、本条包装内容及素材，输出 MP4 与 JPG。Agent 出片与用户在工作台导出都调用它。现行包装作为第一个模板，可以先用现有成片验证这条命令；新设计到位后作为新模板接入同一命令。（2026-10-14 更新：新设计已作为四套模板进入工作台，第五步现在能套 HyperFrames 包装，但混音规则仍与 skill 不同。HyperFrames 统一为 `packaging/` 的一份锁定版本，工作台与固定命令共用。）

后续包装编辑可优先评估文字、字体、颜色、大小、位置、出现时间、显隐和封面调整，再扩展模板切换及更细的动画时间轴。具体阶段顺序尚未冻结。

换镜头可能使圆点和引线指向错误位置；变更镜头时长可能影响卡片、字幕和配音时序。必须明确哪些包装可沿用、哪些需重新检查或调整，不能默认原包装对新镜头仍正确。

第五步能否忠实预览 HyperFrames 包装，是正式闭环的设计与验收项。仅导入视频素材不能宣称完整接管了成片。首期默认保持原片段时长替换（见 4.5），但这不是硬性限制；时长变化时的包装检查方式待设计。

## 9. 人工修改保护

这是必须落实到系统行为的要求，不能只靠 skill 提示 Agent 自觉遵守。

1. 用户保存后形成可追溯版本，保留修改记录及恢复依据。
2. Agent 继续工作前读取当前版本；基于旧版本的写入应被检查，不能静默覆盖。
3. 用户已确认的素材选择、裁剪、顺序、脚本或包装设置受保护。
4. 涉及受保护内容的 Agent 变更先形成候选或提案，经用户选择后生效。
5. 保护粒度需要区分素材、时间线和包装。例如允许按要求调整引线时，不等于允许同时替换用户选定的视频。
6. 用户在工作台发起、或在对话中明确要求的重新生成，新结果可以直接成为当前；Agent 自动续跑（没有用户明确指令）时，不得改动用户改过的镜头、素材或成片，冲突时转为候选或询问。批次续跑也不自动覆盖人工确认的某条成片。

现有基础与缺口（已核实）：

- 第五步每条编辑命令都带期望版本号，已有修订历史、恢复到旧版本、基于版本的提案及应用，片段上也有人工选用标记；`CONTEXT.md` 中的“片段锁定”与本节的受保护内容是同一概念。本节应在这些基础上扩展，而不是另建一套。
- 第二、四步的写入没有版本检查；第二步重新生成后，新图会自动成为该分镜的当前图。用户自己操作时这正是所需行为，但 Agent 写入前需要补充可比对的版本标记。
- 工作台接口没有鉴权，保护必须落在界面与 Agent 共用的写入逻辑上。

具体的确认入口、字段保护模型、版本冲突界面与撤销范围，在设计阶段确定。

本次讨论期间已只读核对：

- `lib/final-edit/schema.ts`：已有成片分组、成片版本、修订记录、提案及包装资源相关结构；这些结构不等同于现成的 HyperFrames 编辑接入。
- `components/mixcut/`：已有素材导入、时间线、裁剪和素材替换相关代码基础。
- `scripts/reassembled-film-queue.mjs` 与 skill 的 `references/runtime.md`：实拍重组目前主要通过工程目录、独立队列和生成台账组织任务。
- skill 的 `references/delivery.md`：已有时间线与 HyperFrames 包装产物约定，尚不能直接等同于工作台可编辑工程。

第二轮对照代码复核（只读）补充：

**可以复用**

- 第五步编辑命令的期望版本号、修订历史与提案：`lib/final-edit/workspace.ts:257` 起。
- 批量生产的正式产物机制：按完整渲染契约判断成片是否过期（提示“当前修改尚未导出”）、视频与封面成对发布、发布前在事务内复核版本，见 `docs/reference/批量生产模块.md`。审片页的版本身份与新版提示可以照此设计。
- 桌面版服务状态文件 `storage/run/electron-service.json` 记录当前地址与实例，可供 skill 发现桌面版。

**与本需求冲突或缺失**

- 导出位置与命名：第五步导出只能写在工作台 storage 内，同名自动加序号（`lib/final-edit/export-naming.ts:71`、`:78`）；批量导出拒绝覆盖。由 skill 导入的成片需要新增“写回交付目录”的导出目标，不改动现有导出规则。
- skill 现行命名为修订另加 `-v2`、旧版原处保留（`references/planning.md`、`references/delivery.md`），实施时同步改为旧版移入 `旧版/`。
- 第二步新结果自动成为当前图（`lib/queue.ts:821`、`app/api/shot-sets/[id]/route.ts:135`），第二、四步写入没有版本检查。
- 工作台队列有自己的重试与崩溃恢复：视频任务部分失败会退回待执行再提交（`lib/video-queue.ts:44`、`:557`），图片队列启动时重新领取中断的任务（`lib/queue.ts:130`）。这与 skill“付费失败不自动重发”的规则不一致，因此 Agent 进行中的任务不能写入工作台任务表。
- 桌面版：服务端口每次随机（`desktop/service-spawn.ts:336`）；第二个实例只会聚焦窗口，不处理链接（`desktop/main.ts:109`）；数据根在从仓库启动时为仓库目录，安装版为 AppData（`desktop/main.ts:45`）。skill 的公司通道从数据根下的数据库读取供应商配置（`scripts/reassembled-film/company-adapter.mjs:27`）。
- 渲染：仓库应用代码中没有 HyperFrames（2026-10-13 起已有：`packaging/` 与 `lib/media-core/packaging-*`）；第五步渲染不做响度归一（`lib/final-edit/renderer.ts:174`），也没有 skill 的人声闪避（这两点至 10-14 仍成立）。skill 的渲染与混音依赖各工程现场适配的脚本（例如 RC2C 的 `media_pipeline.py`、`run_hf.py`）。
- Agent 工程位于仓库 `outputs/` 下，不在工作台数据根的 storage 内，而工作台导出与媒体读取限制在 storage 内。
- 工作台 `app/api` 共 179 个路由，没有鉴权中间件。

因此，本需求涉及业务接入、数据关联、版本保护和包装渲染衔接，不是只添加一个审片页跳转按钮。本次未进行运行时或用户界面验收。

思路参考是 `video-shotcraft` 的“成片交付后打开可编辑工作台”，但本方案明确复用 Creative Studio 的现有五步项目流程，不照搬其独立工作台。

## 12. 分期建议

各问题之间有依赖，按用户最急的“产品结构错误要换镜头”排序。这是建议，不是冻结的执行计划。

- **P0 固定渲染命令**：以现行包装作为第一个模板，抽出统一输入约定，包含技术检查。验收：现有成片不做修改直接重新导出，结果与原片一致。HyperFrames 统一为一份锁定版本，与工作台共用；工作台的四套模板随后作为新模板接入，技能也能选用（2026-10-14）。执行文档见 [P0 执行文档](../plans/2026-10-13-实拍重组固定渲染命令-P0执行文档.md)。
- **P1 第五步闭环**：第五步接收 Agent 成片（每条一个分镜组，登记实际输入与出处，素材可核验）；支持调整入出点、换已有候选、调整顺序；导出调用固定命令写回交付目录（新版本加旧版移入 `旧版/`），并更新审片页；专用链接直达桌面版。验收：从审片页进入、换镜头、再次导出的完整闭环。
- **P2 上游返工与保护**：第二步人工改图重新生成、第四步出新视频、第五步替换回时间轴（默认保持原时长）；Agent 写入前比对版本，自动续跑不碰人工修改。验收：返工后其余内容不变，Agent 续跑不覆盖人工修改。
- **P3 包装编辑与扩展**：包装编辑（文字、位置、时间、模板切换）；MCP 视需要增加；服务器联动另议。

## 13. 后续验收场景

以下作为开发计划的验收输入，当前均未执行：

| 场景 | 期望行为 |
| --- | --- |
| 新安装 skill，工作台不可用 | 明确检查结果并引导连接或安装，不默默生成无法接管的独立工程 |
| skill 与桌面版数据根不一致 | 拒绝登记并说明原因，不把项目登记进用户不会打开的库 |
| 新建一条成片 | 五个步骤中能找到真实关联的素材、脚本、视频与剪辑结果 |
| 同产品制作 28 条 | 可总览本批；编辑第 17 条时只进入该条，不混入其他成片素材 |
| 从 HTML 点击编辑 | 直达桌面版对应项目、成片与明确版本；存在未导出的修改或更新的版本时提示差异 |
| 桌面版未运行时点击编辑 | 经现有启动脚本拉起（公司网关可用）后直达该条 |
| 不做修改直接重新导出 | 结果与 Agent 原片一致：时长、帧数、包装与响度 |
| 替换一个问题镜头 | 其余镜头和已确认内容保留，重新导出反映替换结果 |
| 源分镜存在结构错误 | 从第五步定位到对应分镜，第二步人工修改后重新生成，第四步出新视频，第五步替换回时间轴；片段默认保持原时长，包装时间点不变，其余内容不受影响 |
| 修改后再次导出 | 新成片以 `-v2` 等名称写入原交付目录，上一版连同封面移入 `旧版/`；交付记录指向此次导出版本 |
| 对话返工 | Agent 返工后按同一规则生成新版本并移走旧版 |
| 再次导出后审片 | HTML 审片页刷新或重新打开后播放新版本，版本信息与实际文件一致 |
| 渲染失败 | 不产生新版本文件、不移动旧版，不误报交付成功；其他成片保持不变 |
| 旧版移动失败 | 新版本照常交付，旧版暂留原处并提示重试 |
| 原交付目录不可访问 | 明确提示恢复访问或重新选择，不静默导出到工作台内部目录，不误报交付成功 |
| 用户保存后 Agent 继续运行 | Agent 读取新版本，旧写入不能覆盖人工修改 |
| Agent 重连或重复登记 | 不重复创建工程对象，不重复发起付费生成 |
| 带包装重新导出 | 封面、字幕、音频和包装正确合成；引线等镜头依赖经检查 |
| 用户调整包装 | 编辑能力交付后，人工设置可保存、导出，并受版本保护 |

完成标准应以真实新工程、实际工作台操作及导出成片验证。接口测试或构建通过不能替代完整接管与视觉一致性验收。
