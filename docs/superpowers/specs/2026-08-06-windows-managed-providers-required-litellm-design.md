# Windows 受管供应商与 LiteLLM 强制启动设计

日期：2026-08-06  
状态：已确认，待实施

## 文档关系

本文是 `2026-08-05-windows-installer-provisioning-spec.md` 的增量修订，并覆盖其中以下旧决策：

- “LiteLLM 故障只禁用公司供应商，不阻塞工作台”；
- “外部供应商不受阻塞”；
- “未导入配置时仍显示未配置公司供应商并允许使用其他能力”；
- “重复导入不影响用户自行添加的其他供应商”在安装版中的可见与可执行含义。

旧文档中关于加密 envelope、密钥不进入安装包、loopback 监听、私有运行时、原子写入、卸载保留数据和日志脱敏等约束继续有效。历史供应商数据仍不物理删除，但在受管安装版中不得显示、编辑或执行。

## 背景与已确认根因

在实际安装目录 `H:\Creative Studio` 上完成了只读排查：

- 安装负载中的 `CreativeStudio.exe`、Node、CPython/LiteLLM、sidecar 启动脚本均存在；
- `.provision` 已成功导入，`config.yaml`、`data/provisioning/state.json` 与 `runtime.env` 均已写入，配置哈希匹配；
- LiteLLM 没有生成有效的 `storage/run/stack.json`，错误日志显示读取 `config.yaml` 时抛出 `UnicodeDecodeError`；
- 内置 CPython 在该中文 Windows 环境下默认文件编码为 `cp936`，而 `config.yaml` 为 UTF-8；同一内置 Python 使用 `-X utf8` 后可成功读取该文件；
- 当前启动器把 sidecar 定义为 optional/best-effort，异步启动后不检查退出码或健康状态，因此 LiteLLM 失败时仍会打开工作台。

本次修改既要修复 UTF-8 启动故障，也要把安装版的产品契约改为“受管配置和 LiteLLM 就绪后才允许生产”。

## 目标

1. Windows 安装版只允许使用 `.provision` 导入的公司图片、脚本和视频供应商，以及固定的豆包 TTS。
2. 其他历史或手工创建的供应商在安装版中不可见、不可编辑、不可调用，但不破坏数据库历史引用。
3. 首次打开时呈现空工作台和明显的配置提醒；导入前禁用新建项目和生产入口。
4. 导入成功后自动拉起 LiteLLM，健康检查通过后立即解锁，无需用户重启。
5. 后续每次启动安装版 EXE 都自动确保 LiteLLM 运行；LiteLLM 不健康时工作台保持锁定。
6. 豆包 TTS 继续直接调用豆包官方 API，不经过 LiteLLM；但全局工作台仍以 LiteLLM 就绪为解锁条件。
7. `npm run dev` 等源码开发流程保留现有全部供应商配置能力。

## 非目标

- 不删除历史供应商、项目或任务数据。
- 不把豆包 TTS 改为 LiteLLM 转发。
- 不在安装包中内置真实 `config.yaml`、`.provision`、API Key 或 COS 凭据。
- 不承诺抵御已控制本机 Windows 账户、数据库或安装目录的恶意管理员。
- 不用一次真实、可能计费的模型生成作为每次启动的健康检查；启动门禁验证本机代理、配置状态和进程健康，真实上游错误仍由对应任务返回。
- 不改变 macOS 安装版的供应商策略。

## 受管部署模式

新增独立的安装版信号 `CREATIVE_STUDIO_MANAGED_DEPLOYMENT=1`。它只由 Windows **已安装布局**的启动器和安装版 PowerShell 入口设置。

不复用 `CREATIVE_STUDIO_DESKTOP=1` 作为受管策略开关，因为该变量同时用于 macOS 和其他桌面能力。开发态 `npm run dev`、`start-windows.cmd` 和启动器的源码开发布局不得设置新的受管信号。

服务端是策略权威：前端隐藏仅用于体验，不能充当执行边界。所有策略函数在非受管模式下返回 unrestricted，以保证开发态行为不变。

## 配置状态与受管清单

导入状态升级为无秘密的 v2 结构，示意如下：

```json
{
  "schemaVersion": 2,
  "profileName": "公司统一配置",
  "importedAt": "2026-08-06T00:00:00.000Z",
  "configHash": "<sha256>",
  "managedProviders": {
    "image": ["<provider-id>"],
    "script": ["<provider-id>"],
    "video": ["<provider-id>"],
    "tts": ["doubao-seed-tts-2"]
  }
}
```

受管 ID 必须来自已经解密并通过严格 schema 校验的 provision 明文，不能根据显示名称、模型名称或“是否配置了 Key”猜测。状态文件不保存 Key、endpoint 密钥、密码或完整 provision 内容。

导入顺序为：完整解密与校验 → 准备数据库和文件更新 → 原子应用配置 → 最后原子发布 v2 状态。任一步在持久化前失败都不得产生部分状态。成功再次导入会覆盖受管清单和相同稳定 ID 的凭据，用于 Key 轮换。

旧 v1 状态缺少可靠的 ID 清单，在受管安装版中视为“需要重新导入”，不得通过字符串特征自动放行。当前只有测试安装，没有既有同事部署，因此该一次性重新导入是可接受的安全取舍。

## 供应商允许策略

受管模式同时校验“ID 在导入清单中”和角色结构，避免仅伪造一个 ID 即被放行。

| 角色 | 允许条件 | 调用路径 |
| --- | --- | --- |
| 图片 | ID 在 `managedProviders.image`；类型为 `gateway-task-image`；base URL 为 loopback；使用公司网关环境凭据 | 本机 LiteLLM |
| 脚本/视觉分析 | ID 在 `managedProviders.script`；`executionScope=company`；协议属于 provision schema 允许范围；base URL 为 loopback | 本机 LiteLLM |
| 视频 | ID 在 `managedProviders.video`；类型为 `openai-video`；base URL 为 loopback；使用公司网关环境凭据 | 本机 LiteLLM |
| TTS | ID 在 `managedProviders.tts` 且严格等于 `doubao-seed-tts-2`；类型为 `doubao-http-chunked`；使用 provision 声明的官方 HTTPS endpoint | 豆包官方 API 直连 |

受管模式下：

- 未导入时，供应商集合 API 返回空的安全元数据集合；
- 导入后，集合 API 只返回上述允许项；
- 通用供应商新增、删除、启停和字段编辑入口关闭；受管配置只能通过 `.provision` 更新；
- 针对隐藏供应商的 item API、任务创建、重试、队列执行、默认供应商解析和预览调用必须在服务端拒绝；
- 旧项目若引用隐藏供应商，应返回明确的“该供应商不在公司受管配置中”，不得自动改用另一供应商；
- 数据库中的隐藏行保持原样，以保护历史项目和迁移兼容性。

豆包 TTS 本身不依赖 LiteLLM，但为保持统一生产流程，LiteLLM 不健康时仍不得单独解锁 TTS 或其他工作台功能。

## 安装版状态机与界面

安装版对用户呈现四种明确状态：

| 状态 | 判定 | 界面与能力 |
| --- | --- | --- |
| `unconfigured` | 无 v2 状态、配置哈希不匹配或受管清单无效 | 首页可打开；显示醒目导入提醒；禁用新建项目和生产入口；设置页开放导入 |
| `starting` | v2 状态有效，正在启动或检查 LiteLLM | 显示“正在启动公司模型服务”；工作台保持锁定 |
| `ready` | v2 状态有效且 `127.0.0.1:4000` LiteLLM 健康 | 解锁项目与生产流程；只展示允许供应商 |
| `failed` | runtime 缺失、端口冲突、进程退出、健康超时或其他受控启动错误 | 保持锁定；显示脱敏原因；提供重试和重新导入入口 |

首次安装没有项目时，首页自然呈现空项目列表，并在主要操作位置显示“请先导入公司配置”提示和“立即导入配置”按钮。若本机因重装保留了旧项目，可以只读看到项目存在，但不能新建、进入生产或触发任务，直至状态为 `ready`。

供应商设置页在受管模式下不再显示通用创建表单或第三方类型选项：

- 未配置时显示文件选择、密码输入和导入说明；
- 启动中显示明确进度；
- 就绪后显示公司配置名称、导入时间、代理状态，以及允许供应商的只读配置状态；
- 始终保留“重新导入配置”用于 Key 轮换；
- 失败时显示安全诊断摘要、“重新启动 LiteLLM”和“重新导入配置”。

API Key、密码、完整 endpoint 鉴权参数和配置正文不得回显。

## LiteLLM 自动启动流程

### 首次导入

1. 本地 Node 应用先运行，以便显示空工作台和导入界面。
2. 用户选择 `.provision` 并输入密码。
3. 服务端完成解密、schema 校验和原子配置发布。
4. 配置发布成功后立即调用幂等的 sidecar 启动控制器。
5. UI 轮询受管运行状态；LiteLLM 健康后自动切换为 `ready`，无需重启页面或 EXE。
6. 启动失败时保留已经验证并发布的配置，状态进入 `failed`，用户可直接重试；重新导入可替换错误或已轮换的配置。

### 后续启动

1. Windows 已安装布局设置受管部署信号并启动本地 Node 应用。
2. 若 v2 状态和配置哈希有效，启动链自动、幂等地确保 LiteLLM 运行。
3. 应用在代理健康前只能呈现 `starting` 或 `failed` 锁定界面。
4. 不再存在“sidecar 失败但工作台照常可生产”的降级路径。
5. 已有健康且受控的 sidecar 可以复用；未知进程占用 4000 端口时必须拒绝接管并给出安全提示。

### 编码修复

打包 sidecar 必须显式以 UTF-8 模式启动 CPython：命令行使用 `-X utf8`，并为子进程设置 UTF-8 标准流编码。不得依赖终端机器的活动代码页或区域设置。启动测试必须包含中文或其他非 CP936 安全字符的 UTF-8 YAML，以防回归。

### 停止与轮换

- 现有停止快捷方式、启动窗口退出和 `/api/shutdown` 继续同时回收受控 Node/LiteLLM 进程。
- 再次导入成功后必须重启 LiteLLM，使新配置和新 Key 生效；重启健康前重新锁定工作台。
- PID、根路径与端口仍需按既有受控状态文件校验，不能终止不属于本安装根的进程。

## 服务端门禁

新增共享的受管部署状态和供应商策略模块，供页面、API、队列和默认配置解析器复用。至少覆盖：

- 新建项目；
- 图片、脚本、素材分析和视频任务创建；
- 单条混剪、批量生产、TTS 预览和最终渲染中会触发模型的入口；
- 任务重试、恢复和队列真正执行前的二次校验；
- 图片、脚本、视频和 TTS 供应商列表与 item API；
- 自动选择默认脚本、视觉、视频或 TTS 供应商的逻辑。

允许在锁定状态调用的最小接口包括：只读首页所需数据、受管状态查询、provision 导入、LiteLLM 重试、必要的安全日志摘要和正常关闭。具体白名单应集中定义，避免各页面自行判断。

即使前端状态陈旧，服务端门禁也必须拒绝非 `ready` 的生产请求。队列在领取或重试历史任务时还要重新验证供应商允许策略，避免导入轮换后继续执行已被移出清单的任务。

## 错误处理与诊断

用户可见错误使用稳定、安全的分类，不直接展示 Python traceback：

- 尚未导入或需要重新导入；
- provision 密码错误、文件损坏或 schema 不兼容；
- 配置哈希不匹配；
- 内置 LiteLLM runtime 缺失或损坏；
- 4000 端口被未知进程占用；
- LiteLLM 进程提前退出；
- LiteLLM 健康检查超时；
- 其他可重试的本机启动错误。

完整诊断只写入本机脱敏日志。日志与状态 API 不得输出 API Key、Authorization、Bearer、密码、runtime env 内容、完整 provision 内容或带签名的 COS URL。

## 测试策略

实施遵循测试先行，至少新增或调整以下测试：

1. **编码回归测试**：同一打包 Python 默认区域设置下读取含非 CP936 字符的 UTF-8 YAML；受管启动命令必须以 UTF-8 模式成功。
2. **启动契约测试**：替换当前“sidecar best-effort、不得等待”的旧断言，验证安装版会自动启动、健康前不解锁、失败进入锁定状态且可重试。
3. **配置状态测试**：v2 清单只来自通过校验的 provision；错密码、篡改文件和非法角色不产生部分状态；v1 状态要求重新导入；再次导入更新清单。
4. **供应商策略测试**：fresh DB 中迁移插入的可灵/即梦不可见；历史图片、脚本、视频和 TTS 行不可见、不可编辑、不可执行；允许的公司供应商和固定豆包 TTS 可用。
5. **API 绕过测试**：直接调用通用 provider CRUD、任务创建、重试或隐藏 provider item API 均被服务端拒绝。
6. **开发态回归测试**：未设置受管信号时，现有供应商列表、CRUD 和执行语义不变。
7. **界面状态测试**：未配置提示醒目、新建项目禁用、导入后进入启动中、健康后解锁、失败后显示重试入口。
8. **安装负载测试**：确认私有 Node/Python/LiteLLM 与启动脚本齐全，PowerShell 文件保持 UTF-8 BOM，负载不含秘密或本地数据。
9. **最终 smoke test**：在隔离数据根导入无真实密钥的测试 provision，验证 Node 与 LiteLLM 只监听 `127.0.0.1`、状态从未配置到就绪、停止流程同时回收两个进程。

真实公司模型和豆包 TTS 的计费调用不属于自动化构建测试；如需最终业务验收，应由配置管理员明确授权后单独执行。

## 验收标准

- 干净 Windows 10/11 x64 机器无 Node、Python、npm 或 pip 也可安装。
- 首启显示空工作台和明显导入提醒，新建项目与生产入口不可用。
- 未导入时看不到任何第三方或历史供应商。
- 正确导入后 LiteLLM 自动启动；无需重启即可解锁。
- 每次打开安装版 EXE 都会自动确保 LiteLLM 健康，失败时工作台保持锁定并提供安全诊断与重试。
- 安装版只展示和执行 provision 清单内的公司图片、脚本、视频供应商及固定豆包 TTS。
- 豆包 TTS 直连官方 API；LiteLLM 仍是整个工作台的全局就绪门禁。
- 直接调用 API 或重试历史任务不能绕过受管策略。
- `npm run dev` 的现有供应商能力不受影响。
- 所有应用与代理监听地址保持 loopback，安装包、日志、API 和状态文件不泄露秘密。

## 发布与兼容

- 当前尚无同事部署，因此不为 v1 导入状态实现自动猜测迁移；测试安装升级后需重新导入 `.provision`。
- 默认卸载继续保留本地数据。重装后若发现旧 v1 状态，应显示“请重新导入公司配置”，不能自动放行。
- 完成实现后重新构建 `dist/windows/CreativeStudioSetup.exe`，执行负载扫描、静态与运行测试，并交付文件大小和 SHA-256。
