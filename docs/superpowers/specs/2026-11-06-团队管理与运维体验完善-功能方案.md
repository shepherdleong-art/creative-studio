# 团队管理与运维体验完善

**状态：** `ready-for-agent`

**确认日期：** 2026-11-06（UTC+8）  
**交付阶段：** 需求规格；尚未实施、测试、打包或部署。  
**范围：** 统一生产服务的任务展示、并发分配、公共资源发布、错误中心、管理员运维，以及工作台轻客户端登录保持。

## Problem Statement

管理员需要在界面里看清团队正在制作什么、使用什么模型，并随着成员增加统一管理资源和维护服务器。目前有七类问题：

1. 制作任务没有完整显示本次实际使用的模型，尤其脚本等任务难以追溯。
2. 首页和任务步骤直接显示 UUID、内部模块名及执行键，用户将其感知为“乱码”，无法快速理解正在进行的制作工作。
3. 个人并发需要逐人配置，缺少团队默认规则与按真实需求动态分配的机制；有闲置容量时也不一定能提速。
4. 管理员已在设置中上传资源，发布时却还要寻找和输入资源 ID，重复操作且不清楚发布后员工能否真正使用。
5. 错误中心要求人工填写技术错误码；系统已有部分自动记录，但没有覆盖全部重要失败链路。
6. 备份、升级、恢复主要依赖终端脚本，管理员希望在前端完成，并查看进度、结果和可清理空间。
7. 用户明确反馈：关闭客户端再打开就需要重新输入密码，希望勾选记住登录后 30 天内保持登录。

本轮只整理已讨论的需求，不授权修改业务代码、操作生产数据、升级服务器或分发客户端。

## Solution

提供面向管理员和员工的完整界面流程：

- 任务主信息使用中文名称、项目／画布、制作步骤、人员、供应商和实际模型；原始技术编号保留在排查详情。
- 团队默认采用自动公平分配，按当前有合格排队任务或运行占额的成员分配共享容量；人少可借用空闲名额，人多在后续准入时调节。保留手动固定模式和个人例外。
- 现有成员也迁移到继承团队自动规则；模型权限、费用额度、账号停用和暂停生成分别保留。
- 在设置上传一次后，资源自动进入公共资源的待发布列表；管理员按名称和预览选择，再点击一次“发布给团队”，全程不手填资源 ID。
- 错误由系统捕获、关联和生成编号；员工看自己的错误，管理员集中排查，不要求用户编写技术错误码。
- 备份与维护页提供立即备份、上传升级包并升级、选择备份并还原整套业务数据、预览并清理无用文件等按钮。
- 登录页提供“记住登录状态（30 天）”；修复实际关闭重开丢登录的问题，不以保存明文密码替代会话持久化。

验收以管理员／员工的实际页面操作和现有业务接口为主要边界，另以真实轻客户端和隔离测试服务器验证进程退出及维护切换。该验收范围已获用户确认。

## User Stories

1. 作为管理员，我希望在团队任务中直接看到本次使用的模型，以便判断任务是否用了预期能力。
2. 作为管理员，我希望同时看到供应商名称，以便区分同名模型在不同供应商的调用。
3. 作为管理员，我希望历史任务展示执行时的模型，以便供应商设置修改后仍可追溯。
4. 作为员工，我希望看到自己任务的项目名称与中文制作步骤，以便知道当前在做什么。
5. 作为管理员，我希望首页与完整任务页使用一致的任务名称，以便不用理解两套内部术语。
6. 作为管理员，我希望保留按发起人分组、成员筛选和状态筛选，以便快速找到某个人的任务。
7. 作为排查人员，我希望仍能展开原始任务编号、执行记录与版本，以便定位问题而不干扰正常阅读。
8. 作为管理员，我希望区分制作任务与一次次调用记录，以便不把润色、标题修复或重试误认成额外成片或重复扣费。
9. 作为管理员，我希望只配置一次团队并发规则，以便增加成员时不用逐人填写。
10. 作为新成员，我希望自动继承团队规则，以便具备模型和费用权限后正常排队生产。
11. 作为管理员，我希望现有成员也转为继承自动规则，以便旧的固定上限不会继续阻止自动提速。
12. 作为有生产任务的成员，我希望系统按实际任务需求分配容量，以便只打开页面的其他人不会占走生产名额。
13. 作为当前唯一有需求的成员，我希望在真实上游容量内借用空闲名额，以便更快完成可并行的工作。
14. 作为后来加入生产的成员，我希望逐步得到公平的运行机会，以便不会一直被先提交的大量任务挤占。
15. 作为正在生成的成员，我希望其他人加入后自己的已提交任务仍继续，以便不浪费已有生成和费用。
16. 作为管理员，我希望可以切换手动固定模式，以便需要控制速度时明确限制并发。
17. 作为管理员，我希望为个别成员设置例外并可恢复继承，以便兼顾特殊需求和日常管理便利。
18. 作为管理员，我希望看到规则来源、当前占用和等待原因，以便区分个人限制、共享容量及其他条件。
19. 作为管理员，我希望并发变化不改动模型权限和费用额度，以便生产速度与访问、费用控制各自清楚。
20. 作为管理员，我希望设置中已上传的资源直接出现在待发布列表，以便不重复上传或查找 ID。
21. 作为管理员，我希望按名称、源文件、版本、条目数和预览选择资源，以便确认发布内容正确。
22. 作为管理员，我希望上传后仍需点击“发布给团队”，以便检查完再让员工使用。
23. 作为管理员，我希望资源列表显示待发布与已发布状态，以便避免不清楚当前团队正在使用哪个版本。
24. 作为员工，我希望发布后的完整模板和条目都能使用，以便不会只看到名称却打不开内容。
25. 作为已有任务的成员，我希望公共模板更新不改变已冻结的输入，以便历史生成和任务恢复仍可追溯。
26. 作为员工，我希望出错时系统自动生成错误编号，以便不用知道技术错误码怎么写。
27. 作为管理员，我希望错误关联人员、项目／画布、任务、模型、阶段和版本，以便减少来回询问。
28. 作为员工，我希望断网时发生的错误在恢复连接后能够补报，以便客户端异常不会完全丢失。
29. 作为管理员，我希望重复上报不会刷满错误列表，以便集中处理真实故障。
30. 作为员工，我希望只看到自己的错误和诊断，以便其他成员的工作内容不会出现在我的页面。
31. 作为管理员，我希望在前端立即备份并查看结果，以便不打开终端也能维护服务器。
32. 作为管理员，我希望看到备份时间、类型、校验状态和可用性，以便选择可靠的还原点。
33. 作为管理员，我希望在网页上传升级包并预览版本，以便不手工把包放入服务器目录。
34. 作为管理员，我希望确认升级后系统自动备份和执行升级，以便不用逐条运行脚本。
35. 作为管理员，我希望页面断开或服务器重启后仍能查看维护进度，以便知道操作是否完成。
36. 作为管理员，我希望升级失败时保留明确的状态与恢复路径，以便不会误以为已经完成或反复点击重复执行。
37. 作为管理员，我希望选择一份备份还原整套服务器业务数据，以便在必要时回到一个明确时间点。
38. 作为管理员，我希望还原前保留当前状态并验证备份，以便切换失败或选错还原点时仍有退路。
39. 作为管理员，我希望清楚知道还原点之后的数据如何处理，以便不会误以为新旧数据会自动合并。
40. 作为管理员，我希望先看到清理范围和预计释放空间再确认，以便有把握地清理无用文件。
41. 作为成员，我希望正常项目中的原素材和成片不被这次历史清理删除，以便现有制作成果仍可使用。
42. 作为管理员，我希望维护记录显示真实发起人，以便多人管理时可以追溯操作。
43. 作为员工，我希望勾选记住登录后关闭客户端再打开无需输入密码，以便每天顺畅开始工作。
44. 作为员工，我希望重启电脑和更新客户端后仍保留有效登录，以便正常使用不会反复中断。
45. 作为员工，我希望主动退出或修改密码后按规则重新登录，以便明确控制设备上的账号访问。
46. 作为管理员，我希望停用账号后已有登录也失效，以便停用行为真正生效。
47. 作为验收人员，我希望使用隔离数据和模拟供应商完成自动验收，以便验证功能时不影响生产数据或产生付费调用。

## Implementation Decisions

以下是行为合同和基于现有架构的实施约束；具体表名、路由命名、算法实现和任务拆分由后续实施确定，不把尚未复现的推测当作根因。

### 1. 任务展示与模型追溯

- 首页、团队任务列表及排查信息复用一致的展示语义：项目／画布名称、中文任务名称、中文子步骤、成员、状态、供应商、模型。保留已有按发起人分组和筛选能力。
- 当前源码的模型投影主要来自图片与视频任务；脚本等调用已存在执行时供应商快照。优先读取对应执行快照，兼容可信旧记录，不能拿当前供应商配置替换历史事实。
- “实际模型”指系统本次实际配置并提交的模型标识；如果另有可验证的供应商返回模型，可单独展示。供应商内部不可见路由不能推断；缺失记录显示“未记录”，尚未选择显示“待确定”，不适用的本地工作显示“不适用”。
- 多模型或重试更换模型的任务，按实际执行记录展示，不将某一次模型冒充整项任务唯一模型。等待中已确定的配置不标成已经调用。
- 内部步骤键解析为中文业务步骤，例如第几条文案、生成、润色和标题修复。不能把原始键中的任意数字未经语义核验就当成业务条目或次数；未知步骤用可理解的通用名称，原始值放入详情。
- 完整 UUID、内部步骤键、执行记录、输入与版本编号继续可复制，不作为主标题。普通页面不返回密钥或整个供应商快照。
- 不改变业务任务、任务尝试、执行调用和费用的含义；页面标明当前列表计数口径。首页与任务页不能把一条脚本的多个子步骤计为多份作品或多次确定扣费。

### 2. 自动与手动并发

- 分开两层配置：真实上游共享容量是硬边界；团队／个人策略决定如何使用容量。“自动”不是自动探测上游额度，也不是随在线人数无限增加总并发。
- 团队默认模式为自动公平共享；提供手动固定个人并发默认值。成员默认继承团队模式，可设置明确的个人固定上限例外，并可恢复继承。
- 自动分配按各共享资源池的实际任务需求进行。合格排队成员须具备模型权限、费用条件及运行条件；只有登录或浏览页面不计作生产需求。已受理或受理结果不明的请求持续计入真实占额。
- 无需求者不预留空闲份额；有足够并行工作且不受其他限制的单个成员可借用空余容量。多人竞争时，在后续名额释放时按公平顺序准入，不能依赖各模块 worker 抢占速度或随机分配。
- 公平性以运行机会和共享名额为口径，不承诺不同模型、不同耗时任务同时完成。容量小于竞争人数时轮流准入，不能因整数均分为零而让所有人停滞。
- 示例：池容量为 10，只有 A 有足够可执行工作时可使用最多 10 个名额；B 加入时不取消 A 的现有请求，新释放的名额优先补足 B 的机会；两人持续有需求且无其他约束时趋向均衡。20 人竞争 10 个名额时应可持续轮转，无长期饥饿。
- 个人固定上限是最大占用约束，不是保留席位；仍受共享池容量和公平准入约束。自动模式不得自动放宽模型权限、费用额度、账号状态或管理员明确的暂停状态。
- 已确认迁移：现有成员的旧固定并发值不再作为运行限制，统一改为继承团队自动规则；新成员同样继承。迁移记录原值以便审计，只执行一次，不在以后升级或启动时覆盖新设的个人例外。
- 迁移不更改费用额度、模型权限、账号停用、明确暂停或团队维护状态。旧并发为零与显式暂停是不同状态，不能混同；自动模式不绕过任何独立的禁生成条件。
- 下调容量、切换模式或改变成员数只影响后续准入，不取消已有付费调用、不丢失结果、不释放受理不明请求的占额。剩余容量不足时清楚显示等待。
- 规则落实在共享执行准入边界，覆盖图片、视频、脚本、画布以及使用共享池的配音／对齐入口，包括指定执行记录的路径。多个入口不能各自拥有一份可突破总上限的计数。
- 检查模块内部固定 worker 限制和任务内依赖；只提升真正允许并行的部分。某池拥堵不能无理由堵住同一成员在其他空闲池的独立任务。本地实拍重组和本机 Agent 不纳入本轮集中统计。
- 管理界面显示策略来源、当前占用、固定上限或自动状态、共享池占用及等待原因；自动分配不展示为永久承诺的个人配额。

### 3. 公共资源上传与发布

- 设置仍可上传／创建资源；公共资源页读取同一份受管内容形成候选列表，不要求重复上传，也不复制一套内容产生双重管理。
- 至少覆盖已有设置入口中的产品策略知识库、脚本模板库、爆文模板及视频提示词模板；其他已支持发布的资源按同一原则接入。BGM 既有上传、试听和发布能力继续可用。
- 候选资源通过真实权限与资源登记查询，显示名称、类型、源文件、版本、条目数或适用预览、发布状态。无候选项时引导到相应上传入口，不能要求编造或手填 ID。
- 上传成功进入待发布状态；只有管理员点击“发布给团队”后员工才可使用。程序内部仍使用稳定身份，不把文件名当作资源 ID。
- 库、当前修订和必要条目作为完整可用版本发布；不要求管理员分别发布内部库根、修订、条目，也不能只更改库根可见性就报成功。
- 沿用已确认的团队当前版本和历史快照合同：新版本经显式发布后供新任务使用，旧任务保留已冻结输入；取消上传、解析失败、发布失败都不切换当前版本。
- 已上传版本可从列表选中发布；重复点击幂等，并发发布发现基准版本变化时提示刷新确认，不能静默覆盖其他管理员刚发布的版本。
- 员工不能修改或发布公共资源；私人资源不会因管理员打开发布页而自动公开。个人空库不能遮住已经发布的团队版本。
- 现有公共页直接上传入口可保留，但应与设置上传共用资源和版本状态，不形成两套团队当前版本。

### 4. 错误中心与自动上报

- 正常使用流程自动生成错误码和错误编号。手工填写技术码与任务 ID 的表单退出常规流程；错误编号查询、复制排查信息和诊断包仍保留。
- 覆盖服务端生成提交／轮询／结果下载、API 异常、存储和媒体执行失败，以及轻客户端界面异常、上传／下载失败和更新失败。复用既有诊断记录与执行关联，不另造无法串联的日志系统。
- 自动关联可信的成员、项目／画布、任务、执行尝试、阶段、模型和版本；无法取得的字段明确缺失，不凭客户端传入的任意任务编号认定归属。
- 普通界面先显示中文原因、时间、关联任务及可行动提示，技术码放在详情。取消、正常排队和预期表单校验不能当成系统故障大量上报；已经自动恢复的事件与最终失败须可区分。
- 同一事件使用稳定身份去重；断网时客户端有界保存脱敏事件，恢复后补报，切换账号不得错归属。上报本身失败不递归制造新的错误风暴，也不阻塞正常业务。
- 只记录排查所需的脱敏信息；不上传素材原文、完整请求体、密钥、Cookie、签名 URL 或完整鉴权串。员工仅看本人，管理员按授权查看团队记录。
- 自动错误采集是本轮交付项，不以保留一个手工反馈表单代替。

### 5. 前端备份、升级、还原与清理

- 所有入口只供管理员使用，员工不能通过直接调用接口执行。使用固定受控动作和受管对象身份，不能把网页做成任意命令、任意文件路径执行器。
- 维护作业保存真实发起管理员、动作、目标、阶段、状态、时间和结果。重复请求不会重复启动同一操作；互斥维护动作不能同时修改同一实例。
- 复用现有备份屏障、引用保护、迁移 gate 和维护状态机。操作通过持久作业交给应用之外、不会随被升级应用停止的受控执行器；页面可重连查询原作业，不因一次 HTTP 断开丢失结果。
- 现有回环控制凭据不下发浏览器，不直接开放原来对外封闭的运维控制通道。新增网页业务入口重新验证管理员身份及来源。

**备份**

- 提供“立即备份”和备份列表，显示备份类型、时间、校验状态、大小及可否还原。沿用既有定时备份与保留策略，不因新增手动按钮更改其频率。
- 一致性校验完成后才显示成功；空间不足、备份失败显示原因，不产生可用于还原的假成功记录。手动／升级前／还原前备份按各自用途保留，不混入普通缓存清理。

**升级**

- 已确认流程：网页选择并上传服务器升级包 → 校验兼容性与完整性 → 显示当前／目标版本 → 管理员确认升级 → 自动备份、执行升级、自检 → 展示结果。
- 不需要管理员先用终端上传文件或填写服务器路径。仅接受受控服务器发布包；损坏、结构不符、不兼容或来源无法满足现有发布信任要求的包不能进入切换。
- 复用已有发布清单及校验能力，保留运行数据、外部密钥与部署配置；上传失败不改变当前运行版本。不得把“压缩包能解压”视为可升级。
- 切换前进入维护并处理在途请求与受理不明证据；已接受请求不因升级被无依据重发。应用重启后界面能恢复显示同一维护作业。
- 失败时报告阶段及当前实际运行版本；仅在代码／数据兼容性允许时回退，不能承诺任意迁移后都可直接回切。无法自动恢复时保持明确维护状态和可继续处理的记录。
- 第一版不做联网自动发现新版、自动下载新版或无人确认自动升级。

**整套还原**

- 已确认还原含义：选一份备份，将整套服务器业务数据恢复到那个时间点。单项目找回仍由回收站处理。
- 进入操作时显示还原点、覆盖的业务范围、当前版本兼容性，以及还原点之后新增／修改的数据不会自动合入恢复后的业务库。
- 执行前先保存并验证当前状态；在新的独立数据根还原并校验，成功后再确认切换。当前状态的备份与原数据根保留为退路，不边读取生产库边原地覆盖。
- 备份之后的数据保留在还原前备份和受保护旧数据根中，不出现在已回到过去的活动业务视图中；第一版不自动合并新旧数据。切换前后都要能明确区分当前活动数据根与保留副本。
- 保留现有还原后的禁调度与核查机制；远端实际已付费／已受理情况不会随数据库倒退而撤销。结合执行证据核对在途和未知提交，完成前不得自动重发或恢复付费生产。
- 还原作业记录必须在被还原数据库之外保持连续，不能因业务库回退而丢失发起人和进度。当前管理员需要按受控流程完成重新认证与切换后的访问核验；恢复历史会话不得让已撤销登录重新有效。
- 业务还原不等于操作系统镜像恢复，也不未经校验覆盖证书、系统服务账号或部署密钥。缺少必要依赖或兼容条件时停止切换并给出明确原因。

**无用文件清理**

- 已确认第一版仅包括失败任务临时文件、过期缓存，以及回收站中已删除且无引用的产物。
- 先扫描并展示分类、数量、预计可释放空间和被保护原因，再由管理员确认执行；实际执行重新检查引用和运行状态，不能仅凭过期的预览删除。
- 在途任务、历史版本、备份 pin、恢复核查或其他有效引用仍需要的内容不得删除；不能只靠文件修改时间、名称或目录位置推断“无用”。
- 正常项目中的原素材、当前成片和历史正式产物不属于按时间自动清理对象；备份、账本、执行证据、错误审计也不属于普通缓存。
- 展示实际删除结果、释放空间、跳过和失败原因，重复清理可安全重试。沿用现有回收站永久清理保护，补齐统一入口与批量预览。

### 6. 记住登录与关闭重开修复

- 已确认提供“记住登录状态（30 天）”，适用于关闭客户端、重启电脑及正常客户端更新后继续登录；不保存明文密码或把令牌写入前端可读存储。
- UI 补充约定：用户可明确勾选或取消，已选偏好可保留；未选择记住时只保持当前会话，不能仍静默写入 30 天持久登录。勾选后的 30 天按本次认证起算，不承诺无限滑动续期。
- 主动退出、修改密码、管理员重置凭据或账号停用后，旧登录凭据按撤销规则失效；修改密码后要求重新认证，不能保留其他设备旧会话。本条以本次已确认的重新登录语义为准。
- 用户报告的稳定触发是“关闭客户端再打开”；现有源码已有持久 Cookie 和 Electron 持久分区。实施首先复现并记录故障边界，区分 Cookie 未落盘、会话目录变化、会话撤销、启动鉴权及实际运行版本差异。
- 当前关闭流程直接退出进程且未见显式等待 Cookie 保存，只是排查线索，尚不是确认根因；不能只添加保存调用或复选框就宣称修复。
- 正常关闭与更新退出都需要保持有效会话与独立稳定的客户端状态；用户退出账号则撤销会话，二者不得混同。关闭客户端不关闭统一生产服务。
- 有效会话启动直接进入工作台；过期／撤销后显示登录页和明确提示。短暂网络故障不能擅自清掉本来有效的登录。
- 交付包含受影响轻客户端的修复版本与真实启动入口验收；具体打包、旧安装更新和生产分发在后续授权范围内执行，本次规格写入不代表已获部署授权。

### 7. 跨模块约束

- 复用现有团队身份、资源权限、执行准入、诊断及维护模块；保持统一生产服务与工作台轻客户端的职责边界。
- 新配置、操作状态或会话策略如需持久化，采用所属模块追加迁移并遵守共享备份、锁和审计 gate；不修改已发布迁移，不在首次启动时反复重置成员策略。
- 新 UI 使用中文与现有设计令牌，覆盖浅色、深色和系统主题。技术编号、脚本命令和内部资源层级不再成为完成正常操作的必要知识。
- 任何自动化不能越过真实上游限制、模型权限、费用额度、项目归属、未知提交保护和维护屏障；本次不改变收费与历史任务快照语义。

## Testing Decisions

### 已确认的测试边界

用户已确认：主要通过管理员／员工的页面操作及既有业务接口观察行为；自动化采用隔离数据根和模拟供应商，不动生产数据、不发起付费生成；补充真实轻客户端关闭重开及测试服务器备份、升级、还原实机验收。

优先复用现有团队 HTTP／浏览器验收夹具和共享执行 facade，避免每个 UI 组件另开一套测试入口。进程退出和停服升级无法由普通接口测试证明，因此保留两项必要的高层进程边界：真实轻客户端启动器、隔离 Windows 服务器维护执行器。缺少实机环境时必须标记未验收，不能以 mock 结果替代。

好的测试验证用户可观察结果与重要约束：模型正确、中文可读、员工确实能用、任务确实公平获得准入、错误可关联、会话真实保留、维护真正可恢复。避免只断言某函数被调用、源码包含某字符串或快照与实现一模一样。

### 验收矩阵

| 编号 | 主要边界 | 通过条件 |
| --- | --- | --- |
| A01 | 管理员与员工任务页面／查询接口 | 图片、视频、脚本、画布及可用媒体调用显示可信模型；历史设置变化不改历史模型；缺失和不适用明确，不泄露供应商秘密。 |
| A02 | 首页与任务列表 | 原始 UUID／内部步骤不作主标题；已知步骤中文化、未知步骤可理解；详情仍可复制；成员分组、筛选和记录计数口径不退化。 |
| A03 | 团队策略与账号管理接口 | 新老成员默认继承；旧固定上限一次性迁移；后续个人例外不被重置；权限、费用、暂停和停用状态保留。 |
| A04 | 共享执行 facade 与实际模块调用入口 | 单人借满空闲容量、多人加入后公平获得释放名额、人数大于容量仍轮转；指定执行记录路径同样受约束，没有 worker 抢占绕行。 |
| A05 | 多池／多模型执行 | 不同池的独立任务不因队首拥堵无理由停滞；串行依赖不被破坏；局部 worker 限制与可观察吞吐一致。 |
| A06 | 手动策略／并发变更／重启恢复 | 固定上限有效，切换和降额不打断已受理请求；未知提交仍占额；重启、多入口争用不超限、不重复发送。 |
| A07 | 设置上传→公共发布→员工实际使用 | 上传一次进入候选，未发布员工不可读，点击发布后库／版本／条目均可用；不需手填 ID；个人空库不遮挡。 |
| A08 | 公共版本变更 | 重复发布幂等；解析失败、取消和并发冲突不误切版本；既有任务继续使用冻结输入；越权发布被拒绝。 |
| A09 | 模拟故障→错误中心 | 服务端和客户端各类故障自动获得错误编号及可信上下文；员工只能读本人；诊断脱敏且不误计正常取消／等待。 |
| A10 | 客户端断网与错误重试 | 断网后有界保存并补报，同一事件去重，换账号不串记录，上报失败不递归，不阻塞业务。 |
| A11 | 备份 UI 与真实维护作业 | 管理员点击完成经校验备份；重复提交不重复执行；空间不足／失败无假成功；列表可选择真正可用的备份。 |
| A12 | 网页上传包→测试服务器升级 | 无终端完成上传、版本展示、确认、备份、升级、自检；坏包拒绝；断开页面和重启应用后可查同一作业。 |
| A13 | 维护失败与权限边界 | 非管理员、越权请求、任意路径／命令均被拒绝；冲突动作互斥；失败阶段与实际版本明确；仅按兼容条件回退。 |
| A14 | 测试服务器整套还原 | 先验证当前备份，在新数据根恢复并切换；指定还原点业务状态正确，较新数据保留在受保护副本中；维护审计持续存在。 |
| A15 | 还原后的执行与登录 | 未知付费请求不重发；证据核查完成前不自动生产；管理员能重新认证；已撤销的旧会话不因还原复活。 |
| A16 | 清理扫描→确认执行 | 预估和实际结果可对照；预览后新增引用会阻止删除；在途、历史与备份引用均受保护；正常项目素材和正式产物保留。 |
| A17 | 真实轻客户端登录与关闭重开 | 勾选后登录立即关闭／正常使用后关闭／重启电脑／客户端更新，未过期会话仍进入工作台；必须走实际启动入口。 |
| A18 | 登录生命周期与多账号 | 未勾选不跨会话保持；30 天到期、主动退出、改密、重置、停用会撤销旧凭据；网络波动不误清会话；换账号不串数据。 |
| A19 | 多角色综合流程 | 管理员发布资源、调整并发，员工提交任务并查看模型，模拟错误可定位，管理员维护后业务恢复；浅深主题和现有核心流程可用。 |

## Out of Scope

- 本轮规格交付不修改业务代码、不运行数据库迁移、不升级或重启生产服务器、不上传升级包到真实服务、不删除用户数据。
- 不做联网发现新版、无人值守自动升级、任意终端命令执行、操作系统镜像还原或多机灾备平台。
- 不按保留天数自动删除正常项目、原素材、成片或历史正式产物；不自动合并还原点前后的数据库。
- 不自动猜测供应商最大容量，不纳入本机 Agent／本地实拍重组的调用，不保证超过已配置上游容量的速度。
- 不修改模型计价、费用账本、月度额度口径或原有项目隔离；不把任务展示改造扩大为全历史报表重构。
- 不保存明文密码，不取消认证／TLS／CSRF，不把诊断原文、凭据和完整供应商快照暴露给前端。
- 不要求新增一个彻底重构的业务任务聚合看板；本轮先解决名称、步骤、模型、计数说明与现有列表一致性。
- 不重复实现已经上线的发起人分组或公共模板能力；实施前按实际基线复核并补齐本规格合同。

## Further Notes

### 已确认决策与授权

| 确认项 | 最终结论 |
| --- | --- |
| Q1 公共资源 | 设置上传一次，进入待发布列表，点一次发布后全员可用，不填 ID。 |
| Q2 登录 | 记住登录状态 30 天；关闭客户端、重启电脑仍有效；主动退出、改密或停用后重新登录。 |
| Q3 自动并发 | 按实际任务需求公平分配；团队默认、个人例外、手动模式并存；已开始任务不中断。 |
| Q4 清理 | 先清无用临时文件、过期缓存、回收站无引用产物；先预览再确认。 |
| Q5 登录症状 | 用户确认关闭客户端再打开就需要登录。 |
| Q6 旧成员策略 | 现有成员统一继承自动规则，旧固定值不再限制；权限和费用独立。 |
| Q7 升级入口 | 网页选包上传、校验与版本预览、确认后自动备份升级；第一版不联网找新版。 |
| Q8 还原 | 整套业务数据回到选定备份时间点；先保存当前状态、验证备份、再确认切换。 |
| 测试边界 | 页面和业务接口为主，补真实客户端关闭重开与测试服务器备份→升级→还原；隔离数据、模拟供应商、零付费。 |

目前没有阻止规格定稿的产品问题。具体池容量沿用受控配置，不在本规格虚构数值；算法实现、维护作业机制和客户端故障定位属于工程工作，不要求用户选择代码细节。如实施发现恢复无法满足既定合同、运行版本存在重大差异或必须改变数据保留范围，先提出明确差异，不自行缩减已确认功能。
