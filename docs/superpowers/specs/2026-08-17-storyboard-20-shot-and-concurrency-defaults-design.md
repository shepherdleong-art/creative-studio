# 分镜组 20 张上限与生成并发默认值设计

日期：2026-08-17

## 目标

- 将单个分镜组的业务上限从 9 张提高到 20 张。
- 一个含 20 张分镜图的分镜组在执行“生成分镜”时创建 20 个独立图片任务。
- 图片生成与视频生成的默认并发统一为 10，并继续允许用户在 1–10 之间手动调低。

## 当前事实

- 9 张限制分别存在于原始分镜上传、宫格选择、旧分镜创建入口和创建分镜组 API。
- 旧的项目完整创建分支可以直接写入任意数量的 `shots`，当前可绕过主创建 API 的上限。
- `apply-scene` 会遍历组内全部分镜，每张创建一个图片任务；该流程本身没有 9 张限制。
- 图片队列按所选并发数领取任务，因此 20 个任务在并发 10 时由最多 10 个 worker 同时处理，其余任务排队。
- 后续脚本生成会读取分镜组全部图片，并把 4 MiB 视觉载荷预算按图片数量均分；20 张时每张约有 205 KiB 压缩预算。
- 图片并发的新项目、数据库新建默认值和部分缺省回退目前是 3。
- 视频并发的数据库默认值、运行时缺省值和界面初始值目前已经是 10。

## 设计

### 分镜组上限

定义一个前后端共用的分镜组上限常量，值为 20。所有入口统一引用该值：

- 原始分镜上传单次最多选择 20 张；项目仍可分多次上传更多原始素材。
- 创建分镜组时最多按顺序选择 20 张。
- 活跃工作台和保留的旧创建入口都展示“1–20 张”及实时已选数量。
- 创建 API 接受去重后的 1–20 个项目内图片 ID；第 21 张返回明确的 400 错误。
- 仍保留的项目完整创建分支执行同样的去重、1–20 张校验，不能绕过主 API 门禁。
- 数据库结构不增加数量约束，也不需要迁移。

### 图片并发默认值

将图片生成的统一缺省值设为 10，并继续钳制在 1–10：

- 新建项目页面初始值为 10。
- 新数据库中 `projects.concurrency` 的默认值为 10。
- 创建项目 API 未收到并发参数时使用 10。
- 图片队列启动、恢复及分镜生成弹窗在没有可用项目值时回退到 10。
- 已有项目中已经保存的 `projects.concurrency` 不迁移、不覆盖；用户原先主动选择的值继续生效。

### 视频并发默认值

视频链路现有默认值已经是 10，因此保留现有行为，并用回归测试锁定以下口径：

- 新项目的 `videoConcurrency` 缺省为 10。
- 视频面板初始值与视频队列无项目值时的回退值为 10。
- `VIDEO_CONCURRENCY` 环境变量仍可覆盖运行时默认值，但最终值保持在 1–10。

## 数据流

1. 用户最多选择 20 张原始分镜图并创建分镜组。
2. API 校验图片属于当前项目，在单个事务中写入 1–20 条 `shots`。
3. 用户选择场景参考图并点击生成。
4. `apply-scene` 为每条 `shot` 创建一个图片任务；20 张即 20 个任务。
5. 图片队列按项目当前并发执行，默认最多 10 个任务同时运行，其余保持排队状态。

## 错误与兼容性

- 0 张仍拒绝创建，错误口径保持“至少需要 1 张分镜图”。
- 21 张及以上拒绝创建，错误文案改为“分镜图最多 20 张”。
- 重复图片 ID 继续先去重再计算数量与排序。
- 现有 1–9 张分镜组不受影响；现有项目保存的图片、视频并发值不被改写。
- 20 张分镜进入脚本生成时继续使用现有 4 MiB 总预算和逐图动态压缩；如果单图在其预算内仍无法压缩，沿用现有明确错误，不静默丢图。
- 不修改供应商并发闸门、重试、轮询或队列调度算法。

## 测试与验收

- 回归测试证明主创建 API 与旧完整创建分支均为 20 张通过、21 张拒绝、0 张拒绝、重复 ID 按去重结果计算。
- UI 合同测试证明活跃入口和旧入口均使用 20 张上限，不再出现 9 张分镜组文案或选择限制。
- 并发测试证明图片缺省值为 10、取值仍钳制在 1–10，视频缺省值继续为 10。
- 脚本视觉测试使用 20 张图验证逐图预算、总载荷和完整图片数组，不把新增容量转化为脚本生成阶段的隐藏失败。
- 运行相关独立测试、ESLint，并在风险需要时运行生产构建。

## 非目标

- 不把分镜组改成无限数量。
- 不将实际并发提高到 10 以上。
- 不改变“新场景图生成”的候选数量上限；该链路中独立存在的 9 与分镜组容量无关。
- 不扩大单个分镜对应的“运镜描述”批量创建上限。
- 不覆盖已有项目已经保存的并发设置。
