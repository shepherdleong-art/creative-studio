# 智能混剪本地 BGM 导入与试听设计

日期：2026-07-30
状态：已确认，待实施
范围：智能混剪第 3 步“预览调整”右侧栏的“背景音乐”卡片

## 1. 背景

当前“背景音乐”卡片只能从已经存在于全局音乐库中的曲目下拉选择，并调整音量、淡入和淡出。音乐库由 `dataRoot()/storage/bgm/` 与 `final_edit_bgm_tracks` 共同承载，现有预览和渲染流程都通过曲目 ID 使用音乐，但界面没有导入入口，也没有独立试听入口。

本功能允许用户从本机选择一个或多个音频文件，将其复制进 Creative Studio 的全局本地音乐库。导入后，界面立即刷新曲目列表、自动选中本批第一首成功处理的音乐，并允许用户独立试听。

## 2. 目标

- 在“背景音乐”卡片中提供多文件导入入口。
- 将音乐复制到可直接浏览和管理的 `storage/bgm/` 根目录。
- 保留原始文件名；仅在同名冲突时增加可读的数字序号。
- 导入完成后立即刷新当前成片组的 BGM 下拉列表。
- 自动选中本批第一首成功导入或复用的曲目。
- 提供当前选中 BGM 的独立试听与停止能力。
- 复用现有曲目索引、媒体读取、草稿 revision、预览混音和最终渲染链路。
- 保持 Windows 与 macOS 行为一致。

## 3. 非目标

本轮不实现：

- 文件夹选择或文件夹递归扫描；
- 删除、重命名、移动或整理音乐库；
- 音乐分类、标签、收藏、搜索或合集；
- 波形剪辑、入点/出点或音乐片段截取；
- 在线音乐搜索或下载；
- BGM 变速；
- 导出视频目录或文件名可读性改造。该问题另行设计，避免与 BGM 导入耦合。

## 4. 已确认的产品决策

### 4.1 导入方式

采用浏览器系统文件选择器。用户可以一次选择一个或多个音乐文件，前端通过原生 `fetch` 和 `FormData` 上传，服务端将文件复制进本地音乐库。

不保存或依赖用户原文件的绝对路径。原文件被移动、改名或所在移动硬盘断开后，不影响已经导入的 BGM。

### 4.2 音乐库目录与命名

新曲目直接写入：

```text
dataRoot()/storage/bgm/<可读文件名>
```

例如：

```text
storage/bgm/轻快音乐.mp3
```

不得在文件名或目录中加入哈希、UUID 或其他不可读标识。

同名冲突时，在扩展名前增加从 1 开始的序号：

```text
轻快音乐.mp3
轻快音乐(1).mp3
轻快音乐(2).mp3
```

扩展名大小写和原文件名主体保持不变。只有发生同名冲突时允许增加上述数字序号。

完全相同的文件重复导入时复用已有曲目，不再复制一份；同名但内容不同的文件按序号规则保存。数据库内部现有的文件完整性校验值可以继续使用，但不得出现在文件名、目录名或用户界面中。

### 4.3 支持格式与限制

支持格式与现有 BGM 扫描器一致：

- MP3
- WAV
- M4A
- AAC
- FLAC
- OGG

扩展名匹配不区分大小写，但文件仍须通过 FFmpeg/ffprobe 音频探测，不能只信任扩展名或浏览器提供的 MIME 类型。

上传限制沿用现有本地素材导入的安全边界：

- 单次最多 100 个文件；
- 单文件不超过 256 MB；
- 单次请求总大小不超过 512 MB。

## 5. 界面与交互

### 5.1 卡片布局

“背景音乐”卡片保持现有精致极简视觉，不改变音量、淡入和淡出控件的位置与语义。

卡片布局调整为：

1. 第一行：完整宽度的 BGM 下拉框；
2. 第二行：“添加音乐”和“试听/停止”按钮；
3. 后续各行：现有音量、淡入、淡出滑杆。

下拉列表只显示可读文件名，不显示 `bgm/` 前缀、内部路径或校验值。

### 5.2 添加音乐

- “添加音乐”触发隐藏的多选文件输入框。
- 输入框使用 `multiple`，并通过 `accept` 提示支持的音频格式。
- 上传必须使用原生 `fetch + FormData`，不得经过 JSON 请求封装。
- 导入期间按钮显示“导入中…”，并阻止重复提交。
- 导入不影响当前已经选择的 BGM；只有服务端返回至少一首成功处理的曲目后才切换选择。
- 导入完成后刷新当前成片组，并自动选中用户选择顺序中的第一首成功导入或复用的曲目。
- 其余成功曲目出现在同一个下拉列表中。

### 5.3 独立试听

- 没有选择 BGM 时，“试听”按钮禁用。
- 点击“试听”从头播放当前选中曲目，按钮切换为“停止”。
- 再次点击“停止”会暂停并把试听进度归零。
- 切换下拉曲目时立即停止上一首试听，不自动播放新曲目。
- 离开预览步骤、切换成片组或组件卸载时必须停止并释放试听资源。
- 独立试听与时间线整体播放互斥；启动其中一个时停止另一个，避免两路音频叠加。
- 独立试听使用音乐原始播放电平，不应用成片的 BGM gain、淡入或淡出。时间线整体预览和最终渲染继续准确使用这些成片设置。
- 试听媒体继续使用现有 `GET /api/final-edit-bgm/[id]/file` Range 流式接口。

### 5.4 状态反馈

- 卡片内显示简短结果，例如“已导入 3 首，1 首失败”。
- 详细失败原因使用现有页面消息区域展示，包含原始文件名和可理解的中文原因。
- 状态文字使用可访问的 live region，使键盘和辅助技术用户能感知导入结果。
- 成功、部分成功和全部失败必须有不同文案，不能统一显示“导入完成”。

## 6. API 设计

### 6.1 新增接口

```text
POST /api/final-edit-bgm
Content-Type: multipart/form-data
```

请求字段：

- `files`：一个或多个音频文件。

BGM 音乐库是全局共享资源，因此接口不接受 `projectId`、`shotSetId`、`groupId` 或客户端提供的目标路径。服务端固定从 `dataRoot()` 解析 `storage/bgm/`。

### 6.2 响应

响应应区分新建、复用和失败：

```ts
interface BgmImportResponse {
  firstSuccessfulTrackId: string | null;
  imported: Array<{
    id: string;
    filename: string;
    relativePath: string;
    durationUs: number;
  }>;
  reused: Array<{
    id: string;
    filename: string;
    relativePath: string;
    durationUs: number;
  }>;
  errors: Array<{
    filename: string;
    code: string;
    message: string;
  }>;
  tracks: Array<{
    id: string;
    filename: string;
    relativePath: string;
    durationUs: number;
  }>;
}
```

`firstSuccessfulTrackId` 由服务端按照用户原始选择顺序计算，避免新建曲目与复用曲目分列返回后丢失跨列表顺序。`imported` 和 `reused` 各自在自身列表内保持用户选择顺序。`tracks` 是刷新后的完整可用音乐列表，按现有音乐库排序规则输出。

响应状态：

- 至少新建一首曲目：`201 Created`；
- 没有新建曲目，但至少复用一首已有曲目：`200 OK`；
- 所有文件都属于逐文件校验失败：`422 Unprocessable Entity`，仍返回完整错误列表；
- 无文件、非 multipart、文件数超限等请求级错误：`400`；
- 单文件或请求总大小超限：`413`；
- 不可恢复的磁盘或数据库错误：`500`。

### 6.3 当前成片组刷新

音乐导入本身不修改成片组或草稿 revision。前端收到成功响应后：

1. 重新请求当前 `final-edit-group`，取得最新 `bgmTracks`；
2. 使用刷新后的当前 variant revision 调用现有 `set_bgm` 命令；
3. 将响应中的 `firstSuccessfulTrackId` 写入当前草稿；
4. 继续沿用现有自动保存、冲突恢复和 revision 记录逻辑。

整个客户端流程进入现有串行操作队列，防止上传完成时与其他草稿编辑命令竞态。如果用户已经离开当前成片组，则只完成全局音乐库导入，不再修改旧组的选择。

## 7. 服务端设计

### 7.1 模块边界

新增独立的 BGM 导入服务，职责包括：

- 解析和校验上传文件；
- 将每个文件依次暂存到私有临时目录；
- 校验格式、探测时长和计算现有完整性校验值；
- 查找完全相同的现有曲目；
- 解析安全且可读的目标文件名；
- 解决同名冲突；
- 原子写入音乐库并更新索引；
- 返回逐文件结果并清理临时文件。

API 路由只负责调用服务和把领域错误映射为 HTTP 响应，不在路由中实现文件业务逻辑。

### 7.2 文件名安全

- 只采用上传文件名的 basename，丢弃任何客户端路径片段。
- 拒绝空名称、`.`、`..`、空字节和当前操作系统无法安全创建的文件名。
- 不根据客户端字段接受目标目录。
- 目标路径解析后必须仍位于 `dataRoot()/storage/bgm/` 内。
- 除同名数字序号外，不主动改写合法的原始文件名。

### 7.3 同名与并发

候选名称从原名开始，若已存在则依次尝试 `(1)`、`(2)`。文件创建必须使用排他模式，保证两个并发导入请求不能覆盖同一路径。

如果目标候选在检查后、写入前被另一请求占用，则继续尝试下一个序号。不得使用“先判断不存在，再普通覆盖写入”的非原子流程。

### 7.4 文件与数据库一致性

- 文件先写入同目录临时文件，通过探测后再原子落位。
- 数据库索引写入失败时，删除本次新建的目标文件。
- 完全相同文件的并发导入必须收敛到一个曲目记录；失败的一方重新读取已有记录并按 `reused` 返回。
- 导入失败、请求中断或进程异常时，不得留下可被扫描器误识别为正式曲目的临时扩展名文件。
- 现有 `scanFinalEditBgm` 继续支持用户手工放入 `storage/bgm/` 的历史方式。

## 8. 错误处理

采用“逐文件部分成功”语义：

- 某个文件不支持、损坏或探测失败，不回滚其他成功文件；
- 每个失败项保留用户选择时的原始文件名；
- 磁盘空间不足、目录无写权限或数据库不可用时返回明确中文错误；
- 临时文件和未完成目标文件始终清理；
- 自动选中只使用服务端按原始选择顺序计算的 `firstSuccessfulTrackId`；
- 若全部失败，保持当前 BGM 选择不变。

错误码至少覆盖：

- `files_required`
- `too_many_files`
- `file_too_large`
- `upload_too_large`
- `unsupported_audio_format`
- `invalid_audio`
- `invalid_filename`
- `bgm_write_failed`
- `bgm_index_failed`

## 9. 数据与兼容性

- 不修改 `final_edit_bgm_tracks` 现有表结构。
- `relativePath` 继续保存相对 `storage/` 的路径，例如 `bgm/轻快音乐(1).mp3`。
- 服务端通过路径 basename 生成 API 和界面需要的 `filename`，前端不自行解析 Windows 或 POSIX 分隔符。
- 现有 BGM 曲目、成片草稿、历史 revision、渲染快照和使用记录保持兼容。
- 渲染器继续根据相对路径和现有完整性校验读取音乐。
- `storage/` 继续作为运行数据排除在安装包和 Git 之外。

## 10. 测试设计

### 10.1 领域与文件测试

- 单文件成功导入；
- 多文件按选择顺序处理；
- 中文、空格、括号和长文件名；
- 大小写不同的支持扩展名；
- 同名不同内容生成原名、`(1)`、`(2)`；
- 完全相同内容重复导入返回 `reused`；
- 两个并发同名导入不覆盖文件；
- 两个并发相同内容导入只产生一个曲目记录；
- 扩展名伪装、损坏音频、空文件和不支持格式；
- 单文件、数量和请求总大小限制；
- 部分成功；
- 数据库失败、磁盘写入失败和临时文件清理；
- 路径穿越文件名与音乐库边界检查。

文件测试使用 `os.tmpdir()` 下的独立临时目录和内存 SQLite，不读写真实 `storage/bgm/`。

### 10.2 HTTP 契约测试

- 真实 multipart 请求能读取多个 `File`；
- JSON、空 FormData 和越限请求返回正确状态与错误码；
- 客户端伪造的目标目录、项目 ID 等字段被忽略；
- 响应包含 `firstSuccessfulTrackId`、`imported`、`reused`、`errors` 和完整 `tracks`；
- 有新曲目时返回 `201`，仅复用已有曲目时返回 `200`，全部逐文件失败返回 `422`。

### 10.3 UI 契约与浏览器测试

- 文件输入支持 `multiple` 和正确的音频 accept；
- 导入按钮状态、成功摘要和失败详情；
- 下拉列表使用可读文件名；
- 导入后刷新列表并自动选择第一首成功曲目；
- 全部失败时不改变当前选择；
- “试听/停止”状态切换；
- 切换曲目、切换成片组和卸载时停止试听；
- 独立试听与时间线播放互斥；
- 键盘操作、禁用状态和 live region 可访问性。

### 10.4 渲染回归测试

- 选中通过新接口导入的 BGM 后，预览媒体接口支持读取和 Range；
- 最终渲染继续应用 BGM 音量、淡入、淡出、循环和时长裁切；
- 中文、空格和括号路径可以被 FFmpeg 正确读取；
- 原视频静音、TTS 与 BGM 混音行为不发生回归。

## 11. 验收标准

1. 用户可以在“背景音乐”卡片中一次选择一个或多个本地音乐文件。
2. 成功文件以可读名称复制到 `storage/bgm/` 根目录。
3. 文件名不包含哈希、UUID 或乱码；同名冲突只增加 `(n)` 序号。
4. 完全相同的文件不会重复占用空间。
5. 导入后下拉列表无需刷新页面即可显示全部新曲目。
6. 当前草稿自动选中本批第一首成功处理的曲目，并沿用现有自动保存。
7. 用户可以独立试听和停止当前选中 BGM，且不会与时间线音频叠加。
8. 单个坏文件不会阻止同批其他音乐导入。
9. 已有 BGM、历史草稿、预览和最终渲染保持可用。
10. Windows 和 macOS 均能处理中文及带空格、括号的文件名。

## 12. 后续工作

完成本设计后再单独编写实施计划。实施阶段遵循测试先行：先增加失败测试，确认测试因功能缺失而失败，再实现最小代码使其通过。导出视频目录和文件名可读性问题另行建立规格，不纳入本功能。
