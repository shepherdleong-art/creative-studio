# 详情页卖点层级与方向编排设计

> 日期：2026-08-31  
> 状态：设计已确认，待实施  
> 适用范围：详情页智能脚本生成（Script Studio）

## 1. 背景与问题

当前流程会把详情页中识别到的卖点全部展平成一张列表。脚本每次生成时，模型都要重新完成「理解全部卖点 → 归类 → 排序 → 按脚本方向选择 → 写作」。这带来三个问题：

1. 详情页本来已有的「大卖点标题 → 小卖点标题/图片文字」层级丢失了。
2. 卖点库已经复用时，模型仍然反复做选品策略，导致不必要的输入长度和推理时间。
3. 多条脚本都看到同一份完整卖点表，方向和卖点组合容易重复。

本设计不把「卖点多」视为错误。完整卖点库仍是可复用的产品资产；需要改变的是脚本生成前的编排方式。

## 2. 核心模型

### 2.1 卖点主题（Selling Point Theme）

主题对应详情页的一个主要信息区域，通常来自大标题，例如「久坐也舒服」、「小户型也能放下」。

- 主题用于规划、分组和排序。
- 主题标题不自动等于已核验事实。
- 主题可以为下属多条原子卖点提供语境，但不绕过证据门禁。

### 2.2 原子卖点事实（Atomic Selling Point Claim）

原子卖点是可以独立核验和被脚本引用的最小事实单元，例如「靠背采用 X 结构」、「宽度为 X cm」。

每条原子卖点保留：

- 事实文本、卖点类型；
- 逐字证据、页码和切片引用；
- 风险级别和证据门禁结果；
- 所属主题、在主题中的角色与重要度。

### 2.3 方向卖点包（Direction Selling Point Brief）

方向卖点包是本地编排器在脚本生成前准备的小份候选上下文，包含：

- 本条脚本的主主题；
- 必须优先考虑的卖点 ID；
- 可选的补充卖点 ID；
- 本地选择理由和候选数量。

对 15 秒脚本，卖点包默认提供 6–8 条候选，并将其中 2–3 条标记为优先事实。「6–8 条」是给模型的候选上下文，不是要把全部写进成片；最终 15 秒口播通常只使用 2–4 条事实。

## 3. 设计决策

### 🧭 Product Decision 1：保留完整卖点库，生成前做本地编排

- **选择**：提取和证据核验后保留全部合规原子卖点；每条脚本生成前，由确定性本地模块选出小型方向卖点包。
- **原因**：完整卖点库能支持后续不同平台、时长和脚本方向；本地编排可以避免每次让模型重新阅读与选择全库。
- **取舍**：需要维护一套可测试的方向匹配规则，但其结果更稳定、可解释、可重现。
- **Not now**：不在每次生成前再发起一次「请模型帮我选卖点」请求。

### 🧭 Product Decision 2：大标题是策划主题，不是证据豁免项

- **选择**：大标题记为主题元数据；实际写入脚本的数字、材质、结构、功效等仍必须来自通过门禁的原子事实。
- **原因**：详情页大标题常带有营销概括，可以帮助组织信息，但不能替代逐字证据。
- **取舍**：主题可能在证据不足时只做分组，不会被直接作为口播事实。
- **Not now**：不会因为文字更大、位置更靠上，就自动认定其为高可信事实。

### 🧭 Product Decision 3：多方向先分配卖点包，再并行写作

- **选择**：编排器一次为本轮全部脚本方向准备卖点包，而不是每条脚本各自独立选择。
- **原因**：只有看到整轮需求，才能对已使用主题和卖点做降权，在源头增加多样性。
- **取舍**：核心产品主题在事实不足时可以重复，但具体事实和组合应尽量不同。
- **Not now**：不追求绝对不重复；那会在卖点较少时牺牲真实性和脚本质量。

## 4. 方向编排规则

编排器只使用 `usable = true` 且未被用户禁用的原子卖点。证据失败、用户禁用或非法引用不得进入卖点包。

| 脚本方向 | 优先组合 |
| --- | --- |
| 痛点切入 `pain_point` | 1 个主题 + 2 条解决问题的事实 + 1 条证据型事实 |
| 场景种草 `scene_seeding` | 1 个场景主题 + 1–2 条体验/外观事实 + 1 条功能支撑 |
| 卖点直给 `feature_showcase` | 优先从 3 个不同主题各取 1 条强事实 |
| 对比突出 `comparison` | 参数、结构、材质、功效或认证类事实 |
| 开箱顺序 `unboxing` | 外观、结构、材质、安装/使用顺序相关事实 |
| 问题解决 `problem_solving` | 场景或问题 + 结构/功能 + 可核验结果 |
| 情绪体验 `emotional` | 场景、外观、材质与一条功能支撑 |

评分优先级由本地规则确定：方向类型匹配 > 主题中的角色 > 提取重要度 > 证据状态 > 本轮重复惩罚。排序和同分回退必须确定性，相同输入必须得到相同卖点包。

## 5. 数据契约与兼容

`script_studio_selling_points` 追加以下字段：

| 字段 | 含义 | 旧数据回退 |
| --- | --- | --- |
| `themeKey` | 修订内稳定的主题分组键 | 空字符串，由编排器按类型/页码等派生 |
| `themeTitle` | 详情页大标题或规范化主题名 | 使用卖点标题 |
| `hierarchyRole` | `primary` / `supporting` / `detail` | `supporting` |
| `importance` | 1–100 的页内相对重要度 | 50 |

迁移必须以新版本追加，不得修改已发布的 v1。手动编辑创建新修订时，主题与层级元数据必须原样保留。

视觉提取合约升级后，模型需为每条原子卖点返回主题与层级字段。老模型、老响应或老卖点库缺失字段时，本地回退必须仍能生成脚本，不得强制重读详情页。

## 6. 执行流程

### 6.1 首次提取

```text
详情页图片
  → 切片与视觉提取
  → 主题 + 原子卖点 + 证据定位
  → 去重与证据门禁
  → 保存完整层级卖点库
  → 本地为全部脚本方向编排卖点包
  → 模型只根据各自卖点包写作
```

### 6.2 复用卖点库

```text
读取已保存的卖点库
  → 本地重新编排方向卖点包
  → 模型根据小型卖点包写作
```

复用流程不重读图片、不重做卖点提取与证据门禁。

## 7. 可观测性与性能判断

`plan` 阶段快照需记录每个方向的：主题、必选卖点 ID、可选卖点 ID、候选数量和编排理由。任务因此可回放，也能区分「本地编排慢」和「模型写作慢」。

本改动的性能假设是：减少每次生成的候选卖点数和策略选择任务，可降低模型输入和推理时间。这不等于承诺某个固定秒数；真实收益必须通过同一供应商、同一卖点库的前后对比记录确认。

## 8. 验收标准

1. 新提取结果可保存主题、层级角色与重要度，手动修订不丢失这些字段。
2. 旧卖点库在不重新提取图片的情况下仍能生成卖点包。
3. 15 秒脚本每个方向最多向模型提供 8 条候选，且只包含可用卖点。
4. 相同输入多次编排结果一致；多方向卖点包在卖点充足时不完全相同。
5. 生成提示词不再包含全部卖点库，只包含当前方向卖点包。
6. 模型返回卖点包外的 ID 时不得进入脚本引用。
7. 任务 `plan` 阶段能回看卖点包的选择结果。
8. 新旧 schema 迁移、视觉输出兼容、方向多样性和 runner 接入均有本地回归测试。

## 9. 本次不做

- 不处理 Mimo 供应商故障。
- 不为了测速调用公司 Luna、Gemini 或其他真实 API。
- 不删减完整卖点库，不把用户的长期卖点资产固定截断为 6–10 条。
- 不让脚本模型重新看详情页图片。
- 不在本轮引入用户手工拖拽主题或调整编排权重的高级界面。

## 10. 实施交接

执行 AI 应先完整阅读本文与 `docs/reference/详情页智能脚本生成.md`，再检查当前工作树，保留所有与本功能无关的未提交改动。建议按以下顺序实施：

1. **迁移与领域类型**：在 `lib/script-studio/schema.ts` 追加新迁移，并在 `types.ts`、`libraries.ts` 打通新字段的写入、读取与手动修订复制。不得修改 v1。
2. **视觉提取合约**：在 `adapters/vision-extract.ts` 中读取主题与层级，递增 `promptContractVersion`；缺失新字段的响应必须有本地默认值。
3. **去重保真**：在 `dedupe.ts` 合并重复事实时保留主题、最强层级角色、最高重要度与全部证据定位。
4. **深模块编排器**：新建一个纯本地、确定性的卖点编排模块。公开接口一次接收卖点库、全部脚本计划和目标时长，一次返回全部方向卖点包；分组、评分、旧数据回退和重复惩罚都封装在模块内。
5. **生成边界**：`generator.ts` 只向模型传当前卖点包；归一化、时长补齐和确定性回退也只能使用该包内 ID，不能从完整库偷拿卖点。
6. **Runner 与快照**：`runner.ts` 在 `plan` 阶段完成本轮编排，把卖点包写入阶段快照，并在首稿与因相似度触发的重试中复用同一份包。
7. **调度器版本**：任务执行语义改变后，按参考文档要求递增 `bootstrap.ts` 的 executor version，避免 Next.js 热更继续运行旧闭包。
8. **文档同步**：把最终数据契约、运行语义和新测试命令同步到 `docs/reference/详情页智能脚本生成.md`。

最低测试覆盖：

- schema v1 → 新版迁移，以及新建数据库；
- 层级元数据持久化与手动修订保留；
- 老视觉响应、老卖点库的回退；
- 15 秒候选上限、不可用卖点排除、相同输入确定性；
- 卖点充足时的多方向差异，以及 `feature_showcase` 的跨主题选择；
- 提示词只包含卖点包，包外 ID 被拒绝；
- runner 的 `plan` 快照包含卖点包，并保留当前有界并行行为。

实施验证只使用本地假供应商。未获得用户单独授权前，不得调用 Luna、Gemini、Mimo 或其他真实供应商。

### Review 门禁

独立 review 时必须对照本文逐项确认：

1. 完整卖点库是否仍被保留，而不是在入库时截断。
2. 大标题是否只作为主题，没有绕过 `evidenceQuote` 和证据门禁。
3. 模型是否在所有生成、重试和补齐路径中都只能使用卖点包。
4. 多方向差异是否由本地编排产生，而不是仅在 prompt 中要求模型「不要重复」。
5. 旧数据是否无需重读图片即可复用，迁移是否只追加新版本。
6. 任务快照和测试是否足以证明上述契约，而不是只证明代码可编译。

## 11. 📚 Learning Point

详情页已经是一份经过人工编辑的商品叙事，大标题、小标题和对应图文之间的层级是有价值的策划信号。视觉模型应负责「把这份结构读出来」，证据门禁负责「确认哪些事实能用」，本地编排器负责「为每个方向准备什么」，脚本模型最后只负责「怎么说得好」。
