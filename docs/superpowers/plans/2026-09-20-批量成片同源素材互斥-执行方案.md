# 批量成片同源素材互斥执行方案

日期：2026-09-20。状态：实施中（A 方案）；本文件记录讨论共识与执行细节，供后续接手者核对。

> 2026-09-21 修正：真实批次表明同一原图会创建多个分镜组，各组 shotId 不同。
> v3 将同源键追溯到 `shots.sourceImageId`（不是视频任务的生成候选图），并让本片同源避让优先于跨片/历史窗口避让；历史用料不再视为本片已选素材。以下 v2 设计中的「shotId 足够」「历史占用天然纳入本片组集合」已被此修正取代。当前契约见 `docs/reference/批量生产模块.md`。

## 1. 问题（说人话版）

同一张分镜图（同一个分镜位 shot）会反复生成多条视频版次（V01、V02……），内容几乎一样。
但这些视频进了批量生产素材池后，系统只认**内容指纹**——指纹不同就是两个互不相干的素材。
分配器的避让维度（区间重叠、复用次数、重分配历史）都不覆盖「同源」；
而语义打分是「句段 × 素材场景」，同一分镜图的视频分析结果几乎一样、得分都高，
于是同源版次很容易**结伴进入同一条成片**——观众在一条片子里看到同一画面重复出现。

手动混剪侧同理：素材列表把同一分镜位的所有版次平铺，摆时间轴时容易摆重。

## 2. 讨论共识（2026-09-20 与需求方逐项确认）

| 问题 | 结论 |
| --- | --- |
| 撞车场景 | 批量生产成片 + 手动混剪素材池，两处都有 |
| 「按分镜组（shotSet）分批跑」能否解决 | **不能**。同源版次本来就住在同一个 shotSet 内，按组分批后它们依然同池同片。互斥键必须落在 shot / 分镜图粒度 |
| 互斥强度 | **软互斥 + 素材耗尽回退**（与重分配避让 `REALLOCATION_AVOID_PENALTY` 同风格），不硬禁 |
| 跨份（N 条成片之间） | **不互斥**——N 份成片自然消化 V01/V02 不同版次，版次不浪费 |
| 同组定义 | 同一分镜位 `shotId`（换图重做产生的多候选视频也算同源；`sourceImageId` 粒度太细） |

### 分层结论

- **A. 批量生产分配层同源互斥 —— 本期实施（本文档）**。
- B. 手动混剪素材池按 shot 折叠分组展示 —— 后续做，不在本期。
- C. 按 shotSet 组织分批 —— 缓议（对撞车无效，顶多算选素材的便利）。

## 3. A 方案实现细节

### 3.1 同源键入池（`lib/batch-production/media-catalog.ts`）

- `Module4SourceLocation` 增加 `shotId: string | null`（自由素材的 video_jobs.shotId 本身可空）。
- `parseSourceLocation` 兼容旧数据：旧 locationJson 无 `shotId` 字段 → 解析为 `null`。
- `registerModule4Video` 查询 video_jobs 时带出 `shotId` 写入来源定位。
- 旧行自动升级：`insertSource` 的 legacyMatch 按 `module4:<videoJobId>` 键匹配旧行后 UPDATE 为新 JSON。
- 新增导出 `resolveModule4AssetShotIds(db, assetIds)`：按 module4 来源反查素材的 shotId
  （仿 `resolveModule4AssetDisplayNames` 模式；多来源取第一个非空 shotId）。
- **不进内容指纹身份**，不影响冻结/缓存逻辑；linked/managed 来源无 shot 概念，天然为 null。

### 3.2 冻结输入携带 shotId（`lib/batch-production/allocation-store.ts`）

- `buildFrozenInput` 在读取素材池后调用 `resolveModule4AssetShotIds`，
  给每个 `AllocationAssetInput` 挂 `shotId`（无 module4 来源或来源无 shotId 时为 null）。

### 3.3 分配器同组软互斥（`lib/batch-production/allocator.ts`）

- `AllocationAssetInput` 增加 `shotId?: string | null`；
  `NormalizedAsset` 增加 `groupKey`：`shotId` 非空 → `shot:<shotId>`，否则 → `asset:<assetId>`
  （回落 asset 级 = 自己一组，行为与改动前完全一致）。
- 新常量 `SAME_SHOT_GROUP_PENALTY = 150`（与 `REALLOCATION_AVOID_PENALTY` 同量级，
  必须压过语义 ×100 + 钩子 ×8 + 质量 ×2 的理论上限）。
- 惩罚条件精确为「**同组不同素材**」：
  `usedGroupKeys.has(asset.groupKey) && !usedAssetIdsInPlan.has(asset.assetId)`。
  同一素材复用不同窗口仍只走原有 `reuseCount × -3` 轻罚——
  stitch 兜底把一条长素材切成多 chunk 是设计行为，不能被重罚误伤。
- 组集合按「`usedIntervals` 中 `planId === 当前 plan`」收集（经 `assetById` 映射 groupKey）。
  单条重分配时历史版本占用也以目标 planId 登记，天然纳入同组避让——「换一批画面」连同源兄弟一起换。
- 打分接入两处：主候选打分（`assignOne`）与拼接兜底（`stitchSegment`），防止兜底路径绕过互斥。
- 耗尽回退：同组候选被压分后仍是最高分时自然选中（软互斥），并追加 warning
  `same-shot-reused:<unitId|segmentId>`，不阻塞出片。
- `BATCH_ALLOCATION_RULE_VERSION` 升为 `batch-allocation-v2`：
  ruleVersion 是分配 run 幂等键（ruleVersion + seed + inputFingerprint）之一，
  升级后旧 run 不被复用、按新规则重跑；已持久化的 v1 结果仍是合法历史。

## 4. 影响面与兼容

- 改 3 个 lib 文件：media-catalog.ts、allocation-store.ts、allocator.ts。
- 无数据库 migration（locationJson 是 JSON 内加字段，旧行读取兼容、写入自动升级）。
- 无调度/渲染/导出链路改动；分配是纯函数，规则变化只影响新分配 run。
- 测试：`scripts/batch-allocation.test.ts` 增加同源互斥用例；
  `batch-allocation-stitch.test.ts`、`batch-media-catalog.test.ts` 视断言覆盖面补 shotId 断言。

## 5. 验收

1. 池中存在同一 shot 的 V01/V02 两条素材时，单条成片内两句段不再同时分到这两条
   （无其他素材时才回退并报 `same-shot-reused` warning）。
2. 同一素材不同窗口复用、stitch 同素材多 chunk 的行为与改动前一致（不被重罚）。
3. 无 shotId 的存量素材（linked/managed/旧 module4 行）分配行为与改动前一致。
4. `node scripts/batch-allocation.test.ts`、`node scripts/batch-allocation-stitch.test.ts`、
   `node scripts/batch-media-catalog.test.ts` 通过。
