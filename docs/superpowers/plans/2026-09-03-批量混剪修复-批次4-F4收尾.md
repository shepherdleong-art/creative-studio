## G1（P2）：`End` 聚焦到错误的行

### 现状

`components/ui/SystemFontPicker.tsx` 的 `handleListKeyDown`：

```ts
if (event.key === 'End') {
  event.preventDefault();
  if (tab === 'all') setVisibleCount(allTail.length);   // 异步
  const last = Math.max(0, visibleRows.length - 1);      // ← 仍是扩容前的长度
  setActiveIndex(last);
  window.setTimeout(() => focusRowControl(last, activeControl), 0);
  return;
}
```

`visibleRows` 来自本次渲染闭包，`setVisibleCount` 不会同步生效，所以 End **确实把结果全加载了，但焦点停在旧的第 80 项**。产品口径要求「End 会加载完整结果并聚焦末项」。

### 修改方案

- 先算出扩容后的真实末项下标（`allHead.length + allTail.length - 1`，收藏页用 `favRows.length - 1`），用这个值 `setActiveIndex` 并在 `setVisibleCount` 之后的 effect / `requestAnimationFrame` 里聚焦；不要依赖旧闭包里的 `visibleRows.length`。
- 更稳的写法：把「扩容 + 聚焦」收敛成一个 `pendingFocusRef = { index, control }`，在渲染后的 `useEffect` 里消费一次并清空——这样 G2 也能复用同一条通路，不用两处各写一个 `setTimeout`。

### 验证

- Playwright：字体数 > 80 的桩列表，打开面板 → 按 End → 断言 `document.activeElement` 的 `data-font-row` 等于最后一行下标，且该行的 `aria-label` 是排序结果的末项。

## G2（P2）：第 80/81 项边界 ArrowDown 不移动焦点

### 现状

同一个 `handleListKeyDown`：

```ts
let next = ... Math.min(visibleRows.length - 1, activeIndex + 1);
if (event.key === 'ArrowDown' && tab === 'all' && next === visibleRows.length - 1 && hasMore) {
  setVisibleCount((count) => count + BATCH_SIZE);
  window.setTimeout(() => focusRowControl(next, activeControl), 0);   // next === activeIndex
  setActiveIndex(next);
  return;
}
```

在当前批次最后一行时 `next` 被 `Math.min` 钳成 `activeIndex` 本身，所以这一下只追加了下一批、**焦点原地不动**，用户必须再按一次才能到第 81 项。产品口径要求「先同步追加下一批**再移动焦点**」。

### 修改方案

- 边界分支里目标下标应是 `activeIndex + 1`（追加后它一定存在），不能被扩容前的长度钳住。
- 复用 G1 的 `pendingFocusRef` 通路落焦点。

### 验证

- Playwright：桩列表 > 81 项，ArrowDown 连续走到第 80 项，**再按一次**就应聚焦到第 81 项（`data-font-row="80"`），不是停在原地。
- 顺带补 ArrowUp/ArrowLeft/ArrowRight/Home 的基础断言，以及「收藏页全部为缺失字体」时 ArrowDown 能聚焦 `aria-disabled` 选择按钮、ArrowRight 能到星标。

## G3（P2）：`createTask` 的裸 `catch` 吞掉所有插入错误

### 现状

`lib/script-studio/tasks.ts`：

```ts
try {
  const result = db.prepare(`INSERT ... ON CONFLICT(projectId, requestKey) DO NOTHING`).run(...);
  inserted = result.changes > 0;
} catch {
  // 极端并发下的唯一冲突落到回读分支，由 identity 决定复用或 409。
  inserted = false;
}
```

`ON CONFLICT DO NOTHING` 已经把唯一冲突处理掉了，这个 catch 实际只会接住**别的**失败（NOT NULL、FK、磁盘满、schema 未就绪……）。接住之后回读拿不到行 → 抛 `ScriptStudioError('conflict', '任务创建失败，请重试')`：用户拿到一个误导性的 409，真实原因既没日志也没上抛。这条撞 `AGENTS.md` 的「不许塞回会吞掉错误的旧 runner」。

### 修改方案

- 首选直接删掉 try/catch——`ON CONFLICT DO NOTHING` 已经覆盖了它声称要防的场景。
- 若要保留防御性，只在**确认是唯一约束冲突**时降级（`better-sqlite3` 的错误带 `code === 'SQLITE_CONSTRAINT_UNIQUE'` / `SQLITE_CONSTRAINT_PRIMARYKEY`），其余原样 `throw`。
- 回读拿不到行时抛的错不应复用 `conflict` 码——那是给「同 key 不同 body」的语义。换一个更诚实的码（沿用现有 `ScriptStudioError` 码表，别新增数据库字段）。

### 验证

- `node scripts/script-studio-tasks.test.ts`：新增一例——对一张**缺列/被破坏**的表调用 `createTask`，断言抛出的是底层错误而不是 `conflict`，且错误信息里能看到真实原因。
- 既有并发用例（worker_threads 那两组）必须继续绿。

## G4（P2）：overlay host 挂在 dialog 末尾，Tab 顺序跳到抽屉最后

### 现状

`components/batch-production/BatchCoverEditorDrawer.tsx` 与 `components/mixcut/CoverEditorDrawer.tsx` 都把

```tsx
<div ref={setFontOverlayHostRef} />
```

放在 `</aside>` **之后**、`</fieldset>` 之前。两个抽屉的焦点陷阱都是每次 Tab 从 `dialogRef.current.querySelectorAll(...)` 按 **DOM 顺序**重算的，所以从字体浮层内部 Tab 出去会一路跳到抽屉最后一个控件。

mixcut 那侧尤其明显：「共享字体」是 aside 的第 2 个 section，后面还有主标题、副标题、内置样式、自定义预设四段。

批次 3 的任务卡原文写过这条禁令（「别一律塞到 dialog 末尾」），实现没照做，代码注释却写着「位于触发器所在 section 之后紧邻」——注释也要一并改掉。

### 修改方案

- 把 host `<div>` 移到**触发器所在 section 的紧后面**：
  - `mixcut/CoverEditorDrawer.tsx`：紧跟「共享字体」那个 `<section>` 之后。
  - `BatchCoverEditorDrawer.tsx`：`BatchTextStyleEditor` 是在 `map` 里渲染两份（主/副标题），两份共用一个 host 就不可能同时紧邻两个触发器——**给每个 `BatchTextStyleEditor` 各配一个紧邻的 host**，或者让 `BatchTextStyleEditor` 自己在内部渲染 host 并传给它自己的 `SystemFontPicker`（更干净，调用方不用管）。
- host 必须仍然脱离 `overflow-y:auto` 的滚动字段，浮层继续用 fixed 坐标 + 高于抽屉的层级。
- 同步修掉两处与实际不符的注释。

### 验证

- Playwright：在两个封面抽屉里各测一次——打开字体面板 → 从面板内最后一个控件 Tab → 断言焦点落到**触发器所在 section 的下一个控件**，而不是抽屉页脚的按钮；Shift+Tab 反向同理；全程不跳出抽屉。

## G5（P3）：供应商解析仍在重放快路径之前

### 现状

`app/api/projects/[id]/script-studio/tasks/route.ts`：

```ts
const providers = resolveRuntimeProviders(providerId);   // ← 先解析
...
const existing = getTaskByRequestKey(db, projectId, requestKey);
if (existing) { /* 用 storedProvider 比身份，不用当前 providers */ }
```

身份比较本身写对了（用的是任务里冻结的 `providerId/providerModel`），但 `resolveRuntimeProviders` 在它**之前**就执行了。丢包重试期间如果供应商被删或变得不可用，这一行直接抛错，安全重试拿不到既有任务——与「重试期间供应商配置等外部状态变化不算 body 变化，也不能改变已创建任务首次冻结的执行身份」相悖。

### 修改方案

- 只有**派生 requestKey 的分支**需要 `providers`（key 里含 `providerId/providerModel`）。显式 `requestKey`（即「再生成一组」的 action key）不需要。
- 把 `resolveRuntimeProviders` 下移：显式 key → 先查既有任务，命中就直接用冻结身份返回，全程不碰当前供应商；没命中（或走派生 key）再解析。
- 注意 `buildSnapshot(providers.vision)` 只在真正创建时才需要，移动后保持这一点。

### 验证

- 新增 route 级或 `tasks` 级用例：先用显式 key 建好任务 → 把供应商置为不可用 → 用**同一 key/body** 重放 → 断言仍返回 `202 + created:false` 与同一 taskId，而不是抛供应商错误。

## 顺带记（不在本批范围，别顺手改）

- `components/ui/SystemFontPicker.tsx` 的 `id="system-font-picker-overlay"` 是固定值，同页多实例会撞 DOM id（`BatchStepScripts` 一屏就有 3 个）。要改就用 `useId()`。
- `components/script-studio/ScriptStudioPanel.tsx` 的再生成控件初始化 effect：`setTimeout(0)` + 提前写 `lastRegenerateSourceTaskIdRef`，在 `npm run dev` 的 React StrictMode 双调用下会丢初始化（控件停在默认 3 条/15 秒）。生产 standalone 构建不受影响。同一行还硬编码了 `count <= 6`，应改用 `SCRIPT_GENERATION_MAX_COUNT`。
- 「当前选中字体未检测到」的**浏览器**回归还没有：批次 3 review 已修好组件逻辑（`fonts` 不再掺 `value`）并补了「缺失收藏」的 Playwright 用例，但「打开老项目、其字体已卸载」这条路径受会话缓存只增不减的限制，在现有单页测试里造不出来，需要另起一个干净 page 的用例。
- 字形指纹（Canvas 宽度 vs fallback 基线，需注入固定 WOFF2）与同源两页收藏 `storage` 同步，仍然缺自动化覆盖。
