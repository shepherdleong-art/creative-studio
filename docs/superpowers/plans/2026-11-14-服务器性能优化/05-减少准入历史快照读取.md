# 05 减少准入历史快照读取

**状态：** `ready-for-agent`  
**依赖：** 04  
**规格：** [服务器性能优化](../../specs/2026-11-14-服务器性能优化-功能方案.md)

## 修改入口

- `lib/media-core/execution/admission.ts`、`records.ts` 及必要的策略读取。
- 先读团队统一模型调度参考、统一生产 ADR 和当前 unknown 自动并发过期规则。
- 不在本任务改 journal 全量校验或费用语义。

## 验收

保持活跃工作不变时，增加完成历史不使准入读取/解析完整历史输入；只在实际执行需要时加载完整输入，本轮缓存有界。保留个人覆盖、公平轮转、预算/权限、维护/fence、unknown真实占额与已释放预约。排除 journal 后，2000 条完成历史下准入 p50 工程目标下降 80%，同时报告内存。参照规格实施决定 6、9。

## 测试

扩展 `scripts/execution-admission.test.ts`、`execution-admission-contention.test.ts`；回归 `team-acceptance-fairness.test.ts`、`unknown-occupancy.test.ts`、`unified-reconcile.test.ts`。覆盖 0/500/2000 条大快照完成历史、pending/deferred/accepted/unknown混合需求，验证相同决策、读取量及无重复提交。

## Comments

**变更**

- `lib/media-core/execution/admission.ts`：准入事务内只查活跃需求（`pending/deferred/admitted/maybe_sent/accepted/reconciling/unknown`）的轻量投影，不再解析 `inputSnapshotJson`/`resultJson`；终态历史完全不参与每次准入。`automaticConcurrencyLimit` 明确只遍历该活跃集合。
- 移除模块级长期保留的 `demandSnapshots` WeakMap；改为单次准入内的有界缓存（按 actor 策略、按 pool 策略/已占名额、pool+actor 已占名额、held operationId 集合、月度费用、cost_unknown、自动公平上限、资格判定），事务返回即释放。
- 完整输入只在真正授予后按 ID `readOperation` 读取一次；`grant.operation.inputSnapshot` 仍是完整输入。授予路径不再重复读取同一行。
- `records.ts` 新增 `OperationDecision` 轻量投影与列清单；`admission-priority.ts` 的入参收窄为通道身份结构，供投影直接传入。
- 未改 `journal.ts` 全量校验/fsync/损坏拒绝、费用算法、unknown 判定与自动过期释放、个人覆盖、公平轮转、预算/权限、维护/fence。

**残留风险**

- 活跃需求投影仍随同时活跃任务数增长；这是真实需求，不随历史增长。
- 自动公平上限需要逐个判断活跃 pending/deferred 的资格；每个操作每次准入最多计算一次，仍读取这些活跃行的策略字段。
- 数字来自本机合成库，不代表生产端到端 SLA；contention 只计量 worker 的准入调用，不含启动恢复。
- `readMediaAdmissionPriority` 入参由 `OperationRecord` 收窄为结构类型，调用方不受影响。

### 代码审查修复（B 组）

- `waitingRowsByActor` 不再单独查询 `execution_operations`：从已取的活跃需求投影 `demandRows` 过滤 `pending`/`deferred`，按 `actorId, readySeq` 排序后分组；成员内 FIFO 顺序与原 `ORDER BY actorId, readySeq` 一致，成员轮转仍由外层 actors 顺序驱动。
- `heldCounts`（按 pool、pool+actor 计数）与 `heldOperationIds`（held 操作集合）合并为一次 `execution_reservations` 查询，在同一谓词 `kind='concurrency' AND state='held'` 上取回 `operationId/poolKey/actorId` 并在内存聚合；不再用 `GROUP BY` 与 `DISTINCT` 各扫一遍。
- 单次准入的 SQL 条数：需要等待行时少 1 条（waiting 查询），同时需要 held 计数时再少 1 条（held 查询合并）；判定仍使用同一事务内缓存，授予后不会读到新授予的占额，公平/预算/权限/unknown 语义不变。
- 测试：`scripts/execution-admission.test.ts` 的堆增长阈值从 48MiB 放宽到 128MiB，仅作结构性上限——快照字节/行数断言仍严格证明历史未被读取；`execution-admission-contention`、`team-acceptance-fairness`、`unknown-occupancy`、`unified-reconcile` 全部通过。
- 残留风险：活跃需求投影仍随同时活跃任务数增长（真实需求，不随完成历史增长）；内存聚合对 held 行的遍历量与原来的两次 SQL 聚合相同阶。
