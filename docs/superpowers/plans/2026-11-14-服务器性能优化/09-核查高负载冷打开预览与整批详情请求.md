# 09 核查高负载冷打开预览与整批详情请求

**状态：** `ready-for-human`

**优先级：** P2

## 观察

当前已部署构建 `team-server-performance-20261115-r1` 的隔离实例，准备 8 名员工、每批 100 卡、4,000 条各约 64 KiB 的历史快照及 192 个内容分析任务。分析正在执行时，第一位员工冷打开统一审片，12 秒寻帧看门狗内没有得到目标正文帧，页面持续显示“正在准备视频预览”。页面 JavaScript 异常与浏览器外网请求均为 0。

`full-03/user-0.har` 显示 10.5 秒内对 100 个成片计划发出 400 次 arrangement 请求：258 次完成，其余 142 次在测试结束关闭页面时被取消。观察到三簇请求，前两簇各 100 次，最后一簇 200 次；该页面没有收到视频响应。不要把关闭页面产生的取消计作服务器业务失败，也不要把本观察直接归因为解码器卡顿。

## 调查线索

`components/batch-production/review/BatchUnifiedReviewWorkspace.tsx` 的 `loadAllArrangements` 对全部 `workspace.cards` 发出 `Promise.all` 请求，全部完成后才更新 arrangements；依赖包含 `workspace.cards`，活跃工作区刷新会重新触发整批请求。该层不在任务 06 的 tasks/workspace 两类协调器保护内。

这是需要验证的贡献因素。现有证据尚未隔离冷打开等待的全部原因，也尚未给出回归引入提交。应分别量测首个可见成片所需数据、后台批量详情加载、素材缩略图/来源读取，以及不同卡片数和请求并发下的完成时间。

## 验收方向

- 同一隔离构建比较空闲/活跃批次冷进入与已打开页面的持续拖动，保留至少 20 次有意义采样及首帧时间，不能用预热后的成功覆盖冷进入失败。
- 若确认整批请求放大，优先复用聚合数据、按修订失效或分批加载；首个可见画面不应等待无关成片全部详情。保留编辑、契约、同源提醒、权限与历史产物语义。
- 每类后台详情请求有界；切批次与 A→B→A 不能应用旧响应；编辑/重试/发布后仍及时刷新。
- 实现后重跑 07，分别报告 cold 和 warm 场景；该任务当前只记录观察，业务代码未修改。

### 2026-11-15 修复与最终隔离复验

已确认并修复多个贡献因素；最终隔离高负载验收通过，**未部署生产**。

1. 整批详情请求放大：旧实现每次 workspace.cards 刷新都对 100 个计划 Promise.all，等全部完成才显示。现在由 `arrangement-loader.ts` 按内容修订复用、优先可见/选中计划、逐条交付；每个当前 loader 最多 3 个请求。批次/修订变化中止旧请求并拒绝迟到响应；编辑后等待新详情的 Promise 跨后台失效续接，保证撤销快照不丢。纯结构编辑也由 arrangementJson 的 SHA-256 失效，导入和明确刷新仍强制重取。
2. Windows 媒体子进程启动阻塞：20.34 秒原始 CPU 样本有 9.88 秒落在同步 spawnSync；栈对应 `canRunBinary` 反复执行 -version。缓存已验证且文件身份未变的二进制检查；路径/文件替换失效、失败短时重试、PATH 候选定期重验，真实执行及失败回退保留。回归中重复解析 100 次由 100 次版本启动降为 1 次。
3. 仅缓存版本检查仍不足：第二份 20.43 秒样本中同步启动为 0，普通 spawn 仍占 10.55 秒。媒体预览/校验会重复探测；准入延期也会重新切场景、抽帧。现按每次完整 SHA-256 已验证的内容复用元数据（最多 256 项），仅同一业务意图和已验证输入复用完成的准备帧（最多 16 组、图片字符串内存估算上限 64 MiB）。来源权限、健康、完整哈希前后核验、当前文件身份和最终发布检查仍执行；文件身份增加 ctime，准备完成后再检查。没有占住本地媒体位等待供应商，也没有跳过远端准入或改公平性策略。
4. 真实媒体回归先以“延期后 6 次抽帧 ≠ 首轮 3 次”失败，修复后多次延期均只准备一次；改写源文件仍被完整哈希拒绝。请求阶段成功或抛出非延期异常时释放准备缓存；未再重入的延期缓存由上限逐出或进程退出清理。单条分析默认路径和原始抽帧覆盖、场景内回退均保留。

### 2026-11-15 PR #10 补充修复：缩略图连接争用与读取突发

本轮在旧失败之外确认了两个可独立复现的原因。慢缩略图会占满浏览器同源连接，让视频 Range 无法及时得到响应；同一事件循环中连续处理同步读取，则会让静态脚本的每一块传输都等待下一轮。原 HAR 中约 177 KiB 的压缩脚本接收耗时达 12.4s，API 能返回 200 并不能证明页面已可用。

- 准备区及锁定素材卡使用可见性触发、最多 2 个请求的缩略图队列；离开或换来源取消在途及排队请求，回收 Blob URL。真实卡片 + 保持不返回的缩略图 + FFmpeg 合成视频回归，旧实现 2s 内取不到目标像素，新实现通过，重新挂载后全部可见图片仍加载。
- 团队 GET 读取由跨模块共享的 read-turn 队列每轮放行一个继续执行，给脚本和媒体 I/O 留出轮次；进入后重新授权，不缓存权限或结果，不等待整个 handler 完成。取消请求移出队列；FIFO、员工异步上下文及 8 项认证/资源/文件/传输/用量路由回归通过。24 个持续繁忙 HTTP 读取的回归中，压缩脚本接收由 7125.8ms 降为 642.2ms。
- 员工任务页的完整记录投影改为由已选 ID 集合驱动主键点查，避免 SQLite 为 actorId + IN 选择扫描员工历史的索引；最近任务复用同一实现。2003 组/2005 条各 64 KiB 快照的分页、全量搜索、分组、状态、费用与权限回归通过。
- 共享 SQLite 页缓存采用 32 MiB 预算。独立相同查询序列的逻辑读取次数由 45255 降至 21408，耗时约降四分之一；64 MiB 没有进一步减少读取，因此不采用更大预算。
- 准备区四个独立读取真正并行；项目页按需加载其他步骤编辑器，混剪入口保留在首屏，避免额外串行脚本请求。

诊断过程保留在 `outputs/05-日志与排查/2026-11-15-pr10-cold-fix/`。仅缩略图/查询/页面调整的 full-r2 仍只完成 12 次窗口内冷流程；full-r3 的关闭 Next gzip 实验首批页面失败，压缩迁移已撤回。最终 r4 保留原 gzip 和原验收脚本；最终整轮结论见 07 最新记录，不以局部探针替代完整验收。
