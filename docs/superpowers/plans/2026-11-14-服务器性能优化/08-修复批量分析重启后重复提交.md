## 问题

在当前已部署构建 `team-server-performance-20261115-r1`（源码 `ae47d895`）的独立实例中，一个批量内容分析请求已经到达本地模拟供应商，但尚未返回。强制结束实例并在同一临时数据根重启，没有点击重试，模拟供应商收到同一批量任务的第二次请求。旧 execution operation 保留 unknown，新 operation 为 maybe_sent。

这违反“重启不重复付费提交”的验收要求。所有复现均使用隔离 SQLite、合成媒体和回环模拟供应商，真实付费调用 0 次。尚未判定引入该缺陷的提交；不要据此修改生产数据或清除 unknown。

## 已定位的身份变更链路

- `lib/batch-production/scheduler.ts` 的 `recoverInterruptedWork` 将旧 running attempt 标为 interrupted，并让任务重新可领取。`claimNextTask` 仅对 `errorCode=execution_deferred` 的 interrupted attempt 复用身份；普通崩溃恢复会新建 attempt 并递增 `attemptNumber`。
- `lib/batch-production/executors.ts` 将 `claim.attempt.id` 同时作为内容分析的 `inputRevision` 和 `businessAttempt.id`。
- `lib/script-providers/index.ts` 以 `llm/<taskId>/<step>/<inputRevision>` 生成 operationKey，仅按该 key 取已有操作。`lib/media-core/execution/operations.ts` 也按 actorId + operationKey 去重。新 batch attempt 改变 inputRevision，旧 unknown 的阻止重提逻辑因此没有命中新 operation。
- 以上链路由实际请求与数据库行共同验证。不能只把 inputRevision 改为常量：已有 operation 的 business attempt 身份校验、输入变化和显式重试边界也必须保持一致。

## 实现要求

在批量任务自动恢复边界区分“可证明尚未发送”和“已发送但结果不确定”。后者必须复用/关联原执行意图进入核对，禁止自动创造新的付费调用意图。保留原 attempts、journal 回执、成本与预留，不得通过改状态、清账或删除记录绕过检查。

先读 `docs/reference/批量生产模块.md` 以及统一执行恢复、业务尝试和核对相关代码。明确用户显式重试与系统恢复的区别；不要全局阻止合法的新输入或显式业务尝试。

## 验收

1. 真实 server 模式、正式 analyze 入队接口、模拟供应商已经收到请求且未回包；强制结束并在同一隔离根重启。多次观察与第二次重启后，供应商提交总数始终为 1，旧不确定结果和费用完整保留。
2. 同时排队的未发送技术分析任务恢复并完成；未知任务不能阻塞无关合格工作。默认并发、预算、权限、租约、fence 与核对策略不变。
3. 覆盖明确 not_sent、deferred、maybe_sent/unknown、已有成功回执、输入版本变化及显式重试；暂停/继续和优雅停机也不得把原未核清调用当作新意图自动提交。
4. 增加有意义的 runner/execution 回归，并重跑 `scripts/server-performance-load.acceptance.mjs` 的小规模恢复场景和完整负载。不能跳过重启断言或只统计成功响应。
