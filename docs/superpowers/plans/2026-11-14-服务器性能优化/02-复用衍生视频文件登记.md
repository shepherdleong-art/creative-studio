| 场景 | 每次读盘 | p50 | p95 |

**残留风险**

- 不同进程同时首次登记同一衍生物仍可能各算一次哈希（旧有行为，SQLite 唯一约束兜底，无正确性问题）；进程内因函数完全同步不会交错。
- 快速路径信任 `dev/ino/size/mtime/ctime` 身份 + 首尾内容见证；Windows 的 ctime 是创建时间，同尺寸原位改写并保留 mtime 时由见证拦截（见下方修复说明）。
- 由旧版本直接在 `previewPath` 写到一半并崩溃遗留的存量半成品，仍可能被 `existsSync` 信任；本次只保证新转码不再产生半成品。实际旧代码崩溃后 job 处于 running/过期，通常会被恢复重转码覆盖。
- 未做生产服务器验证与线上压测；浏览器集成只跑了一个真实预览用例。

### 代码审查修复（2026-11-14）

**变更**

- 新增 `lib/media-core/file-identity.ts`：把「stat 身份 + 首尾内容见证」的纯函数（`inspectFileContent`、`fileIdentityJson`、`parseFileIdentity`、`fileIdentityMatches`、`FILE_IDENTITY_WITNESS_BYTES`）下沉到共享层，`lib/team-service/files/registry.ts` 改为引用，去掉与 `lib/batch-production/media-catalog.ts` 重复的本地实现。`media-catalog.ts` 未改（独立表、旧格式 dev/ino/size/mtime）。新解析器把缺 `witness` 的旧 JSON 一律视为不可信（返回 null），旧登记会完整核验一次并回填。
- `verifiedIdentityJson` 形状扩展为 `{dev,ino,size,mtimeMs,ctimeMs,witness:{bytes,head,tail}}`：首尾各取最多 64 KiB 的 SHA-256，文件不足时取实际长度并记录 `bytes`。首次登记在一次顺序读里同时算完整 SHA-256 与见证；重复登记先只读首尾最多 128 KiB，stat + 见证全部一致才复用旧 sha256；见证或 stat 不一致 → 完整 SHA-256 重核；哈希不同 → 抛「文件身份与既有不可变登记不一致」，相同 → 刷新身份（含新见证）。Windows 的 ctime 是创建时间，同尺寸原位改写 + 保留 mtime 也会被见证拦住。
- 每次 Range/登记仍执行全部授权、来源谱系与引用校验；通用（非衍生）文件仍每次全量哈希。
- `lib/video-browser-preview.ts`：转码前 best-effort 清理同目录 `${previewPath}.*.tmp.mp4` 中 mtime 超过 24 小时的残留（忽略错误，跳过当前任务临时文件）；失败/取消仍清理当前临时文件。
- 测试：`scripts/team-files.test.ts` 重复登记读盘断言从 0 改为 128 KiB 见证；新增「同尺寸改写 + 强制保留 mtime + 库内身份同步为改写后 stat」回归，断言见证不一致后完整核验并拒绝；新增旧身份 JSON 缺见证解析为不可信断言。`scripts/video-browser-preview-jobs.test.ts` 新增过期临时文件被清理、未过期/当前临时文件保留断言。
