# 03 优化任务列表与总览查询

**状态：** `ready-for-agent`  
**依赖：** 无  
**规格：** [服务器性能优化](../../specs/2026-11-14-服务器性能优化-功能方案.md)

## 修改入口

- `lib/team-service/tasks.ts`、`console-overview.ts`、`dashboard.ts`、`workspace-counts.ts`。
- 索引/字段进入所属模块追加式迁移；执行表归 `lib/media-core/execution/schema.ts`。
- 保留现有先选 ID 再取最近明细，以及侧栏轻量计数。

## 验收

分别优化最近记录、活动统计、任务组分页与状态筛选。管理员及员工都覆盖全量历史，组不拆页，计数与详情不受分页影响；取消/回队等有效状态一致。最近 12 条查询工程目标下降 80%，其他路径分别保存前后值与查询计划。新汇总必须具备回填、失效和恢复规则，参照规格实施决定 4、8、9。

## 测试

扩展 `scripts/team-task-pagination.test.ts`，回归 `team-task-display`、`workspace-badges`、`team-console-routes`、`team-dashboard` 及相关迁移测试（均位于 scripts）。至少 2000 条、约 64 KiB 快照，包含普通及统一任务、重试/取消、两名员工和管理员；不只测全部成功的简单数据。

## Comments

### 变更

- `lib/media-core/execution/schema.ts`：追加 `EXECUTION_MIGRATIONS` v13（不改已发布条目），新增两个索引，并在 `validateExecutionSchema` 的 `schemaVersion >= 13` 分支校验索引存在：
  - `idx_execution_operations_updated(updatedAt DESC, id DESC)`：管理员全量「最近任务」倒序。
  - `idx_execution_operations_activity(actorId, updatedAt DESC, id DESC, status, waitReason, module, taskId, step, scopeType, scopeId, readySeq, mediaTaskId)`：员工可见范围以 `actorId` 为前缀；同时覆盖分组身份、有效状态与活动统计所需列。全历史聚合因此扫描小索引，不再搬运 `execution_operations` 的 64 KiB 输入快照。
  - 两个索引分别对管理员/员工范围评估：管理员最近查询需要全局时间索引，员工最近查询需要 `actorId` 前缀；单靠其中任意一个都会让另一侧退化。团队表无需新增索引，故未追加 `lib/team-service/schema.ts` 迁移。
- `lib/team-service/tasks.ts`：
  - `TaskQuerySource` 新增轻量 `groupJoins`（`execution_operations` + `team_users` + `jobs`/`video_jobs`），保留 `team_users` 内连接以维持原可见范围；完整 `joins` 仍服务投影与搜索。
  - `taskGroupStatsSql` 重写：无搜索时不再构造等价的 `matched` 全扫描；状态筛选在同一遍 `scoped` 扫描里用 `FIRST_VALUE` 求代表状态。有搜索时只有 `matched` 使用完整 join，`scoped` 保持轻量。
  - `selectPageRecords` 改为先按轻量列选本页各组执行记录 ID，再按 ID 读取完整投影（主键查找），同组记录仍整组返回、组内顺序不变。
  - `countScopedTaskGroups`、`listTeamTaskRecords` 的计数与有界选 ID、`readTeamTaskActivity`、`listTeamTaskActors` 都改用 `groupJoins`。
  - 没有引入汇总表/缓存，因此不需要回填、失效、并发写入或重启恢复规则；计数、搜索、状态筛选、活动统计、详情仍覆盖全量授权历史，没有固定历史上限。
- `scripts/team-task-pagination.test.ts`：扩展到 2003 个制作任务 / 2005 条执行记录，每条 64 KiB 输入快照，含统一任务 3 条记录、重试/取消/回队、两名员工与管理员；新增索引存在性、管理员/员工最近查询计划、首屏/活动统计不得全表扫描、覆盖索引使用等性能断言，同时保留并扩展「先选 ID 再读快照」的读取量断言（最近 12 条读 12 份、本页读本页份数）。统一任务的搜索/状态筛选/详情/费用断言保持不变。
- `scripts/execution-operations.test.ts`：同步 `appliedVersions` 期望到 v13。

### 查询计划（关键差异）

- 最近（管理员）before：`SCAN o` + `USE TEMP B-TREE FOR ORDER BY`；after：`SCAN o USING INDEX idx_execution_operations_updated`，无临时排序。
- 最近（员工）before：自动索引 `(actorId, operationKey)` + 临时排序；after：`SEARCH o USING COVERING INDEX idx_execution_operations_activity (actorId=?)`，无临时排序。
- 活动统计 before：`SCAN o USING INDEX sqlite_autoindex_execution_operations_3`，并连接 `team_resource_scopes`/`projects`/`jobs`/`video_jobs`/`image_assets`/`execution_actor_policies`；after：`SCAN o USING COVERING INDEX idx_execution_operations_activity`，只连接 `team_users`/`jobs`/`video_jobs`。
- 首屏分组统计 before：`scoped` 与 `matched` 各一次 `SCAN o`（2 次表扫描）；after：1 次 `SCAN o USING COVERING INDEX idx_execution_operations_activity`。
- 首屏完整投影 before：`SCAN o` 全表；after：`SEARCH o USING INDEX sqlite_autoindex_execution_operations_1 (id=?)` 主键查找。

### 残留风险

- 关键词搜索 `q` 仍是全历史子串匹配，会读取快照 JSON；本任务未把搜索列为性能目标，优化前后同为全扫描，语义与覆盖范围不变。2000×64 KiB 合成数据上约 1.4 s，后续若需要可另立票评估受限字段索引/分词。
- 覆盖索引增加 `execution_operations` 写入放大（每次入队/状态更新维护两个索引）；索引体积远小于 64 KiB 快照列，但长期高频写入应继续观察。
- 查询计划断言依赖当前 SQLite 版本；升级 `better-sqlite3` 后需重跑 `team-task-pagination.test.ts` 与探针确认仍走覆盖索引。
- 分页测试因 2005×64 KiB 快照与多组全历史搜索，运行时间约 1.5 分钟，属于有意增加的规模成本。
- 未做真实生产库采样，也未在浏览器里重跑任务页；本轮以真实 SQLite 公共函数、真实路由合同与同机探针为验收边界。

### 代码审查修复（B 组）

- `listTeamTaskRecords` 的 COUNT、轻量选 ID 与按 ID 读完整投影包进 `db.transaction(...).deferred()`，与 `listTeamTasks` / `listRecentTeamTasks` 一致；同一请求内的授权与筛选解析、计数、选页和投影看到同一快照。
- 总数不再单发 `SELECT COUNT(*)`：轻量选 ID 查询同时带 `COUNT(*) OVER () AS total`，窗口在 `LIMIT` 之前对完整筛选结果计数，同样的 `WHERE` 只扫一遍（无行时 `total=0`）。`items`/`total` 语义、有效状态筛选口径与授权范围不变。
- 单次调用 SQL 从 3 条降为 2 条（授权/筛选解析不额外发 SQL），`WHERE` 扫描次数 2 → 1；窗口计数仍覆盖全量可见历史，不引入固定历史上限或汇总表。
- 回归：`node scripts/team-task-pagination.test.ts`、`team-task-display`、`workspace-badges`、`team-console-routes`、`team-dashboard` 全部通过；`npx tsc --noEmit --incremental false` 与改动文件 ESLint 通过。
- 残留风险：`COUNT(*) OVER ()` 的代价与原来的 `COUNT(*)` 同阶，仍随全量可见历史增长；查询计划依赖当前 SQLite 版本，升级 `better-sqlite3` 后需重跑分页测试。
