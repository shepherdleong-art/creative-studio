## 建议执行顺序

按 01 → 02 → 03 → 04 → 05 → 06 → 07 → 08 → 09 → 10 → 11 → 12 串行交付。
01～05 可以分别准备，但当前不自动创建子代理。若另行安排多人/多 agent，schema、runtime 组合根、generate-config 和包白名单由同一集成人协调；迁移只追加，不能在不同任务重复占用版本。

依赖关系是验收门槛，不只是文件阅读顺序。准备下游接口/测试不等于完成依赖；状态转成 ready-for-human 也不自动解锁，需核对对应行为和提交证据。

先实现 01～09，再由 10 从空数据根走正式入口证明整体可用，11 产出新包与包内说明，12 才验证真实服务器和员工设备。正式签名/origin 等现场输入缺失不妨碍 08 的代码和测试包，仍会阻断 11 的正式客户端交付与 12 的开放签收。

12 的资料收集步骤可从现在开始，不依赖 11；依赖 11 的是实际安装和签收。提前取得正式 origin/签名材料供 08/11 使用，避免“等包才收集参数、等参数才打包”的循环。

## 证据与完成门槛

每张 ticket 的 Comments 至少包含：
- 复现版本、实际原因，或推测不成立的证据；
- 修复提交/文件及实际行为变化；
- 命令、退出码、证据位置及必要的测试场景；
- 未测/失败/剩余现场参数；
- 对本 ticket 勾选项及下游的影响。

大量日志/截图放 outputs 的隔离任务目录，Comments 留脱敏摘要；长期签收结论记录到 docs。不要提交运行库、素材、真实配置、私钥或环境文件。

状态沿用仓库五种字符串：ready-for-agent 表示可实施，ready-for-human 表示待人复核；完成事实写在 Comments 和勾选项中。needs-info 只阻断依赖缺失事实的部分。旧任务的历史 Comments 不改写成新验收结果。

G1/G2/G3 定义以 spec §5 为准。已有单项测试不能替代完整 G2。接手复核补充了同根四模块代表任务及浏览器证据；完整四模块业务矩阵、正式客户端与现场 G3 仍单独列出，不能标记签收。
