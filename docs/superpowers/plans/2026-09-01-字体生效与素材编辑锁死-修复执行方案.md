## 1. 问题一：字体换了等于没换

### 1.1 现象与根因

`lib/final-edit/system-fonts.ts:34` 用**文件名**推导字体族名：

```ts
const family = path.basename(entry.name, path.extname(entry.name))
  .replace(/[-_](Regular|Bold|Light|Medium|Semibold).*$/i, '');
```

而 CSS / Canvas / SVG 认的是字体文件 `name` 表里的**真实 family 名**。两者大面积不一致，UI 下拉框里给出的多数是**无效名字**，选中后渲染器静默回落到默认字体——所以「换了和没换差不多」。

这一份列表被四处消费，全部中招：

| 消费方 | 文件 | 渲染路径 |
| --- | --- | --- |
| 混剪封面编辑器（正式第五步） | `components/mixcut/CoverEditorDrawer.tsx:74` | 浏览器 Canvas |
| 混剪字幕/封面图层烘焙 | `components/final-edit/text-canvas-renderer.ts` | 浏览器 Canvas |
| 批量生产文字样式 | `components/batch-production/BatchTextStyleEditor.tsx:91` | 服务端 sharp/SVG |
| 批量生产脚本步骤 | `components/batch-production/BatchStepScripts.tsx:246` | 服务端 sharp/SVG |
| 旧版检查器 | `components/final-edit/FinalEditInspector.tsx:186` | 浏览器 Canvas |

### 1.2 实证（审计时在本机 macOS 上跑出的结果）

**A. 名字对不上，全库 69%**

零依赖解析 `name` 表（nameID 1 / 16）后与文件名推导对比：

| 文件 | 下拉框显示 | 真实 family |
| --- | --- | --- |
| `Songti.ttc` | `Songti` | **`Songti SC` / `Songti TC`** |
| `STHeiti Light.ttc` | `STHeiti Light` | **`Heiti SC` / `Heiti TC`** |
| `STIXTwoText.ttf` | `STIXTwoText` | **`STIX Two Text`** |
| `Hiragino Sans GB.ttc` | `Hiragino Sans GB` | `Hiragino Sans GB` ✓ |

> 能读出 name 表的 371 个字体文件里，文件名推导 ≠ 任何真实 family 的有 **257 个（69%）**。

**B. 浏览器 Canvas 路径：65% 的候选等于没换**

把 `/api/system-fonts` 返回的 370 个候选逐个丢进与 `text-canvas-renderer.ts` 同构的 Canvas 绘制，与「一个完全不存在的字体」比对像素与宽度：

```
候选总数                                        370
渲染结果 == 完全不存在的字体（即等于没换）        241 (65%)
真正能生效的                                    129 (35%)
```

**C. 服务端 sharp/SVG 路径：同一根因**

```
Songti              → 渲染指纹 a2d010ac21   ← 与「不存在的字体」完全一致
STHeiti Light       → 渲染指纹 a2d010ac21   ← 完全一致
完全不存在的字体XYZ   → 渲染指纹 a2d010ac21
Songti SC           → 渲染指纹 c069027ff9   ← 真名，生效
Heiti SC            → 渲染指纹 1f6cedf090   ← 真名，生效
```

**D. 那道「字体缺失」守卫是假的**

`components/final-edit/text-canvas-renderer.ts:194`：

```ts
if (!document.fonts.check(`16px ${JSON.stringify(family)}`)) throw new Error(`字体缺失：${family}`);
```

实测 `document.fonts.check()` 对**任何**字符串都返回 `true`（含「完全不存在的字体XYZ」）。它挡不住任何无效字体，无效字体一路静默通过烘焙、进成片。

**E. 为什么用户说「差不多」而不是「完全没反应」**

少数字体文件名恰好等于 family 名（`Hiragino Sans GB`、`Arial`、`Avenir` 等拉丁字体为主），换它们真的会变。用户随机踩中 35%，所以感受是「好像有时有点变化，但基本白换」。

**F. 附带缺陷**

- `lib/media-core/cover-domain.ts:25` 默认字体写死 `'PingFang SC'`，但审计机（macOS 26）的 `/System/Library/Fonts` 里**没有 `PingFang.ttc`**，扫描结果里根本没有苹方——默认值不在候选集内。
- `.ttc` 一个文件含多个 family（`Songti.ttc` 内含 SC 与 TC），当前实现一个文件只产出一个名字，信息本身就在丢。
- 全仓库**没有导入自有字体的入口**。用户说的「没办法自定义更换」是准确的（见 F4）。

### 任务卡 F1 — 系统字体列表改为读真实 family 名

**目标**：`/api/system-fonts` 返回的每一个 family 都是渲染器真正认识的名字。

**允许路径**

```
lib/media-core/system-fonts.ts        （新建）
lib/final-edit/system-fonts.ts        （改为兼容再导出）
scripts/media-core-system-fonts.test.ts （新建）
scripts/final-edit-system-fonts.test.ts （更新断言）
```

**实施步骤**

1. 新建 `lib/media-core/system-fonts.ts`，按 `AGENTS.md` 的「共享媒体基础放 `media-core/`，旧路径只做兼容再导出」组织：这份列表同时被 `final-edit` 与 `batch-production` 消费，必须落在 `media-core`。
2. 手写 sfnt `name` 表解析（**零依赖**，审计已验证）：
   - 识别 `ttcf` 头，遍历其中每个子字体的 offset table；`.ttc` 必须产出它包含的**全部** family。
   - 在 table directory 里找 `name` 表；遍历 name record，取 `nameID === 1`（family）与 `nameID === 16`（typographic family）。
   - 编码：platformID 3（Windows）或 0（Unicode）按 UTF-16BE 解码；platformID 3 只取 `languageID === 0x0409`（英文）。platformID 1 且 `languageID === 0` 按 Latin-1 解码。
   - 过滤掉以 `.` 开头的内部名（如 `.Hiragino Sans GB Interface W3`）。
   - 任何单个文件解析失败**只跳过该文件**，不能让整个扫描抛错。
3. 保留原有的目录遍历（深度上限 3、平台目录表）。macOS 目录表补上 `/System/Library/Fonts/Supplemental`——现有 `FONT_DIRECTORIES.darwin` 靠深度递归覆盖到它，但显式列出更稳。
4. 输出结构在现有 `SystemFontEntry` 上扩展，**保持 `family` 字段语义为「可直接写进 CSS/SVG 的名字」**：

   ```ts
   export interface SystemFontEntry {
     family: string;        // 真实 family 名，渲染器认识
     fullName: string;      // 展示名，可与 family 相同
     format: 'ttf' | 'otf' | 'ttc';
     source?: 'system' | 'user';  // 供 F4 使用，本卡先固定 'system'
   }
   ```

   去重键改为 `family`（不是文件名）；排序规则保持 `localeCompare`。
5. `lib/final-edit/system-fonts.ts` 改成 `export { listSystemFonts, type SystemFontEntry } from '../media-core/system-fonts.ts';`，不留第二份实现。
6. 解析结果做**冷缓存**：进程内缓存扫描结果，避免每次开抽屉都重读几百个字体文件（`Songti.ttc` 单文件即 55 MB 量级，全量 `readFileSync` 不可接受）。**只读文件头部所需字节**，不要整文件读入——先读前 12 字节判类型，再按 table directory 定位 `name` 表按需读取。
7. **缓存必须可失效**。现状是每次 `GET /api/system-fonts` 都重新扫盘，所以用户往 `~/Library/Fonts` （Windows 为 `C:\Windows\Fonts`）装完字体，刷新页面就能看到。加了缓存若不给失效途径，就会制造一个新问题：**刚装的字体在列表里不出现**。要求二选一或同时提供：
   - 按各字体目录的 `mtime` 做失效判断（目录内容变化则重扫）；
   - 路由支持 `GET /api/system-fonts?refresh=1` 强制重扫。
   同时给混剪封面编辑器（`components/mixcut/CoverEditorDrawer.tsx`）补一个「刷新字体」按钮——旧版 `FinalEditInspector.tsx:206` 已有这个按钮，正式第五步反而没有。

**测试**（新建 `scripts/media-core-system-fonts.test.ts`）

- 断言返回形状与排序、去重（沿用旧测试的三条）。
- macOS 分支断言：结果**不包含** `'Songti'`、`'STHeiti Light'` 这类文件名推导产物；若系统存在 `Songti.ttc`，则结果**包含** `'Songti SC'`。
- 断言 `.ttc` 能产出多于一个 family（用系统上存在的任一 ttc 验证）。
- 非 macOS 平台只断言形状合法。
- 更新 `scripts/final-edit-system-fonts.test.ts`：删掉「必须包含 .ttc 标记（如 PingFang.ttc）」这条——审计机上已无 `PingFang.ttc`，该断言本身就是错的假设。

```bash
node scripts/media-core-system-fonts.test.ts
```

### 任务卡 F4 —（可选，需所有者确认）导入自有字体

> **这张卡是新功能，不是缺陷修复。未经所有者确认不要实施。**
>
> **先读这段再决定做不做。** 应用**没有**导入入口，但**有间接路径**：`system-fonts.ts:17-21` 的扫描目录已包含 `~/Library/Fonts`（macOS）与 `C:\Windows\Fonts`（Windows），用户把字体装进系统后应用就能扫到。
>
> 这条路目前是废的，原因还是 F1 那个 bug——主流第三方中文字体（思源黑体、Noto Sans SC、阿里巴巴普惠体）文件名一律是 `无空格驼峰-字重.otf`，真实 family 带空格。审计时用同款命名风格的系统字体实测，**12 / 12 全部对不上**（如 `NotoSansBassaVah-Regular.ttf` → 推导 `NotoSansBassaVah`，真实 `Noto Sans Bassa Vah`）。用户装了字体、在列表里看得见、选了没效果——这很可能就是「没办法自定义更换」这句反馈的真实来源。
>
> **所以：F1 落地后这条间接路径自动就通了**，第三方字体会以真名出现并真实生效。F4 届时只剩两点增量价值——省去用户去操作系统装字体这一步，以及让桌面版用户不必碰系统设置。**建议先上 F1，让测试用户实测一轮「自己装字体」是否够用，再决定 F4 做不做。**

**范围草案**

- 新增 `POST /api/system-fonts/import`：接收 `.ttf` / `.otf` / `.ttc`，落盘到 `path.join(dataRoot(), 'storage', 'fonts')`（**必须走 `dataRoot()`**，不得硬编码）。
- 入库前用 F1 的解析器读出真实 family，拒绝解析不出 family 的文件。
- `listSystemFonts()` 合并系统字体与用户字体，用户字体标 `source: 'user'`，UI 分组展示。
- **服务端 SVG 路径**（批量生产）需要 fontconfig 能看到这些文件——sharp/librsvg 不会自动读取任意目录，需在渲染前把用户字体目录注册进 `FONTCONFIG_PATH` / 生成 `fonts.conf`。**这是本卡的主要技术风险，实施前必须先做一个最小验证：把一个自有字体放进临时目录并让 sharp 渲染出它。**
- **浏览器 Canvas 路径**（混剪）需要通过 `@font-face` + 一个 `GET /api/system-fonts/file/[id]` 把字体喂给页面，不能只靠系统安装。
- 打包边界：`storage/fonts` 属于本机运行数据，必须继续被安装包裁剪断言排除（见 `AGENTS.md` 安全注意事项）。

## 2. 问题二：素材无法删除、无法替换

### 2.1 失败机制（已确定）

`lib/final-edit/workspace.ts:1893-1898`，**每一条**编辑命令在落库前，都会遍历**整条时间线的所有 clip** 做源校验：

```ts
for (const clip of timeline.clips) {
  if (clip.timelineInFrame < 0 || clip.timelineOutFrame > timeline.bodyFrames || ...) throw ... // 结构
  const analysis = editableVideoSource(db, storageRoot, String(row.groupId), clip.videoJobId);
  const sourceFrames = Math.floor(Number(...durationUs || 0) * 24 / 1_000_000);
  if (!analysis || analysis.fileFingerprint !== clip.sourceFingerprint || clip.sourceOutFrame > sourceFrames)
    throw new FinalEditError('source_out_of_range', '片段超出源视频真实时长');
}
```

**只要任意一个 clip 不过，本次命令整条被拒**——删除、替换、移动、修剪、换 BGM、换封面全部失效。坏的是片段 A，删片段 B 也删不掉。

前端 `components/mixcut/PreviewStep.tsx:131-134` 捕获后直接 reload 服务端版本：

```ts

  await reloadGroup(currentGroup.id).catch(() => undefined);
  if (mountedRef.current) setMessage(`保存失败，已恢复服务端版本：${error.message}`);

```

界面弹回原样，只在底部留一行小字。用户看到的就是「点了没反应 / 删不掉」，唯一出路是重新生成一版新 variant（新 timeline 绕开坏数据）——与用户描述完全吻合。

**报错文案本身也是问题**：动作是「删除素材」，提示却是「片段超出源视频真实时长」，且不指明是哪个片段、哪个素材——所以用户只能形容成「很奇怪的 bug」。

### 2.2 触发成因（按嫌疑排序，需 M0 收敛）

| # | 成因 | 代码位置 | 判据 |
| --- | --- | --- | --- |
| 1 | **`ceil` / `floor` 差一帧** | 生成 `audio-first-timeline.ts:41` 用 `Math.ceil`，校验 `workspace.ts:1896` 用 `Math.floor` | `sourceOutFrame == floor+1` |
| 2 | **指纹不匹配** | `workspace.ts:1897` | `analysis.fileFingerprint !== clip.sourceFingerprint` |
| 3 | **`mediaJson` 为空 → `durationUs=0` → `sourceFrames=0`，所有片段判超限** | `app/api/final-edit-assets/[videoJobId]/reanalyze/route.ts:25-30` | `mediaJson` 为 `'{}'` |
| 4 | 素材文件被移动/删除；外部导入素材 `status !== 'ready'` | `workspace.ts:623-646` | `editableVideoSource` 返回 `null` |
| 5 | `video_jobs.status !== 'succeeded'` | 同上 SQL 的 `WHERE` 条件 | 同上 |

**成因 1 的实证**（审计时扫本机 `data/workbench.db`）：

```
参与统计的 clip                                  117
durationUs*24 非整数（即 ceil 恒 = floor + 1）    117 / 117  (100%)
sourceOutFrame 正好贴死 floor 边界的 clip          13  (11%)
按 audio-first 路径生成的 clip 中贴死边界的         2 / 68
按旧 planTimeline 路径生成的 clip 中贴死边界的      11 / 49
```

即：`ceil` 与 `floor` **恒定差 1 帧**，而匹配器确实会把素材用到最后一帧（11% 的 clip 贴在边界上）。审计机上这 117 个 clip 全部落在通过侧（复刻校验跑出 **22 个 variant，0 个锁死**，所以本地复现不了是正常的），但只要生成时的 `Math.round` 偏一帧，该 variant 从生成那一刻起就**永久不可编辑**。

旧的 `planTimeline`（`workspace.ts:680`）用 `Math.floor` 算 `mediaEndFrame`，与校验一致，**不会**踩成因 1。分水岭是 `7f8507d`（2026-07-24，audio-first 接入）——这也是必须先问清测试用户版本的原因（见 §3）。

**成因 3 的实证**：`reanalyze/route.ts` 的 `INSERT ... ON CONFLICT` 列清单里**完全没有 `mediaJson`**。表定义 `lib/final-edit/schema.ts:32` 是 `mediaJson TEXT NOT NULL DEFAULT '{}'`，所以新插入的行 `durationUs` 恒为 0。顺带一个独立缺陷：该路由把 `analyzerVersion` 写死为 `'1'`，而正确值是 `workspace.ts:366` 的 `FINAL_EDIT_ANALYZER_VERSION = '2'` —— 点过「重新分析」之后，后续 prepare 的分析缓存**永久失效**，每次都重跑一遍视觉分析，白花钱。

### 任务卡 M1 — 统一 `ceil` / `floor` 边界

**目标**：消除「生成时合法、编辑时非法」的一帧不对称。

**允许路径**

```
lib/media-core/render-contract.ts        （新增共享换算函数）
lib/final-edit/audio-first-timeline.ts
lib/final-edit/workspace.ts
scripts/final-edit-audio-first-timeline.test.ts
scripts/final-edit-workspace.test.ts
```

**实施步骤**

1. 在 `lib/media-core/render-contract.ts`（24fps / 20 帧片头常量的既有归属地）新增**唯一**的换算函数，例如：

   ```ts
   /** 素材可用的最大出点帧（含）。生成与校验必须共用这一个定义。 */
   export function sourceFrameLimit(durationUs: number, fps = FINAL_EDIT_FPS): number {
     return Math.floor(Math.max(0, durationUs) * fps / 1_000_000);
   }
   ```

2. **统一到 `floor`**，不是统一到 `ceil`。理由：`floor` 是素材真实存在的最后一个完整帧；放宽到 `ceil` 会让 ffmpeg 在末尾取到不存在的帧，渲染端靠 `-t` 静默截短，画面会短一帧。**收紧是正确方向**。
3. `audio-first-timeline.ts:41` 改为调用该函数。改完后，原本卡在 `ceil` 上的匹配结果会转为 `material_gap` issue——这是**预期行为**，不是回归：它把问题从「事后永久锁死」提前到「生成时就报告缺口」。
4. `workspace.ts:1896` 改为调用同一个函数（顺带去掉那里硬编码的 `24`，用 `FINAL_EDIT_FPS`）。
5. 全仓库 `rg -n 'durationUs \* (24|FINAL_EDIT_FPS)'` 复核是否还有第三处换算，有则一并收敛。

**测试**

- `scripts/final-edit-audio-first-timeline.test.ts`：构造一个 `durationUs` 使 `ceil > floor`（例如 `3_020_000` → floor 72 / ceil 73），断言生成结果**不会**产出 `sourceOutFrame === 73` 的 clip。
- `scripts/final-edit-workspace.test.ts`：**先写失败测试**——手工塞一条 `sourceOutFrame = floor + 1` 的 clip 进 timeline，断言 `delete_clip` 一个**别的** clip 会失败（修复前）；M4 完成后该断言改为成功。

```bash

node scripts/final-edit-workspace.test.ts
```

**风险**：收紧上限后，素材极短的句段可能新增 `material_gap`。这是把隐性故障显性化，但需要在验收时确认缺口数量没有异常暴涨（对同一组素材，修复前后 `material_gap` 数量差异应当是个位数）。
