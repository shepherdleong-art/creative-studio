## 1. 已确定的产品契约

### D1 — 项目脚本与单条混剪

- 空 `shotSetId` 是项目级脚本，在同项目所有有效分镜组中可选。
- 非空 `shotSetId` 的历史脚本仍只能在所属分镜组中使用。
- 新建单条混剪默认选择最新的可见项目脚本当前版本。
- 已有编辑保留当时的脚本快照；当稳定脚本 ID 的当前 revision 更新时，显示“源脚本有新版本”和明确的“同步最新版本”操作。
- 同步最新版本是显式操作；页面刷新、切换步骤和切换分镜组不能静默覆盖用户修改。

### D2 — 单条混剪导出新鲜度

- render job 属于它创建时的 `groupRevision + variantRevision`。
- 只有两个 revision 都与当前编辑一致的 job 才是“当前导出”。
- 旧版已成功 job 显示为“上一版可下载”；它不能阻止当前修订号再次导出。
- 缺少 revision 的旧 job 按历史产物处理，不猜测它与当前编辑一致。

### D3 — 批量 BGM 交互

- 曲目、音量、淡入、淡出共同组成一份本地 `musicDraft`。
- 任一字段与服务端当前值不同，都启用“应用 BGM 更改”。
- 选择曲目不立即持久化；中间预览和试听立即使用草稿，点应用后再一次性写入当前成片。
- 正在播放时换歌，保留播放头和播放状态，新音源从对应正文时间开始。

### D4 — 场景结果顺序

- 页面默认“最新创建批次在前”。
- 同一请求内按用户提交顺序从左到右排列。
- 任务从 pending 变为 running / succeeded / failed 时位置不变。
- 历史数据没有创建字段时，使用 SQLite `rowid` 作为最后兼容回退，不回填、不重写历史任务。

### D5 — 视频友好名称

- 主名称不包含供应商；供应商继续作为独立元数据显示。
- 命名模式：`<分镜/自由素材序号>-<来源图名>-<运镜模板或自定义>-V<版次>.mp4`。
- 参考示例：`01-LH122K3-B1-沙发-缓慢推近-V01.mp4`。
- 显示名称必须经过安全清洗和长度限制。新任务持久化友好名称；旧任务读取时确定性派生。
- 物理文件仍使用冲突安全的内部名；播放 URL 仍指向物理文件。

### Not now

- 不把项目脚本 revision 直接改成分镜绑定脚本。
- 不设计新的混剪流程、对话框或播放器；只在已有交互中补齐状态。
- 不把历史导出升级成完整版本管理产品。
- 不修改视频轮询、重试、费用或供应商适配器。
- 不按任务状态重排图片或视频卡片。

## 3. C1（P0）项目脚本进入单条混剪

### 3.1 已确认现象与根因

服务端 `lib/final-edit/mixcut-context.ts:248-280` 已通过 `isScriptVisibleInContext` 返回空 `shotSetId` 项目脚本，`lib/final-edit/workspace.ts:431-481` 也能在使用时建立快照。

前端仍有三处精确分镜组等值过滤：

- `components/mixcut/MixcutPanel.tsx:173-175`：默认脚本。
- `components/mixcut/MixcutPanel.tsx:183-185`：缓存脚本是否仍存在。
- `components/mixcut/MixcutPanel.tsx:442`：传给创作步的脚本列表。

此外，新项目脚本在 `lib/media-core/project-script-reader.ts:34-50` 中把 provider/model 投影为空字符串，不适合继续沿用历史下拉文案。同一 `project_scripts.id` 的 `currentRevisionId` 可以更新，仅修复可见性仍无法让用户重新选择“同 ID 的新版本”。

### 3.2 实施要求

1. 统一可见性：Mixcut 前端三处选择都调用同一个纯函数，契约与 `lib/media-core/script-visibility.ts` 一致：空 `shotSetId` 可见，非空值必须匹配当前组。
2. 稳定排序：`listReadableProjectScripts` 中的项目脚本按当前 revision 创建时间降序，新项目脚本在历史 `script_drafts` 之前。新建混剪默认选第一条可见项目脚本。
3. 显式身份：`MixcutContextResponse.drafts` 增加可安全公开的 `sourceKind` / `sourceRevisionId` / `sourceRevisionNumber`（命名可等价，语义必须一致）。不向前端暴露整个任务快照。
4. 快照身份：`ScriptSnapshot` 增加可选的源 revision 身份，创建/更新 final-edit group 时与 `sourceScriptUpdatedAt` 一起写入 `scriptSnapshotJson`。旧快照继续用 timestamp 兼容。这一步不需要数据库迁移。
5. 新版提示：已有 group 的源 revision 与当前 draft revision 不同时，`CreationStep` 显示“源脚本有新版本”和“同步最新版本”。无手工修改时可直接同步；有手工修改时复用现有切换确认语义，允许保留/放弃/取消，不新建另一套对话框视觉。
6. 友好文案：项目脚本显示“当前版本 Vn”，不显示空的 `provider/model` 斜杠；历史脚本保留原元数据。“仅显示当前分镜组”改为能正确表达“项目脚本 + 当前组历史脚本”的文案。
7. 同步后必须经现有 `set_mixcut_script_state` 自动保存链写回，并用服务端返回的快照身份清除“有新版本”状态。

## 4. C2（P0）单条混剪修改后重新导出

### 4.1 已确认现象与根因

`components/mixcut/ExportStep.tsx:73` 只按 variant 取最新 render job，`89-107` 在步骤激活时恢复它，`289-311` 把任何 succeeded job 当成当前成果并隐藏导出按钮。

渲染创建时已把 `groupRevision` / `variantRevision` 写入 `inputSnapshotJson`（`lib/final-edit/workspace.ts:2138-2150`），但 group 视图的 jobs 查询不返回它们（`workspace.ts:942`），单 job API 又删除整个输入快照（`app/api/final-edit-jobs/[id]/route.ts:41-42`）。

### 4.2 实施要求

1. 从 render job 快照只投影两个安全标量，例如 `renderRevision: { groupRevision, variantRevision }`。不把 `inputSnapshotJson` 或本地路径返给前端。
2. `FinalEditGroupView.jobs` 和 `GET /api/final-edit-jobs/:id` 都提供同一结构。解析失败、非 render job 或旧数据缺字段时返回 `null`。
3. `ExportStep` 分别计算：
   - 当前 revision 的最新 job；
   - 当前 variant 的最新历史 succeeded job。
4. 只有当前 revision 的 queued/running job 显示进度并阻止重复点击。旧 revision 的在途任务不能遮住当前导出操作。
5. 当前 revision 已成功：显示“下载视频/封面”。
6. 只有历史成功结果：显示“上一版可下载”及历史下载，同时显示“重新导出当前修改”。
7. group / variant revision 变化、切换 variant 或重新进入导出步时，重新分类 job；不让组件内的旧 `job` state 继续冒充当前结果。
8. 继续使用 `reserveProjectExportTarget`的不覆盖语义；不删除旧 artifact，不改 worker 的快照渲染逻辑。

## 5. C3（P1）批量 BGM 曲目与参数统一应用

### 5.1 已确认现象与根因

`components/batch-production/BatchOutputEditor.tsx:65` 只为音量/淡入/淡出建草稿。曲目下拉在 `685-690` 选中即提交 `set_music_track`，而 `musicParamsChanged` 在 `375-377` 不比较曲目，所以仅换歌时 `708-710` 的应用按钮必然禁用。

中间预览会更换 `<audio src>`（`BatchTimelinePreview.tsx:639-640`），但播放中的换源没有明确的重载、seek 与续播链路。

### 5.2 实施要求

1. 将 `musicParamsDraft` 升级为完整 `musicDraft`：`trackId` / `gainDb` / `fadeInSec` / `fadeOutSec`。
2. 草稿与服务端值的比较覆盖全部四个字段。下拉只更新草稿，不在 `onChange` 中发请求。
3. 将按钮改为“应用 BGM 更改”；任一字段变化即可点。“恢复批次默认”只把参数写入草稿，不绕过应用按钮直接提交。
4. 预览和试听使用 `musicDraft.trackId`，音量包络使用草稿参数。
5. 服务端新增一条原子编辑命令（建议名 `set_music`），一次校验曲目并写入全部参数，只递增一次 `editRevision`。保留旧 `set_music_track` / `set_music_params` 命令作内部兼容，新 UI 不再分两次提交。
6. 草稿在其他编辑命令导致 `loadView(true)` 时保留；只在换 plan、用户取消/重置或应用成功后与服务端真值重新同步。
7. `BatchTimelinePreview` 对 `bgm.fileUrl` 变化建立显式媒体同步：
   - 暂停时：load 新源并定位当前播放头；
   - 播放时：load 新源、定位正文偏移并续播；
   - 不重置画面播放头，不影响口播 GainNode；
   - `play()` 失败按现有安全策略处理，不产生未处理 Promise rejection。
8. 继续使用 `deferRender: true` 和编辑轮结束的 `commit_render`，不为每个 BGM 操作立即排渲染。

## 6. C4（P1）场景结果稳定排序

### 6.1 已确认现象与根因

`app/api/projects/[id]/route.ts:42-50` 对图片 jobs 使用 `ORDER BY j.id`，而 `app/api/projects/[id]/scene-jobs/route.ts:58-61` 使用 UUID v4 作为 ID。`components/ResultGallery.tsx:214-220, 432-434` 保留入参顺序，因此随机 ID 直接变成了随机卡片位置。

`jobs` 基表目前没有创建时间和请求内顺序字段（`lib/db.ts:99-133`），`submittedAt` 只在供应商提交后才写入，不能代表用户创建顺序。

### 6.2 实施要求

1. 在 `jobs` 增加追加式字段：
   - `createdAt TEXT`（新任务显式写入）；
   - `creationIndex INTEGER NOT NULL DEFAULT 0`（同一创建请求内从 0 递增）。
2. 只在 `CORE_DB_MIGRATIONS` 尾部追加 ALTER，同时更新新库基表定义。不回写旧行，不修改任何旧迁移字符串。
3. 所有图片 job 创建入口写入创建身份，至少核对：
   - `app/api/projects/[id]/scene-jobs/route.ts`；
   - `app/api/projects/route.ts` 的新建项目初始场景任务；
   - `app/api/jobs/[id]/regenerate/route.ts`；
   - `app/api/shot-sets/[id]/apply-scene/route.ts`。
4. 同一请求使用同一 `createdAt`，并按循环原始顺序写 `creationIndex`。
5. 项目 jobs 查询返回一个仅用于历史兼容的 `creationSequence`（可由 `j.rowid` 投影），排序规则为：
   - 有 `createdAt`：时间降序，同时间按 `creationIndex` 升序，再用 `creationSequence` 稳定打破平局；
   - 无 `createdAt`：优先旧 `submittedAt/startedAt/finishedAt`，最后按 `creationSequence` 降序。
6. 排序在服务端或一个被服务端和前端共用的纯函数中只实现一次。`ResultGallery` 继续保留入参顺序，不按 status 二次排序。
7. 轮询刷新只更新任务状态，不改变位置。

SQLite 时间比较需要同时兼容 ISO `T` 和历史 `datetime('now')` 的空格格式；使用 `unixepoch()` 或先归一化，不直接依赖两种字符串的字典序。

## 7. C5（P2）生成视频友好展示名称
