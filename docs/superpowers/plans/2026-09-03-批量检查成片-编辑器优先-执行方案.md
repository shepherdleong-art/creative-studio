# 批量成片：检查页只编辑，正式成片在导出时生成（修订执行方案）

> 状态：**只完成方案修订，尚未开始开发。**
>
> 本版取代 2026-09-03 同文件的早先版本。修订原因有两个：
>
> 1. 导出页本来就有视频播放器，不需要再新增一个。
> 2. 用户重新编辑并再次导出后，导出页原来的那张成片卡片必须切换到新正式成片；不能再摆一张新卡片让用户判断哪条才是最新。
>
> 本方案以当前工作区为准。实施时按函数名定位，不依赖文中的旧行号。

## 先讲人话

这次要改成：

> 生产阶段只准备口播、画面安排和封面
>
> → “检查成片”直接进编辑器，用实时预览检查和修改
>
> → 用户点“通过”
>
> → 到“导出成片”时才真正生成 mp4
>
> → 导出页直接播放这份正式成片

如果已经导出过正式成片 A，后来又回去修改：

> 修改期间，导出页继续保留并播放 A，同时提示“当前修改尚未导出”
>
> → 用户再次通过并导出
>
> → 新成片 B 生成成功后，**同一张卡片、同一个播放器切换到 B**
>
> → 如果生成失败，A 继续保留，不拿失败品覆盖它

这里的关键不是“再加一个预览播放器”，而是让现有播放器永远认准“当前正式成片”。

## 🧭 Product Decision：重新导出怎样“覆盖”

- **选择**：做“界面上的逻辑覆盖”。每个计划始终只有一个“当前正式成片”指针；新导出成功后，指针从 A 切到 B，播放器、下载视频、下载封面一起切换。
- **原因**：这符合用户看到的产品心智，也能避免生成失败或应用中断时把上一份可用成片弄丢。
- **代价**：磁盘内部仍可保留 A、B 两份不可变产物，用于防误覆盖和排查；普通界面不显示历史选择器，也不显示“还有 N 个历史版本”。
- **Not now**：本轮不要求导出文件夹里物理上只剩一份同名文件。当前文件导出仍采用不覆盖旧文件、自动追加序号的安全规则。如果以后明确要求连磁盘旧文件也替换或删除，必须单独评估文件占用、回滚和失败恢复，不能顺手夹带。

## 三种东西不要混

| 名称 | 是什么 | 在哪里看 |
| --- | --- | --- |
| 编辑器实时预览 | 浏览器根据片段、字幕、口播和 BGM 即时组合出来的检查画面，不是最终 mp4 | 检查成片 |
| 当前正式成片 | 最近一次成功渲染、校验并注册的可交付 mp4 | 导出成片现有播放器 |
| 内部历史产物 | 为防误覆盖而保留的旧文件和记录 | 默认不在产品界面暴露 |

“通过”只代表编辑方案审核通过；“当前正式成片”只在整片渲染和发布都成功后才更新。两者不能混成一个状态。

## 不可破坏的红线

1. 静音占位素材只能预览，不能正式发布；正式导出仍必须确认口播已就绪，最终渲染结果的 audioMode 为 narration。
2. 正式成片仍从冻结的原始素材和安排快照渲染，不能把浏览器代理预览当成正式输入。
3. 现有完整渲染结果继续要求视频、封面、时长、音轨模式和指纹完整；不能为了“只出封面”把这些字段全改成可空。
4. 批量生产只从 media-core 导入，不能从 final-edit 导入。
5. 数据库迁移只能追加。本方案预期不需要迁移；若实施时发现必须迁移，先停下来修订方案。
6. 老成片只有在新成片完整成功后才失去“当前”身份。排队中、渲染失败、校验失败、复制失败或并发编辑都不能切换当前指针。
7. 前端不得自己拼凑任务状态。导出是否需要渲染、正在渲染、失败或已经发布，由一个服务端编排入口统一判断。

## 目标状态，不再用一个词包打天下

服务端工作区应分别返回以下事实：

- coverStatus：封面任务的 queued、running、succeeded、failed。
- productionReady：口播和正式渲染输入是否齐全。
- reviewStatus：当前版本是否已审核通过。
- exportStatus：not_exported、rendering、failed、exported。
- currentFormalArtifact：当前正式视频和封面的 artifact。
- formalOutdated：当前编辑方案是否比 currentFormalArtifact 更新。

推荐派生规则：

- 有当前版本且批次未停止，就可以进入编辑器。
- productionReady 且封面可检查，才允许“通过”。
- 当前版本、口播、审核和正式导出预检全部通过，才允许排整片渲染。
- 已有正式成片后再编辑，currentFormalArtifact 仍返回，但 formalOutdated 变为 true。
- 新正式成片发布成功，currentFormalArtifact 原位切换，formalOutdated 变回 false。

用户能看到的主路径是：

> 准备封面 → 可检查 → 已通过 → 正在导出 → 已导出

异常分支是：

> 封面失败：可以重试封面
>
> 导出失败：旧正式成片继续可播，可以修复后重试
>
> 已导出后又编辑：显示“当前修改尚未导出”

## 技术问题翻译成人话

| 技术说法 | 人话 |
| --- | --- |
| output_version_cover 还没完整接入 | 数据库允许写这个标签，不代表其他代码认识它。建任务、执行、取消、重试和丢弃旧结果的地方都要补齐。 |
| 封面要用 coverContractHash | 不能只记“第几秒截图”。同一秒换了素材、裁切或标题，也必须认作一张新封面。 |
| 完整渲染结果不能塞一堆 null | “只做封面”和“做完整视频”是两种活，应该各拿各的结果单，避免以后到处猜哪些字段有没有。 |
| 发布前要做 CAS | 开始导出时检查一次还不够。视频生成期间用户可能又改了，临到替换旧视频前必须再检查一次，防止把过期结果顶上去。 |
| 导出接口要幂等 | 自动重试或多点一次不能多导出一份相同文件，也不能多建一张卡。 |
| 任务能后台跑，不等于导出意图能记住 | 服务端记得“这条视频正在渲染”，但目前不记得页面当时勾选了哪些条目。所以关页后任务继续，回来仍需再点一次导出。 |
| candidate 和 artifact 不一样 | candidate 是刚做好的待验货文件；artifact 才是已经校验、正式登记、应该给用户播放和下载的成片。 |

## 关键技术决定

### 1. 封面渲染和整片渲染使用两个明确结果

不要给现有 BatchRenderResult 增加 coverOnly，再把 videoPath、videoChecksum、audioMode、duration 等字段改成 null。

改为：

- 完整渲染继续返回 BatchRenderResult，契约保持严格。
- 新增 BatchCoverRenderResult，只包含封面任务真正拥有的谱系、封面契约、路径和指纹。
- 新增明确的 renderBatchOutputCover 接口；内部可以与完整渲染共享抽帧、色彩处理、裁切和标题合成函数。
- 两类结果分别解析、校验和清理。封面任务绝不能被媒体查询误认成可播放的视频候选。

这样能把“只做封面”的特殊情况关在一个小模块里，不让空值判断扩散到 workspace、导出和正式发布。

### 2. 封面任务仍用 workType=render，但 targetKind 要完整接入

新目标类型为 output_version_cover。数据库字段没有这项 CHECK，因此预期无需迁移，但“数据库能存”不等于“代码已经支持”。

必须同时修改：

- lib/batch-production/tasks.ts 的目标类型和 createBatchTask 入参校验。
- lib/batch-production/batch-render-executor.ts 的任务分派和结果写入。
- lib/batch-production/runner.ts 的心跳与完成前版本校验。
- lib/batch-production/phase-e.ts 的建任务、取消旧任务和重试入口。
- lib/batch-production/output-media.ts 的封面结果解析，且不能把它当成视频结果。

output_version 和 output_version_cover 都属于“绑定某个输出版本”的任务。任务运行期间如果当前版本已经变化，旧任务的晚到结果必须丢弃，不能写回新版本。

### 3. 封面任务的身份不能只看时间点

相同 timeUs 下，用户仍可能换素材、改裁切位置、缩放、主副标题、标题样式或色彩设置。如果请求键只包含 timeUs，系统会误用旧封面。

新增一个唯一的封面渲染契约，由真正参与封面生成的冻结输入组成，至少包括：

- 输出版本和封面渲染器版本。
- 素材身份与素材指纹。
- 取帧时间。
- 裁切、缩放和位移。
- 主副标题文字与样式。
- 色彩链或 LUT。
- 画幅与输出规格。

把规范化后的契约计算为 coverContractHash，并让以下位置共用同一个计算函数：

- 创建封面任务时的 requestKey。
- 判断成功封面是否仍然新鲜。
- 工作区选择当前封面。
- 完整导出前的最终并发校验。

不能在四处各写一套“差不多”的比较。

### 4. 正式成片也只有一份渲染契约

完整渲染任务的 requestKey、新鲜度判断、formalOutdated 判断和发布前 CAS 必须来自同一个规范化渲染契约。契约至少覆盖：

- outputVersionId。
- editRevision。
- coverContractHash。
- 口播、字幕、BGM、画面安排和输出预设的有效身份。
- 渲染器契约版本。

在不加新字段的前提下，可用“成功任务的渲染契约 + 结果指纹”与 currentFormalArtifact 的视频、封面指纹关联当前正式成片。若现有数据不足以可靠判断，不能靠猜；停下来报告是否需要补持久化设计。

### 5. 导出编排做成一个深模块

新增或抽出一个服务端导出编排模块。路由只调用这一个入口，前端只消费它返回的状态，不再分别查询任务、候选和 artifact 后自行推断。

单条计划的返回状态至少要区分：

- skipped：当前版本、口播、审核或预检不合格，并返回人话原因。
- render_queued：刚创建正式渲染任务。
- rendering：任务已经在排队或运行，返回进度。
- render_failed：任务已经失败，返回可重试信息；不能被当成“仍在等待”无限轮询。
- already_published：当前 artifact 已经对应这份渲染结果，重复 POST 不再复制一份。
- published：新 artifact 已注册并成为当前正式成片。

这是本方案最重要的收口点：所有导出状态只在这里判一次。

## 实施顺序

### T0：实施前基线和脏工作区保护

1. 查看 git status --short --branch，记录与本方案重叠的已有改动。
2. 阅读 docs/reference/批量生产模块.md，并以当前源码为准复核函数名。
3. 搜索 deferRender、commit_render、renderStale、output_version_cover 等关键契约，确认尚未被其他改动实现。
4. 后续只按明确路径暂存，不使用 git add -A，不覆盖无关脏改动。

完成标准：交付记录能区分“本次修改”“原有脏改动”和“只读核查”。

### T1：抽出独立封面渲染能力

1. 从 lib/batch-production/batch-renderer.ts 抽出完整渲染和封面任务共用的封面生成步骤。
2. 保持 BatchRenderResult 的完整视频契约不变。
3. 新增 BatchCoverRenderResult、renderBatchOutputCover 和精确清理函数。
4. 封面文件也使用临时文件、校验、指纹和原子落盘；失败时不留下可被当成成功结果的半成品。

完成标准：

- 封面任务不会启动整片视频编码。
- 完整渲染回归测试不需要接受任何视频字段为空。
- 两类结果都能独立清理，互不误删。

### T2：让封面任务进入完整任务生命周期

1. 在 tasks.ts 中显式允许 render/output_version_cover，并继续拒绝非法 workType 与 targetKind 组合。
2. 执行器按 targetKind 调用封面渲染或完整渲染。
3. runner 对两种输出版本任务都做运行中心跳检查和完成前 CAS；版本已过期时丢弃结果并结束旧任务。
4. scheduler 的口播依赖只拦完整 output_version 渲染；封面任务不需要等待口播，但要受版本有效性和并发规则约束。
5. 同一封面契约成功时复用任务；相同输入的失败任务走明确“重试”动作，不得永远返回旧 failed 任务。

完成标准：数据库无迁移；封面任务能排队、运行、失败、重试、取消，并且晚到结果不会污染当前版本。

### T3：Phase E 只排封面，不排整片

1. 口播完成和联合分配完成后，为每个当前输出版本建立封面任务。
2. 删除 Phase E 自动创建 render/output_version 的路径。
3. 换画面、重分配或切换输出版本时，同时取消旧版本的封面和整片渲染任务。
4. 封面任务 requestKey 使用统一 coverContractHash。
5. 原封面重生成接口不再依赖“先有一条完整视频候选”；统一改为封面任务入口。

完成标准：新批次进入检查阶段时有封面，但没有因为准备或编辑而生成 mp4。

### T4：编辑只保存；只有改封面才重做封面

1. 从 BatchOutputEditor、片段编辑接口和动作类型中删除 deferRender 与 commit_render。
2. 裁片、换片、字幕、BGM 等编辑只保存 arrangement、增加 editRevision、重置当前版本审核；不创建整片渲染任务。
3. set_cover 必须在保存成功后建立一条新封面任务。它可能同时改变 assetId、timeUs、framing 和标题，不能只监听旧的独立封面接口。
4. 其他编辑如果没有改变封面契约，不得重做封面。
5. 已有正式成片时，编辑成功立即派生 formalOutdated=true，但继续返回旧 currentFormalArtifact。

完成标准：连续编辑不会出现“欠一次渲染”或靠组件卸载补交任务；除了真正影响封面的编辑，检查阶段不产生 render 任务。

### T5：重做 workspace 状态口径

1. 分开查询 coverTask、fullRenderTask、currentFormalArtifact，不再拿一个 candidate 代表三种东西。
2. publishable 不再表示“已经有完整视频候选”。建议改成更明确的 reviewable、approvable 和 exportEligible，避免旧名字继续误导。
3. 没有完整渲染任务但已可检查的卡片，不能显示为“处理中”或永远 waiting。
4. coverStatus 失败要单独显示和重试，不能变成整批模糊的“需处理”。
5. formalOutdated 由统一完整渲染契约和 artifact 指纹派生。
6. 导出页的视频来源必须 artifact 优先；完整渲染临时候选不能抢在当前正式成片前面播放。

完成标准：Phase E 结束后能进入检查；旧正式成片在返工期间仍可播放，并准确标记“当前修改尚未导出”。

### T6：导出时先验证，再渲染，再原位替换

导出编排必须按以下顺序处理每条计划：

1. 在排昂贵渲染前检查计划归属、当前输出版本、productionReady、口播状态、当前版本审核和正式导出预检。无效条目直接 skipped，绝不先渲再拒绝。
2. 从同一份冻结快照计算完整渲染契约和 requestKey。
3. 若 currentFormalArtifact 的指纹已对应当前成功渲染结果，返回 already_published，保证重复 POST 幂等。
4. 没有任务时创建 render/output_version；刚创建或已有 queued/running 时返回 render_pending，并携带每条进度。
5. 路由创建任务后必须唤醒 scheduler。不能只把任务写进数据库然后等下次偶然启动。
6. failed 任务返回 render_failed，停止自动轮询；用户明确重试后才重新进入队列。
7. succeeded 任务先校验结果结构、productionReady、audioMode=narration、完整渲染契约、文件存在性和指纹，再复制到正式导出目录。
8. 更新 currentArtifactId 前，在最终事务中重新检查 currentVersionId、editRevision、coverContractHash、reviewStatus 和渲染契约。用户若在渲染期间又编辑，旧结果不得成为当前正式成片。
9. 最终 CAS 失败时不切换当前指针；只清理本次新建且尚未注册的目标文件，不能碰旧正式产物。
10. 在同一事务中注册新视频和新封面 artifact，并把 currentArtifactId 原子切换到新视频；当前封面继续按这对产物关联。旧 artifact 留在内部，产品界面只认新指针。

完成标准：

- 第一次导出产生 A。
- 编辑期间仍播放 A，并显示过期提示。
- 再次导出成功后同一卡片切到 B。
- 再次导出失败或发生并发编辑时仍播放 A。
- 网络重试或前端重复 POST 不会重复复制同一份正式成片。

### T7：检查页和导出页按用户心智收口

#### 检查成片

1. 点卡片直接进入编辑器，不再先放一遍渲染视频。
2. 删除“播放器/调整片段/返回预览”双模式。
3. 删除历史版本选择器，也删除“另有 N 个历史版本”等提示；内部记录继续保留。
4. 删除“待重新生成”“等待重新渲染”和 renderStale、renderUncommitted 相关交互。
5. 尚无封面时，只要有当前可编辑版本仍可进入编辑器；封面失败单独给重试入口。

#### 导出成片

1. **复用 BatchStepExport 已有的 video controls 播放器，不新增第二套播放器。**
2. 播放源只绑定 currentFormalArtifact；播放器的 key 至少包含 artifactId，确保 A 切到 B 后浏览器真实换源。
3. 同一卡片的“下载当前正式版视频”和“下载当前正式版封面”也绑定 currentFormalArtifact。
4. 第一次导出时没有旧视频，就显示渲染进度。
5. 返工再导出时，旧视频继续可播，卡片上叠加“当前修改尚未导出”和进度。
6. 新 artifact 注册成功后，刷新 workspace，让原卡片原位切换；不新增“B 版本卡片”。
7. 渲染失败时保留旧视频，并显示人话原因、重试和“回检查成片修改”入口。

同一页面打开期间可以轮询任务，并在全部成功后自动再次调用导出接口完成发布。

关闭或刷新页面后的准确承诺是：

> 服务端渲染任务继续运行；重新进入后能看到状态，但用户需要再点一次“导出”来完成发布。

原因是当前选中的 planIds 和“这次导出意图”只存在前端内存里。若要求应用重启后也自动发布，必须新增持久化导出会话；这不在本轮零迁移范围内，不能在文案里假装已经支持。

### T8：兼容、文档和交付

1. 老批次已有的成功完整渲染任务可以作为新鲜候选继续发布，但导出页只播放正式 artifact。
2. 老 artifact 和导出文件不删除；无历史入口不等于删历史数据。
3. 更新 docs/reference/批量生产模块.md，写清新任务类型、两种渲染契约、导出状态和关闭页面后的真实行为。
4. 不修改 components/mixcut/ 或 lib/final-edit/。
5. T2 至 T7 必须一起交付，避免中间状态把批次卡住。

## 手动验收：照着用户真实操作走

1. 新建小批次。生产结束后封面墙有图，但此时没有完整 mp4 渲染任务。
2. 点一张封面，直接进入编辑器；修改片段、字幕和 BGM，不出现任何“待重新生成”。
3. 改封面素材、时间、裁切或标题，封面刷新；只改普通片段时封面任务不重跑。
4. 通过一条并第一次导出。导出页现有播放器能播放正式成片 A，两个下载入口也都指向 A。
5. 回检查页修改同一条。导出页仍播放 A，并明确显示“当前修改尚未导出”。
6. 再次通过并导出。渲染成功后不增加卡片，同一个播放器切换到 B；刷新页面后仍是 B。
7. 再编辑一次并制造渲染失败。导出页仍播放 B，显示失败原因和重试入口，不循环假装“处理中”。
8. 在渲染进行中再次编辑。旧渲染完成后不得切换当前成片；仍保留 B，并提示当前修改未导出。
9. 连续提交两次相同导出请求。只注册一份当前正式 artifact，不多复制一份。
10. 导出过程中关闭页面。后台渲染继续；重新进入能看到结果，点击一次“导出”后完成发布。
11. 口播失败或仅有静音占位的条目，必须在渲染前被拒绝，且文案明确说明要先修口播。
12. 找一个老批次验证兼容：能继续导出，导出页仍只把 currentFormalArtifact 当正式视频。

第 4、6、7、8、11 条必须实际观察，不能只写“代码看起来没问题”。

## 停下来报告的条件

遇到以下任一情况，不要自行扩大范围：

1. 用户要的“覆盖”其实是导出文件夹里物理删除或覆盖旧文件。
2. 用户要求关闭页面或重启应用后，不再点击也能自动完成正式发布。
3. 现有任务结果与 artifact 指纹不足以可靠判断 formalOutdated，需要新增持久化字段。
4. output_version_cover 最终确实需要数据库迁移。
5. 无法在排整片渲染前守住审核、口播或静音占位闸门。
6. 目标文件已有不明脏改动，无法安全合并。

报告时说明：发现了什么、为什么当前方案不够、有哪些选择、各自代价；等确认后再继续。
