# 19：制作检查的通过标记会被修复逻辑冲掉

**要做什么：** 排时间来源的成片，一个检查单已经跑出 `ready` 结果、内容指纹也和现在的成片对得上，
但成片上的通过标记（`productionReady=true` + `formulaExecution`）会被反复冲掉，审批因此被拦，
而且修复逻辑自己也救不回来。

**现象（10-29 实测，批次 `20261028-ps889-新规矩-300条` 的 3 条试片）：**

- 执行检查结果在 `live_mixcut_formula_schedule_execution_results` 里是 `status='ready'`，
  `contentContractHash` 和当场重算的 `formulaExecutionContentHash(resolveFullRenderContract(...))` 完全相等。
- 但成片的 `arrangementJson` 里 `productionReady=false`、没有 `formulaExecution`、`blockers` 有
  `formula_execution_pending`。手工把通过标记补回去后，几秒内又被打回未通过。
- 把开发服务器停掉再补，标记就不再丢；服务器一跑起来就继续丢 —— 所以是进程内的修复循环在写。

**怀疑的根子：**

- `lib/live-mixcut/runner.ts` 的 `runPendingOnce` 每轮开头都跑 `repairFormulaContinuations` →
  `repairFormulaScheduleExecutionChecks` → `queueFormulaScheduleExecutionCheck`。
- 后者在「没通过」时会把成片重写成未通过、再按输入指纹找/建检查单。它用的是普通
  `db.transaction`（deferred），和执行检查提交的事务会交错：提交先盖了章，修复后写入自己读到的旧快照，
  把章覆盖掉。
- 章一被覆盖，`formulaOutputExecutionReady` 就看的是成片上的章（不是检查结果），于是永远判「没通过」；
  而按输入指纹又能找到那张已经跑完的检查单，不会再跑一次，于是卡死：不会自愈，也不会报错。

**要做什么：**

- 「通过」的判定只认「检查结果 + 内容指纹」，或者修复时看到结果已经 ready 就把标记补回去，
  不要让修复循环能把一个已经合格的成片打回未通过。
- 修复写入用 immediate 事务，或者加条件更新（`WHERE` 里带上当前 revision / 指纹），避免覆盖较新的提交。
- 补一个能复现交错场景的测试：检查提交之后紧接着跑一轮修复，成片仍然是 `productionReady=true`。

**依据：** 任务 13 验收时的实测现象与本次手工补标记的处理经过（见 13 的完成记录）。

## 完成记录

**2026-10-29 修好**

- 「通过」的判定改成只认「检查结果 + 内容指纹」：新增 `readFormulaExecutionProof`
  （`lib/live-mixcut/formula/execution-store.ts`），按血缘视图找这条成片最近的检查，
  结果必须 `ready`，且内容指纹等于现在重算的 `formulaExecutionContentHash(resolveFullRenderContract(...))`。
  `formulaOutputExecutionReady` 改为「成片上的标记指向的那张检查单，用上面这把尺子量一遍」。
- 修复自愈：`queueFormulaExecutionCheck` 和 `queueFormulaScheduleExecutionCheck` 在判「没通过」之后、
  重置标记之前，先看有没有合格结果；有就调 `restoreFormulaExecutionStamp` 把标记补回去并直接返回，
  不重置、不新开检查单。没有才按原来的路重排检查。
- 两个排队函数改成 `db.transaction(...).immediate()`：读到的成片和写回的成片在同一把写锁里，
  不会拿旧快照覆盖别的连接刚提交的标记。
- 真实内容改了（换片、改声音、改包装）时内容指纹会变，`readFormulaExecutionProof` 找不到合格结果，
  仍按原逻辑排新检查 —— 修复不会把「该重检」误判成「已通过」。
