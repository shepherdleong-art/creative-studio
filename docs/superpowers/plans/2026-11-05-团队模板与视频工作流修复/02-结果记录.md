# 02 视频缩略图鉴权修复 — 结果记录

**分支：** `ticket/02-video-thumbs`
**状态：** `ready-for-human` — 实现、定向测试、真实会话浏览器验收与 `check:main-path` 均通过，等 06 跨功能验收
**跑测时间：** 2026-11-05

## 1. 缺陷与成因

`succeeded` 视频卡片的海报来自 `sourceImageId` 对应分镜图，经 `toStorageImageUrl()` 变成
`/api/images/...`。这个路由在 server 模式要求会话 + 已登记文件实体授权。而
`components/VideoGenerationResults.tsx` 原先用 Next 默认图片优化渲染它。

Next 图片优化器是**服务端内部请求**：它不转发入站请求的 Cookie，因此永远取不到受保护图片。
浏览器拿到优化后的失败响应，`<img>` 落到 `complete=true / naturalWidth=0` —— 破图。

### 复现证据（修复前，真实服务 + 真实会话 + Chromium）

`scripts/video-poster-pre-fix-repro.mjs` 把组件临时还原成修复前写法后实测：

```
complete=true, naturalWidth=0, naturalHeight=0
currentSrc = http://127.0.0.1:<port>/_next/image?url=%2Fapi%2Fimages%2Finputs%2F<file>.png&w=384&q=75
/_next/image → 400
```

### 归因（为什么这是「优化器鉴权」而不是「优化器坏了」）

只报「受保护海报优化后 400」不足以归因，因为这个构建里优化器对别的东西也会 400
（例如 SVG 被 `dangerouslyAllowSVG` 策略挡掉；`w=300` 不在允许宽度里）。
所以验收里配了**公开栅格对照图**（`/icons/app-icon-512.png`）：

| 请求 | 结果 |
| --- | --- |
| 公开 PNG → 同一优化器 `w=640&q=75` | **200** |
| 受保护海报 → 同一优化器，无 Cookie | 400 |
| 受保护海报 → 同一优化器，带所属员工 Cookie | 400 |
| 原始海报 URL，带所属员工 Cookie | **200**（字节 SHA-256 与磁盘一致） |

公开图能过、受保护图过不了，且给优化器带上 Cookie 也没用 —— 差异只可能来自
「优化器不转发入站 Cookie」。这就是本票的缺陷本体。

## 2. 修复

`components/VideoGenerationResults.tsx` 新增两个内部单元：

- `PosterThumb` — 用 `unoptimized` 渲染海报。浏览器改为**带自身会话的同源请求**直接取图，
  服务端鉴权、`private, no-store` 缓存策略、`/api/images` 路由全部保持原样。
- `PosterFallback` — 加载失败后把 `<img>` 从 DOM 摘掉、换成「缩略图不可用」占位
  （`role="img"` + `aria-label`），失败地址只记一次，**没有重试计数**，不会对着同一个
  401/404 反复请求。

没有采用的三条捷径（票里明确禁止）：不通过公开文件接口、不取消鉴权、不在 URL 里塞会话凭据。

## 3. 修复范围（票要求的「扫描直接相关调用点」）

`next/image` 在 `components/**` 只有 2 处：

| 文件 | 状态 |
| --- | --- |
| `components/VideoGenerationResults.tsx` | 本票修复（`unoptimized` + 占位） |
| `components/mixcut/MaterialStep.tsx` | **已经是** `unoptimized`，无需改动 |

`next.config.ts` **没有**全局关闭图片优化。契约测试会把「受保护媒体被交给优化器」判为失败，
并已实测：临时去掉 `MaterialStep` 的 `unoptimized` 后该测试立刻报出该行。

其余受保护媒体展示（`ShotSetPanel`、`ResultGallery`、`HoverZoomImage` 等）用的是原生 `<img>`，
本来就走浏览器同源请求，不经优化器，不属于本缺陷范围。

**轻客户端：** `desktop/window.ts` 的 `window.loadURL(host.origin)` —— 同一个 Web 源、同一个会话 Cookie、
同一批页面组件。本票修复自动覆盖轻客户端，无需单独改动。

```powershell
$wsTemp = "I:\m7-studio\.worktrees\tmp-run"
```

### 断言口径（票里写死的那条）

不只看 `<img>` 存在，而是断言 `image.complete === true` **且** `naturalWidth > 0`，
并核对宽度等于夹具图片真实尺寸：

| 角色 | 结果 |
| --- | --- |
| 管理员 | `complete=true`，`naturalWidth=640 / naturalHeight=360` |
| 图片所属员工 | `complete=true`，`naturalWidth=640 / naturalHeight=360`，`currentSrc` **不含** `/_next/image`；`/api/images` 请求 200，海报优化器请求 **0** 次 |
| 其他员工 | 被页面守卫挡出（落点 `/`），浏览器取海报 **404**，无结果卡、无海报元素 |
| 未登录 | 重定向 `/team/login`，取海报 **401**，无海报元素 |

账号隔离（同一浏览器切换）：所属员工 A → 登出 → 其他员工 B，B 在同一上下文取 A 的海报
**404**（`cache-control: no-store`，不可能命中上一账号的缓存），打开 A 的项目被挡出，
页面无结果卡/海报元素。

失败占位：拦截 `/api/images/**` 恒定 404 → 出现「缩略图不可用」占位，DOM 中
**不再保留任何破图 `<img>`**；固定观察窗 4s 内新增请求 **0** 次（无无界重试）。

视频未被破坏：点「播放」后 `readyState >= 2`；下载入口仍指向 `/api/videos/...` 且带建议文件名；
HTTP 直取视频 200 且字节数与磁盘一致。

窗口/主题：1440 与 1100 两种宽度 × 浅色/深色，四种组合下海报均 `complete` 且 `naturalWidth > 0`。

local 模式：同一组件、同一契约，`complete=true`、`naturalWidth > 0`、不经优化器。

## 6. 已知风险 / 未做的现场项

- **未在真实服务器（生产部署）上验证。** 本票证据全部来自隔离数据根 + 本地 `next dev`。
  规格 §8 要求「服务器源码/运行版本对照」，属 06 的范围。
- **轻客户端未单独跑 Electron 实例。** 已从代码确认它 `loadURL` 同一个 Web 源、共用会话 Cookie，
  因此修复方式相同；但没有 Electron 实机截图。
- **图片缺失（`posterImageUrl` 为空）** 仍走原有的 `<video preload="metadata">` 兜底，这是既有行为，
  本票没有改动；「读取失败」路径则走新的占位。
- `src/app` 里没有 `dangerouslyAllowSVG`，因此 SVG 无法作为优化器对照 —— 对照组用了 public 下的 PNG。
- 证据目录 `outputs/` 是 gitignored 的本机产物，不随分支交付；需要复核时按上面命令重跑即可重现。
