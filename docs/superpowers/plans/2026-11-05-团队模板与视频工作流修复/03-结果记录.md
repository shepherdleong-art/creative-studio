## 3. 票里点名的两个场景

### 场景 A：两位同名成员 → 不同组，按 ID 筛选准确

隔离库建了两个 `displayName = 李四` 的账号（工号 0301 / 0302），各自灌入任务。

| 观察点 | 结果 |
| --- | --- |
| 成员下拉选项 | `李四（工号 0301）`、`李四（工号 0302）` 两个独立选项 |
| 选 0301 后页面分组 | 只有 1 个组，`data-actor-user-id` = 0301 的 userId |
| 选 0302 后页面分组 | 只有 1 个组，`data-actor-user-id` = 0302 的 userId |
| 0302 的结果条数 | `当前结果 1 条`（未混入 0301 的 520 条） |

分组身份只认 `actorUserId`，姓名纯粹是显示值；工号一起显示，停用成员也仍可辨认。

### 场景 B：500 条截断下低频成员仍可查出

数据布局：低频成员 1 条极早任务（2026-01-01），随后 520 条较新任务（2026-10-01），
停用成员的等待任务与一条 `stage_canceled` 任务。

| 观察点 | 结果 |
| --- | --- |
| 默认结果条数 | 500（`limit = 500`、`truncated = true`） |
| 总提示文案 | `显示当前结果 500 条…最多返回最近 500 条记录（已到上限，更早的记录未显示）` |
| 组计数口径 | `当前结果 N 条` + 明写「不是该成员全部历史任务数」 |
| 低频成员是否在选项里 | 在（选项来自 `team_users`，不依赖任务结果） |
| 选低频成员后 | `低频成员（工号 0320）当前结果 1 条`，`truncated = false` |

## 5. 接口约定（给 06 / 后续票）

`GET /api/team/tasks` 响应新增字段，均为追加、不破坏既有消费者：

```ts
{
  items: TeamTaskView[];      // 新增 actorAccountStatus: 'active' | 'disabled'
  actors: TeamTaskActorOption[];  // { actorUserId, employeeId, displayName, accountStatus, role }
  limit: number;              // 常量 500
  truncated: boolean;         // 是否还有更早记录未返回
  totalMatching: null;        // 本轮不做全历史分页，显式 null
  localAgentIncluded: false;
}
```

- `actors` 始终返回完整名册（选中某成员后仍可切回其他成员）。
- 员工调用时 `actors` 只含自己，`limit/truncated` 也按本人结果计算。
- 分组纯逻辑在 `lib/team-task-groups.ts`，浏览器与服务端共用，不要另写一份。
