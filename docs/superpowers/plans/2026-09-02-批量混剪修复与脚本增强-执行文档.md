## 任务 B1（P0）：斜体在正式渲染中丢失

### 现象

用户在**第二步「脚本与口播」**的批次级字幕样式面板勾选「斜体」并随批次锁定。之后：第二步面板预览（斜体✓）→ 第三步预览弹窗（直立✗）→ 「调整片段」编辑器（斜体✓）→ 导出文件（直立✗）。

### 根因（已三重验证）

1. **数据链路无问题**：数据库 `batch_production_versions.defaultsJson.subtitleStyles.italic = true` 已正确冻结（该批次仅 v1，不存在"改样式产生新版本但渲染用旧版"）。
2. SVG 生成正确携带 `font-style="italic"`：`lib/media-core/cover-title-svg.ts` 第 52 行 `italicAttr`。
3. **死因**：sharp 依赖的 librsvg/pango 渲染管线**不会为没有 italic 字面的字体合成斜体**。实测（复现脚本 `outputs/diag-italic-render.ts`）：
   - `Alibaba PuHuiTi 3.0`、`Microsoft YaHei`：CJK 部分 italic true/false 渲染**完全一致**（直立）；
   - 拉丁字符走字体回退能找到 italic 字面 → 斜体；
   - `Arial`（自带 italic 字面）→ 正常斜体。
4. 浏览器预览（第二步面板、调整片段编辑器）走 CSS，**浏览器会合成斜体**——两处预览与正式渲染表现不一致的根源。
5. 附带发现：封面标题的"斜体"是**假象**——封面字体 `PingFang SC` 在 Windows 不存在，静默回退到**楷体**（天生斜势），与 italic 标志无关（`outputs/diag-italic-pingfang.ts` 实测 true/false 逐像素一致）。该问题单列 B5。

### 修改方案（已实测可行）

把斜体实现从 `font-style="italic"` 改为**绕文字锚点的 `skewX(-12)` 剪切**，改动只在 `lib/media-core/cover-title-svg.ts` 的 `textStyleToSvgElements`（第 42 行起）一处：

- 现状：每个文字层是 `<text x="{px}" y="{py}" ... font-style="italic">`（阴影开启时两层：偏移下层 + 正文层，第 57-66 行）。
- 改为：当 `style.italic === true` 时，每层包成 `<g transform="translate({px},{py}) skewX(-12)"><text x="0" y="0" ...（不带 font-style）>...</text></g>`；`italic === false` 时保持现有输出不变。
- **去掉 `font-style` 属性**，预览（浏览器）与渲染（librsvg）统一走剪切合成——该函数的设计初衷就是“预览与成片同一份实现”。B1 只保证斜体开关、倾斜方向和角度一致；字体字形是否完全一致仍受各平台字体可用性与 B5 的 fallback 问题影响，不宣称全面 WYSIWYG。
- 取舍（已知并接受）：`Arial` 等有真斜体面的字体也统一走合成，不再使用原生斜体字形。本产品为 CJK 场景，可接受。
- skew 角度固定为 `-12`；本任务不再开放角度分支，边界问题按下一条的补偿规则解决。（2026-09-02 复核在本机 sharp/libvips 8.17.3 上实测：`<g transform="translate(px,py) skewX(-12)"><text x="0" y="0">` 经 librsvg 正常生效，与直立版本像素差异显著，机制成立。）
- 描边（`paint-order="stroke fill"`）与阴影层必须随组一起剪切，保持视觉厚度一致。
- 边界不变量固定为：**原本完整落在文字对齐框内的非斜体，开启斜体后仍完整落在同一对齐框内，并保持 left/center/right 的对齐语义**。描边与阴影也计入边界。
- **补偿规则（照此实现，不要自创）**：`italic === true` 时，把参与 fit 的可用宽度先减去 overhang 再缩字号，**锚点坐标不动**——
  ```
  const overhang = style.italic ? fontSize * Math.tan(12 * Math.PI / 180) : 0;  // ≈ fontSize * 0.2126
  const usableWidth = Math.max(1, style.boxWidthPx - overhang);
  // 用 usableWidth（而不是 boxWidthPx）跑现有的 estimateSingleLineWidth 缩放
  ```
  因为 fontSize 会被缩放回写，overhang 要用**缩放后的最终 fontSize** 迭代一次（先按初始 fontSize 估 overhang → 缩放 → 用新 fontSize 重算 overhang → 再缩一次即可收敛，不必循环）。
  移锚点会破坏 left/right 的对齐语义，所以只允许缩字号，不允许平移锚点。
  副作用是同一段文字开启斜体后可能比直立版本略小，这是接受的取舍。
- 量级参考（80px 字号、PingFang、开描边实测）：直立 bbox `x0=160 x1=639`，skew 后 `x0=164 x1=647`——字形顶部右移约 17px、底部左移约 2px，与 `fontSize × tan(12°)` 吻合。
- `estimateSingleLineWidth` 本身不改（它只负责按可用宽度缩字号）；overhang 的计算放在调用它之前。
- 这是渲染语义变化：把 `lib/batch-production/phase-e.ts` 的 `BATCH_RENDER_ADAPTER_VERSION` 从 `batch-render-v2` 提升到 `batch-render-v3`，同步更新 `scripts/batch-output-clip-edit.test.ts` 中 3 处精确 requestKey 断言。该常量是**新建渲染任务的幂等契约盐**，不是 attempt 级真实执行版本：旧 v2 任务点「重新生成」仍保留原 requestKey，但新 attempt 会运行当前代码并产出修复后的斜体。已存在候选不会自动改写，需显式重渲染。

### 影响面

本次实际影响的是批量生产中调用该共享函数的路径：

## 任务 B2（P0）：重渲染后封面卡片/预览弹窗不刷新

### 现象

「调整片段」替换封面并重新渲染成功后，检查成片页卡片仍可能显示旧封面；预览弹窗也可能继续播放旧产物。另一个必须覆盖的真实场景是：旧视频播放数秒后卡死，用户**没有修改片段**，直接点卡片上的「重新生成」修复渲染；后台会重跑，但 `versionId` 与 `editRevision` 都不会变化。

### 已确认事实与根因

- 卡片上的「重新生成」经 `retryRenderTask` 调用 tasks retry API，最终进入 `retryTask`；后者明确允许已成功的 `output_version` 渲染任务再次排队（`lib/batch-production/scheduler.ts` 第 420-450 行）。每次领取都会产生新的 `batch_task_attempts.id`，渲染器还会使用随机 UUID 建立全新目录（`lib/batch-production/batch-renderer.ts` 第 706-714 行），所以「未编辑直接重新生成」也会真实重跑 FFmpeg，而不是复用旧文件。这里的“新视频”指新的 attempt 和物理文件；输入完全相同时，正常产物的画面甚至 SHA-256 仍可能相同。
- 未编辑重渲染时，`outputVersionId` 和 `editRevision` 保持不变；只有“成功渲染尝试”发生了变化。因此 `candidate.editRevision` 不是渲染代际，`task.attemptCount` 也不是：它在新尝试开始时就会变化，而此时工作区仍应继续播放上一次成功候选。
- 媒体 API 虽然带 `Cache-Control: no-store`，但当前 candidate URL 在重渲染前后完全相同；卡片 `<img>` 不重建，预览 `<video>` 的 key 只含 `planId-versionId`。React 因 `src`/`key` 没变不会可靠地重载媒体。
- Electron 不会消除该问题：页面和媒体元素仍由 Chromium 驱动。对 `<video><source>` 只改数据而不重建 `<video>`，不能保证重新执行 `load()`。
- candidate URL 当前表示“查询当下最新成功尝试”，而视频会发多个 Range 请求。同一个 URL 在播放过程中若突然改指另一份文件，理论上可能把不同文件的分段响应混在同一媒体会话中；修复后一个 URL 必须固定指向一个成功尝试。

### 修改方案

#### 1. 把“最近一次成功渲染尝试”暴露为媒体代际

- `lib/batch-production/batch-workspace.ts` 的候选查询同时读取 `a.id AS renderAttemptId`，在 `BatchWorkspaceCandidateView` 增加必填字段 `renderAttemptId: string`。
- 历史版本列表 `BatchOutputVersionListItem` 增加 `candidateRenderAttemptId: string | null` 和 `artifactId: string | null`；前者指该版本最近成功的渲染 attempt，后者指该版本最近登记的正式视频 artifact（封面按同一导出对解析）。`hasCandidate` / `hasArtifact` 可由对应 ID 是否存在派生。
- “最近一次成功”沿用确定顺序：先按渲染任务 `createdAt DESC, id DESC` 选任务，再按该任务的 `attemptNumber DESC` 选成功尝试；不得按随机 UUID 排序。candidate 的 `renderAttemptId`、`resultJson` 及所有派生字段必须来自**同一 attempt 行**。
- 只采用**已经原子提交成功**的尝试 ID。新尝试处于 queued/running 或失败时继续返回旧成功 ID；runner 在文件校验完成并提交成功结果后，workspace 才能看到新 ID，避免出现“ID 已更新但文件尚不可读”，也保留失败回落能力。

#### 2. 让 candidate URL 真正绑定该尝试

- candidate 媒体 URL 增加 `renderAttemptId`，例如 `...?source=candidate&renderAttemptId=<uuid>`。
- `media/route.ts` 与 `resolveBatchOutputMedia` 接收这个可选参数；传入时必须通过 `batch_tasks + batch_task_attempts` 联表校验 task 确为 `workType=render + targetKind=output_version`、attempt 为 `succeeded`，并且属于当前 `projectId + batchId + planId + outputVersionId`，然后只解析该尝试的 `resultJson`。参数格式无效返回 400；不存在、谱系不符、非成功或结果不可用统一返回 404，不回落到其他计划或“当前最新”。较旧但合法的成功 attempt 仍可读取。
- 未传 `renderAttemptId` 时保留现有“最近一次成功候选”行为，兼容旧调用；新 UI 一律传入。
- artifact 同样增加可选 `artifactId` 参数。传入时校验它是该谱系下已登记的视频 artifact；`kind=cover` 时解析与它同一导出对的封面。未传保持旧行为，新 UI 一律传入当前/历史项暴露的确切 ID。
- 这两个参数不只是 cache-buster。对同一个 `renderAttemptId` 或 `artifactId` 的所有普通/Range 请求都必须解析到同一物理文件。

#### 3. URL 与媒体元素 key 同时使用代际

- `BatchStepReview.tsx`：卡片封面和弹窗视频的 URL 都带对应 `renderAttemptId`；`<img>` 与父级 `<video>` 的 key 至少包含 `source + outputVersionId + renderAttemptId`。不能只给 `<source>` 换 key。
- `BatchOutputEditor.tsx`：固定采用**上层传入**的当前候选 `renderAttemptId`，编辑器封面 URL/key 同步使用；不要再给 arrangement 视图增加第二个媒体代际来源，也不要拿编辑器自己的 `editRevision` 代替。
- `BatchStepExport.tsx`：candidate 预览 URL 和 `<video>` key 同步使用同一代际。
- artifact URL/key 使用确切 `artifactId`；历史版本使用其 `candidateRenderAttemptId` 或 `artifactId`。
- 保留父面板既有轮询：任务状态变化后重新读取 workspace。已打开弹窗必须继续按 `planId` 从最新 workspace 解析 `modalCard`，不能长期保存打开瞬间的 candidate 快照；这样成功后的新 ID 才会真正传到 URL/key。**这一条是「保持现状」不是「新增」**：`BatchStepReview.tsx` 第 195 行已经是 `workspace.cards.find((card) => card.planId === previewCard.planId) ?? previewCard`，别去改它。要改的只有第 482 行 `<video>` 那个只含 ``planId-versionId`` 的 key（缺少渲染代际）。

#### 4. 明确禁止的替代信号

- 不使用 `candidate.editRevision`：未编辑的强制重渲染不会改变它。
- 不使用当前任务的 `attemptCount` 或正在运行的 attempt ID：它们会在新候选成功前变化，导致新 URL 仍取到旧文件，成功时反而不再变化。
- 不只依赖 `Cache-Control: no-store`、关闭弹窗重开或手工 F5；这些都不是自动刷新契约。

### 验证

1. 同一 `outputVersionId`、同一 `editRevision` 连续完成两次成功渲染：两个 attempt ID 和物理目录不同；工作区先保持第一个 ID，第二次成功后切为第二个 ID。
2. 第二次渲染失败：工作区和媒体 URL 仍指向第一次成功候选。
3. 第二次渲染成功：不刷新页面、不关闭弹窗，卡片封面自动换新，已打开的 `<video>` 被重建并播放第二次产物。
4. Electron 手工回归：准备一条可识别的旧候选，未编辑直接点「重新生成」，确认完成后 URL、DOM key 和播放内容都切到新 attempt。
5. 媒体路由测试：合法 attempt/artifact 可读；跨项目、跨批次、跨计划、跨版本或非 succeeded attempt 均不可读；同一媒体 ID 的 Range 请求始终命中同一文件。

## 任务 B3（P1）：「下载视频」重渲染后仍给旧文件

### 根因（已定位）

下载按钮（`components/batch-production/BatchStepExport.tsx` 第 204-209 行）固定走 `media?source=artifact`。artifact 只在正式导出成功时登记，所以重渲染后、下次正式导出前，按钮仍下载上一次正式产物。

`resolveBatchOutputMedia` 对 `candidate` 与 `artifact` 是二选一解析，**不会自动 candidate → artifact 回退**。导出页预览已经在前端计算 `candidate ? candidate : artifact`，下载按钮却没有复用这一选择。另外，candidate 可能是静音占位、落后于当前编辑，默认文件名也只是 `video.mp4` / `cover.jpg`；不能把所有 candidate 无条件当成正式下载源。

### 修改方案

- 固定采用两套独立按钮，不在重渲染成功时自动登记 artifact，也不让同一个按钮静默改变来源：
  - **最新渲染预览**：仅当 `card.task?.status === 'succeeded'`、`candidate.productionReady === true` 且 `!card.renderStale` 时显示「下载最新预览视频 / 封面」，绑定 B2 的确切 `renderAttemptId`。未审核 candidate 仍只是预览下载，不代表正式导出。
  - **上次正式版**：只要 `card.currentVideo` 存在，就独立显示「下载上次正式版视频 / 封面」，绑定 B2 的确切 `artifactId`。它表示该成片最近一次成功登记的正式导出对。
  - queued/running 时旧成功 candidate 只作播放回落，不称为“最新”；failed 时同样不显示最新预览下载，并显示“渲染失败，请重试”。静音占位或 stale candidate 也不提供最新预览下载。
- 当前下载控件包在 `published && (...)` 内；candidate 下载入口必须移出这个条件，否则“已有新渲染但从未正式导出”的成片仍无按钮。artifact 按钮继续以对应 artifact 是否存在为条件。
- candidate 下载继续通过媒体 URL 的 `download=1` 触发 attachment；其 `Content-Disposition` 由服务端生成可辨认的安全文件名（至少包含成片序号、版本号和“预览”），不要沿用渲染目录里的通用 basename。没有 `download=1` 的播放请求保持 inline。
- **文件名的数据来源**：`BatchOutputMediaFile`（`lib/batch-production/output-media.ts` 第 11-16 行）目前只有 `absolutePath / contentType / source / productionReady`，**拿不到成片序号和版本号**。做法是给它加 `planSeq: number` 与 `outputVersionNumber: number`，在 `resolveBatchOutputMedia` 现有的 plan 谱系查询里顺带 `SELECT p.seq, o.versionNumber` 补上（那个查询已经 JOIN 到计划与批次，不用新增独立查询）；route 只负责拼名字与转义，不再自己查库。文件名仍全部由服务端生成，绝不接受浏览器传入的名字。
- artifact 仍只由正式导出流程登记；“通过审核 + 正式导出”的门禁不变。

### 验证

1. 重渲染成功但尚未再次正式导出：点「下载最新预览视频」，SHA-256 与最新成功 candidate 一致，文件名可辨认。
2. 重渲染中、失败或 candidate 落后：不得把旧 candidate 冒充最新；若有 artifact，只提供并明确标注“上次正式版”。
3. 静音占位 candidate 不出现“下载最新预览视频”入口。

- 检查页和导出页**已经有**「待审核 / 待重新生成 / 等待重新渲染」chip，不重复造一套相同状态。
- `loadWorkspace` 会先把不再 publishable 或已经 stale 的 ID 从 `selectedPlanIds` 静默删除（`BatchPreparationPanel.tsx` 第 412-416 行）；`publishSelected` 又会把未审核或 stale 项从 `planIdsToPublish` 过滤掉（第 1392-1427 行）。因此很多失败在请求前就消失，服务端的逐条 skipped 结果看不到这些卡片，单纯放大后端错误文案无法修复。

### 修改方案

1. **编辑响应原子说明审核变化**：`BatchOutputClipEditResult` 增加 `reviewCleared: boolean`。事务内修改前记录是否存在 `arrangement.review`；只有这次有效编辑实际删除了既有 review 时返回 `true`。unchanged、本来就没有 review，或只把同一源区间连续切成两条但不改变顺序/画面输出的纯结构 `split`，均返回 `false`。API 原样透传，无需迁移。
2. **编辑器即时提示**：`BatchOutputEditor.submitEdit` 收到 `reviewCleared: true` 后，在顶部显示常驻提示「本次修改已重置审核状态；重新渲染完成后，请返回检查成片重新通过」。该提示覆盖片段、封面、字幕、BGM、口播音量等所有有效编辑，不只写字幕场景，并在本次编辑器会话内持续显示。
3. **复用现有卡片 chip**：保留现有 `待审核 / 待重新生成 / 等待重新渲染`，只在文案或颜色确有歧义时调整，不新增重复状态源。
4. **选中项失效时立即说明**：保留现有“失效项不能继续勾选/发布”的安全行为，但 `loadWorkspace` 清理既有选择时必须计算被移除的 planId，并按最新 card 状态显示常驻列表，例如「成片 03：修改后需要重新渲染和审核」，不能静默减少“已选”数量。
5. **把剩余选中项全部交给服务端复核**：只在 `selectedCards.length === 0` 时前端拦截。这里的 `selectedCards` 是由当前 `selectedPlanIds` 与 workspace 做归属匹配得到、但**尚未按** `productionReady/publishable/approved/renderStale` 过滤的原始选择集合；请求 planId 必须与它去重后完全相等。服务端已有逐条门禁和 `{ planId, status, reason }` 返回，继续作为最终事实源，也能覆盖最后一次 workspace 读取与 POST 之间的竞态。
6. **结构化展示结果**：前端响应类型补上 `planId`（**后端 `BatchPublishItemResult` 已经有 `planId`**，见 `lib/batch-production/phase-e.ts` 第 460-467 行——只需要改 `BatchPreparationPanel.tsx` 第 1417 行那个内联响应类型 `Array<{ status; reason?; videoRelativePath? }>`，不要动后端），用 workspace 映射成「成片 03 · 标题：等待重新渲染」这样的列表。成功数、前端移除项与服务端 skipped 项分开展示，不再只拼成一行汇总字符串。编辑提示只保持到本轮编辑器关闭，之后由现有 chip 承接；选择失效提示保持到用户重新选择或开始下一次导出；旧导出结果在下一次导出收到响应后整体替换。

### 验证

1. 已审核成片分别做 trim/替换片段、字幕、BGM、口播音量编辑：响应 `reviewCleared:true`，编辑器均出现提示；重复提交无变化值以及输出等价的纯结构 split 返回 `false`。
2. 选中一条成片后再编辑使其 stale/未审核：workspace 刷新可取消其选择，但必须立即列出该成片和失效原因，不能静默消失。
3. 模拟 workspace 读取后、POST 前状态变化的竞态：前端发送该 planId，服务端 skipped，页面逐条展示原因。
4. 同时收到 published 与 skipped：成功项和失败项分开展示；重新渲染并「通过」后再次导出成功。

## 任务 F2（P2）：「再生成一组」支持当次指定条数/秒数

### 现状（已定位）

- 「再生成一组」（`ScriptStudioPanel.tsx` 第 713-719 行 `regenerateGroup`）复用 `startTask`（第 570-605 行），**本来就读当前表单 state**（数量 `requestedCount` 第 394 行、时长 `targetDurationSec` 第 393 行），但表单在第 1 页、按钮在第 3 页，用户无感知。
- 后端 POST `/tasks` 接收合法参数（时长白名单 15/20/30/45/60，数量上限按 F1 调整后的 6），并允许调用方显式传入 `requestKey`。未显式传入时，route 会根据参数生成稳定 requestKey；因此**参数与上次完全相同会返回旧任务（202 + created:false）**。
- 现有 `createTask` 是“先查再插”；route 的外层预查和真正插入之间还会 `await ensureScriptStudioSchedulerStarted()`。因此显式 `requestKey` 只是接口能力，**尚不能保证两个并发请求原子去重**：两边可能同时查不到，后插入者撞唯一约束，而不是稳定返回同一任务。
- 这与按钮「再生成一组」的产品语义冲突：用户即使保持相同条数和秒数，也是在明确要求一组新的脚本，不能提示“复用原结果”。

### 产品与幂等语义

- 第一次生成：可以继续使用参数派生的稳定 requestKey，防止重复提交同一首次任务。
- 每次用户明确点击「再生成一组」：创建一个新的 regeneration action；即使参数完全相同，也必须生成新任务、新脚本组。
- 同一次 action 因双击、重复事件或网络结果不确定而重送：复用**同一个不可变请求快照和同一个 requestKey**，只创建一个任务。
- 相同 `requestKey` 只能代表同一个执行请求；如果 key 相同但客户端冻结的 action body 不同，服务端必须用现有 `conflict` 错误返回 `409`，不能静默复用旧任务。重试期间供应商配置等外部状态变化不算 body 变化，也不能改变已创建任务首次冻结的执行身份。

### 修改方案（无需数据库迁移，前后端配合）

- 在「再生成一组」按钮旁（第 1179 行附近）增加本次专用的条数/秒数控件，复用 F1 的数量契约和 15/20/30/45/60 秒白名单；初始化为上一组参数，但不与第 1 页表单形成隐式共享状态。
- `startTask` 改为接收完整的显式参数，不再从闭包读取关键字段。`RegenerationAction` 定义为不可变的 `{ requestKey, body }`，其中 `body` 就是一次性序列化后实际发送给 `/tasks` 的**完整 POST body**，不能只摘取几个字段再在重试时重建；当前字段包括 `sourceSetId`、`libraryRevisionId`、`targetDurationSec`、`requestedCount`、`creativeBrief`、明确的 `providerId`，以及端点以后新增且会实际发送的任何字段。
- 控件只在**切换到一个新结果组时**从该任务的 `inputSnapshot` 初始化一次；不要用持续运行的 effect 把用户正在编辑的“下一组参数”反复覆盖。
- `regenerateGroup` 使用同步引用实现 `pendingActionRef.current ??= createActionSnapshot()`：第一次点击生成 `regenerate-group:${crypto.randomUUID()}` 并冻结整份 POST body；同一次传输重试原样复用 key 和 body，上一动作得到明确结果并结束后，下一次明确点击才创建新 key。
- 按钮同时使用 `submitting` 禁用和同步 in-flight guard，保证极速双击最多发出一次 fetch。收到明确 `202` 成功或明确不可重试的业务拒绝（例如参数型 `4xx`）后清理 pending action；连接中断、超时、`5xx` 等“服务端是否已经创建任务未知”的结果都保留原 action，并把按钮呈现为「重试本次提交」，不能从最新表单状态重建 body。
- 把 `createTask` 改成数据库层的原子 get-or-create：优先用 `INSERT ... ON CONFLICT(projectId, requestKey) DO NOTHING` 后回读，或捕获该唯一约束冲突后回读既有任务。route 外层预查可以保留作快速路径，但不能承担并发正确性。
- 提取唯一的 canonical identity 构造/比较函数，覆盖 `CreateTaskInput` 的全部持久字段：`projectId`、mode、sourceSetId、libraryRevisionId、requestedCount、parentTaskId，以及规范化后的完整 `inputSnapshot`；不要列白名单漏掉未来字段。route 快速预查命中与原子插入冲突后回读必须调用**同一个 comparator**：一致才返回 `202 + created:false`，不一致用现有 `ScriptStudioError('conflict', ...)` 返回 `409`。

## 任务 F4（P2）：字体搜索、收藏置顶与字形预览

### 用户目标

把当前只能展开一长串名称的原生字体下拉框，改成类似剪映的字体面板：可以按名称搜索、收藏常用字体，收藏项始终排在前面，并且在选择前就能直接看到字体的大致字形。

### 现状与边界（已定位）

- 用户截图对应「调整片段」右栏的 `BatchOutputEditor` → `BatchTextStyleEditor`。当前用原生 `<select>` 展示数百个 family 名称；原生 option 在 Chromium/Electron 和操作系统之间样式能力不一致，无法可靠放搜索框、收藏按钮和双行字形样本，因此不能继续在 `<select>` 上打补丁。
- 字体数据已经有两条来源：`/api/system-fonts` 扫描标准系统/用户字体目录，`components/system-fonts.ts` 再通过 `queryLocalFonts()` 合并字体管家等会话字体，并带会话缓存与后台重校验。本任务复用这条链路，**不新增字体接口、不新增数据库迁移**。
- 目前字体控件并不统一：`BatchTextStyleEditor.tsx` 自己请求接口；`BatchStepScripts.tsx` 也直接请求接口；`FinalEditInspector.tsx` 和 `mixcut/CoverEditorDrawer.tsx` 已使用共享加载器，但仍各自渲染原生 select。只改截图这一处会造成字幕、封面和批次默认样式体验不一致。
- 收藏属于“这台电脑上的个人操作偏好”，跨项目、跨批次、字幕与封面共用；它不是项目内容，也不进入批次冻结快照、成片版本或导出包。
- 本任务中的“字形预览”是浏览器用该 family 实时绘制固定样本文字；它帮助用户挑选字体，但不替代 B5 的服务端字体可用性校验，也不承诺跨操作系统逐像素一致。

### 产品口径

1. 点击字体框后打开自定义浮层。顶部是搜索框，下面只有「全部」「收藏」两个页签；剪映截图里的「最近、系统、品牌、图搜记录」不在本期范围。
2. 「全部」页的正常顺序是匹配的收藏字体 → 其余匹配字体；同一字体只出现一次。唯一例外是“当前选中但未检测到”的保护行，它单独放在最前面的「当前字体」组。收藏组按最近收藏在前，其余字体按 family 名稳定排序。
3. 每一行同时显示：用界面字体书写的 family 名、用目标字体书写的 `春风正好 Aa 123` 样本、当前选中勾选态，以及独立的收藏/取消收藏星标。点星标只改变收藏，不选择字体、不关闭浮层；点字体行才应用并关闭。
4. 字体比较统一使用 `fontIdentity(value) = value.normalize('NFKC').trim().toLocaleLowerCase('en-US')`：搜索、去重、收藏命中和缺失判断全部使用该 identity，提交时仍保留原 family 字符串。搜索做 identity 的包含匹配；不做拼音、模糊纠错或联网搜索。无结果时显示「没有找到匹配字体」，并保留清空搜索入口。
5. 收藏即时写入本机偏好并同步所有已挂载的字体面板；关闭重开、刷新页面和切换项目后仍保留。localStorage 不可读、内容损坏或不可写时，选择字体仍可正常工作，只是不持久化收藏。
6. 这里的“未检测到”只表示 family identity 不在 `/api/system-fonts + queryLocalFonts()` 的客户端合并目录中，不等同于 B5 的“服务端最终可渲染”。已有项目当前选中但未检测到的字体必须保留：触发器继续显示；「全部」页在无搜索或名称命中搜索时增加置顶的「当前字体」组，选择按钮为已选/不可重复选择状态，星标仍可操作。已收藏但当前未检测到的字体保留在偏好中，只在「收藏」页显示为不可选择的「当前未检测到」行，星标仍可取消；重新安装/激活后自动恢复可选。不可选择按钮使用可聚焦的 `aria-disabled="true"` 而不是原生 `disabled`，点击或 Enter/Space 不触发 `onChange`，键盘仍可从它移到星标。搜索期间所有特殊行同样必须匹配名称，不能绕过筛选。
7. 浮层使用当前应用浅色/深色设计令牌；在 Electron 的窄右栏中也不能被 `overflow` 裁掉。下方空间不足时向上展开，左右贴近窗口时自动收边。

### 修改方案

#### 1. 建立唯一共享字体选择器

- 新增 `components/ui/SystemFontPicker.tsx` 与同名 CSS module，替代各处原生字体 select。组件至少接收 `{ value, ariaLabel, disabled, onChange, compact?, portalRoot? }`，内部统一读取共享字体目录与收藏偏好。
- 触发器显示当前 family，并让名称本身使用当前字体绘制；普通页面的浮层通过 `createPortal(..., document.body)` 定位到触发器附近，避免被右栏 `overflow-y:auto` 或卡片裁切。监听 resize 和捕获阶段 scroll 后重算位置。
- 两个封面抽屉已经各自实现焦点陷阱和全局 Esc。抽屉内不能直接把字体浮层挂到 body：否则它不在 `dialogRef.querySelectorAll(...)` 的焦点集合里，Esc 还可能同时关掉字体面板和整个抽屉。为两个抽屉各提供一个位于 `<section role="dialog">` 内、但脱离滚动字段的 overlay host，`SystemFontPicker` 通过可选 `portalRoot` 挂到该 host；host 内的浮层仍用 fixed 坐标和高于抽屉的层级。字体面板先消费 Esc 并阻止继续冒泡，抽屉 keydown 先检查 `event.defaultPrevented`/嵌套浮层状态，实现“第一次 Esc 只关字体面板，第二次才关抽屉”。两个抽屉的焦点陷阱都是每次 Tab 从 `dialogRef.current.querySelectorAll(...)` 按 **DOM 顺序**重算的（`BatchCoverEditorDrawer.tsx` 第 146 行、`mixcut/CoverEditorDrawer.tsx` 第 100 行），所以 overlay host 要放在触发器所在 section **之后紧邻**的位置，别一律塞到 dialog 末尾，否则浮层内控件的 Tab 顺序会跳到抽屉最后。选择器是 `button:not(:disabled), ...`，`aria-disabled` 的按钮天然会留在陷阱集合里，与上文的可访问性口径一致。
- 浮层包含搜索、全部/收藏页签、分组标题、可滚动样本列表和刷新入口。选择后调用 `onChange(family)`、关闭并把焦点还给触发器；Esc 关闭同样还焦点。点浮层外或 Tab 移到外部控件时只关闭浮层，保留用户刚点击/移动到的焦点，不能再抢回触发器。刷新沿用 `requestFontOptions(true)`，失败只给行内提示，不清空现有列表和当前值。
- 在 `components/ui/Icon.tsx` 补共享的 `star`、`chevron-down` 图标；搜索和关闭继续复用已有图标。星标按钮提供完整中文 `aria-label`，不能只靠颜色表达状态。

#### 2. 收藏与排序使用一个外部状态源

- 新增浏览器侧字体偏好模块（例如 `components/font-preferences.ts`），唯一 key 固定为 `creative-studio-font-favorites-v1`，值为去重后的 family 字符串数组；新收藏插到数组头部，取消收藏只删除目标项。
- 解析器容忍非法 JSON、非数组、空字符串和重复值。使用 `useSyncExternalStore` 暴露快照；同页写入时主动通知订阅者，跨标签页/窗口通过 `storage` 事件同步，避免多个字体面板各持一份会漂移的 state。localStorage 写入失败时仍更新本次会话的内存快照，所以收藏按钮当场有效，只是不跨刷新保留。
- 把 `fontIdentity`、去重、搜索、收藏优先排序和“当前缺失项/收藏缺失项”归并提取成不访问 DOM 的纯函数，供 Node 测试直接覆盖。归并输入顺序固定为当前值 → 服务端列表 → `queryLocalFonts()` → 收藏偏好，同 identity 时保留第一个原值；收藏按偏好数组顺序（最近收藏在前），非收藏使用 `Intl.Collator('zh-CN', { numeric: true, sensitivity: 'base' })`，比较相等时再按原 family 字符串码点顺序打破平局，保证各平台测试结果唯一。

#### 3. 复用现有字体加载链路

- `SystemFontPicker` 首帧使用 `getCachedFontOptions()`，挂载后调用 `requestFontOptions()` 做 stale-while-revalidate；因此已有缓存时立即显示完整列表，无缓存时显示轻量加载态，结果回来后不重置搜索、页签、收藏或当前选择。
- `BatchTextStyleEditor.tsx` 和 `BatchStepScripts.tsx` 删除各自的字体 fetch/state/刷新实现，统一交给选择器；`components/system-fonts.ts` 继续作为服务端扫描结果与 `queryLocalFonts()` 的唯一合并入口。
- 不改变 `/api/system-fonts` 返回格式和 `lib/media-core/system-fonts.ts` 的扫描/缓存规则。刷新字体仍只刷新目录，不影响收藏顺序。

#### 4. 一次覆盖所有正式入口

- `components/batch-production/BatchTextStyleEditor.tsx`：覆盖截图中的单条字幕样式，以及复用该组件的批量封面主/副标题精调；增加可选 `portalRoot` 并原样传给共享选择器。
- `components/batch-production/BatchCoverEditorDrawer.tsx`：在 dialog 内提供 overlay host，并把该 host 传给两个 `BatchTextStyleEditor`。
- `components/batch-production/BatchStepScripts.tsx`：覆盖批次默认字幕、封面主标题和封面副标题。
- `components/final-edit/FinalEditInspector.tsx` 的 `StyleEditor`：覆盖单条精准混剪字幕/文字样式。
- `components/mixcut/CoverEditorDrawer.tsx`：覆盖单条精准混剪封面共享字体。
- 所有调用点在 family 变化时都清除旧的 `fontPostscriptName`，避免 family 已换但仍残留上一字体的 PostScript 身份；除此之外保留各入口现有的即时预览、提交、撤销和冻结语义。

#### 5. 可访问性与性能

- 该组件采用 **dialog + 普通按钮列表**，不冒充原生 combobox/listbox：触发器使用 `aria-haspopup="dialog"`、`aria-expanded`、`aria-controls`；浮层为 `role="dialog"`，内部搜索框、`ul/li` 列表、字体选择按钮和星标 toggle button 都是合法的独立可聚焦元素。缺失字体的选择按钮保持在焦点顺序中并标记 `aria-disabled="true"`，事件处理器拦截其激活；星标按钮保持可用。这样不会出现 listbox option 内嵌另一个按钮的非法 ARIA 结构，也不会让全是缺失字体的收藏页成为键盘死区。
- 打开后搜索框自动聚焦；搜索框按 ArrowDown 进入第一条字体选择按钮。选择按钮/星标按钮用 ArrowUp/ArrowDown 移到相邻行的同类按钮，ArrowLeft/ArrowRight 在当前行的选择与星标之间切换，Home/End 到首/末结果，Enter/Space 沿用按钮本身动作。Esc、Tab 和点击外部的关闭/焦点规则按上文执行。嵌套在封面抽屉时，overlay host 内的全部控件必须进入抽屉焦点陷阱集合。
- 字体列表较大时不一次渲染无限行：收藏始终完整显示，其余结果按固定批次渐进追加（每批固定 80 项，滚到底自动加载下一批）。键盘走到当前批次最后一行再按 ArrowDown 时，先同步追加下一批再移动焦点；End 会加载完整结果并聚焦末项。搜索词或页签变化时重置为 80 项、清除活动行并把焦点留在搜索框。当前选中项即使尚未加载也由触发器表达，不强制一次渲染到其排序位置。不能为了性能只截断结果而不给鼠标和键盘继续加载能力。
- 字形样本使用经过引号转义的单个 family 加产品默认 sans-serif fallback；family 名标签仍用界面字体保证可读。列表行固定高度，字体切换不得造成滚动位置大幅跳动。
