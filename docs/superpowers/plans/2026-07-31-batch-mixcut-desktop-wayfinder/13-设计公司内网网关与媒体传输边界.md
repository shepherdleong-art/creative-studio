## Question

如何把仅公司内网可用的 `LiteLLM → 公司模型中转站 → 腾讯云模型` 链路作为可选供应商运行环境，由一键启动统一管理但不阻塞 Creative Studio 与外部供应商，并把当前 Cloudflare 全应用端口隧道替换为安全、稳定、可过期的媒体传输 Adapter？

## Dependencies

- 被 [确定桌面应用与本地服务的边界](./03-确定桌面应用与本地服务的边界.md) 阻塞。
- 被 [设计可恢复任务调度与自动资源控制](./05-设计可恢复任务调度与自动资源控制.md) 阻塞。
- 被 [设计兼容迁移与桌面打包](./10-设计兼容迁移与桌面打包.md) 阻塞。

## Confirmed constraints

- 公司供应商只能在公司内网使用，`LiteLLM` 是公司模型分发协议的必要本地桥接，不能移除。
- 外部供应商继续直连，不经过公司 `LiteLLM` 或媒体隧道。
- 一键启动负责启动和回收 Creative Studio、`LiteLLM` 与当前媒体隧道，用户不需要分别打开多个命令窗口。
- 公司链路启动失败时，只把公司供应商标为不可用；Creative Studio 仍应打开，外部供应商和不依赖公司链路的本地功能继续工作。
- 当前 Cloudflare 只作为开发期媒体传输实现，不作为长期产品基础设施；未来腾讯云方案必须位于可替换 Adapter 后面。
- 批量调度只依赖统一供应商能力与健康状态，不理解 `LiteLLM`、Cloudflare 或腾讯云的部署细节。

## Evidence from current `mixcut01`

- 当前 Windows 启动脚本已经尝试统一启动 `LiteLLM`、Cloudflare／Pinggy 和 Creative Studio，但 sidecar 失败会让整个启动过程退出，与已确认的故障隔离要求不一致。
- 公司图片和视频生成已经分别具有 gateway adapter；现有混剪视觉分析仍通过脚本供应商 adapter 发送抽帧结果，TTS 仍是独立供应商层。
- 当前 Cloudflare 指向完整 Next 服务端口，暴露面不只包含任务所需媒体读取；它只适合作为内部开发桥，不能直接作为未来正式方案。
- 当前媒体输入方式并不完全一致：部分路径要求公网可访问 URL，部分路径仍可能退回 data URL；需要按公司网关的真实协议统一。
- 当前新增 `video_providers` 表重建逻辑需要纳入迁移前备份、版本化迁移和旧库回归，不能只用启动时临时改表作为批量上线前提。

## Information still needed

- 公司允许的腾讯云媒体传输方式：COS 临时对象、预签名 URL、专用上传接口或其他方案。
- 临时媒体的最大尺寸、有效期、下载次数、访问白名单、删除时限与审计要求。
- 公司中转站对图片、视频、抽帧和 data URL 的真实协议限制。
- `LiteLLM` 版本与配置由项目固定携带，还是由公司统一维护并让启动器检查。
- 腾讯云替换 Cloudflare 后，是否仍要求从公司内网发起，以及失败时可展示的可诊断健康信息。

## Exit criteria

- 明确 Company Provider Runtime、Media Transport Adapter 和供应商健康状态的接口与责任边界。
- 给出“不在公司内网”“LiteLLM 未启动”“媒体上传失败”“公司中转站不可用”四类故障的降级行为。
- 设计只暴露任务所需临时媒体、带过期授权且可清理的腾讯云方案；不再把完整工作台端口暴露到公网。
- 为一键启停、公司链路故障隔离、外部供应商旁路、媒体清理和脱敏日志建立可自动验证的合同。
- 把相关数据库变更纳入迁移备份与旧数据库回归门禁。
