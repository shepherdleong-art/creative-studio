# 项目脚本同步与批次快照设计

- 决定日期：2026-07-31
- 决定性质：脚本身份、同步、版本和快照设计，不代表数据库或生产代码已经实现
- 对应票据：[打通项目脚本同步与批次快照](../06-打通模块4脚本同步与批次快照.md)
- 上游依据：[批量生产数据模型](./02-批量生产数据模型.md)

## 给非技术人员的结论

用户不需要在第 3 步与智能混剪之间复制粘贴文案。第 3 步保存过的项目脚本，会连同封面主标题、副标题和原分镜组自动出现在智能混剪中。

批次开始前，系统可以帮助用户保持最新，但不能抢走用户的修改：

- 用户没有在批次里改过这份脚本时，第 3 步的新版本自动更新进尚未开始的批次。
- 用户已经在批次里改过时，只提示“项目脚本有新版”，由用户决定保留批次改写还是换成新版。
- 批次一旦开始，当时使用的正文、标题、来源版本、分镜组和生成份数全部固定；第 3 步后来再改也不会影响它。

同一份脚本要求生成多条成片时，每条成片沿用同样的正文和封面标题，只使用不同的封面底图。第 4 步成功视频始终保留原分镜组来源，不会因为进入批量模式就被自动串到其他分镜组。

## 已确认的十二个场景

本票使用一个不接数据库、不读取真实视频的终端逻辑原型逐步验证，用户确认以下行为符合预期：

1. 第 3 步保存脚本 A 后，A 自动出现在智能混剪。
2. 第 3 步再保存脚本 B 后，A、B 可以同时作为批量候选。
3. 同一个来源保存结果重复到达时，只保留一次，不按标题或正文猜测是否重复。
4. 打开分镜组 A 的单条精准混剪时，只看到 A 的脚本与第 4 步视频。
5. 批量生产可以选择 A 生成两份、B 生成一份，预期得到三张成片卡片。
6. 批次尚未开始且 A 没有被局部修改时，A 自动跟随第 3 步最新版。
7. 用户可以只在当前批次内改写 B，默认不反写第 3 步。
8. B 被局部改写后第 3 步又保存新版时，系统提示冲突而不覆盖。
9. 用户可以明确选择保留批次内的 B 改写。
10. 开始生产时，A、B 的实际正文、主副标题、来源版本和生成份数形成快照。
11. 运行中第 3 步继续更新 A，新批次可以看到新版，当前批次仍使用旧快照。
12. A 的两条成片标题相同但封面底图不同；第 4 步视频仍按原分镜组关联。

原型已经完成验证并按抛弃式原型约定删除，本文件保留其决定。

## 1. 现有能力不是从零开始

当前正式单条混剪已经具备三段可复用能力：

- `lib/final-edit/mixcut-context.ts` 会读取项目中有效的 V2/V3 脚本草稿，按分镜组提供给智能混剪，并从有序脚本段落重新组成口播正文。
- `lib/final-edit/mixcut-script.ts` 已能把来源脚本、用户改写后的正文、封面主副标题和同步状态整理为任务脚本快照。
- `lib/final-edit/workspace.ts` 在开始创建时保存脚本和标题快照，恢复任务时使用已保存快照，不重新读取后来变化的上游脚本。

第 4 步视频也已经通过 `projectId + shotSetId` 查询和校验，正式单条混剪不会看到其他项目或分镜组的视频。

因此批量生产应复用现有解析、校验和快照语义，而不是再造一套“批量脚本文本”格式。真正缺少的是项目脚本的稳定身份、版本关系、多脚本选择以及批次级冻结。

## 2. 项目脚本与项目脚本版本

项目脚本是稳定身份，项目脚本版本是某次明确保存的内容。两者不能混为一个对象。

一份项目脚本版本至少固定：

- 所属项目脚本和项目。
- 来源类型与稳定来源身份。
- 来源分镜组。
- 正文或结构化段落。
- 普通标题、封面主标题和封面副标题。
- 保存时间与版本顺序。

新生成的一份独立脚本默认建立新的项目脚本；只有用户执行“保存为这份脚本的新版本”或系统掌握明确的版本关系时，才追加到同一个项目脚本。不能因为两份脚本文字、标题或来源分镜组相似就擅自合并。

## 3. 稳定去重规则

自动同步使用来源身份去重，而不是内容猜测：

- 第 3 步一次成功保存拥有一个稳定来源草稿 ID。
- 同一项目内，同一来源类型和来源草稿 ID 重复到达时，返回已经建立的项目脚本版本，不再新增。
- 内容完全相同但来源身份不同的两份脚本继续保留，因为用户可能有意生成或保存了两份。
- 用户需要同一脚本生成多条差异成片时，应设置生成份数，不应复制出多份相同项目脚本。

现有 `script_drafts.id` 可以作为历史草稿的稳定来源身份。兼容迁移时，每份可用历史草稿先一对一建立项目脚本和首个版本；没有明确关系的历史草稿不根据标题或正文强行归并。

## 4. 两个模式的范围不同

### 单条精准混剪

- 继续以当前 `projectId + shotSetId` 为硬隔离范围。
- 默认选择当前分镜组最新的有效项目脚本版本。
- 只查询当前分镜组的第 4 步成功视频。
- 不因为新增项目级脚本目录或素材库而扩大既有查询范围。

### 批量生产

- 可以从同一项目选择多份项目脚本，包括来源于不同分镜组的脚本。
- 每份批次脚本分别设置生成份数，份数总和决定成片计划数量。
- 外部粘贴文案默认只属于当前批次；只有用户明确选择“保存为项目脚本”才进入项目脚本目录。
- 批量选择器显示脚本名称、当前版本、来源分镜组和生成份数，不要求用户复制正文。

## 5. 开跑前的安全同步

批次脚本在开始生产前有三种用户可理解的状态：

| 状态 | 含义 | 上游出现新版时怎么处理 |
|---|---|---|
| 跟随项目脚本 | 用户尚未在批次内改写 | 自动换成最新版，并清楚显示版本变化 |
| 批次内已改写 | 用户改过正文或标题 | 保留用户改写并提示有新版，不自动覆盖 |
| 已处理更新 | 用户已选择保留改写或采用新版 | 按用户选择继续，直到再次出现新版本 |

批次内改写默认只影响当前批次。若用户希望反写项目脚本，必须使用明确的“保存为项目脚本新版本”动作；不能把输入框自动保存误当成上游更新。

## 6. 开跑时形成脚本快照

用户第一次点击开始生产时，由批次生产 Module 一次性固定：

- 来源是项目脚本还是批次外部文案。
- 来源项目脚本与项目脚本版本；外部文案则保存批次内来源身份。
- 来源分镜组。
- 实际采用的正文与结构化段落。
- 普通标题、封面主标题和封面副标题。
- 生成份数。

每份脚本快照按生成份数建立稳定的成片计划。例如 A 两份、B 一份，始终是三张成片卡片；失败重试不会变成第四张。

已经开始的批次只读取自己的脚本快照。项目脚本更新、归档甚至从新批次选择器隐藏，都不能破坏历史批次；用户若想采用新版整体重跑，应形成新的批次版本。

## 7. 标题与封面底图

- 标题与正文一起自动同步并一起进入脚本快照。
- 一份脚本快照生成的所有成片使用相同的普通标题、封面主标题和封面副标题。
- 每张成片计划拥有独立封面安排，所以可以为同一标题分配不同底图。
- 底图差异、素材复用次数和成片差异度由后续 [定义联合分配器与差异性规则](../08-定义联合分配器与差异性规则.md) 决定；本票只固定“标题相同、底图按成片计划独立”的关系。

## 8. 第 4 步视频的分镜组关系

每个第 4 步成功视频继续保留自己的项目与分镜组来源：

- 单条精准混剪只看到当前分镜组的视频，这是硬隔离。
- 批量模式可以自动显示每份脚本同分镜组的相关第 4 步视频，帮助用户选择素材。
- “相关”不等于“已经加入批次”；批次实际只能使用用户明确加入批次素材池的项目素材。
- 项目素材即使被明确用于更广范围的批次，也继续保留原分镜组来源，不修改、不伪造新的关联。
- 不根据脚本标题、视频文件名或创建时间把其他分镜组的视频自动串过来。

这既保留了第 4 步的来源可追溯性，也允许批量生产在用户明确选择后使用项目素材库里的实拍或复用素材。

## 9. Module、Interface、Seam 与 Adapter

新增一个深 `ProjectScriptCatalog` Module，把项目脚本身份、版本、去重和有效性判断集中在一起。它的 Interface 只需要表达：

- 记录一次已经明确保存的项目脚本来源，并返回稳定项目脚本与版本。
- 列出某个项目可用于单条或批量模式的项目脚本。
- 读取指定版本，或读取当前版本。

第 3 步保存与第 4、5 步读取之间是这个 Module 的 Seam。现有 `script_drafts` 由兼容 Adapter 映射为项目脚本来源；未来新的保存流程直接记录稳定身份与版本。版本归并、去重、V2/V3 解析和无效草稿过滤都藏在 Module 的 Implementation 内，不能继续散落在页面、API route 和批次逻辑中。

批次内的跟随、冲突提示和冻结属于 `BatchProduction` Module。它通过 `ProjectScriptCatalog` 的 Interface 读取版本，但批次开始后只读取自己的脚本快照。外部文案 Adapter 只创建批次脚本；除非用户明确保存，它不会借同步 Seam 写入项目脚本目录。

## 10. 兼容迁移方向

正式实现时遵守以下顺序，具体表和迁移 SQL 仍由兼容迁移票决定：

1. 保留现有 `script_drafts` 和单条混剪读取路径，先建立可验证的项目脚本兼容视图或记录。
2. 以每个有效 `script_drafts.id` 建立稳定来源映射，不修改原草稿，不按内容合并。
3. 新保存流程开始写入项目脚本版本关系；旧脚本仍能通过兼容 Adapter 使用。
4. 批量模式从 `ProjectScriptCatalog` 选择多份脚本，并在批次版本中保存脚本快照。
5. 单条模式迁移到同一 Interface 前后，必须证明脚本列表、标题快照、分镜组隔离和历史恢复行为没有改变。
6. 数据库变更前执行既定的备份、验证与失败停止流程。

## 必须通过的实现验收

1. 同一第 3 步来源重复同步十次，只产生一个项目脚本版本。
2. 相同正文来自两个不同来源时，不被错误合并。
3. 一个项目的脚本永远不会出现在另一个项目。
4. 单条精准混剪只显示当前分镜组的有效脚本和第 4 步视频。
5. 批量模式可以同时选择不同分镜组的多份项目脚本。
6. A 生成两份、B 生成一份时，只建立三张成片卡片。
7. 尚未改写的批次脚本自动跟随项目脚本新版本。
8. 已改写的批次脚本遇到上游新版时只提示，不覆盖正文或标题。
9. 批次内改写不会自动反写项目脚本。
10. 批次开始后，上游脚本继续更新不改变脚本快照和成片计划。
11. 正文、普通标题、封面主标题和副标题来自同一个实际采用版本并一起冻结。
12. 同一脚本的多条成片标题相同，每条保留独立封面底图安排。
13. 第 4 步视频只自动显示给同分镜组脚本，批次未明确选择的素材不能投入生产。
14. 项目脚本归档后，新批次不再默认显示，历史批次仍可读取自己的快照。
15. 旧 V2/V3 草稿在兼容迁移前后仍能进入单条混剪，且恢复中的任务不读取上游新版本。

## 本票明确不决定的内容

- 不决定 SQLite 表名、字段名、索引和迁移 SQL。
- 不决定第 3 步未来的脚本历史管理界面。
- 不决定联合素材分配、底图差异和素材复用阈值。
- 不决定批量工作区的最终视觉布局。
- 不代表多脚本批量生产已经写入正式业务代码。
