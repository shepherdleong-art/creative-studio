## 给非技术人员的结论

这次不应把现有项目“搬进 Electron 重写一遍”。风险最低的办法是增加一层很薄的桌面外壳：

1. **Electron 只负责桌面窗口、选择本机文件、单实例和退出。**
2. **现有 Next.js、SQLite、任务队列和 FFmpeg 继续运行在独立的私有 Node 服务里。**
3. **第一版 Electron 沿用现有数据根，不同时搬动旧项目和素材。**
4. **第一张批量业务表建立之前，必须先补上数据库备份、版本化迁移、完整性验证和失败停止。**
5. **macOS 和 Windows 安装包必须分别在目标系统、目标 CPU 架构上构建和真机验收；本机能构建不等于用户机器能安装和渲染。**

这种结构可以保留已经验证过的业务与媒体内核，同时避免 `better-sqlite3`、`sharp` 直接改为 Electron ABI 后带来的大范围原生模块重编译。Electron 官方明确说明，普通 Node 与 Electron 的原生模块 ABI 不同，直接把原生模块加载进 Electron 时通常必须针对 Electron 重新编译；因此本项目第一阶段继续让它们由配套 Node 22 运行时加载更稳妥。[Electron：Native Node Modules](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules/)

## 2. 推荐的薄 Electron 进程边界

```text
Electron Main（Runtime Host）
├── 单实例锁、窗口、菜单、原生文件对话框
├── 启动并监管“私有 Node + standalone server.js”
├── 只允许固定的本机服务来源进入 BrowserWindow
└── 退出时请求服务保存状态、关闭数据库并停止子进程

Electron Renderer（现有 React / Next UI）
├── 不启用 Node
├── 不直接得到任意本机路径读取能力
└── 只通过窄 preload API 发起“选择素材、打开目录”等桌面动作

独立 Node 服务（现有业务内核）
├── SQLite、项目数据和持久任务
├── 素材校验、代理、LUT、TTS、字幕
└── FFmpeg / ffprobe 子进程
```

Electron 官方也提供 `utilityProcess.fork()`，可创建带 Node 和消息端口的受管子进程，并可获得 PID、stdout、stderr、退出事件和 `kill()`；但它使用 Electron 所带的 Node 环境。[Electron：utilityProcess](https://www.electronjs.org/docs/latest/api/utility-process) 结合前述 Electron ABI 约束，本项目第一阶段**不建议**把现有 server 直接改为 utility process。推荐让 Electron Main 用不经过 shell 的进程启动 API 执行仓库已经打包的私有 Node，继续保持现有 Node 22 原生模块边界；Node 官方也支持给子进程指定明确的可执行文件、环境变量和工作目录。[Node.js：Child process](https://nodejs.org/api/child_process.html)

### 2.1 启动顺序

1. Electron Main 在创建窗口前申请单实例锁；第二次启动只唤醒已有窗口。`app.requestSingleInstanceLock()` 的返回值就是 Electron 官方提供的主实例判定机制。[Electron：app.requestSingleInstanceLock](https://www.electronjs.org/docs/latest/api/app#apprequestsingleinstancelockadditionaldata)
2. 确定安装资源目录和**既有** `CREATIVE_STUDIO_DATA_ROOT`，建立本次运行的随机秘密和本机端口。
3. 启动私有 Node 服务，只绑定 `127.0.0.1`，捕获 stdout、stderr、PID 和退出状态。
4. Node 先完成数据库备份／迁移门禁，再由健康接口报告 `ready`、`compatibility-only` 或 `migration-failed`。
5. 只有健康接口可用后才显示正式工作区；启动期间显示本地启动页，不能把空白窗口或连接错误交给用户。

端口随机化不能替代鉴权。桌面服务应接收 Electron Main 生成的每次运行秘密，BrowserWindow 使用的独立 Session 为目标本机来源自动附加秘密；服务端同时校验秘密、Host 和允许的 Origin。渲染页面和普通浏览器脚本都不应得到秘密明文。现有 `POST /api/shutdown` 在 Electron 版中也必须受桌面鉴权或改为只走受管进程通道，不能继续作为任意本机网页可调用的退出开关。这一段是结合 Electron 安全原则作出的工程设计，不是 Electron 对本项目接口的现成实现。

### 2.2 文件和文件夹选择

文件选择应由 Main 进程调用 `dialog.showOpenDialog()`：手机／相机素材使用 `openFile + multiSelections`，整文件夹导入使用 `openDirectory`。Electron 官方说明这三个属性分别代表文件、目录和多选；Windows 与 Linux 不能在同一个对话框中同时兼做文件和目录选择，因此产品上应保留两个明确入口。[Electron：dialog.showOpenDialog](https://www.electronjs.org/docs/latest/api/dialog#dialogshowopendialogwindow-options)

推荐的数据路径是：

1. renderer 只调用 `window.desktop.selectVideoFiles()` 或 `selectMaterialFolder()` 这样的具体能力。
2. preload 通过 `contextBridge` 暴露窄接口，不能把整个 `ipcRenderer` 交给页面；Electron 官方 IPC 指南也明确要求限制 renderer 可用的 Electron API。[Electron：IPC](https://www.electronjs.org/docs/latest/tutorial/ipc)
3. Main 校验 IPC sender，只把用户本次明确选择的路径交给本地服务登记。
4. 服务完成扩展名、真实路径、符号链接、内容指纹与项目权限校验后返回素材 ID。
5. renderer 最终只保存素材 ID、安全元数据和在线状态，不获得“读取任意绝对路径”的通用接口。

如果未来进入 Mac App Store 沙箱，Electron 对话框可以返回 security-scoped bookmarks；该能力在官方文档中明确标注为 macOS MAS 选项，因此当前 Developer ID 直发版本不能假定已经具备同一套持久授权行为。[Electron：dialog bookmarks](https://www.electronjs.org/docs/latest/api/dialog#bookmarks-array)

## 3. Electron 安全默认值与生命周期

### 3.1 BrowserWindow 必须显式固定的值

即使当前 Electron 版本已有安全默认值，工程仍应显式配置并用测试钉住：

- `nodeIntegration: false`（官方默认 false）。
- `contextIsolation: true`（官方默认 true）。
- `sandbox: true`（Electron 20 起官方默认 true）。
- `webSecurity: true`（官方默认 true）。
- 禁止 `webviewTag`、任意新窗口和非允许来源导航。
- CSP 至少限制脚本来源；所有 IPC 校验 sender；外部链接只允许明确的 `https:` allowlist。

这些默认值和风险均来自 Electron 的 [BrowserWindow 配置](https://www.electronjs.org/docs/latest/api/browser-window#new-browserwindowoptions) 与 [安全检查清单](https://www.electronjs.org/docs/latest/tutorial/security)。安全清单还要求限制导航、新窗口、`shell.openExternal`，不要把原始 Electron API 暴露给页面，并持续使用受支持的新 Electron 版本。

本项目加载的是本机 `http://127.0.0.1:<port>`，不是公网远端页面；但它仍是一个能接触用户数据的网页来源。因此必须用 URL 解析器做**完整 origin 等值比较**，不能用字符串前缀判断；Electron 官方特别指出 `startsWith()` 可能被类似域名绕过。[Electron：限制导航](https://www.electronjs.org/docs/latest/tutorial/security#13-disable-or-limit-navigation)

### 3.2 单实例与退出

- 第二实例不再启动第二个 Node、第二个数据库连接和第二套队列，只恢复并聚焦现有窗口。[Electron：single instance](https://www.electronjs.org/docs/latest/api/app#apprequestsingleinstancelockadditionaldata)
- 正常退出使用 `app.quit()` 的生命周期，不使用会跳过 `before-quit`／`will-quit` 的 `app.exit()`。[Electron：app.quit 与 app.exit](https://www.electronjs.org/docs/latest/api/app#appquit)
- `before-quit` 进入一次性关闭流程：停止领取新任务，通知 Node 持久化可恢复状态，关闭 SQLite，终止 FFmpeg 子进程树，等待有限时间后再退出。重复退出事件必须幂等。
- Windows 系统关机、重启或注销时，Electron 官方说明 `before-quit`、`will-quit` 可能不会发出，因此安全性不能依靠退出回调；任务状态必须本来就持久化，SQLite 必须能按 WAL 规则恢复。[Electron：app lifecycle](https://www.electronjs.org/docs/latest/api/app#event-window-all-closed)
- “关窗口是否继续后台生产”是产品决定，不应偷偷等同于进程退出。无论最后选择哪种体验，都必须把“关闭窗口、暂停批次、停止批次、退出应用”分成四个明确动作。

Electron 的 `userData` 默认位于每用户应用数据目录，但官方明确不建议把大文件放在这里，因为部分环境会把它备份到云端；Chromium session 缓存也可能很大。[Electron：app.getPath](https://www.electronjs.org/docs/latest/api/app#appgetpathname) 因而 `userData/sessionData` 只用于 Electron 配置和浏览器缓存，几十 GB 的原片、代理与成片仍走 Creative Studio 自己的 `CREATIVE_STUDIO_DATA_ROOT` 和已设计的项目／缓存目录。

## 4. SQLite 在线备份、迁移与回退

### 4.1 为什么不能直接复制 `workbench.db`

当前数据库使用 WAL。SQLite 官方明确说明：`-wal` 是数据库持久状态的一部分；在数据库仍打开时把主数据库与 WAL 分开，可能丢失已提交事务或损坏数据库。[SQLite：Write-Ahead Logging](https://www.sqlite.org/wal.html#the_wal_file) 因此禁止在服务运行中用普通文件复制只拷贝 `workbench.db`。

推荐使用 SQLite Online Backup API 生成一致快照。官方说明它可以增量复制在线数据库，只在短暂读取时锁住来源，完成后目标是一份一致快照；还可以用页数报告真实进度。[SQLite：Online Backup API](https://www.sqlite.org/backup.html) 当前安装的 `better-sqlite3` 已在本地实现和类型中暴露异步 `db.backup(destination, { progress })`，所以不需要为此更换数据库库，但正式实现必须补自动测试。

### 4.2 第一份批量迁移的硬门禁

在任何批量表、索引或回填 SQL 执行前，数据库启动 module 必须按以下顺序工作：

1. 打开现有数据库并启用外键，读取新的批量／应用迁移版本表。
2. 如果没有待执行的新迁移，正常启动，不重复制造备份。
3. 如果有待执行迁移，先用 Online Backup API 写入同一数据根下的临时备份文件。
4. 以只读连接打开备份，执行 `PRAGMA integrity_check` 和 `PRAGMA foreign_key_check`；前者检查底层格式、页面、索引和常见约束，后者单独检查外键，因为官方说明 `integrity_check` 不检查外键。[SQLite：PRAGMA integrity_check / foreign_key_check](https://www.sqlite.org/pragma.html#pragma_integrity_check)
5. 验证通过后原子发布为带旧版本号、目标版本号和时间的备份文件，并记录文件大小与哈希；验证失败则不迁移。
6. 每个新迁移用独立、明确版本号执行；SQL 和版本记录在同一事务中提交，不修改已经发布的旧迁移。
7. 写迁移优先使用 `BEGIN IMMEDIATE` 等价能力，尽早发现另一个写连接，而不是做到一半才遇到写锁；SQLite 官方说明 IMMEDIATE 会立即开始写事务，有其他写事务时返回 `SQLITE_BUSY`。[SQLite：Transaction](https://www.sqlite.org/lang_transaction.html)
8. 提交前再次执行结构断言、`foreign_key_check` 和必要的业务不变量检查；通过后才报告服务 ready。

新的批量迁移不得继续放进当前“捕获所有异常并当作字段已存在”的 `CORE_DB_MIGRATIONS` runner。旧 runner 保持兼容，不重写发布历史；新批量结构使用类似 `final_edit_schema_migrations` 的版本化表，并且只忽略明确判断为“已经应用”的版本，不能吞掉磁盘满、SQL 写错或约束失败。

SQLite 的 `user_version` 是应用可自由使用、SQLite 本身不解释的整数。[SQLite：PRAGMA user_version](https://www.sqlite.org/pragma.html#pragma_user_version) 本项目已经有模块迁移表，继续用可审计的迁移表比只保存一个整数更适合记录版本和时间；`user_version` 可作为快速总版本标记，但不能替代迁移历史。

### 4.3 失败和回退规则

- **事务内失败**：显式回滚本次迁移，批量功能进入 `migration-failed`，旧单条功能只在确认未依赖新表时进入 compatibility-only；不能带半张新表继续工作。
- **备份失败、磁盘不足或完整性验证失败**：一条迁移都不执行，显示可操作错误和备份位置，不自动删除旧数据。
- **应用升级后想降级**：追加列通常可以被旧代码忽略，但新任务快照不能假装能被旧版本理解。旧版本只读历史的规则要在每个 schema 版本中明确；不存在通用的“倒放 SQL”。
- **需要从备份恢复**：先完全退出 Electron、Node 和所有 FFmpeg 子进程，确认 SQLite 已关闭，再把当前数据库隔离保存后恢复经验证的快照。禁止边运行边覆盖主库，也禁止随手删除 `-wal`；SQLite 明确指出 WAL 只能由 SQLite 安全处理。[SQLite：WAL file](https://www.sqlite.org/wal.html#the_wal_file)
- **自动恢复边界**：事务失败依靠事务回滚，不自动覆盖源数据库；只有用户明确选择恢复且通过停机、备份校验和版本确认后，才执行文件级恢复。

## 5. 数据根兼容策略

第一版 Electron **不同时迁移工作台数据根**：

- macOS 继续使用已经发布的 `~/Library/Application Support/CreativeStudio`。
- Windows 升级安装继续使用旧安装器已有的 `{app}` 数据根。
- Electron 的 `userData` 只存 Electron 自己的窗口设置和 Chromium 数据，不作为工作台 DB、素材、代理或正式产物的权威目录。
- `lib/data-root.ts` 继续只认 Electron 启动 Node 时注入的 `CREATIVE_STUDIO_DATA_ROOT`；业务代码不读取 Electron 路径。

这是为避免“换桌面壳、迁数据库结构、移动大量文件”三个高风险动作同时发生。Windows 把工作台数据留在安装目录是已知技术债；若后续迁往标准本地应用数据目录，Microsoft 的 Known Folder 文档确认 `%LOCALAPPDATA%` 是每用户本地目录。[Microsoft：Known Folder IDs](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid) 该迁移应另开票，采用“停机 → 盘符／空间检查 → 复制或移动到候选目录 → 文件清单与哈希验证 → 切换根标记 → 保留旧根等待确认”的独立流程，不夹在 Electron 首次升级里。

无论数据根在哪里，原片的“链接素材”都不复制、不迁移、不删除；只迁移 Creative Studio 管理的 DB、托管素材、代理缓存、日志和正式产物。代理与缓存仍可重建，正式产物和原片不能被清理动作误删。

## 6. macOS 与 Windows 安装包约束

### 6.1 共同布局

建议把包分成两类资源：

- `app.asar`：只放 Electron Main、preload 和适合只读打包的桌面代码。
- unpacked／`resources`：Next standalone、私有 Node、`.node` 原生模块、sharp 依赖、FFmpeg 和 ffprobe。

Electron 官方说明 ASAR 是只读虚拟文件系统，不能作为子进程 `cwd`；`spawn` 也不能直接执行其中的二进制，原生模块和可执行文件通常需要 unpack。[Electron：ASAR limitations](https://www.electronjs.org/docs/latest/tutorial/asar-archives#limitations-of-the-node-api) 所以不能把 Node、FFmpeg 或 standalone 工作目录藏进 ASAR 后再依赖临时解包。

共同构建门禁：

1. 每个平台从干净依赖树执行 `npm ci` 和生产构建，不复用另一平台的 `node_modules`。
2. 私有 Node 版本、Node ABI、`better-sqlite3`、sharp、Electron、FFmpeg 和 ffprobe 的平台／架构形成一份可审计 manifest。
3. 安装包内逐项执行：Node `--version`、原生模块加载、SQLite 读写、sharp 小图、FFmpeg `-version`、真实探测和最小转码。
4. 继续断言 payload 不含真实 `data/`、`storage/`、`outputs/`、`.env*`、API Key 或开发缓存。
5. FFmpeg 项目本身只发布源代码，当前 `ffmpeg-static` 二进制来自第三方打包链；安装包必须锁定包版本、保存来源／许可证信息并核对实际 `ffmpeg -buildconf`，不能把“来自 npm”误称为 FFmpeg 官方二进制。[FFmpeg：Download](https://ffmpeg.org/download.html)

### 6.2 macOS

当前工程只承诺 Apple Silicon：Node、Electron、启动器、FFmpeg、ffprobe、`better-sqlite3` 和 sharp 都必须是 arm64；`Info.plist` 当前最低系统版本为 macOS 11。若未来支持 Intel 或 Universal，必须新增独立产物矩阵，不能把当前 arm64 DMG 改名后宣称兼容。

当前脚本只执行 `codesign --sign -` 的 ad-hoc 签名，没有 Developer ID、公证或 stapling。[`build-mac-installer.sh`](../../../../../scripts/build-mac-installer.sh#L208-L209) Apple 对站外分发的正式要求是：使用 Developer ID 签名所有可执行代码、启用 Hardened Runtime、带安全时间戳、提交 notary service，并把成功票据 staple 到交付物；Apple 还明确说 ad-hoc 或本地开发证书不能用于该公证流程。[Apple：Notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

因此正式发布流水线至少要：签嵌套 helper／Node／原生模块和主 app → 验证签名 → 生成并签 DMG → `notarytool` 提交并等待 → `stapler` → 在干净机器用 Gatekeeper 验收。Hardened Runtime 会限制代码注入和未签名库加载，所需 entitlement 必须最小化并用真实 `better-sqlite3`、sharp、FFmpeg 验证，不能先开宽泛例外。[Apple：Hardened Runtime](https://developer.apple.com/documentation/security/hardened-runtime)

### 6.3 Windows

当前安装器为 Inno Setup、最低权限用户安装、x64 compatible；构建脚本没有 Authenticode 签名步骤。[`CreativeStudio.iss`](../../../../../installer/windows/CreativeStudio.iss#L19-L21) 第一版 Electron 应继续明确只支持 Windows x64，不在未验证时承诺原生 Windows ARM64。Electron 官方说明 ARM64 需要相应 Electron 产物，并需要为 ARM64 重编原生模块和核对其 DLL／LIB。[Electron：Windows on ARM](https://www.electronjs.org/docs/latest/tutorial/windows-arm)

正式 Windows 发布需要对项目生成的 EXE 和最终安装器执行 Authenticode 签名并验证。Microsoft 说明 SignTool 可以签名、验证和加时间戳；新的签名应使用 SHA-256 和 RFC 3161 时间戳，时间戳使签名在证书过期后仍可验证。[Microsoft：SignTool](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool) [Microsoft：Authenticode timestamp](https://learn.microsoft.com/en-us/windows/win32/seccrypto/time-stamping-authenticode-signatures)

## 7. 推荐迁移顺序

| 阶段 | 只改变什么 | 必须通过后才能继续 |
|---|---|---|
| 0. 迁移安全层 | Online Backup、版本表、事务迁移、完整性检查、失败停止 | 旧库副本迁移、注入失败、磁盘不足、重复启动、备份恢复测试 |
| 1. 批量空 schema | 只追加最小批量身份／版本表，不接 UI 和 worker | 新旧数据共存；单条精准混剪完整回归 |
| 2. Electron 薄壳 | 只接窗口、单实例、文件对话框和 Node 监管；沿用旧数据根 | 当前 Web 运行方式仍可用；Electron 退出／崩溃／重启恢复通过 |
| 3. 桌面文件引用 | 原生选择登记链接素材，renderer 只收素材 ID | 外置盘、中文路径、改名重定位、任意路径越权测试 |
| 4. 批量调度 | 接持久任务、暂停／停止／恢复和真实进度 | 重启不重复收费／渲染；单条功能不退化 |
| 5. 代理、LUT、联合分配 | 接可重建缓存和批量成片版本 | 原片不修改；清缓存不删原片；快照不被上游改写 |
| 6. 双平台发布 | 签名、公证、安装／升级／卸载和真实 FFmpeg | 干净 macOS arm64 与 Windows x64 真机完整验收 |

最重要的顺序约束是：**阶段 0 必须在第一条新批量迁移之前；Electron 只在数据库安全层稳定后接入；数据根搬迁不与首次 Electron 升级合并。**
