# 联合分配器与差异性规则设计

- 决定日期：2026-07-31
- 决定性质：批量素材分配、差异性、锁定、局部重分配和可解释降级设计，不代表数据库或生产代码已经实现
- 对应票据：[定义联合分配器与差异性规则](../08-定义联合分配器与差异性规则.md)
- 上游依据：[批量生产数据模型](./02-批量生产数据模型.md)、[项目素材库与原文件引用设计](./04-项目素材库与原文件引用设计.md)、[项目脚本同步与批次快照设计](./06-项目脚本同步与批次快照设计.md)

## 给非技术人员的结论

现在的单条混剪像是先排好一条成片，再复印几份；封面和音乐可以不同，但镜头时间线仍然相同。批量生产不能这样做。

新的做法是把本批全部文案、每份文案要生成几条、用户选中的全部素材和人工决定一次交给一个“联合分配器”。它先保证画面与文案匹配、时间够用，再从合适候选里统筹错开开头、素材区间、镜头顺序、封面底图和音乐。

三条原则已经由用户确认：

1. 画面符合文案优先，不能为了看起来不同而硬塞明显不合适的素材。
2. 用户锁定或手工替换的镜头是硬决定，机器不能偷偷覆盖。
3. 素材不足时继续生成；做不到的差异必须清楚提示，不能假装结果仍然丰富。

同一文案生成多条时，标题继续使用同一个脚本快照，不添加“版本 1”“版本 2”等后缀；系统只尽量更换封面底图。

## 原型确认的场景

本票曾使用一个不接数据库、不读真实视频、不运行 FFmpeg 的抛弃式终端原型检查以下行为：

1. 两份脚本分别要求 2 条和 1 条时，先建立 3 个稳定的成片计划，再一次统筹素材。
2. 素材充足时，三条成片的开头、原素材区间、封面底图和音乐均可错开，标题仍来自各自脚本。
3. 用户锁定一条成片的开头后，后续重分配保留该镜头。
4. 用户手工替换中段后，这次人工决定自动成为锁定，直到用户明确解除。
5. 单条重分配只产生目标成片的新成片版本，其他成片计划和版本不变。
6. 用户排除某条未被锁定的素材后，整个批次只在剩余素材内重新统筹。
7. 素材只剩两条时仍完成三条成片，先换用不同区间，再提示重复开头、重复区间和较弱语义匹配。
8. 素材只剩一条时仍尽量完成，但不再承诺低相似度，并明确提示音乐与区间复用。
9. 锁定指向离线、排除或不存在的区间时，只阻塞受影响的成片，不自动解锁，也不拖垮已经可用的其他成片。
10. 相同批次快照、分配规则版本和种子重复计算时，得到相同结果，不会无缘无故随机洗牌。

原型完成回答后已删除，本文件只保留确认过的决定。

## 1. 当前工程的真实差距

现有单条精准混剪已经拥有值得复用的成熟能力：

- `audio-first-matcher.ts` 能按照真实配音句段时长、素材场景、语义分数、开头分数、复用成本和人工锁定生成一条时间线。
- 它会校验锁定区间、素材时长和语义地板，并返回素材缺口、降级原因和选材理由。
- `semantic-matrix.ts` 能建立一份脚本句段到素材场景的语义矩阵。
- `proposal.ts` 能在一条素材中寻找尚未占用的来源区间。
- `overlap.ts` 已有成片间重合检查，可作为新差异报告的输入之一。

但 `workspace.ts` 当前只调用一次 `matchAudioFirst`，再在生成多个版本的循环中把同一个 `converted.timeline` 放入每个版本；只有封面候选和背景音乐轮换。因此它是“单条时间线的多个包装”，不是多文案、多成片的联合分配。

参考项目也主要提供单条最小成本匹配和批次流程思路，不能直接解决本项目的批次快照、成片版本、用户锁定和历史隔离问题。这里只迁移能力，不复制其 Python 或 Electron 架构。

## 2. `BatchAllocator` 是独立的深 Module

批量模式新增一个纯计算的 `BatchAllocator` Module。它不读取 SQLite、不寻找文件、不调用供应商、不启动 FFmpeg，也不发布成片；它只接收已经冻结并核验的输入，返回可持久化的成片计划和差异报告。

它的外部 Interface 只有两类能力：

```text
allocateBatch(frozenBatchInput) -> allocationResult
reallocateOutput(frozenBatchInput, currentAllocation, targetOutputPlanId, reason) -> allocationResult
```

Interface 的业务合同包括：

- 相同输入快照、分配规则版本和种子产生相同结果。
- 全批分配一次看到所有成片请求，不能把单条匹配器独立调用 N 次后拼起来。
- 单条重分配把其他成片视为固定占用，只能生成目标成片的新版本。
- 无效锁定不能被忽略；它阻塞受影响成片并返回可操作说明。
- 结果返回事实和原因，不直接写数据库或修改运行中的批次。

这种形状让复杂分配、降级和诊断集中在一个 Implementation 内。页面、调度器、数据库 Module 和详细编辑器都不需要各自理解差异算法。

## 3. 联合分配器的冻结输入

一次全批分配至少接收以下事实：

### 批次身份

- 项目、批次和批次版本的稳定身份。
- 分配规则版本、明确种子和输入摘要。
- 目标画幅、帧率、默认音乐策略等已冻结设置。

### 全部成片请求

- 启用的脚本快照，而不是可继续变化的上游脚本。
- 每份脚本的生成份数和由此形成的成片计划身份。
- 正文句段、标题、结构化封面标题、真实配音或预计时长。
- 匹配表示与原脚本句段的稳定映射，继续兼容 `sourceSegmentId`。

### 批次素材池

- 用户明确选择的素材身份和已核验来源状态。
- 批次采用的素材分析版本、场景、可用区间、质量问题和封面候选。
- 原片内容指纹、时长和批次冻结的 LUT 选择；代理文件不是分配身份。
- 被排除的素材和不可使用区间。

### 评分与人工决定

- 每个句段对每个素材场景的语义分数和开头适合度。
- 用户锁定的成片、句段、素材身份和精确来源区间。
- 用户手工替换、裁剪或明确保留的片段；后续自动分配把它们视为锁定。
- 当前批次已有的其他成片计划，供单条重分配时计算占用和差异。

输入中不能出现任意未核验文件路径，也不能临时读取“上游最新版”。素材或脚本整体变化必须先形成新的批次版本。

## 4. 输出不是一组时间线数组

一次分配运行返回：

- 每个成片计划的一条候选成片版本，包含脚本绑定、镜头顺序、原素材区间、时间线区间、封面底图和音乐选择。
- 每个镜头是否由用户锁定、采用哪个分析场景、语义等级以及为什么选择它。
- 批次级素材使用次数和差异报告。
- 哪些差异是正常达成、哪些是被迫复用、哪些是语义降级。
- 阻塞、警告和下一步处理建议。
- 分配规则版本、种子、输入摘要和结果摘要，供重启与历史复核。

分配结果本身不是正式产物，也不是渲染任务。持久化 Module 将它登记为成片计划或成片版本后，调度器才按计划建立配音、字幕、预览和渲染任务。

## 5. 决策优先级

联合分配遵守明确的四级优先顺序。

### 第一层：绝不能违反的硬约束

- 项目和批次版本归属正确。
- 脚本、素材和分析版本确实属于冻结输入。
- 素材来源已核验，场景和裁剪区间没有越界。
- 片段满足最短时长、目标时间覆盖和时间线合法性。
- 排除项不可用，用户锁定与手工替换必须保留。
- 同一条时间线不能产生非法重叠或无法解释的空白。

锁定与排除发生冲突时，系统不能猜用户更想要哪个。受影响成片进入“需要处理”，并提供“解除锁定”或“取消排除”的明确入口；其他成片继续。

### 第二层：内容正确

- 句段与画面语义匹配。
- 第一镜头适合作为开头。
- 素材质量可接受，并符合句段真实时长。

现有单条匹配器的语义地板、真实 TTS 句段拆分和降级理由应继续复用。系统不能为了降低统计相似度而选取明显错误的画面。

### 第三层：批次差异与使用平衡

在内容正确的候选中依次争取：

1. 不同开头；开头对用户感知差异最强。
2. 同一素材采用不同且尽量不重叠的来源区间。
3. 不同素材组合和镜头顺序。
4. 全批次素材使用次数不过度集中。
5. 不同封面底图；同一脚本的标题保持相同。
6. 素材和曲目充足时选择不同背景音乐。

用户明确锁定造成的重复仍被记录，但不被算法改掉。

### 第四层：稳定复现

分数完全相同时使用稳定身份、规则版本和种子裁决。普通重试不能随机重排已经满意的成片；用户明确点击“换一种分配”时，才以新种子产生新的分配运行和成片版本。

## 6. 全批次分配流程

`BatchAllocator` 的 Implementation 可以演进，但必须保持以下行为阶段：

1. 展开请求：把多份脚本和生成份数展开为稳定的成片计划与句段请求。
2. 建立候选：只从采用的素材分析版本中生成满足时长和来源约束的候选区间。
3. 校验并预占锁定：锁定候选先进入计划与全局使用账本；冲突返回到对应成片。
4. 全局主分配：把所有未锁句段一起纳入最小成本分配，而不是逐条贪心复制；语义、开头、区间占用和素材使用次数共同形成成本。
5. 序列修复：在不穿越语义与时长约束的前提下，检查相邻重复、相同开头、相同顺序和完全相同时间线，并尝试交换可接受候选。
6. 封面与音乐分配：使用同一份全局使用账本错开底图和曲目，标题不参与差异化改写。
7. 生成报告：重新按最终结果计算所有事实指标，不能把优化过程中的估计值冒充结果。

V1 可以复用现有最小成本流思路，将全批句段展开为一张更大的候选图，并用递增容量成本表达素材和区间复用。序列差异可在主分配后通过确定性的有限修复完成。具体求解器属于 Implementation，将来可替换，但 Interface 和诊断合同保持不变。

单条精准混剪继续使用现有 Interface，不因批量 Module 上线而改变用户行为。可复用的语义地板、候选合法性和选择理由应下沉为共享 Implementation，不能复制出两套逐渐漂移的规则。

## 7. 差异报告按维度说明，不只给一个神秘分数

每两条可用成片至少比较：

- 时间线是否完全相同。
- 开头是否使用相同素材与相同来源区间。
- 相同时间位置使用同一区间的比例。
- 素材集合重合程度。
- 镜头顺序相似程度。
- 同一素材来源区间的实际重叠程度。
- 封面底图是否相同。
- 背景音乐是否相同。

批次整体还报告：

- 每份素材的使用次数和集中程度。
- 被迫重复的区间、开头、封面和音乐数量。
- 低于首选语义范围但仍被采用的句段。
- 因锁定造成、因素材不足造成和算法本可避免的重复，三者必须分开。

主界面只显示“分配健康”“已完成，有提醒”“部分成片需要处理”等简单状态和受影响条数。具体成片对、句段、区间、选择原因和建议放进任务详情。

不锁死一个“低于 30% 就算合格”的单一阈值。后续真实验收已经确认：素材构成和成片数量由用户决定，差异按开头、来源区间、顺序、封面和音乐等事实解释；提醒不阻止导出。内部权重变化仍属于规则版本，不能改写旧报告。

## 8. 素材不足的可解释降级顺序

“继续生产”不等于跳过所有质量约束。系统按以下顺序逐步放宽差异要求：

1. 使用语义合适且从未使用的素材区间。
2. 复用同一素材，但换用未使用且不重叠的区间。
3. 复用已经出现过的素材，在其他有效区间取材并改变顺序。
4. 在时长仍合法时允许区间部分重叠、开头重复或音乐重复。
5. 没有首选语义候选时，采用仍可解释的最佳降级候选并标记语义降级。
6. 只有在完全没有可用媒体、锁定冲突未解决或时间线无法合法覆盖时，才阻塞受影响的单条成片。

降级不得跨项目借素材、读取未选择素材、使用内容已变化的文件、静默解除锁定、改写标题或用代理文件替代正式原片。

用户看到的处理建议按事实给出：增加素材、解除冲突锁定、取消排除、手工替换、接受当前相似风险或停止受影响成片。批次不会因为一条失败而回滚已经完成的其他成片。

## 9. 锁定、手工替换和排除

- 片段锁定绑定成片计划、脚本句段、素材身份、内容指纹和精确来源区间。
- 手工替换或手工裁剪完成后默认形成片段锁定，避免下一次自动分配把用户劳动覆盖掉。
- 用户可以明确解除锁定；仅仅点击重试、恢复应用或重新进入页面不解除。
- 排除作用于当前批次版本，不归档项目素材，也不影响其他批次。
- 已锁素材随后被排除、离线或内容变化时形成锁定冲突，系统不能擅自选边。
- 锁定造成的相似度偏高如实记录，但不把它描述为算法失败。

详细编辑器产生的替换、裁剪和锁定仍只作用于目标成片版本。重新分配不能把其他成片当前时间线覆盖成相同副本。

## 10. 单条重分配

单条重分配接收同一批次快照、当前全批分配、目标成片计划和用户原因：

- 其他成片计划和当前成片版本全部固定，不重新计算、不增加版本。
- 其他成片占用的素材区间、开头、封面和音乐进入目标成片的差异账本。
- 目标成片的锁定和人工替换继续是硬约束。
- 未锁镜头尽量避开目标成片旧版本和其他成片，但仍以语义正确为先。
- 成功时形成同一成片计划的新成片版本；失败时保留旧版本并返回阻塞原因。
- 结果说明具体改了哪些镜头、为什么改；如果没有更合适组合，也明确说明“没有找到更合适的新组合”。

单条重分配不是新的生成份数，也不能新建一张成片卡片。

## 11. Seam 与 Adapter

### 冻结输入组装 Seam

批次工作区 Module 从数据库读取批次版本、脚本快照、素材分析版本、LUT、锁定和排除，并组装 `BatchAllocator` 输入。生产使用 SQLite Adapter，逻辑验证使用内存 Adapter。文件路径和数据库行都停在这个 Seam 外。

### 语义评分 Seam

语义矩阵仍通过现有供应商评分与确定性降级 Adapter 取得。评分结果进入冻结输入后，`BatchAllocator` 不再调用网络。真实供应商、缓存结果和测试矩阵是这个 Seam 的不同 Adapter。

### 成片计划持久化 Seam

分配结果通过成片计划仓储 Interface 保存为分配运行、成片计划、成片版本和差异报告。SQLite Adapter 负责事务与历史，`BatchAllocator` 不知道表名。

### 调度 Seam

分配完成后，批量生产编排 Module 才把可运行的成片版本转换为生产任务。调度器只消费计划和阻塞状态，不重新实现分配规则。

差异策略、稳定排序和降级阶梯暂时只有一套正式规则，因此属于 `BatchAllocator` 的内部 Implementation，不为了“以后可能变化”提前建立虚假 Adapter。

## 12. 实现验收

1. 2 份脚本分别要求 2 条和 1 条时，结果恰好建立 3 个成片计划，不因任务重试增加数量。
2. 相同批次快照、规则版本和种子连续运行两次，计划与报告摘要完全一致。
3. 素材充足时，不出现完全相同时间线，开头、区间、顺序、封面和音乐达到校准后的差异目标。
4. 同一脚本的所有成片版本保留相同标题快照，不自动添加版本后缀。
5. 全批次素材使用次数不过度集中；必要集中能在报告中追溯原因。
6. 用户锁定和手工替换在全批重算、单条重分配、暂停恢复和应用重启后保持不变。
7. 排除素材不会进入新计划，也不会归档或删除项目素材。
8. 锁定与排除、离线或内容变化冲突时，只有受影响成片阻塞，系统不偷偷解锁。
9. 素材不足时优先换区间，然后才允许重叠、重复开头或较弱语义匹配，并逐项报告。
10. 只剩一条可用素材时仍尽量生成；报告不承诺低相似，也不伪装成健康。
11. 完全没有合法媒体或时长无法覆盖时，只阻塞受影响成片，不输出黑帧假成片。
12. 单条重分配只增加目标成片版本，其他成片的身份、版本和时间线摘要不变。
13. 单条重分配返回具体变更和理由，没有替代方案时保持旧版本并说明原因。
14. 主界面只显示简单状态和数量，所有成片对、句段、区间、分数与降级理由进入任务详情。
15. 单条精准混剪原有测试继续通过，批量 Module 不改变其 `projectId + shotSetId` 隔离。
16. 对多组用户自选数量验证候选规模、运行时、内存占用和差异事实；任何测试数字都不成为产品上限或统一相似度及格线。

## 本票明确不决定的内容

- 不决定 SQLite 表名、字段名、迁移 SQL 或 HTTP route。
- 不把原型中的语义分数、惩罚权重或阈值当作生产默认值。
- 不承诺素材不足时仍能达到低相似度，只承诺继续尝试并清楚提示。
- 不决定批量工作区卡片和任务详情的最终视觉布局。
- 不决定固定素材数、脚本数、成片数或统一相似度及格线；产品只记录事实并提示用户选择。
- 不代表联合分配器、成片计划持久化或批量渲染已经实现。
