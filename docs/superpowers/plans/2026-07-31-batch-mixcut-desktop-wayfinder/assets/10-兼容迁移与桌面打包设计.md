## 给非技术人员的结论

这次升级采用“先不搬家，只安全增加新房间”的办法。

- 旧项目、旧素材、旧单条混剪和已导出结果继续留在原位。
- 第一张批量业务表建立前，先自动生成一份经过检查的数据库备份。
- 新结构只做追加，不删除、改名或覆盖旧结构。
- Electron 是新的桌面窗口，不是第二套后端；现有 Node、SQLite、任务和 FFmpeg 内核继续工作。
- 桌面安装包不在当前抢先做；先让批量核心与供应商运行环境稳定，再做 Apple 芯片 macOS 与普通 64 位 Windows 内部测试包。
- 公司供应商所需 LiteLLM 和媒体传输可由同一入口统一管理，但失败只禁用公司供应商，不影响软件与外部供应商。
- 首版手动安装升级，不做自动更新。
- 卸载默认只删程序，项目和成片继续保留；彻底删除数据必须单独二次确认。
- 正式签名、公证和 Windows 证书暂缓；当前产物必须明确标为内部测试包，不能称为公开发布版。

这样把“数据库结构升级”“换成桌面窗口”“搬动大量用户数据”拆开，任何一步出问题都更容易停住和回退。

## 用户确认的九项决定

1. **首次桌面升级不搬旧数据。** 先备份数据库，再追加新批量结构；失败不进入批量功能。
2. **换外壳，不换发动机。** Electron 负责窗口和本机能力，现有业务与媒体内核继续由私有 Node 服务承载。
3. **升级体验默认自动。** 快速完成时直接进入项目；需要等待才显示真实步骤；失败说明旧数据安全，并提供重试、恢复备份和详情。
4. **首版平台收敛。** 只承诺 macOS Apple Silicon 与 Windows x64，不承诺 Intel Mac 或 Windows ARM。
5. **正式签名暂缓。** 当前只做内部测试包；未来公开分发时再加入 macOS Developer ID／公证和 Windows Authenticode。
6. **首版手动升级。** 不建设自动更新服务器和在线回滚链路，新版本由用户运行新的安装包。
7. **卸载默认保留数据。** 彻底删除数据是单独、高风险、需二次确认的动作。
8. **安装包最后做。** 先完成批量核心、供应商链路和真实媒体验证，项目稳定后再实施 Electron 与双平台安装包。
9. **公司 sidecar 故障隔离。** LiteLLM 是公司供应商必要组件，一键入口负责联动，但其失败不能阻塞应用或外部供应商。

## 1. 当前工程基线

当前工程已经拥有可复用的安装基础：

- Next 使用 standalone 输出，并把静态资源复制进独立运行目录。
- macOS 和 Windows 安装包已经携带私有 Node 22、Next 服务、FFmpeg 和原生依赖。
- macOS 构建会校验 Apple Silicon FFmpeg，并对不可用 ffprobe 使用现有 FFmpeg 回退。
- Windows 构建要求真实 Windows x64 主机和 Node 22。
- 安装包会排除 `data/`、`storage/`、`outputs/`、`.env*`、开发文档和缓存。
- 数据库已经启用 WAL 与外键；成片模块已有版本化事务迁移，核心迁移仍是逐条执行并捕获异常的旧机制。

本票调查期间，本地通过了：

- `node scripts/db-migrations.test.ts`
- `node scripts/final-edit-schema-migrations.test.ts`
- `node scripts/macos-installer.test.mjs`
- `node scripts/windows-installer.test.mjs`
- `node scripts/macos-installer-payload.test.mjs`

这些证据只说明现有迁移与安装负载基线没有先坏掉。当前安装包仍会打开系统浏览器；没有 Electron、没有迁移前数据库备份、没有 Windows 真机 Electron 包。现有 macOS 包只有 ad-hoc 签名，也不是正式公开分发包。

## 2. 最终运行结构

```text
产品素材工作台.app / CreativeStudio.exe
└── Electron Desktop Runtime Host
    ├── 单实例、窗口、菜单和原生文件选择
    ├── 启动并看管私有 Node 服务
    ├── 受控 preload Bridge
    └── 退出与恢复协调

Resources/server
├── Next standalone + React 界面
├── SQLite、供应商 Adapter、任务调度
└── FFmpeg、TTS、分析、代理与渲染

Resources/runtime
└── 固定版本的私有 Node 22

Optional company-provider sidecars
├── LiteLLM（公司供应商必要，本地桥接）
└── Media Transport Adapter（当前开发期 Cloudflare，未来腾讯云）
```

Electron main 和 preload 不加载 `better-sqlite3`、sharp 或媒体业务模块。原生模块继续只由匹配 ABI 的私有 Node 22 加载，避免为了 Electron 重编整个成熟后端。

最终用户双击桌面应用后看到 Electron 窗口，不再自动打开系统浏览器。`npm run dev` 的浏览器模式继续保留给开发和自动测试，但不是安装版用户的默认工作方式。

## 3. 数据库升级门禁

新增一个数据库升级 Module，放在任何业务 schema 初始化之前。Electron 启动 Node 后，只有这个 Module 报告 `ready` 或安全的 `compatibility-only`，窗口才进入项目工作区。

建议的稳定状态：

| 状态 | 含义 | 用户体验 |
|---|---|---|
| `current` | 没有待执行迁移 | 正常进入，不制造备份或提示 |
| `backing_up` | 正在生成一致数据库快照 | 需要明显等待时显示“正在备份项目数据” |
| `validating_backup` | 正在核验备份 | 显示真实步骤，不给虚假百分比 |
| `migrating` | 正在执行明确版本的追加迁移 | 显示“正在升级项目数据” |
| `validating_result` | 正在检查新结构与旧数据 | 通过后进入工作区 |
| `compatibility_only` | 新功能迁移未完成，但旧库保持完整 | 旧项目和单条混剪可用，批量入口暂不可用 |
| `recovery_required` | 备份或现有数据库存在需人工决定的问题 | 提供重试、恢复备份、查看详情 |

状态必须写入可审计的升级记录，不能只存在启动窗口内存中。

### 3.1 升级顺序

1. 取得单实例和数据库升级锁，禁止第二个服务同时迁移。
2. 打开旧库，启用外键，确认数据根和当前 schema 版本。
3. 没有待执行迁移时直接结束，不重复创建备份。
4. 有新迁移时检查数据库可读、备份目录可写和磁盘空间。
5. 使用 SQLite Online Backup API 在同一数据根的备份目录生成临时快照，不在活跃 WAL 数据库旁只复制 `workbench.db`。
6. 用独立只读连接验证备份的 `integrity_check`、`foreign_key_check`、目标文件大小与哈希。
7. 原子发布备份和 manifest 后，才开始新迁移。
8. 每个 schema 版本在单独事务中执行 SQL、业务回填和版本记录。
9. 检查外键、结构、核心旧数据数量和新业务不变量，通过后才报告 `ready`。

### 3.2 备份范围与保存位置

升级备份只备份 SQLite 数据库，因为本次追加 schema 不修改视频、图片、LUT 或正式产物。复制几十 GB 媒体既没有必要，也会让升级更慢、更容易因磁盘不足失败。

备份建议统一放入：

```text
<dataRoot>/backups/database/pre-<targetSchema>-<timestamp>/
├── workbench.db
└── manifest.json
```

manifest 至少保存应用版本、来源 schema、目标 schema、创建时间、数据库大小、SHA-256、完整性检查结果和数据根身份。目录继承当前用户的私有访问权限；数据库含供应商密钥，不能进入 ZIP、日志、安装包或公共目录。

至少保留最近三份成功升级备份；当前版本完成真实启动和回归前不自动清理旧备份。失败升级使用的备份永久保留，直到用户明确处理。

### 3.3 迁移失败和恢复

- 事务内失败立即回滚，不允许半张表或半批回填继续存在。
- 备份失败、磁盘不足或备份检查失败时，一条新迁移都不执行。
- 自动流程不会擅自用旧备份覆盖当前库；事务回滚后优先进入兼容模式。
- 用户明确选择“恢复备份”时，先完全停止 Electron 中的业务窗口、Node、SQLite 和 FFmpeg；把当前库隔离保存后，再原子替换为已验证快照。
- 恢复后重新检查完整性和 schema，不能仅以“文件复制成功”作为恢复成功。

## 4. 新批量 schema 必须与旧迁移隔离

批量功能建立自己的版本化迁移列表与迁移表，例如 `batch_schema_migrations`。它采用和现有成片模块类似的“版本 + SQL + 事务”模式，但外层增加本票确定的升级备份与验证门禁。

规则如下：

- 不修改已经发布的 `CORE_DB_MIGRATIONS` 或 `FINAL_EDIT_MIGRATIONS` 条目。
- 新批量表、索引和追加字段只能放入新版本；不能把复杂迁移塞进旧 runner 后捕获所有错误。
- V1 优先新建独立表并引用既有项目、分镜组、脚本和正式产物身份，避免破坏旧表。
- 不删除、重命名或改变旧列语义；旧版本程序可以忽略不认识的新表。
- 批量 API 在 schema 未就绪时返回明确的“功能暂不可用”，旧项目和单条 API 不依赖新表。
- 数据回填必须有稳定幂等键；重复启动不会多建批次、素材或任务。

这使正常降级更简单：重新安装旧测试包时，旧程序忽略追加的新表；新批量数据仍留在数据库，重新升级后继续可见。需要恢复旧数据库时仍走明确的备份恢复流程，不提供危险的通用“倒放 SQL”。

## 5. 首版不迁移数据根

首版 Electron 沿用当前安装版的数据根：

- macOS：`~/Library/Application Support/CreativeStudio`
- Windows：现有安装目录的数据根行为

Electron 自己的 `userData` 只保存窗口设置和 Chromium 数据，不存项目数据库、大视频、代理或正式产物。业务代码继续只认 main 注入私有 Node 的 `CREATIVE_STUDIO_DATA_ROOT`。

Windows 数据长期放在安装目录不是理想终态，但当前数据库仍保存部分受管素材绝对路径。首次 Electron 升级同时搬根会额外需要大文件移动、旧绝对路径改写、空间检查和完整回滚，因此本票明确暂缓。未来如迁到 `%LOCALAPPDATA%`，必须作为独立迁移处理，不能夹进本次桌面化。

链接素材继续留在用户原文件夹或外置盘；本票不复制、不移动、不删除用户原片。

## 6. 安装包资源布局

Electron 桌面代码与业务运行时分开：

- `app.asar` 只包含 Electron main、preload 和必要的纯桌面代码。
- Next standalone、私有 Node、`.node` 模块、sharp 依赖、FFmpeg 和 ffprobe 放在 ASAR 外的只读安装资源区。
- SQLite、storage、代理、正式产物和日志写入 `CREATIVE_STUDIO_DATA_ROOT`，绝不写进 ASAR 或只读资源目录。
- main 使用明确可执行文件和参数启动私有 Node，不经过通用 shell 字符串。
- renderer 不得到 `fs`、`child_process`、任意绝对路径读取或任意 IPC channel。

使用标准 Electron packaging 工具生成正确的 helper 与资源结构；继续复用现有自定义 DMG 外观、Inno Setup 安装体验和 payload 排除断言，不手工仿造 Electron helper 目录。

构建生成一份 runtime manifest，记录：

- 应用、Electron 和私有 Node 精确版本。
- 平台、CPU 架构、Node ABI。
- `better-sqlite3`、sharp、FFmpeg、ffprobe 包版本和实际二进制架构。
- 下载运行时的来源与 SHA-256。
- 构建时间和 Git commit。

Node 下载必须校验固定 SHA-256，不能只因为 URL 返回成功就进入安装包。

## 7. 平台与构建矩阵

### macOS V1 内部测试包

- 只支持 Apple Silicon arm64 和当前最低系统版本约束。
- 构建主机必须是 arm64 macOS、Node 22，不在 Rosetta 下混装原生模块。
- Electron、私有 Node、`better-sqlite3`、sharp、FFmpeg 和可用的 ffprobe 全部核验 arm64。
- 保留现有 FFmpeg 元数据探测回退。
- 当前允许 ad-hoc 内部测试签名；文件名和界面明确标记“内部测试版”。

### Windows V1 内部测试包

- 只支持 Windows x64。
- 必须在真实 Windows x64 构建，不能从 Mac 复制 `node_modules` 或假设跨平台原生模块可用。
- 保留当前 Inno Setup 每用户安装和稳定 AppId，确保新安装包能识别旧安装。
- Electron、私有 Node、`.node`、FFmpeg 和 ffprobe 均在包内执行真实 smoke。
- 当前允许未签名内部测试包；明确提示可能出现 Windows 安全警告，不称为正式发布版。

Intel Mac、Universal Mac 和 Windows ARM64 不属于 V1 承诺。未来每增加一个目标，都要增加独立二进制、构建主机和真机验收矩阵。

## 8. 启动、升级和退出

1. Electron main 先取得单实例锁，不允许两个调度器争用同一数据库。
2. 确定既有数据根，生成本次启动秘密和随机本机端口。
3. 直接启动私有 Node，捕获 PID、stdout、stderr 与退出状态。
4. Node 先完成数据库升级门禁，再开放带实例身份的健康检查。
5. 核心服务就绪后即允许加载当前精确 `127.0.0.1` origin；不再打开默认浏览器。
6. 仅当配置并选择公司供应商时启动或检查 LiteLLM 与媒体传输 sidecar；失败记录明确健康状态，但不关闭核心服务或窗口。
7. 关闭窗口只隐藏应用并继续后台生产；明确退出才暂停任务、关闭数据库并回收 Node、FFmpeg 与本次启动入口持有的 sidecar。
8. 异常退出依靠持久任务恢复，不能假设操作系统一定给清理时间。

首版不做自动更新。新版本由用户手动运行安装包；安装器先停止旧实例，程序首次启动再按上述门禁备份和升级。应用版本只从 `package.json` 生成，不允许 DMG、Electron metadata 和 Inno 脚本各自维护不同版本号。

## 9. 卸载与彻底删除

普通卸载只删除应用程序和只读运行资源，默认保留：

- `workbench.db`、升级备份和供应商配置。
- 项目托管素材、分析结果、脚本和任务记录。
- 正式视频、封面和其他项目产物。
- 代理与临时缓存；它们可以在软件内另行清理，但不能借卸载偷删。

重新安装同版本或新版后，应用使用原数据根继续打开项目。

“彻底删除本地数据”是独立动作：

1. 明确展示将删除的数据根、数据库、项目、正式产物、备份和预计空间。
2. 明确说明链接在外部的原片不会被删除。
3. 要求二次确认，并先关闭 Node、SQLite 和 FFmpeg。
4. 只允许删除经过 realpath 核验的应用数据根内白名单目录，不能删除任意路径、用户主目录或外置素材。
5. 完成后报告删除内容与不可恢复性。

## 10. 当前签名与发布边界

用户已明确暂时不需要正式签名、公证或 Windows 证书，因此它们不进入当前实现范围，也不阻塞内部功能验收。

当前允许产出：

- macOS ad-hoc 签名内部测试 DMG。
- Windows 未签名内部测试安装器。

当前不允许宣称：

- macOS Gatekeeper 无提示公开分发。
- Apple 公证已经通过。
- Windows SmartScreen 无提示或 Authenticode 已验证。
- 可自动更新的公开发行版。

将来需要外部分发时，单独增加 Developer ID、Hardened Runtime、notary／staple、Windows Authenticode SHA-256 和 RFC 3161 时间戳，并重新做干净机器验收。

## 11. Module、Seam 与 Adapter

### 数据库升级 Module

负责发现版本、备份、验证、事务迁移、兼容模式和恢复。业务页面、Electron main 和安装脚本不直接执行 SQL。

### 备份 Adapter

生产使用 `better-sqlite3` 的 Online Backup 能力；测试使用临时文件与故障注入 Adapter。普通文件复制不能伪装成 WAL 数据库备份。

### Desktop Runtime Host

只监管窗口、preload、本机服务、可选公司 sidecar 和退出，不理解批次、成片或 FFmpeg 参数。开发 Adapter 可以启动本地 `npm` 服务，安装 Adapter 必须启动包内私有 Node；sidecar 失败通过健康状态上报，不得使核心服务退出。

### 打包 Adapter

macOS 与 Windows 分别组装目标架构资源，执行相同的 runtime manifest、敏感文件排除和最小媒体 smoke 合同。DMG 与 Inno 是不同 Adapter，不复制业务规则。

### 签名 Adapter

当前为明确的内部测试实现：macOS ad-hoc、Windows unsigned。Interface 保留未来正式签名门禁，但当前不要求用户配置证书，也不在日志或仓库保存证书材料。

## 12. 实现验收

### 数据迁移

1. 没有待执行迁移时不创建新备份，启动路径与旧版等价。
2. 对真实旧数据库副本升级前先生成可独立打开的 SQLite 快照。
3. 备份必须通过完整性、外键、大小和哈希检查；失败时新 SQL 一条不执行。
4. 注入 SQL 错误、进程崩溃、磁盘不足和第二实例时，不留下半迁移状态。
5. 相同版本重复启动不重复建表、回填或创建业务对象。
6. 迁移成功后旧项目、设置、API Key、脚本、单条混剪和正式产物数量与内容保持一致。
7. 迁移失败时批量入口关闭，旧项目和单条混剪可以进入兼容模式。
8. 明确恢复备份后，隔离失败库并重新通过完整性检查。

### 桌面运行

9. 双击应用只出现一个 Electron 窗口和一套私有 Node／调度器，不打开默认浏览器。
10. 原生多选文件和文件夹选择能登记素材，renderer 不能读取未授权任意路径。
11. 关闭窗口后台任务继续；再次点击应用图标恢复原窗口和页面。
12. 明确退出会安全暂停任务、关闭数据库并回收 Node 与 FFmpeg；强制结束后重启可恢复。
13. 本机端口冲突不会打开另一个程序的网页；健康检查必须核验实例身份。
14. `POST /api/shutdown` 不再是任意本机页面可调用的无认证退出开关。

### macOS arm64 内部测试包

15. 干净 Apple Silicon Mac 无需系统 Node 或 FFmpeg即可启动。
16. 包内 Node、`better-sqlite3`、sharp、FFmpeg 和真实最小转码通过。
17. 旧 DMG 安装数据升级后仍可打开，卸载默认保留数据，重装后项目仍在。
18. 明确记录 ad-hoc 内部测试状态，不把本机 smoke 当成正式公证。

### Windows x64 内部测试包

19. 在真实 Windows x64 主机构建并在另一台干净 Windows x64 机器安装。
20. 包内 Node、`better-sqlite3`、sharp、FFmpeg／ffprobe 和最小转码通过。
21. 旧安装器原地升级、中文与长路径、卸载保留、重装恢复和进程无残留通过。
22. 明确记录 unsigned 内部测试状态，不把静态安装脚本测试当成 Windows 真机通过。

### 回归边界

23. `npm run dev` 和生产 standalone 仍可作为开发／测试形态运行。
24. 单条精准混剪、模块 1–4、项目导出和现有成片编辑回归通过。
25. 安装负载不含用户数据、API Key、开发文档或真实项目文件。
26. 每次交付分别报告设计、代码、本地测试、真实 FFmpeg、macOS 真机、Windows 真机、真实供应商和用户验收状态。

## 13. 推荐落地顺序

1. 先实现数据库升级门禁、Online Backup、验证、故障注入和兼容模式。
2. 用独立版本表加入最小批量空 schema，验证旧程序与新程序共同读取旧项目。
3. 在现有本地运行形态中逐阶段完成批量素材库、调度、代理、LUT、联合分配和卡片工作区，并持续回归单条混剪。
4. 做稳外部供应商旁路、公司 LiteLLM 运行环境、媒体传输 Adapter 与故障隔离；真实供应商调用仍需逐次授权。
5. 核心稳定后加入 Electron 开发壳、单实例、窄 Bridge、私有 Node 与可选 sidecar 监管。
6. 把 Next standalone、Node、媒体二进制及必要 sidecar 放入受控资源布局，分别改造 DMG 与 Inno 内部测试构建。
7. 最后真实验证升级、卸载、重装、关闭窗口、退出、崩溃恢复、最小 FFmpeg 和用户选择规模的完整批量运行。

最终的小提交、文件清单和每阶段命令由 [汇总可执行阶段与小步提交计划](../12-汇总可执行阶段与小步提交计划.md) 统一编排。

## 14. 本票明确不做

- 不重写现有 Next、SQLite、队列或 FFmpeg 内核。
- 不复制参考项目的 Python 后端、Electron renderer 或通用 IPC。
- 不在首版 Electron 中移动 Windows 旧数据根或用户原素材。
- 不支持 Intel Mac、Universal Mac 或 Windows ARM64。
- 不实现自动更新。
- 不购买、生成、提交或持久化正式签名证书。
- 不把内部测试包描述成公开可发布产品。
