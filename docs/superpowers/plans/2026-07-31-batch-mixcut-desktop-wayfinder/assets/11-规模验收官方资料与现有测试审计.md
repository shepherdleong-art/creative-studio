# 批量混剪规模验收：官方资料与现有测试审计

> 研究日期：2026-07-31  
> 范围：验证矩阵与验收设计，不实现资源调度器，不发起真实供应商请求。  
> 结论状态：仓库现状已审计；跨平台性能、安装升级、60/8/20 规模和真实供应商仍待实施后真机验证。

> **评审后的产品修正（2026-08-01）**：下文的固定 60／8／20、固定素材构成和普通压力下自动降档是研究阶段候选方案，未被用户采纳。最终决定以 [验证矩阵与可变规模真实验收设计](./11-验证矩阵与可变规模真实验收设计.md) 为准：数量和素材构成由用户决定；默认全速，普通高负载提醒用户选择，只有磁盘不足或内存危险才保护暂停。

## 1. 结论先行

“60 条素材、8 份脚本、20 条成片跑通”不能只由一条自动化测试证明。完整验收至少要同时满足五件事：

1. 20 个计划任务都拥有可恢复的持久化状态，单条失败不拖垮整批。
2. 成功项的 MP4、封面和数据库产物都真实存在、可解码、可再次打开；失败项有稳定错误码和可重试入口。
3. 分析显示真实完成数量，FFmpeg 导出显示真实媒体时间；远端供应商没有百分比时不得伪造百分比。
4. 至少在 Apple Silicon macOS 和 Windows x64 的安装包里分别完成规模运行、暂停恢复、异常恢复和升级验证。
5. 报告必须标明验证层级；mock、本地单平台或一次成功都不能写成“完整通过”。

当前仓库已经有较扎实的领域规则、SQLite、真实小样 FFmpeg 和浏览器流程测试，但没有批量领域模型、自动资源控制、Electron 运行壳、60/8/20 规模套件、Windows 真机结果或真实供应商验收。因此当前只能说“单条混剪基础具备迁移价值”，不能说“批量能力已验证”。

## 2. 自动资源控制：可采集的指标和不能统一的阈值

### 2.1 可作为跨平台基础信号

| 信号 | 能回答什么 | 使用边界 |
|---|---|---|
| `os.availableParallelism()` | 操作系统估计应用可使用的默认并行度 | 用来确定保守的初始槽位上限，不等于 FFmpeg 最佳线程数。Node 明确建议用它估算可用并行度，而不是直接使用逻辑 CPU 数量。[Node.js OS API](https://nodejs.org/docs/latest-v22.x/api/os.html#osavailableparallelism) |
| `os.totalmem()` / `os.freemem()` | 当前系统总内存和空闲内存快照 | 可观察趋势和保护下限，但“空闲”不等于各系统相同含义的“可安全再分配内存”，不能单独决定并发。[Node.js OS API](https://nodejs.org/docs/latest-v22.x/api/os.html#osfreemem) |
| `process.memoryUsage()` / `process.cpuUsage()` | Node 后端自身的 RSS、堆和 CPU 时间 | 只覆盖当前 Node 进程；`process.cpuUsage()` 的多核 CPU 时间可以大于经过的墙钟时间，不能直接当整机百分比。[Node.js process.memoryUsage](https://nodejs.org/docs/latest-v22.x/api/process.html#processmemoryusage)、[process.cpuUsage](https://nodejs.org/docs/latest-v22.x/api/process.html#processcpuusagepreviousvalue) |
| `performance.eventLoopUtilization()` / `monitorEventLoopDelay()` | UI 后端事件循环是否被阻塞 | 用来保护“界面还能操作”，不能代表 FFmpeg 子进程或整机 CPU。事件循环延迟由直方图采样，ELU 是事件循环活跃时间，不是系统 CPU 利用率。[Node.js Performance API](https://nodejs.org/api/perf_hooks.html#performanceeventlooputilizationutilization1-utilization2)、[monitorEventLoopDelay](https://nodejs.org/api/perf_hooks.html#perf_hooksmonitoreventloopdelayoptions) |
| Electron `app.getAppMetrics()` | Electron 自身 Browser/Tab/Utility/GPU 等进程的 CPU 和内存 | 可发现桌面壳自身异常，但它不是整机指标，也不应假设包含任意 FFmpeg 子进程。[Electron app.getAppMetrics](https://www.electronjs.org/docs/latest/api/app#appgetappmetrics)、[ProcessMetric](https://www.electronjs.org/docs/latest/api/structures/process-metric) |
| 文件系统剩余空间 | 代理、缓存、临时渲染和最终成片是否有安全写入余量 | 应按本次任务估算的输入、临时文件和输出需求做相对校验，不用固定“剩余 10GB”覆盖所有项目。[Node.js fs.statfs](https://nodejs.org/docs/latest-v22.x/api/fs.html#fspromisesstatfspath-options) |
| 电源、休眠和降速事件 | 电脑切到电池、系统暂停/恢复、CPU 被系统降速 | Electron 的电池与 `speed-limit-change` 支持 macOS/Windows，可作为降并发信号。[Electron powerMonitor](https://www.electronjs.org/docs/latest/api/power-monitor) |

### 2.2 只能作为平台增强信号

- macOS 有 `nominal / fair / serious / critical` 热状态，Apple 建议热状态升高时减少系统资源使用；Electron 的当前热状态 API也只标注 macOS。[Apple ProcessInfo thermalState](https://developer.apple.com/documentation/foundation/processinfo/thermalstate-swift.property)、[Electron powerMonitor](https://www.electronjs.org/docs/latest/api/power-monitor)
- macOS 原生 `DispatchSourceMemoryPressure` 能监听系统内存压力；它不是 Windows 的同名统一接口。[Apple DispatchSourceMemoryPressure](https://developer.apple.com/documentation/dispatch/dispatchsourcememorypressure)
- Windows `GlobalMemoryStatusEx` 能返回近似物理内存负载和可立即复用的物理内存，但这是 Windows 专用语义。[Microsoft MEMORYSTATUSEX](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/ns-sysinfoapi-memorystatusex)
- Windows 的 CPU “忙碌时间”和“处理能力”并非同一个指标；微软说明 Turbo Boost 等会使不同性能计数器出现不同解释，甚至超过 100%。因此不能把某个平台任务管理器里的固定百分比复制成跨平台产品阈值。[Microsoft CPU utilization explanation](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/cpu-usage-exceeds-100)

### 2.3 不应成为统一硬阈值的指标

- `os.loadavg()`：Windows 固定返回 `[0, 0, 0]`，不能跨平台控制并发。[Node.js OS API](https://nodejs.org/docs/latest-v22.x/api/os.html#osloadavg)
- CPU 温度、GPU 占用、硬件编解码器占用：Electron/Node 没有统一、稳定且含义一致的 API。
- 单次的“空闲内存百分比”或“CPU 90%”：编码主动吃满 CPU 并不必然是故障；不同机器的内存压缩、交换区、频率和硬件编码能力也不同。
- 文件大小、分辨率或“4K”标签：它们不能独立代表解码成本；编码格式、位深、色度采样、帧率、码率、旋转、VFR、滤镜和 LUT 都会改变负载。
- 一次磁盘测速或一次任务耗时：会受缓存、温控、其他应用和磁盘剩余空间影响，不能永久给电脑分级。

### 2.4 对本项目的调度建议

资源控制应是“保守起步 + 持续反馈 + 迟滞”，而不是启动时给电脑打一个永不变化的分数：

1. 初始上限由可用并行度、总内存、任务类型和供应商并发上限共同决定。
2. 采样系统内存、磁盘余量、事件循环、应用进程资源、电源/降速信号；macOS 再叠加热状态和内存压力。
3. 只在任务边界调整槽位：压力持续出现时先停止派发新重任务，再逐级降并发；连续稳定一段时间后才逐级升并发，避免来回抖动。
4. 分开管理本地分析、代理生成、FFmpeg 导出和远端请求。远端 API 并发受供应商限流控制，本地 FFmpeg 并发受电脑资源控制，二者不能用同一个数字。
5. 已启动的 FFmpeg 不因一次瞬时采样就强杀；只有用户取消、硬错误或系统进入需要保护的严重状态时才中断，并保留可恢复状态。

这套策略的**信号来源已由官方 API 确认**；具体升降阈值、采样周期和最低硬件要求必须用目标真机校准，当前不能作为已确认值。

## 3. 真实进度如何产生

### 3.1 FFmpeg 导出

FFmpeg 官方 `-progress` 会周期性输出机器可解析的 `key=value`，一组输出以 `progress=continue` 或 `progress=end` 结束，更新周期可由 `-stats_period` 控制。[FFmpeg `-progress`](https://www.ffmpeg.org/ffmpeg.html#toc-Generic-options)

本仓库已经在 `lib/ffmpeg.ts` 解析 `out_time_us`，并在 `lib/final-edit/renderer.ts` 用 `outTime / 预期总时长` 计算渲染进度。批量版应沿用这个事实来源：

- 单条导出进度 = `clamp(out_time_us / 计划输出总时长)`。
- 只有 FFmpeg 正常退出、文件发布成功、产物可探测后才能显示 100%。
- `ffprobe` 用机器可解析格式读取时长、流、尺寸和帧率；无法打开或识别的媒体会返回非零退出码。[ffprobe 官方文档](https://ffmpeg.org/ffprobe.html)
- 批次总览显示“已导出 n/20”，正在导出的卡片显示真实媒体时间百分比；不得用定时器匀速增长。

### 3.2 素材分析

分析包含多种性质不同的工作，不能硬拼成一个看似精确的百分比：

- 批次层显示真实计数：`已分析素材数 / 需要分析素材数`；缓存命中也应记录为“复用完成”。
- 当前素材显示可验证子阶段：读取媒体信息、场景扫描、抽取第 `x/y` 张帧、等待 AI 分析、写入结果。
- 本地场景扫描若接入 FFmpeg `-progress`，可用媒体时间显示当前文件内部进度；当前 `detectVideoScenes` 尚未接入该进度输出。
- 远端视觉分析没有供应商返回的明确百分比时，只显示“请求中/等待响应/校验中”，不能把等待秒数换成百分比。

当前 `lib/final-edit/workspace.ts` 的 prepare job 使用 `0.3 / 0.55 / 0.82` 等阶段权重。这能表达状态单调前进，但属于产品内部估算，不应在新版批量界面标成“真实分析百分比”。

### 3.3 TTS、脚本和其他远端供应商

- 分段 TTS 可以用 `已完成句段 / 总句段`，因为仓库已有 `onSegmentComplete(completed, total)`。
- 异步视频供应商可以显示已提交、轮询状态、已完成条数和下载阶段；只有供应商协议明确返回百分比且适配器验证其含义时，才显示单任务百分比。
- 普通 LLM/视觉请求只保证开始和结束时，显示阶段及已完成请求数。当前脚本 V3 的 32%、45% 等也是流程权重，不是供应商计算进度。
- 轮询超时后如果已经取得 `providerTaskId`，状态应为“待核查”，不能直接当失败后重复提交，以免重复计费。当前 `lib/video-queue.ts` 已有这一边界。

## 5. 60 条素材、8 份脚本、20 条成片的代表性样本

### 5.1 固定样本清单

样本必须有不可变 manifest：文件名、SHA-256、大小、时长、容器、视频/音频 codec、分辨率、帧率、位深、色度采样、旋转、色彩/LOG 标记、来源类型和预期结果。不能临时从个人素材文件夹随便挑 60 条后只记录“跑过”。

建议 60 条分层如下：

- 24 条手机 SDR：1080p/4K、横竖屏、H.264/HEVC、24/25/30/50/60fps，包含旋转元数据、VFR、有声和无声。
- 18 条相机普通色彩：1080p/4K、不同码率、H.264/HEVC、8/10-bit，包含长 GOP、高码率和较长素材。
- 10 条相机 LOG：至少来自实际计划支持的相机/编码组合，覆盖不开 LUT 直接预览、导入 LUT、生成代理后预览与导出。
- 8 条边界/故障素材：极短、较长、同内容重复、中文/空格/括号文件名、缺音轨、错误扩展名、截断文件、不可识别文件。后两类预期是可解释失败，不能为了“60/60 成功”排除。

8 份脚本建议覆盖 15 秒、30 秒和较长口播；含多句、少句、标点和换行差异、相同文案生成多条、同标题自动传递、个别 TTS 失败。20 条 Output Plan 固定分配为 `3+3+3+3+2+2+2+2`，这样每份脚本都有多条结果，也能验证“同脚本标题相同、封面底图不同”和重复素材控制。

主规模批次使用一个明确的用户默认输出规格，避免把“同一批 20 条”偷偷拆成多种规格降低压力；其他画幅用独立小批次做兼容烟测。

### 5.2 规模通过的硬条件

- 60 条都被登记；预期有效素材进入可用池，预期损坏素材进入可解释失败/排除状态，一条坏文件不阻塞其余 59 条。
- 8 份脚本和 20 个 Output Plan 在点击开始前被冻结为可追溯修订；重启后数量、对应关系和设置不变。
- 20 张成片卡片预先存在并最终进入明确终态；失败后重试仍是原卡片，不额外增加第 21 条。
- 所有成功 MP4 均非空、可由打包同源 FFmpeg 完整解码、时长在设计容差内；封面可读取，标题正确，底图差异和素材重复约束符合既定规则。
- 每条使用的素材区间、脚本、标题、代理/LUT 身份、重试次数、输出路径都有持久化证据；项目/shotSet 隔离无串数据。
- 应用保持可操作，资源控制没有 OOM、整批崩溃或无限等待；性能数字完整记录，但首轮不能凭未经校准的单一耗时阈值判死刑。
- 同一构建和同一 manifest 在每个声明支持的平台至少连续成功 3 次；三次都保留运行报告。偶然一次通过不计“规模通过”。

## 6. 故障注入与恢复验收

| 注入点 | 操作 | 必须观察到的结果 |
|---|---|---|
| 导入/探测 | 混入截断、错误格式、无视频流和路径含中文/空格的文件 | 单文件失败可见，其余继续；临时文件可清理；重新打开状态不丢 |
| 视觉/LLM | 本地假服务依次返回 429、500、超时、无效 JSON、断连 | 只按策略重试；达到上限后单素材失败；不伪造百分比；日志无密钥 |
| TTS | 第 3 份脚本某句失败、超时或返回无效音频 | 只影响相关 Output Plan；可重试该脚本/卡片；已完成项不重做 |
| FFmpeg | 非零退出、超时、缺少 codec、被用户取消 | 进程被收回；临时产物不发布为完成；卡片保留重试入口和 stderr 尾部诊断 |
| 磁盘 | 在临时/发布阶段注入 `ENOSPC` 或 SQLite `SQLITE_FULL` | 停止派发新重任务，已完成产物不丢，数据库不出现“成功但文件不存在”。SQLite 明确区分磁盘满、I/O、忙和损坏错误。[SQLite result codes](https://www.sqlite.org/rescode.html) |
| 数据库提交 | 在批次/卡片终态事务提交前后分别故障 | 单事务要么全有要么全无；SQLite 事务具有原子性。[SQLite transactional guarantees](https://www.sqlite.org/transactional.html) |
| 进程重启 | 分析中、等待供应商、渲染中、发布前后分别强制结束桌面进程 | 重开后 running 任务被审计并恢复/待核查；不得重复创建卡片、重复发布或重复计费 |
| 暂停/恢复 | 分析和导出高峰点击暂停，退出并重开，再恢复 | 暂停后不再领取新任务；正在运行项按产品约定完成安全边界或取消；恢复从持久状态继续，进度不倒退 |
| 单条重试/重新分配 | 对第 7 条失败卡片操作 | 只改第 7 条及其修订；其他 19 条的文件、状态和映射不变 |
| 资源压力 | 同时制造低内存、降速/热状态或磁盘余量不足 | 调度器停止加并发并逐级降载；恢复稳定后再缓慢升载；主界面和暂停按钮仍可响应 |

WAL 允许读写并行但同一时间仍只有一个 writer；检查点还会受长读事务影响，因此规模验收要记录 `SQLITE_BUSY`、WAL 大小和检查点结果，不能仅看页面。[SQLite WAL concurrency](https://www.sqlite.org/wal.html#concurrency)

## 7. 安装、升级和数据安全矩阵

### 7.1 每个平台都要跑的场景

| 平台 | 全新安装 | 旧版升级 | 60/8/20 | 暂停重开 | 卸载重装保留数据 |
|---|---:|---:|---:|---:|---:|
| Apple Silicon macOS | 必须 | 必须 | 必须 | 必须 | 必须 |
| Windows x64 | 必须 | 必须 | 必须 | 必须 | 必须 |

每个平台至少包含一台候选最低配置和一台常用配置。8GB/16GB、CPU 型号、系统版本、磁盘类型与空闲空间只作为候选测试档，不在数据出来前写成正式最低配置。

### 7.2 升级验收

1. 使用去标识化的真实旧版数据库副本和旧 storage；记录升级前表行数、关键项目 ID、文件 manifest。
2. 运行在线一致性备份，打开备份执行完整性检查，再开始追加式迁移。SQLite Online Backup API完成后提供一致快照，并可用 page count 报告备份进度。[SQLite Online Backup API](https://www.sqlite.org/backup.html)
3. 正常升级后验证旧项目、单条混剪、供应商设置和文件仍可访问；新批量表可用；重复启动迁移幂等。
4. 在备份中、迁移中和迁移成功标记前注入失败；旧数据必须仍可用，批量功能不得处于半开启。
5. 恢复备份后再次校验数据库、行数和文件 manifest。

## 8. 真实供应商验收边界

真实供应商调用会传输项目派生的图片、视频帧、脚本文字或语音文本，并可能产生费用；执行前必须单独确认供应商、数据范围、预计请求数/费用和保留策略。本研究没有发起任何外部请求。

获授权后，按“适配器路径”而不是只按供应商名称验收：

- 视觉分析：真实素材抽帧 → 真实协议 → 结构校验 → 数据库缓存 → 重启复用。
- TTS：8 份脚本真实合成 → 音频可探测 → 句段完成计数 → 字幕对齐 → 失败单独重试。
- 每条协议至少覆盖正常成功、可重试错误/限流、取消或超时后的状态确认；记录 provider task ID/请求 ID 的脱敏证据。
- 真实供应商通过不能替代本地 mock 故障注入；mock 能稳定制造边界，真实验收只能证明当时的真实协议可用。

## 9. 防止误报的统一报告格式

每次报告必须包含：Git commit、构建号、测试层级、OS/架构、硬件与内存、安装/开发运行形态、样本 manifest 哈希、是否真实供应商、是否发生费用、开始/结束时间、20 个卡片终态统计、产物 manifest、失败与重试统计、峰值/趋势资源记录和日志位置。

只允许使用以下分层结论：

- **静态通过**：lint/type/build/文本契约通过。
- **本地确定性通过**：内存数据库、mock 和本机真实 FFmpeg 小样通过。
- **规模通过（平台名）**：该平台安装包连续 3 次完成固定 60/8/20 manifest。
- **真实供应商通过（协议/供应商名）**：经过授权的真实请求完成并有脱敏证据。
- **跨平台通过**：macOS Apple Silicon 与 Windows x64 均达到相同硬条件。
- **用户验收通过**：用户实际安装、打开、暂停恢复、检查和导出后确认。

以下说法一律禁止：

- Playwright mock 绿了就写“真实后端通过”。
- macOS 跑过就写“桌面版通过”。
- 7 个 3 秒合成素材成功就写“60 条 4K/LOG 规模通过”。
- 真实供应商单次成功就写“稳定通过”。
- job 状态是 `succeeded`，但没有检查卡片、MP4、封面和项目 artifacts，就写“成片完成”。

## 10. 票据建议的最终验收门

票据 11 可以把未来实施的“完成”定义为：

1. 新增批量测试 manifest、故障注入器和分层报告器。
2. 现有 80 个测试、lint、type/build 继续通过。
3. 本地确定性 60/8/20 在两端目标安装包连续 3 次通过。
4. 升级、暂停恢复、进程重启、磁盘满、远端错误和单条重试通过。
5. 在单独授权后完成真实视觉分析/TTS 协议验收。
6. 最后由用户在真实素材上确认“进度看得懂、电脑仍可操作、失败能处理、成片能用”。

在此之前，只能按实际层级报告部分通过，不能宣布批量混剪或桌面迁移整体完成。
