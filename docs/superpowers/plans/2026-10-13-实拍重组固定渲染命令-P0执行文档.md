# 实拍重组固定渲染命令（P0）执行文档

状态：待执行。

执行环境：真实工程验收必须在 Windows 生产机上做（`I:\m7-studio`；RC2C 等工程和已验证脚本都在那里的 `outputs/`，不进 Git）。单元测试和合成素材冒烟测试在 macOS、Windows 上都能跑。

## 0. 目标

把成片的最后一段——包装、HyperFrames 渲染、混音、封面和技术检查——做成一条不依赖 Agent 的固定命令。现行包装（静帧封面、贴纸、卖点标注、片尾）作为第一个模板。

完成后：
- Agent 出片和以后工作台导出（P1）都调用这条命令，两边结果一致；
- 同一份输入重复渲染，得到同样的成片；
- 用户的新包装设计按本文第 4 节的模板约定接入同一条命令。

**验收锚点**：拿现有成片的工程，不做任何修改直接重新渲染，结果与当初交付的成片一致（标准见第 9 节）。

| 片段准备、HyperFrames 渲染、混音、封装、封面、QA | 各工程现场适配的脚本：RC2C 的 `tools/media_pipeline.py`、`run_hf.py`；PC673 的 `revisions/hyperframes-v3/tools/` 下 `build_revision.py`、`prepare_media.py`、`run_hf.py`、`finish_audio.py`；PC673 工程的 `build_timeline.py`、`qa_frames.py`、`validate_final.py` | Windows 生产机 `outputs/`，**不在仓库里** |
| 旧版纯 ffmpeg 合成 | `scripts/reassembled-film-render.py`：HyperFrames 之前的做法，画面用预渲染 PNG 叠层；**混音链已验证**，见下 | 仓库 |
| HyperFrames 调用 | product-film skill 的 `render.py`：`npx -y hyperframes@0.8.134 render -o renders/final_video.mp4 --fps 24 --quality looks`，设 `HYPERFRAMES_SKIP_SKILLS=1`、`HYPERFRAMES_FFMPEG_PATH`、`HYPERFRAMES_FFPROBE_PATH`；Windows 上直接用 node 运行 `npx-cli.js`，避开带空格路径的引号问题 | `~/.agents/skills/product-film/scripts/render.py` |
| 字体与 GSAP | `SourceHanSansCN-VF.ttf`（约 17.7 MB）、`gsap.min.js`，由 `--assets` 指向 product-film 的 `templates/hf` | 不在仓库里，各机器路径不同 |

旧版 `reassembled-film-render.py` 里已验证、要原样继承的混音做法：
- 逐句配音按 48 kHz 单声道 PCM16 在采样点上拼接。多输入 adelay/amix 链曾在实测中被截断成封面长度（0.833 秒），这是有意的规避；
- BGM `-14 dB`，`sidechaincompress=threshold=0.025:ratio=8:attack=15:release=250` 由配音压低，淡入 0.35 秒、淡出 1 秒；
- 两遍 `loudnorm` 到 `I=-16:TP=-1.5:LRA=11`；
- 每一步都核对实际音频时长，防止截断。

已知的坑：
- RC2C 实测 HyperFrames 输出右侧有 8 像素黑条，当时核对源素材边缘正常后，在最终合成时去掉；
- HyperFrames lint：`letterSpacing` 动画判错；没有 `@font-face` 的回退字体判错；故意重叠的元素要逐个加 `data-layout-allow-overlap="true"`；
- `contract.py` 用到 `hashlib.file_digest`，需要 Python 3.11+。macOS 自带的 3.9 跑不了，本机用 `~/.local/bin/python3.12`；
- macOS 沙箱里 Playwright 启动浏览器会因权限失败，需要提权重跑；
- Windows 上写文件可能被读取者或杀毒软件短暂占用（EPERM/EBUSY），`runtime.mjs` 里有有限重试的写法可参考。

## 4. 模板约定

```text
scripts/reassembled-film/templates/
  classic/
    1/
      template.json   # 模板身份、画幅、元素、资源哈希
      build.py        # build(spec, out_dir, assets_root)：写出 index.html 等
```

`template.json` 示例：

```json
{
  "id": "classic",
  "version": "1",
  "displayName": "现行包装（静帧封面、贴纸、卖点标注、片尾）",
  "canvas": { "width": 1080, "height": 1440, "fps": 24, "introFrames": 20 },
  "elements": ["cover", "sceneTransition", "subtitles", "labels", "callouts", "outro"],
  "assets": {
    "assets/fonts/SourceHanSansCN-VF.ttf": "<sha256>",
    "assets/scripts/gsap.min.js": "<sha256>"
  }
}
```

约定：
- `build()` 只读渲染单和资源根，只写 `out_dir`；同样的输入必须产出逐字节相同的 `index.html`。
- 样式分两层：模板自带的结构和动效（含标注样式），加上工程级 `style.css`（按产品调整的字体、配色、字号）。工程样式照现在的顺序追加在模板样式之后，可以覆盖。
- 模板只负责画面。音频不进 HyperFrames，视频元素全部 `muted`，与现在一致。
- 新模板（用户的新设计）按同样的目录接入，用不同的 `id`；至少要有构建快照测试和合成素材冒烟测试。
- 「贴纸」就是 `packaging.json` 里逐镜的 `labels`（kicker、主标题、辅助文字），用户已于 2026-10-13 确认。

## 5. 渲染单（render spec v1）

一次渲染的全部输入放在一个 JSON 里。`spec` 子命令从现有工程生成它；P1 由工作台从数据库生成同样的格式。路径为绝对路径，或相对 `project.root`。

```json
{
  "schemaVersion": 1,
  "project": { "root": "I:/m7-studio/outputs/<工程>", "variant": "01", "baseName": "<开工日期>-<店铺>-<型号>-<生产类型>-<制作人>-01" },
  "canvas": { "width": 1080, "height": 1440, "fps": 24, "introFrames": 20, "frames": 432 },
  "template": { "id": "classic", "version": "1", "assetsRoot": "C:/Users/<user>/.codex/skills/product-film/templates/hf",
                "projectCss": "tools/style.css", "designDoc": "DESIGN.md" },
  "content": {
    "openingEffectId": "carton-explosion",
    "theme": "…",
    "cover": { "image": "variants/01/…/cover.png", "title": ["…", "…"], "tag": "…", "note": "…",
               "brand": "…", "model": "…", "productName": "…" },
    "shots": [ { "id": "O01", "file": "variants/01/clips/O01.mp4", "startFrame": 20, "endFrame": 96, "inSec": 0.3, "rate": 1 } ],
    "subtitles": [ { "text": "…", "startFrame": 24, "endFrame": 70 } ],
    "labels": { "S02": ["KICKER", "标题", "辅助文字", "class"] },
    "callouts": [],
    "outro": { "title": ["…", "…"] }
  },
  "audio": {
    "voices": [ { "file": "variants/01/vo/b1.wav", "trimStart": 0.0, "trimEnd": 2.1, "atFrame": 24 } ],
    "music": { "file": "music/…", "gainDb": -14, "fadeInSec": 0.35, "fadeOutSec": 1,
               "ducking": { "threshold": 0.025, "ratio": 8, "attackMs": 15, "releaseMs": 250 } },
    "loudness": { "integratedLufs": -16, "truePeakDb": -1.5, "lra": 11 }
  },
  "output": { "coverFrame": 10 }
}
```

字段来源（`spec` 子命令的转换规则，以 RC2C 实际文件核对后为准）：

| 渲染单 | 现有来源 |
| --- | --- |
| `content.shots`、`subtitles`、`callouts`、`openingEffectId`、`theme` | `variants/<片号>/timeline.json` |
| `content.cover.title`、`outro.title`、`cover.tag` | `timeline.json` 的 `title`、`endtitle`、`tag` |
| `content.cover.image` | `timeline.json` 的 `coverImage`（相对 `variants/<片号>/`） |
| `brand`、`model`、`productName` | `packaging.json` |
| `cover.note`、`labels` | `packaging.json` 的 `variants[片号].coverNote`、`labels` |
| `template.projectCss`、`designDoc` | `tools/style.css`、`DESIGN.md` |
| `audio.voices`、`audio.music` 及参数 | 以 RC2C `media_pipeline.py` 实际读取的文件和参数为准；旧版 `render.py` 用的是 `timeline.json` 的 `voices[]`、`music` |
| `project.baseName` | 命令行 `--base-name`；没给时取 `review/delivery.json` 里该片号的交付文件名；都没有就用片号 |

要求：
- 渲染单只描述「要渲染什么」，不含任何审核结论。
- 渲染单本身和它引用的每个文件都要算哈希，写进清单。
- 参数的默认值等于已验证值，但渲染单里必须显式写出，不靠代码里的隐式默认。

## 6. 命令

入口：`python scripts/reassembled-film/film.py <子命令>`（Windows 用 `python`，需 3.11+）。

| 子命令 | 作用 |
| --- | --- |
| `doctor [--assets 目录]` | 检查 Python 版本、ffmpeg/ffprobe（按 D6 查找）、Node 22+ 与 npx、固定版本的 HyperFrames 能否运行（顺带预热 npx 缓存）、资源哈希是否与模板一致。输出 JSON |
| `templates` | 列出可用模板（id、版本、名称、画幅、元素），供 P1 界面使用 |
| `spec <工程> <片号> [--base-name 名称] [--out 路径]` | 从现有工程只读生成渲染单并校验 |
| `render <渲染单> [--run-id ID] [--progress-json]` | 按第 7 节执行全部阶段 |
| `verify <成片.mp4> --spec <渲染单>` | 对任意成片做第 8 节的技术检查，也能用于已交付的旧成片 |
| `compare <新.mp4> <旧.mp4> --spec <渲染单> [--sheet 输出图]` | 第 9 节的一致性比较，生成并排对比图 |
| `gate <工程> <片号>` | 开场视觉审核闸门（从 `contract.py` 拆出），skill 交付前调用 |

输出约定：
- `--progress-json` 时，每个阶段的开始、完成、失败各打印一行 JSON，例如 `{"stage":"hyperframes","status":"done","elapsedMs":41230}`；
- 最后一行打印结果 JSON：成功时含清单路径和产物路径；失败时含 `stage`、`code`、`message`；
- 退出码：0 成功；2 输入不合法；3 缺少工具或资源；4 渲染或检查失败。

## 7. render 的阶段

输出目录为 `variants/<片号>/renders/<runId>/`，`runId` 取 `YYYYMMDD-HHMMSS-<渲染单哈希前 8 位>`：

```text
renders/<runId>/
  spec.json                 # 本次渲染单副本
  hf/                       # HyperFrames 工程：index.html、assets、media、renders
  audio/                    # narration.wav、premix.wav、final.wav
  review/                   # 无损封面 PNG、检查抽帧
  <baseName>.mp4
  <baseName>-封面.jpg
  checks.json
  render-manifest.json
```

| 阶段 | 内容 | 完成判定 |
| --- | --- | --- |
| 1 校验 | 渲染单格式；技术契约（1080×1440、24 fps、20 帧封面、片长 ≥ 15 秒、时间线连续、单条内不重复、标注合法）；所有输入存在且在允许的根目录内；计算哈希 | 任何一项不过即退出码 2，不建输出目录 |
| 2 准备片段 | 每镜生成 `hf/media/<镜号>.mp4`：从 `inSec` 起截、按 `rate` 变速、缩放裁切到画幅、24 fps、无声；除最后一镜外多留 4 帧给转场（模板里每镜 `data-duration` 多 4/24 秒）。编码参数照 RC2C 的准备步骤 | 每段实际帧数不少于所需帧数；源片不够长直接报错 |
| 3 构建合成 | 调用模板 `build()` 写出 `index.html` 等，复制资源和封面图 | 资源哈希与模板一致 |
| 4 HyperFrames | 用固定版本渲染画面，lint 必须通过；失败时只保留日志最后 40 行 | 产出非空视频，帧数与渲染单一致 |
| 5 边缘修正 | 检查右侧黑条：输出最右若干列明显发黑、而源片对应位置不黑时，按 RC2C 已验证的方法修正，并写进清单 | 修正后检查通过；源片本身边缘就黑的不处理 |
| 6 混音 | 按第 1 节继承的做法：PCM 采样点拼接配音 → BGM 加闪避 → 两遍响度归一 | 每一步的实测时长与片长相差 ≤ 0.02 秒 |
| 7 封装 | 画面加 `final.wav` 封装成 `<baseName>.mp4`；编码参数照 RC2C 最终合成；需要重编码时（边缘修正）在这一步完成 | 文件能完整解码 |
| 8 封面 | 从静帧封面段（默认第 10 帧）导出 `<baseName>-封面.jpg`，无损 PNG 放 `review/`。如果 RC2C 用的是别的取法，以 RC2C 为准 | JPG 与第 0–19 帧一致 |
| 9 检查 | 第 8 节的全部技术检查，写入 `checks.json` | 全部通过才算成功 |
| 10 清单 | 写 `render-manifest.json`：渲染单哈希；模板 id、版本、文件哈希；资源哈希；工具版本（Python、ffmpeg、ffprobe、Node、HyperFrames）；输入文件哈希；各阶段耗时；产物路径、哈希、帧数、时长；检查摘要 | — |

失败处理：任何阶段失败都不写成功结果；已生成的中间文件留在 run 目录里便于排查；不自动重试。

## 8. 技术检查（`verify`）

以 skill `references/delivery.md` 的交付检查为准。阈值优先用 RC2C `validate_final.py` 里的值，括号里是没有现成值时的默认：

- 片长 ≥ 15 秒；1080×1440、24 fps；总帧数等于渲染单。
- 完整解码无错误。
- 视频容器时长与音轨时长相差 ≤ 2 帧（0.0833 秒）。
- 整体响度与真峰值（I 在 −17 到 −15 LUFS 之间，真峰值 ≤ −1.0 dBTP），实测值写进 `checks.json`。
- 第 0–19 帧完全静止，第 0 帧就是完整封面（相邻帧差异接近 0，第 0 帧不是黑帧）。
- 封面 JPG 与静帧封面一致。
- 右侧没有渲染黑条。
- 音轨没有被截断，覆盖全片。

这些只证明技术合格。产品保真、标注落点、口播和画面是否对得上，仍然要人或 Agent 看片。

## 9. 一致性比较（`compare`）与验收锚点

「不做修改直接重新渲染，结果与原片一致」按下面判定：

- 帧数、时长、分辨率、帧率完全相同；
- 抽样帧 SSIM ≥ 0.98：第 0、10、19 帧，每镜入点后第 5 帧和中点，每个贴纸、标注的中点，片尾中点，最后一帧；低于阈值的帧逐个列出，并输出并排对比图；
- 整体响度相差 ≤ 0.5 LU，音轨时长相差 ≤ 1 帧；
- 重新生成的 `index.html` 与原工程当时渲染所用的 `index.html` 逐字节一致；不一致的地方逐条说明原因。

验收样本（Windows 生产机）：
- RC2C 至少 2 条（10-09 交付，HyperFrames 实际渲染）；
- BS619-A v3 静帧封面版 1 条（由更新后的 `packaging.py` 生成）；
- PC673 -03 的合成由 `build_revision.py` 生成，`index.html` 可能与 `packaging.py` 不同，只有确认它也来自 `packaging.py` 时才纳入。

卖点标注（10-11 新增）还没有真实交付样本，由合成素材冒烟测试和现有 Playwright 测试覆盖。

## 11. 交给 P1 的接口

- 工作台在 P1 以子进程调用 `film.py render <渲染单> --progress-json`，按进度行更新界面，按最后一行结果判断成败。
- 渲染单 v1 就是工作台要从数据库生成的格式；`templates` 提供模板列表。
- 安装包和免安装包都不带 `scripts/`（打包禁入清单），所以 P1 只覆盖从仓库启动的桌面版；要进安装包需另行评估。
- P1 还要解决：工作台怎样找到 Python 3.11+（源码启动用系统 Python；免安装包里的 `python-runtime/` 目前只给 LiteLLM 用）；取消与停机（接入 `lib/shutdown.ts` 的停机流程）；交付步骤（`-v2` 命名、旧版移入 `旧版/`、审片页更新）。

## 12. 风险

| 风险 | 应对 |
| --- | --- |
| HyperFrames 或 Chrome 版本不同，导致画面细微差异 | 固定版本，清单记录版本；比较用 SSIM 阈值，不要求逐字节一致 |
| 第 0 步发现各工程脚本做过额外的个性化处理 | 能参数化的放进渲染单；不能的写进附录并告诉用户，不悄悄丢掉 |
| 首次运行 npx 需要联网（内网可能要代理） | `doctor` 负责预热；离线时明确报错 |
| 字体、GSAP 在不同机器上路径不同、版本不同 | 资源根可配置，哈希不符直接拒绝 |
| Windows 路径带空格、中文 | 子进程一律传参数列表，不拼命令行字符串；HyperFrames 按 product-film 的方式直接调用 `npx-cli.js` |
| 每条多一次片段准备和检查，渲染变慢 | 记录各阶段耗时，验收时报告；P0 不做并行优化 |
