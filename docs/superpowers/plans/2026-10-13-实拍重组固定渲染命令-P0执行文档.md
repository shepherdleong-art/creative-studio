## 0. 目标

把成片的最后一段（包装、HyperFrames 渲染、混音、封面、技术检查）做成一条不依赖 Agent 的固定命令。

- **第一阶段（本期必须完成）**：现行技能包装（下称 classic：静帧封面、贴纸、卖点标注、片尾）作为第一个模板。验收锚点：拿现有成片的工程，不做任何修改直接重新渲染，结果与当初交付的成片一致（标准见第 9 节）。
- **第二阶段（第一阶段验收后做）**：技能也能选用工作台的四套模板（A 花字种草、B 手账拼贴、C 极简高级、D 综艺撕纸）。
- **贯穿两阶段**：仓库只保留一份 HyperFrames（`packaging/`，锁文件固定版本），工作台和本命令共用；模板资源都放进仓库；渲染核心写成 `lib/` 里的 TypeScript 函数，P1 工作台可以直接导入、放进自己的任务调度。

完成后，Agent 出片和以后工作台的再次导出（P1）都调用这条命令，两边结果一致；同一份输入重复渲染，得到同样的成片。

旧版 `reassembled-film-render.py` 里已验证、要原样继承的混音做法：
- 逐句配音按 48kHz 单声道 PCM16 在采样点上拼接。多输入 adelay/amix 链曾在实测中被截断成封面长度（0.833 秒），这是有意的规避；
- BGM `-14 dB`，`sidechaincompress=threshold=0.025:ratio=8:attack=15:release=250` 由配音压低，淡入 0.35 秒、淡出 1 秒；
- 两遍 `loudnorm` 到 `I=-16:TP=-1.5:LRA=11`；
- 每一步都核对实际音频时长，防止截断。

已知的坑：
- RC2C 实测 HyperFrames 输出右侧有 8 像素黑条；当时核对源素材边缘正常后，在最终合成时去掉。
- HyperFrames lint：`letterSpacing` 动画判错；没有 `@font-face` 的回退字体判错；故意重叠的元素要逐个加 `data-layout-allow-overlap="true"`。
- Windows 上旧版 ffprobe-static 在多层管道里会卡在输出末尾（修复前测 8 次卡 2 次，见 `docs/2026-10-13-视频包装迁移.md`）。本命令调 HyperFrames 时必须照 `package-video.mjs` 的做法用 `node --require <packaging/win-hide-spawn.cjs>` 注入（走命令行参数，不能走 NODE_OPTIONS，否则中文路径会出错），并设 `CREATIVE_STUDIO_PACKAGING_WORK_ROOT`（这个修复用它放探针临时文件）。本命令自己调 ffprobe 时通过文件描述符把 stdout/stderr 直接写临时文件，退出后读取，不使用匿名管道；2026-10-14 实测内置 macOS ffprobe 4.4 不支持原定 `-o`，用户已批准此兼容调整及 `lib/spawn-hidden.ts` 的 stdio 类型重载。
- HyperFrames 收尾探针偶尔超时，报 `ffprobe deadline`。工作台的处理是重跑一次，本命令照做；其他失败不重试。
- 不要用 `runExportVideo`：有 NVIDIA 显卡的机器上它会改用 NVENC，同一份输入在不同机器上编码结果不同。
- 命令行入口必须先设好 `CREATIVE_STUDIO_DATA_ROOT`、`CREATIVE_STUDIO_PACKAGING_DIR`，再动态 `import` lib 模块（写法照 `scripts/packaging-render.test.ts:9–12`）。
- `contract.py` 用到 `hashlib.file_digest`，要 Python 3.11+（本机用 `~/.local/bin/python3.12`）。生成金样和跑旧测试时需要。
- macOS 沙箱里 Playwright 启动浏览器会因权限失败，需要提权重跑。
- Windows 上写文件可能被读取者或杀毒软件短暂占用（EPERM/EBUSY），参照 `scripts/reassembled-film/runtime.mjs` 的有限重试。
- `packaging/_t-verify.mjs` 写死了 `chrome-headless-shell.exe`，只能在 Windows 上跑。

## 5. 模板约定

```text
packaging/templates/classic/1/
  template.json                       # 模板身份、画幅、元素、资源哈希
  assets/fonts/SourceHanSansCN-VF.ttf
  assets/scripts/gsap.min.js          # 3.14.2，不能换成四套模板用的 3.15.0
lib/film-render/templates/classic-v1.ts   # build(spec, outDir)：写出 index.html 等
```

`template.json` 示例：

```json
{
  "id": "classic",
  "version": "1",
  "kind": "composition",
  "displayName": "现行包装（静帧封面、贴纸、卖点标注、片尾）",
  "canvas": { "width": 1080, "height": 1440, "fps": 24, "introFrames": 20 },
  "elements": ["cover", "sceneTransition", "subtitles", "labels", "callouts", "outro"],
  "assets": {
    "assets/fonts/SourceHanSansCN-VF.ttf": "25a01e41b5cc99893eb35a6cd2cc7611841dc19eb03cbaf7f0c1de8210f2ba0b",
    "assets/scripts/gsap.min.js": "c174bfce53a729418d57a8ad8625e7247c793a22fef8e2851e3cfa3de9cd8280"
  }
}
```

约定：
- 目录结构保持 `assets/fonts`、`assets/scripts`，这样 Python `packaging.py --assets packaging/templates/classic/1` 也能直接用它生成金样。
- 构建器只读渲染单和模板目录，只写输出目录；同样的输入必须产出逐字节相同的 `index.html`。
- 样式分两层：模板自带的结构和动效（含标注样式），加上工程级 `tools/style.css`（按产品调整的字体、配色、字号）。工程样式照现在的顺序追加在后面，可以覆盖。
- classic 是"整片合成"模板：视频片段、转场、字幕、贴纸、标注、封面、片尾都在 HTML 里，音频不进 HyperFrames，视频元素全部 `muted`。四套模板是"叠层"模板（第 11 节），两类模板共用渲染单的公共部分。
- "贴纸"就是 `packaging.json` 里逐镜的 `labels`（kicker、主标题、辅助文字），用户已于 2026-10-13 确认。
- 新模板按同样的方式接入，用不同的 `id`；至少要有构建快照测试和合成素材冒烟测试。

**TypeScript 移植要逐字节复现 Python 的输出格式：**
- Python 把浮点数转成字符串时，整数值带 `.0`（`96/24` 输出 `4.0`），JS 输出 `4`；数值很小或很大时，两边切换科学计数法的界限也不同。要写一个与 Python `repr(float)` 一致的格式化函数。
- `{x:.6f}` 对应 `toFixed(6)`，正好落在两个值中间时两边舍入规则不同，靠金样测试兜底。
- `json.dumps` 默认在逗号、冒号后面加空格（`{"cx": 430, "cy": 600}`），`JSON.stringify` 不加；默认还会把非 ASCII 字符转义成 `\uXXXX`，`meta.json` 用的是 `ensure_ascii=False`。
- `html.escape` 会把单引号转成 `&#x27;`。
- 输入 JSON 里写成 `430.0` 的数，Python 会原样输出 `430.0`，而 JS 解析后分不出来。需要时用 `JSON.parse` 回调里的 `context.source` 保留原始写法。

## 6. 渲染单（render spec v1）

一次渲染的全部输入放在一个 JSON 里。`spec` 子命令从现有工程生成它；P1 由工作台从数据库生成同样的格式。路径写绝对路径或相对 `project.root` 的路径，都必须落在 `project.root` 里。

```json
{
  "schemaVersion": 1,
  "project": { "root": "I:/m7-studio/outputs/<工程>", "variant": "01", "baseName": "<开工日期>-<店铺>-<型号>-<生产类型>-<制作人>-01" },
  "canvas": { "width": 1080, "height": 1440, "fps": 24, "introFrames": 20, "frames": 432 },
  "template": { "id": "classic", "version": "1" },
  "shots": [ { "id": "O01", "file": "variants/01/clips/O01.mp4", "startFrame": 20, "endFrame": 96, "inSec": 0.3, "rate": 1 } ],
  "subtitles": [ { "text": "…", "startFrame": 24, "endFrame": 70 } ],
  "audio": {
    "voices": [ { "file": "variants/01/vo/b1.wav", "trimStart": 0.0, "trimEnd": 2.1, "atFrame": 24 } ],
    "music": { "file": "music/…", "inSec": 0, "gainDb": -14, "fadeInSec": 0.25, "fadeOutSec": 1,
               "ducking": { "threshold": 0.025, "ratio": 8, "attackMs": 15, "releaseMs": 250 } },
    "loudness": { "integratedLufs": -16, "truePeakDb": -1.6, "lra": 11 }
  },
  "classic": {
    "projectCss": "tools/style.css", "designDoc": "DESIGN.md",
    "theme": "…",
    "cover": { "image": "variants/01/…/cover.png", "title": ["…", "…"], "tag": "…", "note": "…",
               "brand": "…", "model": "…", "productName": "…" },
    "labels": { "S02": ["KICKER", "标题", "辅助文字", "class"] },
    "callouts": [],
    "outro": { "title": ["…", "…"] }
  },
  "output": { "coverFrame": 16 }
}
```

`template.id` 为 `classic` 时必须有 `classic` 段；第二阶段的四套模板改用 `packaging` 段（第 11 节）。

字段来源（`spec` 的转换规则，以 RC2C 实际文件核对后为准）：

| 渲染单 | 现有来源 |
| --- | --- |
| `canvas`、`shots`、`subtitles`、`classic.callouts`、`classic.theme` | `variants/<片号>/timeline.json` |
| `classic.cover.title`、`classic.outro.title`、`classic.cover.tag` | `timeline.json` 的 `title`、`endtitle`、`tag` |
| `classic.cover.image` | `timeline.json` 的 `coverImage`（相对 `variants/<片号>/`） |
| `brand`、`model`、`productName` | `packaging.json` |
| `classic.cover.note`、`classic.labels` | `packaging.json` 的 `variants[片号].coverNote`、`labels` |
| `classic.projectCss`、`classic.designDoc` | `tools/style.css`、`DESIGN.md` |
| `audio.voices`、`audio.music` 及参数 | 以 RC2C `media_pipeline.py` 实际读取的文件和参数为准；旧版 `reassembled-film-render.py` 用的是 `timeline.json` 的 `voices[]`、`music` |
| `project.baseName` | 命令行 `--base-name`；没给时取 `review/delivery.json` 里该片号的交付文件名；都没有就用片号 |

要求：
- 校验规则照 `contract.py:16–32`（画幅、15 秒以上、时间线从第 20 帧连续、单条内不重复、标注合法），另加：所有输入存在且落在 `project.root` 内；配音为 48kHz 单声道 PCM16 WAV，放置后不重叠、不超片尾。
- 渲染单只描述"要渲染什么"，不含任何审核结论（开场审核在 `gate`）。
- 渲染单本身和它引用的每个文件都要算哈希，写进清单。
- 参数的默认值等于已验证值，但渲染单里必须显式写出，不靠代码里的隐式默认。

## 7. 命令

入口：`node scripts/film-render.ts <子命令>`。在任意目录运行都可以，入口自己定位仓库根。

| 子命令 | 作用 |
| --- | --- |
| `doctor` | 检查：Node 版本；ffmpeg/ffprobe 的实际路径和版本（`CREATIVE_STUDIO_FFMPEG` 无效而被静默回退时报警告）；`packaging/` 运行时——`package.json` 声明、锁文件、已安装的 HyperFrames 三处版本一致，Chrome 可执行文件存在，HyperFrames 内置的 `CHROME_VERSION` 等于安装脚本的 buildId；每个模板的资源哈希与 `template.json` 一致。输出 JSON |
| `templates` | 列出可用模板（id、版本、类别、名称、画幅、元素），供 P1 界面使用 |
| `spec <工程> <片号> [--base-name 名称] [--out 路径]` | 从现有工程只读生成渲染单并校验；`--out` 目标已存在则拒绝，不给就输出到 stdout |
| `render <渲染单> [--run-id ID] [--progress-json]` | 按第 8 节执行全部阶段 |
| `verify <成片.mp4> --spec <渲染单>` | 对任意成片做第 9 节的技术检查，也能用于已交付的旧成片 |
| `compare <新.mp4> <旧.mp4> --spec <渲染单> [--ssim 阈值] [--sheet 输出图]` | 第 9 节的一致性比较，生成并排对比图 |
| `gate <工程> <片号>` | 开场视觉审核闸门：把 `contract.py:16–17`、`:33–44` 的规则移植成 TS，结论与原实现一致；skill 交付前调用 |

输出约定：
- 带 `--progress-json` 时，每个阶段的开始、完成、失败各打印一行 JSON，例如 `{"stage":"hyperframes","status":"done","elapsedMs":41230}`；
- 最后一行打印结果 JSON：成功时含清单路径和产物路径；失败时含 `stage`、`code`、`message`；
- 退出码：0 成功；2 输入不合法；3 缺少工具或资源；4 渲染或检查失败。

核心 API（供 P1 导入）：`renderFilm({ spec, runDir, signal, onStage })`，返回清单对象。命令行入口只负责参数、目录、环境变量、进度行和退出码。

## 8. render 的阶段（classic）

输出目录为 `variants/<片号>/renders/<runId>/`，`runId` 取 `YYYYMMDD-HHMMSS-<渲染单哈希前 8 位>`：

```text
renders/<runId>/
  spec.json                 # 本次渲染单副本
  hf/                       # HyperFrames 工程：index.html、assets、media、renders
  audio/                    # narration.wav、premix.wav、final.wav
  review/                   # 无损封面 PNG、检查抽帧
  <baseName>.mp4
  <baseName>-封面.jpg
  checks.json
  render-manifest.json
```

| 阶段 | 内容 | 完成判定 |
| --- | --- | --- |
| 1 校验 | 第 6 节全部规则；计算哈希 | 有一项不过就退出码 2，不建输出目录 |
| 2 准备片段 | 每镜生成 `hf/media/<镜号>.mp4`：从 `inSec` 起截、按 `rate` 变速、缩放裁切到画幅、24 fps、无声；除最后一镜外多留 4 帧给转场（模板里每镜 `data-duration` 多 4/24 秒）。编码参数照附录 A | 每段实际帧数不少于所需帧数；源片不够长直接报错 |
| 3 构建合成 | 调用 `classic-v1.ts` 写出 `index.html`、`meta.json`、`hyperframes.json`，复制资源、`DESIGN.md` 和封面图 | 资源哈希与 `template.json` 一致 |
| 4 HyperFrames | 用 `packaging/` 运行时渲染画面，参数照附录 A（预计 `--fps 24 --quality looks`）；环境变量设 `HYPERFRAMES_BROWSER_PATH`（`packaging/runtime/` 的 Chrome）、`HYPERFRAMES_FFMPEG_PATH`、`HYPERFRAMES_FFPROBE_PATH`、`HYPERFRAMES_SKIP_SKILLS=1`、`HYPERFRAMES_NO_AUTO_INSTALL=1`、`HYPERFRAMES_NO_TELEMETRY=1`；Windows 修复按第 2 节注入。lint 必须通过；失败时只保留日志最后 40 行 | 产出非空视频，帧数与渲染单一致 |
| 5 边缘修正 | 检查右侧黑条：输出最右若干列明显发黑、而源片对应位置不黑时，按附录 A 的方法修正，并写进清单 | 修正后检查通过；源片本身边缘就黑的不处理 |
| 6 混音 | 按第 2 节继承的做法：PCM 采样点拼接配音 → BGM 加闪避 → 两遍响度归一。WAV 读写自己实现，要逐块解析 RIFF，不能假定文件头固定 44 字节 | 每一步的实测时长与片长相差 ≤ 0.02 秒 |
| 7 封装 | 画面加 `final.wav` 封装成 `<baseName>.mp4`；编码参数照附录 A；需要重编码时（边缘修正）在这一步完成 | 文件能完整解码 |
| 8 封面 | 从静帧封面段（默认第 10 帧）导出 `<baseName>-封面.jpg`，无损 PNG 放 `review/`。RC2C 若用别的取法，以 RC2C 为准 | JPG 与第 0–19 帧一致 |
| 9 检查 | 第 9 节的全部技术检查，写入 `checks.json` | 全部通过才算成功 |
| 10 清单 | 写 `render-manifest.json`：渲染单哈希；模板 id、版本、构建器与资源的哈希；工具版本（Node、ffmpeg、ffprobe、HyperFrames、Chrome，以及 `packaging/package-lock.json` 的哈希）；输入文件哈希；各阶段耗时；产物路径、哈希、帧数、时长；检查摘要 | — |

失败处理：任何阶段失败都不写成功结果；已生成的中间文件留在 run 目录里便于排查；除 `ffprobe deadline` 重跑一次外，不自动重试。

需要读 stderr 的 ffmpeg 调用（loudnorm 第一遍、响度测量、SSIM）用 `spawnHidden(resolveFfmpegPath(), …)` 自己捕获输出，并支持 AbortSignal；其余调用用 `runFfmpeg`。

## 9. 技术检查（`verify`）与一致性比较（`compare`）

技术检查以 skill `references/delivery.md` 的交付检查为准。阈值优先用 RC2C `validate_final.py` 里的值，括号里是没有现成值时的默认：
- 片长 ≥ 15 秒；1080×1440、24 fps；实际解码出的帧数等于渲染单。
- 完整解码无错误。
- 视频容器时长与音轨时长相差 ≤ 2 帧（0.0833 秒），音轨覆盖全片。
- 整体响度与真峰值（I 在 −17 到 −15 LUFS 之间，真峰值 ≤ −1.0 dBTP），实测值写进 `checks.json`。
- 第 0–19 帧完全静止，第 0 帧就是完整封面（相邻帧差异接近 0，第 0 帧不是黑帧）。
- 封面 JPG 与静帧封面一致。
- 右侧没有渲染黑条。

这些只证明技术合格。产品保真、标注落点、口播和画面是否对得上，仍然要人或 Agent 看片。

一致性比较——"不做修改直接重新渲染，结果与原片一致"按下面判定：
- 帧数、时长、分辨率、帧率完全相同；
- 抽样帧 SSIM ≥ 0.98（`--ssim` 可调；同一份渲染单重复渲染用 0.99）：第 0、10、19 帧，每镜入点后第 5 帧和中点，每个贴纸、标注的中点，片尾中点，最后一帧。低于阈值的帧逐个列出，并输出并排对比图；
- 整体响度相差 ≤ 0.5 LU，音轨时长相差 ≤ 1 帧；
- 重新生成的 `index.html` 与原工程当时渲染所用的 `index.html` 逐字节一致；不一致的地方逐条说明原因。

## 11. 第二阶段：技能调用四套模板

第一阶段验收后再做。设计已在 2026-10-14 的讨论中定好，要点如下；开工前按当时的代码再核对一遍。

- **怎么渲**：四套模板是叠层模板。命令先渲底片（20 帧封面图 + 正文硬切 + 字幕），再调用 `renderVideoPackaging()` 套包装，和工作台是同一份代码。混音照第一阶段的技能链路。
- **字幕**：用批量生产的画法（`textStyleToSvgElements` + sharp，参照 `batch-renderer.ts:780`，不要从批量模块导入）和默认样式 `defaultTextStyle('subtitle', 1080)`。默认字体是系统字体（Mac 苹方、Windows 微软雅黑），同一台机器结果固定，跨机器字形不同。
- **渲染单**：`template.id` 为 `overlay-poster`、`overlay-journal`、`overlay-minimal`、`overlay-variety` 之一，配 `packaging` 段。`packaging` 段直接用 `FinalEditPackagingConfig` 的字段（`enabled`、`template`、`varsOverrides` 里的 `title`/`subtitle`/`point1`–`point3`、`pointCuesMode`、`pointCues`、`layouts`），用 `sanitizePointCues`、`sanitizePackagingLayouts` 校验，清洗后有变化就判为不合法。主副标题必须非空（模板遇到空标题会渲出"标题需修改"占位字）；第二阶段不支持字体槽。
- **技能写法**：在 `packaging.json` 的 `variants[片号]` 下新增 `packaging` 段：`template`、`title`、`subtitle`、`coverPoints`（最多 3 条）、`bodyCues`（带帧区间的正片卖点）、`layouts`。`spec` 用 `postProcessTimedCues` 和 `sanitizePointCues` 把 `bodyCues` 转成 `pointCues`，调整过的条目逐条报告；不按口播自动提取或对齐卖点。
- **编码**：片段用无损 `-qp 0`，叠好字幕的底片用 `-crf 12`，最终编码由包装管线完成（`-crf 18 -preset veryfast`，不动）。
- **检查**：第 0 帧是完整封面、第 0–15 帧静止（取决于第 14 节的确认）；第 10 帧与无包装封面明显不同（SSIM < 0.98），证明包装确实生效。
- **验收**：四套模板的合成素材端到端在 macOS、Windows 上通过；同一份渲染单渲两次比较通过；一条真实工程用四套模板各出一版交用户看片。
- **skill**：规划阶段可在 classic 和四套模板中选择；选四套模板时，圆点引线标注、贴纸、片尾不可用，正片卖点改用模板的卖点标签。

## 12. 交给 P1 的接口

- 工作台在自己的 worker 里直接调用 `renderFilm()`，传入 AbortSignal 和进度回调，并发由工作台的队列决定；不需要 Python，也不需要另起子进程。
- 渲染单 v1 就是工作台要从数据库生成的格式；`templates` 提供模板列表。
- classic 的 TS 构建器可以直接给第五步做 classic 包装预览（和四套模板一样把 HTML 放进 iframe），需求共识第 8 节要求的"第五步能否忠实预览 HyperFrames 包装"有了基础。
- 渲染这一环不再把 P1 限制在从仓库启动的桌面版：核心在 `lib/`，被应用路由导入后会进 standalone，`packaging/` 运行时和 classic 资源都随安装包发布。命令行入口在 `scripts/`，只供技能从仓库调用。P1 是否支持安装版，仍取决于数据根一致等其他条件。
- P1 还要解决：写回交付目录、`-v2` 命名、旧版移入 `旧版/`、审片页更新；技能成片文件名和工作台 J/K/A–D 编号的关系（四种开头 ID 与 `BUILTIN_OPENING_CODES` 完全对应；classic 没有包装字母）；工作台包装任务和本命令同时渲染时争抢资源（都会起多路 Chrome）；接入 `lib/shutdown.ts` 的停机流程。

## 14. 待用户确认（第二阶段，不影响第一阶段开工）
