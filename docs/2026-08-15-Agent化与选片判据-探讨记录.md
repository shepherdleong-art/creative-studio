# Agent 化与选片判据 — 探讨记录

日期：2026-08-15
性质：**探讨记录 + 现状盘点**，不是执行文档。结论中标注了「已核实」与「判断/建议」，后者需要落地前再确认。
起点问题：能否把 Creative Studio 做成 MCP 供 agent 调用（甚至内嵌 agent），实现「投喂一张需求表 → 全自动产出并导出」。

---

## 0. 一句话结论

**MCP 那层本身不难，两三天的事。真正的卡点有两个：**

1. **系统从未记录过任何一次「否决」** —— 没有合格线，agent 无从判断，也无法回测。
2. **图片 prompt 没有模板机制** —— 隐性约束全靠手打，agent 接手第一天质量就会崩。

而第 2 点的解法，同时解决了大半个第 1 点。详见第 6、7 节。

**目标应修正为**：不是「全程无人干预」，而是**「自动跑完 + 最后一次集中审片」**。这个目标现在就够得着。

---

## 1. 现状盘点：已经具备的地基（已核实）

三件事决定改造是「薄封装」还是「大重构」，三件都在正确的一边。

### 1.1 业务逻辑在服务端，不在 UI 里

- `lib/` 约 **38,000 行** vs `components/` 约 **16,700 行**
- **120 个 API route**，基本都是 DB + queue 的薄壳
- 无任何鉴权层（纯 localhost 裸跑）

含义：agent 调 API 拿到的能力和人点 UI 拿到的是同一套，不存在「关键判断只活在 React state 里」。这是最容易搞砸的一点，没搞砸。

风险面：无鉴权意味着一旦接入 agent，防线只剩「输入是否可信」。

### 1.2 `batch-production` 里已有一台自主执行引擎

`lib/batch-production/scheduler.ts`（653 行）提供：

- `claimNextTask` / `renewLease` / `hasValidLease` / `expireStaleLeases`
- `recoverInterruptedWork` / `settleInterruptedTask`
- `retryTask` / `pauseBatch` / `resumeBatch` / `pauseTask` / `resumeTask` / `cancelTask` / `stopBatch`

已注册的 8 种 workType：
`asset_prepare` / `script_snapshot` / `semantic_score` / `narration` / `proxy_request` / `proxy_generate` / `render` / `output_version`

**这是本项目相对同类工具的核心资产。** agent 最不擅长盯长任务，而这里 agent 只需「下单 + 轮询」，重试与崩溃恢复由调度器承担。

### 1.3 共享盘素材挂载能力已存在

- `lib/batch-production/media-catalog.ts:393` → `registerLinkedSource`
- 出口：`POST /api/desktop/import-linked`（按 `filePath` 登记，不拷贝）

粒度是「单文件」，目录枚举需调用方自己做——对 agent 而言不是问题。

## 2. 三个缺口

### 缺口 A：选片判据（本次讨论主体，见第 5–7 节）

### 缺口 B：没有统一状态视图

- `lib/project-status.ts` 共 **24 行**，只查 `jobs` 一张表，产出 `completed / needs_check / partial_failed / draft`
- `video_jobs`、final-edit jobs、batch `tasks` **全都不覆盖**

**准确表述：这个「统一视图」目前存在于操作者脑子里，不存在于系统里。** 人切三个 tab 各扫一眼在脑内拼装，这个动作没有任何代码承载，agent 继承不到。

判断：实现难度不大，人和 agent 同时受益，且它会逼迫「一次生产跑到哪一步」在数据层被定义清楚——那个定义正好是缺口 C 的骨架。

> 用户意见（2026-08-15）：认同缺口成立，但**实现难度不大，优先级让位于选片**。

### 缺口 C：没有 run manifest

一张需求表派生出的 project / shot_sets / jobs / batch version 之间没有共同凭证。后果：

- agent 中途挂了，重启后不知道干到哪
- 分不清哪些是 agent 建的、哪些是人手工建的
- **无法设预算闸门**

关于预算：`jobs.estimatedCost` 已存在，manifest 上加 `maxCost` 上限、超限即停并询问人，改动很小但**不能不做**——能无人值守下 500 个 job 的 agent 就是个漏钱的水龙头。

## 3. 关键纠正：视觉判断能力**已经存在并在生产中运行**

讨论中一度把「选片」当成从零开始的能力空白，这是错的。

### 3.1 现有链路（已核实）

- `lib/media-core/adapters/video-analysis-prompt.ts` —— 按场景抽帧（每段 **30% 位置一帧**）送视觉模型
- `BatchContentAnalysisResult`（`lib/batch-production/executors.ts:78`）产出：

  ```
  summary / sellingPoints / semanticTags
  usableRanges[{startUs, endUs, qualityScore}]
  qualityIssues[] / coverFrameTimesUs[]
  scenes[{startUs, endUs, description, labels, qualityScore}]
  ```

- 工程保障齐全：供应商必须 `supportsVision`；模型 / `executionScope` 变更即报错重做；内容指纹变更拒绝发布；company 域走 COS 受控传输且 fail-closed（`provider-execution-gate.ts`）

**这不是原型，是带指纹校验和审计的生产级管线。**

### 3.2 但它接错了地方、性质也不对

| 问题 | 现状 | 需要 |
|---|---|---|
| 作用对象 | 只作用于**混剪素材池里的视频**（batch assets） | 生成环节的**候选产物**（场景图 / 分镜图 / 图生视频结果） |
| 判据性质 | `qualityScore`，用于池内**排序**的相对分 | **合格 / 不合格**的绝对裁决 |

**排序器 vs 闸门的区别很要命**：排序永远有第一名，哪怕全是废片；闸门可以全毙掉并触发重 roll。

**用户要的是闸门。** 原话就是「如何判断这张图**能用**」，不是「哪张**更好**」。

### 3.3 「正确与否」必须是对照判断，不能是绝对判断

单给模型一张图问「这张对不对」，它答不了——**没有基准**。模型不知道你家 A 型号该长什么样，也不知道这家店铺要白底还是场景底。这么设计出来的东西会很自信地瞎猜，而且无人值守时发现不了。

正确问法：**「这张候选图和原始产品图相比，产品是不是同一个？有没有变形、掉细节、logo 糊？场景是否符合 XX 要求？」**

基准在库里是现成的：`jobs.inputImageId`（原始产品图）+ `jobs.referenceImageIds`（场景参考图）+ 需求表里的型号/卖点/店铺规范。

**关键交叉验证：`shot_gen` 输出 104 张 = `shot_result_candidates` 104 条**，一一对应，没有任何生成结果被删过。

### 4.1 一处需要记录的纠错

讨论中我先给出过「**52% 的分镜被重 roll 过**」——**这个数字是错的**。当时的查询用 `jobs.inputImageId = shots.sourceImageId` 关联，把 `scene_gen` 的 job 也算了进去。

**正确结论：只有 11/88 ≈ 12.5% 的分镜生成过第二次。一次过率约 87.5%。**

（后续任何基于「重 roll 频繁」的推论都应作废。）

### 4.2 最要命的发现

- **`reviewMark` 字段 100 个分镜全部为空，从未使用过**
- 视频侧 `succeeded` 只表示**接口返回了视频**，不代表人认为可用

> **这套系统从头到尾，从来没有记录过任何一次「否决」。**

不是判据没写下来，是**连写判据的原材料都没在采集**。每次看到废片，动作是重新生成，那个「为什么不行」的判断在脑子里闪半秒就消失了。

连带后果：**没有标注集 ⇒ 没法回测 AI 判得准不准。**

### 4.3 一个待验证的反向解读

87.5% 一次过，也可能不是质量真的好，而是**重 roll 太费事所以将就了**。这两种情况对应完全不同的合格线。目前无法区分。

## 5. 用户给出的真实失败模式

讨论中用户直接口述了判据（证明隐性知识是说得出来的，只是从没被问过）：

1. **尽量少用特写图** —— 特写有时会「显示错误」，生成奇怪的东西，例如**变成全景**，与参考图/实际场景相差极大
2. **产品摆放位置与参考图不一致时会出偏差** —— 例如**柜子直接嵌进床垫里面**（穿模 / 空间关系错误）

同时明确：图片侧 bug 很少；场景图基本一次 pass；分镜图历史上的主要缺陷是**后端把图一图二接反**导致不按提示词走，**已修复**。

### 5.1 两个失败模式的可检测性差一个量级

| | 特写变全景 | 柜子嵌床垫 |
|---|---|---|
| 问题性质 | 景别失控（粗粒度分类） | 三维空间关系 / 物理合理性 |
| 模型检出率 | **高**（远好于「美不美」） | **低**——画面在纹理光影上自洽，崩的是空间逻辑，模型常「看着挺协调」就放过 |
| 有无基准可对照 | 有（产品占画面比可量化） | **无**——不能问「和参考图一样吗」，因为场景本来就要求换掉 |
| 建议解法 | **输入端拦截**（见第 6 节） | 输入端压低发生率 + **剩余交人眼** |

**结论：柜子嵌床垫这类空间错误，输出端自动检测目前是弱项，建议明确「认了」。** 靠输入约束把发生率压下去，漏网的交给最后一次集中审片；因为发生率本来就低，人工成本可接受。

---

## 6. 关键转向：输入端约束 > 输出端检测

用户自己已经给出了答案——**「尽量少用特写图」是一条输入约束，不是验收判据。**

在输入端拦掉，比生成完再判**便宜一个量级**：不用等生成、不花 API 钱、不用重 roll、不会有漏网。

**这类知识应固化进配方（prompt 模板 + 需求表 schema），而不是变成一条「生成后检查是否变成全景」的规则。**

## 7. 最高优先级发现：SOP 已经写在 `jobs.prompt` 列里

### 7.1 已涌现的模板（从历史 prompt 中提取）

```
图1 是待编辑分镜图，是本次修改的主要对象。
图2 是场景参考图。
请参考图2的空间风格、光线、墙面、软装和布置，重绘图1的场景。
保持图1中的{沙发 / 实木床}结构、模特姿态、主体位置和画面构图尽量一致。
```

以及场景图侧：

```
基于图1生成新的{沙发 / 室内产品}场景图。保留适合{...}展示的空间关系，
重构墙面、软装、灯光、窗帘、地面和整体氛围，使画面更适合电商生活方式图。不要添加文字。
```

### 7.2 两个观察

**（1）防穿模的手段早就被发明了，但没系统化。**

`保持图1中的…主体位置和画面构图尽量一致` —— 这句就是在防「柜子嵌进床垫」。用户早已发现产品摆放一偏就会崩，所以加了这句。但它现在依赖**每次手打时记不记得加**，不是系统保证。

同理「全景图」三个字——景别控制也是靠手打。

**（2）图片 prompt 完全没有模板机制。**

- 库里只有 `video_prompt_templates`（5 条，视频用）
- 图片侧 prompt 从 request body 直接传入自由文本（`app/api/shot-sets/[id]/apply-scene/route.ts:16`）
- **视频有模板，图片没有**

### 7.3 建议的模板槽位

| 槽位 | 取值 | 作用 |
|---|---|---|
| 产品品类 | 沙发 / 实木床 / 柜子… | 目前手打替换的那个词 |
| **景别** | **全景（默认）/ 中景 / 特写（需显式开启）** | 把「少用特写」变成系统默认，不靠记性 |
| 一致性约束 | 结构 / 模特姿态 / 主体位置 / 画面构图 | **固定不可删**，防穿模 |
| 场景重构范围 | 墙面 / 软装 / 灯光 / 窗帘 / 地面 | 已在使用的那串 |

### 7.4 为什么这是 agent 化的**前提**而不是优化项

**agent 填槽位是可靠的；agent 自由写 prompt 是灾难。**

现有的自由文本 prompt 交给 agent，第一天质量就会崩——不是 agent 笨，是它没有人手打时脑子里那些没说出口的约束。**模板把隐性约束变成结构，agent 才有得可依。**

## 8. 修正后的自动化目标

> **不是「全程无人干预」，是「自动跑完 + 最后一次集中审片」。**

agent 从需求表一路跑到导出，中间不停；人只在最后打开一个界面，把这一批产出一次性过一遍，挑出崩的重 roll。

与原设想的实际差别不大——**因为现在的干预是分散在五个步骤里等着的，改成集中在最后一次**，实际投入时间预计降 80% 以上。且该目标**当前即可达成**，不依赖任何「万能判官」。

## 9. MCP 层的设计要点（尚未动工）

### 9.1 先做 MCP server，后做内嵌 agent

理由不是简单，而是**它是个逼真的检验**：拿 Claude Code 当外部 agent，喂真实需求表，看能否跑通到导出。跑不通的地方就是 API 语义不够自解释的地方——这个反馈在自己写内嵌 agent 时拿不到（会下意识把知识塞进 prompt 绕过去）。

外部 agent 稳定跑通后，内嵌 agent 就只是「同一套工具 + 一个循环 + 一个 UI」，风险已出清。

### 9.2 工具粒度：**不要 1:1 映射 120 个 route**

工具一多，agent 选择准确率会显著下降。正确粒度是**一个工具对应一个人类决策点**，约 12 个：

```
建项目 / 挂载共享盘素材 / 出场景图 / 出分镜图 / 选片 /
生成脚本 / 图生视频 / 建批次 / 启动 / 查状态 / 导出 / 自检
```

**MCP 层不是转发器，是一层新的编排门面**——需要把「apply-scene → run queue → 轮询至 succeeded」这类多步序列收成一个工具。代码量不大，但设计要花心思。

## 10. 视频可用性判断的技术选项

现状：每场景抽 **1 帧**（30% 位置）。

**能抓到**：单帧内硬伤——手指数量、结构崩坏、糊、构图崩、产品明显变形。

**抓不到**：**时间维度问题**——运动中途形变、logo 转动时融化、突然多一只手又消失、闪烁抖动、物理不合理运动。**这些在任何单帧上看都可能正常。**

三个层次，成本递增：

1. **ffmpeg 帧间差分**（`ssim` / `signalstats` 滤镜）——纯 CV，不用模型，便宜且确定；突变尖峰即闪烁/跳变信号。**适合第一道粗筛**，ffmpeg 链路现成。
2. **密集抽帧送序列**——如每 0.5s 一帧，一次给模型 8–16 帧。`lib/media-core/scene-detect.ts` 已有分段能力，改造量不大。
3. **原生视频理解模型**——最准，取决于供应商是否支持直接吃视频。

**但最有价值的检测不是通用「找畸变」，而是：产品在整段视频里是否始终是同一个产品。** 抽 N 帧逐帧与原始产品图对照，问「还是同一个东西吗 / logo 完整吗 / 比例对吗」，对不上的那一帧就是形变位置。这比泛泛找畸变准得多——**又回到对照判断而非绝对判断**。对电商场景而言，产品走样是唯一不能容忍的硬伤。

## 11. 待写文档的建议结构

用户将另行整理 SOP 文档。建议分三块，性质不同，**不要混写**：

1. **配方约束**（硬规则，直接固化进模板与需求表 schema）
   —— 大部分内容应落在这里：景别白名单、一致性约束、各品类措辞、一次导入多少张、模特图/场景图顺序。**写完可直接变代码。**

2. **验收判据**（必须看图才能判的）
   —— 应该很短。按目前描述可能只有「产品走样」「空间穿模」两条。

3. **已知无法自动判定的**（明确交人）
   —— 诚实列出。不是失败，是给最后那道集中审片划范围。

## 13. 建议的推进顺序（判断，非定论）

1. **图片 prompt 模板化**（第 7 节）—— agent 化的前提，且同时压低两类失败模式
2. **用户整理 SOP 文档**（第 11 节）—— 与 1 并行，互为输入
3. **统一状态视图**（缺口 B）—— 纯工程，无前置依赖，人与 agent 同时受益
4. **run manifest + 预算闸门**（缺口 C）
5. **MCP server**（第 9 节）—— 用外部 agent 做真实检验
6. 视觉闸门 / 视频可用性检测 —— 有了模板与 SOP 之后再谈

## 附录：本次使用的核查查询（可复现）

```sql
-- 规模盘点
SELECT '项目数', COUNT(*) FROM projects
UNION ALL SELECT '分镜组', COUNT(*) FROM shot_sets
UNION ALL SELECT '分镜(shots)', COUNT(*) FROM shots
UNION ALL SELECT '候选图总数', COUNT(*) FROM shot_result_candidates
UNION ALL SELECT '有选中结果的分镜', COUNT(*) FROM shots WHERE latestGeneratedImageId IS NOT NULL;

-- 每个分镜实际产出过几个 job（正确算法：走候选表，勿用 inputImageId 关联）
SELECT n AS job数, COUNT(*) AS 分镜数
FROM (SELECT shotId, COUNT(DISTINCT jobId) n FROM shot_result_candidates GROUP BY shotId)
GROUP BY n ORDER BY n;

-- 否决记录是否存在
SELECT COALESCE(NULLIF(reviewMark,''),'(空)') AS mark, COUNT(*) FROM shots GROUP BY mark;

-- 历史 prompt（模板提取原料）
SELECT DISTINCT substr(prompt,1,110) FROM jobs WHERE prompt IS NOT NULL AND prompt <> '';

-- 素材角色分布
SELECT role, COALESCE(NULLIF(usage,''),'(无)') u, COUNT(*) FROM image_assets GROUP BY role,u ORDER BY 3 DESC;
```
