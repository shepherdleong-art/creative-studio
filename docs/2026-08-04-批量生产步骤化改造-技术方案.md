## 一、目标

1. 批量生产改成和「单条精准混剪」同构的**分步向导**,不再是一条长滚动页面。
2. **口播独立成一步**,参照单条的第 2 步(文案 + 音色 + 试听 + 开跑),打通目前断掉的链路。
3. 清掉界面上的 `Phase A/B/D/E` 等内部研发术语,全部换成人话。
4. 保留 1440px 破格布局 —— 这是为小屏监看有意设计的,不动。

## 三、目标信息架构

### 3.1 四步,和单条 1:1 同构

| | 单条精准混剪 | 批量生产(新) |
|---|---|---|
| 第 1 步 | 导入素材 | **准备素材** |
| 第 2 步 | AI 智能创作 | **脚本与口播** |
| 第 3 步 | 预览调整 | **检查成片** |
| 第 4 步 | 导出渲染 | **导出成片** |

用户从单条切到批量,心智模型不变。

### 3.2 常驻区域(不占步骤)

- **topbar**:批次切换器 + 新建批次 + 画幅选择 + 批次状态徽标。
  对应单条 topbar 的「画幅」段。批次相当于单条的「分镜组」,属于全局上下文而非某一步。
- **左侧栏**:批次概览(已选素材数 / 脚本数 / 目标成片数 / 已完成数)、当前步骤说明、最近批次列表。
  直接复用 `MixcutSidebar.tsx` 的结构(`styles.panel` / `styles.statGrid` / `styles.session`)。

### 3.3 每一步装什么

#### 第 1 步 · 准备素材

来源:现 `项目素材池`(:1428)+ `媒体准备`(:1067)

## 四、口播步骤的技术方案 ★ 核心

### 4.1 好消息:两边的数据形状几乎一致

单条 TTS 适配器输出(`lib/final-edit/adapters/tts-registry.ts` 的 `FinalEditTtsAdapter.synthesize`):

```ts
{
  relativePath: string;
  absolutePath: string;
  durationUs: number;
  segmentTimings: Array<{ segmentId: string; startUs: number; endUs: number }>;
  wordTimings: Array<{ text: string; startUs: number; endUs: number }>;
}
```

批量口播接口需要(`lib/batch-production/narration.ts` 的 `BatchLocalNarrationArtifact`):

```ts
{
  audioRelativePath: string;
  audioFingerprint: string;
  durationUs: number;
  segmentTimings: Array<{ sourceSegmentId: string; startUs: number; endUs: number }>;
}
```

**差异只有两处**:

1. 字段改名:`relativePath` → `audioRelativePath`,`segmentId` → `sourceSegmentId`
2. 缺 `audioFingerprint` —— 对产出的音频文件算 SHA-256 即可,`lib/batch-production/fingerprint.ts` 已有现成工具

### 4.2 需要动的四个点

| # | 位置 | 改动 |
|---|---|---|
| 1 | `lib/batch-production/allocator.ts:162-164` | 把 `narration` 的字面量类型 `{ ready: false; productionReady: false }` 放开为 boolean,否则类型层面永远接不上 |
| 2 | 新增 `lib/batch-production/narration-executor.ts` | 批量口播执行器:读冻结脚本 → 调 TTS 适配器 → 算指纹 → `createLocalNarrationSnapshot()` → 写回 arrangement。参照 `lib/final-edit/runtime.ts:75-90` 的 provider 解析和 `lib/final-edit/workspace.ts:1076-1096` 的调用方式 |
| 3 | `lib/batch-production/scheduler.ts` / `executors.ts` | 注册 `narration` 任务类型,排在 `allocation` 之后、`render` 之前 |
| 4 | `lib/batch-production/batch-renderer.ts:122-125` | 接收带 `productionReady: true` 的 narration,`audioMode` 才会变成 `'narration'`,`batch-export.ts:224` 的闸门自然打开 |

### 4.3 一个重要优化:同脚本多份共用一条口播

批量的「份数」语义是:**同一份脚本生成 N 条成片,画面不同、口播相同**。

所以口播只需按 `hash(脚本正文 + 音色 + 语速)` 合成**一次**,N 条成片复用同一个音频文件。

> 音色改为按脚本设置后此结论不变 —— 复用键本来就含音色和语速,只是复用范围从整批收窄到单份脚本内。

单条已有现成范式:`lib/final-edit/workspace.ts:1075-1096` 用 `narrationHash` 做缓存复用,批量照搬即可。

> 影响:一份脚本出 10 条成片,TTS 调用从 10 次降到 1 次。

### 4.4 口播失败时的降级

保留现有 `silent_placeholder` 机制,但**语义要在 UI 上说清**:
- 第 3 步卡片显示「无配音样片 · 仅供检查画面」
- 第 4 步导出时该卡片显示「缺配音,无法导出 —— 回第 2 步生成口播」,而不是抛内部报错
- **不提供无配音样片的导出旁路**(产品已决策)

### 4.5 BGM 技术方案

#### 4.5.1 需要动的三个点

| # | 位置 | 改动 |
|---|---|---|
| 1 | 批次输入快照 / `startBatch` 链路 | 把每份脚本选中的曲目 ID 列表传进分配器的 `musicTrackIds`。分配器的轮询逻辑(`allocator.ts:851-853`)**已实现,不用动** |
| 2 | `lib/batch-production/batch-renderer.ts` | 读 `arrangement.music.trackId` → 解析曲目路径 → 加入 FFmpeg 输入与滤镜链。**直接移植** `lib/final-edit/renderer.ts:117-118 / 152-153` 的实现 |
| 3 | 曲库读取 | 复用 `lib/final-edit/bgm.ts` 的 `scanFinalEditBgm()`,共用 `storage/bgm/` 与 `final_edit_bgm_tracks` 表,**不新建批量专属曲库** |

#### 4.5.2 混音链(照搬单条)

```
[bgm]  aresample=48000
     → loudnorm=I=-16:TP=-1.5:LRA=11     # 响度归一化,保证人声不被盖
     → volume=<gainDb>dB                  # 默认 -18dB
     → atrim=duration=<成片时长>           # 长于成片则裁切
     → afade(in/out)                       # 默认淡入 1.0s / 淡出 1.5s
     → [music]
[narration][music] amix=inputs=2:duration=longest:dropout_transition=0
```

循环用 `-stream_loop -1` 输入侧解决(短于成片时自动循环)。

#### 4.5.3 身份校验

BGM 必须纳入现有的指纹校验体系,与原片和 LUT 一致:

- 锁定批次时记录曲目的 `fileFingerprint`(`scanFinalEditBgm` 已经算好 SHA-256)
- 渲染前重新核验;不一致则该条失败并报「背景音乐文件已丢失或被修改」
- 参照单条 `lib/final-edit/renderer.ts:90` 的做法

> 这一点不能省 —— 否则「锁定输入」的承诺对 BGM 不成立,同一批次两次渲染可能出不同音乐。

#### 4.5.4 BGM 必选,且默认全自动分配

产品决策:
- BGM 与配音、字幕、封面并列为合格成片的必要条件
- **默认全自动** —— 用户往 `storage/bgm/` 放满曲子,不做任何选择,系统自动分配
- **可选手动指定** —— 每份脚本可手动挑 1–N 首收窄范围

**关键约束:自动分配必须是确定性的。**

「随机」不能实现成每次渲染现掷骰子,否则同一锁定版本重跑会出不同音乐,「锁定输入」的承诺对 BGM 就不成立。正确做法:

```
锁定批次时:
  seed = hash(batchVersionId)
  pool = shuffle(曲库或手动指定的曲目, seed)     // 确定性打乱
  第 i 条成片 → pool[i % pool.length]           // 依序取,天然均匀
  结果写进 arrangement.music.trackId 并冻结曲目指纹

渲染时:
  只读 arrangement.music.trackId,不再做任何选择
```

打乱后依序取优于纯随机:既有随机感,又保证曲目使用均匀(3 首出 9 条 = 每首各 3 次),且完全可重现。

> 现有的 `allocator.ts:852` 是 `musicPool[planIndex % musicPool.length]` —— 依序取的部分**已经就绪**,只需在传入前先做一次确定性打乱。

**闸门放在第 2 步开始按钮**,而非导出时:

- 曲库为空 → 禁用开始按钮,提示曲库位置与刷新入口
- 手动模式下指定为空的脚本 → 禁用开始按钮,指明是哪几份

> 理由:BGM 缺失是**输入问题**,应该在输入阶段拦住。等到跑完几十条再在导出口拒绝,浪费的是渲染时间。这与配音不同 —— 配音可能因供应商故障在运行期失败,所以仍保留运行期的 `silent_placeholder` 降级路径。

### 4.6 按脚本目标时长(需改分配器 + 补上游同步)

产品决策:时长在第 3 步生成脚本时已选定,批量**完全不提供时长设置**。

**时长语义**(`lib/script-duration-policy.ts`):

```
SCRIPT_DURATION_OPTIONS = [15, 20, 30, 45, 60]      // 枚举档位,非自由输入
SCRIPT_CALIBRATED_CHARS_PER_SECOND = 4.2            // 按此推出字数上下限
```

时长与文案字数是**绑死**的 —— 写脚本时选了 30 秒,字数就按 30 秒的预算约束过。批量再给一个自由时长输入会与已写定的字数矛盾,所以彻底取消。

**断点定位**:

| 位置 | 现状 |
|---|---|
| `StoredScriptOutput` | **有** `targetDurationSec`(V2 与 V3 都有) |
| `script-catalog.ts` `syncProjectScripts()` | ⚠️ 同步进批量脚本目录时 metadata 只带了 `coverTitleJson` / `shotSetId` / `contentRevision`,**没带时长** |
| `batch_scripts` / `batch_script_snapshots` 表 | **没有时长列** |
| `allocator.ts:527-530` | 目标时长是**整批一个值**,同一个值传给所有 plan |
| `allocator.ts:494` | `normalizePlan(rawPlan, index, targetDurationUs)` 签名接收外部统一值 |

**改动(四处,缺一不可)**:

1. 迁移 v17 给两张表各加 `targetDurationSec`(见 §4.7)
2. **`syncProjectScripts` 的 metadata 补上 `targetDurationSec`** —— 漏了这步,新列永远是默认值
3. 锁定批次时把它冻进快照
4. `normalizePlan` 改为从 plan 自身的脚本快照读时长,`normalizeInput` 的整批值降级为兜底

**兼容性**:v17 之前的快照没有该字段,读入回落 15 秒(最小档位),不得报错。

### 4.7 迁移 v17

两项决策都要新增字段,**合并成一次迁移**,只动一次数据库:

| 表 | 字段 | 用途 |
|---|---|---|
| `batch_scripts` | `targetDurationSec` | 脚本目录承接时长(§4.6) |
| `batch_script_snapshots` | `targetDurationSec` | 冻结各脚本目标时长(§4.6) |
| `batch_productions` | `archivedAt` | 批次归档,空值表示未归档(§4.9) |

**现成先例**:迁移 v9(`schema.ts:336-341`)就是同时给 `batch_scripts` 和 `batch_script_snapshots` 各加三列,照同样写法追加即可:

```sql

ALTER TABLE batch_script_snapshots ADD COLUMN targetDurationSec INTEGER NOT NULL DEFAULT 15;
ALTER TABLE batch_productions ADD COLUMN archivedAt TEXT;
```

**约束**(照搬 CLAUDE.md 的既有规则):

1. 必须走**共享写锁 + 验证备份 + 审计**网关,不得放进旧核心表的 catch-and-continue 流程
2. 已发布的 v1–v16 **不得修改**,只能追加 v17
3. `archivedAt` 必须是**独立于 `status` 的新维度**,不能塞进批次状态枚举,否则破坏现有状态机
4. 两个字段都要允许为空,历史行读入不报错

### 4.8 内容分析模型的默认选择

> **先澄清一个概念**:「自动配画面」(allocator)**不调任何模型** —— `allocator.ts` 全文 grep `fetch` / `provider` / `vision` / `llm` 零命中,是纯确定性本地计算。用模型的是**第 1 步的内容分析**,它把画面语义、镜头标签、可用区间写进分析结果;分配器只是消费这些结果。分配质量取决于分析质量。

**现状**:

| 位置 | 事实 |
|---|---|
| 视觉能力来源 | 复用 `script_providers` 表,每个供应商一个 `supportsVision` 开关,**数据库默认 0** |
| `store.ts:35` | `SELECT * FROM script_providers ORDER BY name` —— 二进制排序 |
| `BatchPreparationPanel.tsx:195-197` | 默认值 = `find(p => p.configured && p.supportsVision)`,即**排序后第一个** |
| `BatchPreparationPanel.tsx:1444` | 下拉项只渲染供应商名,**不显示模型名** |
| 执行链路 | `executors.ts:109` → `final-edit/adapters/video-analysis.ts` 的 `analyzeVideoWithVision({ providerId })` |

**问题**:默认分析模型由供应商名称的字母序偶然决定。`GPT / OpenAI` 排在 `Gemini` 前,只因为 `P`(0x50) < `e`(0x65)。**重命名任一供应商都可能换掉默认分析模型**,且用户无从察觉。

**改动**:

| # | 改动 |
|---|---|
| 1 | 分析模型的选择持久化到项目或批次设置,不再每次从列表现算 |
| 2 | 下拉项渲染为 `<供应商名> · <模型名>`,区分同模型的多个接入 |
| 3 | 无任何供应商开启 `supportsVision` 时,渲染引导文案而非空下拉 |
| 4 | 首次默认值改为显式规则(如内置优先),并在 UI 上标注「默认」 |

> **附带发现**:`visionCostPerRequest` 当前全部为 0,导致 `estimateAnalysisCost` 恒返回 0,批量分析的成本估算失真。不阻塞本次改造,但若成本数字要可信,需在供应商设置补单价。

### 4.9 批次归档与搜索

> **参照对象是单条模式的「最近会话」**(`components/mixcut/MixcutSidebar.tsx` 的 `sessions` 列表):侧栏里一组按钮,每项「一行标题 + 版本标签」加「一行元信息」。批次列表照此实现,**放侧栏而非顶栏下拉**。搜索与归档是本次新增能力。

| # | 改动 |
|---|---|
| 1 | 批次列表接口支持 `includeArchived` 参数,默认只返回未归档 |
| 2 | 新增归档/恢复接口,写 `archivedAt`;**不删除任何数据** |
| 3 | 归档 `running` 状态的批次前,先走现有的停止批次流程 |
| 4 | 搜索在前端按名称过滤即可,批次数量级不需要后端搜索 |

**成片版本展示**(Q5):默认只查询并展示各 plan 的最新版本;卡片提供切换入口按需拉取历史版本。**底层 append-only 语义与「正式产物不覆盖」保持不变** —— 手动切换需要历史记录,且已导出成片可能正在投放。

## 八、风险与注意

1. **`allocator.ts` 的类型放开会牵动快照兼容性** —— arrangement 有 `schemaVersion`,需要确认旧版本记录读入时的降级路径,别让历史批次读不出来。
2. **口播执行器要走现有调度器和锁** —— `lib/batch-production/scheduler.ts` 的租约机制不能绕过,否则并发下会重复合成。
3. **第 3 批是纯重构** —— 建议单独一次提交,不夹带任何行为变更,方便出问题时二分定位。
4. **`readiness.ts` 闸门** —— 所有批量 API 都在共享的 readiness/backup/lock/audit 网关后面,新增口播任务类型也必须走同一条路,不能新开旁路。
5. **BGM 曲库是两个模式共用的** —— `storage/bgm/` 与 `final_edit_bgm_tracks` 表同时服务单条和批量。改动扫描逻辑时要确认不破坏单条模式的现有行为。
6. **BGM 轮询分配必须是确定性的** —— 同一个锁定版本重跑,第 N 条成片必须还是同一首曲子,否则「锁定输入」的承诺不成立。`allocator.ts:852` 用 `planIndex % musicPool.length`,前提是 `musicTrackIds` 已排序(`allocator.ts:564` 有 `.sort()`),接入时不要绕过这个排序。
