### F2（P1）C3 的浏览器/播放证据没有产出，且用了文档点名禁止的替代方式

`scripts/batch-phase-e-ui-contract.test.mjs` 是纯 `fs.readFileSync` + 正则源码匹配。`e2211ce` 往里加的 12 条断言**全部**是匹配源码字符串，例如：

```js
assert.match(batchTimelinePreview, /lastBgmFileUrlRef/, 'BGM 换源必须建立显式媒体同步');
assert.match(batchTimelinePreview, /playingRef\.current && bgm/, '播放中换源必须按音量包络续播');
```

执行方案 §5.4 原话：

> 浏览器证据必须覆盖：成片预览正在播放 → 切换曲目 → 新 `<audio>` 源生效，`paused === false`，时间与正文播放头误差在可接受范围，画面播放头不归零。
>
> 若当前环境无法做媒体播放自动化，必须把该项标记为「人工必做，尚未验证」，**不得用源码匹配冒充播放证据**。

§5.3 建议的「聚焦 BGM 换源的 Playwright 测试」也没有新增（`ls scripts/*.playwright.test.mjs` 仍是原来 4 个）。C3 的核心交互至今没有任何运行时证据。

### F3（P2）C3 换源续播：从「关闭 BGM」切到某首曲目时不生效

`components/batch-production/BatchTimelinePreview.tsx:453`

```js
const previous = lastBgmFileUrlRef.current;
lastBgmFileUrlRef.current = bgmFileUrl;
if (previous === null || previous === bgmFileUrl) return;
```

`previous === null` 把「首次挂载」和「BGM 原本是关闭的」混成了一件事。`lastBgmFileUrlRef` 初值就是 `null`，而 `bgm` 在 `musicDraft.trackId` 为空时也是 `null`（`BatchOutputEditor.tsx:227` 的 `previewBgm`）。

**复现**：

1. 成片预览播放中 → 曲目下拉选「关闭 BGM」→ 走到 `element.pause()`（正确）
2. 再选一首曲目 → `previous` 是 `null` → **直接 return**

新 `<audio src>` 已经生效，但没有任何代码调 `play()`：rAF tick（同文件 334 行）只设 `element.volume`，`startPlayback` 只在点播放键时跑，`synchronizePausedAudio` 只 seek。结果是音乐不再响，要等用户暂停/重播才恢复。

「初始没有 BGM、播放中第一次选曲」是同一条路径，同样不响。

**修复方向**：用独立的 `initializedRef` 区分首帧，让 `previous === null && bgmFileUrl !== null` 走 resume 分支，而不是靠 `previous` 兼任两种语义。

### F4（P3）换源 resume 的两个小问题（同一段代码）

- **`BatchTimelinePreview.tsx:458`** —— `resumeBgm` 闭包捕获的是 effect 运行时的 `playheadSec`。走 `loadedmetadata` 异步分支时（换 src 后 `readyState` 会掉到 0，所以这是常走分支），加载耗时期间播放头已经前进，seek 会落后一个加载时长。改读 ref（如同文件已有的 `lastDrivenSecRef`）更稳。
- **`BatchTimelinePreview.tsx:477`** —— `addEventListener('loadedmetadata', resumeBgm, { once: true })` 没有 cleanup。**同文件 256–257 行的同类监听器是带 `removeEventListener` 的**，这里破了本文件自己的惯例。快速连换两首时，第一个陈旧监听器仍可能触发一次 seek/play。

### F5（P3）C5 让批量视频卡片在批次内变成倒序，方向和 C4 相反

`app/api/shot-sets/[id]/video-jobs/batch/route.ts:132` 给同批次逐条写 `new Date(batchBaseMs + index).toISOString()`，而列表 API（同目录 `route.ts:133`）是 `ORDER BY vj.createdAt DESC`。

于是同一批 3 条运镜现在稳定显示成 V03 → V02 → V01（改动前是 `datetime('now')` 秒级并列、顺序未定义）。

不违反 D5 任何条款（D5 没管顺序），但和 C4 刚给图片定下的「同一请求内按用户提交顺序从左到右」正好拧着。**要不要对齐是产品决定，不是 bug。**

> 补充：`components/VideoGenerationResults.tsx:67` 本来就按 status 排序（succeeded → running → pending → needs_check → failed → canceled），`Array.sort` 稳定所以同状态内保留入参顺序。这个 status 排序是既有行为，本轮没动。

### F6（P3）一条恒真的废断言

`scripts/project-job-order.test.ts:44-54` 的「排序比较与状态字段无关」是把同一对对象比较两次然后断言相等，恒真、零覆盖。

真正的覆盖在紧随其后的内存库集成段（`UPDATE jobs SET status='succeeded'` 后重查顺序不变），所以**不是覆盖缺口**，只是噪音。

### F7（P3）范围外的连带改动，都合理但没人报告
