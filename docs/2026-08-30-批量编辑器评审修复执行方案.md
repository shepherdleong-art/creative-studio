## F1（P1）commit_render 丢渲染 + 状态文案说谎

### 现象

用户在「调整片段」里改完东西，**关掉浏览器标签页 / 刷新页面**，或者改完立刻点关闭（编辑请求还在途中），退出这轮时的 `commit_render` 不会发出。结果：`arrangement.editRevision` 已经前进，渲染候选停在旧修订号，卡片永远 `renderStale`——勾选框禁用，提示写「修改已保存，等待重新渲染完成」，**可队列里根本没有任何渲染任务**。

用户能自救（卡片上的「重新生成」走 `retryTask`，`scheduler.ts:445` 专门放行 succeeded 的 `output_version` 任务，worker 会按当前 arrangement 重渲），但没人会想到要点它——文案明确告诉他「等着就行」。

### 根因

`components/batch-production/BatchOutputEditor.tsx:116-131`：

```tsx
return () => {
  if (!pendingRenderRef.current) return;
  pendingRenderRef.current = false;          // ← ① 请求发出前就清了欠账
  void fetch(url, { …, keepalive: true })
    .then(() => onChangedRef.current?.())    // ← ② 没看 response.ok
    .catch(() => undefined);                 // ← ③ 失败被吞
};
```

三个独立漏点：

- **A. 关标签页 / 刷新不会走 React 卸载**，所以这段 cleanup 根本不执行。单条剪辑有 `components/mixcut/MixcutPanel.tsx:526` 的 `beforeunload` 兜底，批量这边**一个都没有**（全仓 `grep -rn "beforeunload\|pagehide" components/ app/` 只有那一处）。
- **B. 编辑请求在途时卸载**：`pendingRenderRef` 只在响应回来后才置位（`BatchOutputEditor.tsx:207`），而服务端已经写了 arrangement、`editRevision` 已经 +1。
- **C. commit 请求本身失败**（离线、5xx）时欠账已经被清，无法补救。

### 改法

#### F1-a　提交逻辑收紧（`BatchOutputEditor.tsx`）

把 116-131 的 effect 换成下面这版（`commitRender` 定义在 `loadView` 之后、第一个 effect 之前）：

```tsx
  /**
   * 提交这一轮欠着的重渲染。keepalive 让卸载/关标签页时请求仍能发出;
   * 只有服务端确认收下才清欠账——失败就留着,让 pagehide 或下一次卸载再补一次。
   * commit_render 按 requestKey 幂等(phase-e.ts:39-50),多提交一次只会拿回同一个任务。
   */
  const commitRender = useCallback((url: string) => {
    if (!pendingRenderRef.current) return;
    void fetch(url, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ type: 'commit_render' }),
      keepalive: true,
    }).then((response) => {
      if (!response.ok) return;
      pendingRenderRef.current = false;
      onChangedRef.current?.();
    }).catch(() => undefined);
  }, []);

  useEffect(() => {
    // 退出这一轮调整(关闭弹窗/换成片/切步骤)时把欠着的重渲染一次性提交。
    // url 按当次的 projectId/batchId/planId 固化:换成片时提交的必须是上一条的渲染。
    // 关标签页/刷新不会走 React 卸载,只有 pagehide 能兜住(单条走的是 beforeunload)。
    const url = `/api/batch-production/batches/${encodeURIComponent(batchId)}/outputs/${encodeURIComponent(planId)}/clips?projectId=${encodeURIComponent(projectId)}`;
    const flush = () => commitRender(url);
    window.addEventListener('pagehide', flush);
    return () => {
      window.removeEventListener('pagehide', flush);
      flush();
    };
  }, [projectId, batchId, planId, commitRender]);
```

#### F1-b　欠账提前置位（`BatchOutputEditor.tsx`，`submitEdit` 开头）

在 `setSubmitting(true)` 之前插入：

```tsx
    // split 是纯结构操作(不改像素,不递增 editRevision),其余命令都可能改画面。
    // 响应回来前组件就被卸载时(改完立刻关弹窗),响应里的 visualChanged 没人接得到,
    // 所以先记欠账再发请求;命令实际没生效时最多多发一次幂等的 commit。
    if (payload.type !== 'split') pendingRenderRef.current = true;
```

`BatchOutputEditor.tsx:207` 那行按响应置位的逻辑**保留不动**（双保险）。

#### F1-c　把「等待重渲染」和「还没提交重渲染」拆成两种文案

**服务端**：`lib/batch-production/batch-workspace.ts`

1. 接口 `BatchOutputCardView`（第 95 行 `renderStale` 之后）新增：

```ts
  /** 候选与 arrangement 不一致、但队列里没有渲染任务——需要用户点「重新生成」。 */
  renderUncommitted: boolean;
```

2. 计算（第 566-570 行 `renderStale` 之后）新增，并加进返回对象（第 628 行 `renderStale` 之后）：

```ts
    // renderStale 是导出闸门的镜像;renderUncommitted 进一步区分「真的排了渲染在跑」
    // 和「改动还没提交重渲染」——后者要用户自己点「重新生成」,不能显示成「等待完成」。
    const renderUncommitted = Boolean(
      plan.currentVersionId && candidate && !pendingRender
      && (candidateRevisionStale || candidateCoverStale),
    );
```

**前端文案**（只改文案，`renderStale` 作为禁用/过滤条件的地方一律不动）：

- `BatchStepReview.tsx:323` checkbox `title`：`card.renderStale` 分支改为
  `card.renderUncommitted ? '修改还没提交重新渲染，请点卡片上的「重新生成」' : '修改已保存，等待重新渲染完成'`
- `BatchStepReview.tsx:344-345` 徽标文字：`{card.renderUncommitted ? '待重新生成' : '等待重新渲染'}`
- `BatchStepReview.tsx:157-159` `otherBlockers`：`card.renderStale` 分支同样按 `renderUncommitted` 二选一
- `BatchStepExport.tsx:173-175` checkbox `title`：同上二选一
- `BatchStepExport.tsx:187` 徽标：改为
  ```tsx
  {!card.publishable ? '不可导出' : card.renderUncommitted ? '待重新生成' : card.renderStale ? '等待重新渲染' : card.approved ? '可导出' : '待审核'}
  ```
  **注意**：`scripts/batch-phase-e-ui-contract.test.mjs:113-117` 断言 `"!card.publishable ? '不可导出'"` 必须出现在 `"card.renderStale ? '等待重新渲染'"` 之前。按上面这个写法两个 substring 都还在且顺序不变，**该断言不需要改**；改完务必重跑确认。

### 影响面

`renderStale` 的语义和全部禁用/过滤逻辑保持不变，所以导出闸门、勾选规则、`batch-workspace.test.ts:107-125` 的既有断言都不受影响。新增字段是纯附加。

手工：进「调整片段」拖一下片段边界 → 直接关标签页 → 重开项目 → 卡片应显示「等待重新渲染」（因为 pagehide 已经提交了），而不是「待重新生成」。

## F2（P2）未应用的字幕样式草稿被静默吃掉

### 现象

在右栏调好字幕颜色/位置（中栏预览**已经实时变了**），还没点「应用字幕样式」，顺手去时间轴拖一下片段 —— 草稿被清空，预览跳回旧样式。用户会以为自己白调了，或者以为改动没生效。

同一个右栏里，BGM 那张卡片不会这样（它的 effect 依赖的是具体数值），**两张卡片行为相反**。

### 根因

`components/batch-production/BatchOutputEditor.tsx:167-171`：

```tsx
  useEffect(() => {
    if (!view) return;
    const timer = window.setTimeout(() => setSubtitleStyleDraft(view.subtitleStyle), 0);
    return () => window.clearTimeout(timer);
  }, [view?.editRevision, view?.planId, view?.subtitleStyle]);
```

`view` 每次 `loadView(true)` 都是新解析出来的对象，`view.subtitleStyle` 的引用**必然变**，所以这个 effect 在**每一次 `submitEdit` 之后**都会跑，把草稿盖回服务端值。

### 改法

1. **整段删除** 167-171 这个 effect。
2. 换计划时的重置已经由 98-113 那个 effect 里的 `setSubtitleStyleDraft(null)` 覆盖，`effectiveSubtitleStyleDraft = subtitleStyleDraft ?? view.subtitleStyle`（第 331 行）会自动回落到服务端值，不需要额外补。
3. 样式提交成功后主动清草稿，让它回落到服务端真值——改两个按钮（`BatchOutputEditor.tsx:569-585`）：

```tsx
              // 恢复批次默认
              onClick={() => {
                void submitEdit({ type: 'set_subtitle_style', style: null })
                  .then((accepted) => { if (accepted) setSubtitleStyleDraft(null); });
              }}
```
```tsx
              // 应用字幕样式
              onClick={() => {
                void submitEdit({ type: 'set_subtitle_style', style: effectiveSubtitleStyleDraft })
                  .then((accepted) => { if (accepted) setSubtitleStyleDraft(null); });
              }}
```
「恢复批次默认」原来那句 `setSubtitleStyleDraft(view.subtitleStyleDefault);` 一并删掉（提交成功后回落即可）。

4. `BatchTextStyleEditor` 的 `key` 里含 `view.editRevision`（第 562 行），会因为别的编辑而整块重挂载、丢掉内部 UI 态。把 key 改成 `'batch-subtitle-style-' + view.planId`。

### 验证

```bash
node scripts/batch-phase-e-ui-contract.test.mjs
npx tsc --noEmit
```

`scripts/batch-phase-e-ui-contract.test.mjs` 追加一条源码契约断言：`outputEditor` 里不得再出现 `view?.subtitleStyle` 作为 effect 依赖（例如 `assert.doesNotMatch(outputEditor, /view\?\.subtitleStyle\]/)`）。

手工：调字幕颜色不点应用 → 拖片段 → 颜色草稿和预览都应保持；点「应用字幕样式」→ 按钮变灰、预览不变。

## F3（P2）进全屏后没有任何控制器

### 现象

点「全屏」后只有画面进入全屏，播放键、进度条、安全区开关、全屏按钮全在全屏层外面 → **不能播、不能拖、不能点按钮退出**，只能按 ESC。`toggleFullscreen` 里的 `exitFullscreen` 分支实际上永远点不到。

复盘文档把这写成「只让预览 stage 进入 fullscreen，不把控制器一起放大」，意图没错，但结果是「全屏 = 一张静止画面」。

### 根因

`components/batch-production/BatchTimelinePreview.tsx:429-431` 的 `fullscreenRef` 只包住了 stage；控制条是它的兄弟节点（第 471 行起）。另外第 415 行 `void root.requestFullscreen?.()` 没有 `catch`，被浏览器拒绝时是未处理的 promise rejection。

### 改法

按「控制条不放大、但要能操作」的原意做：**全屏时把同一份控制条以浮层形式渲染进全屏层底部**。

1. 新增全屏态跟踪（放在 `toggleFullscreen` 附近）：

```tsx
  const [isFullscreen, setIsFullscreen] = useState(false);
  useEffect(() => {
    const sync = () => setIsFullscreen(document.fullscreenElement === fullscreenRef.current);
    document.addEventListener('fullscreenchange', sync);
    return () => document.removeEventListener('fullscreenchange', sync);
  }, []);
```

2. `toggleFullscreen` 补 `catch`，并让退出走当前元素：

```tsx
  const toggleFullscreen = () => {
    const root = fullscreenRef.current;
    if (!root || typeof document === 'undefined') return;
    // requestFullscreen 在非用户手势/被策略拒绝时会 reject,必须吞掉避免未处理拒绝。
    if (document.fullscreenElement) void document.exitFullscreen().catch(() => undefined);
    else void root.requestFullscreen?.().catch(() => undefined);
  };
```

3. 把 471-502 那段控制条抽成一个渲染函数（**只抽取，不改内部任何控件**），外层容器 className 参数化：

```tsx
  const renderControls = (overlay: boolean) => (
    <div className={overlay ? styles.fullscreenControls : 'flex flex-wrap items-center gap-2'}>
      {/* …原有播放键 / 进度条 / 预览内容切换 / 安全区 / 全屏 按钮，原样搬进来… */}
    </div>
  );
```
全屏按钮的文字与 `aria-label` 改为 `isFullscreen ? '退出全屏' : '全屏'`。

4. 挂载位置：`fullscreenRef` 那个 div 内部、stage 之后加 `{isFullscreen && renderControls(true)}`；原来的位置改成 `{!isFullscreen && renderControls(false)}`。

5. `components/batch-production/batch-preview.module.css` 追加（**只追加**）：

```css
.fullscreenShell:fullscreen {
  position: relative;
}

.fullscreenControls {
  position: absolute;
  right: 0;
  bottom: 0;
  left: 0;
  display: flex;
  flex-wrap: wrap;
  align-items: center;
  gap: 8px;
  padding: 12px 20px;
  background: linear-gradient(to top, rgba(0, 0, 0, .72), rgba(0, 0, 0, 0));
}
.fullscreenControls,
.fullscreenControls span,
.fullscreenControls button { color: #fff; }
.fullscreenControls button {
  border-color: rgba(255, 255, 255, .28);
  background: rgba(255, 255, 255, .14);
}
.fullscreenControls input[type='range'] { accent-color: #fff; }
```

### 影响面

非全屏路径的 DOM 与样式完全不变（只是同一段 JSX 换了个渲染入口）。控制条在两种模式间切换会重挂载 `<input type="range">`，但播放状态存在 ref 里，不受影响。

### 验证

```bash
node scripts/batch-phase-e-ui-contract.test.mjs
npx tsc --noEmit
```

`scripts/batch-phase-e-ui-contract.test.mjs` 追加：`timelinePreview` 源码必须同时含 `fullscreenchange` 与 `退出全屏`；`batch-preview.module.css` 必须含 `.fullscreenControls`。

**手工必做（自动化 harness 进不了系统级全屏，这条只能人工）**：真实浏览器里点全屏 → 底部应出现控制条 → 能播放、能拖进度、能点「退出全屏」回到弹窗；3:4 画幅在全屏下不被拉伸。

## F4（P3）窄窗口下右栏被裁掉且不能滚动

### 现象

- 视口宽 < ~1073px：三栏最小宽 254+420+300+24(gap) = **998px**，而弹窗内可用宽 = `0.96vw − 32`，装不下；父层 `BatchStepReview.tsx:464` 是 `overflow-hidden`，直接裁掉，**没有横向滚动**。
- 视口宽 < 1024px（`lg` 断点以下）：三栏塌成一列，三段纵向叠加远超弹窗高度，grid 自身没有 `overflow-y` → 同样被裁，**右栏整块摸不到**。
- 1280 及以上正常（1196 > 998）。

### 改法

`components/batch-production/BatchOutputEditor.tsx`：

1. 第 357 行三栏容器：`lg:grid-cols-[…]` 改成 `xl:grid-cols-[…]`（1280px 才启用三栏），并补一个兜底滚动：

```tsx
      <div className="grid min-h-0 min-w-0 flex-1 gap-3 overflow-y-auto xl:overflow-visible xl:grid-cols-[minmax(254px,280px)_minmax(420px,1fr)_minmax(300px,340px)]">
```

2. 第 358 行左栏 `lg:min-h-0` 同步改 `xl:min-h-0`。

三栏生效时（≥ xl）中栏/右栏各自的独立滚动行为完全不变；三栏未生效时由外层这一个滚动条兜住。

### 验证

`npx tsc --noEmit` + 手工把浏览器窗口拉到约 900px / 1024px / 1100px / 1440px 四档，确认右栏「视频封面设置」在每一档都能触达。

## F5（P3）中栏预览的片头封面不跟随封面精调

### 现象

中栏「成片预览」的前 20 帧片头用的是 `kind=cover&source=candidate`——**上一次渲染的产物**。在封面精调 drawer 里改完截帧点/构图/标题并应用后，drawer 自己的预览是对的，中栏片头还是旧封面；又因为渲染被推迟到退出编辑，**整个编辑期都不会更新**。与「编辑过程中的预览实时反映修改」直接冲突。

### 根因

`BatchOutputEditor.tsx:181-183` 生成 `coverUrl` 指向渲染候选；`BatchTimelinePreview.tsx:452-458` 直接 `<img src={coverUrl}>`。而客户端已经有一套与渲染同源的封面合成（`BatchCoverDraftPreview` + `coverFramingGeometry` + `textStyleToSvgElements`），只是没接进来。

### 改法

## F6（P3）BGM 参数草稿不进预览

### 现象

  // 预览吃草稿值:拖滑块即时试听,与右栏字幕样式的即改即看保持同一种心智模型。

## F7（P3）封面 drawer「应用」一次就抢焦点 + 重置草稿

### 现象

在封面精调里点「应用」后：焦点先被还给背景里的「封面精调」按钮、再被抢回 drawer 的关闭按钮（可见闪烁）；之后关闭 drawer 时的焦点还原目标已经错了。草稿也会在应用后被重置，用户在这个间隙的微调会丢。

### 根因

`components/batch-production/BatchCoverEditorDrawer.tsx:154` 的依赖数组：

```tsx
  }, [active, assets, framing, initialAssetId, initialTimeUs, outputWidth, title]);
```

`assets` / `title` / `framing` 都来自 `view`，每次 `loadView` 后引用必变 → 应用一次就整轮 cleanup（含 `previousFocusRef.current?.focus()`）+ 重新初始化（含 `setDraft` 与 `closeButtonRef.current?.focus()`）。

### 改法

把这个 effect 拆成两个，各管各的：

```tsx
  // ① 草稿初始化:只在真正「打开这个 drawer / 换了目标封面」时重置。
  //    title/framing/assets 每次 loadView 都换引用,不能进依赖,否则应用一次就把草稿冲掉。
  const initialSnapshotRef = useRef({ title, framing, assets });
  useEffect(() => { initialSnapshotRef.current = { title, framing, assets }; });
  useEffect(() => {
    if (!active) return;
    const snapshot = initialSnapshotRef.current;
    const selectedInitialAsset = snapshot.assets.find((asset) => asset.assetId === initialAssetId) ?? null;
    const timer = window.setTimeout(() => {
      setDraft(createDraft(snapshot.title, snapshot.framing, initialAssetId, initialTimeUs, outputWidth, selectedInitialAsset));
    }, 0);
    return () => window.clearTimeout(timer);
  }, [active, initialAssetId, initialTimeUs, outputWidth]);

  // ② 焦点陷阱 / 滚动锁 / ESC:只跟 active 走。
  useEffect(() => {
    if (!active) return;
    /* …原有 previousFocusRef / body.overflow / keydown 全套,原样搬过来… */
  }, [active]);
```

### 验证

`npx tsc --noEmit`；手工：drawer 里改标题 → 应用 → 焦点不跳、草稿保持；ESC 与点遮罩仍能关闭；关闭后焦点回到「封面精调」按钮；Tab 循环仍被困在 drawer 内。

## F8（P4）四个小修

**F8-1　空应用也会触发重渲染**
`lib/batch-production/output-arrangement.ts:874-879` 的「无变化」判定直接比 `currentCover.title`（首次为 `undefined`）与解析后的 `nextCover.title`，所以**打开封面 drawer 什么都不改直接点应用，也会 +1 editRevision、清掉审核结论、排一次整片重渲**。
改法：比较前先把 `currentCover` 也过一遍 `resolveBatchCoverTitleOverride(frozenCoverTitle, currentCover, outputWidth)`，用解析后的 `{primary, secondary, styles, framing}` 与 `nextCover` 的对应值比。
验证：`node scripts/batch-output-clip-edit.test.ts`，并补一条「重复提交同一份封面覆盖返回 `changed: false`」。

**F8-2　pointercancel 未处理**
`components/batch-production/BatchTimeline.tsx` 的三处 pointer 拖拽（播放头 208-209、片段 528-529、字幕 681-682）都只监听了 `pointermove`/`pointerup`。指针被系统取消（触控板手势打断、窗口失焦）时监听器不摘、`onDraftChange` 的草稿留在屏幕上。
改法：`up` 同时注册到 `pointercancel`（`{ once: true }`），并在取消分支只做 `onDraftChange(null)` 不提交。

**F8-3　tab 语义不完整**
`components/batch-production/BatchOutputEditor.tsx:455-471` 有 `role="tablist"`/`role="tab"`，但没有 `aria-controls`、没有对应的 `role="tabpanel"`、也没有左右方向键。
改法：给两个 tab 加 `id` 与 `aria-controls`，给第 476 行的内容容器加 `role="tabpanel"` + `aria-labelledby`；未选中的 tab 设 `tabIndex={-1}` 并在 tablist 上处理 `ArrowLeft/ArrowRight`。

**F8-4　同一成片可能排两次渲染（只记录，本轮不做）**
「进编辑 → 改 → 退出 → 再进 → 再改 → 退出」时，第一次的渲染任务可能还没跑完，`claimNextTask`（`lib/batch-production/scheduler.ts:58-84`）只对口播做闸门，不互斥同一 `output_version` 的 render。结果不会错（jobDir 带 uuid、导出按 editRevision 卡住旧候选），只是白烧一次 ffmpeg。**要动的话必须动调度器闸门，风险高于收益，本轮不做，记在这里备查。**
