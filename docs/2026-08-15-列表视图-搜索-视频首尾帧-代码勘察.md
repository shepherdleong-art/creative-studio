### 勘察结论 / 注意点

- **整张卡片是一个 `<Link>`**（162 行），不是 div 包 a。表格行要保持可点进项目的话，要么整行包 Link（tr 里不能放 a，得用 onClick + router.push），要么只在名称列放 Link。
- **统计块和列表是同一份 `projects` 数据**。搜索如果直接过滤 `projects` state，顶部四个数字会跟着一起变 —— 打字时数字乱跳。要保留一份未过滤的原始数组。
- **localStorage 命名惯例**：项目里已有 `creative-studio:video-shot-set:${projectId}`（`components/VideoGenerationPanel.tsx:87`）。视图偏好按这个前缀走。
- **hydration**：`app/page.tsx` 是客户端组件但仍会 SSR 首屏，读 localStorage 必须放 `useEffect`，不能在 useState 初始值里读。

## 2. 视频首尾帧

三件事里唯一要动数据库 + 适配器 + 队列 + API + UI 的。

### 2.1 数据库现状

`lib/db.ts:266-302` 是 `video_jobs` 建表语句。现有列：

```
id, projectId, shotSetId, shotId, sourceImageId, providerId, model,
templateId, prompt, durationSec, status, providerTaskId, providerStatus,
providerRawResponse, lastPolledAt, pollCount, remoteVideoUrl,
localVideoPath, filename, attempt, maxAttempts, errorMessage,
startedAt, finishedAt, createdAt
```

**只有一个 `sourceImageId`，没有尾帧字段。**

外键：`projectId` ON DELETE CASCADE、`shotSetId`/`shotId` ON DELETE SET NULL、`sourceImageId`/`providerId`/`templateId` 无 ON DELETE 规则。

迁移惯例：`lib/db-migrations.ts` 的 `CORE_DB_MIGRATIONS` 是 append-only 扁平 SQL 数组，`lib/db.ts:321-323` 逐条 try/catch 执行。另外 `lib/db.ts:325-331` 还有一小段独立的 `videoJobMigrations` 数组（历史遗留，`lastPolledAt` / `pollCount` 在那里）。既有 ALTER 写法都**不带外键**，例如 `ALTER TABLE video_jobs ADD COLUMN lastPolledAt TEXT`。

### 2.2 图片上传现状

`app/api/upload/route.ts`：

- `POST /api/upload`，formData：`files` / `role` / `projectId` / `usage` / `preprocessEnabled` / `targetMaxSide` / `jpegQuality`
- `role` 只允许 `'input' | 'reference'`（62 行）；reference 最多 3 张、input 最多 50 张（23-24 行）
- **`usage` 有白名单**：`['', 'scene_seed', 'shot_source']`（52 行），传别的值直接 400
- 做了 magic bytes 校验（只认 PNG/JPEG/WebP），会跑 `preprocessImage` 生成 processed 版本
- 落库表 `image_assets`，role 约束在 `lib/db.ts:70`：`CHECK(role IN ('reference','input','output'))`

### 2.3 image_assets 会被谁扫到（决定尾帧图打什么标记）

`GET /api/projects/[id]`（`app/api/projects/[id]/route.ts:21-23`）返回该项目**全部** image_assets，不做 role 过滤。前端各处自己过滤：

| 位置 | 过滤条件 | 尾帧图会不会混进去 |
|---|---|---|
| `app/projects/[id]/page.tsx:184` | `role==='input' && usage==='scene_seed'` | 不会 |
| `app/projects/[id]/page.tsx:188` | `role==='input' && usage==='shot_source'` | 不会 |
| `components/ShotSetPanel.tsx:532` | `role==='input' && usage==='shot_source'` | 不会 |
| `components/ShotSetPanel.tsx:371` | `role==='reference'`（无 usage） | **role 用 reference 就会混进去** |
| `components/ResultGallery.tsx:304` | `role==='reference'`（无 usage） | **同上** |
| `components/SceneReferencePanel.tsx:145` | `role==='output' \|\| role==='input'`（无 usage） | **会混进去**（场景参考的选图弹窗） |

结论：尾帧图用 `role='input'` + 新 usage 值最干净，只有 `SceneReferencePanel.tsx:145` 一处需要补 usage 排除。

**删除项目会连带清理**：`app/api/projects/[id]/route.ts` 的 `DELETE`（73-114 行）按 `projectId` 查出所有 image_assets，事务内删 DB 行，之后 unlink `path` / `originalPath` / `processedPath` 三个文件。所以尾帧图**绑 projectId 就能被自动回收**，不绑就会永久残留。

### 2.4 三家适配器现状（协议差异很大）

契约在 `lib/video-providers/types.ts`（26 行，全文很短）：

```ts

```

**只有单张图，没有任何尾帧概念，也没有能力声明（supports 之类）。**

#### kling —— `lib/video-providers/kling.ts`

- 端点 `POST {base}/v1/videos/image2video`，body 组装在 76-93 行
- 首帧走 `image` 字段，**裸 base64**（不是 data URL），`fileToBase64` 在 28-31 行
- 认证特殊：access_key + secret_key 现算 HS256 JWT（`createKlingJwt`，9-23 行），队列在 `lib/video-queue.ts:256-260` 调 `getKlingToken`
- 已有的模型分支先例：86-93 行，`if (/v3|3\.0/i.test(request.model))` 才加 `multi_shot`/`shot_type`，注释明说老模型（kling-v2-5-turbo）会拒绝这两个字段。**按模型加字段这件事这里已经有成熟写法可抄。**

#### jimeng —— `lib/video-providers/jimeng.ts`

- 端点 `POST {base}/contents/generations/tasks`（火山 Ark 协议）
- body 是 `content` 数组（79-96 行），现在是 `[{type:'text'}, {type:'image_url'}]`，**image_url 那项没有带 `role` 字段**

#### openai-video —— `lib/video-providers/openai-video.ts`

### 2.5 队列现状

`lib/video-queue.ts`（583 行），单任务执行在 265-324 行：

- 266-277 行：`SELECT * FROM image_assets WHERE id = ?` 查 `job.sourceImageId`，取 `processedPath || path`，mimeType 兜底 `image/png`。**只查一张。**
- 298-309 行：组装 `adapter.submit({model, prompt, sourceImagePath, sourceMimeType, durationSec}, apiKey, baseUrl, signal)`

## 3. 外部 API 事实（已查证）

### 可灵 image2video 尾帧

- 字段名 `image_tail`（部分第三方转发平台写作 `imageTail` / `tail_image`）
- 约束：JPG/PNG、≤10MB、边长 ≥300px、**必须与首帧同时传**
- 语义：给首尾两张图，模型自动补中间运动
- **版本支持不确定**：1.0/1.5/1.6 明确支持；2.5-turbo 只在第三方平台（Pollo AI 等）的封装文档里看到 `imageTail`，官方直连 API 对 2.x/3.x 的支持没查到确证。**这是最大的未验证点** —— 团队主力恰好是可灵 2.5/3.0。

### 即梦 Seedance 首尾帧

- 在 `content` 数组里放两个 `image_url`，分别带 `role: "first_frame"` 和 `role: "last_frame"`
- 现在代码里首帧**没有带 role**，一旦加尾帧，首帧必须补上 role，否则 Ark 会当成参考图模式
- **Seedance 2.0 的三种模式互斥**：单首帧图生视频 / 首尾帧 / 多模态参考（参考图+参考视频+参考音频），不能混用

### openai-video 网关

`images` 数组第二个元素是否被当作尾帧 —— **无任何文档依据**，需要对照《小林生影_AIGC模型调用文档》确认。另外尾帧同样要走 COS 拿预签名 URL，网关读不到本地路径。

来源：
- https://docs.router.shengsuanyun.com/7438181m0 （可灵 API）
- https://docs.apiyi.com/api-capabilities/seedance2/overview （Seedance 2.0）
- https://docs.pollo.ai/m/kling-ai/kling-v2-5-turbo （Kling 2.5 Turbo，imageTail）
