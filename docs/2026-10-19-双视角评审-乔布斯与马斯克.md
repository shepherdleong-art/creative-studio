**证据边界**：数据库是本机开发库，21 个项目里混有测试项目；成片成本是文档估算而非供应商实扣；「首版合格率」样本只有两份完整复盘（6 条），存在选择性记录偏差。下文所有数字都按这个口径读。

**来自考古的七个硬事实（本轮补充）**

1. **首页三处文案来自三个产品年代**：hero 说「做成一整套素材」；新手引导说「上传参考图和待编辑图……导出报告」；空状态说「创建第一个批量图片编辑项目」。同一页在卖三个不同产品（`app/page.tsx:199-233,355-356`）。
2. **错误用原生弹窗播报**：`alert()` 80 处、`confirm()` 14 处，工作台单页 21 处。整套 Apple sheet 视觉语言旁边，是 1995 年的浏览器弹窗（详细分布见 `outputs/2026-10-19-review/01-product-ux.md` F2）。
3. **第 5 步是两套产品**：单条混剪 991 行、批量生产 2525 行，用户进门先选模式；单条内部 4 个子步，标签却写成 STEP 01 → STEP 05。同一个流程还有「模块 2/3/4」与「第 2/4 步」两套叫法。
4. **真实主业务不在 UI 里**：按你的 SOP 与 P1 验收，当前主力业务是实拍重组——Agent 做 6 步，人只审片；但这条路径在产品 UI 里的入口数是 **0**，起点在 Claude Code + `scripts/reassembled-workbench.mjs` + Electron 深链。10 月的 15 条订单也全部不进 `workbench.db`。
5. **真正的魔法藏起来了**：审片页点一下 → 换一个镜头 → 新版本自动写回原目录（v3→v4，12/12 技术检查），这是全产品唯一「人花 30 秒、系统承担全部风险」的时刻；批量同屏 28 条 + 重复素材红框，是唯一「只有这个产品能做」的判断。两者都不在门面上。
6. **批量产线有一处静默降级**：`batch_task_attempts` 里语义匹配 680 次尝试，成功 29 次、失败 646 次（95%），实际一直走关键词兜底——这解释了为什么「素材错配」返工反复出现。
7. **静默失败是一种系统性模式**：核心迁移 98 条全部 `catch {}` 吞错、没有版本账本；队列轮询失败只 `console.error`；页面加载失败渲染成「项目不存在」；语义匹配失败静默降级。产品、数据、产线三层的失败都在「假装没事」。

## 一、Steve Jobs 看这个项目

### 一句话判决

**你做出了一个了不起的车间，但它还不是一个产品。**

我先说清楚：这不是 bullshit。你拥有从一张产品图到一条成片的整条链，而且是本地的、可复现的、带版本交付的。大多数团队会把五个 SaaS 拼在一起，你选择自己做整台机器——这叫 the whole widget。我喜欢这个决定。

但一个产品不是「你能做多少事」，而是「用户为什么非你不可」。你今天答不上来。而且 5 个月 42 条成片、月均 8.4 条——这是一个很好的试点，还不是一个品类。

### 我会先承认的三件事

**1. 你控制了整条体验链。**
图片、分镜、脚本、视频、混剪、渲染、交付，全在自己手里。你甚至自己定了渲染契约（`lib/media-core/render-contract.ts` 的 24fps / 20 帧片头），自己做了固定渲染命令。这意味着你能对最终画面负责，而不是把责任推给某个 API。这是对的。

**2. 你在看不见的地方也做了工艺。**
379 个测试、74,281 行测试代码、固定的渲染契约、12/12 技术检查、幂等导入、人工修改不被 Agent 覆盖、版本化交付、旧版归档。你的 `schema-upgrade/` 把迁移当分布式事务来做：跨进程锁、Online Backup + 完整性校验、可修复审计、失败只降级不阻塞旧功能——这是全仓最该保留的 930 行。你的 `render-contract.ts` 用 16 行常量把「差一帧」的血案固化成单一事实源。木匠不会在柜子背面用胶合板——你也没有。这是我最看重的部分。

**但你把最好的工程做在新模块，地基还是旧的。** 核心迁移 98 条全部 `catch {}` 吞错、没有版本账本；`final-edit` 在新库里缺了 v4（旧库还留着 v4），账本已经分叉。新模块有 gate、有审计、有备份，老地基在假装没事。这不是能力问题，是优先级问题。

**3. 你有真正的「技术与人文的交汇」。**
`docs/「痛点解决型」15s AI脚本生产标准 V1.0.md` 是一份 500 行的内容方法论：卖点 → 用户利益 → 痛点 → 人群 → 场景 → 匹配强度。这不是 prompt 技巧，这是你对「什么是一条好片」的判断。这才是你的护城河——不是 ffmpeg，不是 194 个 API，是这套标准。可惜它现在藏在 docs 里，没有变成产品的一部分。

### 我会当场砸掉的五件事

**1. 首页在卖工厂，不卖成片。**
首页大标题是「把复杂产品 做成一整套素材」，副标题是「场景图生产 · 分镜管理 · 视频任务准备。从一张场景图出发，自动并发、保存、导出。」

这是一个功能清单，不是一句话定义。而且它甚至说错了：你现在交付的是成片，不是「素材」。用户要的是「一条能投放的片」，不是「一套素材」。这句话像 2016 年的工具官网，不像 2026 年的产品。

更糟的是，同一页还有两段更老的文案：新手引导让你「上传参考图和待编辑图……导出报告」，空状态让你「创建第一个批量图片编辑项目」。这是三个产品年代的化石叠在一个首页上。用户第一次打开，就被教了一条不存在的路。

再往下四个数字：21 项目 / 347 已完成任务 / 0 运行中 / **13/13 供应商已配置**。前三个是过程指标，最后一个是工程自嗨。没有人为「13 个供应商」激动。用户只想知道：这个月你帮我出了几条片？哪条能直接用？

「13/13 供应商已配置」是 bullshit。把它从首页拿掉。

**2. 一句话说不清它是什么。**
五个步骤、两个额外入口（创作画布、批量成片）、一个 Agent skill、两种名字、四种运行形态（dev server / 桌面版 / 免安装 / 安装包）。你给用户的是五个门，门后面是同一间房。

如果你不能用一句话说清楚它是什么，这个产品就有问题。你的品牌 spec 里其实已经写出了一句比首页好的话：「一件产品的整条内容流水线，装在一台笔记本电脑里。」但那还是在描述机器。真正的一句话应该描述结果。三个候选，挑一个，别都留着：

1. **一张产品图，一条能投放的片。**（推荐，最像 iPod 那句，结果导向）
2. **把一件产品，做成一条片。**（你品牌 spec 里的，动作导向）
3. **每一件产品，都有一条能投放的片。**（规模化承诺，适合对内/对外都讲）

还有一句必须回答的话：**为什么是你，而不是那四家也叫「造境」的同类产品？** 你的品牌研究已经证明这个赛道很挤。如果只做内部工具，这个问题可以不答；如果要对外发行，「本地优先 + 整条流水线 + 批量审片 + Agent 接入」目前还是一串功能，不是一句「非你不可」的理由。真正的理由可能是那套 15 秒脚本标准——它代表一种对「什么是一条好片」的判断，而不是又一层生成能力。

**3. 第一次打开看不到魔法。**
一个新用户要看到第一条成片，得先干什么？配 13 个供应商、填 key、配公司网关、配 COS、建项目、上传、跑 5 个步骤、等模型、审片、渲染。这是 onboarding，不是产品。

iPod 是「1,000 songs in your pocket」，不是「支持 5GB 存储和 13 种编码格式」。你的产品也需要一个「一千首歌」的瞬间：让他打开就看到一条已经做好的片，5 分钟内看完整个流程，然后再让他配置自己的 key。**示例工程不是文档，是产品的一部分。** 你现在连一个 zero-config 的 sample 都没有。

**4. 你在让用户操作机器。**
五个步骤的导航暴露的是你的流水线：新场景图 → 分镜 → 脚本 → 视频 → 智能混剪。用户每时每刻都在想「我现在在第几步」。但你的真实使用记录说得很清楚：Agent 在选材、编排、审图，用户只审最终片（`docs/2026-10-08-BS619-A-开头偏差与耗时复盘.md`：「中间审核仍由 agent 实际看图，用户只审最终片」）。那你为什么给用户一个操作五台机器的控制台？

更难看的是机器漏出来的地方：80 处 `alert()`、14 处 `confirm()`；第 5 步只有 4 个子步却写着 STEP 01 → STEP 05；同一个流程一会儿叫「模块 4」一会儿叫「第 4 步」；项目加载失败时，界面告诉你「项目不存在」，而不是「网络断了」。**界面在模仿 Apple，但它没有消失。** 白色、大圆角、系统字体、发丝线——这些是表层。Apple 的真正教训是：界面退到任务后面。你的界面在任务前面，而且是五个步骤的仪表盘。用户不该「用工作台」，用户该「看片、挑片、交片」。

**5. 你最好的东西藏在后面。**
审片页点一下、换个镜头、新版本自动写回原目录——人花 30 秒，系统承担全部风险。这是你的「一千首歌」。但它的入口是命令行 + Electron 深链，在产品 UI 里是 0。你却在首页拿「13/13 供应商」当卖点。把最好的东西搬到门口，把最丑的东西收进抽屉。

### 我会怎么重做

**先把首页变成成片墙。**
最好的 6 条成片，全屏，自动播放，带封面和时长。下面只有一个按钮：「开始一条片」。数据只留一个：「本月交付 N 条成片」。供应商、任务数、运行中——全部进设置或「高级」。

**再做一个 zero-config 示例。**
预置一个家具项目、几张真实素材、一条已经渲染好的成片，加一个 60 秒的引导。用户点击「看它怎么做的」就能看到五步的展开；不想看就直接改自己的产品图。先给结果，再给机制。

**默认流程改成「导演椅」，不是「工作台」。**
用户说「做一条 15 秒的床的种草片」，Agent 跑完 1–4 步，把 3 条候选放到一个审片队列里。用户只做三件事：看片、点通过/重做、交付。五步工作台保留，但作为「高级视图/排障视图」，不是在主航道。

**砍掉或降级创作画布。**
节点式无限画布是另一个产品，它和「把一条片做出来」不在同一条关键路径上。它有自己的调度器、自己的 12 张表、自己的导出。把它从主导航拿掉，放进 Lab，或者干脆等主产品成立后再做。

**名字这周定，不要再做 VI。**
你的品牌研究已经做得很好了：造境被四家同类占用，打样间冲突最低。对外用打样间，内部继续叫造境，都可以。但名字不是产品，产品才是产品。选一个，改显示名，继续走。不要再用一周做第三版字标——那是在拖延真正的问题。

**最后，给产品一个「首映」。**
渲染完成后，不要直接跳到一个文件列表或 ZIP。给一个放映屏：一条成片、封面、时长、技术检查通过、一个「交付」按钮。让用户在看片的那一刻感到「这是我的作品」。这是产品的情感回报，你现在把它做成了「导出成功」。

### 这周我会做的一件事

把首页从「功能 + 任务数 + 供应商」改成「成片墙 + 一个动作」，再塞一个 zero-config 示例。就这一件事。做完之后，你会立刻知道产品到底缺什么——因为用户会开始问「为什么这条片不能用」，而不是问你「这个功能在哪」。

## 二、Elon Musk 看这个项目

### 一句话判决

**你在第 5 步（自动化）上很努力，但第 1 步（质疑需求）和第 2 步（删除）还没做。**

先算。728 个 commit、99 张表、194 个 API、8 个 schema 写入者、7 个调度入口、379 个测试、13 个供应商，5 个月换来约 42 条成片（月均 8.4；10 月两天峰值 15 条）。已记录的 API 账只有 ¥211.57；单条总成本约 ¥26–64，其中 API ¥13–22、人工 ¥13–42。这个比值不对：机器的复杂度，远大于它今天交付的产出；而成本的大头不是 API，是人的时间与返工。

具体一点：7 个调度/队列入口、5 条 ffmpeg 构图路径、4 套导出、8 个 schema 写入者（相当于每个项目配 4.7 张表）；批量生产一个功能 43 条 API；第 5 步里塞了两套产品（991 行 + 2525 行）；统一审片的单屏是 1641 行时间轴 + 801 行工作区 + 14 个快捷键 + 8 种颜色。你在用剪辑软件的复杂度，解决「判断这条能不能交」的问题。这不是工程能力，这是复杂度失控。

还有一件很讽刺的事：你有 74,281 行测试、测试:产品 = 1:2.0，却没有 CI，也没有一个能一次跑完的总入口。你建了一个质检部门，却没把它接到产线上。379 个测试文件靠人记得去跑——那它就不是质量体系，是资料库。

### 先算清单位经济

**成本结构（按文档估算 + usage_ledger）**
- 单条成片 API 成本（图片 + 视频，未计 TTS）：XQ5A 约 ¥12.7/条，BS619 约 ¥20.8/条
- 端到端墙钟时间/条（含编排、等待、审片、返工，不等于纯人工）：XQ5A 约 24 分钟（96 分 44 秒 / 4）；BS619 首批约 45 分钟（90 分钟 / 2）
- 生成本身不是算力瓶颈（但等待占墙钟 73%）：可灵中位数 175 秒，Seedance 263 秒，图片 88–108 秒，两条渲染各约 60 秒
- 有完整复盘的两个批次：**首版 6 条，6 条被拒收或要求返工**

**白痴指数（内容版）**
一条成片对你们值多少钱（这个数字你们自己知道，可能是几百到几千块）；它的原材料成本是「一张产品图 + 一份脚本 + 几十秒模型推理」，几块钱。中间的差价不在 API，在**人的审片和返工**。这就是你要攻击的地方。你现在在优化 API 成本、供应商数量、界面功能——那些都不是主要矛盾。

### 成本结构：先把视频生成的浪费砍掉

- 视频生成占已记录成本的 **82.8%**；每镜出 5 秒、成片只用约 2 秒，直接浪费约 20%
- Seedance 2.5 单价是可灵 3.0 的 **3.2 倍**；只有开场需要 Seedance，正文全用可灵
- 8–9 镜压到 6–7 镜，成本线性下降；图片渠道有 **6.3 倍价差**（¥1.58 vs ¥0.25/张）
- 乐观估计：单条 API 从 ¥21.5 降到 **¥11–14（-35–50%）**，不牺牲成片数量

这些都不是「加功能」，是「停止浪费」。先做这个，再谈优化。

### 五步算法诊断

| 步骤 | 你应该做的 | 你实际做的 |
|---|---|---|
| 1. 质疑需求 | 每条需求附上提出者的名字：创作画布是谁要的？五步导航是谁要的？13 个供应商是谁要的？ | 没有记录需求所有者。功能在增加，提出者在消失 |
| 2. 删除 | 删掉不增加核心价值的东西；删到过头再补回 10% | 画布、五步导航、重复的迁移流、多供应商手工配置都还在 |
| 3. 简化 | 把剩下的流程压成一条 | 五个入口、两种名字、四种运行形态 |
| 4. 加速 | 缩短循环时间 | 动态队列、并行、审查前置——这部分你做得不错 |
| 5. 自动化 | 最后才自动化 | Agent + 固定渲染——你已经做了，而且做得不错 |

**顺序是反的。** 你在 4 和 5 上投入了很多，但没有做 1 和 2。自动化一个不该存在的流程，是最大的浪费。

### 墙钟瓶颈是等 API；成本瓶颈是返工

先纠正一个直觉：**当前墙钟的 73% 在等供应商**（图片 + 视频），审片约 17%，渲染只占 4%。把渲染从 105 秒优化到 37 秒，对一条 24 分钟的片影响不到 1 分钟。生成速度不是靠更快的模型解决，是靠并发与调度——你已经在做。

但最该动的不是并发，是返工。你有 **35–40% 的生成请求没有变成采用资产**；每条成片平均 **1.6 次返工事件**；其中结构保真 + 素材错配占 45.8%，这两类在提交给视频模型之前就能拦住。更糟的是：批量生产的「智能语义匹配」在 680 次尝试里失败了 646 次（95%），实际一直走关键词兜底——这就是素材错配反复出现的结构性原因。它不是一次返工，是一条静默降级的产线。

（还有一处更基础的：产品说 15 秒档写 54–59 字，SOP 说 15 秒最少 60 字；按产品建议写，交片会被打回。这不是文案 bug，是**没有单一事实源**。）

所以验证闭环要建在**提交前**，不是审片时：

1. **提交前产品一致性检查**：候选镜头先对照原始产品图检查结构、材质、比例、关键部件；结构敏感镜头强制人工确认，其余自动。
2. **参考锁定**：把「哪些部件必须保留」变成结构化约束，而不是 prompt 里的一句话。
3. **异常路由**：只把不确定的镜头交给人；结构类错误不走「生成后再看」。
4. **修语义匹配 + 禁止静默降级**：失败必须显式暴露，关键词兜底要标红；95% 失败率不是「可重试」，是产线坏了。
5. **评测集**：把 review marks、拒收原因、返工记录变成可重复跑的 eval；每次改 prompt/模型/流程，先跑 eval。

**不要做全自动。** 理论最短 7–9 分钟/条很诱人，但全自动等于拆掉结构/素材类返工的拦截点，按 35% 返工率，成本会被打回 ¥25–30/条。正确做法是「结构敏感镜头人工确认，其余自动」。

还有一条数据卫生：45 个批次里 36 个停在 `running`，没有终态——这意味着批次完成率根本没法统计。连状态机都没闭环，谈自动化早了点。

### 10x 会先碎在哪

当前墙钟瓶颈是等供应商。10x 时先碎的不是渲染，按顺序：

1. **一行 `let tail = Promise.resolve()`**：`lib/final-edit/heavy-job-lock.ts` 用 6 行把整个进程的分析、TTS、渲染、包装串成一根链条；44 次 prepare 均值 75.1 秒、最长 269 秒、累计 55 分钟纯串行，且没有并发旋钮。这是你最便宜的吞吐上限。
2. **供应商限流**：视频并发默认 10、21/21 个项目都开到 10，没有全局预算；429 冷却只存在内存，重启即失忆。10 个项目同时开跑 = 最多 100 个并发打同一把 key。
3. **ffmpeg 没有全局闸门**：5 个局部额度上限相加没有任何总上限；CPU 被打满时所有任务一起变慢。
4. **存储/版本**：324MB/项目、162MB/条、版本文件比独立成片多 92%，正式产物只增不减；10x 约 68GB，介质便宜，检索和清理不便宜。
5. **SQLite**：排第 5，不是第一。WAL 单写者会疼，但 10 倍写入仍在舒适区；真正的风险是长事务/迁移锁，不是吞吐。

这个顺序和直觉相反：会先死的不是数据库，是那 6 行锁。**最贵的用户等待，往往是最便宜的代码造成的。**

### 我会删掉的三个东西

1. **创作画布**：不在「产品图 → 成片」的关键路径上，却带着自己的调度器、12 张表、自己的导出。删掉主入口，保留代码做实验。失去的是「节点式探索」，但那不是今天的瓶颈。同样的问题也出在批量审片：保留「重复素材识别」，但把 4 轨时间轴、14 个快捷键、8 种颜色的非线性编辑层降级——审片的价值是判断，不是剪辑。
2. **重复的迁移流/任务流**：8 个 schema 写入者（core、final-edit、batch、canvas、script-studio、usage、video_providers、seed）；7 个调度入口累计约 5,600 行；99 张表。不是让你今天重写，而是冻结新增，做一个统一的 schema/任务契约路线图。失去的是「模块完全独立」，得到的是可维护性。架构考古还会指出：`script-studio` 的第二套队列语义是「为默认关闭的形态付的维护税」——保留同步生成，删掉那套调度，是比删整个模块更划算的一刀。
3. **多供应商手工配置**：13 个启用的供应商暴露给用户选，是把内部复杂度外化。按成本/质量/可用性自动路由，设置页只给管理员。失去的是「手动指定」，得到的是默认正确。

**但有一件事不要按代码体积删：实拍重组。** 架构考古把它列为删除候选，因为它最新、最窄、只在桌面模式可用；可它是你当前的**真实主业务**，还带着全仓唯一可复现验证的渲染契约（spec + sha256 + SSIM + 金样）。它的问题不是该不该存在，而是它不该藏在 CLI 和 Electron 深链里。把它搬到产品正面，别删。

### 这周我会做的一件事

**先埋点，再删功能。** 在 BS619 复盘里你自己已经列出了要打点的阶段：开工、输入解析、提交、返回、审查、返工、渲染、交付。把它们变成一张仪表盘：

- 每周合格成片数
- 首版合格率 / 返工率
- 每条成片的端到端分钟数（并单独记录其中的人工注意力分钟）
- API 等待占比（当前 73%）
- 每条成片的 API 成本（视频占 82.8%）
- 返工原因分布（结构保真 + 素材错配 = 45.8%）

然后，任何不改善这几个数字的功能，先不做。**没有基线的优化都是自嗨。**

名字不重要。打样间能用，造境也能用（如果只内部用）。三套 VI 里，「机房」那版有时间码，是这台机器唯一诚实的视觉证据；但品牌不是瓶颈。把时间花在首版合格率上。

## 四、合并裁决：如果只能做一件事

**把产品从「工作台」改成「导演椅 + 放映厅」。**

三句话：

1. **一个动作**：Agent 生产 → 人审片 → 通过 → 交付。其他都是这个动作的支撑。
2. **两个视图**：成片墙（结果）+ 待审/异常队列（需要你判断的片）。五步工作台保留为 drill-down，不是默认首页。
3. **一个指标**：每条合格成片的端到端分钟数（其中人工注意力是关键路径）+ 首版合格率。所有功能按这两个指标排序。

为什么是这件事：你的数据已经证明，人不是花在「操作五步」上，而是花在「判断这条片能不能用」和「返工」上。产品应该围绕判断设计，而不是围绕流水线设计。这也是你最近三个方向（批量统一审片、Agent 接入、固定渲染）的自然终点——它们都在把「操作」变成「审片」。

更直接的证据：你当前的主力业务（实拍重组）已经是 Agent 做 6 步、人只审片；而这条路径在产品 UI 里的入口数是 0。也就是说，产品事实上已经是一个审片/接管工具，只是门面还写着「五步工作台」。把它承认下来，产品会立刻变简单。

**如果这 30 天只能做一个改动：把默认入口从「五步工作台」换成「待审队列 + 成片墙」，并把 Agent 设为默认生产者。** 这一个改动会同时逼出首页、首启、指标、质量闭环四个问题的答案。

最后一个问题留给你的团队：**如果明天只能保一种生产形态，另外三种的 4 万行代码，谁来签字同意继续维护？** 这不是让你今天删，是让你知道「保留」也是一个需要负责的决定。

## 六、他们不会替你做的判断（诚实边界）

1. **这是内部工具还是对外产品？** 品牌研究里已经出现了这个岔路：如果只给部门用，打样间/造境都行，开源和安装包都不重要；如果要对外发行，竞争、定价、分发、支持都是新问题。两位评审都假设「先把它做成一个好用的内部产品」，这个假设需要你确认。
2. **真实用户只有你（和你的团队）。** 21 个项目里混着测试项目；没有第二支团队的使用数据。10 月 15 条订单不进 `workbench.db`，工程在 `outputs/`，部分已不在盘上——本机库不是完整生产账本。所有「用户会怎么想」都是推断。
3. **返工率的样本仍然有限。** 「首版 6 条 6 条返工」是两份完整复盘的样本；更大样本（15 条订单）的返工率约 35–40%。两者都指向返工是主要成本，但具体数值区间仍宽。
4. **成本是估算，不是账单。** `usage_ledger` 只覆盖约 37–39% 的视频秒数与 11% 的图片，¥211.57 不是真实总成本；人工分钟数是基于墙钟与触点的假设（±50%）；全库没有售价/回款数据，所以毛利、回本、单位经济是否成立无法计算。
5. **架构考古的「删除候选」不是判决。** 它按「维护面 / 用户价值」算出画布、实拍重组、脚本调度是最该删的三项；但实拍重组是你的主业务，脚本调度的价值也可能在未来。报告给的是权衡，不是结论——删不删由你，但每个「保留」都要有人负责。
6. **角色扮演不是本人。** 乔布斯 2011 年后没有公开表态；马斯克 skill 截止 2026-04，且他的框架在社会/审美领域会系统性偏弱。这两位给你的是一副镜片，不是判决书。
