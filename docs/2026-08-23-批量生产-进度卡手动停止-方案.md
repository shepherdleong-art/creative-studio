# 批量生产进度卡增加手动停止（方案留存）

日期：2026-08-23

## 背景与根因

批量生产开跑后若卡在「匹配画面语义 进行中 · 0/1」（供应商 API 连不上或执行器挂起），界面上没有任何办法让它停下来。

调查结论：**后端能力已完整存在，缺的是第 2 步进度卡上的控制入口**。

- `POST /api/batch-production/batches/[id]/control` 已支持 `pause` / `resume` / `stop`（`app/api/batch-production/batches/[id]/control/route.ts`）。
- `stopBatch`（`lib/batch-production/scheduler.ts:625`）：批次 `controlState → stopped`，queued/failed 任务直接 cancelled，running 任务由调度心跳感知后收敛 cancelled；已成功的结果保留，历史不删除。停止是终态（`resumeBatch` 对已停止批次报错）。
- 面板里 `controlBatch(action)` 已存在（`components/batch-production/BatchPreparationPanel.tsx:1417`），但此前只传给了第 3 步 `BatchStepReview`（那里有 暂停批次/继续批次/停止批次 三个按钮，`:180-188`）。
- 卡顿时展示的「生产进度」阶段列表卡是 `BatchProductionProgressCard` 的 full 变体，渲染在第 2 步 `BatchStepScripts.tsx:1182-1184`；compact 变体在 `BatchPreparationPanel.tsx:1665-1667`（activeStep > 1）。该卡此前纯展示，无任何控制。
- `workspace.batch.controlState` 在选中批次后即加载、生产期间每 3s 轮询（`BatchPreparationPanel.tsx:507-517`），第 2 步同样拿得到新鲜状态。

## 改动方案（UI-only，不动后端/调度器）

### 1. `components/batch-production/BatchProductionProgressCard.tsx`

新增可选 props（不传则保持现状纯展示）：

```ts
controlState?: 'running' | 'paused' | 'stopped';
controlBusy?: boolean;
onControl?: (action: 'pause' | 'resume' | 'stop') => void;
```

- full 与 compact 两个变体的头部右侧渲染控制按钮，样式与第 3 步一致（`btn-secondary text-xs`，停止加 `text-fail`）：
  - `controlState === 'running'` → 「暂停批次」
  - `controlState === 'paused'` → 「继续批次」
  - `controlState !== 'stopped'` → 「停止批次」
  - 按钮 `disabled={controlBusy}`，加 `aria-label` 便于契约测试定位；全部任务终态（`finished`）后按钮隐藏——批次已经跑完，暂停/停止没有意义。
- 头部状态文案：`stopped` 时显示「已停止 · 总用时 X」（替代此前会误显示的「已完成」）；`paused` 时显示「已暂停 · 已用时 X」；其余沿用现有 已完成/生产中 逻辑。
- full 变体阶段列表：`controlState === 'stopped'` 时，状态为 running/waiting 的阶段行右侧文案显示「已停止」、图标按 waiting 中性样式（不伪报「已完成」）。

### 2. `components/batch-production/BatchStepScripts.tsx`

- Props 接口（`:109` 附近）新增 `controlState`、`controlBusy`、`onControlBatch` 三个可选字段。
- `:1182-1184` 渲染 full 进度卡处透传给 `BatchProductionProgressCard`。

### 3. `components/batch-production/BatchPreparationPanel.tsx`

- 调用 `BatchStepScripts` 处（`:1750` 起）传入：
  - `controlState={workspace?.batch.controlState}`（workspace 未加载时 undefined → 按钮暂不显示，选中批次后第一次轮询即出现）
  - `controlBusy={phaseEBusy !== null}`
  - `onControlBatch={(action) => void controlBatch(action)}`
- compact 变体调用处（`:1665-1667`）同样传入这三个 props，让第 3/4 步顶部的紧凑进度条也能停（第 3 步卡片自带的按钮保留，不冲突）。
- `controlBatch`（`:1417`）在成功后补一次 `await loadTasks(selectedBatchId)`：停止后轮询会随 `shouldPollBatch` 变 false 而停，需要这一次性刷新让阶段列表立刻落到 cancelled/已停止，而不是等 3 秒或停留在「进行中」。

### 4. 契约测试 `scripts/batch-preparation-workspace.test.mjs`

追加源码断言（与现有风格一致）：

- `BatchProductionProgressCard.tsx` 含 `onControl`、`停止批次`、`已停止`；
- `BatchStepScripts.tsx` 含 `onControlBatch`；
- `BatchPreparationPanel.tsx` 中进度卡两处用法均传 `controlState`。

## 验证

1. `npx eslint` 改动三个组件文件 + `npx tsc --noEmit` 通过。
2. `node scripts/batch-preparation-workspace.test.mjs` 通过。
3. 本地 `npm run dev` Playwright 实测：进 G564 项目 → 批量生产 → 选运行中/卡住的批次 → 第 2 步进度卡出现「暂停批次/停止批次」；点「停止批次」→ 批次变「已停止」、阶段行不再显示进行中、按钮消失；再进第 3 步确认原按钮行为不受影响。

## 明确不做

- 不改 `stopBatch` 语义、不加自动超时/重试（那是「卡住」的根因治理，超出本次范围）。
- 停止是终态不可恢复——与第 3 步现有「停止批次」行为一致，不额外加二次确认弹窗（保持两处一致；如需要可后续统一加）。
- 不动第 3 步 `BatchStepReview` 已有按钮。

## 后续修复（同日，用户实测反馈）

停止按钮上线后实测暴露了两个更深层的问题，已一并修复：

### 1. 停止后再点「开始批量生产」卡死（僵尸态）

**现象**：停止批次 → 再点开始 → 没反应；回来看进度条还在走。

**根因**：`stopBatch` 只把 `controlState` 置为 `stopped` 并终态化任务，而 `PUT /start` 的语义门禁（`prepareBatchSemanticScoreBeforeStart`）会照常排队新的打分任务——调度器 `claimNextTask` 只认 `controlState='running'`，这批任务永远不会被领取，形成「已停止但进度条还在走」的僵尸态。

**修复**：

- `lib/batch-production/scheduler.ts` 新增 `reactivateBatchForStart`：显式开跑时把 `paused`/`stopped` 批次重新激活为 `running`。与 `resumeBatch` 的语义边界：调度器不得擅自复活已停止批次，但用户点击「开始」是显式新动作。
- `app/api/batch-production/batches/[id]/start/route.ts` 在语义门禁之前调用它。
- `BatchPreparationPanel` 计时器加 `batchStopped` 闸门：已停止批次残留的 queued 任务不再让「已用时」空转。

### 2. 语义匹配无限重试循环（「卡死」的真正根因）

**根因链**：供应商 API 故障 → 打分任务每次 ~1s 快速失败（`semantic_fallback`）→ 前端「任务终态后自动续跑」再次打 `PUT /start` → 门禁的 `queueBatchSemanticScoreTasks` 把 failed 任务**无条件**原地回 queued → 再失败 → 再复活……实测 16 分钟白打了 306 次供应商 API，UI 永远显示「匹配画面语义 进行中 0/1」。设计文档本来就写了「打分失败/不可用不阻塞开跑」，这个循环违背了它。

**修复**（`lib/batch-production/semantic-match.ts`）：

- `queueBatchSemanticScoreTasks` 新增 `reviveFailed: 'always' | 'auto'`（默认 `always`，手动「重新生成语义匹配」与确认快照入口行为不变）。
- 开跑门禁 `prepareBatchSemanticScoreBeforeStart` 走 `auto` 档：失败任务的尝试次数低于 `SEMANTIC_SCORE_MAX_AUTO_ATTEMPTS`（3）才复活；达到上限后保留 `failed`，门禁 pending 归零，开跑流程按设计意图走关键词兜底继续生产。
- 附带修复：同 requestKey 的**已取消**任务此前被幂等跳过吞掉（停止后再开跑同一版本时打分永远不会重建），现在落到 `createBatchTask` 的 requestKey 释放路径重建新任务。
- 附带修复：进度卡「自动配画面」阶段此前在语义失败时直接标红「失败」，但兜底分配实际会成功——现在该阶段只看分配是否完成，语义失败由「匹配画面语义」阶段自己如实展示。

**实测确认**（批次 8，修复前已积累 307 + 148×2 次无效尝试）：点开始 → 已达上限的失败打分任务不再复活 → 关键词兜底分配 → 口播 2/2、渲染 2/2、封面 2/2 全部完成，阶段列表如实显示「匹配画面语义 失败 · 0/3」而其余阶段已完成。

**测试**：`scripts/batch-semantic-match.test.ts` 新增门禁上限、手动复活不受限、取消任务重建三个用例；`scripts/batch-scheduler.test.ts` 新增场景 6b（停止→显式开跑→重新激活→新任务可领取，暂停同理）；契约测试补 `reactivateBatchForStart` 与计时器闸门断言。
