# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev                  # Dev server at localhost:3000; predev first tries to start the LiteLLM sidecar (failure only disables company providers, never blocks dev)
npm run dev:win              # Dev server at 127.0.0.1 (Windows)
npm run dev:desktop          # Compile the Electron payload and run the desktop shell against an existing `npm run build` standalone output
npm run build                # Production build (next build + sync standalone assets)
npm run lint                 # ESLint
npm run icons                # Regenerate app icons from source art
npm run build:win-installer  # Build Windows installer (PowerShell/Inno Setup; run on Windows)
npm run build:mac-installer  # Build macOS DMG (bash; Apple Silicon host, requires Node 22.x)
```

Two macOS double-click entry points exist and must stay distinct: `start.command` runs the **web** app (dev server on 3000, opens a browser), while `start-desktop.command` runs the **desktop** shell (Electron + private Node service on a random loopback port, consuming the production standalone output; `--rebuild` forces a fresh `npm run build`). Both share the same project data root, so they must not run at once — the desktop entry warns when 3000 is occupied. The packaged `.app` deliberately excludes `config.yaml` and `.venv-litellm/`, so **company-scoped providers work only in source runs, never in the installed app**.

Company-gateway local stack (macOS / Windows source runs): when `.venv-litellm` and `config.yaml` are present, `start.command`, `start-desktop.command` and the `npm run dev` `predev` hook all use `scripts/start-litellm.sh` on macOS and `start-windows.cmd` uses `scripts/start-stack.ps1 -SkipApp` on Windows to bring up the LiteLLM proxy before the app starts. Both launch commands must explicitly pass `--host 127.0.0.1`; dependencies are pinned in `requirements-litellm.txt`, and a missing or failed sidecar only disables company-scoped providers. The Windows portable package does not use a venv: it ships a built-in `python-runtime/` (portable Python 3.12.10 + LiteLLM 1.89.2, gitignored), its root `start-windows.cmd` is generated from `installer/windows/start-windows-portable.cmd` and always passes `-Portable`, which validates `portable-manifest.json` (schemaVersion 1 / `windows-portable-v1` / key-file list) and launches the proxy via `python-runtime\python.exe scripts\start-litellm-proxy.py`; corruption means "re-copy the package", never online repair or venv/system-Python fallback. Portable packages are assembled whitelist-only by `scripts/build-windows-portable.ps1 -OutputPath <new dir>`. Public delivery of reference images goes through Tencent COS (`CREATIVE_STUDIO_COS_*`, see `lib/cos-media.ts`). Security constraint: local services (app and proxy) must never be exposed to the public internet — COS is the only public delivery path. Platform stop scripts, Ctrl+C in the start window, and the UI shutdown button (`/api/shutdown` reads the controlled `stopScript` in `storage/run/stack.json`) all tear down the proxy too. `storage/run/stack.json` is BOM-less JSON; `scripts/*.ps1` MUST stay UTF-8 **with BOM** — PS 5.1 misreads BOM-less Chinese and fails to parse.

There is no `npm test` script. Tests are standalone files under `scripts/*.test.ts` and `scripts/*.test.mjs`, run directly via Node's native TypeScript support (Node 22+):

```bash
node scripts/db-migrations.test.ts   # run a single test file
node scripts/<name>.test.ts          # pattern for any other test file
```

Portable-packaging boundary tests: `node scripts/python-runtime-windows.test.mjs` (runtime lock + build/verify contract), `node scripts/company-provider-startup.test.mjs` (start/stop + `-Portable` mode), `node scripts/windows-portable-payload.test.mjs` (portable assembly whitelist + manifest), `node scripts/standalone-desktop-boundary.test.mjs`, `node scripts/windows-installer.test.mjs`. `scripts/macos-installer-payload.test.mjs` needs the macOS toolchain and only runs on an Apple Silicon build host.

## Architecture

**Creative Studio** is a local-first AI asset production workbench — it turns a product image into scene images, shot sequences, scripts, video tasks, and rendered final edits, then exports a ZIP package. Built with Next.js 16 App Router + React 19 + SQLite (`better-sqlite3`). Ships either as a plain web app or as a packaged Windows/macOS desktop installer with a bundled private Node runtime.

### Core layers

- **`app/api/`** — REST API route groups for projects, jobs, images, shots, scripts, video, shutdown, and the versioned final-edit/mixcut workflow (context, scoped Module 4 assets, external assets, groups, variants, jobs, BGM and proposals)
- **`lib/`** — Business logic
  - `db.ts` / `db-migrations.ts` — SQLite init (WAL mode, foreign keys); `CORE_DB_MIGRATIONS` is an append-only flat SQL list applied after core tables exist, each wrapped in try/catch so already-applied columns/indexes are skipped
  - `schema-upgrade/` — shared safe-upgrade infrastructure: SQLite Online Backup, disk preflight, a cross-process SQLite write lock, repairable JSONL audit records, one shared gate, and verified recovery-candidate discovery; paths derive from `dataRoot()`
  - `batch-production/` — independent batch-production module; `schema.ts` uses versioned `IMMEDIATE` transactions and `readiness.ts` is the locked, audited gate behind every batch API. Published migrations v1–v13 cover the domain foundation, authoritative sources, structured script snapshots, lifecycle, and scheduler leases. Phase D uses v14 for managed LUT/cache/task-schema support and v15 for canonical LUT fingerprints, complete color snapshots, and durable `batch_proxy_requests` with batch-version lineage. Proxy tasks target durable requests rather than deletable cache rows. `requestProxy` validates project→batch→version→asset-pool ownership, reuses one global proxyKey/cache safely across versions, and preserves the request-frozen original/color identity. `proxy-cache.ts` owns controlled paths, in-process read/write leases, task-scoped cleanup, and persistent pending-delete that completes when the last lease releases. `proxy-executor.ts` re-verifies the request-frozen original and LUT fingerprints, runs FFmpeg under the existing scheduler with cooperative cancellation, and publishes only after a final request/cache check. `color-pipeline.ts` owns the explicit LUT interpolation and SDR filter contract; `preview.ts` chooses matching ready proxy or an honest original/warning fallback; `export-preflight.ts` requires re-verified originals and frozen LUT content and never falls back to proxy. Batch APIs expose snapshot/start/tasks, LUT management, proxy requests and task control, cache usage/cleanup, Range-aware preview, and read-only export preflight. `BatchPreparationPanel.tsx` provides the minimal Phase D LUT, proxy, task, preview, and cleanup UI, while settings provides all-project proxy cleanup. All batch APIs stay behind the shared readiness/backup/lock/audit gate, and Phase D does not implement Phase E allocation or formal rendering.
  - Batch-production Phase E adds migration v16, a pure deterministic whole-batch allocator plus persisted allocation runs/exclusions, original-media-only FFmpeg rendering through the existing scheduler, a storage-relative verified narration seam, append-only paired video/cover publishing, safe candidate/artifact media routes, and an aggregated card workspace. Silent placeholders are preview-only and cannot pass formal publication. Single-plan reallocation ("换一批画面") penalizes the target plan's current non-locked assets/windows (cover included) so repeated clicks keep rotating footage, derives its seed from the current version pointer (same-state retries stay idempotent), and never disturbs locked segments.
  - The Phase A project-media cards enqueue pre-snapshot local FFprobe analysis through the existing batch scheduler. Results are explicitly `technical`, never synthetic content analysis. Project media access resolves only `projectId + assetId`, re-verifies authoritative sources, full SHA-256, and the real container, then serves controlled 960×540 JPEG thumbnails and Range-aware original preview. Batch start no longer creates duplicate analysis tasks.
  - Semantic-priority allocation and cover titles land in migrations v17–v23: v17 content-analysis requests `batch_asset_analysis_requests` (freezes asset fingerprint + vision provider identity), v18 execution scope, v19 per-script target duration, v20 narration config, v21 `narration` workType, v22 asset-source verification fast path, v23 `semantic_score` workType + `batch_semantic_matrices` (keyed by content fingerprint, not bound to a version). `semantic-match.ts` scores script sentences against the pooled scenes via LLM, queued idempotently after snapshot confirm with `POST .../semantic-score` for manual trigger/provider switch; failed/unscored allocation falls back to keyword+quality matching without blocking start. `createSemanticScoreExecutor` completes+skips without content analysis and fails with code `semantic_fallback` on LLM errors; scoring and allocation share `splitAllocationScriptBody` sentence splitting. `cover-title.ts` reuses the global `final_edit_title_presets`: batch settings write `coverTitleMode('none'|'preset'|'custom')`/`coverTitlePresetId`/`coverTitleStyles`/`coverTitleFraming` into the version `defaultsJson` (UI always writes the full stable shape with current-ratio resolved styles; canonical comparison folds styles into the input identity automatically), and `batch-renderer.ts` composites primary/secondary titles onto covers via sharp SVG under the frozen styles — including after cover-frame regeneration. When no single scene interval covers a segment's estimated duration, the allocator falls back to intra-segment multi-clip stitching (`stitchSegment`: reason `semantic_stitch_fallback`, chunk clipIds carry `:part:<k>`, warning `stitched-segment:<id>`; `no-legal-media` is kept only for an empty/sceneless pool), and subtitle cues are cut once per segment across the merged clip window instead of repeating per chunk. `subtitle-cues.ts` routes narration-aligned sentences through `splitNarrationForDisplay` (punctuation cleaned, ≤16 chars per cue, char-weight proportional timing inside the aligned window, same as the estimated path). `PUT .../start` first runs `prepareBatchSemanticScoreBeforeStart` for draft versions — with scoring tasks still incomplete it returns `semantic_scoring` without freezing, and the frontend re-fires start automatically once tasks reach a terminal state; failed/unavailable scoring never blocks start. Batch rendering now opens with a cover intro on the same contract as single-video mixcut (`FINAL_EDIT_INTRO_DURATION_US`, 20 frames): the titled cover is generated *before* the video so it can be the intro still, audio is delayed and subtitle overlays shifted by the intro, and the verified output duration is intro + body — `script-duration-policy` already reserves those frames, so omitting the intro made every batch video systematically one cover short. Because the cover is baked into the video, `BATCH_RENDER_ADAPTER_VERSION` is `batch-render-v2` and the render `requestKey` includes `cover.timeUs`; changing the cover frame calls `scheduleRenderAfterCoverChange` to re-render that output instead of only rewriting the standalone cover file.
  - `video-provider-schema.ts` — safely upgrades the legacy `video_providers` CHECK constraint only when an `openai-video` provider is created or selected; normal database startup must not rebuild the table without a verified backup
  - `data-root.ts` — resolves the local data root for the current run mode (dev server / installed app / EXE, overridable via `CREATIVE_STUDIO_DATA_ROOT`); all local paths (`data/`, `storage/`) derive from this
  - `local-image-url.ts` — turns a local `storage/` image into an `/api/images/...` HTTP URL for gateway upstreams that only accept real URLs (e.g. Tencent); the address is auto-detected (first non-internal IPv4 + `PORT`/3000, overridable via `CREATIVE_STUDIO_PUBLIC_BASE_URL`), otherwise callers fall back to data URLs
  - `cos-media.ts` — Tencent COS reference-image relay. With `CREATIVE_STUDIO_COS_SECRET_ID` / `CREATIVE_STUDIO_COS_SECRET_KEY` / `CREATIVE_STUDIO_COS_DOMAIN` set (optional `CREATIVE_STUDIO_COS_PREFIX` default `ref-images/`, `CREATIVE_STUDIO_COS_URL_TTL_SEC` default 86400, `CREATIVE_STUDIO_COS_SIGN_HOST`), the `gateway-task-image` / `openai-video` adapters upload each reference image under its content SHA-256 name (GET `Range: bytes=0-0` dedup check skips re-uploads) and hand the gateway a 24h pre-signed GET URL; the `q-sign-algorithm=sha1` signature is hand-rolled with `node:crypto` (zero new deps) against the configured custom domain. Uploads are compressed by default before hitting COS (disable with `CREATIVE_STUDIO_COS_COMPRESS=0`; tune `CREATIVE_STUDIO_COS_MAX_BYTES` / `MAX_DIM` / `QUALITY`, defaults 2MB / 4096px / 90); video first/tail frames only compress above 4.8MB by default (`CREATIVE_STUDIO_COS_VIDEO_MAX_BYTES` / `VIDEO_MAX_DIM` / `VIDEO_QUALITY`, defaults 4.8MB / 4096px / q95, read via `getCosVideoCompressOptions()`; Tencent caps LastFrameUrl tail images at 5M and FileInfos first frames at 10M, rejecting larger ones with a 400 before task creation — the threshold takes the stricter limit with margin) to avoid blurring the video-generation start frame — only the transient COS copy is affected, never the local finished asset. CDN custom domains rewrite Host to the origin endpoint (e.g. `<bucket>.cos.ap-guangzhou.myqcloud.com`) and rewrite HEAD as GET — in that case set `CREATIVE_STUDIO_COS_SIGN_HOST` to the origin endpoint for signing, and never dedup via HEAD. When COS is unconfigured or an upload fails, adapters fall back to the `local-image-url` local-URL behavior. Keys live only in `.env.local`; never log signature parameters. Company-scoped script-provider vision calls (`completeJson` with images) use the same controlled transport: `tryUploadBufferToCosAndSign` uploads in-memory frames to COS and the model receives the pre-signed URL instead of inline base64; without COS configured, the execution gate (`provider-execution-gate.ts`, `transport_unavailable`) fails closed
  - `gateway-media-url.ts` — normalizes gateway result URLs (rewrites localhost/relative result URLs back onto the gateway origin) and downloads media with Bearer auth only when the target is the gateway origin
  - `queue.ts` / `video-queue.ts` — Async job polling queues
  - `providers/` — Image generation adapters (Packy, GeekAI, OpenAI-compatible, `gateway-task-image` for gateways that expose image models via the async `/v1/videos` task protocol)
  - `script-providers/` — LLM script generation through Gemini, OpenAI-compatible Chat Completions, OpenAI Responses/SSE, or Anthropic Messages (`/v1/messages`) adapters selected by persisted `apiStyle`
  - `video-providers/` — Video generation adapters (Kling, Jimeng, `openai-video` for New API-style gateways speaking the OpenAI `/v1/videos` protocol). Video tail frames (`video_jobs.tailImageId`) are gated by each adapter's `tailFrameCapability(model)` with exact-model allowlists: `jimeng` only for direct `doubao-seedance-2-0-260128` (Ark `first_frame`/`last_frame` roles); `openai-video` only for the verified company aliases in `lib/company-gateway-tail-frame.ts` — Kling `kling-3.0` uses Tencent-native `LastFrameUrl` + `OutputConfig.AspectRatio`/`Resolution='1080P'` (duration goes via `OutputConfig.Duration`: the gateway's LastFrameUrl branch does not forward `seconds` and falls back to the 5s default, while `OutputConfig` fields pass through to Tencent verbatim — verified by a real 10s task on 2026-08-18) (`images[1]` is treated as a reference image, disproven), Seedance `doubao-seedance-2-0(-fast)-260128` uses `images[1]`; company tail frames enforce loopback LiteLLM + COS presigned URLs for BOTH frames and fail closed before POST on any gate/upload failure.
  - `company-gateway-size.ts` — size whitelist and snap-to-whitelist logic for the company model gateway (llm-gateway-idc.linshimuye.com via a local LiteLLM proxy, config in `config.yaml`); the `gateway-task-image` / `openai-video` adapters snap requested sizes to the documented per-model combinations and add the required `response_format` only for company models; completed tasks often carry no result URL, so both adapters fall back to downloading from `/v1/videos/<id>/content` using the ORIGINAL submit-time task id (poll-response ids may lose the embedded model_id and misroute at the LiteLLM proxy)
  - `final-edit/` — Versioned final-edit schema, group/variant workspace, external-material import, timeline planning and FFmpeg rendering. Shared media foundations (storage paths, matching, cover title types/rendering, scene detection, video analysis, TTS and alignment adapters, and the `render-contract.ts` 24fps / 20-frame cover-intro constants) live in `media-core/` and are re-exported from the legacy final-edit paths for compatibility; `batch-production/` imports only from `media-core/`, never from `final-edit/`. Mixcut context and external assets are scoped by `projectId + shotSetId`; never infer grouping from filenames or timestamps
  - Final-edit prepare and batch narration jobs register one shared AbortController with the shutdown worker; TTS normalization/concatenation and five-minute prepare previews receive the task signal and interrupted prepare rows return to `queued` for lease-style recovery. Three intentionally short FFmpeg calls remain signal gaps by policy: `lut-catalog.ts:269` (10s), `project-asset-media.ts:230` (60s), and `final-edit/video-frame.ts:48` (30s); process-wide FFmpeg shutdown remains their fallback.
  - `image-output-normalize.ts` — Sharp-based crop/resize to target dimensions
  - `provider-concurrency.ts` — Per-provider concurrency limits
  - `ffmpeg.ts` — resolves ffmpeg/ffprobe (env → static package → PATH), probes media with an asynchronous fallback, runs final-edit renders with progress/timeout/error-tail handling and AbortSignal support, and exposes direct-process shutdown broadcast/waiting
  - `shutdown.ts` — the single idempotent graceful-shutdown orchestrator shared by the UI endpoint and SIGTERM/SIGINT handlers; it stops batch scheduling, drains direct FFmpeg, closes SQLite, and runs only the controlled LiteLLM stop script
- **`components/`** — React UI (workbench tabs, shot panels, video panels); `components/mixcut/` is the formal fifth-step “智能混剪” workspace, while `components/final-edit/` retains shared preview, inspector, and Canvas editing primitives
- **`data/`** — Local SQLite DB (`workbench.db`, gitignored)
- **`storage/`** — Uploaded assets & generated outputs (gitignored)

### Data flow

1. User creates project → uploads scene/input images → sets prompt & model
2. Job submitted to provider, stored in `jobs` table with polling state (`lastPolledAt`, `pollCount`, `maxAttempts`)
3. Queue polls provider status asynchronously; on completion, image downloaded and normalized via Sharp
4. Results stored in `image_assets`, organized into `shot_sets` → `shots` → `shot_result_candidates`
5. Scripts generated via LLM providers; video jobs created from shots
6. Final edit analyzes selected video, generates narration and aligned subtitles, builds timelines, and renders output through FFmpeg
7. Project artifacts, including historical storyboard candidates, can be exported as ZIP

### Desktop packaging

- `scripts/build-win-installer.ps1` and `scripts/build-mac-installer.sh` each run the production build, compile the Electron main/preload payload, download a matching private Node runtime, and assemble a self-contained Electron installer. Windows keeps the Inno Setup wrapper; macOS copies the Electron runtime and uses `installer/macos/Info.plist` as metadata. The legacy launcher sources remain only as historical/dev resources and are not packaged.
- Both installer scripts run `npm ci` first (unless their explicit skip flag is used); on the normal branch, if the Electron runtime is still missing, they explicitly run `node_modules/electron/install.js` with the current Node and then perform the hard existence assertion. Skip branches do not install Electron automatically. macOS ATS is limited to `NSAllowsLocalNetworking`; the Electron service records its loopback `origin` and `instanceId` in `CREATIVE_STUDIO_DATA_ROOT/storage/run/electron-service.json` and removes that exact state on stop. The Windows installed-stop script validates that state against `/api/desktop/health`, then requests `/api/shutdown` before its bounded `taskkill /T /F` fallback.
- macOS builds are Apple Silicon-only and must run on an arm64 Node 22.x host — the bundled runtime is pinned to a specific Node 22 build, and a mismatched major version or x64 Node under Rosetta breaks the native module ABI for `better-sqlite3`/`sharp`. Release builds require a Developer ID identity plus a `notarytool` keychain profile; `--allow-adhoc` is explicitly local-only.
- Installer payloads must not leak local data, credentials, or dev-only paths (`data/`, `storage/`, `outputs/`, `docs/`, `scripts/`, `.git/`, `.env*`, `config.yaml`, `.venv-litellm/`, `python-runtime/`); the build scripts prune them and then assert none remain before packaging. `python-runtime/` ships only in the Windows portable package (whitelist assembly) — never in Git, Inno/DMG installers, or the standalone output. Both platforms require bundled FFmpeg. On macOS the installer verifies an arm64 FFmpeg and removes the currently mislabeled x86_64 `ffprobe-static` payload, relying on the tested FFmpeg metadata-probe fallback; Windows still requires its native ffprobe binary.
- `app/api/shutdown` exposes a graceful `POST` shutdown endpoint used by the Electron service supervisor; explicit app quit stops the service and then falls back to process-group/tree termination. Windows' installed stop script targets only the matching `CreativeStudio.exe` path, and user data lives below `CREATIVE_STUDIO_DATA_ROOT` or the platform app-data directory.
- `MACOS.md` covers the macOS installer's user-facing install/uninstall/data-location instructions.

### Key conventions

- **Provider adapter pattern**: All three provider layers (image/script/video) use adapters — add new suppliers by implementing the adapter interface, not modifying core logic.
- **Database migrations**: Keep published `CORE_DB_MIGRATIONS` and `FINAL_EDIT_MIGRATIONS` entries unchanged. Existing core tables retain the append-only legacy stream; final edit and batch production have separate versioned streams. Batch migrations and the legacy video-provider table rebuild must pass the shared lock, validated-backup, and audit gate; never place them in the legacy catch-and-continue core runner.
- **Cost tracking**: Each job stores estimated cost; providers expose a cost calculation method.
- **`projects.concurrency`** controls max parallel job submissions per project.
- **`.env.local`** holds LLM API keys (Gemini, Qwen, Kimi, GPT) and the Tencent COS credentials (`CREATIVE_STUDIO_COS_*`) — never commit this file.
- **`docs/`** holds design/review/session-summary records; `outputs/` holds phase specs, test checklists, and delivery records; `docs/superpowers/{specs,plans}/` holds spec-driven planning docs for larger features.
- UI language is Chinese; key domain terms: 项目 (project), 分镜 (shot/storyboard), 场景图 (scene image), 脚本 (script).
